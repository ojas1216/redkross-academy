## Introduction and conceptual foundation

Security orchestration, automation and response, or SOAR, describes a way to coordinate investigative work and, when authorised, defensive actions. A security process often passes through several tools. For example, an alert enters an analyst queue, an asset directory supplies a business owner, an analyst decides whether to open a case, and an endpoint responder confirms the result of any approved change. The purpose of automation is to remove predictable repetitive work and make these handoffs observable. A workflow still needs human accountability for decisions whose authority or evidence cannot be inferred from its input.

Start with the problem, not the catalogue of tools. A shift may spend a long time identifying duplicated alerts and attaching the same information to several tickets. The work is repetitive, but the appropriate solution depends on what constitutes a duplicate, which system owns the final case, and what happens when a late event adds new evidence. A product connecting the systems does not answer those questions. A defensible design writes down the contract first so analysts can test whether the integration does what they need.

## Distinguish capabilities

Orchestration is the coordination of activities across components or people. A workflow might accept an alert from a source, use an internal inventory to obtain an asset owner, and send an analyst a case link. The workflow describes how one step's result becomes another step's input. Automation means that some of these activities run without a person repeating them manually. An approved decision can still be taken by a human after an automatic enrichment step. Conversely, an employee moving between tools manually may perform an orchestrated process without a central automation engine. The concepts overlap, but the difference matters when describing which decisions are already governed by code.

Response functions may change state, such as assigning a case or applying a protective restriction with the authorised service. These functions deserve controls proportionate to their impact. Writing a draft task in a training case is a different risk from making a change to a production identity. A workflow owner should classify each activity by what it can disclose or change, who is affected, and whether the outcome can be verified or undone. A read-only look-up is not always risk-free. Sending a restricted identifier to an external service can still disclose information. An internal connector with limited read access may be appropriate for routine use while a higher-impact action waits for approval.

The event source, workflow engine and case record have different responsibilities. The source supplies a record that an event occurred or an alert was generated. The engine records execution state, such as which action ran or was skipped. The case system records the investigation, assessment, decisions and ownership. A workflow must maintain links between these records. If an analyst sees only a workflow status of completed, they may not be able to tell which case was updated or whether a person reviewed the decision. If the link is recorded only in a private workflow variable, the next shift may need a manual search. Decide early which system is the source of truth for each kind of state.

## Describe a workflow contract

The contract begins with the trigger. A trigger can be a valid synthetic alert in a training exercise, a human marking a case ready for review, or a scheduled reconciliation in an authorised system. Define the required fields. A simple intake requires a stable source identifier, an event identifier, an event time in a common time base, and a typed entity. Define how missing or invalid inputs are recorded. Treat arbitrary inputs as data. A field containing unrecognised text must not become a command, destination or approval. If the caller is a system, the owner should know how its identity and expected scope are established.

The contract describes each branch and output. A first valid event can create a case draft. A duplicate can link the receipt to an existing case. A missing entity can go into a manual review queue. If a trusted inventory source is unavailable, the case can retain the alert and explicitly record that enrichment could not be completed. The branch labels should identify why the next step ran. For example, ?inventory unavailable? is more useful than ?false? because the alert has not become a verified benign result. A workflow can finish cleanly after producing a pending manual decision. Its definition of success should distinguish reaching an intended state from completing every possible action.

A contract should specify freshness and versioning. An alert replay from last week may still be relevant for investigation but might no longer justify the same action automatically. One team may update its entity schema while another team still sends an older format. Preserve the source format and use a clear version to select a mapping. A workflow can accept older formats deliberately or route them to review. Changing the interpretation without changing the version can make past evidence impossible to reproduce. Record the workflow version next to the case effects so a future reviewer can explain why two otherwise similar events were treated differently.

The recorded source and timestamp let an analyst spot stale context and update the decision before any approved change. The structure supports rapid processing and a clear review when data disagrees.

## Handle event retries and partial results

An incident coordination system should anticipate retries. The sender might deliver the same event after a timeout. One workflow step might create the draft case successfully and then lose the receipt. If the engine retries the entire workflow without identifying the prior effect, it can create additional cases and confuse the next shift. A stable key based on the source and event identity lets the workflow recognise the same intended effect. Include the intended action or scope when storing a key for a distinct effect. Two genuinely different observations concerning the same endpoint should not become duplicates simply because they share a device name.

Idempotence is the property that repeating an operation for the same intent leaves the appropriate result rather than creating it again. It does not mean every network request should run only once. An engine may retry a read or record a second receipt. It should avoid repeated state changes when it can determine the existing result. For a case draft, lookup by stable correlation key can provide that assurance. If a remote system cannot return a reliable existing result and an earlier call may have succeeded, it is appropriate to stop and ask for reconciliation. Repeating a high-impact action blindly can produce a second change or modify a newly restored system. Record unknown outcomes explicitly.

A completed step, a completed workflow and a resolved incident are different states. A workflow can attach inventory information and move a case to the analyst queue while identity verification remains open. It can also stop at an approval gate and still achieve its purpose of preparing a decision. Label each operational state clearly. For review, preserve the input reference, branch reason, state transitions, timestamps, output references and owner. Use a short fixed reason for machine counts and a longer human explanation if needed. Avoid recording secrets and full artifact contents in execution logs by default. Keep the data needed to reproduce the action and link to restricted stores for sensitive detail.

## Worked example: a narrow intake improvement

Consider a fictional control room that receives the same VPN risk notification twice during a short interruption. The first copy has a source name, an alert ID and an account identifier. A permitted internal directory can associate the account with a business unit. There is no evidence of a verified affected device in the source. The team designs an intake workflow that validates the event, checks for an earlier identical event ID, looks up only the business unit and creates a draft case. It does not decide whether the account is compromised. It records missing session and device context for an analyst to investigate.

On the first receipt the directory is available and the workflow creates case R-29. On the second receipt the engine finds that the exact event already produced R-29. It records a duplicate receipt and returns the same reference. A different alert about the same account five minutes later has its own event ID. It is not a duplicate receipt. The workflow can route it to an analyst for association with R-29 or, if policy allows, correlate it while retaining a separate event reference. That distinction prevents the duplicate control from discarding new evidence. The exercise is about availability and workflow behaviour, not how the alerts were generated.

If the inventory system is unavailable, consider which work the SOC can still do. It has a valid alert and an account identifier. It can create a draft with an explicit missing context state or send the alert to manual review. The choice depends on the organisation's case rules. Which choice matters less than defining it and verifying it. An incoming analyst can check the account and escalate as appropriate without relying on a false claim that the directory returned no affected assets. If context arrives later, associate it with the original case and note the update. This avoids oscillating case status just because one supporting service failed temporarily.

## Design an acceptance check

Define a positive example, a benign or no-action example, a duplicate, a malformed input and an unavailable dependency. For each, specify the expected case state and the evidence you will inspect. The positive example produces one case draft with the expected reference. The duplicate produces no second draft and remains visible as a receipt. The malformed input routes for review with no response action. The unavailability case records the lookup status and a task to recover it. A no-action example can still produce a useful auditable result when its reason and supporting evidence are clear.

Add one case that arrives late. Ask whether it should be investigated, attached to an existing case, or allowed to trigger a fresh operational change. Have the owner record thresholds, evidence gaps and who can approve an exception. Use a paper execution or mock services before granting a connector any live reach. An owner who cannot specify what stopping safely means is not ready to turn on the workflow. Test outcomes in the case system in addition to checking a green execution indicator. Train analysts to locate where decisions, pending work and verification results appear without guessing.

## Practical exercise

On paper or in a local worksheet, define the workflow for the fictional VPN alert above. Draw a table with columns for input state, validation, case effect, next owner and acceptance evidence. Include a new alert, one retry of that same alert, an unrelated alert for the same account, a missing event ID and a directory timeout. For the first valid alert, write one sentence describing the case created and why no device change has been approved. For the retry, show how the reviewer checks that there is still exactly one case.

Now exchange the worksheet with a peer. Ask them to mark any step where an undefined condition would allow a side effect. In a second pass, examine whether a known completion or a pending state is captured correctly. For example, a workflow awaiting a human action should have a notification destination, an owner and a time for review. A workflow that completed its intake function does not need to pretend that an incident is closed. The exercise is successful when a peer can reproduce each decision, find its record, and state how they would verify any eventual protective action.

## Choose the first workflow to automate

Compare two candidate tasks before investing in connectors. Repeating a lookup of a stable device ID and attaching the result to a restricted case is a good candidate when the inventory has an owner, reliable access and a clear unknown state. Deciding whether to disrupt a production service is a poorer candidate for automatic execution when each case relies on different evidence and authority. The latter can still benefit from automatically arranging the evidence in a decision request. Split the repetitive preparation from the decision and name the value of each.

Do not measure the value only in analyst seconds saved. Ask how long a person spends correcting wrong ownership, reconciling repeats or tracing unverified effects. A first controlled playbook can add visible error reporting and consistent case references, even if it initially does not speed up every case. Record a baseline before deploying and compare the same type of work afterward. Keep the cases that could not be processed in the comparison. They may reveal more about required training or data quality than the successful majority.

Also define a retirement path. If the inventory is replaced, verify that the next version supplies the same identifier and scope. Disable automatic downstream actions while the mapping is uncertain, and retain a manual queue for legitimate incoming cases. A runbook should name the owner of the decision to disable or restore the connector and explain how they will reconcile events from the interruption. A workflow that can be paused and recovered with predictable handoffs offers better operational control than a feature whose only states are deployed and forgotten.

## Key takeaways

- Define what the trigger supplies and what each branch is allowed to produce.
- Keep source records, workflow execution and incident decisions linked and distinct.
- Make retries, missing data and unresolved effects visible to the analyst.
- Verify the case outcome and apply human authority where impact or uncertainty requires it.
