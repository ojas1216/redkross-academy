## Lab objective

Use a local simulator to check whether an incident automation design creates one authorised training task, records repeats correctly, and leaves invalid or unapproved inputs for an owner. This exercise models a SOC case workflow with fictional records. The only effect is a dictionary entry in the running Python process. No external applications, live connectors, credentials, accounts or endpoint controls are used. The task is to produce observations and a short handoff explaining what the simulator proved and what a real deployment would still need.

A starter worksheet should have columns for input identity, requested effect, expected path, actual state, observed effect and reviewer. Include a place for conditions that the simulator does not model. For example, the exercise uses strings from fixed fixtures to represent approval status, while a real decision mechanism needs authentication, role and scope verification. When you claim that a test passed, specify exactly which contract the fixture exercised. A reliable reviewer should not have to infer which parts are assumptions and which parts were executed.

## Predict the results first

The lab receives six records. The first is in scope and approved for creating a training review task. The second repeats the same intended effect. The third is valid but waiting for a decision, and the fourth has a denial. The fifth contains an unapproved target label. The sixth lacks an event identifier. The valid target names all belong to the fictional set in the program. Read those independently from the approval values, because an approved status in a record cannot broaden the accepted target set.

Write the expected outcome for all six inputs before running the simulator. Predict the number of distinct tasks, the number of receipts and which rows should contain a task identifier. Explain why the two A-17 rows can legitimately carry the same reference. Then compare your expectations with the outcome after execution. This sequence guards against explaining a surprising result away after looking at the output. It also lets two readers compare their understanding of the intended rules.

In the worksheet, retain the difference between invalid and unapproved. A missing event ID or an out-of-scope target is recorded as a review-input outcome. A pending decision is a valid record that needs an approving role. A denial says the proposed effect cannot proceed on the current request. If later evidence requires a new request, that occurs in a new decision record. These separate paths let an operator assign work to the source owner, lead or responder as appropriate rather than dumping every stopped run into the same queue.

## Run the simulator

The script below uses only the Python standard library and reads no external input. Run it as written in a local Python environment. The approved decision is an attribute of a trusted exercise fixture. Treat it as a simulation of a prior review, not a mechanism for accepting permission from incoming production events.

```python
from collections import Counter

tasks = {}
audit = []
fixtures = [
    {"event": "A-17", "target": "LAB-41", "decision": "approved"},
    {"event": "A-17", "target": "LAB-41", "decision": "approved"},
    {"event": "A-18", "target": "LAB-43", "decision": "pending"},
    {"event": "A-19", "target": "LAB-42", "decision": "denied"},
    {"event": "A-20", "target": "EXTERNAL", "decision": "approved"},
    {"target": "LAB-41", "decision": "approved"},
]
allowed_targets = {"LAB-41", "LAB-42", "LAB-43"}

for row in fixtures:
    event = row.get("event")
    target = row.get("target")
    verdict = row.get("decision")
    key = (event, target, "training-review-task")
    task_id = "-"
    if not event or target not in allowed_targets:
        state = "review_input"
    elif verdict == "pending":
        state = "awaiting_approval"
    elif verdict != "approved":
        state = "not_approved"
    elif key in tasks:
        state = "existing_task"
        task_id = tasks[key]
    else:
        state = "created_task"
        task_id = f"T-{len(tasks) + 1:03d}"
        tasks[key] = task_id
    audit.append((event or "-", target, state, task_id))

for item in audit:
    print(*item)
print("Tasks:", len(tasks))
for state, count in sorted(Counter(row[2] for row in audit).items()):
    print(state, count)

assert len(audit) == 6
assert len(tasks) == 1
assert audit[0][3] == audit[1][3] == "T-001"
assert all(row[3] == "-" for row in audit[2:])
```

```text
A-20 EXTERNAL review_input -
- LAB-41 review_input -
Tasks: 1

existing_task 1
not_approved 1
review_input 2
```

Each row has an event, target, state and task reference, using a dash when the event or task is unavailable. The final counts summarise audit rows rather than inventing additional effects. Check that the same task appears on the two A-17 rows. Then check that the remaining four rows carry no task identifier. The assertions show one observable execution contract: exactly one task from the given inputs and no additional effect from any other row. The input state strings also explain each no-action result so the receiving reviewer can determine whether it needs follow-up.

The program checks the scope before it enters the approval decision. That order is important. The out-of-scope row can say approved in this synthetic record and still cannot create a task. In a deployed system, an approval claim should be verified against a trusted record separate from the source event. The simulator trains the logic without implementing an authorisation service. It ends with in-memory state, so it demonstrates repeat handling within one run. It cannot establish protection across processes or restarts.

**Fourth variation, model an uncertain result on paper.** Assume a simulated case service accepts a request and the client loses its receipt. Write the expected record as effect unknown. It also helps separate the success of a workflow from the completion of an incident.
