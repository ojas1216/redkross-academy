## Introduction and conceptual foundation

Lesson 3 placed an "internal threat-intelligence platform" at stage 3 of the enrichment cascade: a curated, marked store of indicators that the SOC trusts more than general reputation services and that never sends a query outside the organisation. This lesson looks inside one widely used example of such a platform, **MISP**.

MISP is an open-source threat-intelligence and sharing platform. The name originally stood for *Malware Information Sharing Platform*; the project has long since grown beyond malware and now presents itself as an open-source threat intelligence and sharing platform. It is developed as a community project with substantial support from CIRCL, the Computer Incident Response Center Luxembourg, and is used by national CERTs, sector ISACs, managed security providers and individual SOCs. Its purpose is twofold: to **store** structured information about threats in a way that tools and analysts can query, and to **share** that information with exactly the partners who should receive it.

For a SOC analyst, MISP matters in three ways:

1. **As a source.** Feeds and partner communities arrive as MISP data. Understanding the data model is what lets you read an indicator's context, confidence and sharing restrictions correctly, instead of seeing only a bare value.
2. **As a memory.** Every case the SOC closes produces indicators, behaviours and conclusions. Recorded in MISP, they correlate automatically with tomorrow's data, which is how an organisation stops re-learning its own incidents.
3. **As a sharing channel.** When Banyan's SOC finds something its sector peers should know, MISP is the mechanism that delivers it under controlled distribution, with the right markings.

This lesson explains the concepts that every MISP user meets: **events, attributes, objects, tags and taxonomies, galaxies, distribution and sharing groups, and correlation**, plus the publishing and feedback mechanisms that tie them together. It describes how MISP organises information, not the exact layout of any particular version's screens or the literal text of its API responses; those change between releases, and the official MISP documentation and training material are the reference for them.

> The course lab kit does not include a MISP instance, so this lesson contains no MISP screenshots or API output. The examples map the kit's real `ioc_match.py` feed and the Banyan case onto MISP concepts. If you install MISP to practise, do it in an isolated lab with fictional data only.

## Key terminology

| Term | Precise meaning in MISP |
| --- | --- |
| Event | The container for one coherent piece of intelligence: an incident, a report, a campaign observation or a feed batch. |
| Attribute | One typed value inside an event, such as a domain, an IP address or a file hash, with a category, a comment and sharing settings. |
| Category | The broad role of an attribute in the event, for example *Network activity* or *Payload delivery*. |
| Type | The precise kind of value, for example `domain`, `ip-src`, `ip-dst`, `url` or `sha256`. |
| IDS flag (`to_ids`) | Marks an attribute as suitable for automated detection; detection exports normally include only flagged attributes. |
| Object | A group of attributes built from a template (for example a *file* object holding filename, size and hashes) so that values that belong together stay together. |
| Tag | A label on an event or attribute; machine tags from **taxonomies** have the form `namespace:predicate="value"`. |
| Taxonomy | A shared, versioned vocabulary of machine tags, such as the TLP taxonomy or the Admiralty scale. |
| Galaxy / cluster | A galaxy is a knowledge base of higher-level concepts (threat actors, malware families, ATT&CK techniques); a cluster is one entry in it. |
| Distribution | The setting that controls how far an event or attribute travels between organisations and connected MISP instances. |
| Sharing group | A named list of organisations (and optionally instances) allowed to receive specific data. |
| Correlation | MISP's automatic linking of attributes with the same value across different events. |
| Sighting | Feedback recorded against an attribute: it was seen, it was a false positive, or it has expired. |

## The data model: events and attributes

### Events

An **event** is the unit of intelligence in MISP. It answers the question *what is this information about?* One phishing campaign observed by an ISAC is one event; one intrusion investigated by a SOC is one event; one day's batch from a feed may be one event. Everything else in the data model hangs off an event.

An event carries descriptive and control fields:

- **Info**: a short title, which should say what happened to whom and when, without naming internal systems unnecessarily ("Loader delivered via look-alike payroll domain, microfinance sector, Nov 2026").
- **Date**: the date the event refers to.
- **Threat level**: one of High, Medium, Low or Undefined, the producer's view of the threat's seriousness.
- **Analysis**: Initial, Ongoing or Completed, which tells consumers how mature the information is. An event marked *Initial* should be read as early, possibly wrong, information.
- **Distribution**: how far the event may travel, described later in this lesson.
- **Creator organisation and owner organisation**: the organisation that created the information and the organisation that owns this copy on this instance. When an event is synchronised to another MISP instance, the creator remains the original producer, which is what lets a consumer judge the source.
- **Published state**: whether the event has been released for sharing and notification.
- **UUID**: a globally unique identifier, so the same event can be recognised across instances and exports.

### Attributes

An **attribute** is one atomic piece of information within an event. Each has a **category**, a **type**, a **value**, an optional **comment**, an **IDS flag**, its own **distribution** (which can inherit the event's or be more restrictive), timestamps and, in current versions, optional *first seen* and *last seen* times.

Category and type together say what the value means. A `domain` in category *Network activity* is a domain the malware or actor communicates with; a `url` in category *Payload delivery* is where a malicious file was downloaded from; a `sha256` in category *Payload delivery* or *Artifacts dropped* is a file hash at a particular stage of the intrusion. Choosing these well is not bureaucracy: a consumer's detection export may include *Network activity* domains for proxy blocking while excluding *External analysis* references, so a mis-categorised attribute either never reaches the control that needed it or reaches one where it causes false positives.

Direction matters for addresses. MISP distinguishes `ip-src` (an address seen as the source of activity, such as a scanning or spraying host) from `ip-dst` (an address the victim connected to, such as command-and-control). In the kit's feed, `203.0.113.66` is a source: it sent the VPN login attempts. Recording it as `ip-dst` would send a consumer looking in the wrong field of their logs.

The **IDS flag** (`to_ids`) is the single most consequential attribute setting for a SOC. It states that the producer considers the value specific enough to drive automated detection. A command-and-control domain registered for one campaign deserves it. An address on shared hosting, a legitimate file-sharing domain used once in an attack, or a value kept only for context does not, because automated matching on it will produce noise. Lesson 3's pipeline should match all attributes for enrichment but generate alerts or blocks only from flagged ones, and should still apply its own allowlists and validity checks.

### Objects

Some facts only make sense together. A malicious file is a filename, a size and several hashes; a phishing e-mail is a sender, subject, reply-to address and attachment; a web request is a URL, a host name and an address it resolved to. Storing these as unrelated attributes loses the fact that they describe the same thing.

**Objects** solve this. An object is created from a **template** (MISP maintains a shared library of object templates, such as *file*, *url*, *domain-ip* and *email*) and holds a set of attributes that belong together. Objects can be linked to each other by **object references**, each with a relationship type, so an event can state, for example, that a file object was downloaded from a URL object. Objects make events richer and easier to export into structured formats such as STIX 2.1, which also models intelligence as objects joined by relationships.

### Tags, taxonomies and galaxies

**Tags** label events and attributes. Free-text tags are possible, but MISP's strength is **taxonomies**: shared vocabularies of **machine tags** written as `namespace:predicate="value"` (some taxonomies, such as TLP, use just `namespace:predicate`). Because the vocabulary is shared, a tag means the same on every instance and can be acted on by tools. Examples a SOC meets constantly:

- **TLP**: `tlp:amber`, `tlp:green`, `tlp:clear` and the other TLP 2.0 levels, stating how recipients may further share the information (Lesson 7).
- **Admiralty scale**: tags for source reliability and information credibility, the grading scheme from Lesson 2, for example a source graded *B* (usually reliable) with information graded *2* (probably true).
- **PAP**, the Permissible Actions Protocol: tags stating what recipients may *do* with an indicator, for example whether they may actively query it on external services or only use it passively. This connects directly to the privacy gate of Lesson 3.

**Galaxies** carry higher-level knowledge. A galaxy is a collection of **clusters**, each describing a concept in depth: a threat actor with its aliases, a malware family, a tool, a sector, or a MITRE ATT&CK technique. Attaching a cluster to an event (or an attribute) says "this relates to that concept". For a SOC the ATT&CK galaxy is the most immediately useful, because it links indicators, which change, to behaviours, which do not: an event tagged with ATT&CK technique T1204.002 (User Execution: Malicious File) tells a detection engineer which behaviour-based rule should also fire, whatever the next campaign's domain is.

**Relationships and arrows.** Arrows from *Event* to *Attribute* and *Object* are labelled **contains**: an event owns its attributes and objects. The arrow from *Object* to *Attribute* is labelled **groups**, because an object's contents are attributes too, which is why object values correlate and export like any other attribute. The arrow from *Object* to *Object reference* shows that relationships hang off objects. Arrows from *Event* and *Attribute* to *Tag (taxonomy)* are labelled **tagged**, since tags can apply at either level, and the arrow from *Event* to *Galaxy cluster* is labelled **relates to**. The arrow from *Sighting* to *Attribute* points inwards, labelled **about**: sightings are created by consumers and recorded against an existing attribute.

**Execution flow.** A producer creates the event, adds attributes and objects, tags and attaches clusters, then publishes. Consumers later add sightings, which flow back to the producer through synchronisation where distribution allows.

**Decision logic.** At each attribute the producer decides category, type, IDS flag and distribution; at the event the producer decides threat level, analysis state and distribution. These are the choices that determine whether consumers can act safely.

**Technical interpretation.** Correlation and detection exports read attribute values and flags; sharing reads distribution; filtering and automation read machine tags. A value hidden in the event title or a free-text comment is invisible to all three.

**Practical example.** Banyan's intrusion becomes one event; `cdn-telemetry-sync.example` an attribute; the delivered `invoice.docm` a file object; `tlp:green` a tag; T1204.002 a galaxy cluster; and a peer's confirmation that the domain appeared in its proxy logs a sighting.

**Security implications.** A wrong `to_ids` flag turns context into blocking; a missing TLP tag removes the producer's sharing instruction; a mis-typed address sends consumers to the wrong log field.

**Key learning.** Put each fact in the element designed for it, because MISP's automation only sees what is in the model.

## Worked example: modelling the Banyan case

The kit's feed and the Banyan investigation give enough material to design a MISP event on paper. The table below is a modelling exercise, not an export from a MISP instance; it shows the decisions an analyst makes and why.

| Element | Choice | Reason |
| --- | --- | --- |
| Event info | Loader delivered via look-alike payroll domain, microfinance sector, Nov 2026 | Says what happened and to which sector without naming hosts or staff |
| Threat level / analysis | High / Ongoing | Confirmed intrusion; investigation still open |
| Attribute | `domain` `banyan-payroll-update.example`, *Payload delivery*, IDS flag on | Banyan's own finding, registered for this campaign |
| Attribute | `url` `https://banyan-payroll-update.example/invoice.docm`, *Payload delivery* | The exact delivery URL from the proxy log |
| Object | *file*: filename `invoice.docm`; hash added only if Banyan recovers the file | The vendor's hash is TLP:AMBER, and Banyan's telemetry holds no hashes |
| Attribute | `domain` `cdn-telemetry-sync.example`, *Network activity*, IDS flag on | Beaconing destination: 18 regular, equal-sized proxy requests |
| Attribute | `ip-src` `203.0.113.66`, *Network activity*, IDS flag off, last seen 2026-11-03 | Spraying source; addresses are cheap to change and may be shared |
| Not included | `198.51.100.104` | Expired open-feed entry that matched an ordinary employee session; not part of the intrusion |
| Tags | `tlp:green`, Admiralty grading for Banyan as source | Shareable within the sector community; consumers can weigh the source |
| Galaxy clusters | ATT&CK T1204.002, T1059.001, T1110.003 | Malicious file opened by user, PowerShell executed, password spraying |

Several decisions in the table deserve comment.

**Your own observations versus someone else's intelligence.** `cdn-telemetry-sync.example` was already reported by ISAC-A under TLP:AMBER. Banyan independently observed it in its own proxy logs, so Banyan may describe its own observation; but it must not copy ISAC-A's context ("C2 for loader seen in finance-sector phishing") into a TLP:GREEN event, because that text is ISAC-A's information under a more restrictive marking. The cleaner contribution is often a **sighting** on ISAC-A's existing attribute, which tells the producer and its community "this was seen here too" without redistributing anything. Copying another organisation's indicators into your own event under a looser marking is one of the most common, and most damaging, mistakes in intelligence sharing.

**The IDS flag follows specificity, not severity.** `203.0.113.66` was part of a serious attack, but an address is easy to change and may later belong to someone else. Leaving its IDS flag off, with a *last seen* time, gives consumers the context without causing automatic blocks weeks later. This mirrors the kit's feed, where the address carried the lowest validity window of the three live indicators and was the first to expire.

**Leaving things out is a decision.** The expired `198.51.100.104` is not part of the incident. Including it would spread a false association to every consumer.

**Behaviour travels further than indicators.** The three ATT&CK clusters are taken from the course's own detection content: the Sigma rule `rk_office_spawns_shell.yml` is tagged `attack.t1204.002` and `attack.t1059.001`, and `R2` detects VPN password spraying (T1110.003). A peer who never sees these domains can still check whether its behaviour-based detections would have caught the same sequence.

**Internal details stay internal.** The workstation name `WS-104`, the user names and the internal addresses belong in Banyan's case notes, not in a shared event. If the event is kept only inside Banyan's own instance, they may be recorded with distribution *Your organisation only*; they never go into a shared copy.

## Distribution and sharing groups

MISP enforces how far information travels with a **distribution** setting on every event and attribute. The levels are:

| Distribution level | Who receives it |
| --- | --- |
| Your organisation only | Users of the creating organisation on this instance |
| This community only | All organisations on this MISP instance |
| Connected communities | Organisations on this instance and on instances directly connected to it |
| All communities | Propagates across connected instances without a hop limit |
| Sharing group | Only the organisations (and instances) listed in a named group |

Attributes also have an *Inherit event* option, and an attribute can be more restrictive than its event, so a single event can share most of its content while keeping one sensitive value local.

A **sharing group** is the precise tool: a named list of organisations, and optionally specific MISP instances, permitted to receive the data. An ISAC might maintain a sharing group for its finance members; two banks investigating the same fraud campaign might create a group of just themselves. Sharing groups suit the many real situations where "everyone on the instance" is too wide and "only us" is too narrow.

Distribution and TLP are often confused, and the difference is fundamental. **Distribution is enforced by the platform**: MISP will not synchronise an event to an instance that the setting excludes. **TLP is an instruction to humans**: once a person can see the data, the TLP tag tells them what they may do with it outside MISP, in e-mail, tickets, reports and conversations. A TLP:RED event with distribution *All communities* is a contradiction that will leak; a TLP:CLEAR event restricted to *Your organisation only* simply under-shares. Set both, and make them agree.

**Publishing** is the release step. Creating or editing an event does not share it; publishing marks it as ready, which triggers synchronisation to connected instances within its distribution and, where configured, notifications to subscribed users. Many organisations require a second analyst to review an event before publication, checking exactly the issues in the worked example: internal details, inherited markings, IDS flags and distribution.

## Correlation

Correlation is the feature that turns a MISP instance from a filing cabinet into an analytic tool. When an attribute is added, MISP compares its value with the values of attributes in other events on the instance and records a link wherever the values match. Opening an event then shows which other events share values with it.

For the Banyan case, correlation would immediately link Banyan's new event to ISAC-A's earlier report through the shared value `cdn-telemetry-sync.example`. That link is exactly the corroboration Module 5 asked analysts to seek by hand: an independent producer reported the same infrastructure in a related context. Correlation also works across time. If, six months later, a new event from a different partner contains `banyan-payroll-update.example`, the analyst opening that event sees the link to Banyan's case without anyone remembering it.

Correlation in its basic form is **exact value matching**. It does not understand that a URL contains a domain or that two addresses are in the same network, although MISP offers optional, more expensive correlation modes for some types (such as address ranges) that an administrator can enable. Because matching is literal, the canonicalisation discipline from Lesson 3 applies here too: a domain stored with an upper-case letter or a trailing dot in one event and canonically in another may fail to correlate.

The weakness of exact correlation is **over-correlation**. Some values appear in huge numbers of events without meaning anything: public DNS resolvers, major content-delivery and cloud addresses, popular software update domains, the address of a widely used sandbox. Correlating on them links unrelated events and buries the meaningful links. MISP addresses this in three ways:

- **Warninglists**: maintained lists of values known to produce false positives (private address ranges, public resolvers, top-ranked domains, cloud provider ranges and similar). When an attribute's value is on a warninglist, MISP warns the analyst, and warninglists can also be used to filter matches out of detection exports. They play the role of stage 1 in Lesson 3's cascade.
- **Disabling correlation per attribute**: a producer can mark an attribute so that it is stored and shared but not correlated, appropriate for values kept for context only.
- **Correlation exclusions**: an administrator can exclude values or patterns from correlation across the whole instance.

**Relationships and arrows.** In the lower group the arrows converge: two attributes in different events feed one correlation, which produces one link. In the upper group the arrows describe a control path: a value is recognised as common, flagged by a warninglist, and then excluded from correlation or has correlation disabled. No arrow joins the two groups, because a value is handled by one path or the other.

**Execution flow.** When an attribute is saved, MISP checks its value against other events. If it matches and the value is specific, a correlation is recorded and appears in both events. If the value is on a warninglist, the analyst is warned when adding it, and the producer or administrator decides whether to keep it out of correlation.

**Decision logic.** The key judgement is specificity. A domain registered for one campaign links related intrusions; an address that half the internet uses links nothing.

**Technical interpretation.** Correlation compares stored values literally. Warninglists are checked against values on entry and can filter exports. Exclusions and per-attribute flags change what the correlation engine considers.

**Practical example.** Banyan's event correlates with ISAC-A's on `cdn-telemetry-sync.example`, giving the case independent corroboration. Had Banyan's analyst carelessly added the address of a public resolver seen in its DNS logs, a warninglist would have flagged it before it linked Banyan's event to thousands of others.

**Security implications.** Over-correlation wastes analyst time and can create false associations between unrelated incidents; under-correlation (inconsistent spelling, values buried in comments) loses real links. Correlations are leads, not conclusions: two events sharing an address on a cloud provider may involve entirely different actors.

**Key learning.** Correlation is valuable in proportion to the specificity of the values it links, so manage common values with warninglists and exclusions.

## Feeds, synchronisation, sightings and automation

**Feeds** are how MISP ingests external data. An instance can subscribe to feeds published in MISP's own format or in simpler formats such as CSV or free text, and can cache them so that their values correlate with local events without importing every feed entry as a full event. Lesson 5 of this module examines feeds and their pitfalls; for now, note that a feed's values arrive with whatever context, markings and quality the feed provides, and nothing more.

**Synchronisation** connects MISP instances. An administrator configures a link with another instance, and published events flow between them according to their distribution settings. This is how sector communities operate: each member runs or uses an instance, and the community instance relays what each member is allowed to share.

**Sightings** are the feedback channel. A consumer records a sighting against an attribute to say it was seen in their environment, that it was a **false positive**, or that it has **expired**. Sightings are cheap to give and very valuable to producers: a domain with sightings from five organisations is clearly active, and an indicator that several consumers have marked false positive should be reviewed or withdrawn. Lesson 3's pipeline should generate sightings automatically for confirmed matches and route false positives back through analysts.

MISP also supports scoring indicators down over time with configurable **decay models**, which apply the shelf-life idea from Lesson 1 so that old attributes count for less unless sightings refresh them.

**Automation.** MISP exposes a REST API, authenticated with per-user keys, and the project maintains PyMISP, a Python library for it. SOC pipelines use these to search attributes, pull detection exports (for example only IDS-flagged attributes of given types and tags), add sightings and create events from cases. Exports include MISP's own JSON format, STIX and formats for intrusion-detection systems. API keys carry the permissions of their user and should be scoped to the minimum role the integration needs, stored in a secrets manager and rotated.

## Common mistakes and misconceptions

- **Treating every attribute as a blocking indicator.** Only IDS-flagged, current, specific attributes should drive automated action, and even they pass through allowlists.
- **Re-sharing under a looser marking.** Copying a partner's TLP:AMBER indicator and context into your own TLP:GREEN event breaks the original producer's trust; add a sighting or ask the producer.
- **Confusing distribution with TLP.** Distribution controls where MISP sends data; TLP tells people what they may do with it. Both must be set and consistent.
- **Putting facts in free text.** Values in the event title or comments do not correlate, export or filter.
- **Ignoring analysis state.** An *Initial* event is early information; acting on it as if it were *Completed* invites mistakes.
- **Reading a correlation as attribution.** A shared value is a lead to investigate, especially on shared infrastructure.

## Security implications, detection and defence

A MISP instance concentrates sensitive information: your incidents, your partners' restricted reports and the identities of the organisations you trust. Treat it as a high-value system. Restrict administrative access, require strong authentication for users, scope and rotate API keys, keep the platform patched, and log user and API activity so that unusual bulk exports or searches can be noticed.

Quality is a security property too. An attacker who can publish into a community you trust, or a careless member, can push benign values with IDS flags set and cause disruptive blocks. Defend with the controls from this module: source grading through the Admiralty taxonomy, organisation-level trust decisions about which producers' IDS flags you honour automatically, warninglists, allowlists in your own pipeline, and review of high-impact actions before they reach blocking controls.

Finally, sharing obligations do not stop at the platform. In India, organisations report specified cyber incidents to CERT-In under its directions; MISP sharing with a sector community does not replace that legal reporting, and a shared event must not disclose personal data beyond what the purpose requires under the Digital Personal Data Protection Act, 2023.

## Best practices

- Model each fact in the right element: typed attributes, template objects, taxonomy tags, galaxy clusters.
- Set the IDS flag on specificity and current validity, with first-seen and last-seen times where known.
- Tag every event with TLP and set a matching distribution; use sharing groups for precise audiences.
- Give sightings, including false positives, back to producers.
- Use warninglists and correlation exclusions to keep correlation meaningful.
- Require a second-analyst review before publishing, focused on internal details, inherited markings and flags.

## Key takeaways

- MISP stores intelligence as events containing typed attributes and template objects, labelled with taxonomy tags and linked to galaxy clusters such as ATT&CK techniques.
- Category, type and the IDS flag decide whether a value reaches the right control; the IDS flag follows specificity and validity, not severity.
- Distribution is enforced by the platform; TLP instructs people. Use sharing groups for precise audiences and keep the two consistent.
- Correlation links events by exact value; warninglists, exclusions and disabled correlation keep it meaningful.
- Sightings, feeds, synchronisation and the API connect MISP to the SOC pipeline and return feedback to producers.
