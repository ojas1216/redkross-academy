## Introduction and conceptual foundation

By the end of Lesson 2 every event that reaches the SIEM has been parsed: the raw text of a firewall syslog line or a VPN JSON record has been split into named fields, and its timestamp has been converted to UTC. Parsing answers the question "what does this one record say?". It does not answer the question an analyst actually asks during an investigation: "show me everything this address, this user or this host did, across every source we collect". That second question is only answerable if the same idea is stored under the same name, in the same format, in every source. Turning many parsed vocabularies into one shared vocabulary is **normalisation**.

The problem normalisation solves is easy to underestimate. A Linux firewall writes the client address as `SRC=`. A VPN concentrator's JSON log calls it `clientIP`. Windows Security events call it `IpAddress`, a web proxy might call it `c-ip` or `client_ip`, and a cloud audit log might call it `sourceIPAddress`. Each of these is a correct parse of its own format. But an analyst who searches for `src_ip = "203.0.113.66"` will silently miss every source that used another name, and the SIEM will report "no results" with complete confidence. Unnormalised data does not fail loudly; it fails by returning partial answers that look complete.

Normalisation therefore has three jobs:

1. **Names.** Map each source-specific field name to one agreed field name (`SRC`, `clientIP` and `IpAddress` all become `source.ip`).
2. **Values.** Map each source-specific value to one agreed representation (`SUCCESS`, `Success`, `0` and `allowed` become `success`; `DROP` and `deny` become a common action; timestamps become UTC ISO 8601).
3. **Meaning.** Classify what kind of event this is (an authentication, a process start, a network connection, a web request), so that a search or rule can ask for "all failed authentications" without listing every product that produces them.

On top of a normalised event the pipeline usually adds **enrichment**: context that the original source never knew, such as who owns the host, how critical it is, which department the user works in, where an external address is registered and whether it appears in threat intelligence. Normalisation makes events comparable; enrichment makes them meaningful.

This lesson uses the Banyan Microfinance dataset from the course lab kit (`LAB_ASSETS/C08/banyan_events.jsonl`, 340 synthetic events from four sources) and the kit's normalisation demonstration (`LAB_ASSETS/C08/normalise_demo.py`). The next lesson, Correlation, depends entirely on what you build here: a correlation rule can only join events on a field that every source fills in the same way.

> [!NOTE]
> Parsing, normalisation and enrichment are often drawn as three boxes, and in many products they run in the same ingest pipeline. Keep them separate in your head: parsing extracts fields from one format, normalisation makes fields agree across formats, enrichment adds facts from outside the event.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Normalisation | Mapping source-specific field names, values and event types onto one common schema. |
| Common schema | A published dictionary of field names, types and allowed values that all sources are mapped to. |
| ECS | Elastic Common Schema: an open schema of dotted field names grouped into field sets (`source.*`, `user.*`, `host.*`, `event.*`, `process.*`). |
| OCSF | Open Cybersecurity Schema Framework: an open, vendor-neutral schema that organises events into categories and classes. |
| Field set | A group of related fields under one prefix, for example `source.ip`, `source.port`, `source.geo.country_iso_code`. |
| Categorisation fields | Fields that say what kind of event this is, in ECS `event.kind`, `event.category`, `event.type` and `event.outcome`. |
| Field mapping | The documented table that says which source field becomes which schema field, and how its value is transformed. |
| Enrichment | Adding context from outside the event (asset inventory, identity provider, geolocation, threat intelligence). |
| Ingest-time enrichment | Context written into the stored event when it arrives; fast to search, frozen at that moment. |
| Search-time enrichment | Context joined from a lookup table when a query runs; always current, costs work on every query. |
| Raw event | The original record as received, kept beside the normalised fields for evidence and re-parsing. |

## Why a common schema, and which one

A SIEM could, in principle, leave every source in its own vocabulary and push the problem to the analyst. Early deployments often did exactly that, and the result was a library of searches that each worked for one product. When the organisation replaced its VPN vendor, every VPN search and every rule that mentioned `clientIP` broke on the day of the migration, usually without anyone noticing. A common schema breaks that coupling. Searches, dashboards and correlation rules are written once against the schema; when a source changes, only its mapping changes.

Several schemas are in wide use:

- **Elastic Common Schema (ECS)** defines dotted field names grouped by what they describe. The client side of a connection is `source.*`, the server side is `destination.*`, the account is `user.*`, the machine is `host.*`, the program is `process.*`, and the event itself is described by `event.*`. It is used natively by the Elastic Stack and has become a common reference vocabulary well beyond it.
- **Open Cybersecurity Schema Framework (OCSF)** is a vendor-neutral open project, started in 2022 by a group of security vendors including AWS and Splunk. It organises events into categories (for example identity and access management, network activity, system activity) and classes within them, each class defining the attributes it carries.
- **Vendor models** such as the Splunk Common Information Model (CIM), which maps data into data models like Authentication, Network Traffic and Web, and Microsoft Sentinel's Advanced Security Information Model (ASIM), which uses parsers to present different products through one set of normalised tables and functions.

The schemas differ in detail but agree on the idea. The honest professional answer to "which schema is best?" is the same one the course library gives: **consistency matters more than which one you choose**. A SOC that maps every source carefully to a modest in-house schema is in a far better position than one that adopts ECS on paper and maps half its sources badly. This lesson uses ECS names for its examples because the lab kit does and because they are self-explanatory, but every idea transfers.

### How ECS thinks about an event

ECS is worth studying even if your platform uses another schema, because its structure teaches the questions normalisation must answer.

**Who and where.** The `source.*` and `destination.*` field sets describe the two ends of a network interaction. `source.ip` is always the initiator's address and `destination.port` the port it connected to, whatever the product called them. `host.name` is the machine on which the event was observed, and `user.name` the account involved. When an event involves a second account (an administrator creating a new user, for example), ECS keeps the acting account in `user.*` and the affected account in `user.target.*`, so that "who did it" and "who was it done to" never collide in one field.

**What ran.** The `process.*` field set describes a program: `process.executable` for the full path, `process.command_line` for its arguments, and `process.parent.executable` for the program that started it. Sysmon's `Image` and `ParentImage` and an EDR's `ProcessPath` and `ParentPath` all land here.

**What kind of event.** The `event.*` field set separates *description* from *classification*. `event.module` and `event.dataset` record where the event came from; `event.action` records the source's own verb (`drop`, `login`, `user-created`); `event.code` holds a source's identifier such as a Windows event ID. The categorisation fields then classify the event using a small, fixed set of allowed values: `event.kind` (for example `event` for an ordinary record, `alert` for something a detector raised), `event.category` (for example `authentication`, `process`, `network`, `web`, `iam`), `event.type` (for example `start`, `creation`, `denied`, `allowed`) and `event.outcome` (`success`, `failure` or `unknown`). Because the allowed values are fixed, a rule can ask for `event.category: authentication AND event.outcome: failure` and receive failed logons from Windows, the VPN, a cloud identity provider and a Linux SSH daemon in one result set.

**Bookkeeping.** `@timestamp` holds the event time in UTC. Fields that the schema does not define are not thrown away; they are kept under a source-specific namespace (Winlogbeat, for example, keeps Windows-only details under `winlog.*`), so nothing is lost while the shared fields stay clean.

> [!TIP]
> Learn the field sets, not individual fields. If you know that ECS describes the initiator under `source`, the account under `user` and the program under `process`, you can usually guess the exact field name correctly and then confirm it in the reference.

## Field mapping in practice

A field mapping is a written table, kept under version control, that states for each source: which raw field feeds which schema field, how its value is transformed, and what is deliberately left out. It is the contract between the people who onboard data and the people who write detections. If it is not written down, it exists only in the parser code, and nobody notices when a new hire maps the VPN's `clientIP` to `destination.ip` by mistake.

The lab kit's `normalise_demo.py` is a complete, small example. It takes two raw records that Lesson 2 parsed, a classic syslog line from a Linux firewall and a JSON record from the VPN:

```text
Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389
{"time":"2026-11-03T06:46:00Z","service":"vpn","user":"gopal","clientIP":"203.0.113.66","result":"SUCCESS"}
```

and emits each as an ECS-style event. Copy the kit to a working folder of your own and run it there (never run scripts inside the course library folder itself):

```terminal
$ python normalise_demo.py
{"@timestamp": "2026-11-03T06:46:21Z", "destination.ip": "10.40.0.5", "destination.port": 3389, "event.action": "drop", "event.module": "firewall", "host.name": "fw01", "network.transport": "tcp", "source.ip": "203.0.113.66"}
{"@timestamp": "2026-11-03T06:46:00Z", "event.action": "login", "event.module": "vpn", "event.outcome": "success", "source.ip": "203.0.113.66", "user.name": "gopal"}
```

`python normalise_demo.py` takes no arguments; both raw records are constants inside the script, and it prints one normalised JSON object per line with its keys sorted. Read the output as a list of decisions the mapping made:

- **Names converge.** The firewall's `SRC=` and the VPN's `clientIP` both became `source.ip`. The firewall's `DST=` and `DPT=` became `destination.ip` and `destination.port`; the device name `fw01` became `host.name`; `user` became `user.name`.
- **Values converge.** The VPN's `SUCCESS` became `success` (lower-case, the ECS allowed value for `event.outcome`). The firewall's `DROP` became the action `drop` and `TCP` became `tcp`. `DPT=3389` became the integer `3389`, not the string `"3389"`, so that a range query on ports works.
- **Time converges.** The firewall line said `12:16:21` with no year and no zone; the parser applied the device's configured zone (IST, UTC+05:30) and stored `06:46:21Z`. The VPN already logged UTC and was passed through.
- **Meaning is recorded.** The script adds `event.module` (where the event came from) and, for the VPN, an `event.action` of `login` that the raw record never stated; the mapping author knew that this VPN log only records login attempts.

The payoff is a single search. One filter, `source.ip: "203.0.113.66"`, now returns both events: the same address logged in successfully to the VPN as `gopal` at 06:46:00, and 21 seconds later the firewall dropped a remote desktop attempt (TCP 3389) from it. Neither source alone tells that story, and without normalisation the analyst would have needed to know two vendors' field names to find it.

**Purpose.** The figure is a field-mapping table: the written contract that turns several vendors' vocabularies into one. It matters because every search, dashboard and correlation rule later in this module is written against the left-hand column, and is only as good as the mapping that fills it.

**Components.** The table has four columns. *Common field (ECS)* is the target name. *Firewall syslog* and *VPN JSON* show the raw name each source used in `normalise_demo.py`. *minisiem column* shows the flat name under which the lab SIEM stores the same idea. Each row is one concept: `@timestamp`, `source.ip`, `user.name`, `host.name`, `event.outcome`, `event.action` and `destination.port`. The rows are tinted by tone: the time row is orange because time is the field every other operation depends on; the identifier rows that correlation joins on (`source.ip`, `user.name`, `host.name`) are blue; the classification rows are violet; and the port row, which only the firewall fills, is slate.

**Relationships.** Read each row as "these raw fields are renamed and transformed into that common field". A cell reading *not present* is as important as a filled one: the firewall has no user and no outcome, and the VPN record has no host. Those gaps are why a rule that joins on `host.name` will never see a VPN login unless enrichment (later in this lesson) adds one.

**Execution flow.** At ingestion the parser extracts the raw fields, the mapping renames them and converts values (case, type, zone), and the event is stored under the common names alongside its raw text.

**Decision logic.** For each raw field the mapping author decides one of three things: map it to a common field, keep it under a source-specific namespace, or drop it. In the demo, `kernel` and `IN=eth0` were not mapped to common fields because no search in this module needs them.

**Technical interpretation.** The `@timestamp` row hides the hardest transformation in the table: the firewall value `Nov 3 12:16:21` has neither year nor zone, so the mapping depends on configuration knowledge (the device runs in IST). The `event.outcome` row shows value normalisation: `SUCCESS` becomes `success`.

**Practical example.** Searching `source.ip: "203.0.113.66"` finds the VPN login and the firewall drop 21 seconds apart; in minisiem the same question is `WHERE src_ip = '203.0.113.66'`.

**Security implications.** A mapping error is a silent detection gap. If the VPN's `clientIP` were mapped to `destination.ip`, every rule that watches `source.ip` for sprayers would stop seeing VPN attacks and nothing would alert. Mappings must be reviewed like code and tested with sample events.

**Key learning.** Normalisation is a table of decisions; write it down, review it, and remember that empty cells are where correlation breaks.

## A flat schema in the lab: minisiem

Production SIEMs store hundreds of normalised fields. The lab's teaching SIEM, `LAB_ASSETS/C08/minisiem.py`, keeps only twelve, as plain SQLite columns, and stores the complete original JSON in a thirteenth column called `raw`:

```python
FIELDS = ["ts", "source", "event_id", "host", "user", "src_ip", "url", "outcome",
          "image", "parent_image", "bytes_out", "target_user"]
```

This is a normalised schema in miniature: every source is stored under the same twelve names, and anything else (`command_line`, `logon_type`, `status`, `country`, `group`) stays available in `raw`. The design is the same trade-off real SIEMs make: promote the fields you search and correlate on to fast, typed, indexed columns; keep the rest as evidence and so that you can re-parse when a format changes.

A normalised schema is only useful if you know which sources actually fill each field. After loading the dataset (`python minisiem.py load`, which prints `loaded 340 events`), this query counts, per source, how many events have a non-null value in each column. `COUNT(column)` in SQL counts non-null values only, which is exactly what we want:

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS n, COUNT(event_id) AS event_id, COUNT(host) AS host, COUNT(user) AS user, COUNT(src_ip) AS src_ip, COUNT(url) AS url, COUNT(outcome) AS outcome, COUNT(image) AS image, COUNT(bytes_out) AS bytes_out FROM events GROUP BY source"
source | n | event_id | host | user | src_ip | url | outcome | image | bytes_out
proxy | 284 | 0 | 284 | 284 | 284 | 284 | 0 | 0 | 284
sysmon | 33 | 33 | 33 | 33 | 0 | 0 | 0 | 33 | 0
vpn | 10 | 0 | 0 | 10 | 10 | 0 | 10 | 0 | 0
windows | 13 | 13 | 13 | 13 | 10 | 0 | 13 | 0 | 0
```

The `search` subcommand takes one argument, an SQL statement, runs it against `minisiem.db` and prints a header row and pipe-separated results. This small table is a **field coverage matrix**, and every SOC should keep one for its real sources. It tells you, before you write a rule, what that rule can and cannot see:

- `user` is filled by all four sources, so it is the only identifier you can join on everywhere.
- `host` is missing from every VPN event. A VPN login belongs to a person, not to a workstation, so a "same host" rule will never connect it to endpoint activity.
- `src_ip` is missing from Sysmon process events, so you cannot ask "which process made this connection" by address in this dataset.
- `outcome` exists only for VPN and Windows events; proxy requests record an HTTP `status` instead, which stays in `raw`.

## Value normalisation and its traps

Renaming is the easy half of normalisation. Making values mean the same thing is harder, and the Banyan dataset contains three classic traps.

**Placeholders that look like data.** Windows logon events carry a source address field even for interactive logons at the keyboard, and write a dash when there is none. The dataset keeps that dash. A query classifying every non-null `src_ip` shows what happens:

```terminal
$ python minisiem.py search "SELECT source, CASE WHEN src_ip LIKE '10.%' THEN 'internal' WHEN src_ip='-' THEN 'placeholder' ELSE 'external' END AS kind, COUNT(*) AS n FROM events WHERE src_ip IS NOT NULL GROUP BY source, kind"
source | kind | n
proxy | internal | 284
vpn | external | 10
windows | placeholder | 10
```

Ten Windows events hold the string `-` in an address column. Any rule that counts "events with a source address" or groups by `src_ip` will treat `-` as one very busy address. A good mapping converts placeholders such as `-` and `N/A` into a true null, so that "unknown" and "a value" can never be confused.

**Same name, different meaning.** The same query shows that `src_ip` in proxy events is always an internal `10.40.0.x` address (the workstation making the request), while in VPN events it is an external address (the remote user's or attacker's public IP). Both are correctly "the initiator", so both belong in `source.ip`, but a rule written as "alert on many failures from one `src_ip`" means something completely different on each source. Behind NAT or a proxy, many people share one address; on the VPN, one address may be one attacker. Normalisation fixes the names; it cannot remove the need to know your sources.

**Case and representation.** The dataset stores user names in lower case (`divya`, `gopal`), but Windows often reports `DIVYA` or `BANYAN\divya`, and a cloud identity provider reports `divya@banyan.example`. A search for `user = 'divya'` matches only the first form. Mature mappings normalise case and split the domain into its own field (ECS has `user.domain` for this), so that one person has one searchable identity. Where that is not done, analysts must use the platform's case-insensitive operators, and every rule author must remember to.

**Time, again.** Lesson 2 converted timestamps to UTC at parse time, and normalisation must guarantee that every source did. One source left in local time shifts its events by five and a half hours against everything else and turns a clean attack sequence into nonsense. Clock accuracy is part of the same problem: CERT-In's directions of April 2022 require Indian organisations to synchronise their ICT system clocks to the NTP servers of NIC or NPL (or to sources traceable to them), precisely so that logs from different systems can be lined up.

## Enrichment: adding what the source never knew

A normalised VPN event tells you that `gopal` logged in from `203.0.113.66`. It does not tell you that `gopal` is a sales employee with a standard account, that his usual laptop is `WS-107`, that the address belongs to no network Banyan has ever seen him use, or that a sector sharing group has reported the address for password spraying. Each of those facts changes what an analyst should do next, and none of them is in the event. Enrichment brings them in.

Typical enrichment sources are:

| Source of context | Fields it adds | Question it answers |
| --- | --- | --- |
| Asset inventory / CMDB | host owner, role, criticality, location | How much does this machine matter? |
| Identity provider / HR | department, title, manager, privileged flag | Who is this person and what may they do? |
| Geolocation and ASN data | country, city, network owner of an IP | Where is this address, and whose network is it? |
| Threat intelligence | indicator match, confidence, source, expiry | Has anyone seen this value doing harm? (Module 5) |
| Vulnerability data | open findings on the host | Could this activity exploit a known weakness? |
| Internal networks list | internal, VPN pool, DMZ, guest | Is this address ours, and which zone? |

The lab kit shows enrichment as an analyst would meet it. `LAB_ASSETS/C08/triage.py` (used fully in Module 4) holds small lookup tables that stand in for a CMDB and an identity provider, and adds their facts to every rule hit:

```python
ASSETS = {"WS-104": ("finance workstation", 3), "WS-107": ("sales laptop", 2)}
USERS = {"divya": ("Finance", "payments approver"), "gopal": ("Sales", "standard")}
PRIMARY_HOST = {"divya": "WS-104", "gopal": "WS-107"}  # VPN events carry no host
```

The third table is the important lesson. The field coverage matrix showed that VPN events have no `host`. `PRIMARY_HOST` fills that gap from identity data, so the VPN alert for `gopal` can be shown with his laptop and its criticality. The kit's saved triage output shows the effect on one line:

```text
 7.2  R2 vpn_spray_then_success  host=WS-107 (sales laptop) user=gopal (standard) ip=external (documentation range in this lab)
```

Every fact after the rule name came from enrichment: the host and its role from `PRIMARY_HOST` and `ASSETS`, the account type from `USERS`, and the address class from a small `ip_context` function that checks the address against the internal range `10.0.0.0/8`. Note also the honesty of the mapping: the inferred host is a *primary* host, an assumption that the analyst must confirm, not an observed fact. Good enrichment labels inferred context as inferred.

**Decision logic.** For each kind of context the architect chooses ingest-time or search-time enrichment. Ingest-time context (geolocation of an IP on the day it was seen) is fast to search and records what was true at that moment. The figure draws the ingest-time case; the alternative, search-time context (current owner of a host, current intelligence) joined from the same reference sources when a query runs against *Store*, is always up to date but costs work on every query and can rewrite history: a host reassigned last week will appear to have belonged to its new owner during an old incident.

**Technical interpretation.** In minisiem, `triage.py` is pure search-time enrichment: its dictionaries are consulted when the rules run, and nothing is written back into the `events` table.

**Practical example.** The VPN success for `gopal` from `203.0.113.66` enters without a host. *Enrich* adds the primary host `WS-107` and its role from the identity and asset data, classifies the address as external, and (in Module 5) matches it against the intelligence feed that lists it for password spraying.

**Security implications.** Enrichment sources are now part of your detection system. A stale CMDB mislabels a critical server as low priority; a compromised or poisoned intelligence feed can flood the queue or hide an attacker. Treat context sources as inputs that need owners, freshness checks and access control.

**Key learning.** Normalise first, then enrich on normalised keys; decide deliberately which context is frozen at ingestion and which is looked up live.

### Ingest-time or search-time?

Most SOCs use both. A reasonable rule of thumb is to enrich at ingestion with facts that describe the event at that moment and are expensive or impossible to reconstruct later (geolocation and ASN of an address, the asset's criticality at the time, an intelligence match that might later expire), and to enrich at search time with facts that should always be current (who owns the asset today, whether an account is now disabled). When you enrich at ingestion, record when and from which version of the reference data, so that an investigator months later can tell what the analyst knew at the time.

## Common mistakes and misconceptions

- **"We adopted ECS, so we are normalised."** A schema is a vocabulary. Normalisation is the mapping of each source onto it, and that is where mistakes live. Audit mappings source by source.
- **Mapping by name instead of by meaning.** A field called `src` in one product is the client; in another it is the device that generated the log. Read the vendor's field documentation and test with known events.
- **Dropping unmapped fields.** If a field has no common name, keep it under a source namespace or in the raw event. The field nobody needed this year is the one an incident needs next year.
- **Leaving placeholders as values.** `-`, `N/A` and empty strings must become nulls, or counts and joins will be wrong, as the Windows `src_ip` example showed.
- **Treating enrichment as fact.** Geolocation of an address is an estimate, a primary host is an assumption, intelligence has a confidence and an expiry. Present them as context, not proof.

## Security implications, detection and defence

Normalisation is a security control, and its failures are detection failures. Three practices keep it honest:

1. **Monitor the pipeline.** Count, per source, events that failed parsing or arrived with an empty key field (`source.ip`, `user.name`, `host.name`). A sudden rise in empty `user.name` from one source usually means the vendor changed its format. In ECS, events that failed processing can be marked with `event.kind: pipeline_error`, which makes them searchable instead of invisible.
2. **Test mappings like code.** Keep a small set of sample raw events per source and the normalised output they must produce; run them whenever a parser or mapping changes. Module 6 applies the same idea to detection rules with the kit's `test_rules.py`.
3. **Keep the raw event.** Normalised fields are an interpretation. The raw record is the evidence, and it lets you re-normalise history when you find a mapping mistake.

Enrichment brings personal data into the SIEM: departments, managers, locations. Under India's Digital Personal Data Protection Act 2023, personal data should be processed for a lawful, specified purpose and limited to what that purpose needs. For a SOC this means enriching with the identity attributes that security decisions need, restricting who can see them, and not turning the SIEM into a general employee-monitoring database.

## Best practices

- Choose one schema, publish the field mapping for every source, and version it.
- Normalise names, values, types, case and time; convert placeholders to null.
- Populate the categorisation fields (`event.category`, `event.type`, `event.outcome`) so that rules can be written by meaning rather than by product.
- Maintain a field coverage matrix and consult it before writing any rule.
- Enrich on normalised keys, label inferred context, and give every context source an owner.

## Key takeaways

- Normalisation maps names, values and meaning from every source onto one schema, so that one search or rule covers all sources.
- ECS organises fields into sets (`source`, `destination`, `user`, `host`, `process`, `event`); OCSF, Splunk CIM and Sentinel ASIM do the same job differently. Consistency matters more than the choice.
