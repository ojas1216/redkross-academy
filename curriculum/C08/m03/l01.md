## Introduction and conceptual foundation

Module 2 followed telemetry from the systems that produce it, through agents, forwarders, relays and queues, to the door of the SIEM. This module starts on the other side of that door. A **Security Information and Event Management (SIEM)** platform is the system in which a SOC stores events from every source, searches them, runs detection rules over them and investigates what those rules find. Everything it does later (parsing, normalisation, correlation, dashboards, search and retention, the subjects of the next six lessons) depends on one first step being done correctly: **ingestion**.

Ingestion is the work the SIEM does from the moment an event arrives to the moment that event can be found by a search. It sounds like plumbing, and much of it is, but it is plumbing with consequences. During ingestion the SIEM decides where one event ends and the next begins, which source the event came from, what time it will be filed under, which index or table it lands in (and therefore who can see it and how long it will be kept), and whether it is stored at all. Each of these is a decision about evidence. An event filed under the wrong time is invisible to a search of the right time window. An event routed to the wrong index is invisible to the rule that looks in the right one. An event dropped by an ingest-time filter is gone, and no later analysis can recover it.

Module 2 Lesson 7 already covered buffering, delivery guarantees and source-health monitoring; this lesson looks inside the SIEM's own ingestion layer. It asks what happens to an event before it becomes searchable, how much arrives and what that costs, and how you know ingestion worked, using the course's teaching SIEM, `minisiem.py`, on the Banyan Microfinance dataset, including deliberately breaking it in a copy of the kit.

> [!NOTE]
> "The SIEM" here means any platform in this role (Splunk, Elastic Security, Microsoft Sentinel, Wazuh, QRadar and others); platform-specific terms are flagged as such.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Ingestion | Everything the SIEM does between receiving data and making it searchable: receiving, splitting into events, identifying the source, assigning time and metadata, routing, writing and indexing. |
| Input / listener | The SIEM-side endpoint that accepts data: a syslog port, an HTTP collector endpoint, an agent connection or an API connector. |
| Event breaking | Splitting an incoming stream of bytes into individual events, for example one event per line, or one per multi-line stack trace or XML record. |
| Source type | A label saying what kind of data an event is (for example "Linux firewall syslog" or "Windows Security"). Splunk calls it `sourcetype`; other platforms use a dataset, table or log type name. It selects the parsing and time rules. |
| Event time | The time at which the event happened, taken from the event itself. |
| Ingest time | The time at which the SIEM received or indexed the event (Splunk records `_indextime`; the Elastic Common Schema defines `event.ingested`). |
| Index / data stream / table | The named storage container an event is written to. The container usually determines retention, access rights and which searches look there. |
| Routing | Choosing the container (and sometimes the storage tier) for each event at ingest time. |
| EPS | Events per second, the usual measure of ingestion rate. |
| Daily ingest volume | The amount of data ingested per day, usually in GB/day; many SIEMs are licensed or priced on it. |
| Ingest-time filtering | Dropping or trimming events inside the SIEM's ingestion layer before they are stored. |
| Onboarding | The controlled process of adding a new data source to the SIEM, including validation that it arrives complete, on time and correctly labelled. |

## Inside the ingestion layer

Every SIEM's ingestion layer performs the same ordered operations, each using the result of the one before.

### 1. Receive

An **input** accepts data. Typical inputs are a syslog listener (UDP or TCP, ideally TLS), an HTTP endpoint that accepts JSON posted by forwarders or applications (Splunk's HTTP Event Collector is the best-known example, authenticated with a token), a connection from the platform's own agents, and connectors that pull from cloud and SaaS APIs. Each input is configured with what it expects: the port or endpoint, the authentication it requires and, importantly, a **default source type** and **default index** for anything that arrives on it. Those defaults are the commonest source of mis-filed data: a new appliance pointed at an existing port inherits that port's defaults.

### 2. Break into events

A stream must be cut into events. For most single-line formats the rule is simple: one line, one event. It becomes difficult for multi-line records: a Java stack trace that spans forty lines, a Windows event rendered as XML, a JSON document pretty-printed over several lines. If the breaking rule is wrong, the SIEM produces forty one-line "events" from one stack trace (none of which makes sense alone), or merges several real events into one long one (so a count-based rule under-counts). Breaking also enforces limits: platforms impose a maximum event size and truncate or split beyond it, which matters for long PowerShell script-block events and large cloud audit records.

### 3. Identify the source and attach metadata

Each event is labelled with **where it came from** (the sending host and the input or file path), **what it is** (the source type) and **which container it belongs in** (the index, data stream or table). These labels are how the SIEM selects the right parser in the next lesson's sense, and how analysts scope searches. The `host` label deserves care: for data relayed through a syslog server or a collector, the "host" the SIEM sees may be the relay rather than the original device, unless the ingestion layer takes the host name from inside the message.

### 4. Assign event time and record ingest time

The SIEM extracts the event's own timestamp, using the time-format rules of its source type. Module 2 Lesson 6 covered the formats and the traps (classic syslog without a year or zone, local time, epoch values). Here the point is operational: **when the SIEM cannot find or understand a timestamp, it substitutes something**, typically the time of receipt or the time of the previous event from the same input. That substitution is silent. A batch of events from a device whose clock was wrong, or whose format changed, may be filed hours or years away from where an analyst will look. Good ingestion therefore records **both** times. The gap between them is the ingestion lag for that event, and an unusual gap is a signal that either the clock or the pipeline is wrong.

### 5. Route

Using the metadata, the SIEM decides which container receives the event. Routing is a security decision as much as a storage decision, because the container usually carries the **retention period**, the **access control** (who may search it) and the **performance tier**. Identity logs containing personal data may go to a container that only the SOC can read; high-volume, low-value data may go to a cheaper tier with slower search. Routing is also where ingest-time filtering usually happens: rules that drop, trim or divert events before storage.

### 6. Write and index

Finally the event is written to storage and indexed. Indexing builds the structures that make search fast: in search-engine-based SIEMs, an **inverted index** that maps each term or field value to the events containing it; in table-based platforms, columnar storage organised by time. Almost every SIEM organises storage by time first, because almost every search is bounded by a time range. Indexing is not instantaneous: most platforms make new data searchable after a short refresh interval, and under heavy load the delay grows. An event is not part of the SOC's evidence until this stage completes.

**Relationships and arrows.** The arrows run in one direction only, because each stage consumes the previous stage's output: you cannot assign a time to an event that has not yet been separated from its neighbours, and you cannot route an event whose source type is unknown. The direction is also the direction of dependency for troubleshooting: an error discovered at a later box is often caused at an earlier one.

**Execution flow.** Bytes arrive at **Receive**, are cut into events, labelled, timed, routed to a container and finally written and indexed. Only after the last box is the event returned by a search.

**Decision logic.** Every box contains a choice made by configuration, not by the event: which defaults an input applies, which breaking rule a source type uses, which timestamp pattern to try and what to substitute when it fails, which container and tier to use, and whether a filter discards the event. The side notes are the failure branches: wrong defaults, broken or merged events, a relay's name recorded as the host, a substituted time, data sent to the wrong index or dropped, and indexing delay under load.

**Technical interpretation.** The orange **Assign time** stage is highlighted because its failure is the hardest to see. The event is present, correctly labelled and searchable, but filed under the wrong time; a search over the right window simply does not return it. Recording ingest time beside event time turns this from an invisible problem into a measurable one.

**Practical example.** Banyan adds a second firewall and points it at the existing syslog input used by the first. Its events arrive and are written, so collection "works", but they inherit the first firewall's source type. The new model writes its timestamps differently, so the **Assign time** stage falls back to receipt time, and the events land in the default index. A rule that searches the firewall index for blocked connections never sees them.

**Security implications.** Inputs are an attack surface: an unauthenticated syslog port accepts forged events from anyone who can reach it, and a flood of junk can exhaust licence or storage. Routing and filtering rules are security controls and deserve change control and review.

**Key learning.** Ingestion is a chain of filing decisions. Check each one when a source is added, and record both event time and ingest time so that mis-filing can be detected.

## How real platforms organise ingestion

The stages are universal; the vocabulary is not.

**Splunk** forwarders send data to indexers; every event receives the default fields `host`, `source`, `sourcetype` and `index`, with event time in `_time` and indexing time in `_indextime`. The source type selects line-breaking and timestamp rules, so a wrong source type corrupts both. **Elastic** agents ship to Elasticsearch, where an **ingest pipeline** of processors can transform each document before indexing; data is commonly organised in **data streams** named by type, dataset and namespace, and the Elastic Common Schema puts ingest time in `event.ingested`. **Microsoft Sentinel** stores data in tables of a Log Analytics workspace, and **data collection rules** can transform records at ingest time with KQL; event time is `TimeGenerated`. **Wazuh** agents send events to the Wazuh manager, which decodes them and evaluates rules before alerts and archives are indexed for search; Lesson 8 uses it in the lab.

The table below lines the vocabulary up against the stages.

| Stage | Splunk | Elastic | Sentinel | minisiem (course kit) |
| --- | --- | --- | --- | --- |
| Receive | Forwarder inputs, HTTP Event Collector | Agent / Beats, Logstash inputs | Connectors, agent, data collection rules | Reads `banyan_events.jsonl` |
| Label source and type | `host`, `source`, `sourcetype` | Data stream dataset, `event.dataset` | Destination table | `source` field from the event |
| Event time | `_time` | `@timestamp` | `TimeGenerated` | `ts` copied from `@timestamp` |
| Ingest time | `_indextime` | `event.ingested` | Recorded by the platform | Not recorded |
| Container | Index | Data stream / index | Table in a workspace | One table, `events` |
| Ingest-time transform | Index-time configuration | Ingest pipeline processors | DCR transformation (KQL) | None |

## Index design: routing is a control

It is tempting to send everything to one place and let searches sort it out. Most mature SOCs do not, because the container an event lands in carries properties that matter long after ingestion:

- **Retention.** Containers usually have their own retention period. Firewall connection logs might be kept hot for 30 days and archived for longer; identity and administrative audit logs are often kept longer because investigations reach back further. In India, CERT-In's April 2022 directions require covered entities to retain ICT system logs for a rolling 180 days within Indian jurisdiction, so routing a regulated source into a short-retention container can be a compliance failure. Lesson 7 treats retention fully.
- **Access.** Logs differ in sensitivity. Proxy logs reveal what individuals browse; HR and identity data contain personal data protected under the Digital Personal Data Protection Act 2023. Separate containers allow access to be limited to those who need it.
- **Search performance and cost.** Searches that name a container scan less data. Separating a high-volume, low-value source keeps it from slowing down every search of high-value data.
- **Rule scope.** Detection rules usually name the container they search. If routing changes, rules must change with it, or they fall silent.

Route by **data type and sensitivity**, and document where each source lives.

## Volume, rate and cost

Ingestion is where telemetry becomes a bill. **EPS** drives processing capacity and is stated as an average and a peak, because logon storms, patch nights and incidents multiply the normal rate. **Daily ingest volume** (GB/day) drives storage and, on many platforms, licence charges.

The arithmetic is simple and worth doing before onboarding any source. Volume per day is approximately average EPS multiplied by average event size multiplied by 86,400 seconds:

$$\text{GB/day} \approx \frac{\text{EPS} \times \text{bytes per event} \times 86{,}400}{10^9}$$

A source producing 2,000 events per second with an average size of 500 bytes ingests 1,000,000 bytes per second, which is about 86.4 GB per day, before indexing overhead or replication. The same calculation for the Banyan teaching dataset, which you will measure in the worked example, gives a tiny figure, because it is 340 events from eight workstations over one working day; the method, not the number, is what transfers to a real estate.

Volume pressure produces the most consequential decisions in ingestion: what **not** to keep. The options, in increasing order of risk, are:

1. **Route to a cheaper tier.** Keep everything, but store low-value data where it is slower to search.
2. **Trim fields.** Remove repeated boilerplate (for example, the long descriptive text Windows includes in every rendered event) while keeping the structured fields.
3. **Aggregate.** Store summaries (counts per hour per host) instead of every record for very high-volume, low-value data.
4. **Drop.** Discard whole event types.

Each step down the list loses evidence. A dropped event type is permanently missing for every future detection and investigation. The defensible way to decide is per event type: which detections or investigations use it, what an investigator would lose without it, and whether it can be recovered from the source if needed. Record the decision, its owner and its review date, exactly as you would for a risk acceptance.

> [!WARNING]
> Ingest-time filters are rarely reviewed after they are written. A filter that dropped "noisy" PowerShell events during a cost-saving exercise will also drop the script-block events that would have recorded an intruder's commands. Treat every drop rule as a detection change.

## Worked example: ingesting the Banyan dataset with minisiem

The course lab kit contains `LAB_ASSETS/C08/minisiem.py`, a teaching SIEM of about 60 lines built on Python's standard-library SQLite module. Its `load` command is a complete, if minimal, ingestion layer, which makes it ideal for seeing each stage and each gap. Copy the kit to your own working directory first and run everything there; never run scripts inside the course library or the `LAB_ASSETS` folder.

```bash
mkdir -p ~/c08-work && cp LAB_ASSETS/C08/minisiem.py LAB_ASSETS/C08/banyan_events.jsonl ~/c08-work/
cd ~/c08-work
```

`mkdir -p` creates the working directory if it does not exist; `cp` copies the SIEM script and the dataset, so that the experiments below change only your copies.

### Step 1: load

```terminal
$ python -I minisiem.py load
loaded 340 events
```

`load` is the sub-command; `-I` runs Python in isolated mode, ignoring environment variables and the user's site packages. All outputs in this lesson were produced by running the kit's script, unchanged, in a temporary copy with CPython 3.14.4.

Reading `load()` stage by stage shows what it does. It **receives** by opening one file, `banyan_events.jsonl`, with one JSON object per line, so **event breaking** is "one line, one event". It **labels** each event with the `source` value the event already carries (`windows`, `sysmon`, `proxy` or `vpn`). It **assigns time** by copying `@timestamp` into a column called `ts`; it records no ingest time. It **routes** everything to a single table, `events`, after first running `DROP TABLE IF EXISTS events`. It **writes** twelve common fields as columns plus the original line in a `raw` column, using a parameterised `executemany` insert, and **indexes** by creating `idx_ts` on `ts`, because, like every SIEM, it expects searches to be bounded by time.

### Step 2: inspect what was stored

The kit's `search` command runs a SQL query against the database. First, the schema:

```terminal
$ python -I minisiem.py search "SELECT name, type FROM pragma_table_info('events')"
name | type
ts | 
source | 
event_id | 
host | 
user | 
src_ip | 
url | 
outcome | 
image | 
parent_image | 
bytes_out | 
target_user | 
raw | TEXT
```

Twelve columns and `raw`. Only `raw` has a declared type; the others are untyped, so SQLite stores whatever type each value had in the JSON. Next, volume per source:

```terminal
$ python -I minisiem.py search "SELECT source, COUNT(*) n, SUM(length(raw)) bytes, ROUND(AVG(length(raw)),1) avg_b FROM events GROUP BY source ORDER BY n DESC"
source | n | bytes | avg_b
proxy | 284 | 53450 | 188.2
sysmon | 33 | 7726 | 234.1
windows | 13 | 2187 | 168.2
vpn | 10 | 1367 | 136.7
```

`length(raw)` measures the stored original line in characters. The proxy produces 284 of the 340 events and 53,450 of the 64,730 characters, about 83 per cent of the volume. Sysmon events are the largest on average (234 characters) because they carry full image paths and command lines. Real estates look the same: network logs dominate volume while the highest-value events are a small share, so any trimming of network data must first ask which detections (beaconing, large uploads) depend on it.

Some fields in the dataset are not among the twelve columns. SQLite's `json_extract` reads them from `raw`:

```terminal
$ python -I minisiem.py search "SELECT source, SUM(json_extract(raw,'$.logon_type') IS NOT NULL) logon_type, SUM(json_extract(raw,'$.command_line') IS NOT NULL) cmdline, SUM(json_extract(raw,'$.status') IS NOT NULL) status, SUM(json_extract(raw,'$.country') IS NOT NULL) country FROM events GROUP BY source"
source | logon_type | cmdline | status | country
proxy | 0 | 0 | 284 | 0
sysmon | 0 | 33 | 0 | 0
vpn | 0 | 0 | 0 | 10
windows | 10 | 0 | 2 | 0
```

Four fields (`logon_type`, `command_line`, `status`, `country`) were ingested but not given columns. They survive only because `raw` was kept. A rule that needs the logon type or the VPN country must extract it from `raw` at search time, which is slower and easier to get wrong. This is the ingest-time versus search-time trade-off from Module 2, seen in a real schema: the ingestion layer's column list is a decision about which fields are first-class.

### Step 3: break it on purpose

Two experiments, each in a **separate scratch copy** of the kit, show how this ingestion layer behaves when the input is not perfect.

**A duplicated line.** Appending a copy of one existing proxy event (WS-104's 06:40 request to `https://mail.banyan.example/`) to the dataset and reloading gives:

```terminal
$ python -I minisiem.py load
loaded 341 events
$ python -I minisiem.py search "SELECT COUNT(*) total, COUNT(DISTINCT raw) distinct_raw FROM events"
total | distinct_raw
341 | 340
```

The SIEM accepted the duplicate without comment. Nothing in `load()` checks for it, which is how many ingestion layers behave by default: at-least-once delivery upstream (Module 2 Lesson 7) produces occasional duplicates, and unless the ingestion layer de-duplicates on a stable identifier they are stored and counted. The `COUNT(DISTINCT raw)` comparison is a cheap health check that reveals them.

**A malformed line.** Inserting one truncated JSON line (missing its closing brace) in the middle of the file and reloading ends with a Python traceback whose last line is shown here:

```terminal
$ python -I minisiem.py load
json.decoder.JSONDecodeError: Expecting ',' delimiter: line 2 column 1 (char 75)
$ python -I minisiem.py search "SELECT COUNT(*) FROM events"
COUNT(*)
0
```

One bad event out of 341 left the SIEM with **zero** events. The reason is visible in the code: `load()` drops and recreates the table first, then parses every line into a list in memory before inserting any of them, so an exception on any line aborts the load after the old data is already gone. This is all-or-nothing ingestion, acceptable for a teaching tool that reloads a known file, and unacceptable in production, where one malformed record from one device must never stop the ingestion of everything else.

**Execution flow.** Read each pair from left to right, as a question you would ask of any SIEM during onboarding: "the teaching tool does this; what does ours do, and how have we verified it?"

**Decision logic.** The two failure items illustrate different principles. The duplicate pair is about *accuracy*: counts and thresholds are wrong if duplicates are stored. The malformed-line pair is about *isolation*: a fault in one event must be contained to that event. A production design quarantines the bad record, tags it, counts it and keeps ingesting.

**Technical interpretation.** The ingest-time pair is the one most often missing in real deployments too. Without ingest time, lag cannot be measured per event, a late-arriving batch looks identical to a timely one, and nobody can tell whether a correlation rule evaluated a window before all of its events had arrived.

**Practical example.** Before Banyan connects its new VPN source, the engineer runs the same two experiments against the staging SIEM: replaying a sample twice and including one malformed record. The platform reports the duplicate rate and quarantines the malformed record while ingesting the rest, so the source passes onboarding.

**Security implications.** All-or-nothing ingestion is a denial-of-service condition: anyone who can inject one malformed record into a feed can blind the SOC to the whole feed. Silent duplicates can inflate counts enough to trigger false threshold alerts or mask a genuine change in volume.

**Key learning.** Test ingestion with imperfect input before trusting it. Isolation of bad events, ingest time and duplicate detection are requirements, not refinements.

## Onboarding a new source, step by step

The worked example generalises into a procedure for every new source.

1. **State the purpose.** Name the detections and investigations the source supports, and the fields they need. This decides what must be kept and which fields deserve first-class treatment.
2. **Estimate volume.** Measure or estimate average and peak EPS and event size, convert to GB/day, and confirm licence and storage headroom.
3. **Choose input, source type and container.** Use a dedicated input or an explicit source-type assignment; do not let the source inherit another device's defaults. Choose the container by data type, retention and sensitivity.
4. **Collect samples.** Capture real raw events, including the awkward ones: multi-line records, the largest records, records from every event type the source emits.
5. **Ingest into a test container.** Check event breaking (one real event per stored event), the `host` value, event time against the source's own clock, and ingest time.
6. **Test imperfect input.** Replay a duplicate and a malformed record; confirm duplicates are counted and bad records are isolated.
7. **Reconcile counts.** For a fixed window, compare the number of events the source says it sent with the number the SIEM holds.
8. **Hand over to health monitoring.** Add the source to the expected-source inventory with its normal volume and lag, so that Module 2's health checks cover it from day one.

## Common mistakes and misconceptions

- **"It is in the SIEM, so it is searchable."** An event filed under the wrong time or index is present but not found. Check where and when it was filed.
- **Sharing one input among different devices.** Every device inherits the same source type and index, and with them the wrong time and breaking rules.
- **Trusting the `host` field on relayed data.** For syslog relays and collectors, the host label may name the relay, not the original device.
- **Recording only event time.** Without ingest time, lag and late batches cannot be measured, and back-dated events cannot be distinguished from timely ones.
- **Treating volume reduction as housekeeping.** Every drop rule removes evidence. It is a detection decision with an owner.

## Security implications, detection and defence

The ingestion layer is part of the SOC's attack surface, and the techniques used against it are documented. MITRE ATT&CK's **T1562** (Impair Defenses) covers adversary actions that reduce what defenders can see, and an intruder who understands ingestion has quieter options than stopping an agent.

- **Forged events.** An unauthenticated syslog or HTTP input accepts events from anyone who can reach it. Forged events can create false leads or bury real ones. Defence: authenticate inputs (TLS with client certificates, per-source tokens), restrict them by network, and alert on events arriving from unexpected senders on each input.
- **Flooding.** A burst of junk events can exhaust licence quotas, fill storage or push the ingestion layer into a backlog, delaying the events that matter. Defence: alert on sudden volume rises per source as well as falls, apply per-input rate limits where the platform supports them, and size for peaks.
- **Malformed input.** If one bad record can stall a feed, malformed input becomes a way to blind the SOC. Defence: isolate and quarantine bad events, and count them as a health metric.
- **Tampering with configuration.** Changing a routing or filter rule is a quiet way to make a whole event type disappear. Defence: put ingestion configuration under change control, audit administrator actions in the SIEM, and alert on changes to drop and routing rules.
- **Time manipulation.** Events carrying wildly wrong timestamps can be filed where nobody looks. Defence: compare event time with ingest time and flag large or negative gaps.

Privacy is a design input too: routing sensitive sources to restricted containers and keeping only what detection needs supports the DPDP Act 2023's purpose limitation and safeguard duties.

## Best practices

- Give every source an explicit source type and container; never rely on input defaults.
- Record event time and ingest time on every event, and monitor the gap.
- Keep the raw event beside extracted fields; quarantine malformed events and keep ingesting.
- Measure duplicates, reconcile counts for new feeds and size for peak EPS.
- Treat routing and filter rules as change-controlled security controls.

## Key takeaways

- Ingestion is everything between arrival and searchability: receive, break into events, label source and type, assign time, route and write. Each stage is a filing decision that can mis-file evidence silently.
- Record both event time and ingest time; the gap reveals lag, late batches and clock or parsing problems.
- The container an event is routed to sets its retention, access and search scope, so routing is a security and compliance control.
- Volume (EPS and GB/day) drives cost; reductions range from tiering to dropping, and every drop is a detection decision.
- The minisiem experiments showed real failure modes: duplicates stored silently (341 rows, 340 distinct) and one malformed line leaving the table empty. Production ingestion must count duplicates and isolate bad events.
- Ingestion inputs and configuration are attack surface: authenticate inputs, alert on volume changes in both directions, and change-control routing and filter rules.
