## Lab objective and scope

This lab puts the whole of Module 3 to work on one investigation. You will load the Banyan Microfinance dataset into the course's teaching SIEM, orient yourself in the data, run the saved correlation rules, pivot from an alert into the related events, write and test a new cross-source correlation rule, build a host timeline, produce two dashboard panels as queries, and finally export the evidence with a hash and a custody record so that it outlives SIEM retention. An optional final section explains how the same exercise maps onto a self-hosted Wazuh or Elastic single-node lab, so that the skills transfer to the platforms you will meet at work.

The core of the lab uses `minisiem.py` deliberately. A production SIEM hides the pipeline behind agents, pipelines and a web interface; minisiem is about sixty lines of Python over SQLite, so every stage of Lessons 1 to 7 is visible: ingestion in `load`, normalised columns plus a `raw` column, search in `search`, correlation in `RULES`. When you later sit in front of Kibana or the Wazuh dashboard, you will know what each screen is doing underneath.

By the end of the lab you should be able to say, from evidence you produced yourself: what happened on WS-104, in what order, which second account was compromised and from where, and where the exported evidence is with its hash.

## Key terminology

| Term | Meaning in this lab |
| --- | --- |
| Saved search | A query kept for reuse; in minisiem, any SQL passed to `search`. |
| Correlation rule | A saved search that joins or aggregates events, run on a schedule; the entries of `RULES` in `minisiem.py`. |

## How the lab exercises a SIEM

The lab follows the order in which an analyst actually uses a SIEM during an investigation: prove the data is there, look at what the rules found, pivot and correlate to understand the story, summarise it, and preserve it.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the lab's route map. Each step corresponds to a group of numbered lab steps below and to one capability of a SIEM taught earlier in the module, so that you always know which concept a command is exercising.

**Components.** There are seven steps, top to bottom. **Load and orient** ("minisiem.py load; counts by source, time range") is slate: it is plumbing, proving that ingestion worked (Lessons 1 to 3). **Run saved rules** ("R1-R6: six detections") is blue, the routine correlation output (Lesson 4). **Pivot on an alert** ("VPN spray: src_ip 203.0.113.66") is violet, the analyst's first decision: which alert to pull on and by which field (Lesson 6). **Write rule R7** ("download then Office spawn within 10 min") is orange because it is the key new skill: a cross-source, time-bounded join you design and test yourself. **Build host timeline** ("WS-104, 06:00Z-09:00Z") is blue, the reconstruction. **Dashboard panels** ("hourly by source; top talkers") is green, the summary view (Lesson 5). **Export evidence** ("SHA-256 + custody record") is dark, the trust anchor: the output that survives retention (Lesson 7).

**Relationships and arrows.** The arrows show order and dependency: every step reads the `events` table built in the first step, and each later step uses what the earlier ones found. The rule output tells you where to pivot; the pivot tells you what R7 should join; the timeline shows which window to export.

**Execution flow.** You work top to bottom once. In practice an analyst loops between pivot, rule and timeline several times; the lab keeps the loop to one pass so the outputs are reproducible.

**Decision logic.** At the pivot step you choose a field. Pivoting on a source IP finds everything that address touched across sources; pivoting on a host finds everything that happened on one machine. The lab does both: the IP for the VPN story and the host for the endpoint story.

**Technical interpretation.** Every step is a SQL query over the same table. That is not a simplification of the idea, only of the syntax: Kibana's Discover, Elastic's detection rules and Wazuh's rules perform the same filtering, grouping and joining over an index.

**Practical example.** The R2 alert names 203.0.113.66. Pivoting on that address shows eight failures in 49 seconds and one success for gopal. That result tells you the spray succeeded, which you then carry into the timeline and the evidence scope.

**Security implications.** The final step is the one that protects the case. Without it, the conclusions of every earlier step rest on data that the retention policy will eventually delete.

**Key learning.** A SIEM investigation runs from proven data through alerts, pivots and correlation to a preserved timeline; the lab walks that path once with every step visible.

## Lab steps

### Step 1: Load the dataset

```terminal
$ python minisiem.py load
loaded 340 events
```

`load` drops and recreates the `events` table in `minisiem.db`, reads `banyan_events.jsonl` line by line, copies twelve normalised fields into columns, stores each original line in the `raw` column and indexes the timestamp. Because the table is recreated, you can rerun this step at any time to return to a clean state.

### Step 2: Orient yourself

Before trusting any rule, confirm what the SIEM holds: which sources and over what period.

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS n FROM events GROUP BY source ORDER BY n DESC"
source | n
proxy | 284
sysmon | 33
windows | 13
vpn | 10
$ python minisiem.py search "SELECT MIN(ts), MAX(ts), COUNT(*) FROM events"
MIN(ts) | MAX(ts) | COUNT(*)
2026-11-03T03:07:00Z | 2026-11-03T13:33:00Z | 340
```

All four expected sources are present, and the data covers 03:07Z to 13:33Z (08:37 to 19:03 IST) on 3 November 2026. The proxy dominates volume, as web proxies do in real estates. Every time in the dataset is UTC, marked by the trailing `Z`.

### Step 4: Pivot on the VPN alert

R2 says that one source IP failed against at least five users and then succeeded. Pivot on that IP across every source:

```terminal
$ python minisiem.py search "SELECT ts, user, src_ip, outcome FROM events WHERE source='vpn' AND src_ip='203.0.113.66' ORDER BY ts"
ts | user | src_ip | outcome
2026-11-03T06:42:00Z | asha | 203.0.113.66 | failure
2026-11-03T06:42:07Z | ben | 203.0.113.66 | failure
```

Eight users, one failure each, seven seconds apart, in alphabetical order: that is the shape of a password spray (one password tried against many accounts), not of a person mistyping. Three minutes later the same address logs in successfully as gopal. Remove `source='vpn' AND` from the query and it returns the same nine rows: the address appears nowhere else in this dataset. Note it: gopal's account is compromised independently of the WS-104 activity, and containment must cover both.

### Step 5: Write and test a cross-source correlation rule (R7)

R1 tells you that Word started PowerShell, but not *why*. The hypothesis is that the user opened a macro-enabled document downloaded moments earlier. Each source alone is weak evidence: a `.docm` download is common, and so, in some organisations, are Office add-ins that start scripts. The combination on the same host within minutes is much stronger. That is the purpose of correlation (Lesson 4).

Open your working copy of `minisiem.py` and add one entry to the `RULES` dictionary, after R6 and before the closing brace:

```python
    "R7 doc_download_then_office_spawn": """
        SELECT s.ts, s.host, s.user, p.url FROM events s
        JOIN events p ON p.host = s.host AND p.source = 'proxy'
        WHERE s.source='sysmon' AND s.event_id=1
          AND lower(s.parent_image) LIKE '%winword.exe%'
          AND lower(p.url) LIKE '%.docm'
          AND p.ts <= s.ts
          AND p.ts >= strftime('%Y-%m-%dT%H:%M:%SZ', s.ts, '-10 minutes')""",
```

How it works: the table is joined to itself, with `s` as the process-start event (Sysmon Event ID 1 whose parent is Word) and `p` as a proxy event on the **same host**. The parent path in the data is `WINWORD.EXE` in capitals. SQLite's `LIKE` already ignores case for ASCII letters, but `lower()` makes the intent explicit and keeps the rule correct if it is ported to an engine whose pattern match is case-sensitive. The last two conditions are the **time window**: the download must be at or before the spawn and no more than ten minutes earlier. `strftime` with the `'-10 minutes'` modifier subtracts ten minutes and formats the result in exactly the same ISO 8601 UTC style as the stored timestamps, so the string comparison is also a correct time comparison. Then run the rules again:

```terminal
$ python minisiem.py rules
```

R1 to R6 print exactly as in Step 3, followed by the new rule:

```text
R7 doc_download_then_office_spawn: 1 hit(s)
    ('2026-11-03T06:14:00Z', 'WS-104', 'divya', 'https://banyan-payroll-update.example/invoice.docm')
```

The rule links the 06:12Z download of `invoice.docm` from a look-alike payroll domain to the 06:14Z PowerShell launch. Test the boundaries before you trust it: change `'-10 minutes'` to `'-1 minutes'` and the hit should disappear, because the download was two minutes earlier; change it back. A rule you have not seen fail is a rule you have not tested (Module 7 develops this into rule testing).

```terminal
ts | source | event_id | detail

2026-11-03T06:12:00Z | proxy | None | https://banyan-payroll-update.example/invoice.docm
2026-11-03T06:14:00Z | sysmon | 1 | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
2026-11-03T06:40:00Z | proxy | None | https://mail.banyan.example/
2026-11-03T07:02:00Z | windows | 4720 | svc_update
2026-11-03T07:03:00Z | windows | 4732 | svc_update
2026-11-03T07:19:00Z | proxy | None | https://cdn.example.org/

```

`COALESCE` returns the first non-empty of its arguments, giving one readable `detail` column whichever source the row came from. The routine browsing to intranet, mail and public sites is the user's normal day continuing around the intrusion, which is realistic: attackers work inside a legitimate session. Read the five kinds of row that are not routine and the story is visible: document download, script execution, local account creation and promotion, large upload to a file-sharing look-alike, log clearing.

### Step 7: Dashboard panels as queries

A dashboard panel is a saved aggregation (Lesson 5). Two panels are useful for this case. First, event volume per hour by source, the basic shape of the day:

```terminal
$ python minisiem.py search "SELECT substr(ts,12,2) AS hour_utc, SUM(source='proxy') AS proxy, SUM(source='sysmon') AS sysmon, SUM(source='windows') AS windows, SUM(source='vpn') AS vpn FROM events GROUP BY hour_utc ORDER BY hour_utc"
hour_utc | proxy | sysmon | windows | vpn
03 | 16 | 4 | 8 | 0
04 | 45 | 18 | 2 | 0
05 | 24 | 10 | 0 | 0
06 | 37 | 1 | 0 | 9
07 | 36 | 0 | 2 | 0
08 | 32 | 0 | 1 | 0
09 | 26 | 0 | 0 | 0
10 | 25 | 0 | 0 | 0
11 | 32 | 0 | 0 | 0
12 | 11 | 0 | 0 | 0
13 | 0 | 0 | 0 | 1
```

`substr(ts,12,2)` takes the two hour characters from the timestamp, a cheap time bucket; in SQLite a comparison such as `source='proxy'` evaluates to 1 or 0, so `SUM` counts matching rows. The 06 row stands out only in the VPN column: nine VPN events in one hour against none in the hours around it. Most of the intrusion is invisible at this level of aggregation, which is the lesson of dashboards: they show shape and anomalies in volume, not individual malicious events.

Second, a top-talkers panel by bytes sent through the proxy:

```terminal
$ python minisiem.py search "SELECT host, COUNT(*) AS requests, SUM(bytes_out) AS bytes_out FROM events WHERE source='proxy' GROUP BY host ORDER BY bytes_out DESC LIMIT 3"
host | requests | bytes_out
WS-104 | 49 | 48263095
WS-103 | 37 | 82933
WS-106 | 32 | 78117
```

WS-104 sent about 48 MB, nearly 600 times the next host. A single number like this is exactly what a dashboard is good at surfacing.

### Step 8: Scope the indicators

Before closing the investigation of WS-104, ask whether any other host is affected. The beacon domain is the most specific indicator:

```terminal
$ python minisiem.py search "SELECT host, COUNT(*) AS n FROM events WHERE url LIKE '%cdn-telemetry-sync.example%' GROUP BY host"
host | n
WS-104 | 18
```

Only WS-104 contacted it. Repeat the query for `banyan-payroll-update.example` and `files-share-drop.example` to complete the scope check. A negative result is only as strong as your data: it means "no other host in the retained, collected telemetry", which is why Lesson 7's retention and Module 2's source health matter.

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| `no such table: events` | `load` has not been run in this folder, or you are in a different directory from `minisiem.db`. Run `python minisiem.py load` here. |
| `loaded` reports a number other than 340 | The dataset was regenerated or edited. Restore `banyan_events.jsonl` from the kit and reload. |
| R7 does not appear | The new entry is outside the `RULES` braces, or a missing comma joined it to R6. Check the dictionary syntax. |
| R7 shows 0 hits | A typo in the time condition or the `LIKE` pattern; test each condition on its own with `search`. |
| A query returns nothing on a shell | Quoting: the shell consumed a quote. Wrap the whole SQL in double quotes and use single quotes inside it, as in the examples. On PowerShell, the same quoting works for these queries. |
| The SHA-256 differs | The export window, host or dataset differs from the kit defaults, or the file was opened and saved by an editor. Re-export into a fresh case folder. |

## Optional: the same exercise on Wazuh or Elastic

minisiem exists to make the mechanics visible; it is not a SIEM you would run in production. The two open platforms most often used for home and training labs are **Wazuh** and the **Elastic Stack** (with Elastic Security). Both can run as a single-node lab on one machine or virtual machine. This section explains how each maps onto what you have just done, so that you can repeat the investigation on a real platform. It deliberately does not reproduce installation commands or screen output: those change between releases, and the official documentation for the version you install is the authority.

> [!CAUTION]
> Build the platform lab on a host or virtual machine you own, on an isolated or host-only network. Do not expose the platform's web interface or API ports to the internet, keep authentication and TLS enabled (Elasticsearch 8.x enables security by default; leave it on), change any generated default credentials, and allocate memory according to the vendor's current hardware requirements; a single-node lab still needs several gigabytes of RAM. Ingest only the course dataset or logs from your own lab machines.

### Wazuh architecture in brief

A Wazuh deployment has four parts. The **Wazuh agent** runs on monitored endpoints, reading logs and other host data, and sends events over an encrypted channel to the **Wazuh server** (the manager). The server's analysis engine runs **decoders**, which parse events into fields, and **rules**, which match decoded events and assign each alert a **level** from 0 to 15 that expresses its severity; rules can also count repeated matches within a time frame and chain to earlier rules, which is how Wazuh expresses correlation. Alerts are written on the server (in `/var/ossec/logs/alerts/`, including `alerts.json`) and shipped to the **Wazuh indexer**, a search engine derived from OpenSearch, and the **Wazuh dashboard**, derived from OpenSearch Dashboards, is where analysts search and visualise them. Custom rules live in `local_rules.xml` on the server, and the `wazuh-logtest` utility lets you paste a log line and see which decoder and rule it triggers, the Wazuh equivalent of testing R7 at its boundaries.

To repeat this lab, an agent can be configured to read a copy of the Banyan JSON Lines file as JSON, so that the built-in JSON decoder extracts its fields. You would then write custom rules equivalent to R1-R7 and investigate the resulting alerts in the dashboard. One conceptual difference matters: Wazuh is **alert-centric**. By default it indexes alerts, not every event, so a search for "all WS-104 events" in the dashboard finds only those that matched a rule, unless archiving of all events is enabled. Pivots such as Step 6 depend on that choice.

### Elastic architecture in brief

In the Elastic Stack, **Elastic Agent** (centrally managed through **Fleet**) or the older **Beats** shippers collect data; **ingest pipelines** parse and enrich it into the **Elastic Common Schema (ECS)**, the field naming Lesson 3 used (`source.ip`, `user.name`, `host.name`, `event.outcome`); **Elasticsearch** stores and indexes it; and **Kibana** provides search (Discover, with KQL and ES|QL), dashboards, and the **Elastic Security** application with its detection rules and case management. Kibana also offers a file-upload feature for importing a small file such as the Banyan dataset for practice. Elastic is **event-centric**: every ingested event is searchable, and detection rules run over those events.

Elastic Security's rule types map closely onto the minisiem rules. R1, R3, R4 and R5 are single-event conditions, the natural fit for a **custom query** rule. R2 counts distinct users per source address, which is what a **threshold** rule does. R7, "event A then event B on the same host within ten minutes", is the textbook use of an **EQL sequence** query, which joins events by a field within a maximum time span. R6 needs an aggregation over a period (many requests, nearly constant size), better suited to an ES|QL rule or to the anomaly-detection features than to a simple query. Retention is handled by **index lifecycle management (ILM)**, whose hot, warm, cold, frozen and delete phases are the tiers of Lesson 7; Wazuh's indexer has the equivalent in OpenSearch's index state management policies.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The table is a translation key. It lets you carry each step of this lab from minisiem to either platform, and it shows that the concepts of the module, not the product, are what you have learned.

**Components.** There are four columns: **Stage**, **minisiem**, **Wazuh** and **Elastic**. The eight rows are the pipeline and investigation stages. **Collect** maps `load` from the JSONL file to the Wazuh agent and to Elastic Agent or Beats. **Parse + normalise** maps the kit's pre-normalised fields (raw kept) to Wazuh decoders and to Elastic ingest pipelines and ECS. **Store + index** maps the SQLite `events` table to the Wazuh indexer and to Elasticsearch indices. **Search** maps `search` with SQL to the Wazuh dashboard and to Kibana Discover. **Detect** maps the `RULES` dictionary to Wazuh rules with levels 0-15 and to Elastic detection rules (query, threshold, EQL). **Dashboards** maps `GROUP BY` queries to the dashboards of each platform. **Retention** maps the purge experiment of Lesson 7 to index management policies on the indexer and to ILM phases. **Evidence** maps `evidence_export.py` to exporting the relevant events with a hash and custody record on either platform.

**Relationships.** Reading across a row shows the same function in three implementations. Reading down a column shows one platform's full pipeline. The rows run in the same order as Figure 1 and as the data itself: collection first, evidence last.

**Execution flow.** To port the lab, work down the rows: get the dataset collected and parsed, confirm the event count (Step 2) in the platform's search, recreate the rules, then repeat Steps 4 to 9 with the platform's tools.

**Decision logic.** The key difference to watch is in the **Store + index** row: Elastic stores every event, while Wazuh stores alerts by default. That changes whether timeline pivots (Step 6) are possible without additional configuration.

## Key takeaways

- An investigation in a SIEM runs from proven data, through rule output, pivots and correlation, to a timeline, and ends with preserved evidence.
- Five of six saved rules pointed at WS-104; the sixth revealed a separate compromise of gopal's VPN account from 203.0.113.66 that a host-only view would have missed.

- Exported raw events with a SHA-256 hash and custody record outlive SIEM retention and can be verified by anyone.
- Wazuh (agent, server with decoders and leveled rules, indexer, dashboard) and Elastic (Agent, ingest pipelines and ECS, Elasticsearch, Kibana and Elastic Security) implement the same stages; the main conceptual difference is alert-centric versus event-centric storage.
