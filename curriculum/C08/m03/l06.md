## Introduction and conceptual foundation

Correlation rules (Lesson 4) and dashboards (Lesson 5) are searches that someone wrote in advance. Every investigation, though, eventually reaches a question that nobody anticipated: what else did this host do in the ten minutes before the alert, has any other machine contacted this domain, did the account that logged in through the VPN do anything afterwards? Answering those questions quickly, correctly and in a way that someone else can repeat is the analyst's core technical skill. It is called **searching**, and the SIEM's search language is the tool for it.

Search languages differ between products. Splunk uses SPL, Microsoft Sentinel and Defender use KQL, Elastic offers ES|QL alongside its older query syntaxes, and Wazuh's web interface is built on OpenSearch Dashboards. Learning one well makes the others easy, because they all express the same small set of operations: choose a time range, filter events, select fields, aggregate and count, sort, and join or pivot from one result to the next search. This lesson teaches those operations as **query thinking**, a way of turning an investigative question into a sequence of searches, and practises them with real outputs from the course lab's teaching SIEM, `minisiem.py`, whose search language is plain SQL over the normalised Banyan dataset.

The emphasis is on reasoning, not syntax. A syntactically perfect query that answers the wrong question, silently drops half the events because a field is empty, or misses a match because of letter case is worse than useless: it produces a confident wrong answer that goes into a case note. Most of this lesson is about recognising those traps.

> [!NOTE]
> `minisiem.py search` runs any SQL the analyst types. That is acceptable only because minisiem is a single-user teaching tool working on a local copy of synthetic data. A multi-user SIEM restricts and audits what each user can search; see the security section at the end of this lesson.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Query | A statement in the SIEM's search language that selects and transforms events. |
| Time range | The window of event time a search covers; the first and most important filter. |
| Filter (predicate) | A condition that keeps or removes events, such as `source='vpn'`. |
| Projection | The choice of which fields to return. |
| Aggregation | Combining many events into summary rows: count, distinct count, sum, minimum, maximum. |
| Group-by key | The field or fields whose values define the summary rows. |
| Stacking (frequency analysis) | Counting how often each value occurs and examining the rarest and most common. |
| Pivot | Taking a value found in one result (a host, user, IP or domain) and using it as the filter of the next search. |
| Entity | Something events are about: a host, user, address, process or domain. |
| Null | A field that is absent from an event; distinct from an empty string or a placeholder such as `-`. |
| Case sensitivity | Whether `WS-104` and `ws-104` compare as equal; it differs between operators and products. |
| Saved query | A query stored with the case or as a reusable search so the result can be reproduced. |

## Query thinking: from question to evidence

An analyst who opens the search bar and types the first thing that comes to mind usually ends up with too many results, too few, or the wrong ones. Query thinking imposes a short discipline.

First, **write the question** as a sentence. "Did anything on WS-104 talk to the beacon domain before the alert?" is a question; "check WS-104" is not. The sentence tells you which entities, which sources and which time window are involved. Second, **set the time range** before anything else. Searches without a time range are slow on real platforms and dangerous in reasoning, because they mix today's events with last month's. Choose a window generous enough to catch precursors (start a little before the earliest known event) but narrow enough to read.

Third, **filter** to the sources and conditions that the question names, using normalised fields so that one condition works across sources. Fourth, **inspect raw events** before summarising. Look at a handful of matching events in full; this is where you discover that a field is empty for one source, that a value is upper case, or that the events are not what you thought. Fifth, **aggregate** to see the shape of the result: count per entity, distinct values, first and last seen, rarest values. Sixth, **pivot**: take the interesting value from the result and make it the filter of a new, related search. Finally, **record** the query and its result in the case notes, with the time range and the time it was run, so that a colleague can reproduce it.

The process is a loop, not a line. Pivoting produces a new entity, and a new entity produces a new question.

A dashed feedback arrow runs from the last box back to the first, labelled "new entity: new question".

**Relationships and arrows.** Each downward arrow means "narrow or transform the previous result". The order is deliberate: inspection comes before aggregation because a summary of broken data looks as tidy as a summary of good data. The feedback arrow is the pivot loop: recording a result usually exposes the next entity to examine.

**Execution flow.** One pass through the boxes is one search. A typical triage involves three to ten passes, each starting from a value the previous pass produced, until the scope of the activity is known or the question is answered.

**Decision logic.** At **Inspect raw events** the analyst decides whether the data can answer the question; if a needed field is null for the source, the query must be changed or another source used. At **Aggregate** the decision is which values deserve a pivot: the rare, the new and the suspiciously regular. At **Record**, the analyst decides whether the question is answered or a new loop starts.

**Technical interpretation.** In SQL terms the boxes map to clauses: the time range and filter to `WHERE`, inspection to `SELECT ... LIMIT`, aggregation to `GROUP BY` with `COUNT`, `COUNT(DISTINCT ...)`, `MIN` and `MAX`, sorting to `ORDER BY`. Pivoting is a new query whose `WHERE` uses a value copied from the last result. Pipe-based languages such as SPL, KQL and ES|QL express the same steps as stages separated by `|`.

**Practical example.** Starting from rule R6's beacon alert, the analyst asks which hosts contacted `cdn-telemetry-sync.example`, sets the lab day as the range, filters proxy events on that domain, inspects a few, aggregates by host and user (one host, WS-104, 18 hits), pivots to all non-proxy events from WS-104, and records each query in the case.

**Security implications.** Skipping inspection or recording is how wrong conclusions enter incident reports. Unrecorded queries cannot be reviewed, and analysts' searches over personal data should themselves be auditable.

**Key learning.** Question, time range, filter, inspect, aggregate, pivot, record: and loop, because each answer reveals the next question.

## The minisiem search interface

The kit's SIEM is deliberately transparent. After `python minisiem.py load`, all 340 Banyan events sit in one SQLite table, `events`, with one column per normalised field and the full original event in a `raw` column. Work in your own copy of `LAB_ASSETS/C08`, never in the course folder:

```terminal
$ python minisiem.py load
loaded 340 events
```

| Column | Content | Populated for |
| --- | --- | --- |
| `ts` | Event time, ISO 8601 UTC (`2026-11-03T06:14:00Z`) | All sources |
| `source` | `windows`, `sysmon`, `proxy` or `vpn` | All |
| `event_id` | Windows or Sysmon event ID (4624, 4625, 4720, 4732, 1102, 1) | windows, sysmon |
| `host`, `user` | Workstation name, account name | host: not vpn; user: all |
| `src_ip` | Source address | proxy, vpn, some windows |
| `url`, `bytes_out` | Requested URL, bytes sent | proxy |
| `outcome` | `success` or `failure` | windows, vpn |
| `image`, `parent_image` | Process and parent process paths | sysmon |
| `target_user` | Account acted upon (for example a created user) | windows (4720, 4732) |
| `raw` | The original JSON event, including fields without a column | All |

A search is one SQL statement in double quotes; minisiem prints the column names and then one line per row, separated by ` | `. Absent values print as `None`. Fields that have no column, such as the VPN's `country`, can still be read from `raw` with SQLite's `json_extract()`.

Because the time is stored as ISO 8601 text in a single zone (UTC, with a trailing `Z`), string comparison orders it correctly, so `ts BETWEEN '2026-11-03T06:10:00Z' AND '2026-11-03T06:20:00Z'` is a valid time-range filter. This only holds while every timestamp uses exactly the same format and zone, which is one of the practical reasons normalisation (Lesson 3) converts times to UTC at ingest.

## Filters: getting the right events, all of them

Filtering looks trivial and is where most search errors happen. Three traps deserve hands-on practice.

### Letter case

```terminal
$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE host='ws-104'"
COUNT(*)
0

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE lower(host)='ws-104'"
COUNT(*)
58

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE host LIKE 'ws-104'"
COUNT(*)
58
```

The first query says WS-104 has no events at all, which is false: it has 58. In SQLite the `=` operator compares text exactly, including case, while `LIKE` ignores case for ASCII letters, and wrapping the field in `lower()` normalises it explicitly. An analyst who typed the host name in lower case from a ticket would have written "no activity found on ws-104" in the case notes. Every SIEM has its own rules here (some operators are case-sensitive, some are not, and the default differs between products and between field types), so the habit to build is product-independent: when a search returns nothing for an entity you expected to see, suspect the query before concluding the absence. Correlation rule R1 in minisiem applies `lower()` to process paths for exactly this reason, because Windows paths such as `WINWORD.EXE` appear in mixed case.

### Wildcards

`LIKE` with `%` matches any run of characters, so `image LIKE '%powershell%'` finds the PowerShell process however its path is written:

```terminal
$ python minisiem.py search "SELECT ts, host, parent_image FROM events WHERE image LIKE '%powershell%'"
ts | host | parent_image
2026-11-03T06:14:00Z | WS-104 | C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE
```

Wildcards are convenient and costly. A leading wildcard (`%powershell%`) prevents the use of an index on most platforms and forces every event in the time range to be read. On 340 events that is irrelevant; on billions it decides whether the search finishes. Wildcards are also imprecise: `%banyan.example%` matches Banyan's own sites but not the look-alike `banyan-payroll-update.example`, and a careless pattern can match far more, or less, than intended. Prefer exact matches on normalised fields where the value is known, and wildcards where it is not.

### Absent values

Not every source populates every field, and how the platform treats an absent field changes the answer:

```terminal
$ python minisiem.py search "SELECT source, src_ip, COUNT(*) AS n FROM events WHERE source='windows' GROUP BY src_ip"
source | src_ip | n
windows | None | 3
windows | - | 10

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE src_ip <> '203.0.113.66'"
COUNT(*)
295

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE src_ip IS NULL"
COUNT(*)
36
```

Windows logon events (4624 and 4625) carry `src_ip` as the placeholder `-`, which is a real string value; the account-management and log-clearing events (4720, 4732, 1102) have no `src_ip` at all, which SQL represents as NULL. The second query is the trap. The dataset has 340 events, nine of them from 203.0.113.66, so "everything except that address" ought to be 331, but the query returns 295: the 36 events with a NULL `src_ip` (all 33 Sysmon events plus the three Windows events) are neither equal nor unequal to anything, so the condition silently excludes them. Exclusion filters ("not this user", "not this address", "not the allowlist") are where this bites hardest, because the events dropped are those from sources that lack the field, which are often the endpoint sources you most need. Check the fill rate of a field per source before relying on it; Lesson 5 showed the query that does this.

### Time ranges

Always constrain time, and state the range in the notes. A window around a known event is the most common investigative filter:

```terminal
$ python minisiem.py search "SELECT ts, source, event_id, user, image, url, target_user, bytes_out FROM events WHERE host='WS-104' AND ts BETWEEN '2026-11-03T06:10:00Z' AND '2026-11-03T06:20:00Z' ORDER BY ts"
ts | source | event_id | user | image | url | target_user | bytes_out
2026-11-03T06:12:00Z | proxy | None | divya | None | https://banyan-payroll-update.example/invoice.docm | None | 812
2026-11-03T06:14:00Z | sysmon | 1 | divya | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | None | None | None
2026-11-03T06:17:00Z | proxy | None | divya | None | https://cdn-telemetry-sync.example/api/v2/ping | None | 220
```

Ten minutes around the R1 alert at 06:14 tell the story in three lines: a macro-enabled document (`invoice.docm`) downloaded from a look-alike domain at 06:12, PowerShell at 06:14, and the first request to the beacon domain at 06:17. No rule joined these; a time-boxed search on one host did.

## Aggregations: seeing the shape of the data

Lists of events are for reading; aggregations are for understanding many events at once. The core functions are few: `COUNT(*)` counts rows, `COUNT(field)` counts rows where the field is not null, `COUNT(DISTINCT field)` counts different values, and `SUM`, `MIN` and `MAX` summarise numbers and times. `GROUP BY` decides what each output row represents, `HAVING` filters on the aggregated values, and `ORDER BY ... LIMIT` turns the result into a top-N or bottom-N list.

```terminal
$ python minisiem.py search "SELECT src_ip, COUNT(DISTINCT user) AS users_failed FROM events WHERE source='vpn' AND outcome='failure' GROUP BY src_ip HAVING users_failed >= 5"
src_ip | users_failed
203.0.113.66 | 8
```

This is the question "which source addresses failed against five or more different accounts?" Counting distinct users rather than events is what distinguishes a password spray (one address, many accounts, few attempts each) from a single user mistyping a password many times. `HAVING` is applied after grouping, so it can test the count; `WHERE` is applied before and cannot. Correlation rule R2 (Lesson 4) is this aggregation with a join to the later success added.

### Stacking: the rare and the regular

Stacking counts how often each value of a field occurs and examines both ends of the list. Adding a distinct count of hosts shows how widespread each value is:

```terminal
$ python minisiem.py search "SELECT url, COUNT(DISTINCT host) AS hosts, COUNT(*) AS n FROM events WHERE source='proxy' GROUP BY url ORDER BY hosts ASC, n ASC"
url | hosts | n
https://banyan-payroll-update.example/invoice.docm | 1 | 1
https://files-share-drop.example/upload | 1 | 1
https://cdn-telemetry-sync.example/api/v2/ping | 1 | 18
https://crm.banyan.example/ | 8 | 37
https://intranet.banyan.example/ | 8 | 37
https://maps.example.net/ | 8 | 45
https://cdn.example.org/ | 8 | 46
https://news.example.com/ | 8 | 48
https://mail.banyan.example/ | 8 | 51
```

Six destinations were visited by all eight workstations; three were visited by exactly one, and all three belong to the intrusion. Two are single requests (the document download and the 48 MB upload); the third was contacted 18 times by one host, which is rare in breadth but frequent in count, a pattern typical of automated traffic. Stacking does not prove anything is malicious. A newly installed legitimate agent also contacts one domain regularly from one host. It produces a short list of values worth a pivot, and in a real organisation with thousands of destinations it is one of the most productive searches a hunter can run (Module 10).

## Pivoting: following an entity across sources

A pivot takes a value from one result and makes it the filter of the next search. Normalisation is what makes pivots possible: because every source calls the workstation `host` and the account `user`, one value can be followed from proxy to endpoint to Windows logs without translating field names. The worked investigation below starts from rule R6's beacon alert and follows two threads.

**Pivot 1: from the domain to the host and user.**

```terminal
$ python minisiem.py search "SELECT host, user, COUNT(*) AS hits, MIN(ts) AS first_seen, MAX(ts) AS last_seen FROM events WHERE url LIKE '%cdn-telemetry-sync.example%' GROUP BY host, user"
host | user | hits | first_seen | last_seen
WS-104 | divya | 18 | 2026-11-03T06:17:00Z | 2026-11-03T07:42:02Z
```

One host and one user, 18 requests between 06:17 and 07:42. `MIN` and `MAX` of `ts` turn a list into a time span, which is what scoping needs.

**Pivot 2: from the host to everything else it did.** Excluding the noisy proxy source leaves the host's endpoint and Windows events:

```terminal
$ python minisiem.py search "SELECT ts, source, event_id, image, parent_image, url, target_user, bytes_out FROM events WHERE host='WS-104' AND source<>'proxy' ORDER BY ts"
ts | source | event_id | image | parent_image | url | target_user | bytes_out
2026-11-03T03:18:00Z | windows | 4624 | None | None | None | None | None
2026-11-03T03:29:00Z | sysmon | 1 | C:\Program Files\App\excel.exe | C:\Windows\explorer.exe | None | None | None
2026-11-03T04:31:00Z | sysmon | 1 | C:\Program Files\App\explorer.exe | C:\Windows\explorer.exe | None | None | None
2026-11-03T04:50:00Z | sysmon | 1 | C:\Program Files\App\outlook.exe | C:\Windows\explorer.exe | None | None | None
2026-11-03T05:14:00Z | sysmon | 1 | C:\Program Files\App\msedge.exe | C:\Windows\explorer.exe | None | None | None
2026-11-03T06:14:00Z | sysmon | 1 | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE | None | None | None
2026-11-03T07:02:00Z | windows | 4720 | None | None | None | svc_update | None
2026-11-03T07:03:00Z | windows | 4732 | None | None | None | svc_update | None
2026-11-03T08:17:00Z | windows | 1102 | None | None | None | None | None
```

The morning is routine: a logon and four ordinary applications started by Explorer. Then PowerShell started by Word at 06:14, a new account `svc_update` created (4720) and added to a group (4732) at 07:02-07:03, and the Security log cleared (1102) at 08:17. A proxy pivot on the same host adds the 48,200,000-byte upload to `files-share-drop.example` at 08:12, five minutes before the log was cleared.

**Pivot 3: from the VPN alert's address to the account and back to a host.**

```terminal
$ python minisiem.py search "SELECT ts, user, src_ip, json_extract(raw, '$.country') AS country, outcome FROM events WHERE source='vpn' AND outcome='success'"
ts | user | src_ip | country | outcome
2026-11-03T06:46:00Z | gopal | 203.0.113.66 | ?? | success
2026-11-03T13:33:00Z | gopal | 198.51.100.104 | IN | success

$ python minisiem.py search "SELECT ts, source, host, event_id, url FROM events WHERE user='gopal' AND ts BETWEEN '2026-11-03T06:30:00Z' AND '2026-11-03T07:30:00Z' ORDER BY ts"
ts | source | host | event_id | url
2026-11-03T06:42:42Z | vpn | None | None | None
2026-11-03T06:46:00Z | vpn | None | None | None
2026-11-03T07:22:00Z | proxy | WS-107 | None | https://intranet.banyan.example/
```

`json_extract(raw, '$.country')` reads a field that has no column, showing why keeping the raw event matters. The account `gopal` logged in through the VPN at 06:46 from the spraying address with an unknown country (`??`), while his other VPN logon that day, at 13:33, came from 198.51.100.104 with country `IN`. Pivoting on the user over the following hour shows his own workstation, WS-107, browsing the intranet at 07:22. The data does not say who used which session; it raises a precise question for the analyst to put to the user and the VPN team: was gopal working from his office desk while a VPN session in his name was open from an unknown location? That is the value of a pivot: it turns a vague alert into a specific, answerable question.

## From SQL to production query languages

The operations in this lesson exist in every SIEM language; only the spelling changes. SQL states the whole query as one statement whose clauses run in a fixed logical order (`FROM`, then `WHERE`, then `GROUP BY`, then `HAVING`, then `SELECT`, then `ORDER BY`). The common SIEM languages are instead **pipelines**: the query starts from a set of events and passes it through a sequence of stages separated by `|`, each stage transforming the output of the one before. Reading a pipeline left to right is therefore reading the analyst's reasoning in order, which is one reason they suit investigation.

| Operation | SQL in minisiem | Pipeline idea (SPL, KQL, ES&#124;QL) |
| --- | --- | --- |
| Choose data | `FROM events` | Start from an index, table or data stream |
| Time range | `WHERE ts BETWEEN ...` | Usually a time picker or a time filter stage |
| Filter | `WHERE source='vpn'` | A filtering stage (`where` in KQL, `WHERE` in ES&#124;QL; search terms in SPL) |
| Aggregate | `GROUP BY src_ip` with `COUNT(DISTINCT user)` | A statistics stage (`stats` in SPL, `summarize` in KQL, `STATS ... BY` in ES&#124;QL) |
| Filter aggregates | `HAVING users_failed >= 5` | A filtering stage placed after the statistics stage |
| Sort and limit | `ORDER BY n DESC LIMIT 10` | Sort and limit stages |

The last two rows show a practical advantage of pipelines: there is no separate `HAVING`, because a filter placed after the statistics stage naturally filters the aggregated rows. Every product also adds its own functions for time bucketing, parsing at search time, lookups against reference tables and joins, and each has rules about case sensitivity, null handling and wildcard cost that you must learn from its documentation rather than assume. Module 4, Lesson 7 returns to query writing on real log types; the Lesson 8 lab of this module uses Wazuh and Elastic.

## Search performance and cost

On 340 events every query is instant. On a production SIEM holding billions of events, the same habits decide whether a search finishes in seconds, minutes or not at all, and whether it slows the correlation searches that everyone depends on.

**Narrow time first.** Storage is organised by time on nearly every platform, so a tight time range is the single most effective way to limit the data read. minisiem's `load` creates an index on `ts` for the same reason.

**Filter on indexed or normalised fields early.** Conditions on fields the platform indexes (source, host, event ID) remove most events cheaply; conditions that require parsing raw text or a leading wildcard force a full read of whatever remains.

**Aggregate before returning.** Returning a million rows to the browser to count them by eye is slow and unreadable; let the SIEM count and return twenty rows.

**Limit while exploring.** When inspecting raw events, take ten or twenty with a limit; you need to see their shape, not all of them.

**Mind joins.** Joining large sets to each other is expensive in every product. Rule R2's self-join works on ten VPN events; on a real VPN log it would be restricted to a short time window and to failures above a threshold first.

## Common mistakes and misconceptions

**Concluding absence from an empty result.** Zero rows can mean nothing happened, the field is named differently for this source, the value differs in case, the field is null, the time range is wrong, or the source was not ingested. Before writing "no activity", try a broader version of the same search and confirm the source sent data in that window.

**Exclusion filters that drop nulls.** `src_ip <> '203.0.113.66'` returned 295 events, not 331, because NULLs are neither equal nor unequal. Use explicit `IS NULL` handling when exclusions matter.

**Mixing time zones.** A window written in IST against data stored in UTC is 5 hours 30 minutes off and returns the wrong events, which may look entirely plausible.

**Summarising before inspecting.** A count per host of a broken field looks as clean as a correct one; look at raw events first.

**Unrecorded queries.** "I searched and found nothing" is not evidence. The exact query, the time range and the time it was run are.

**Over-trusting one source.** The proxy dominates the Banyan data (284 of 340 events), but the account creation and log clearing appear only in Windows events, and the spray only in VPN events.

## Security implications, detection and defence

**Search access is privileged access.** A SIEM search can read authentication records, browsing history and process command lines across the whole organisation. Access should be role-based (for example, restricting HR-related or privileged-account data to named roles), and every search should be logged with the user, the query and the time. Under the DPDP Act 2023, personal data in logs is processed for a purpose (security monitoring), and searches that go beyond it are a misuse an audit should be able to detect.

**Query injection and free-form SQL.** minisiem passes the analyst's text straight to SQLite, which is safe only because one person uses it on a local copy. A multi-user SIEM must never build queries by pasting untrusted input (for example a value taken from an alert or an email) into query text, and it must sandbox what a query can do. minisiem's `load` itself uses parameterised inserts for exactly this reason.

**Searches as evidence.** Case notes that record the query, range and result allow peer review and, if needed, reproduction in a legal or regulatory context. Exporting result sets with hashes is covered in Module 8.

**Attackers and search.** An intruder with SIEM access can learn what the SOC sees and which rules exist. SIEM accounts should have MFA, and search activity by unusual accounts or at unusual times is itself worth monitoring.

## Best practices

- Write the question first, then set the time range before any other filter.
- Use normalised field names, and check each field's fill rate per source before relying on it.
- Normalise case explicitly (`lower()` or the product's case-insensitive operator) when matching names and paths.
- Inspect a few raw events before aggregating.
- Use `COUNT(DISTINCT ...)`, `MIN(ts)` and `MAX(ts)` to scope entities; stack values to find the rare and the regular.
- Pivot on one entity at a time and note the field used for each pivot.
- Record every query, its time range and when it was run in the case.
- Treat an empty result as a question about the query and the data, not as an answer.

## Key takeaways

- Searching is query thinking: question, time range, filter, inspect, aggregate, pivot, record, and loop.
- Filters fail quietly: in minisiem `host='ws-104'` returned 0 of 58 events, and an exclusion on `src_ip` silently dropped 36 events with no address.
- Aggregations show shape: distinct counts separate sprays from typos, and stacking found the three one-host destinations of the intrusion.
- Pivots follow entities across sources; normalised `host`, `user` and `src_ip` fields make them possible.
- SPL, KQL and ES|QL are pipelines expressing the same operations; learn each product's rules for case, nulls and cost.
- Search access is privileged; log it, restrict it and record every investigative query as evidence.
