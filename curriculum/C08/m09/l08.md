## Lab objective and evidence boundaries

You will prepare a phishing-triage handoff using the course's fictional Banyan Microfinance records. The lesson combines a read-only scope check with an evidence review, a response recommendation and a written case update. The objective is to reach a defensible decision from incomplete evidence. Real investigations often begin this way. An earlier report may mention an invoice, while the proxy and endpoint records arrive before original mail. The team still needs a protective action supported by the available sources and a clear request for missing evidence.

Use the C08 lab kit and its `banyan_events.jsonl` file. The exercise cells below interpret saved records. No suspicious message is opened and no destination is contacted. Keep the training data local. The three domain names use the reserved example namespace and are treated as text values in the dataset. The course fixture represents proxy, Sysmon, Windows and VPN records. It does not contain original mail, mail gateway delivery, cloud identity audit, user reports or decoded document content. An observation about a request in the proxy dataset therefore cannot establish how the destination first reached the user.

## Step 1: Count the matching proxy and VPN records

Run the following Python in the folder containing the extracted fixture. The script opens the saved data as text, parses JSON lines and groups exact host matches from proxy URLs. The URL parser only separates text fields. It does not open a connection. The resolved path is relative to your working folder, so check the filename and location if Python cannot read it.

```python
import json
from pathlib import Path
from urllib.parse import urlsplit

rows = [json.loads(line) for line in Path("banyan_events.jsonl").read_text(
    encoding="utf-8"
).splitlines()]
case_hosts = {
    "banyan-payroll-update.example",
    "cdn-telemetry-sync.example",
    "files-share-drop.example",
}
for domain in sorted(case_hosts):
    hits = [
        row for row in rows
        if row.get("source") == "proxy"
        and urlsplit(row.get("url", "")).hostname == domain
    ]
    hosts = sorted({row["host"] for row in hits if row.get("host")})
    first = min((row["@timestamp"] for row in hits), default="-")
    last = max((row["@timestamp"] for row in hits), default="-")
    print(domain, len(hits), ",".join(hosts), first, last)

vpn = [
    row for row in rows
    if row.get("source") == "vpn"
    and row.get("src_ip") == "203.0.113.66"
]
failed_users = {row["user"] for row in vpn if row.get("outcome") == "failure"}
successes = sorted(
    (row["@timestamp"], row["user"])
    for row in vpn if row.get("outcome") == "success"
)
print("VPN distinct failed users:", len(failed_users))
for timestamp, user in successes:
    print("VPN success:", timestamp, user)
```

The following output was obtained from the course's saved fixture. The proxy columns show the exact requested hostname, matching rows, observed hosts, first time and last time. The VPN lines show the number of distinct identities with failures and the later success.

```text
banyan-payroll-update.example 1 WS-104 2026-11-03T06:12:00Z 2026-11-03T06:12:00Z
cdn-telemetry-sync.example 18 WS-104 2026-11-03T06:17:00Z 2026-11-03T07:42:02Z
files-share-drop.example 1 WS-104 2026-11-03T08:12:00Z 2026-11-03T08:12:00Z
VPN distinct failed users: 8
VPN success: 2026-11-03T06:46:00Z gopal
```

Every proxy match returned by this check names WS-104. That is a bounded statement about three exact hostnames in the available fixture. It says nothing about domains the search did not include, traffic that bypassed proxy collection, or additional mail recipients. The eighteen rows name one observed host, not eighteen affected users. Write the positive observations and the scope limit beside each other. A reviewer should be able to distinguish a low count caused by a narrow search from a true high-confidence exclusion.

The VPN results answer a different question. There are eight distinct identities with a failure from the selected address, and the data records a successful authentication for gopal. The query does not show the user behind the session or any later session activity. The VPN records do not name a host, and the ordinary workstation associated with an account in inventory is not the observed source device. Keep the authentication as an identity lead with a separate owner. A defensive analyst can ask the VPN team to verify session and source details without assuming it is the same actor as the workstation case.

### Visual Walkthrough & Architectural Breakdown

The first row is the endpoint thread. It puts the proxy download, process event and follow-on network records in one review path because they name the same asset and are in a meaningful time order. There is substantial evidence of a workstation event requiring response. Individual records still support different claims. The proxy records do not describe execution and the process event does not tell you the exact contents of the file or remote transfer. The assessment should preserve the difference between the available facts and the analyst's explanation of their relationship.

The second row is the VPN thread. Several identities have failures and one later authenticates successfully from the same source. Consider the success as an actionable identity lead. The source does not name the workstation or provide later session records. When you route that item to an identity owner, ask for authentication context and a verified response rather than stating that the VPN session controlled WS-104. A lead could later find an additional link, but there is no reason to close the endpoint case or postpone identity protection while waiting for one.

The third row is deliberately empty of direct observations. The fixture provides no original mail, delivery trace or recorded employee report. Your findings should therefore refer to those records as requested evidence. A learner who writes ?only one mailbox received the message? has moved from asset scope to delivery scope without a source. If later trusted delivery data confirms additional recipients, you can add that scope without changing what the proxy query found.

The last column takes each row to a specific role. The endpoint owner verifies the state and containment of WS-104. The identity owner reviews the authentication and related sessions. The mail team checks original message and delivery data through the authorised route when available. These actions can proceed in parallel. ## Review and troubleshoot the work

If the proxy check produces zero rows for a hostname, first confirm that the file is the C08 fixture and that the parsed field is present. Compare the lane names in the fixture with those selected by the script. Checking the wrong file or a changed version can cause an empty result. Preserve a note of the version used and avoid changing only the query until it returns the expected count. If an event appears later or earlier than the course example, confirm UTC and check whether you copied the field from the source or from an enriched view.

Have a second student audit three conclusions. Ask them to point to the record that supports the endpoint action, the data gap that prevents definite mail scope and the evidence that bounds the VPN finding. Then ask them to locate the action owner, approval status and verification method for each proposed action. For a deliberate error, change ?available proxy records show one host? to ?one user received the message.? A reviewer should reject the second statement and be able to explain what source would be required. This is a check of reasoning and source coverage as much as a check of the answer.

For a second variation, suppose the authorised mail owner later confirms five deliveries and one blocked message in an additional hypothetical record. Update the handoff with the new source, time and disposition. Do not revise the proxy count. Then suppose the only observed access to a link from another mailbox was an automated preview. Record the preview as service activity and leave human interaction unknown. The updated exercise illustrates why later facts should add to or revise a particular assessment without silently changing the historical record of what the analyst knew.

## Key takeaways

- Read the saved records and preserve a traceable observation before drawing a conclusion.
- Report search scope and visibility explicitly, especially for negative results.
- Route the endpoint, identity and mail decisions to the appropriate owners.
- A verified lab output and a proposed operational response are different deliverables.
