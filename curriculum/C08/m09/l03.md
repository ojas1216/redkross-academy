## Introduction and conceptual foundation

Lesson 2 ended with a question that static checks often cannot answer. You can hash an attachment, look the hash up, read the file type from its magic bytes, notice that an "invoice" is a macro-enabled Word document, and see that the link in the message points to a domain registered last week. All of that tells you the file is *suspicious*. It does not tell you what the file *does*: which programs it starts, which addresses it contacts, what it writes to disk, how it tries to survive a reboot. Those are the facts that decide scope (who else received it, which hosts must be checked), containment (which domains to block, which persistence to remove) and detection (which behaviour to hunt for across the estate).

A **sandbox** answers that question by running the suspicious object in an isolated, instrumented environment and recording its behaviour. The SOC analyst rarely builds or operates the sandbox; that is usually the job of a malware analysis or platform team. The analyst's job is to decide *whether* an object should go to a sandbox, *which* sandbox it may go to, and then to *read the report* critically: separating the evidence from the vendor's verdict, spotting what the run could not show, and turning behaviour into indicators and actions.

This lesson is written entirely from that defender's side. It explains what a sandbox report contains and how to read each part, why a clean report is not proof of innocence, what evasion looks like at a conceptual level so that you recognise its fingerprints, and, just as important, what you must check before any sample leaves your organisation. It does not teach how to handle, detonate or modify live malware: in a real SOC that work is done only by authorised staff in purpose-built, segregated infrastructure under a written procedure, and the course lab contains no live malware at all.

> [!IMPORTANT]
> Submitting a file to a sandbox is a disclosure decision, not just a technical step. A user's attachment may contain customer records, contracts or salary data. Treat every upload as you would treat emailing the file to an outside party: it needs a reason, an approved destination and a record in the case.

The examples follow the course's fictional company, Banyan, and its synthetic day of telemetry in `LAB_ASSETS/C08/banyan_events.jsonl`. In that dataset, the finance user `divya` on `WS-104` downloads `invoice.docm` from `banyan-payroll-update.example` at 06:12Z, and two minutes later Word starts a hidden PowerShell process. We will use those real dataset events to show what a sandbox report of such a document would be expected to reveal, and how its findings line up with the endpoint and proxy evidence you already have.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Sandbox | An isolated, instrumented environment that executes a file or opens a URL and records its behaviour for analysis. |
| Detonation | The act of executing or opening a sample inside a sandbox so that its behaviour can be observed. |
| Dynamic analysis | Learning what a sample does by running it and observing it, as opposed to static analysis, which examines it without running it. |
| Analysis VM / guest | The virtual (or physical) machine inside the sandbox in which the sample runs, built to resemble a normal workstation. |
| Process tree | The parent-child structure of every process the sample started or caused, with command lines. |
| Behavioural signature | A rule in the sandbox that names a behaviour (for example "Office application spawned a script interpreter") and contributes to the score. |
| Verdict / score | The sandbox's summary judgement (malicious, suspicious, clean or a number). An opinion derived from signatures, not evidence in itself. |
| Artefact | Anything the run produced that can be examined: dropped files, memory dumps, packet captures, screenshots. |
| Sandbox evasion | Behaviour by which malware detects that it is being analysed, or avoids running its real logic during analysis (MITRE ATT&CK T1497, Virtualization/Sandbox Evasion). |
| Public sandbox | A sandbox service on the internet open to anyone; submissions are often retained and may be visible to other users. |
| Private sandbox | A sandbox run by the organisation or a contracted provider under an agreement, where submissions are not shared. |

## Where sandboxing fits in phishing triage

Sandboxing is the expensive step in the triage chain, so it comes after the cheap ones. A sensible order is:

1. **Header and sender checks** (Lesson 1): is the message authenticated, who really sent it, is it part of a wider wave?
2. **Static URL and attachment checks** (Lesson 2): hashes, file type, reputation, lookalike domains, macros present or not.
3. **Known-answer lookups**: has this exact hash, URL or domain already been seen and classified, in your own case history, your threat intelligence platform or an approved reputation service? A hash lookup discloses only the hash, not the content.
4. **Dynamic analysis** only when the answer still matters and is still unknown: the object is new, the static checks are inconclusive or alarming, and its behaviour would change what you do.

Many reported emails never reach step 4. A credential-phishing message with a link to a fake login page needs URL analysis and a check of who clicked, not a full detonation of an attachment it does not have. A known commodity sample whose hash is already classified with high confidence does not need to be run again; its existing report can be retrieved. Running everything wastes sandbox capacity and, worse, multiplies the number of times sensitive files leave their owner's control.

When dynamic analysis is warranted, the sandbox provides facts no other source in triage can: what would have happened on a victim's machine, in a controlled place where nothing real is harmed. In the Banyan case, the endpoint telemetry already shows part of the answer, because the document was opened on a real workstation. The sandbox is then used to fill the gaps the endpoint sensors did not capture (for example, files written and registry changes that the Sysmon configuration did not log) and to give a clean, repeatable account of the sample's behaviour that can be compared with the real host.

## Inside a sandbox: how a run works

You do not need to build a sandbox to read its report well, but you do need a mental model of what it observes and how, because every limit in the report follows from that model.

A sandbox platform has a **controller** that receives submissions, queues them and schedules runs; a pool of **analysis guests**, which are virtual machines (sometimes bare-metal machines) prepared to look like ordinary workstations, with an office suite, a browser, a PDF reader and realistic user files; and a set of **monitors** that record what happens inside and around each guest. For each run the controller restores a guest to a clean snapshot, copies the sample in, opens or executes it (often simulating a user: moving the mouse, clicking "Enable content" on a document's banner, scrolling), lets it run for a configured time, then collects everything the monitors captured and resets the guest.

The monitors are of three kinds:

- **In-guest monitoring** hooks or traces the operating system's interfaces, recording process creation, file operations, registry operations, API calls and loaded modules. Some platforms do this from inside the guest with an agent; others observe from the hypervisor, which is harder for the sample to see.
- **Network capture** records all traffic leaving the guest. Many platforms route it through a controlled path: some simulate internet services (answering every DNS query and HTTP request with a fake response), some allow real outbound traffic through an anonymising route, and some block it entirely. This choice strongly affects what the report can show.
- **Post-run collection** gathers dropped files, memory dumps, screenshots and the full packet capture, and runs static analysis and signatures over them.

Finally, a **scoring engine** evaluates behavioural signatures over everything collected and produces the verdict. The report you read is the output of that pipeline.

Open-source platforms such as CAPE (a descendant of the Cuckoo Sandbox project) follow this architecture, as do the commercial sandboxes built into many email security gateways and EDR products. The details of their reports differ, but the four core sections, which are the subject of the next part of this lesson, appear in nearly all of them.

**Purpose.** The diagram explains where each section of a sandbox report comes from. An analyst who knows which component observed a behaviour can judge how much weight the observation deserves and what the run could not have seen.

**Components.** The slate box **Submitted sample** ("file or URL + run options") is what the analyst sends: the object itself, plus settings such as run time, guest image and network mode. The two orange boxes are the observers: the **In-guest / hypervisor monitor** ("processes, files, registry, APIs") and **Network capture** ("DNS, HTTP/TLS, PCAP"). The four green boxes are the evidence sections of the report: **Process tree**, **File activity**, **Registry activity** and **Network activity**. The dark box, **Signatures and verdict** ("an opinion built on the evidence"), is the summary most people read first.

**Relationships and arrows.** Arrows run in the direction of data. The sample goes to the controller, which **detonates** it in the guest. The guest's behaviour flows to the two monitors. The in-guest monitor feeds three report sections (process, file and registry activity); the network capture feeds the network section alone. All four evidence sections flow into the signatures and verdict, never the other way: the verdict is derived from the evidence.

**Execution flow.** Submission, queueing, snapshot restore, detonation with simulated user activity, observation for the configured run time, collection, scoring, report.

**Decision logic.** There are no branches in the diagram, but there is an implicit one at the end: the analyst decides what to do with the verdict. That decision should be made by reading the green boxes, not by copying the dark one.

**Technical interpretation.** The **process tree** lists each process with its parent, command line and often its integrity level; it is the backbone of the report, because almost every other behaviour is attributed to a process in it. **File activity** lists files created, modified or deleted, with paths and hashes of dropped files. **Registry activity** lists keys and values written, especially those under autostart locations such as the `Run` keys, which indicate persistence. **Network activity** lists DNS queries, connections, HTTP requests (with host, path and user agent) and, for TLS, the server name and certificate details, plus the packet capture.

**Practical example.** For a document like Banyan's `invoice.docm`, you would expect the process tree to show the word processor starting a script interpreter, the network section to show a DNS query for an unfamiliar domain followed by HTTPS requests, and the file and registry sections to show whether anything was written for later stages or persistence.

**Security implications.** Each monitor has blind spots. If the sample detects the analysis environment, the in-guest sections may be nearly empty. If the network mode blocks traffic, the network section shows attempts but not what the server would have sent. If the run is short, behaviour scheduled for later never appears.

**Key learning.** A sandbox report is four bodies of evidence and one opinion. Base your decisions on the evidence sections and use the verdict only as a pointer to where to look.

## Reading each section critically

### The process tree

Start here. Find the process that represents the sample being opened (for a document, the office application; for an executable, the sample itself) and read downwards. The questions are the same ones you asked of endpoint telemetry in earlier modules: is this parent-child relationship normal? Is the command line normal for this program? Is anything running from a user-writable location such as a temporary or downloads folder?

In the Banyan dataset, the real workstation produced exactly the kind of record a sandbox process tree would show. This is the Sysmon process-creation event from `banyan_events.jsonl`, reformatted for reading:

```json
{
  "@timestamp": "2026-11-03T06:14:00Z",
  "source": "sysmon",
  "event_id": 1,
  "host": "WS-104",
  "user": "divya",
  "parent_image": "C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE",
  "image": "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
  "command_line": "powershell.exe -NoP -W Hidden -EncodedCommand <redacted-for-course>"
}
```

`WINWORD.EXE` is the parent, and Word has no ordinary business starting PowerShell. The command line options are each a warning sign in this context: `-NoP` (short for `-NoProfile`) skips the user's PowerShell profile, `-W Hidden` (`-WindowStyle Hidden`) hides the window from the user, and `-EncodedCommand` takes the command as Base64-encoded text, which hides its content from a casual reader. The course redacts the encoded command. In a real report you would read the decoded form in the analysis platform, never by pasting it into a public website.

### Network activity

The network section turns behaviour into indicators you can search for and block. Read the DNS queries first (which names did the sample resolve?), then the connections and requests (which hosts, paths and user agents?). Separate the noise of the guest operating system (update checks, certificate revocation lookups, time synchronisation) from traffic that the process tree attributes to the sample's processes.

The real host in the Banyan dataset shows what to expect. Three minutes after PowerShell started, the proxy recorded the first of 18 requests to the same URL, each one sending 220 bytes, about five minutes apart. The first three, from `banyan_events.jsonl` (fields reordered for reading):

```json
{"@timestamp": "2026-11-03T06:17:00Z", "source": "proxy", "host": "WS-104", "user": "divya", "url": "https://cdn-telemetry-sync.example/api/v2/ping", "bytes_out": 220, "status": 200}
{"@timestamp": "2026-11-03T06:22:01Z", "source": "proxy", "host": "WS-104", "user": "divya", "url": "https://cdn-telemetry-sync.example/api/v2/ping", "bytes_out": 220, "status": 200}
{"@timestamp": "2026-11-03T06:27:03Z", "source": "proxy", "host": "WS-104", "user": "divya", "url": "https://cdn-telemetry-sync.example/api/v2/ping", "bytes_out": 220, "status": 200}
```

A sandbox run of the same document would be expected to record the DNS query for `cdn-telemetry-sync.example` and the first request. Whether it records the second depends on the run time: if the run lasts only a few minutes, a five-minute beacon may appear once or not at all. A single connection in a report does not tell you the sample beacons; the host telemetry does.

### File and registry activity

These sections answer two containment questions: did the sample leave anything behind, and did it arrange to run again? Look for executables, scripts or libraries written to user-writable folders; scheduled tasks; services; and values written to autostart registry locations. Record the path and hash of every dropped file, because those become the search terms for checking other hosts.

The Banyan dataset does not contain file or registry events for `WS-104`; its Sysmon configuration logged process creation, not file creation or registry writes. That is precisely the gap a sandbox can fill. If the sandbox shows the sample writing a file or an autostart value, you now know what to look for on the real host and across the estate, even though your own telemetry never recorded it. If the sandbox shows nothing, you have not proved that nothing happened on the host; you have learned only that nothing happened in the sandbox during that run.

### Signatures and the verdict

The signatures section lists the named behaviours the platform matched, such as "Office application spawned a script interpreter", "process started with a hidden window" or "contacted a recently registered domain", each with a weight. The verdict is their weighted sum or a classification derived from them. Use the signature list as an index to the evidence: each signature should point to specific lines in the process, file, registry or network sections, and you should confirm that it does. A signature that fires on the guest's own background behaviour is a false positive inside the report, and a high score made up of weak signatures is weaker than a moderate score made of one decisive one.

> [!TIP]
> Copy evidence, not adjectives, into the case. "Sandbox says malicious, score 9/10" helps nobody at the next stage. "Sandbox run shows WINWORD.EXE spawning hidden PowerShell with an encoded command, then DNS and HTTPS to cdn-telemetry-sync.example" lets the next analyst search, block and hunt.

## Limits of sandboxing and evasion awareness

A sandbox shows what a sample did, in one environment, for one run. Every conclusion you draw has to carry those three qualifiers. The limits fall into two groups: those that come from the sandbox itself, and those that the sample's authors create on purpose.

### Limits that come from the sandbox

- **Run time.** Runs are short, often a few minutes, because capacity is finite. Anything the sample does later (a second stage fetched after an hour, a scheduled task that fires tomorrow, an operator who connects interactively) is outside the window. In the Banyan dataset, the local account `svc_update` was created at 07:02Z and added to Administrators at 07:03Z, 48 minutes after PowerShell started; a short sandbox run of the document would not be expected to show that, and it may not have been automated at all.
- **Environment.** The guest has one operating system version, one office version, one language and locale, and no access to your domain, your file shares or your users' real data. A sample that targets a different version, or that needs to reach an internal server, may do nothing visible.
- **Network mode.** If outbound traffic is blocked or simulated, a downloader cannot fetch its next stage, so the report shows the attempt but not the payload. If traffic is allowed out, the run may alert the operator that their sample is being analysed. Neither choice is wrong; you need to know which one was used.
- **User interaction.** Some samples act only after a convincing human action: enabling content, clicking through a dialog, entering a password into a form, scrolling to a page. Sandboxes simulate some of this, never all of it.
- **Monitoring gaps.** A monitor sees what it is built to see. Activity carried out through mechanisms the monitor does not instrument will be absent from the report.

### Evasion, at the level a defender needs

Malware authors know their samples will be analysed, and many samples are built to behave innocently when they suspect it. MITRE ATT&CK records this as technique T1497, Virtualization/Sandbox Evasion. You do not need to know how to build evasion; you need to recognise its fingerprints in a report so that a quiet result is not mistaken for a clean one. Conceptually, evasion takes four forms:

- **Environment checks.** The sample looks for signs of an analysis machine (virtualisation artefacts, analysis tools, an unrealistically small disk or memory, a freshly installed system with no user history) and exits or does something harmless if it finds them.
- **Interaction checks.** The sample waits for evidence of a real person (mouse movement, a certain number of clicks, recently opened documents) before acting.
- **Timing.** The sample sleeps or delays past the likely run time, or acts only on a certain date.
- **Targeting.** The sample, or the server it contacts, checks location, language, domain membership or the requesting address, and delivers the real payload only to intended victims. A server can simply decline to answer anyone who does not look like a target.

The fingerprints in a report are indirect: a process that starts and ends almost immediately; a long sleep followed by nothing; queries that read hardware or system information and then an exit; a document that clearly contains active content but produces no child process; a network request that receives an empty or error response. When you see these, record the result as **inconclusive**, not clean, and fall back to other evidence: the static findings from Lesson 2, the delivery context from Lesson 1, and what the endpoint and proxy logs show on any host where the object was really opened.

> [!WARNING]
> "The sandbox says clean" is never by itself a reason to close a phishing case. A clean result from a sample with active content, a suspicious sender and a lookalike domain is an inconclusive result. Escalate it to the malware analysis function under your playbook rather than releasing the message to users.

## Before you upload: privacy and data handling

The most common real-world sandbox mistake by SOC analysts is not a misread report. It is a disclosure. Public sandboxes are valuable community resources, and that is exactly why they are risky: on many public services, submissions are retained, reports are searchable by other users, and in some cases the submitted file itself can be downloaded by other users or subscribers. Anything you upload should be assumed to be visible to strangers, including, potentially, the attacker who sent it, who can see that their sample has been found.

What can leak through a single upload:

- **The content of the file.** A real invoice, contract or spreadsheet attached to a phishing email (or a legitimate document wrongly reported as phishing) may contain personal data of customers or staff, financial details or confidential business information.
- **Identifiers inside the sample.** Phishing documents and links are often personalised: the recipient's email address embedded in a URL, a name in the document body, a tracking token tied to one person.
- **Your organisation's identity and response.** Filenames, internal hostnames in screenshots and the timing of submissions tell observers who received the campaign and when you noticed it.
- **Shared intelligence under restriction.** A sample received from a sharing partner under TLP:AMBER or TLP:RED (Module 5) must not be placed on a public service; doing so breaks the terms on which it was shared.

In India, uploading a file that contains personal data of customers or staff to a third-party service is processing of digital personal data, and the Digital Personal Data Protection Act 2023 places obligations on the organisation (the data fiduciary) for how that data is processed and protected. Your organisation's policy, not your own judgement on the night, decides which services are approved for which kinds of data. A SOC should have that decision written down before the first case needs it.

**Relationships and arrows.** Arrows show the order of decisions and are labelled with the answer that leads along them. A "yes" on the first question goes to the existing report; a "no" continues. **Execution flow.** Check the digest in approved internal sources first. A digest does not disclose the file bytes, but a third-party lookup can still reveal interest in a specific file. Only if the object is unknown do you consider running it, and then the destination is decided by what the file contains and by the terms on which you hold it.

**Decision logic.** Uncertainty is treated as "yes, it contains data". The public service is reachable after a "no" on both the prior report and data questions and a "yes" on sharing approval, so it is the exception, not the default.

**Technical interpretation.** The private sandbox may be run by the organisation, provided inside its email or endpoint security platform, or contracted from a provider whose terms state that submissions are not shared. Which of these exist, and which are approved for which data, is a policy fact the analyst looks up rather than decides.

**Practical example.** Banyan's `invoice.docm` was delivered to a finance approver. The analyst first looks up its hash; suppose there is no match. The document may contain the recipient's details, and the analyst cannot be sure it does not, so the answer to the data question is "unsure", which leads to the private sandbox. The upload is recorded in the case with the time, the platform and the reason.

**Security implications.** Skipping this check can turn a contained phishing case into a data-protection incident of the SOC's own making, and can tip off the attacker. Following it costs a few minutes.

**Key learning.** Look up before you upload, treat "unsure" as "contains data", and record every submission. Public sandboxes are for objects you would be content to publish.

## Worked example: reading a report into a case

Suppose Banyan's private sandbox has run `invoice.docm`. The analyst's task is not to repeat the verdict but to write findings that drive the next actions. A good case note separates three things:

1. **Observed in the sandbox**, with the run settings: for example, guest image, run duration, network mode, and the observed behaviour: Word spawned a hidden PowerShell process with an encoded command; a DNS query and HTTPS request followed to `cdn-telemetry-sync.example`; any dropped files with their paths and hashes; any autostart registry values.
2. **Confirmed on the real host**, from Banyan's own telemetry: the 06:12Z download of `invoice.docm` by `divya` from `banyan-payroll-update.example`, the 06:14Z Sysmon event showing `WINWORD.EXE` spawning `powershell.exe`, and the regular 220-byte requests to `https://cdn-telemetry-sync.example/api/v2/ping` from 06:17Z.
3. **Not shown, and why**: behaviour outside the run window (the 07:02Z account creation is not expected in a short run), anything the network mode prevented, and any sign of evasion.

From those findings the analyst derives actions for the later lessons in this module: search the proxy logs for every host contacting `cdn-telemetry-sync.example` and the delivery domain; search mail logs for every recipient of the same attachment hash; search endpoints for any dropped-file hashes; and hand the domains and hashes to containment (Lesson 6). The sandbox report does not replace the host investigation. It tells you what to look for.

> [!NOTE]
> The sandbox findings in this worked example describe what such a report would be expected to show given the real behaviour recorded on `WS-104`. The course lab kit contains no malware sample and no sandbox output; only the telemetry quoted from `banyan_events.jsonl` is real lab data.

## Common mistakes and misconceptions

- **"Malicious verdict, case closed."** The verdict tells you that something is wrong, not who else is affected or what to block. The evidence sections are where the scope and the indicators come from.
- **"Clean verdict, release the email."** A quiet run is inconclusive when the static and delivery evidence say otherwise (see the evasion section).
- **Uploading first, thinking later.** Pasting a user's attachment into a public service to "get a quick answer" is a disclosure. Look up the hash first and follow the pre-submission check.
- **Treating all network traffic in a report as the sample's.** Guest operating systems make their own connections. Attribute traffic through the process tree before turning it into indicators, or you will block a software update service.
- **Ignoring run settings.** A report without its run duration, guest image and network mode cannot be interpreted properly. Record them with the findings.
- **Running live samples on an ordinary workstation "to see what happens".** This is not sandboxing; it is self-infection. Dynamic analysis belongs in approved, isolated infrastructure operated under procedure.

## Security implications, detection and defence

Sandbox output is one of the richest sources of detection content a SOC has, because it describes behaviour rather than single indicators. The parent-child pair Office-application-to-script-interpreter seen in the process tree is the same behaviour Banyan's Sigma rule `rk_office_spawns_shell.yml` in the lab kit detects on real endpoints; a sandbox run that shows a new variant of that behaviour is a prompt to test whether the rule still matches it (Module 6). Network indicators from the report feed the proxy and DNS blocks and the hunting queries; dropped-file hashes feed EDR searches, with the caution from Module 5 that hashes are the easiest indicator for an attacker to change.

The sandbox itself is also an asset to defend. It holds live malware and sensitive files, so it must be segregated from production networks, its stored submissions protected and retained according to policy, and access to submit and to download artefacts restricted and logged. Integration through SOAR (Module 1 introduced the pattern) is helpful, but an automated playbook that uploads every attachment to a public service is an automated data leak; automated submissions must go only to approved, private destinations.

## Best practices

- Order the checks: headers, static checks, hash lookup, then dynamic analysis only when its answer is needed.
- Follow the pre-submission check every time; treat "unsure" as "contains personal or business data".
- Use the organisation's approved private or contracted sandbox for anything from a user's mailbox.
- Read the process tree first, attribute network traffic to processes, and record dropped files and autostart changes with paths and hashes.
- Record run settings (duration, guest image, network mode) alongside the findings.
- Write "observed in sandbox", "confirmed on host" and "not shown, and why" as separate parts of the case note.
- Record clean-but-suspicious runs as inconclusive and escalate them under the playbook.
- Turn behaviours into detections and hunts, not only into blocks.

## Key takeaways

- A sandbox runs a suspicious object in an isolated, instrumented environment and reports its behaviour; it is the expensive step that comes after header checks, static checks and hash lookups.
- The report's evidence is the process tree, file activity, registry activity and network activity; the verdict is an opinion derived from signatures over that evidence.
- Every finding is limited to one environment, one run and one run time; long delays, environment and interaction checks, targeting and blocked networks all hide behaviour.
- A quiet run of an otherwise suspicious object is inconclusive, never proof of innocence.
- Uploading is a disclosure: look up the hash first, use private or contracted sandboxes for anything that may contain personal or business data, respect TLP and record every submission.
- Good case notes separate what the sandbox observed, what the real host confirms and what was not shown, and turn behaviour into searches, blocks and detections.
