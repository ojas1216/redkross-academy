## Introduction and conceptual foundation

Phishing is the alert a SOC sees more than any other. Users report suspicious messages, the mail gateway flags others, and some only come to light afterwards, when an endpoint alert leads back to an email nobody questioned. In the Banyan Microfinance case that has run through this course, the first malicious event in the dataset is a proxy record: at 06:12Z the finance user divya on WS-104 downloaded `invoice.docm` from the look-alike domain `banyan-payroll-update.example`, and two minutes later Word started hidden PowerShell. The dataset contains proxy, endpoint, Windows and VPN events but no email, so the message that delivered that link is not in front of you. In a real SOC, the next question would be: what email was it, who sent it, and who else received it? This module answers that question from the defender's side, starting with the part of an email that the user never sees: the header.

An email has two parts. The **body** is what the reader sees: text, links, images and attachments. The **header** is a block of `Name: value` lines above the body that records who the message claims to be from, who it is to, when it was written, and, crucially for an analyst, how it travelled and what the receiving servers concluded about it. The body is entirely under the sender's control. Much of the header is too. But some header lines are written by the servers that handled the message, and the ones written by *your own* organisation's servers are evidence that the sender could not forge. Header analysis is the skill of telling those lines apart and reading them in the right order.

Three standards define what you will read. **RFC 5322** (Internet Message Format) defines the message itself: the header fields such as `From`, `To`, `Date`, `Subject` and `Message-ID`, and how a header is laid out. **RFC 5321** (Simple Mail Transfer Protocol, SMTP) defines how servers pass the message between them, including the *envelope*, a separate set of addresses that servers use for delivery and that need not match the header at all. And a family of authentication standards, **SPF** (RFC 7208), **DKIM** (RFC 6376) and **DMARC** (RFC 7489), lets a receiving server test whether the sending domain authorised the message, with the verdicts recorded in an **Authentication-Results** header defined by RFC 8601.

This lesson teaches you to read a header from top to bottom and reach a defensible conclusion about where a message came from. It uses one illustrative specimen throughout. The specimen uses only documentation domains (`example.com` for the receiving organisation, `example.org` for the claimed sender and `example.net` for the sender's real infrastructure, all reserved for documentation by RFC 2606) and documentation IP addresses. It is modelled on the kind of message that could have preceded the Banyan download, but it is a teaching specimen, not evidence from the case.

> [!NOTE]
> Header analysis is passive. You read text that has already arrived; nothing in this lesson involves contacting the sender's servers, opening links or replying. Safe handling of the links and attachments themselves is Lesson 2, and detonation in a sandbox is Lesson 3.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Header field | One `Name: value` line (possibly folded over several lines) in the message header, as defined by RFC 5322. |
| Folding | Continuing a long header value on the next line, which must start with a space or tab. A parser joins folded lines back together. |
| Envelope | The SMTP-level addresses: `MAIL FROM` (the return path for bounces) and `RCPT TO` (the actual recipients). Separate from the `From` and `To` header fields. |
| `Return-Path` | Header added by the final delivering server, recording the envelope `MAIL FROM` address. |
| `Received` | Trace header that each accepting server prepends, recording where it got the message from, its own name, protocol, an ID and a timestamp. |
| `Authentication-Results` | Header (RFC 8601) in which a receiving server records the results of SPF, DKIM, DMARC and similar checks, labelled with that server's identifier. |
| SPF | Sender Policy Framework (RFC 7208): the domain in `MAIL FROM` publishes in DNS which IP addresses may send for it. |
| DKIM | DomainKeys Identified Mail (RFC 6376): the sending domain signs selected header fields and the body; the receiver verifies with a public key from DNS. |
| DMARC | Domain-based Message Authentication, Reporting and Conformance (RFC 7489): the domain in the visible `From` publishes a policy and requires an *aligned* SPF or DKIM pass. |
| Alignment | The domain that passed SPF or DKIM matches the `From` domain (exactly in strict mode, or sharing the same organisational domain in relaxed mode, the default). |
| `Message-ID` | A globally unique identifier for the message, normally generated by the sender's client or first server. |
| `Reply-To` | Where replies go, if different from `From`. A mismatch is a classic sign of payment fraud. |

## Anatomy of a header

A header is read as plain text. Mail clients hide most of it; every major client has an option such as "show original" or "view message source" that shows the full header, and a mail administrator can export the message as an `.eml` file, which is the raw RFC 5322 text. Always work from that raw text, never from a screenshot of what the client chooses to display, because clients decode, reorder and omit fields.

Here is the specimen header, exactly as it would appear in the `.eml` file. The DKIM signature values are shortened to `...`, and the body is omitted.

```text
Return-Path: <bounce-7731@mailer.example.net>
Received: from mx1.example.com (mx1.example.com [192.0.2.10])
	by mbox.example.com (Postfix) with ESMTPS id 4F2A1C0042
	for <divya@example.com>; Tue, 03 Nov 2026 06:08:14 +0000
Authentication-Results: mx1.example.com;
	spf=pass smtp.mailfrom=mailer.example.net;
	dkim=pass header.d=mailer.example.net header.s=s1;
	dmarc=fail (p=none) header.from=example.org
Received: from out.mailer.example.net (out.mailer.example.net [203.0.113.45])
	by mx1.example.com (Postfix) with ESMTPS id 9B71E2001A
	for <divya@example.com>; Tue, 03 Nov 2026 06:08:12 +0000
Received: from [198.51.100.23] (unknown [198.51.100.23])
	by out.mailer.example.net with ESMTPSA id 0C1D77
	for <divya@example.com>; Tue, 03 Nov 2026 06:08:09 +0000
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=mailer.example.net;
	s=s1; h=from:to:subject:date:message-id; bh=...; b=...
From: "Accounts Payable" <ap@example.org>
Reply-To: <ap-payments@example.net>
To: <divya@example.com>
Subject: Revised invoice INV-20431 - action needed today
Date: Tue, 03 Nov 2026 06:08:05 +0000
Message-ID: <20261103060805.5512@out.mailer.example.net>
MIME-Version: 1.0
Content-Type: text/plain; charset=utf-8
```

Notice the structure before reading any single line. The header falls into two zones. The **lower zone**, from `DKIM-Signature` down to `Content-Type`, was written by the sender: their mail client composed `From`, `To`, `Subject`, `Date` and `Message-ID`, and their outbound server added the DKIM signature. The **upper zone**, from `Return-Path` down to the lowest `Received`, is the **trace**: lines that servers added as they handled the message, each new line placed on top of the previous ones. This is why a header reads like a stack of papers: the last thing to happen is on top.

That stacking rule has one consequence every analyst must internalise. Any server, including one controlled by the sender, can prepend whatever lines it likes before passing the message on. A malicious sender can therefore write fake `Received` lines, even a fake `Authentication-Results` line, at the bottom of the trace. They can never write a line *above* the one your own server added, because your server adds its line after receiving the message. So the reliable part of the header is the top of the trace, down to and including the first line your organisation wrote about receiving the message from outside. Records below that point need independent corroboration.

## The Received chain

A `Received` line has a standard shape defined in RFC 5321 (section 4.4): `from` the host that handed over the message (the name it announced, followed in parentheses by the name and IP address the receiving server actually saw), `by` the server writing the line, `with` the protocol used, an `id` that is the receiving server's internal queue identifier, often `for` the recipient, and after the semicolon a timestamp. The parenthesised part is the most valuable: the announced name after `from` is whatever the connecting host chose to say, while the IP address in square brackets is what the TCP connection actually came from, as observed by the writing server.

The protocol keyword is also informative. `SMTP` is plain SMTP; `ESMTP` is extended SMTP; an `S` after it (`ESMTPS`) means the session was encrypted with TLS; an `A` (`ESMTPA`, `ESMTPSA`) means the client authenticated to the server, which is what a user's mail client does when it submits a message to its own provider. RFC 3848 registers these keywords. In the specimen, the bottom line says `with ESMTPSA`: a client at `198.51.100.23` logged in to `out.mailer.example.net` and submitted the message over TLS. That is the external relay's reported submission event. It remains a lead outside the organisation's trust boundary.

Each hop's queue `id` is worth recording. If your mail team needs to find the message in their logs, the `id` that your own server wrote (`9B71E2001A` on `mx1.example.com`, `4F2A1C0042` on `mbox.example.com`) is the key they will search for, far more precise than a subject line.

Start at the two receiving-side lanes. At 06:08:12, the organisation's MX accepted a connection from 203.0.113.45. This is the last peer the organisation can substantiate directly using this trace and its gateway logs. The mailbox store's entry at 06:08:14 confirms the subsequent internal handoff. These two events establish the order of the inbound and internal transfers. They do not establish the identity of the human sender. The earlier submission from 198.51.100.23 appears only in an external relay's account of the route. Treat it as a useful lead to corroborate, for example with records supplied by the relay operator through the organisation's established incident process.

The two internal queue identifiers describe different queues. When a reviewer searches for the gateway identifier on the mailbox store, the search may return nothing even though delivery was successful. Record the identifier beside the name of the system that issued it. If the analyst has access to both sets of logs, confirm the direction of the handoff and compare recipient and time without treating an exact timestamp match as necessary. A short internal delay may reflect queueing or processing. Unexpected gaps warrant investigation, but require a check of clock offsets and the handling path before they can support any causal claim. This interpretation lets the next shift find the relevant records even if mailbox delivery took a different route for another copy of the message.

## Reading the authentication results

The trusted gateway identifies itself as the authentication service and lists its checks. Verify that the service identifier belongs to an expected evaluator and that the record was added inside the organisation's trust boundary. RFC 8601 describes how sites manage that boundary. Check the gateway configuration or use the message trace when the path is unfamiliar. A result copied into an incident ticket is useful for communication but should retain a link to the preserved original so the next reviewer can inspect its provenance.

**SPF** asks whether the connecting server is authorised to send for the identity evaluated by the receiver, typically the envelope sender domain. Here the evaluator reports a pass for `mailer.example.net`. That is evidence about authorisation for that identity at receipt, not a pass for the visible From address. A forwarder may legitimately change the connecting system and affect SPF interpretation. When you are reviewing an old message, distinguish the gateway's recorded result at receipt from what a domain's current DNS happens to say.

**DKIM** verifies a signature for a signing domain and the message elements covered by the signature. The relevant signing identity is the `d=` value. A successful check for `mailer.example.net` provides evidence of its signature and the integrity of the signed material under DKIM's rules. It does not identify the author, establish that all display fields were covered, or attest to the legitimacy of a payment request. A message may have several signatures. Preserve the individual results and note whether any passing signature aligns with the domain under evaluation.

**DMARC** evaluates the relationship between the visible From domain and the domains that passed SPF or DKIM. A single aligned pass can satisfy the authentication requirement. In the specimen both successful checks belong to `mailer.example.net`, while the visible From belongs to `example.org`. These are separate domains, and the gateway records a DMARC failure. The specimen's result includes a monitoring policy, so delivery is consistent with the absence of a requested quarantine or rejection under that policy. Local delivery decisions can also reflect other security controls and receiver policy. The fact of inbox delivery alone does not establish why any particular decision was made.

### Visual Walkthrough & Architectural Breakdown

The top card names the visible From identity. Read it first because it is the identity against which alignment is measured. The centre divides into SPF and DKIM, two distinct checks that can give different answers on the same message. On the SPF side the receiver evaluates the connecting system for the envelope identity. On the DKIM side the receiver validates the signing identity and the signature. Their green cards report successful checks for the domains shown on those cards. Green here has a narrow meaning. It means that the specific authentication mechanism succeeded for that particular identity.

Follow both paths from those results to the comparison. The visible From domain is example.org. Both passes concern mailer.example.net, so neither pass supports alignment with example.org. The red alignment card is the reason the final result can be a failure without contradicting either green card. Reverse the observation as a classroom check. If an approved signature for example.org were verified while the envelope identity stayed mailer.example.net, the DKIM path could satisfy the alignment requirement even with the existing SPF result. That comparison makes clear that a valid signature and a domain match are separate pieces of evidence.

The policy card beneath the result is a separate idea. It describes a domain owner's request for handling a message that fails the check. A receiving system still has its own local policies and other evidence. The final card shows what happened in this fictional example, which is that the message reached a mailbox. An analyst who starts at that last card may assume the security gateway approved the business transaction. Start at the three identities and the gateway's results instead. Document the mismatch, validate the transaction with a known contact, and use the recipient's account of any interaction to determine urgency. That sequence keeps the explanation useful to the mail administrator and the finance responder.

## Correlate before deciding

Header analysis establishes a trustworthy starting point for the rest of triage. Put the receiving system, its attributed peer, time, envelope identity, visible From identity and authentication verdict in a case note. Give each item a source. For instance, the identity reported in the From field comes from the stored message, the inbound peer comes from the organisation's gateway, and evidence of a click would come from a separately authorised source. This habit prevents a downstream reviewer from reading all fields as though they had the same provenance.

Inspect the Reply-To separately. It is the destination many clients offer when the user replies. A mismatch can be legitimate for ticketing services or marketing platforms, but it is a meaningful clue if the business request expects the user to reply to a vendor. Compare against a trusted directory, known support channel, or the approved vendor record. A verification call must use a number from that independently maintained record. A number printed in the suspicious message belongs to the evidence, not to the verification process.

Use the Message-ID as a search key and keep its limitations visible. A Message-ID is normally useful for matching records within a mail system, but it is often sender supplied. A subject line can be copied widely and may change with forwards. A match across several fields, paired with the trusted gateway's identifiers, is a stronger basis for associating a record with the specimen. If a candidate appears under a different recipient, record whether the evidence establishes a separate delivery or merely a forwarded report. The distinction changes the count of exposed mailboxes and can affect the response scope.

Context matters for apparently inconsistent results. A team may legitimately use an external sender to deliver invoices. Before escalating an authentication mismatch as a compromise, compare with known valid examples or confirm the vendor relationship. Before dismissing an unfamiliar result, check whether the payment instructions changed, whether the conversation was expected, and whether the recipient shared data or acted on the request. A compromised legitimate sender can send an authenticated message. The presence or absence of a DMARC pass cannot settle the underlying transaction.

## Worked case note

For the example, the trusted gateway recorded receipt at 06:08:12 UTC from 203.0.113.45, and the internal store recorded the transfer two seconds later. The header presents Accounts Payable at example.org. The gateway reports passes for SPF and DKIM against mailer.example.net and a DMARC failure against example.org. Reply-To names a third identity at example.net. The note should treat these as distinct fields. It should also state that no transaction verification or account interaction is established by the header alone. Attach the preserved specimen and record the two internal queue identifiers so a mail administrator can reconstruct the route.

The next step is to ask Finance whether the invoice is expected using the previously approved channel. Then ask the reporter whether they replied, opened any linked content, or submitted information. If they only viewed the message and reported it, the response may focus on confirming delivery scope and disposition. If they changed a payment destination or disclosed authentication information, immediately involve the teams responsible for that impact and record that handoff. A payment-related incident can require urgent coordination even when endpoint telemetry shows no relevant process activity. The work follows the reported action and independently corroborated evidence instead of a single technical indicator.

## Practical application

Use the fictional header above as a text record. On paper or in a local text editor, make two columns headed Observed and Unconfirmed. Under Observed include the inbound peer as observed by the receiving MX, the trusted authentication results and the visible and reply identities. Under Unconfirmed include the sending human, the transaction's business legitimacy, and any claimed interaction with the message. Add the evidence source, timestamp and next required check to each conclusion. Compare your notes with a peer and identify any conclusion that one person inferred from outside the preserved record.

For a second paper exercise, suppose a vendor's known contact confirms their mail platform generated the message, but the vendor account owner does not recognise the changed payment instructions. Write an update that records both facts and states the escalation owner. Keep the evidence and the business decision separate. In a third variation, move the Authentication-Results field below the first trusted inbound hop and leave the content unchanged. Explain why the former authentication conclusion now needs a trusted gateway log. These variations teach the analyst how confidence changes as provenance or context changes, without requiring any access to a real message or external service.

## Key takeaways

- Read newly added trace lines at the top and mark the organisation's trust boundary before inferring a route.
- Record system names beside queue identifiers so later investigators query the correct source.
- Check the authenticated identities and alignment separately from the claimed author and the safety of the message.
- Use a trusted independent channel to verify the business request and document which facts still need confirmation.

Sources for the protocol details are [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html), [RFC 3848](https://www.rfc-editor.org/rfc/rfc3848.html), and [RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html).
