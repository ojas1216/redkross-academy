## From predictions to data requirements

A hypothesis tells the analyst what should be visible if a behavior occurred. Data needs analysis asks whether it can be visible, given what the organization actually collects. This is the step where many hunts quietly fail. An analyst writes an excellent hypothesis about credential misuse in cloud email, searches the SIEM, finds nothing, and reports that the behavior was not present. In fact, the SIEM never received cloud identity or mailbox audit logs. The hunt did not find a negative result. It found nothing because it looked in a place where the evidence could not be.

The purpose of this lesson is to make that gap explicit before any query is written. For every prediction in a hypothesis, the analyst identifies the source that would record it, the fields required to recognize it, the time coverage needed, the quality conditions that must hold, and the join keys needed to connect it with other predictions. The result is a data-needs matrix: a small table that shows, prediction by prediction, whether the hunt can answer its own question.

Data needs analysis also produces something valuable on its own: a list of visibility gaps tied to specific hunting questions. A gap phrased as "we have no mailbox audit data" is easy to deprioritize. A gap phrased as "we cannot test whether finance staff received invoice-themed documents, which sector intelligence flags as a current concern" makes the case for collection.

## The five questions for each prediction

For each observable prediction, ask five questions.

**1. Which source would record it?** Name the log source and, where it matters, the event type. "Endpoint data" is not specific enough; "Sysmon process creation events" or "Windows security log logon events" is. Different sources record the same behavior at different levels: a proxy sees a domain and byte count, an endpoint agent sees a process and its parent, a firewall sees addresses and ports.

**2. Which fields are required?** A prediction about an Office application starting a child process needs the child image, the parent image, the host, and a timestamp. If the endpoint source records process creation but not the parent, the prediction cannot be tested even though the source exists.

**3. What time coverage is needed?** The hunt window must be covered, and so must any baseline window. If a hypothesis predicts a destination "not seen in the prior 30 days," the source must retain at least 30 days before the hunt window. Retention shorter than the baseline period silently converts every destination into a first-seen destination.

**4. What quality conditions must hold?** Are clocks synchronized across sources? Are events complete, or does the collector drop events under load? Are fields normalized, or does one source write hostnames in uppercase and another in lowercase? Quality problems rarely make data unusable, but they change how confident a conclusion can be.

**5. What join keys connect it to other predictions?** If the hypothesis needs a proxy event and an endpoint event on the same host, both sources must carry a host identifier that can be matched. If one records a hostname and the other records only an IP address, the analyst needs a reliable mapping, such as DHCP records, for the time window.

## The Banyan data inventory

The C08 lab kit's saved Banyan dataset contains 340 rows: 284 proxy records, 33 Sysmon records, 13 Windows event records, and 10 VPN authentication records. The dataset omits several sources: there is no cloud identity audit, no mail gateway log, no mailbox audit, and no direct payload evidence. The VPN records have no endpoint identifier and no later session activity.

This inventory is small by design, but its shape is realistic. Many organizations have strong proxy coverage, partial endpoint coverage, sparse VPN detail, and nothing from mail or cloud identity sources. Reading the inventory before hunting allows the analyst to sort every question into one of three classes.

**Answerable.** The source exists, the fields exist, coverage spans the window, and quality is adequate. "Did WS-104 make a proxy request to banyan-payroll-update.example on 2026-11-03?" is answerable from proxy records, and the saved records contain one such request at 06:12:00Z.

**Partially answerable.** The source exists but lacks a field, a join key, or coverage needed for the full question. "What did WS-104 send to files-share-drop.example?" is partially answerable: the proxy records 48,200,000 outbound bytes, which answers how much, but there is no payload evidence, so what was sent is unanswerable.

**Unanswerable.** No source in the inventory could record the prediction. "Did WS-104's user receive an email containing the downloaded file?" is unanswerable because there is no mail gateway or mailbox audit data.

## Absence of evidence and evidence of absence

The distinction between these two phrases is the core idea of the lesson.

**Absence of evidence** means a search returned nothing. It says nothing about whether the behavior happened unless the search could have found it.

**Evidence of absence** means a search returned nothing and the analyst has shown that the search would have returned something if the behavior had occurred. That requires the right source, the right fields, adequate coverage and quality, and a query that has been validated against a known positive.

Consider the VPN thread. The saved records show that the VPN summary for 203.0.113.66 contains eight distinct identities that failed authentication and a successful authentication for gopal at 06:46:00Z. Suppose an analyst asks whether gopal's session then accessed internal file shares. A search of the VPN records returns no file share activity. That is absence of evidence, not evidence of absence, because the VPN records contain no later session activity at all. The correct result is a no-data outcome with a stated gap: "Post-authentication session activity is not recorded in the available VPN data."

Now consider a proxy question: "Did any workstation other than WS-104 contact files-share-drop.example on 2026-11-03?" If proxy coverage includes all workstations for that day and a query validated against the known WS-104 request returns only WS-104, that is evidence of absence for other workstations, within the proxy's coverage. The difference is that the analyst can show the search was capable of finding a positive.

## Coverage is not binary

Analysts often describe sources as "we have it" or "we don't." In practice, coverage varies along several dimensions.

**Population coverage.** Which hosts or identities send data? An endpoint agent may be installed on 90 percent of workstations. A hunt that finds no Office child processes across "all workstations" has really tested 90 percent of them. The documentation should say which.

**Event coverage.** Which event types does the source record? A Sysmon configuration may log process creation but exclude network connections to reduce volume. A Windows event log may record successful logons but not failures if the audit policy is narrow.

**Field coverage.** Which fields are populated? Proxy logs sometimes omit user identity for unauthenticated requests. A hunt that relies on the user field will miss those requests unless the query handles null values deliberately.

**Temporal coverage.** Which period does the data span, and are there gaps? A collector outage of two hours inside the hunt window means the hunt cannot speak to those two hours.

Coverage can be summarized per source as a short statement, for example: "Proxy: all workstations, request and byte fields populated, 2026-11-03 00:00 to 23:59 UTC, no known gaps." The Banyan inventory, as reported, supports statements at this level for proxy records on 2026-11-03, but the analyst should not assume coverage for other dates or hosts without checking the saved records.

## Time: synchronization, zones and windows

Time is the most common silent failure in data needs analysis.

**Time zones.** If one source writes UTC and another writes local time, a sequence can appear reversed. An Office child process recorded at 06:14 local and a download at 06:12 UTC may be hours apart. Every source should be normalized to UTC before sequencing, and the documentation should state that it was. The Banyan brief states times in UTC, which is the course convention.

**Clock skew.** Even when all sources use UTC, device clocks drift. A skew of a few seconds rarely matters for hour-scale patterns but can reverse an order that depends on seconds. If the hypothesis predicts that a download preceded execution by two minutes, a skew of up to a minute is tolerable; a skew of five minutes is not.

**Ingest time versus event time.** Many SIEMs record both the time the event occurred and the time it was received. Queries should use event time for sequencing. Ingest time is useful for spotting collection delays.

## Join keys and entity resolution

A hypothesis with predictions in two sources needs a way to say the predictions refer to the same entity. This is entity resolution, and it is where cross-source hunts often break.

**Host identity.** Proxy logs may record a hostname, an internal IP address, or both. Endpoint logs usually record a hostname. If the proxy records only an IP, the analyst needs a DHCP or asset mapping valid for the event time, because IP addresses move between hosts.

**User identity.** One source may write "gopal", another "BANYAN\gopal", another an email address. Normalization rules should be stated, not assumed.

**Missing keys.** Sometimes there is no join key at all. The Banyan VPN records have no endpoint identifier, so there is no field that links the gopal authentication to WS-104 or any other workstation. An analyst may notice that both threads occur on the same morning, but temporal proximity is not a join key. The correct statement is that the available records do not connect gopal's successful VPN session to WS-104.

**Enrichment is not observation.** An asset inventory may say WS-104 is assigned to a particular user or department. That is useful context, but it is enrichment: it describes the organization's records about the host, not something the proxy or endpoint source observed on 2026-11-03. When an inventory field is used, label it as enrichment and note its date. Do not use inventory ownership to create a link that the event data does not contain.

## Bounded case reasoning

The following cases use a small synthetic inventory authored for this lesson. It is not Banyan source data.

Synthetic inventory: proxy logs for all workstations with hostname, destination domain, bytes out and UTC timestamp, retained 14 days; endpoint process creation for workstations with parent image, retained 7 days; no DNS logs; no mail logs.

**Case 1: "Domain first seen in the last 30 days."** Proxy retention is 14 days, so the baseline cannot span 30. The question is partially answerable: the analyst can test "first seen in the last 14 days" and must record the reduced baseline as a limitation. Reporting a 30-day first-seen result would be wrong.

**Case 2: "Office child process within 10 minutes of a download, 10 days ago."** Endpoint retention is 7 days. The proxy half is answerable, the endpoint half is unanswerable for that date. The outcome for the full hypothesis is no-data, and the documentation should not report the proxy half as if it settled the question.

**Case 3: "Same host resolved a rare domain then connected to it."** No DNS logs exist. The proxy shows the request but not the resolution. The resolution half is unanswerable, though the request itself is visible; the analyst should consider whether the resolution step adds discriminating power at all, and drop it if not.

**Case 4: "No other workstation contacted the rare domain."** Proxy covers all workstations for 14 days, and a query validated against the known host returns only that host. This is evidence of absence within the proxy's population and time coverage.

## Building the data-needs matrix

The matrix has one row per prediction. Columns typically include: the prediction, the source, required fields, coverage needed, coverage available, join key, and status (answerable, partial, unanswerable). A final column states the consequence for the hunt, such as "test as written," "test with reduced baseline," or "record as gap."

Writing the matrix takes a few minutes and prevents hours of wasted querying. It also makes peer review faster, because a reviewer can check the matrix before reading any query.

The matrix should be revisited when the hunt uncovers something unexpected. If a query returns events from a host the analyst thought was out of coverage, that is a sign the coverage statement was wrong, and the matrix should be corrected before conclusions are drawn.

## Common errors

- **Treating an empty result as a negative result** without showing the source could have recorded a positive.
- **Assuming retention matches the baseline period** when the source keeps less history than the hypothesis needs.
- **Joining on time alone** when no shared host or identity field exists.
- **Using inventory enrichment as if it were an observation** to connect a user to a host.
- **Ignoring null fields** so that unauthenticated or unattributed events fall out of the result.
- **Mixing local time and UTC** and producing a reversed or invented sequence.
- **Describing coverage as "we have it"** without population, event, field and temporal detail.

## Practical exercise

Use the saved-record Banyan inventory: 284 proxy, 33 Sysmon, 13 Windows and 10 VPN records, with no cloud identity audit, mail gateway, mailbox audit or payload evidence, and VPN records without endpoint identifiers or later session activity.

For each hunt question below, classify it as answerable, partially answerable or unanswerable, name the source, and write one sentence on the consequence for the hunt.

1. Did WS-104 request a file from banyan-payroll-update.example on 2026-11-03?
2. Was the file WS-104 downloaded delivered by email?
3. How much data did WS-104 send to files-share-drop.example?
4. What data did WS-104 send to files-share-drop.example?
5. Did the identity that authenticated successfully from 203.0.113.66 use WS-104?
6. How many distinct identities failed VPN authentication from 203.0.113.66?
7. Did the gopal session access any internal resource after 06:46:00Z?
8. Did an Office application start a child process on WS-104 near 06:14?

**Model answer notes.** Questions 1, 3, 6 and 8 are answerable from proxy, proxy, VPN and Sysmon or Windows records respectively, subject to confirming field coverage in the saved rows. Question 4 is partially answerable as a pair with question 3: volume is visible, content is not. Questions 2 and 7 are unanswerable: no mail data and no session data. Question 5 is unanswerable because no join key exists; temporal proximity does not establish a link, and inventory ownership would be enrichment, not observation.

## Key takeaways

- For each prediction, identify the source, fields, coverage, quality conditions and join keys before writing a query.
- Absence of evidence becomes evidence of absence only when the analyst shows the search could have found a positive.
- Coverage varies by population, event type, field and time; state it precisely.
- Normalize to UTC and use event time for sequencing.
- A missing join key means no link, and enrichment from inventory is context, not an observation.
