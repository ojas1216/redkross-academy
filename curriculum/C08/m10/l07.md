## Two things to validate

A hunt produces a result, and before anyone acts on it, two different things need checking. The first is the **query**: did the search actually test the hypothesis, and could it have found a positive if one existed? The second is the **finding**: given what the query returned, is the interpretation correct, and does it survive the most plausible innocent explanations?

These are easy to confuse. An analyst who reviews a list of candidate rows and decides that each one is benign has validated findings. They have not validated the query. If the query missed rows because of a time zone defect, the review is thorough but incomplete. Conversely, an analyst who proves that a query returns a seeded test row has validated the query, but says nothing yet about whether the real rows it returned mean anything.

Validation is where the three outcomes used throughout this module, positive, benign and no-data, are actually assigned. A hypothesis is not positive because a query returned rows; it is positive when the rows survive validation. It is not benign because a query returned nothing; it is benign when the query has been shown capable of finding a positive and the scope was adequate. And it is no-data when either validation step cannot be completed because the required data is absent.

## Validating the query

A query is validated by showing it behaves correctly on cases where the right answer is already known. Four checks cover most defects.

**Seeded positive.** Construct or identify a record set that the query should match, run the query logic over it, and confirm the match. In a production environment, teams sometimes use a test host and a sanctioned, harmless action to produce a known record. In this course, seeded positives are synthetic records written into a fixture, and the query is traced by hand. The Lesson 3 fixture already contains one: P06 followed by E01 on WS-203 is a known positive for the rare-download join.

**Known negative.** Confirm the query does not match a similar case that should be excluded. E03 in the Lesson 3 fixture, an Office child process on a host with no rare download, is a known negative. If the query returned E03, its join or rarity condition would be broken.

**Coverage check.** Count the records in scope before filtering, and compare against expectations. If a proxy source should cover five hosts for an hour and the scoped input contains rows from only three, the query or the source is missing data. Count rows with null values in key fields, since filters and joins drop them silently.

**Boundary check.** Test the edges of time windows and thresholds. Does a process event exactly ten minutes after the download match? Does one exactly at the download time? Does a host with exactly the threshold number of distinct failures pass? Off-by-one errors in thresholds and inclusive versus exclusive time bounds are common and change results at the margin.

A query that passes all four is fit for purpose within its stated assumptions. Record the checks in the hunt record, so a reviewer can see that the zero-result or few-result output is trustworthy.

## Validating the finding: corroboration

Once the query is trusted, its results need interpretation. The strongest validation is corroboration: other evidence that the hypothesis predicts and that the original query did not already use.

**Independent sources.** Two sources are independent when they observe the activity through different mechanisms. A proxy log and an endpoint process log are reasonably independent: one sees network requests, the other sees processes starting on the host. If both agree on host and order, the agreement is meaningful.

**Non-independent sources.** Two sources are not independent when one derives from the other or both observe the same thing at the same point. A proxy log and a firewall log of the same outbound connection both confirm the connection happened; they do not independently support any claim about why it happened. A SIEM alert built from proxy logs is not corroboration for the proxy log. Counting non-independent sources as separate support inflates confidence.

**Additional predictions.** A good hypothesis generates more predictions than the first query tests. If a download led to execution, the hypothesis might also predict a new file written to disk shortly before the process started, or an outbound connection from the child process. Checking these, where data permits, adds independent support or exposes a gap.

**Enrichment as context.** Asset inventory, change calendars and software deployment records can corroborate or contradict a benign explanation. They are not observations of the activity, but they matter. If a change record shows a sanctioned software rollout to the host at the time of the Office child process, the benign alternative gains strong support.

## Validating the finding: benign explanations

Every hunt finding should be tested against the most plausible benign explanations. The goal is not to explain away every anomaly, but to rule in or out the innocent explanations that a reviewer would raise.

Common benign explanations in hunting include:

- **Scheduled or sanctioned activity:** software updates, backup jobs, approved file transfers, administrative scripts.
- **Known business tools:** a file-sharing service the business uses, a telemetry agent from an installed product.
- **User error:** mistyped passwords, a user retrying with an old password after a reset.
- **Shared infrastructure:** many users behind one egress address, such as a partner site, a hotel or a mobile carrier.
- **Data artifacts:** duplicate records, clock skew creating a false order, a parser splitting one event into two.

For each, identify what evidence would support it and look for that evidence. A sanctioned file transfer leaves a change record or a known destination on a business allowlist. A shared egress address shows many identities succeeding as well as failing over time. A duplicate record has identical fields and timestamps.

When the benign explanation cannot be checked because the data is missing, say so. "Shared egress not ruled out; no historical VPN data to show whether 203.0.113.66 normally carries multiple identities" is an honest statement. It lowers confidence without changing the outcome to benign.

## Checking for false negatives

A finding is only as strong as the hunt's ability to see related activity. Validation should also ask whether the query missed things.

**Variants.** Did the query's filters express the behavior, or a single tool? An Office parent list that includes only word processors misses spreadsheets.

**Thresholds.** If the threshold was three distinct failed identities in ten minutes, how many sources had two? A slower guessing pattern could stay under it.

**Coverage gaps.** Which hosts or periods were outside source coverage? A finding on one host does not tell the analyst about hosts without endpoint telemetry.

**Nulls and unresolved rows.** Were rows dropped because a key field was empty? P11 in the Lesson 3 fixture is a second source of traffic to the same rare domain that the query could not assign to a host. Leaving it unresolved means the finding's scope may be understated.

False-negative checks rarely change a positive finding to benign, but they often change its scope. A finding that was "one host" can become "one confirmed host and one unresolved address."

## Assigning outcome and confidence

With query and finding validated, assign the outcome.

**Positive** when the predictions were observed, the query passed its checks, and the main benign alternatives were ruled out or remain clearly less plausible. Confidence depends on independence and on how many alternatives were checked.

**Benign** when the predictions were not observed by a validated query with adequate coverage, or when they were observed but a benign explanation was confirmed with evidence.

**No-data** when the data needed to test the predictions, or to validate the query, is missing or cannot be joined.

Outcomes can differ for different parts of a hypothesis. The Banyan VPN thread illustrates this. The authentication-pattern hypothesis, failures across distinct identities from one address followed by a success, has supporting observations in the saved-record summary: eight distinct failed identities from 203.0.113.66 and a success for gopal at 06:46:00Z. If the saved rows confirm the summary and the time span is short, that part may be positive at moderate confidence, with the shared-egress alternative unresolved. The post-authentication hypothesis, that the session was then used for further activity, is no-data, because there is no session data. Writing a single outcome for the whole thread would hide the difference.

Confidence should come with a reason, not just a label. "Moderate: VPN records alone; shared egress not ruled out; no session data" tells the reader what would raise or lower it.

## Deciding what happens next

A validated outcome leads to one of three actions.

**Escalate.** A positive finding with moderate or high confidence goes to incident response with the hunt record and citations. Escalation does not wait for certainty; hunting rarely achieves certainty, and incident response has tools and authority the hunter does not.

**Close.** A benign finding with a validated query and adequate scope is closed with its scope statement. If the hunt revealed a gap in detection, a rule candidate goes to detection engineering.

**Carry forward.** A no-data finding, or a positive with low confidence, is carried forward with a specific trigger for revisiting: "Revisit when VPN session logs are available," or "Rerun after 14 days of DNS retention." Carrying forward is not the same as leaving a hunt open indefinitely; it has a named condition and an owner.

## Peer review

A second analyst reviewing the hunt record is the last validation step. Reviewers should check the hypothesis was written before results, the query passed its four checks, the claims are labeled, the benign alternatives were reasonable, and the outcome matches the evidence. A useful reviewer habit is to try to argue for the opposite outcome. If the reviewer can make a reasonable case that a positive is benign, the record needs more evidence or a lower confidence level.

## Bounded case reasoning

Three synthetic validation cases follow, authored for this lesson.

**Case 1: the query that could not fail.** An analyst reports "no rare-domain downloads followed by Office child processes across all workstations last week." During review, the seeded positive check is run by hand on a synthetic record pair and the query does not match it. The cause is that the endpoint timestamps are stored in local time two hours ahead of UTC. The original zero result is invalid. The outcome changes from benign to no-data until the query is corrected and rerun.

**Case 2: two logs, one event.** An analyst reports a high-confidence finding that WS-208 sent 40 MB to a rare destination, "confirmed by proxy and firewall logs." The reviewer notes that both logs record the same connection at the same network boundary. They corroborate that the transfer happened, but they are not independent evidence of anything beyond the connection. Confidence for an exfiltration hypothesis drops to moderate until an independent source, such as endpoint process data showing which program made the connection, is checked.

**Case 3: the benign explanation with evidence.** A hunt finds an Office application starting an unusual child process on WS-210. Validation finds a change record showing a sanctioned add-in deployment to finance workstations that morning, and the same parent-child pair on every other finance workstation within the same hour. The finding is benign, with the change record cited as enrichment and the prevalence cited as observation. The hunt hands a note to detection engineering so the add-in's child process is understood before any related rule is written.

## Common errors

- **Validating findings but not the query**, so a broken query's empty result is trusted.
- **Counting non-independent sources** as separate corroboration.
- **Treating an unchecked benign explanation as ruled out** because no one looked.
- **Assigning one outcome to a hypothesis with parts that differ**, such as a supported authentication pattern and an untestable session question.
- **Waiting for certainty before escalating**, which delays response.
- **Carrying forward without a trigger**, leaving hunts open indefinitely.
- **Ignoring unresolved rows**, which can understate scope.

## Practical exercise

Use the synthetic fixtures from Lesson 3 (proxy P01 to P12, endpoint E01 to E04, VPN V01 to V08). No query is executed; all checks are traced by hand.

1. For the rare-download join, list the seeded positive and the known negative in the fixture, and state what each confirms about the query.
2. Perform a boundary check: add synthetic row E06 on WS-203 at exactly 09:20:00 with parent WINWORD.EXE. Does the query as written in Lesson 3 match it to P06? Explain using the window bounds.
3. Identify one false-negative risk in the join query and state how it could change the finding's scope.
4. For the VPN finding on 192.0.2.140, list two benign explanations, the evidence that would support each, and whether the fixture contains that evidence.
5. Assign outcomes, with confidence and a reason, to: the 192.0.2.140 authentication pattern; post-authentication activity for noor; and the 198.51.100.23 pattern.

**Model answer notes.** The seeded positive is P06 with E01; the known negative is E03, which confirms the rarity condition excludes routine Office children on hosts without rare downloads. E06 at 09:20:00 is exactly ten minutes after P06; the Lesson 3 query uses "less than or equal to plus 10 minutes," so it matches. A team that intended an exclusive bound would need to change the query and record the choice. One false-negative risk is P11: its null host means a second source of sync-relay.example traffic is unassigned, so the finding's scope may be wider than WS-203. Benign explanations for 192.0.2.140 include a shared egress address, supported by historical successes for many identities from that address, and an expired-password wave after a policy change, supported by a change record; the fixture contains neither. Outcomes: 192.0.2.140 pattern positive at moderate confidence, benign alternatives unchecked; noor post-authentication no-data, no session records; 198.51.100.23 benign at moderate confidence, one identity retrying then succeeding.

## Key takeaways

- Validate the query and the finding separately.
- Query validation uses a seeded positive, a known negative, a coverage check and boundary checks.
- Corroborate with independent sources, and do not count logs of the same event twice.
- Test the most plausible benign explanations with evidence, and say when one cannot be checked.
- Assign outcomes per part of a hypothesis, give confidence with a reason, and choose escalate, close or carry forward with a trigger.

### Visual Walkthrough & Architectural Breakdown

The figure is a top-to-bottom validation flow that a hunt result passes through before an outcome is assigned. It is read as a series of gates, each of which can stop the flow and redirect the result.

The first gate is the query check, colored violet, covering the seeded positive, known negative, coverage and boundary checks. If the query fails here, every result it produced, including an empty one, is untrusted. The flow does not continue to interpretation; it returns to query correction or ends in no-data if the data needed to correct it is missing.

The second gate is corroboration, colored blue. The question is whether independent sources agree. The sub-label reminds the reader that logs of the same event at the same point do not count twice. The third gate is the benign explanation check, colored orange because it is the step that most often changes an outcome. Each plausible innocent explanation is tested with evidence, and any that cannot be tested is recorded as an open alternative that lowers confidence.

The fourth gate is the false-negative check, colored slate. It rarely changes the outcome, but it often changes scope, for example by adding an unresolved address to a finding that seemed limited to one host. The fifth step assigns an outcome and confidence, and the final green step sets the action: escalate, close or carry forward with a trigger.

As an example, the synthetic Case 1 in this lesson fails the first gate: the seeded positive does not match because of a time zone defect, so the original empty result never reaches corroboration and the outcome becomes no-data. Synthetic Case 3 passes the query gate and corroboration, then reaches a benign outcome at the third gate, supported by a change record and by the same behavior appearing on every peer.
