## What a hunt query is for

A hunt query is the mechanism that tests a hypothesis's predictions against saved records. It differs from a detection rule in purpose and lifespan. A detection rule runs continuously, must keep false positives low enough for a queue, and is tuned for months. A hunt query runs a handful of times, is allowed to return a manageable set of candidates for human review, and is judged by whether it answers the hypothesis clearly. Many good detection rules begin life as hunt queries, but the analyst writing a hunt query should optimize for clarity and correctness first, not for alert volume.

Hunt queries in this course are read-only. They select, count, group, filter and join saved records. They never change data, contact external systems, or reproduce adversary activity. The examples are written in neutral pseudocode so the logic is visible regardless of which SIEM or log platform a team uses. No query in this lesson has been executed against a live system; the results shown are traced by hand against a small synthetic fixture so that any learner can verify them on paper.

This lesson covers four building blocks: stacking, filtering, time windows and entity joins. It then covers the defects that most often make a hunt query return the wrong answer, and how to document a query so another analyst can trust it.

## Building block 1: stacking

Stacking means grouping records by a field and counting. It is the simplest and most productive hunt technique, because rare values in a large population stand out without the analyst needing to know what to look for in advance. The hypothesis supplies the field to stack on; the stack shows the distribution.

```
FROM proxy
WHERE time_utc >= '2026-10-14T09:00:00Z' AND time_utc < '2026-10-14T10:00:00Z'
GROUP BY domain
COMPUTE rows = count(), hosts = count_distinct(host)
SORT hosts ASC
```

Traced by hand, the result is:

| domain | rows | hosts |
|---|---|---|
| invoice-viewer.example | 1 | 1 |
| sync-relay.example | 2 | 1 |
| updates.example | 4 | 4 |
| portal.example | 5 | 5 |

Two things deserve attention. First, the two rare domains, invoice-viewer.example and sync-relay.example, each appear on only one named host. Second, sync-relay.example shows two rows but only one distinct host. That mismatch is caused by P11, which has a null host. Most query engines exclude nulls from a distinct count, so P11 disappears from the host count while still counting as a row. If the analyst had stacked only on distinct hosts, the second source of traffic to sync-relay.example would be invisible.

Stacking choices shape what the analyst sees. Stacking by rows emphasizes volume; stacking by distinct hosts emphasizes prevalence. For rarity-based hunts, distinct hosts is usually the right measure, but the row count should be kept alongside it as a check.

## Building block 2: filtering

Filtering narrows records to those relevant to a prediction. Filters should express the behavior, not a single tool. A prediction about Office applications starting child processes should filter on a set of Office parent images, not on one.

```
FROM endpoint_process
WHERE lower(basename(parent_image)) IN ('winword.exe', 'excel.exe', 'powerpnt.exe', 'outlook.exe')
```

Against the fixture, this returns E01 (WS-203, WINWORD.EXE to cmd.exe) and E03 (WS-204, EXCEL.EXE to splwow64.exe). E04 is not returned because WINWORD.EXE is the child there, not the parent.

The filter alone does not discriminate between interesting and routine. E03 is a common printing helper started by Office applications when a user prints. A hunter who reported every Office child process would bury the useful result under routine ones. That is why filters are combined with stacking or joins rather than used alone, and why the analyst should know which Office children are routine in the environment, a question for the baseline lesson.

Case sensitivity is a frequent filter defect. If one source writes "winword.exe" and the filter expects "WINWORD.EXE", a case-sensitive engine returns nothing. Normalize case explicitly in the query, or confirm the engine's default behavior, and record the choice.

Path form is the other trap. The fixture stores bare file names, but many real sources (including the Banyan lab data) store the full path, such as `C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE`. An exact match on `WINWORD.EXE` returns zero rows against those records. That is why the filter above compares the file name at the end of the path (`basename`, written here as pseudocode; use your engine's equivalent), in lower case. In the same way, the Banyan proxy records hold a full `url`, not a `domain` field, so the hostname must be extracted from the URL before any domain filter or prevalence count.

## Building block 3: time windows

Many hypotheses predict a sequence: one event followed by another within a period. Time windows express that. They need a direction, a lower bound and an upper bound.

A window of "within 10 minutes" is ambiguous. Does it mean 10 minutes before or after, or either? For a download-then-execution hypothesis, the endpoint event should follow the proxy event, so the window is from 0 to 10 minutes after the proxy time. Using an absolute difference would also match process events that came first, which contradicts the hypothesis and would inflate the result.

Window width is a trade-off. Too narrow, and real sequences with a delay are missed, for example when a user downloads a file and opens it after a meeting. Too wide, and unrelated events on a busy host pair up by coincidence. The hypothesis should justify the width, and the documentation should note what a wider window would add.

## Building block 4: entity joins

A join connects predictions from different sources on a shared entity. The join key must exist in both sources and mean the same thing. In the fixture, host is the key between proxy and endpoint records.

The full hunt query combines all four blocks: stack proxy domains to find rare ones, then join those rows to Office child process events on the same host within 0 to 10 minutes after.

```
rare = FROM proxy
       WHERE time_utc >= '2026-10-14T09:00:00Z' AND time_utc < '2026-10-14T10:00:00Z'
       GROUP BY domain
       HAVING count_distinct(host) <= 1

candidates = FROM proxy AS p
             JOIN endpoint_process AS e
               ON lower(e.host) = lower(p.host)
              AND e.time_utc >= p.time_utc
              AND e.time_utc <= p.time_utc + 10 minutes
             WHERE p.domain IN rare.domain
               AND lower(basename(e.parent_image)) IN ('winword.exe', 'excel.exe', 'powerpnt.exe', 'outlook.exe')
             SELECT p.row, p.time_utc, p.host, p.domain, e.row, e.time_utc, e.parent_image, e.image
```

Traced by hand: the rare domains are invoice-viewer.example and sync-relay.example. Proxy rows for those domains are P06 (WS-203, 09:10:00), P10 (WS-203, 09:40:00) and P11 (null host, 09:45:00). For P06, E01 is on WS-203 at 09:11:30, ninety seconds later, with an Office parent: it matches. For P10, there is no Office child event on WS-203 between 09:40:00 and 09:50:00: no match. For P11, the host is null, so the join cannot match any endpoint row. The result is one candidate: P06 joined to E01.

E03 is not returned because WS-204 contacted no rare domain. That is the join doing its job: it filtered out a routine Office child process by requiring a rare download first.

P11 is not returned, but it has not been explained. It is a second source of traffic to sync-relay.example, identified only by 10.20.5.77. The query cannot say which host that was. Resolving it requires a DHCP or asset mapping for 09:45 UTC, which the fixture does not include. The analyst should record P11 as an unresolved row, not drop it silently.

## Common query defects

**Null-field exclusion.** Filters and joins on a field drop rows where the field is null. P11 demonstrates this. Check how many rows have nulls in key fields before trusting a result.

**Join fan-out.** A join on host alone, without a time window, pairs every proxy row on a host with every endpoint row on that host. In the fixture, WS-203 has three proxy rows (P03, P06, P10) and one endpoint row (E01), so a host-only join produces three candidate pairs, two of which are meaningless. On real data, fan-out can produce millions of rows and hide the real result.

**Time zone mismatch.** If the endpoint source wrote local time two hours ahead of UTC, E01 would read 11:11:30 and would not fall in any window after P06. The query would return nothing, and the analyst might wrongly report a negative. Confirm that every source is in UTC before joining on time.

**Wrong window direction.** Using an absolute time difference matches events in the wrong order. A process event at 09:08:00 would match P06 under an absolute 10-minute window even though it preceded the download.

**Over-specific indicators.** Filtering on a single domain or file name from a report finds only that indicator. The hunt should express the behavior, with indicators used as supplementary filters.

**Unbounded time ranges.** A query without explicit start and end times may run against whatever the platform default is, which can change between runs. Always state the range.

## Documenting a query

A hunt query should be documented well enough that another analyst can rerun it and expect the same result on the same saved data. The minimum record includes:

- **Purpose:** which prediction from which hypothesis it tests.
- **Inputs:** sources, time range in UTC, and any reference lists such as the set of Office parent images.
- **Assumptions:** for example, that host names are case-insensitive and that all sources are in UTC.
- **Expected positive:** what a matching row would look like.
- **Expected negative:** what a non-matching but similar row would look like, such as an Office child on a host with no rare download.
- **Known limitations:** rows the query cannot evaluate, such as null-host proxy rows.
- **Version:** a date or revision label, so changes are traceable.

The expected positive and negative are especially valuable. They let a reviewer check the query against a seeded example before trusting it on real data, a practice covered further in Lesson 7.

## Bounded case reasoning

Applying the same logic to the saved-record Banyan facts shows how a query result should be stated. The saved records show that WS-104 made one proxy request to banyan-payroll-update.example at 06:12:00Z on 2026-11-03, and the saved endpoint data records an Office child process at 06:14. If the saved endpoint row is on WS-104 and the destination is rare in the proxy data for that day, the join query above, adapted to that date, would return one candidate pair with a gap of roughly two minutes.

What the result would show is a rare download followed by an Office child process on the same host within the window. What it would not show is what the downloaded file was, how it arrived, or whether the child process did anything harmful. Those statements need further evidence, some of which the dataset does not contain. The query result is a candidate for validation, not a finding of compromise.

A learner using the Banyan data should confirm two things in the saved rows before relying on that reading: that the endpoint record's host field is WS-104, and that banyan-payroll-update.example is rare among workstations on that day. Neither should be assumed from the summary.

## Verify the Banyan join against the saved file

A read-only check of the C08 kit's `banyan_events.jsonl` found one proxy record for banyan-payroll-update.example. It names WS-104 at 06:12:00Z. The Sysmon data records an Office child process on WS-104 at 06:14:00Z. Pairing the records by the observed host and subtracting their UTC timestamps gives a recorded 120 seconds (the Sysmon times in this file are minute-resolution, so the true gap is roughly one to three minutes). That pair satisfies the same-host, forward-window conditions used in this lesson. This check concerns the two named observations and their relationship, irrespective of how many other candidates a broader hunt might produce.

Record the exact predicate you used to select a destination. A match on a full URL means the displayed path is part of the selection, while a hostname match includes all paths at that host. The two queries may answer different questions. First reproduce the narrow example with the known source rows. Then document why any wider search and scope are needed. If a row's host is missing, it remains outside a validated host join and needs another approved source for attribution. Give a peer the two timestamps, the common observed asset and the reasoning for the match. They should be able to reproduce the arithmetic without assuming that the document's contents are known.

## Key takeaways

- Hunt queries are read-only tests of hypothesis predictions, optimized for clarity rather than alert volume.
- Stacking, filtering, time windows and entity joins are the core building blocks.
- Null fields, join fan-out, time zone mismatch and wrong window direction are the most common defects.
- Trace queries by hand on a small fixture before trusting them on real data.
- A query result is a candidate for validation, stated in terms of what the records show and do not show.

### Visual Walkthrough & Architectural Breakdown

The figure traces the fixture's proxy-to-endpoint hunt query from all records down to a single candidate, with a side branch for rows the query cannot evaluate. Read it from top to bottom as a funnel, where each step reduces the record set according to one building block.

The first step is the scoped input: twelve proxy rows in a one-hour UTC window. The second step stacks by domain and counts distinct hosts, which surfaces two rare domains. The third step selects the proxy rows for those domains, which yields three rows: P06, P10 and P11. At this point the flow divides. P11 has a null host and cannot be joined, so it goes to an orange "unresolved" step instead of being silently lost. This placement is deliberate: a query that drops a row has not explained it, and the hunt record needs to show that the row is still open.

The fourth step joins the remaining rows to endpoint process events on the same host, within zero to ten minutes after, and with an Office parent. Only P06 and E01 satisfy every condition. P10 has no Office child afterward, and E03 never enters the join because WS-204 had no rare download. The final green step is the candidate pair, labelled as a candidate rather than a finding because validation has not happened yet.

As an example of using the figure to debug, suppose the result came back empty. The analyst would walk up the funnel: was the stack correct, did the rare rows exist, did the join fail on case or time zone? Each step is a checkpoint where the hand trace can be compared with the platform output.
