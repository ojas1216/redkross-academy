## Introduction and conceptual foundation

A detection rule is never finished on the day it is deployed. It meets an environment its author only partly understood: software that behaves in unexpected ways, administrators with unusual habits, parsers that change, users who move offices. Within weeks the rule's alerts start to tell a story about the rule itself. Some rules prove sharp and quiet. Others fire dozens of times a day on activity nobody cares about, and analysts learn to close them on sight. **Tuning** is the engineering discipline of reading that story and changing the rule so that it alerts on what it was written to detect, and as little else as possible, without losing the attacks it was meant to catch.

Module 5, Lesson 5 looked at the same problem from the queue. There you learned to tell a false positive from a benign true positive, to write a false-positive record that a detection engineer can act on, and to build a documented, expiring suppression. This lesson picks up where that one stopped: the tuning request has arrived on the detection engineer's desk. What does the engineer measure, how do they decide which kind of change to make, and how do they make that change without breaking the rule or silently blinding it?

The lesson is organised around four questions:

1. **How good is the rule now?** Precision measured per rule, from dispositions, over enough alerts to mean something.
2. **Why is it noisy?** The cause decides the fix: bad data, logic broader than its intent, a threshold or window that does not match the real baseline, or a genuine benign pattern.
3. **What is the narrowest change that removes the noise?** Narrowing logic, re-setting a threshold or window from evidence, lowering priority, or (as a last resort) a scoped suppression.
4. **How is the change controlled?** Version control, tests that must still pass, replay against stored data, peer review, staged deployment and monitoring afterwards.

All practical work uses the course kit, `LAB_ASSETS/C08/`: `minisiem.py` (the teaching SIEM and its rules R1 to R6), `test_rules.py` (the rules' unit tests, the subject of Lesson 4) and `banyan_events.jsonl` (the synthetic Banyan Microfinance day). Two small scripts and a handful of synthetic events were written for this lesson; each is shown in full and labelled.

### Why tuning is a security activity, not housekeeping

It is tempting to see tuning as cosmetic: making the queue tidier. The opposite is true. Every tuning change alters what the SOC can see. A good change raises the share of alerts that deserve attention, which protects analysts from the alert fatigue described in Module 5 and makes it more likely that a real attack is noticed. A bad change, made in a hurry by someone without tests, can remove the attack along with the noise, and nobody will know, because a rule that no longer fires produces no complaint. Tuning is therefore held to the same standard as writing a rule in the first place: evidence before the change, tests around it, review by a second person and measurement afterwards.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Precision | The share of a rule's alerts that were worth an analyst's attention: TP / (TP + FP), with benign true positives counted as noise when the question is queue value. |
| Recall (detection rate) | The share of real occurrences of the behaviour that the rule caught. It cannot be measured from the alert queue alone, because misses never appear there. |
| Alert volume | Alerts per rule per day (or week). With precision, it gives the analyst time a rule consumes. |
| Baseline | The measured normal behaviour of the field a rule tests: typical counts, sizes, intervals and their spread. |
| Threshold | A numeric boundary in a rule: a count, a size, a distinct-value count. |
| Window | The maximum time span over which events are related or counted. |
| Narrowing | Changing the rule's logic so that it matches its intent more exactly, for everyone. |
| Suppression | Stopping a specific, documented benign instance from alerting while the rule stays unchanged (Module 5, Lesson 5). |
| Regression test | A test that proves a change did not break what already worked, such as a known-bad sample that must still match. |
| Replay | Running a changed rule over stored historical data to see how its alert count and precision would have changed. |
| Change control | The governed path a rule change follows: request, version control, testing, review, deployment, monitoring and rollback. |

## Measuring alert precision

Tuning starts with a number, not a feeling. "R6 is noisy" is a complaint; "R6 raised 140 alerts in the last 30 days, 131 closed as false positive or benign, precision 0.06, about 7 analyst-hours" is a tuning case. The number comes from the dispositions analysts already record. If the SOC follows the Module 5 discipline, each closed alert carries a label (TP, FP, BTP, undetermined) and the rule ID, so precision per rule is a simple grouped count over the case system.

Several details make the measurement honest:

- **Measure per rule, not per analyst or per queue.** A SOC-wide false-positive share (Module 1, Lesson 7 computed one with `soc_metrics.py`) tells you the SOC has a noise problem; only per-rule precision tells you where it is.
- **Decide what counts as noise.** For queue value, benign true positives are noise even though the rule worked. For rule correctness, they are not errors. Report both views when the difference matters, because the fix differs: an FP points at the logic or the data, a BTP points at context or a suppression.
- **Exclude undetermined alerts from the ratio, but report how many there were.** A rule with many undetermined closures has an evidence problem (missing telemetry, unclear triage steps), which is a different defect.
- **Use enough alerts and a long enough period.** Precision computed on five alerts is anecdote. A rule that fires twice a month needs a quarter's data; a rule that fires hourly can be judged in a week. Seasonal patterns (month-end batch jobs, patch days) need at least one full cycle.
- **Pair precision with volume.** A rule with precision 0.10 and two alerts a month is cheap; a rule with precision 0.50 and two hundred alerts a day is not. The cost to the SOC is roughly volume multiplied by the average triage time.

Precision alone can also mislead in the other direction. A very high precision may mean the rule is excellent, or that it is so narrow it catches only one variant of the behaviour. Recall cannot be read from the queue, because what a rule misses never becomes an alert. It is estimated in other ways: by testing the rule against known-bad samples and emulated behaviour (Lesson 4), by hunting for the behaviour independently, and by reviewing incidents to see which steps no rule caught. Tuning that improves precision while quietly cutting recall is the failure this lesson is designed to prevent.

### A threshold sweep

A **threshold sweep** runs the same rule at several parameter values and scores each result. The script below, `sweep.py`, was written for this lesson (it is not part of the kit). It reuses the storyline labelling to count true and false positives for R4 at five upload thresholds and for R6 at four combinations of minimum hit count and maximum size range:

```python
"""Threshold sweep for R4 and R6 (written for M7 L5; not part of the kit)."""
import sqlite3

con = sqlite3.connect("minisiem.db")
BAD = ("banyan-payroll-update.example", "cdn-telemetry-sync.example", "files-share-drop.example")


def score(rows, url_col):
    tp = sum(1 for r in rows if any(d in r[url_col] for d in BAD))
    fp = len(rows) - tp
    prec = f"{tp / len(rows):.2f}" if rows else "n/a"
    return len(rows), tp, fp, prec


print("R4 large_upload: bytes_out > T")
print("T          alerts  TP  FP  precision")
for t in (10_000_000, 3_900, 3_500, 3_000, 2_000):
    rows = con.execute("SELECT ts, host, url FROM events WHERE source='proxy' AND bytes_out > ?",
                       (t,)).fetchall()
    print(f"{t:<10} %6d %3d %3d  %s" % score(rows, 2))

print("R6 beacon_regular_small: hits >= N AND size range < W")
print("N   W      alerts  TP  FP  precision")
for n, w in ((10, 50), (10, 3_000), (10, 3_500), (5, 3_500)):
    rows = con.execute("""SELECT host, url FROM events WHERE source='proxy' GROUP BY host, url
                          HAVING COUNT(*) >= ? AND MAX(bytes_out) - MIN(bytes_out) < ?""",
                       (n, w)).fetchall()
    print(f"{n:<3} {w:<6} %6d %3d %3d  %s" % score(rows, 1))
```

The R4 query is the kit's rule with its constant replaced by a parameter (`?`), and the R6 query is the kit's rule with both constants parameterised. `score()` counts a hit as a true positive when its URL contains a storyline domain. Run it after `minisiem.py load`:

```terminal
$ python sweep.py
R4 large_upload: bytes_out > T
T          alerts  TP  FP  precision
10000000        1   1   0  1.00
3900            5   1   4  0.20
3500           32   1  31  0.03
3000           64   1  63  0.02
2000          142   1 141  0.01
R6 beacon_regular_small: hits >= N AND size range < W
N   W      alerts  TP  FP  precision
10  50          1   1   0  1.00
10  3000        2   1   1  0.50
10  3500        3   1   2  0.33
5   3500       33   1  32  0.03
```

Read the R4 block from the top. At the kit's threshold of 10,000,000 bytes the rule raises one alert, the exfiltration, and nothing else. Lowering the threshold to 3,900 bytes, just under the routine maximum of 3,999, already adds four routine requests; at 2,000 bytes, below the routine average, half of all routine traffic alerts. The true-positive count never changes, because the one real upload is far above every threshold tried. That is the shape of a well-separated signal: there is a wide band of thresholds (roughly 4,000 bytes to 48 MB here) in which the rule is both precise and complete, and the engineer's job is to choose a value inside that band with a margin on both sides.

The R6 block shows the same effect on a rule with two parameters. Widening the allowed size range from 50 bytes to 3,000 lets WS-103's requests to `cdn.example.org` qualify; widening to 3,500 adds WS-103's intranet traffic as well; dropping the minimum count to five on top of that produces 33 alerts for one real beacon. Two lessons follow. First, parameters interact: the count and the size range together define what "regular and small" means, and loosening both at once multiplies the noise. Second, a sweep on stored data is cheap and fast, so there is no excuse for choosing a threshold by intuition.

> [!IMPORTANT]
> A sweep measures precision against the data you have. It says nothing about attacks that are not in that data. An attacker who uploads 9 MB at a time passes under R4's 10 MB threshold on every request. The baseline tells you how low you can go before noise explodes; the threat model tells you how low you need to go. When the two conflict, the answer is usually a second rule (for example, total bytes per host and destination per hour), not a threshold that drowns the queue.

## Diagnosing the cause before choosing the change

A tuning request usually arrives with a proposed fix ("add WS-103 to the exclusions"). The engineer's first job is to set the proposal aside and find the cause, because the same symptom, too many alerts, has several different causes and each has a different correct change. Module 5, Lesson 5 listed the options as the analyst sees them; here they are ordered as the engineer should test them, from the most general fix to the most specific.

1. **Is the data wrong?** If the false positives arise because a field is empty, mis-parsed or carries a different meaning on one source (a `parent_image` that holds the grandparent, a `user` field that holds the service account rather than the person), the defect is in the pipeline. Fix the parser or normalisation (Module 3). The fix improves every rule and every search that uses the field, and no rule change is needed.
2. **Is the logic broader than its intent?** If the rule matches activity that does not fit its own description for anyone, in any environment, narrow the logic. The rule's title and description are the specification: R6 is called `beacon_regular_small`, so something that is neither regular over time nor persistent is outside its intent.
3. **Are a threshold or window out of line with the measured baseline?** If the logic is right in kind but its numbers were guessed, re-set them from a sweep and from the spacing of real attack steps, as in the previous section.
4. **Is it a specific, known, authorised instance?** If the behaviour genuinely matches the rule's intent but this particular instance is approved (a named build account, a sanctioned monitoring agent), the rule is correct and the instance is a benign true positive. Use a scoped, owned, expiring suppression exactly as Module 5 described, or enrich the alert with the context that lets triage close it in seconds.
5. **Is it ambiguous on some assets and important on others?** Lower its priority or confidence for the low-value context rather than hiding it, so that it stays visible to a curious analyst or hunter.

The order matters because each step is more specific, and less durable, than the one before. A data fix is permanent and benefits everything. A logic change applies to all hosts and is covered by tests. A suppression covers one pattern, must be reviewed and expire, and is a place an attacker could hide. Starting from the bottom of the list (the analyst's natural instinct under pressure) produces a growing pile of suppressions around a rule whose real defect was never fixed.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the detection engineer's triage of a tuning request: a series of questions that leads from a measured problem to the narrowest durable fix. It matters because the most common tuning error is not a wrong threshold but the wrong *kind* of change, typically a suppression applied to what is really a data or logic defect.

**Components.** At the top is a slate box, **Noisy rule**, with the sub-label *measured precision and volume*: the input is a number from the dispositions, not a complaint. Four violet decision boxes follow: **Is the data wrong?**, **Logic broader than intent?**, **Threshold or window off baseline?** and **Known authorised instance?** Each has an outcome box: **Fix parser or normalisation**, **Narrow the logic**, **Re-set from measured baseline** and **Scoped suppression** (with the sub-label *owner, reason, expiry*). An orange box, **Lower priority, keep visible**, catches the cases where none of the questions is answered yes. All outcomes lead to one dark box, **Tests, replay and review**.

**Relationships and arrows.** A *yes* arrow leaves each decision box to its fix; a *no* arrow leads to the next question. Every fix box has an arrow into **Tests, replay and review**, which is the point of the diagram's shape: no route reaches production without passing through the same gate.

**Execution flow.** The engineer asks the questions in order and stops at the first *yes*. The order runs from the most general change, a data fix that improves every rule using the field, to the most specific, a suppression that covers one documented pattern.

**Decision logic.** Each question needs evidence to answer. *Is the data wrong?* is answered by reading the raw events behind the false positives and comparing them with the normalised fields. *Logic broader than intent?* is answered by comparing the alert with the rule's own title, description and ATT&CK mapping (Lesson 3). *Threshold or window off baseline?* is answered by a sweep. *Known authorised instance?* is answered only by a record of approval with an owner, never by the identity of the user.

**Technical interpretation.** Each fix is a scope statement. A parser fix changes a field for every consumer; narrowing changes one rule for every entity; a new threshold changes one rule's sensitivity for every entity; a suppression changes one rule for one entity pattern. The further down the chain, the smaller the scope and the higher the maintenance cost per alert removed.

**Practical example.** In the next section, R6 fires on WS-102's twelve identical 180-byte requests to `crm.banyan.example` within one minute. The data is correct, so the first answer is *no*. A one-minute burst is not a beacon in any environment, so the second answer is *yes*, and the fix is to narrow the logic. A sanctioned agent that polls an update server every five minutes all day would instead reach the fourth question, because that really is regular, small and persistent.

**Security implications.** Every fix removes alerts; each must be justified with evidence and must not remove the behaviour the rule exists to catch. The common gate is the control: tests prove that known-bad samples still match, and replay shows how volume and precision change before anyone relies on the change.

**Key learning.** Find the cause first and make the most general fix that removes it; suppress only a specific, authorised instance, and send every change through the same test and review gate.

## Narrowing logic: the R6 burst

R6 is written as an aggregation over the whole data set: per host and URL, ten or more requests whose sizes vary by less than 50 bytes. Its name promises a *beacon*, a periodic check-in over time, but the query never looks at time. Any burst of identical small requests satisfies it, and modern web applications produce such bursts routinely (status polling, retries, health checks).

To reproduce the false positive, make a second working copy of the kit (here `change/`) and append twelve synthetic proxy events: WS-102 (user ben, whose workstation address in the dataset is 10.40.0.21) requesting a CRM status endpoint every five seconds for one minute, 180 bytes each. The last appended line is:

```json
{"@timestamp": "2026-11-03T09:30:55Z", "bytes_out": 180, "host": "WS-102", "source": "proxy", "src_ip": "10.40.0.21", "status": 200, "url": "https://crm.banyan.example/api/status", "user": "ben"}
```

The other eleven are identical apart from their timestamps, 09:30:00 to 09:30:50 in steps of five seconds. Reload and run the rules (only R6 is shown):

```terminal
$ python minisiem.py load
loaded 352 events
$ python minisiem.py rules
R6 beacon_regular_small: 2 hit(s)
    ('WS-102', 'https://crm.banyan.example/api/status', 12, 180, 180)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

The loader counts 340 + 12 = 352 events and R6 now has a false positive next to the real beacon. A suppression for `host = WS-102` would hide it, and would also hide a real beacon from WS-102 tomorrow. A suppression for the CRM URL would hide it, and would also hide a beacon to that URL if the CRM were ever compromised. Neither addresses the cause, which is that the rule's definition of "beacon" has no time dimension.

The narrowing adds one condition to R6's `HAVING` clause in the working copy of `minisiem.py`: the requests must span at least 30 minutes.

```sql
SELECT host, url, COUNT(*) AS hits, MIN(bytes_out) AS min_b, MAX(bytes_out) AS max_b
FROM events WHERE source='proxy'
GROUP BY host, url HAVING hits >= 10 AND max_b - min_b < 50
  AND (julianday(MAX(ts)) - julianday(MIN(ts))) * 1440 >= 30
```

`julianday()` converts the ISO 8601 timestamps to fractional days, so the difference between the last and first request multiplied by 1,440 is the span in minutes. Thirty minutes is chosen from the threat model, not from the burst: a beacon that checks in every five minutes covers 30 minutes after seven check-ins, and an implant that is useful to an attacker has to stay in contact for longer than that. Rerun:

```terminal
$ python minisiem.py rules
R6 beacon_regular_small: 1 hit(s)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

(Only R6 is shown.) The burst is gone and the real beacon, 18 requests at five-minute intervals from 06:17, remains. This is narrowing done well: the change brings the rule closer to its own name, it applies to every host equally, and it needs no list of exceptions to maintain.

(The traceback's full path to the working copy is shortened to `...`.) The known-bad R6 test no longer matches. The kit's test builds ten 220-byte requests *without timestamps*, because the original rule ignored time. With no `ts`, `julianday()` returns NULL, the span condition is NULL, and SQL treats NULL in a `HAVING` clause as not true, so the group is dropped. The rule is right and the test fixture is now unrealistic. This is the typical shape of a test failure after tuning, and it must be investigated, never bypassed. Two outcomes are possible: the change broke detection (revert it), or the change made a test's assumptions out of date (fix the test so that it describes the new specification). Here it is the second.

The test fix gives the known-bad sample realistic timing, ten requests five minutes apart, and adds a new near-miss test that freezes the reason for the change into the suite:

```python
    def test_regular_small_requests(self):
        ev = [dict(source="proxy", host="WS-1", url="https://c2.example/p", bytes_out=220,
                   ts=f"2026-11-03T{6 + (5 * i) // 60:02d}:{(5 * i) % 60:02d}:00Z")
              for i in range(10)]
        self.assertEqual(len(run(self.rule, ev)), 1)

    def test_short_burst_not_matched(self):
        ev = [dict(source="proxy", host="WS-1", url="https://crm.example/api/status",
                   bytes_out=180, ts=f"2026-11-03T09:30:{5 * i:02d}Z") for i in range(12)]
        self.assertEqual(run(self.rule, ev), [])
```

The f-string in the first test produces 06:00:00, 06:05:00 and so on to 06:45:00, a span of 45 minutes. The second test is the WS-102 burst in miniature: twelve requests five seconds apart.

> [!TIP]
> Not every regular, small, persistent pattern is malicious. A sanctioned update agent or monitoring probe can be every bit as regular as an implant. That case reaches the fourth question in the figure, not the second: the behaviour matches R6's intent and only the instance is approved. It calls for a scoped suppression or enrichment that marks the destination as sanctioned, handled as Module 5 described, not for loosening R6 for everyone.
