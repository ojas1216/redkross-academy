## Introduction and conceptual foundation

A detection rule is a hypothesis: "if this behaviour happens, these events will appear, and this logic will recognise them, and nothing else will". Every part of that sentence can be wrong. The behaviour might produce different events from the ones you expected; the events might not reach the SIEM; the logic might contain a typo, a case-sensitivity error or an off-by-one threshold; and the logic might match far more legitimate activity than you imagined. Lessons 1 and 2 taught you to write the logic carefully, and Lesson 3 taught you to say precisely which technique it claims to detect. This lesson is about **proving** those claims before an analyst has to rely on them.

The idea is borrowed directly from software engineering. A well-run development team does not ship code because it "looks right"; it ships code that passes a suite of automated tests, and it adds a test every time a bug is found so that the bug cannot quietly return. Detection engineering treats rules the same way, which is why the practice is often called **detection as code**. Rules live in version control, every rule has test cases, and the tests run automatically whenever a rule changes.

The core of rule testing is simple to state. For every rule you write at least two kinds of case:

- **Positive cases**: known-bad events that represent the behaviour. The rule **must fire**.
- **Negative cases**: known-good events, ideally **near misses** that resemble the behaviour but are legitimate or out of scope. The rule **must not fire**.

A rule that passes only positive cases may be catching half the network; a rule that passes only negative cases may be catching nothing. The pair together pins the rule's behaviour from both sides. To these two, practitioners add **boundary cases** (exactly at and just below a threshold), **regression cases** (a recreation of every past miss or false positive), and **known-limitation cases** (documented gaps that the team has decided to accept, recorded so that the decision is visible).

Unit tests answer "is the logic right?". Two further kinds of testing answer different questions. **Historical replay** runs the rule over days or weeks of real stored data to answer "how noisy is it?". **End-to-end emulation** safely reproduces the behaviour in an isolated lab to answer "does the telemetry actually arrive, with the fields the rule needs?". This lesson concentrates on unit testing with the course kit, because it is the part you can automate and run hundreds of times a day, and then places replay and emulation around it.

All the commands in this lesson were run in a scratch copy of `LAB_ASSETS/C08/` with CPython 3.14.4. The outputs are the real outputs of those runs.

> [!NOTE]
> Rule testing is a defensive activity on your own data. When a test needs attacker-like activity to happen for real (end-to-end emulation), it is done only in an isolated lab you own or in a formally authorised exercise with written scope, using benign stand-ins wherever possible. Course 19 covers how such exercises are run.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Test case | One input (one or more events) plus the expected result of running the rule on it. |
| Positive case | A known-bad input that the rule must match. Proves the rule can fire. |
| Negative case | A known-good input that the rule must not match. Proves the rule is not over-broad. |
| Near miss | A negative case that differs from a positive case in exactly one attribute, so that it tests one specific part of the logic. |
| Boundary case | A case at the edge of a threshold or window (for example exactly 5 users, and 4 users) that documents the exact limit. |
| Regression case | A test added after a missed detection or a false positive, so that the same problem cannot silently return. |
| Test oracle | The source of truth for the expected result: here, the analyst's written statement of what the rule must and must not detect. |
| Fixture | The controlled environment a test runs in; in the kit, a fresh in-memory SQLite table per test. |
| Historical replay | Running a rule over a large body of stored production data to measure alert volume and spot false positives. |
| End-to-end emulation | Safely reproducing a behaviour on a lab system to confirm that the expected events are generated, collected, parsed and matched. |
| Detection as code | Managing rules like software: version control, peer review, automated tests and a deployment pipeline. |

## How the kit's unit tests work

The kit provides two files that work together. `LAB_ASSETS/C08/minisiem.py` defines the rules: a Python dictionary named `RULES` that maps each rule name to an SQL query, and a list named `FIELDS` that names the columns of the `events` table. `LAB_ASSETS/C08/test_rules.py` imports both and tests three of the six rules (R1, R2 and R6) with Python's standard `unittest` framework.

The heart of the test file is a helper function called `run`:

```python
def run(rule, events):
    con = sqlite3.connect(":memory:")
    con.execute(f"CREATE TABLE events ({', '.join(FIELDS)}, raw TEXT)")
    for e in events:
        con.execute(f"INSERT INTO events VALUES ({', '.join('?' * (len(FIELDS) + 1))})",
                    [e.get(f) for f in FIELDS] + [""])
    return con.execute(RULES[rule]).fetchall()
```

Line by line: `sqlite3.connect(":memory:")` opens a brand-new database that exists only in memory, so every test starts from an empty, isolated fixture and no test can be affected by another. The `CREATE TABLE` statement builds the same `events` table that minisiem builds from the real dataset, using the shared `FIELDS` list so that the test and production schemas cannot drift apart. The loop inserts each test event, a Python dictionary; `e.get(f)` returns `None` for any field the dictionary does not mention, which SQLite stores as `NULL`. The `?` placeholders make the insert a parameterised query, so values are passed as data, never pasted into SQL text. Finally, the function executes the **real rule text** from `RULES` and returns the matching rows as a list.

That last point is the most important design decision in the file. The test does not contain its own copy of the rule logic; it runs the same string that production runs. If someone edits R2 in `minisiem.py`, the next test run exercises the edited version. A test that checks a copy of the rule proves nothing about the rule.

Each test then asserts on the result. A positive case asserts that exactly one row came back, `self.assertEqual(len(run(self.rule, [e])), 1)`; a negative case asserts that the result is an empty list, `self.assertEqual(run(self.rule, [e]), [])`. ### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows the path of a single unit test through the kit, from a hand-written event to a pass or fail verdict. It matters because every rule test you write in this course, and most detection-as-code frameworks in industry, follow the same five-stage shape: build input, build fixture, run the real rule, compare with the expectation, report.

**Components.** There are five steps in a vertical sequence. The slate first step, **Synthetic test event**, has the sub-label "Python dict: only the fields the rule reads". The blue second step, **Fresh in-memory table**, reads "sqlite3 ':memory:' with minisiem FIELDS". The orange third step, **Run the production rule**, reads "RULES[rule] from minisiem.py, unchanged". The violet fourth step, **Compare with the oracle**, reads "assertEqual: 1 row (positive) or [] (negative)". The dark final step, **ok / FAIL**, reads "unittest reports per test; any FAIL blocks the change".

**Relationships and arrows.** The arrows run downwards in one direction only: data flows from the test's input to the verdict and nothing flows back. The key relationship is between the third step and `minisiem.py`: the test borrows the rule text rather than restating it, so the arrow into **Run the production rule** carries the exact query an analyst's SIEM would run.

**Execution flow.** Take `test_word_spawns_powershell` from class R1. Step one creates `dict(source="sysmon", event_id=1, parent_image=WORD, image=PS)`, where `WORD` and `PS` are the full Office 16 and PowerShell paths defined at the top of the file. Step two creates an empty table and inserts that one row; every other column is `NULL`. Step three runs R1, which requires `source='sysmon'`, `event_id=1`, a parent containing `winword.exe` and an image containing `powershell.exe` or `cmd.exe`, all compared in lower case. Step four checks that one row came back. Step five prints `ok`.

**Decision logic.** The only branch is at the violet comparison step. If the rule returns what the oracle predicted, the test passes; otherwise `unittest` prints `FAIL` with the expected and actual values. A positive case that fails means the rule is blind to the behaviour; a negative case that fails means the rule is too broad.

**Technical interpretation.** Because the fixture is rebuilt for every call, tests are independent and can run in any order. Because the event contains only the fields the rule reads, the test also documents the rule's data dependencies: if R1 needed `command_line`, the positive case would have to supply it.

**Practical example.** In the near-miss test `test_explorer_spawns_powershell_is_not_matched`, the event is identical except that the parent is `C:\Windows\explorer.exe`. It travels through the same five steps and step four expects an empty list. One attribute differs, so the test proves that the parent condition, specifically, is doing its job.

**Security implications.** A green test run is evidence about logic, not about telemetry. All five steps happen inside the test process; none of them proves that Sysmon on a real workstation records the parent image or that the SIEM parses it into `parent_image`. That gap is closed by end-to-end testing, discussed later in this lesson.

**Key learning.** A good unit test runs the production rule, unchanged, against a minimal synthetic event in a fresh fixture, and compares the result with a written expectation.
