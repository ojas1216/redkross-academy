## Introduction and conceptual foundation

A detection rule is a hypothesis: "if this behaviour happens, these events will appear, and this logic will recognise them, and nothing else will". Every part of that sentence can be wrong. The behaviour might produce different events from the ones you expected; the events might not reach the SIEM; the logic might contain a typo, a case-sensitivity error or an off-by-one threshold; and the logic might match far more legitimate activity than you imagined. Lessons 1 and 2 taught you to write the logic carefully, and Lesson 3 taught you to say precisely which technique it claims to detect. This lesson is about **proving** those claims before an analyst has to rely on them.

The idea is borrowed directly from software engineering. A well-run development team does not ship code because it "looks right"; it ships code that passes a suite of automated tests, and it adds a test every time a bug is found so that the bug cannot quietly return. Detection engineering treats rules the same way, which is why the practice is often called **detection as code**. Rules live in version control, every rule has test cases, and the tests run automatically whenever a rule changes.

The core of rule testing is simple to state. For every rule you write at least two kinds of case:

- **Positive cases**: known-bad events that represent the behaviour. The rule **must fire**.
- **Negative cases**: known-good events, ideally **near misses** that resemble the behaviour but are legitimate or out of scope. The rule **must not fire**.

A rule that passes only positive cases may be catching half the network; a rule that passes only negative cases may be catching nothing. The pair together pins the rule's behaviour from both sides. To these two, practitioners add **boundary cases** (exactly at and just below a threshold), **regression cases** (a recreation of every past miss or false positive), and **known-limitation cases** (documented gaps that the team has decided to accept, recorded so that the decision is visible).

Unit tests answer "is the logic right?". Two further kinds of testing answer different questions. **Historical replay** runs the rule over days or weeks of real stored data to answer "how noisy is it?". **End-to-end emulation** safely reproduces the behaviour in an isolated lab to answer "does the telemetry actually arrive, with the fields the rule needs?". This lesson concentrates on unit testing with the course kit, because it is the part you can automate and run hundreds of times a day, and then places replay and emulation around it.

All the commands in this lesson were run in a scratch copy of `LAB_ASSETS/C08/` with CPython 3.14.4. The outputs are the real outputs of those runs.

> [!NOTE]
> Rule testing is a defensive activity on your own data. When a test needs attacker-like activity to happen for real (end-to-end emulation), it is done only in an isolated lab you own or in a formally authorised exercise with written scope, using benign stand-ins wherever possible. Course 19 covers how such exercises are run.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Test case | One input (one or more events) plus the expected result of running the rule on it. |
| Positive case | A known-bad input that the rule must match. Proves the rule can fire. |
| Negative case | A known-good input that the rule must not match. Proves the rule is not over-broad. |
| Near miss | A negative case that differs from a positive case in exactly one attribute, so that it tests one specific part of the logic. |
| Boundary case | A case at the edge of a threshold or window (for example exactly 5 users, and 4 users) that documents the exact limit. |
| Regression case | A test added after a missed detection or a false positive, so that the same problem cannot silently return. |
| Test oracle | The source of truth for the expected result: here, the analyst's written statement of what the rule must and must not detect. |
| Fixture | The controlled environment a test runs in; in the kit, a fresh in-memory SQLite table per test. |
| Historical replay | Running a rule over a large body of stored production data to measure alert volume and spot false positives. |
| End-to-end emulation | Safely reproducing a behaviour on a lab system to confirm that the expected events are generated, collected, parsed and matched. |
| Detection as code | Managing rules like software: version control, peer review, automated tests and a deployment pipeline. |

## How the kit's unit tests work

The kit provides two files that work together. `LAB_ASSETS/C08/minisiem.py` defines the rules: a Python dictionary named `RULES` that maps each rule name to an SQL query, and a list named `FIELDS` that names the columns of the `events` table. `LAB_ASSETS/C08/test_rules.py` imports both and tests three of the six rules (R1, R2 and R6) with Python's standard `unittest` framework.

The heart of the test file is a helper function called `run`:

```python
def run(rule, events):
    con = sqlite3.connect(":memory:")
    con.execute(f"CREATE TABLE events ({', '.join(FIELDS)}, raw TEXT)")
    for e in events:
        con.execute(f"INSERT INTO events VALUES ({', '.join('?' * (len(FIELDS) + 1))})",
                    [e.get(f) for f in FIELDS] + [""])
    return con.execute(RULES[rule]).fetchall()
```

Line by line: `sqlite3.connect(":memory:")` opens a brand-new database that exists only in memory, so every test starts from an empty, isolated fixture and no test can be affected by another. The `CREATE TABLE` statement builds the same `events` table that minisiem builds from the real dataset, using the shared `FIELDS` list so that the test and production schemas cannot drift apart. The loop inserts each test event, a Python dictionary; `e.get(f)` returns `None` for any field the dictionary does not mention, which SQLite stores as `NULL`. The `?` placeholders make the insert a parameterised query, so values are passed as data, never pasted into SQL text. Finally, the function executes the **real rule text** from `RULES` and returns the matching rows as a list.

That last point is the most important design decision in the file. The test does not contain its own copy of the rule logic; it runs the same string that production runs. If someone edits R2 in `minisiem.py`, the next test run exercises the edited version. A test that checks a copy of the rule proves nothing about the rule.

Each test then asserts on the result. A positive case asserts that exactly one row came back, `self.assertEqual(len(run(self.rule, [e])), 1)`; a negative case asserts that the result is an empty list, `self.assertEqual(run(self.rule, [e]), [])`. **Execution flow.** Take `test_word_spawns_powershell` from class R1. Step one creates `dict(source="sysmon", event_id=1, parent_image=WORD, image=PS)`, where `WORD` and `PS` are the full Office 16 and PowerShell paths defined at the top of the file. Step two creates an empty table and inserts that one row; every other column is `NULL`. Step three runs R1, which requires `source='sysmon'`, `event_id=1`, a parent containing `winword.exe` and an image containing `powershell.exe` or `cmd.exe`, all compared in lower case. Step four checks that one row came back. Step five prints `ok`.

**Decision logic.** The only branch is at the violet comparison step. If the rule returns what the oracle predicted, the test passes; otherwise `unittest` prints `FAIL` with the expected and actual values. A positive case that fails means the rule is blind to the behaviour; a negative case that fails means the rule is too broad.

**Technical interpretation.** Because the fixture is rebuilt for every call, tests are independent and can run in any order. Because the event contains only the fields the rule reads, the test also documents the rule's data dependencies: if R1 needed `command_line`, the positive case would have to supply it.

**Practical example.** In the near-miss test `test_explorer_spawns_powershell_is_not_matched`, the event is identical except that the parent is `C:\Windows\explorer.exe`. It travels through the same five steps and step four expects an empty list. One attribute differs, so the test proves that the parent condition, specifically, is doing its job.

**Security implications.** A green test run is evidence about logic, not about telemetry. All five steps happen inside the test process; none of them proves that Sysmon on a real workstation records the parent image or that the SIEM parses it into `parent_image`. That gap is closed by end-to-end testing, discussed later in this lesson.

**Key learning.** A good unit test runs the production rule, unchanged, against a minimal synthetic event in a fresh fixture, and compares the result with a written expectation.

## Designing test cases

Writing the code of a test is easy; choosing the cases is the skill. A useful method is to list the **decision points** in the rule, the conditions that each have to be true for it to fire, and then write one positive case that satisfies all of them and one near miss per condition that breaks only that condition.

R2, the VPN spray rule, shows the method well. Its SQL joins every VPN success to the VPN failures from the same source IP at or before the success, groups them, and keeps groups where at least five distinct users failed:

```sql
SELECT s.src_ip, COUNT(DISTINCT f.user) AS users_failed, s.user AS success_user, s.ts
FROM events s JOIN events f ON f.src_ip = s.src_ip
WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn'
  AND f.outcome='failure' AND f.ts <= s.ts
GROUP BY s.src_ip, s.user, s.ts HAVING users_failed >= 5
```

Its decision points are: failures and success come from the same IP; at least five distinct users failed; a success exists; the failures came at or before the success. The kit's R2 class builds its cases with a small generator:

```python
def spray(self, n, success=True):
    ev = [dict(source="vpn", outcome="failure", user=f"u{i}", src_ip="203.0.113.9",
               ts=f"2026-11-03T06:00:{i:02d}Z") for i in range(n)]
    if success:
        ev.append(dict(source="vpn", outcome="success", user="u0", src_ip="203.0.113.9",
                       ts="2026-11-03T06:05:00Z"))
    return ev
```

`spray(n)` produces `n` failures for users `u0` to `u(n-1)`, one second apart, from the documentation address 203.0.113.9, followed by a success for `u0`. The three tests then use it to probe three decision points: `spray(5)` is the positive case at the threshold; `spray(4)` is the boundary near miss one below it; and `spray(8, success=False)` is a near miss that has plenty of failures but no success. Notice that the boundary is tested from both sides. A test only at eight users would still pass if someone changed `>= 5` to `>= 8`; testing at exactly five and at four fixes the threshold precisely.

Applying the same method to R1 gives the parent condition (tested by the explorer.exe near miss), the child condition (not tested by the kit), the event type and the case handling. R6, the beacon rule, has a count condition (at least ten hits per host and URL) and a regularity condition (largest minus smallest size under 50 bytes); the kit tests the second with ten requests whose sizes grow by 40 bytes each, a spread of 360 bytes.

> [!TIP]
> Name tests after the behaviour, not the mechanics: `test_four_users_is_below_threshold` tells a reviewer exactly what the rule is meant to do without reading the code. Good test names become the rule's executable specification.

## Extending the tests: what a failing test teaches

To close part of that gap, a second file, `test_extra.py`, was written in the scratch copy. It imports the kit's own `run`, `WORD` and `PS` so that it uses exactly the same fixture, and adds cases for R3, R5 and further R1 edges. The R5 class is the interesting one:

```python
class R5(unittest.TestCase):
    rule = "R5 log_cleared"

    def test_security_log_cleared_1102(self):
        e = dict(source="windows", event_id=1102, user="divya")
        self.assertEqual(len(run(self.rule, [e])), 1)

    def test_logon_4624_is_not_matched(self):
        e = dict(source="windows", event_id=4624, user="divya")
        self.assertEqual(run(self.rule, [e]), [])

    def test_1102_from_another_source_is_not_matched(self):
        e = dict(source="appliance", event_id=1102, user="-")
        self.assertEqual(run(self.rule, [e]), [])
```

The third case encodes a weakness already known from the kit's Sigma version of this rule, `rk_security_log_cleared.yml`: converted to Splunk without a processing pipeline, it becomes the bare query `EventID=1102`, which could match an unrelated event that happens to share the number. The test asks whether R5 has the same weakness, using a synthetic event from a different source. ## Regression protection: tests that guard tuning

Tests are most valuable not when a rule is written but when it is changed. Suppose an analyst, tired of R2 alerts, raises its threshold from five users to six without telling anyone. To see what happens, the scratch script `tuned_threshold.py` made exactly that change to the in-memory copy of `RULES` and reran the kit's tests:

```terminal

Without the test, the change would have shipped silently and the only symptom would have been a missed intrusion months later. With it, the change cannot be merged until someone consciously updates both the rule and its test, which forces the discussion the team should have had. That is what "tests document the exact threshold" means in practice.

## Beyond unit tests: replay and end-to-end checks

Unit tests prove the logic against events you invented. Two further checks connect the rule to reality.

### Historical replay: how noisy will it be?

Replay runs the rule over a large body of real stored data and counts the hits. The question is not "does it fire?" but "how often, and on what?". A rule that passes every unit test but would produce four hundred alerts a day is not ready to deploy, however correct its logic.

In the lab, `python minisiem.py rules` over the 340-event Banyan dataset is a miniature replay. It produced 1, 1, 2, 1, 1 and 1 hits for R1 to R6, every one of them part of the storyline, so on this data each rule's precision is perfect. That result is expected and therefore weak evidence: the dataset was built to contain the attack. In a real SOC you would replay against several weeks of production data from the systems the rule will watch, inspect a sample of the hits, and record the expected daily volume in the rule's documentation so that a later change in volume is noticed. Replay is also where the two defects found above would have shown up as real false positives, much more expensively.

### End-to-end checks: does the telemetry arrive?

A unit test inserts `parent_image` directly into a table. In production, that value has to be produced by Sysmon on a workstation, forwarded, parsed and normalised into the field the rule reads. If any link is broken (Sysmon not installed on a new build, a parser update renaming a field, a forwarder dropping a channel), the rule is logically perfect and practically blind.

End-to-end testing closes that gap by making the real event happen in a controlled way and checking that the rule fires in the real SIEM. For many behaviours a completely benign stand-in exists. To test R3, an administrator in an isolated lab domain can create a local test account and then delete it; Windows writes event 4720 on creation, and the test passes when the alert appears with the right host and account name. To test R5 in a lab, clearing the Security log of a disposable lab virtual machine generates event 1102. For R1, a harmless lab document whose only action is to start PowerShell with a benign command exercises the same parent-child relationship without any malicious content.

> [!CAUTION]
> End-to-end tests change real systems. Run them only on lab machines you own or within a written, authorised test plan; never clear logs or create accounts on production or third-party systems to "see if the SIEM notices". Record each test (who, when, on which host) so that its events are not later mistaken for an intrusion, and remove any test accounts afterwards.

Because end-to-end tests are slower and need lab infrastructure, teams usually run them on a schedule (for example after every SIEM or agent upgrade) rather than on every rule change. The unit tests run on every change; the end-to-end tests confirm periodically that the pipeline underneath them still works.

## Tests in the detection-as-code pipeline

The three kinds of test fit into the rule's life in a fixed order. When an engineer changes a rule, the repository's pipeline first validates its syntax (for Sigma rules, `sigma check`), then runs the unit tests, and refuses the change if any test fails. A reviewer (Lesson 7) then reads the rule together with its tests, which is far quicker than reasoning about the logic unaided. Before deployment the rule is replayed against recent data to estimate volume. After deployment, scheduled end-to-end checks and production metrics (Lesson 5 and Module 1) take over. Each stage catches a different class of fault, and none replaces another.

A practical rule follows: **no rule without tests, and no change without a test run**. When a rule is tuned, the tuning change and the updated or new test travel in the same commit, so that the history shows not only what changed but what behaviour the change was meant to preserve.

## Common mistakes and misconceptions

**Testing only the attack example.** The positive case is usually the event that inspired the rule, so it almost always passes. As the test report showed, defects are found by negative cases.

**Near misses that differ in many attributes.** If the negative case changes the parent, the child and the host at once, a pass tells you nothing about which condition did the work. Change one attribute per near miss.

**Copying the rule into the test.** A test that contains its own version of the query keeps passing after the real rule changes. Always execute the production rule text, as `run()` does.

**Testing a threshold from one side only.** Five users must fire and four must not; testing only at eight leaves the threshold unpinned.

**Deleting or weakening a failing test to make the build pass.** A red test is a finding. Fix the rule, or record an explicit, reviewed decision to accept the limitation.

**Believing a green test suite means the rule works in production.** It means the logic is right. Telemetry, parsing and volume need replay and end-to-end checks.

## Security implications, detection and defence

Rule testing is where detection quality is made measurable. Untested rules fail in two dangerous ways. Over-broad rules generate false positives that teach analysts to ignore an alert, so that the one true positive is closed unread; both defects found in this lesson were of that kind. Over-narrow or broken rules fail silently: nobody notices a rule that never fires, and the gap only becomes visible during an incident review. A test suite turns both failure modes into a red line in a build log, at the moment a change is made, when they are cheapest to fix.

Tests also protect against the slow drift that affects every detection estate. Parsers are updated, field names change, thresholds are tuned under pressure, and engineers move on. Without tests, the knowledge of what a rule is meant to catch lives in someone's head; with tests, it is written down, runnable and enforced.

## Best practices

- Write at least one positive case and one near miss per decision point, and test every threshold from both sides.
- Run the production rule text in a fresh, isolated fixture; never a copy.
- Turn every missed detection and every confirmed false positive into a regression test.
- Keep rule and tests in the same repository and change them in the same commit; block merges on failing tests.
- Replay against recent production data before deployment and record expected volume.
- Schedule end-to-end checks with benign stand-ins in an isolated lab, especially after agent, parser or SIEM upgrades.

## Key takeaways

- Every rule needs positive cases that must fire and near-miss negative cases that must not; boundary cases pin thresholds exactly.
- The kit's `run()` helper shows the right design: a fresh in-memory fixture and the unchanged production rule.
- Near misses found two real defects in the Banyan rules: R5 ignores the event source, and R2 has no time window.
- Tests turn silent tuning mistakes into immediate failures, as the five-to-six threshold change showed.
- Unit tests prove logic; replay measures noise and end-to-end checks in an authorised lab prove the telemetry arrives.
