## Introduction and conceptual foundation

Every alert that reaches an analyst's queue exists because somebody once wrote a piece of logic that said "when the telemetry looks like *this*, tell a human". Modules 3 to 5 treated that logic mostly as a given: you loaded the Banyan Microfinance dataset into `minisiem.py`, ran the six saved rules R1 to R6, and triaged what they produced. This module turns the question around. You are now the person who writes the rule, and the quality of everything downstream (triage time, missed intrusions, analyst fatigue, the credibility of the SOC) depends on the choices you make at this stage.

**Detection engineering** is the discipline of designing, building, testing, deploying and maintaining that logic. It treats detections as software: they start from a requirement, they are written in a defined language, they are reviewed and tested before release, and they are measured once they run. This first lesson deals with the core design question that comes before any syntax: *what kind of logic should this detection use, and what will that choice cost?*

There are three broad answers. A **signature** detection looks for a specific known value or exact pattern: a file hash, a domain from an intelligence feed, an event ID that only one action produces. A **behavioural** detection looks for a pattern of activity that an attacker's technique produces regardless of the specific values involved, such as a word processor starting a command shell. An **anomaly** detection looks for a departure from what is normal for a user, host or population, such as an upload far larger than anything that host has sent before. Real rules often combine these, and they are expressed through a handful of logical shapes (single-event matches, thresholds, sequences and aggregations) that cut across the three families.

None of the three is "best". Each trades **precision** (how many of the alerts are real) against **recall** (how many of the real events produce an alert), and each fails in a characteristic way. Signatures are precise but brittle; behaviours are durable but need careful handling of legitimate look-alikes; anomalies catch the unknown but are noisy and need a baseline that may itself be contaminated. A detection engineer's job is not to pick one family but to know which one a given threat calls for, to state the trade-off openly, and to layer rules so that the weaknesses of one are covered by another.

The lesson uses the kit's six minisiem rules as running examples. Earlier modules introduced them as things to run and triage; here you take each one apart as a design: what it keys on, which values the attacker controls, what legitimate activity looks the same, and what happens to its precision and recall when you change a single number.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Detection logic | The condition, applied to telemetry, that decides whether an alert is raised. |
| Signature (atomic) detection | Logic that matches a specific known value or exact pattern: a hash, domain, IP address, string or uniquely meaningful event ID. |
| Behavioural detection | Logic that matches a pattern of activity produced by a technique, independent of the particular values an attacker can change. |
| Anomaly (statistical) detection | Logic that fires on deviation from a measured baseline of normal activity for an entity or population. |
| Baseline | The measured normal range of a quantity (bytes sent, logon hours, process pairs) for a host, user or group. |
| True positive (TP) | An alert raised on activity that is genuinely the threat the rule is meant to detect. |
| False positive (FP) | An alert raised on activity that is not the threat (benign or out of the rule's intent). |
| False negative (FN) | Threat activity that occurred but raised no alert. |
| Precision | TP / (TP + FP): the share of alerts that are real. |
| Recall | TP / (TP + FN): the share of real threat events that produced an alert. Also called detection rate or sensitivity. |
| Base rate | How often the threat actually occurs in the data the rule examines; usually tiny compared with benign activity. |
| Attacker-controlled value | A field whose content the attacker can choose (file name, URL path, user agent) and therefore change to evade a rule. |
| Legitimate look-alike | Benign activity that produces the same telemetry pattern as the threat. |

## Three families of detection logic

### Signature detection: matching what is already known

A signature rule asks a yes-or-no question about a value: *is this hash in the list of known-bad hashes; is this domain the one named in the advisory; is this event the one with ID 1102?* You met the most common signature workflow in Module 6, where `ioc_match.py` compared proxy URLs and addresses against an intelligence feed. Signatures have three attractive properties. They are **cheap** to evaluate (an exact match or a set lookup). They are **precise**: if the value is truly unique to malicious activity, almost every hit is a true positive. And they are **explainable**: the alert carries its own justification ("this domain is on the ISAC's TLP:AMBER list").

Their weakness follows directly from what they match. A hash changes if one byte of the file changes. A domain is abandoned and replaced for a few currency units. An IP address is rented by the hour. These indicators sit at the bottom of David Bianco's Pyramid of Pain, which you met in Module 6: cheap for the attacker to change, so the signature's useful life is short. Signatures therefore have high precision but **narrow recall**: they detect *this* sample or *this* infrastructure, not the next one.

Not every signature is about attacker infrastructure, though. Rule **R5 log_cleared** is a signature in form, matching a single event ID:

```sql
SELECT ts, host, user FROM events WHERE event_id=1102
```

Windows writes Security event 1102 when the audit log is cleared. The value 1102 is not attacker-controlled in the way a file name is: an attacker who clears the Security log cannot choose a different event ID for that action. So R5 has the precision of a signature *and* durability, because what it matches is a property of the operating system, not of the attacker's tooling. That distinction (who controls the value being matched) matters more than the label "signature" or "behaviour".

### Behavioural detection: matching what the technique must do

A behavioural rule describes activity that a technique produces however the attacker implements it. Rule **R1 office_spawns_script** is the course's clearest example:

```sql
SELECT ts, host, user, image FROM events
WHERE source='sysmon' AND event_id=1
  AND lower(parent_image) LIKE '%winword.exe%'
  AND (lower(image) LIKE '%powershell.exe%' OR lower(image) LIKE '%cmd.exe%')
```

It does not care which document was opened, what it was called, where it came from or what the script did next. It cares about one relationship: Microsoft Word, a document editor, started a script interpreter. A malicious macro almost always has to hand off to something that can run commands, so the *parent-child relationship* survives changes to the lure, the sender, the download domain and the payload. That is why behaviour sits near the top of the Pyramid of Pain: to evade R1, the attacker must change *how* they execute code, not just *what* they send.

Rule **R3 new_local_admin** is also behavioural, although it looks like a signature: it matches Windows events 4720 (a user account was created) and 4732 (a member was added to a security-enabled local group). The behaviour it captures is "someone created or elevated a local account", a persistence step that does not depend on the account name the attacker chooses.

Behavioural rules pay for their durability with **legitimate look-alikes**. IT staff create accounts; some finance macros really do start scripts. The behaviour is the same whether the actor is an attacker or an administrator, so precision depends on how often the benign version happens in your estate and on the context you add to separate the two (who, where, when, how often). Behavioural rules also depend on the right telemetry existing: R1 is useless without process-creation events that record the parent image.

### Anomaly detection: matching what is unusual

An anomaly rule does not describe the threat at all. It describes *normal* and fires when something departs from it. In its full form it needs a **baseline**: a measured distribution of a quantity per entity (each user's usual upload volume, each host's usual logon hours, each server's usual outbound destinations), and a test for how far a new observation sits from that distribution.

The kit's two "unusual" rules are deliberately simplified. **R4 large_upload** uses a fixed number rather than a per-host baseline:

```sql
SELECT ts, host, user, url, bytes_out FROM events
WHERE source='proxy' AND bytes_out > 10000000
```

A fixed 10,000,000-byte threshold is the simplest approximation of "unusual": it says "more than about 10 MB in one request is not normal *anywhere* in this estate". **R6 beacon_regular_small** measures a different kind of abnormality, regularity:

```sql
SELECT host, url, COUNT(*) AS hits, MIN(bytes_out) AS min_b, MAX(bytes_out) AS max_b
FROM events WHERE source='proxy'
GROUP BY host, url HAVING hits >= 10 AND max_b - min_b < 50
```

Humans browsing the web produce requests of varied sizes; a program checking in with a command-and-control server tends to send the same small request again and again. R6 aggregates every request by host and URL and fires when there are many requests whose sizes barely vary.

Anomaly detection is the only family that can, in principle, catch something nobody has described yet. Its costs are equally clear. Unusual is not the same as malicious: the quarterly backup, the new marketing video upload and the software updater that polls every five minutes are all anomalies. Baselines take time to build and drift as the business changes. And if the attacker was already present while the baseline was measured, their activity becomes part of "normal".

### Logical shapes: how the families are expressed

Families describe *what* a rule looks for; shapes describe *how* the condition is computed. Module 3 Lesson 4 introduced the shapes in the context of correlation, and they map onto the families like this:

- **Single-event match**: one record is tested on its own (R1, R3, R4, R5). Any family can use it.
- **Threshold**: a count over a group or window must reach a number. **R2 vpn_spray_then_success** requires failures for at least five distinct users from one address.
- **Sequence**: events must occur in order. R2 also requires that the success comes after the failures (`f.ts <= s.ts`).
- **Aggregation**: a statistic over many events (count, spread, sum) is compared with a limit (R6).

R2 shows why the families blur in practice. "Many accounts failing from one address, then one succeeding" is a behaviour (password spraying followed by a valid logon), but it is *expressed* through a threshold and a sequence. When you design a rule, decide the family first (what fact about the threat are you relying on?) and the shape second (what computation captures that fact?).

**Execution flow and decision logic.** The table has no arrows, but there is an implied decision for each row: if the "Easiest evasion" is cheap for the attacker, the rule needs a partner that covers that evasion; if the "Legitimate look-alike" is common in your estate, the rule needs context or tuning before it can page anyone.

**Technical interpretation.** Notice that the evasion column names a *field the attacker controls* for R1 (the child image), R4 (request size), and R6 (size and timing), but an *operating-system fact* for R3 and R5. That is the deeper reason R5 can be both signature-shaped and durable. Notice also that the anomaly rules have the broadest look-alike column: they describe "unusual", and plenty of benign things are unusual.

**Practical example.** In the Banyan storyline, R1 fired at 06:14 on WS-104 when Word started PowerShell. Had the macro started `wscript.exe` instead, R1 would have stayed silent, but R6 would still have caught the 220-byte check-ins that followed, and R5 would still have caught the log clearing at 08:17. Layering, not any single rule, gave the SOC the intrusion.

**Security implications.** A rule whose evasion is trivial and whose look-alike is common (a pure name match on a popular tool, for example) gives both false confidence and noise. Writing this table during design review exposes such rules before they reach production.

**Key learning.** For every rule, name what it relies on, how it is most cheaply evaded and what benign activity looks the same; those three answers predict its false negatives, its durability and its false positives.

## Precision and recall: measuring the trade-off

Two numbers summarise how a rule behaves against reality. Using the counts defined in the terminology table:

$$\text{precision} = \frac{TP}{TP + FP} \qquad \text{recall} = \frac{TP}{TP + FN}$$

Precision answers the analyst's question: *when this rule fires, how often is it real?* Recall answers the defender's question: *when the threat happens, how often does this rule fire?* They pull against each other because almost every change to a rule moves the boundary between "alert" and "no alert". Make the condition looser and more true events fall inside it (recall rises) but so do more benign ones (precision falls). Make it tighter and the benign ones drop out (precision rises) but some true events drop out with them (recall falls).

The kit lets you see this with real numbers. R6 has two conditions in its `HAVING` clause: at least ten requests, and a size spread under 50 bytes. You can run variants of it with `minisiem.py search` against the loaded dataset. First, drop the spread condition and keep only the volume threshold:

```terminal
$ python minisiem.py search "SELECT host, url, COUNT(*) AS hits FROM events WHERE source='proxy' GROUP BY host, url HAVING hits >= 10"
host | url | hits
WS-103 | https://cdn.example.org/ | 10
WS-103 | https://intranet.banyan.example/ | 11
WS-104 | https://cdn-telemetry-sync.example/api/v2/ping | 18
```

`search` runs the quoted SQL against `minisiem.db` (created earlier by `python minisiem.py load`) and prints a header row and one line per result, with columns separated by ` | `. Three host-and-URL pairs now qualify, and only one of them (the WS-104 beacon) is the intrusion. The two WS-103 rows are a busy user on the intranet and a content-delivery site. Precision has fallen to one in three. Now restore the spread condition but raise the volume threshold from 10 to 20:

```terminal
$ python minisiem.py search "SELECT host, url, COUNT(*) AS hits FROM events WHERE source='proxy' GROUP BY host, url HAVING hits >= 20 AND MAX(bytes_out)-MIN(bytes_out) < 50"
host | url | hits
```

Only the header is printed: no rows. The beacon made 18 requests between 06:17 and 07:42, so a threshold of 20 misses it entirely. Recall for this storyline is now zero, and there is no alert to have a precision at all. The rule as shipped, with `hits >= 10 AND max_b - min_b < 50`, returns exactly the one true pair, as `python minisiem.py rules` showed in earlier modules:

```terminal
$ python minisiem.py rules
...
R6 beacon_regular_small: 1 hit(s)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

**Decision logic.** The second variant is better than the first because the extra condition encodes something *true about beacons* (constant size) that is *rarely true of people* (varied sizes). The third variant is worse because its extra strictness encodes nothing about beacons; it merely demands more of them. Good tightening adds discriminating information; bad tightening just raises a number.

**Technical interpretation.** The dataset is small and synthetic, so these counts are illustrations, not estimates for a real estate. In production, "1 true" becomes an unknown you estimate through testing (Lesson 4) and analyst feedback (Lesson 5), and recall is especially hard to measure because you rarely know about the attacks you missed.

**Practical example.** Imagine a vendor's update agent on every Banyan workstation that polls a fixed URL with identical 300-byte requests every few minutes. All three variants would fire on it, on every host. R6 would need an allowlist of known agents or a further condition (for example, a destination first seen recently) before deployment.

**Security implications.** An attacker who understands the rule can add random padding to each request so that the spread exceeds 50 bytes, moving the beacon out of all three variants. Knowing the trade-off includes knowing which condition the attacker can cheaply defeat.

**Key learning.** Tighten rules with conditions that describe the threat, not with bigger numbers; every threshold you raise should be checked against the real volume of the behaviour you are trying to catch.

### The base-rate problem

Precision is harsher in production than intuition suggests, because the threat is rare. Suppose, purely as an illustration, that a rule examines one million process-creation events a day, that ten of them are malicious, and that the rule catches all ten while wrongly flagging just 0.1% of the benign events. 0.1% of 999,990 is about 1,000 false positives. The rule's precision is $10 / (10 + 1000) \approx 0.01$: ninety-nine alerts in every hundred are noise, even though the rule is "99.9% accurate" on benign events.

This is why SOC detections cannot be judged by a single accuracy figure, and why the behavioural and signature rules that page analysts must have very low false-positive *rates*, while broad anomaly rules usually feed a risk score or a hunting queue rather than paging anyone directly. It is also why the size of the benign population matters when you choose where a rule runs: R1 examines only Sysmon process creations with Word as the parent, a tiny slice of all events, so even a modest false-positive rate produces few alerts.

### Which error is worse?

There is no universal answer, and you should decide it per rule and write the decision down. A missed log clearance (an R5 false negative) means an attacker removed evidence undetected, a serious loss for a rare and high-value event, so R5 is tuned for recall and accepts the occasional maintenance false positive. A beacon detector on a network full of update agents may need to accept lower recall to remain usable at all, provided another layer (R1 on the initial execution, proxy category blocking, endpoint detection) covers the gap. The cost of a false positive is analyst time and, eventually, trust; the cost of a false negative is dwell time. Severity (Module 5) and the existence of compensating detections should drive the choice.

## Designing a rule: the questions to answer first

The syntax of a rule is the last and easiest part of the work. Before writing it, answer five questions in writing. They become the rule's documentation and the basis of its tests later in this module.

1. **What exactly is the behaviour?** State it in one sentence, in terms of the technique, not the tool: "a document editor starting a command interpreter", not "detect the invoice malware".
2. **Where does it appear in telemetry, and which fields carry it?** Which source (Sysmon process creation, Windows Security, proxy, VPN), which event type, which fields? If the data is not collected, the rule cannot work, however good its logic.
3. **Which of those values does the attacker control?** Anything the attacker can choose (file names, paths, command-line text, URL paths, request sizes, timing) can be changed to evade the rule. Prefer fields the attacker cannot easily change.
4. **What is the legitimate look-alike, and how often does it happen here?** Name the benign activity that produces the same pattern and estimate its volume in *your* estate.
5. **What context would make it more or less suspicious?** An unusual parent, a rare host, a privileged account, a first-seen destination, an out-of-hours time, a combination with another alert on the same entity.

### Worked example: hardening R1 on paper

Apply the questions to R1.

**The behaviour** is "Word starts a script interpreter", which is technique-level: it maps to user execution of a malicious file and to the use of a command or script interpreter. **The telemetry** is Sysmon event 1 (process creation), using the `parent_image` and `image` fields. In the Banyan dataset, Sysmon recorded 33 process creations. Grouping them by parent and child shows how distinctive the target behaviour is:

```terminal
$ python minisiem.py search "SELECT parent_image, image, COUNT(*) FROM events WHERE source='sysmon' AND event_id=1 GROUP BY 1,2"
parent_image | image | COUNT(*)
C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | 1
C:\Windows\explorer.exe | C:\Program Files\App\excel.exe | 8
C:\Windows\explorer.exe | C:\Program Files\App\explorer.exe | 8
C:\Windows\explorer.exe | C:\Program Files\App\msedge.exe | 8
C:\Windows\explorer.exe | C:\Program Files\App\outlook.exe | 8
```

`GROUP BY 1,2` groups by the first and second selected columns. Thirty-two of the 33 starts are ordinary applications launched from the Windows shell, `explorer.exe`; one is Word starting PowerShell. In this (synthetic) estate, the parent-child pair is a near-perfect discriminator, which is exactly what you want from a behavioural rule. A real estate would have many more pairs, and the first job would be to measure how often `WINWORD.EXE` legitimately has any child at all.

**Attacker-controlled values** are where R1 is weakest. The rule matches *names* in the image path. An attacker cannot easily make Word not be Word, but they can choose which interpreter to start, and they can copy an interpreter to a new name. The course library describes a fictional teaching scenario in which an authorised red team copied PowerShell to `updater.exe` and ran the same command past a name-based rule. Three design improvements address this, each at the level of what to look for rather than how to evade:

- **Match on a property the attacker cannot rename.** Sysmon and most EDR products record the executable's embedded original file name (Sysmon's `OriginalFileName` field), which stays `PowerShell.EXE` when the file is copied to another name. The kit's dataset does not include that field, so R1 cannot use it; a production rule should.
- **Widen the child list deliberately.** PowerShell and `cmd.exe` are the most common, but Windows has other script hosts (`wscript.exe`, `cscript.exe`, `mshta.exe`). Each one you add raises recall and must be checked for look-alikes.
- **Widen the parent list deliberately.** The kit restricts R1 to Word; Excel and PowerPoint macros are equally capable. The dataset shows `excel.exe` launched by `explorer.exe` eight times, which is normal and would not trigger an Excel-parent rule, but before widening you would measure Excel's own children in your estate.

**The look-alike** is an approved macro that starts a script, which the kit's Sigma version of this rule records under `falsepositives` (Lesson 2). **Context** that raises suspicion includes a document recently downloaded from an external domain (in the storyline, `invoice.docm` from `banyan-payroll-update.example` at 06:12), a command line with an encoded payload, and the same host producing a beacon shortly afterwards.

There is also a subtle **semantic** detail in the SQL. Windows paths are case-insensitive: `WINWORD.EXE`, `WinWord.exe` and `winword.exe` are the same program. R1 therefore lowercases the field with `lower()` and compares it with a lowercase pattern. In SQLite the `=` operator is case-sensitive, and although `LIKE` ignores the case of ASCII letters by default, that default can be changed and other query languages behave differently; writing the normalisation explicitly makes the rule's intent survive translation. In the dataset the parent path is stored as `...\Office16\WINWORD.EXE` in capitals, so a case-sensitive comparison against `winword.exe` would miss it. Forgetting this kind of normalisation is one of the most common reasons a correct-looking rule silently misses. Note too that `LIKE '%winword.exe%'` is a *contains* match: it would also match a hypothetical `notwinword.exe`. The Sigma version in Lesson 2 uses an *ends-with* match on `\WINWORD.EXE`, which is stricter.

### Context turns weak signals into strong ones

Some behaviours are too common to alert on alone but highly meaningful in combination. R3 (account created or added to a local group) fires on every legitimate provisioning action; R4 (a large upload) fires on every big legitimate transfer. On WS-104, however, R1, R6, R3, R4 and R5 all fired on the same host and user within about two hours. Module 3 Lesson 4 showed how entity risk aggregation turns such co-occurrence into a single, high-confidence alert. From a design point of view the lesson is: a rule does not have to be precise on its own if its job is to *contribute* to a case. Decide, for every rule, whether it is meant to page an analyst directly or to add weight to an entity, and design its precision target accordingly.

### Baselines for real anomaly rules

R4's fixed 10 MB threshold works on the dataset because ordinary proxy requests there are small: a summary by host shows that every workstation except WS-104 sent at most 3,999 bytes in a single request, and WS-104's maximum was the 48,200,000-byte upload. In a real business a single number rarely fits everyone. A design team in Banyan's marketing department might upload large files every day, while a payments approver almost never does. A per-entity baseline asks "is this large *for this host or user*?", typically by comparing the new value with that entity's own history (for example, its recent maximum or a high percentile of its past values) over a defined learning period.

Baselines bring their own design decisions: how long the learning period is, how often it is recalculated, how new hosts and users are treated before they have history, and how to stop an attacker's slow, gradual increase from becoming the new normal. These are tuning questions, which Lesson 5 develops; at the design stage, record which baseline the rule assumes and what it does for an entity with no history.

## Layering the families

Because each family fails differently, mature detection sets combine them on purpose:

| Family | Typical role | Fails when |
| --- | --- | --- |
| Signature on attacker infrastructure | Fast, cheap confirmation of known campaigns; feeds from intelligence (Module 6) | The attacker changes the indicator |
| Signature on operating-system facts | High-value single events (log cleared, audit policy changed) | Telemetry is missing or disabled first |
| Behavioural | Main alerting layer for techniques | The attacker uses a different technique or an unlisted variant |
| Anomaly | Catch the unknown; feed risk scores and hunts | The baseline is wrong or the attacker blends in |

In the storyline, a signature (the ISAC's domain list matched the beacon destination in Module 6), behaviours (R1, R2, R3), an operating-system fact (R5) and anomalies (R4, R6) each saw part of the intrusion. Any single layer, removed, would still have left the SOC with enough to open a case. That redundancy is the goal; a detection set in which each technique is covered by exactly one brittle rule is the opposite.

## Common mistakes and misconceptions

- **"Behavioural rules have no false positives."** They have different false positives: the legitimate version of the same behaviour. Measure it before deployment.
- **Matching on names the attacker chooses.** Process names, file names and URL paths are suggestions, not facts. Prefer original file names, signatures, hashes of known tools, or relationships.
- **Tightening by raising numbers.** As the R6 variants showed, a higher threshold can remove the true positive while adding no discriminating power.
- **Judging a rule by accuracy.** With a tiny base rate, a rule can be "99.9% accurate" and still produce ninety-nine false alerts in every hundred.
- **Forgetting case and normalisation.** Windows paths, user names and domains are often case-insensitive; a case-sensitive comparison is a hidden false negative.
- **Treating R4-style fixed thresholds as baselines.** A fixed number is a placeholder for a baseline, acceptable only when you have measured that it fits.
- **Designing without the data.** A rule for a field that is not collected, or is parsed under a different name, will pass review and never fire.

## Security implications, detection and defence

Detection logic is itself an attack surface. Attackers study public rules and common SIEM content and choose techniques that fall between them; the "Easiest evasion" column of Figure 1 is what a capable adversary will try. Defenders respond by preferring values the attacker cannot change, by layering families so that each evasion lands in a different rule, and by keeping some detection logic (thresholds, allowlists, enrichment sources) out of public view.

The second implication is dependency on telemetry. Every rule in this lesson assumes the data arrives. An attacker who disables Sysmon, stops log forwarding or clears logs blinds the rules that rely on that data. That is why R5 matters beyond its own alert, and why absence rules (Module 3) that notice a source going quiet are part of a sound detection design.

Finally, detections process personal data: user names, browsing history, authentication records. Under India's Digital Personal Data Protection Act 2023, processing should be for a lawful purpose and limited to what is necessary; design rules and alert payloads to carry the fields an analyst needs, not everything available.

## Best practices

- Write the five design answers (behaviour, telemetry, attacker-controlled values, look-alike, context) before the logic, and keep them with the rule.
- Choose the family from the fact you rely on; choose the shape (single event, threshold, sequence, aggregation) from how that fact appears in the data.
- Prefer conditions that describe the threat over conditions that merely demand more of it.
- State each rule's precision target and its role: page an analyst, contribute risk, or feed a hunt.
- Normalise case and field names explicitly, and check the semantics of every comparison (contains, ends with, equals).
- Record which error is worse for each rule, and which other rule compensates for its blind spot.
- Re-measure look-alike volume whenever the estate changes (new software, new departments, new log sources).

## Key takeaways

- Detection logic falls into three families: signatures match known values, behaviours match what a technique must do, anomalies match departures from normal. Shapes (single event, threshold, sequence, aggregation) express them.
- What matters most is who controls the value you match: operating-system facts (event 1102) are durable even as signatures; attacker-chosen names are brittle even inside a behavioural rule.
- Precision is TP / (TP + FP) and recall is TP / (TP + FN). Loosening a rule usually raises recall and lowers precision; tightening does the reverse.
- On the Banyan data, dropping R6's size condition gave 3 alerts with 1 true; raising its volume threshold to 20 missed the 18-request beacon entirely.
- Because threats are rare, a tiny false-positive rate can still mean that most alerts are noise; decide per rule whether it pages, scores or hunts.
- Layer families so that each cheap evasion lands in another rule's field of view, and design around the telemetry the attacker may try to remove.
