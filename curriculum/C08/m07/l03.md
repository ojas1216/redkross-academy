## Introduction and conceptual foundation

By the end of Lesson 2 you could write a Sigma rule, check it and convert it into a query. A rule on its own, however, answers only a narrow question: "does this pattern appear in my data?" A SOC manager, an auditor or a threat-intelligence team asks wider questions. Which attacker behaviours can we see at all? Which ones would we miss? If a report says a ransomware group uses a particular way to gain persistence, do we have anything that would fire? Answering those questions requires a shared vocabulary for attacker behaviour that every rule, every log source and every intelligence report can be attached to. In modern security operations that vocabulary is **MITRE ATT&CK**.

ATT&CK (Adversarial Tactics, Techniques and Common Knowledge) is a freely available knowledge base maintained by MITRE. It describes how adversaries behave once they target an organisation, and it is built from observed, publicly reported intrusions rather than from theory. Its central idea is that an intrusion is a sequence of **goals** (tactics) achieved by particular **methods** (techniques and sub-techniques), carried out in concrete ways by real groups and tools (procedures). Because the entries are numbered and stable enough to cite, a detection engineer in Pune, an incident responder in Singapore and a vendor's research team can all say "T1059.001" and mean the same thing: use of PowerShell as a command and scripting interpreter.

**ATT&CK mapping** is the practice of attaching those identifiers to your own artefacts. In this module the artefacts are detection rules, but the same practice is used for log sources, incident timelines, threat-intelligence reports, red-team findings and security controls. Mapping turns a pile of rules into something you can reason about as a whole: you can count, compare and colour your detections against a common grid and see where the empty squares are. That grid is the **coverage matrix**, and it is the bridge between this lesson and Lesson 6 (Coverage gaps).

Mapping is also easy to do badly: a coverage heat map that shows a technique as green because one untested rule mentions it creates false confidence. This lesson therefore treats mapping as a judgement with rules of evidence. You will learn how ATT&CK is structured, how to decide which technique a rule genuinely detects, how to link techniques to the data sources that make detection possible, how to build an honest coverage matrix, and how to keep mappings correct as ATT&CK itself changes.

Throughout, the worked examples use the course's Banyan dataset (`LAB_ASSETS/C08/banyan_events.jsonl`, 340 synthetic events) and the six correlation rules in the teaching SIEM `LAB_ASSETS/C08/minisiem.py`, together with the two Sigma rules in the kit.

> [!NOTE]
> Every technique ID in this lesson was chosen because it is long-established in ATT&CK Enterprise. ATT&CK is versioned and changes over time (techniques are added, renamed, split, deprecated or revoked), so the professional habit is to look an ID up in the version you are mapping to and record that version with the mapping. Never copy an ID from a blog post, a vendor rule or even a course file without checking it.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Matrix | A view of ATT&CK for one technology domain. Enterprise (Windows, Linux, macOS, cloud, network, containers and identity platforms), Mobile and ICS are the three domains. |
| Tactic | The adversary's tactical goal: the *why* of an action, such as Execution or Persistence. Identified as `TA` plus four digits, e.g. TA0002 Execution. Tactics are the columns of the matrix. |
| Technique | A general method of achieving a tactic: the *how*, such as T1059 Command and Scripting Interpreter. Identified as `T` plus four digits. |
| Sub-technique | A more specific variant of a technique, written as the parent ID plus a three-digit suffix, e.g. T1059.001 PowerShell. |
| Procedure | A specific, observed implementation of a technique by a group or tool, for example "a macro in a Word document starts hidden PowerShell with an encoded command". Procedures are what logs actually show. |
| Group / Software | ATT&CK entries for named threat groups (`G` IDs) and malware or tools (`S` IDs), each linked to the techniques they have been reported using. |
| Mitigation | A preventive control category linked to techniques (`M` IDs), such as restricting Office macros. |
| Data source | The kind of telemetry in which a technique can be observed (for example process creation, logon sessions, network traffic). ATT&CK's own way of modelling data sources has changed between versions; the idea of "which data shows this behaviour" is what matters here. |
| Mapping | Associating one of your artefacts (rule, log source, finding, report sentence) with the ATT&CK tactic and technique it represents, with a stated version and rationale. |
| Coverage matrix | A table or heat map that shows, per technique relevant to your threats, whether the data is collected, whether a detection exists and whether it has been tested. |
| ATT&CK Navigator | MITRE's open-source web tool for annotating and colouring the matrix; an annotated view is saved as a JSON "layer" file that can be shared and version-controlled. |

## How ATT&CK is organised

### Tactics: the adversary's goals

The Enterprise matrix arranges tactics roughly in the order in which an intrusion tends to unfold, although real intrusions loop back and skip steps. The long-standing Enterprise tactics, with their identifiers, are listed below. Notice that the numeric IDs are not in kill-chain order: TA0043 Reconnaissance and TA0042 Resource Development were added later and placed at the front, and TA0011 Command and Control comes before TA0010 Exfiltration in the matrix even though its number is higher. IDs are identifiers, not sequence numbers.

| Tactic ID | Tactic | The adversary is trying to... |
| --- | --- | --- |
| TA0043 | Reconnaissance | gather information to plan the operation |
| TA0042 | Resource Development | establish infrastructure, accounts or capabilities |
| TA0001 | Initial Access | get into your network |
| TA0002 | Execution | run malicious code |
| TA0003 | Persistence | keep their foothold across restarts and credential changes |
| TA0004 | Privilege Escalation | gain higher-level permissions |
| TA0005 | Stealth | avoid being noticed (formerly part of Defense Evasion) |
| TA0112 | Defense Impairment | disable or weaken defences such as logging and security tools (formerly part of Defense Evasion) |
| TA0006 | Credential Access | steal account names and passwords |
| TA0007 | Discovery | learn about your environment |
| TA0008 | Lateral Movement | move through your environment |
| TA0009 | Collection | gather data of interest |
| TA0011 | Command and Control | communicate with compromised systems |
| TA0010 | Exfiltration | steal data |
| TA0040 | Impact | disrupt, destroy or manipulate systems and data |

Two things about tactics matter for mapping. First, a tactic is a *goal*; a detection observes an action, and the tactic is inferred from what that action achieves. Second, one technique can serve more than one tactic. T1078 Valid Accounts appears under several tactics, among them Initial Access, Persistence and Privilege Escalation, because logging in with a stolen but genuine password can achieve each of them (check the current release for its full tactic list: ATT&CK content version 20.1 split the former Defense Evasion tactic into Stealth and Defense Impairment, and older material still shows the old name). When you tag such a technique, choose the tactic that matches what *your rule* sees in context, or list several only when the rule genuinely covers each.

### Techniques and sub-techniques: the methods

Each tactic column contains techniques. Many techniques are split into sub-techniques that describe more specific variants. T1059 Command and Scripting Interpreter, for example, has sub-techniques for PowerShell (T1059.001) and the Windows Command Shell (T1059.003) among others. T1110 Brute Force includes T1110.003 Password Spraying, where the attacker tries one or a few common passwords against many accounts instead of many passwords against one account.

The sub-technique level is usually the right level for a detection tag, because detections are specific. A rule that watches for `powershell.exe` starting under Word observes PowerShell specifically, so tagging T1059.001 says more than tagging T1059. Conversely, if you genuinely cannot tell which variant an event represents, tag the parent technique and say why; a precise-looking sub-technique that you guessed is a false statement.

### Procedures: what the logs actually show

Below the sub-technique sits the procedure: the concrete way a particular adversary performed the technique. Detection rules are written against procedures and their artefacts (a parent-child process pair, an event ID, a request pattern), and then mapped *upwards* to the technique and tactic. This is the core movement of mapping, and the figure below follows one rule from the Banyan case through every level of the hierarchy.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows the ATT&CK hierarchy as a stack, from the most abstract level at the top to the most concrete at the bottom, using one real chain from the course dataset. It exists to make one point concrete: you write rules at the bottom of the stack and map them upwards, never the other way round.

**Components.** There are five stacked bands. The dark top band, **Tactic: TA0002 Execution**, carries the sub-label "the why: run malicious code". The violet band below it, **Technique: T1059**, is labelled "Command and Scripting Interpreter". The orange band, **Sub-technique: T1059.001**, is labelled "PowerShell". The red band, **Procedure**, reads "Word macro starts hidden PowerShell (WS-104, 06:14)". The green band at the bottom, **Detection: minisiem R1 / Sigma rule**, reads "WINWORD.EXE parent + powershell.exe child". The note under the stack states the direction of mapping.

**Relationships.** Each band is a more specific case of the band above it. Execution can be achieved by many techniques; T1059 is one of them; PowerShell is one variant of T1059; the macro-launched PowerShell on WS-104 is one observed instance of that variant; and the rule is the logic that recognises the instance in telemetry.

**Execution flow.** Read the diagram bottom-up when you map. The Sysmon event at 06:14 on WS-104 records `WINWORD.EXE` as the parent of `powershell.exe` with `-W Hidden -EncodedCommand`. The rule fires on that parent-child pair. You then ask: what technique does this observation demonstrate? A scripting interpreter being run, specifically PowerShell, so T1059.001. And what goal does that serve? Running code, so TA0002 Execution.

**Decision logic.** The stack also shows where to stop. If the rule could not tell PowerShell from other interpreters, you would stop at the violet T1059 band. If the rule saw only "Word started something", you would not be entitled to the T1059 bands at all. The narrower the observation, the lower in the stack you can tag with confidence.

**Technical interpretation.** The upper bands are stable and shared across the industry; the lower bands are specific to your environment and change with each campaign. This is why a coverage matrix is organised by the upper bands while rules are built from the lower ones.

**Practical example.** The kit rule `rk_office_spawns_shell.yml` carries the tags `attack.execution`, `attack.t1204.002` and `attack.t1059.001`. The second tag, T1204.002 User Execution: Malicious File, sits beside T1059.001 in the same Execution column: the user opening a malicious document is a separate technique observed in the same event, because Word is the parent.

**Security implications.** Mapping downwards ("we need something for T1059, so search for the string PowerShell") produces brittle rules that match on names. Mapping upwards from a well-understood procedure produces tags that are true.

**Key learning.** Detections live at the procedure level; ATT&CK IDs are the labels you attach to them after asking what the detection actually observes.

## Mapping a detection: the rules of evidence

Mapping a rule means answering three questions in order, and writing the answers down.

1. **What does the rule observe?** State it in terms of fields and values, not intentions. R1 observes "a Sysmon process-creation event (event ID 1) whose parent image contains `winword.exe` and whose image contains `powershell.exe` or `cmd.exe`". It does not observe phishing, a macro or malicious intent.
2. **Which technique does that observation demonstrate?** Look the candidate technique up and read its description. Does the observed artefact meet the definition on its own, or only when combined with other evidence you do not have? Tag only what the artefact demonstrates on its own.
3. **Which tactic does it serve in this context?** For techniques that appear under several tactics, choose by what the action achieves in the scenario the rule targets.

Three principles follow from those questions.

**Tag what the rule detects, not what the attacker did.** The attacker in the Banyan case phished a user, ran code, beaconed, sprayed VPN passwords, created an account, uploaded data and cleared a log. R1 detects one moment of that story. If R1 were tagged with every technique in the incident, the coverage matrix would claim that one rule covers exfiltration, which it plainly does not.

**Prefer the most specific technique the evidence supports.** R1 sees `powershell.exe` by name, so T1059.001 is supported. But R1 also fires for `cmd.exe`, which is the Windows Command Shell, T1059.003. The kit rule tags only T1059.001. That is an under-mapping: the rule genuinely covers both sub-techniques, and a coverage matrix built from its tags will miss the second one. Small inconsistencies like this are exactly what a rule review (Lesson 7) should catch.

**When the evidence is ambiguous, tag the parent and record the doubt.** R4 fires on any proxy upload larger than 10,000,000 bytes. In the dataset it found 48,200,000 bytes sent to `https://files-share-drop.example/upload`. If you know the destination is a cloud storage service, T1567.002 Exfiltration Over Web Service: Exfiltration to Cloud Storage fits. If you only know it is an HTTPS web service, the parent T1567 Exfiltration Over Web Service is the honest tag. The rule itself cannot tell what kind of site it is talking to; that is enrichment, not detection.

| Observation (rule) | Evidence in the dataset | Technique | Tactic |
| --- | --- | --- | --- |
| Download of `invoice.docm` from a look-alike domain (no rule) | proxy, 06:12, WS-104 | T1566 Phishing (sub-technique unconfirmed) | Initial Access |

| Word is the parent of cmd.exe (R1, second branch) | not present in the dataset | T1059.003 Windows Command Shell | Execution |
| 18 identical 220-byte HTTPS requests (R6) | proxy, from 06:17 | T1071.001 Web Protocols | Command and Control |
| 8 users fail from one IP, then one succeeds (R2) | VPN, 203.0.113.66, 06:42-06:46 | T1110.003 Password Spraying | Credential Access |
| The success itself: a real password over the VPN (R2 output) | gopal at 06:46 | T1078 Valid Accounts; T1133 External Remote Services | Initial Access |
| Account `svc_update` created, event 4720 (R3) | Security log, 07:02 | T1136.001 Create Account: Local Account | Persistence |
| `svc_update` added to Administrators, event 4732 (R3) | Security log, 07:03 | T1098 Account Manipulation | Persistence; Privilege Escalation |
| 48.2 MB upload (R4) | proxy, 08:12 | T1567 Exfiltration Over Web Service (T1567.002 if the site is cloud storage) | Exfiltration |
| Security log cleared, event 1102 (R5) | Security log, 08:17 | T1685.005 Clear Windows Event Logs (formerly T1070.001) | Defense Impairment |

Several judgements in this table deserve a sentence each, because they are the kind you will make every week.

**The phishing row has no sub-technique.** The proxy shows a web download of a macro-enabled document from `banyan-payroll-update.example`. T1566.001 Spearphishing Attachment describes a file attached to a message; T1566.002 Spearphishing Link describes a link the user follows. A web download is more consistent with a link, but the lab collects no mail logs, so we cannot see how the URL reached the user. Tagging the parent T1566 and writing "delivery vector unconfirmed: no mail telemetry" is accurate; picking a sub-technique would be a guess. Notice also that *no rule* fires here. R1 catches the next step, which is a common and acceptable design, but the matrix must show that the initial-access step itself is undetected.

**R2 maps to two moments.** The failures are password spraying. The success afterwards is the use of a valid account through an external remote service. A rule that only counted failures would support T1110.003 alone; because R2 requires the success, its alert is evidence of T1078 and T1133 as well. Whether to tag all three is a team decision; many teams tag the technique the rule is *designed* to find (T1110.003) and mention the others in the rule's documentation.

**R3 maps to two techniques because it matches two event IDs.** Event 4720 is account creation; event 4732 is a member being added to a security-enabled local group. Mapping also exposed a limitation: minisiem's table has no `group` column, so R3 fires on *any* 4732, not only additions to Administrators, despite its name `new_local_admin`. Mapping forces you to read the logic closely enough to see such gaps.

**R5 and the kit's Sigma tag.** The kit's Sigma rule `LAB_ASSETS/C08/rk_security_log_cleared.yml` detects the same behaviour as R5 (Security event 1102) and carries the tag `attack.t1685.005`. That tag is current. In ATT&CK content version 20.1 the former Defense Evasion tactic was split into Stealth (TA0005) and Defense Impairment (TA0112), and clearing Windows event logs is now T1685.005 Clear Windows Event Logs under Defense Impairment, a sub-technique of T1685 Disable or Modify Tools. Older material, and older rules, cite the former ID T1070.001 Indicator Removal: Clear Windows Event Logs under Defense Evasion. The kit rule's weakness is not the ID but the missing record of which ATT&CK version it was mapped to: the next reviewer has no way to tell a current tag from a stale one. Pin the ATT&CK version your organisation maps to, record it with every mapping, and re-map older content that still uses the former ID. If the rule repository and the ATT&CK reference disagree, automated coverage reports silently drop or misplace the rule.

> [!IMPORTANT]
> A mapping is a claim. Write it down with its evidence: the ATT&CK version, the technique ID and name, and one sentence explaining why the rule's observation demonstrates that technique. A tag without a rationale cannot be reviewed.

### Writing the mapping into the rule

In Sigma, ATT&CK mappings go in the `tags` list using lower-case identifiers: `attack.` followed by the tactic name (`attack.execution`, `attack.defense-impairment`) or the technique ID (`attack.t1059.001`). Applying the judgements above to the kit's first rule would give:

```yaml
tags:
  - attack.execution
  - attack.t1204.002
  - attack.t1059.001
  - attack.t1059.003   # the rule also matches cmd.exe
```

and to the log-clearing rule, mapped against ATT&CK 20.1 (record that version in the rule's description):

```yaml
tags:
  - attack.defense-impairment
  - attack.t1685.005   # formerly T1070.001
```

`sigma check` validates the *form* of tags (that they follow the naming convention), but it cannot tell whether a technique is the right one for the logic. Correctness of a mapping is a human review responsibility.

## Mapping data sources

A detection needs three things to work: the behaviour must produce an observable artefact, the artefact must be collected and parsed, and logic must recognise it. Rules map to techniques; **data sources** map to the first two conditions. For every technique you care about, you should be able to say which telemetry would show it and whether you collect that telemetry with the fields the logic needs.

For the Banyan techniques the data requirements are concrete:

| Technique | Telemetry needed | Fields the logic depends on | Collected in the lab? |
| --- | --- | --- | --- |
| T1204.002, T1059.001, T1059.003 | Process creation with parent (Sysmon event 1 or EDR) | `Image`, `ParentImage`, ideally `CommandLine` and `OriginalFileName` | Yes (image, parent image, command line) |
| T1071.001 | Web proxy or HTTP logs | host, URL, bytes out, timestamp | Yes |
| T1110.003, T1078, T1133 | VPN or remote-access authentication logs | user, source IP, outcome, time | Yes |
| T1136.001, T1098 | Windows Security log, account management | event ID, target account, group | Partly: the group is in the raw event but not a minisiem column |
| T1567 | Proxy logs with upload sizes; ideally destination categorisation | URL, bytes out, category | Sizes yes; category no |
| T1685.005 | Windows Security log, forwarded off-host | event ID, host, user | Yes |
| T1566 | Mail gateway logs (sender, attachment, links) | sender, recipient, attachment hash, URL | No |

The last column is where data-source mapping earns its keep. It shows, without writing a single rule, that the lab cannot see phishing delivery at all and cannot distinguish cloud storage from other upload destinations. Those are telemetry gaps, and no amount of clever logic closes them.

> [!TIP]
> Event 1102 is written when the Security log is cleared, into the log that has just been cleared. If that log is stored only on the host, an attacker who clears it has also removed most of the evidence you would use to investigate. Forwarding to a SIEM in near real time is what makes the 1102 detection useful. Mapping the data source is how you notice such dependencies.

## Versions and the life of a mapping

ATT&CK is updated regularly, typically with two major releases a year. Releases add techniques, refine descriptions, split techniques into sub-techniques, and sometimes deprecate or revoke entries. A revoked entry has been replaced by another one, so an ID that was right when a rule was written can become wrong without anyone touching the rule. This has practical consequences:

- **Record the version.** Each mapping, and each coverage report, should state the ATT&CK version it was made against. A heat map without a version is not reproducible.
- **Re-validate on upgrade.** When you move to a new version, check every tag in the rule repository against the new dataset. Tools that read ATT&CK's published data (MITRE publishes it in the STIX 2.1 format) can flag tags that no longer exist or have been revoked.
- **Expect disagreement between sources.** Vendor content, community rules, course material and threat reports may cite different IDs for the same behaviour; the kit tag above is a live example. Resolve disagreements against the official ATT&CK site for your chosen version, not by majority vote.

## Coverage matrices

Once rules and data sources are mapped, you can combine them into a coverage matrix. The simplest useful form is a table with one row per technique that matters to your organisation and, at minimum, three yes/no columns: **data collected**, **rule exists**, **rule tested**. A fourth column records the resulting status in words that do not overstate it.

Each column fails in a different way. A technique with no data cannot be detected, whatever the rule repository says. A technique with data but no rule is a quick win: the telemetry is already paid for. A technique with an untested rule may or may not be detected; you do not know until the rule has been shown to fire on a known-bad case and stay quiet on a near miss, which is the subject of Lesson 4. Collapsing the three into one colour hides exactly the information you need to plan work.

Which techniques belong in the rows? Not all of ATT&CK, whose empty squares would drown the important gaps. Rows should come from your threat model: the techniques used by the groups and malware that target your sector (ATT&CK's Group and Software pages list them, with references), techniques seen in your own incidents and in red-team or purple-team exercises, and techniques your auditors or regulators ask about. For a teaching environment like Banyan, the incident itself defines the rows.

Only then is the status column written.

**Decision logic.** Two rows show the subtler cases. **T1059 PowerShell / cmd** is blue: R1 is tested, but only for Word as the parent, so PowerShell or cmd started by any other Office application or by a script host is not covered. **T1136.001, T1098, T1567 and T1685.005** are orange: rules R3, R4 and R5 exist and fired correctly on the dataset, but the kit contains no test for them, so the status reads **untested**, not covered.

**Technical interpretation.** A heat map in ATT&CK Navigator would show these same rows as coloured cells in the matrix. The danger is that Navigator colours whatever score you give it; if "rule exists" is scored as green, the four orange rows above would turn green and the matrix would claim far more than has been demonstrated.

**Practical example.** Suppose a manager asks "would we detect the Banyan attacker clearing logs again?" The row for **T1685.005** answers precisely: the data is collected (Security log), a rule exists (R5), and it fired on this dataset, but it has never been tested against a near miss. Lesson 4 adds exactly that test and finds a weakness.

**Security implications.** The single red row is the most valuable line on the page. The organisation has no detection at the moment of delivery and depends on catching the attacker one step later. Whether that is acceptable is a risk decision, but it must be visible to be decided.

**Key learning.** Coverage is the weakest of three facts: data, rule, test. A matrix that records all three cannot overstate what the SOC can see.

### Coverage theatre

"Coverage theatre" is coverage reporting that looks reassuring and means little: one weak, name-matching rule per technique coloured green; over-tagged rules inflating the count of covered techniques; community rules counted although their log source is not collected; and last year's matrix, made against an older ATT&CK version, presented as current. The defence is the discipline already described: map what the rule observes, record the version, keep the three columns separate, and score untested rules as untested.

## Common mistakes and misconceptions

**"ATT&CK is a checklist; the goal is to cover every cell."** It is a knowledge base of observed behaviour; coverage goals should follow threat relevance and risk, not the size of the matrix.

**"The tactic is the most important tag."** Tactics are too coarse to drive detection or gap analysis on their own. A matrix that says "Execution: covered" because one rule exists hides the dozens of execution techniques that are not. Tag techniques or sub-techniques, and use tactics for grouping and reporting.

**Mapping by keyword.** Searching ATT&CK for the word in the rule title ("PowerShell") and taking the first result can give the wrong technique. Read the technique description and decide whether your observation meets it.

**Treating a mapping as permanent.** IDs change between ATT&CK versions; rules change during tuning. A tuning change that narrows R1 to PowerShell only should also remove the T1059.003 tag.

**Assuming the mapping proves detection.** A tag is a claim; only tests and real-world results prove that the rule fires.

## Security implications, detection and defence

ATT&CK mapping is a defensive tool, but it also shapes how defenders think. Three implications are worth stating plainly.

First, mapping exposes **telemetry gaps**, which must be closed before any detection is possible. In the Banyan case, adding mail-gateway logs would make the delivery of `invoice.docm` visible and would allow a T1566 rule. No rule-writing effort can substitute for that data.

Second, mapping supports **communication with other teams**. Threat-intelligence reports are increasingly written with ATT&CK IDs; a red team or purple team (Course 19) reports which techniques they exercised; auditors ask which techniques a control addresses. A well-mapped rule repository lets the SOC answer "do we detect what this report describes?" in minutes. Any adversary emulation used to check such answers must stay inside an isolated lab or a formally authorised exercise with written scope.

Third, a mapped incident timeline shows which stages were detected and which were invisible. In India, CERT-In's directions require reportable incidents to be reported within six hours of being noticed; a SOC that can quickly state which stages it saw and which it did not is better placed to give an accurate early report and to correct it later.

## Best practices

- Map from the procedure upwards, at the most specific level the evidence supports.
- Store the ATT&CK version, technique IDs and a one-sentence rationale with every rule, in version control.
- Choose matrix rows from your threat model, and never score an untested rule as covered.

## Key takeaways

- ATT&CK organises adversary behaviour as tactics (why), techniques and sub-techniques (how) and procedures (what was actually done); detection rules are written at the procedure level and mapped upwards.
- Map what the rule observes, at the most specific level the evidence supports, with the ATT&CK version and a written rationale.
- Data-source mapping reveals telemetry gaps that no rule can close, such as the missing mail logs in the Banyan lab.
- An honest coverage matrix keeps data, rule and test separate; its status is the weakest of the three.
- Mappings age: re-validate them when ATT&CK or the rule changes, and pin and record the version you map to: IDs change, as log clearing did when T1070.001 became T1685.005 under Defense Impairment.
