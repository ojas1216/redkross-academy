## Introduction and conceptual foundation

Lesson 1 designed detections as ideas: a family, a fact to rely on, a trade-off between precision and recall. To run, an idea has to be written in a query language, and every SIEM has its own. The kit's R1 is SQLite SQL; the same logic in Splunk is SPL, in Elastic it is KQL or EQL, in Microsoft Sentinel it is KQL of a different kind. If a SOC writes its detections directly in one product's language, its detection knowledge is locked into that product, cannot be shared with peers who use another, and must be rewritten every time the platform changes.

**Sigma** solves this by separating *what to detect* from *how a particular SIEM searches for it*. A Sigma rule is a YAML file that describes a log-based detection in generic terms: which kind of log it applies to, which field values to look for, how to combine them, how serious a hit is and what benign activity may trigger it. Tools convert that description into a specific SIEM's query. The open-source project maintains the specification, a large public rule repository, and the Python library **pySigma** with its command-line front end **sigma-cli**, which validate and convert rules through pluggable **backends** (one per target query language) and **processing pipelines** (which adapt generic field names and log sources to a particular deployment).

For a SOC, Sigma is more than a file format. It makes **detection as code** practical: rules live in version control as small readable text files, changes are reviewed as diffs, automated checks run on every change, and the same rule can be deployed to more than one platform. It also gives analysts a shared language: a Sigma rule published in an advisory can be read, judged and adapted before anyone converts it.

This lesson takes the kit's two Sigma rules, `rk_office_spawns_shell.yml` (the Sigma form of R1) and `rk_security_log_cleared.yml` (the Sigma form of R5), field by field. You will see how the detection section expresses AND, OR and NOT, how `logsource` decides where a rule applies, how `sigma check` catches mistakes, and why converting a rule without the right pipeline can silently produce a query that searches the wrong data.

> [!NOTE]
> All commands in this lesson run on your own machine against rule files in a copy of the kit. Converting a rule only produces query text; nothing is sent to any system. The outputs shown were produced with sigma-cli 4.0.1, pySigma 2.1.0 and pysigma-backend-splunk 3.0.1 (the course library records the same results with sigma-cli 4.0.0). Other versions may word their messages differently.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Sigma rule | A YAML document describing one log-based detection in a platform-independent way. |
| Log source (`logsource`) | The section that states which kind of log the rule applies to, using `category`, `product` and/or `service`. |
| Detection (`detection`) | The section holding named search identifiers (selections) and the `condition` that combines them. |
| Selection | A named search identifier: a map of field names to values that a single event must match. |
| Modifier | A suffix after a field name, separated by `\|`, that changes how values match (for example `endswith`, `contains`). |
| Condition | The Boolean expression over selection names (`and`, `or`, `not`, parentheses, `1 of`, `all of`) that decides a match. |
| Level | The rule's severity: `informational`, `low`, `medium`, `high` or `critical`. |
| Status | The rule's maturity, for example `experimental`, `test` or `stable`. |
| pySigma | The Python library that parses, validates and converts Sigma rules. |
| sigma-cli | The command-line tool built on pySigma (`sigma check`, `sigma convert`, `sigma list`). |
| Backend | The pySigma component that renders a rule into one target query language (Splunk SPL in this lesson). |
| Processing pipeline | A set of transformations applied before rendering: mapping generic field names and log sources to a specific deployment. |

## Anatomy of a Sigma rule

Here is the complete file `LAB_ASSETS/C08/rk_office_spawns_shell.yml`, exactly as it ships in the kit:

```yaml
title: Office Application Spawning Script Interpreter
id: 6c0f4d2b-9a1e-4f53-8a3e-2f7b7e9c1a01
status: experimental
description: Detects Microsoft Word starting PowerShell or cmd.exe, a common
  sign of a malicious document (RedKross Academy teaching rule).
references:
  - https://attack.mitre.org/techniques/T1204/002/
author: RedKross Academy
date: 2026-11-07
tags:
  - attack.execution
  - attack.t1204.002
  - attack.t1059.001
logsource:
  category: process_creation
  product: windows
detection:
  selection_parent:
    ParentImage|endswith: '\WINWORD.EXE'
  selection_child:
    Image|endswith:
      - '\powershell.exe'
      - '\cmd.exe'
  condition: selection_parent and selection_child
falsepositives:
  - Legitimate macros that launch scripts (rare; document and allow-list)
level: high
```

The fields fall into five groups, which Figure 1 shows as a tree: identity, context, the log source, the detection logic, and triage hints.

**Purpose.** The diagram breaks one Sigma rule into the five groups of fields that make it up, so you can see which parts a converter actually uses to build a query and which parts exist for people and tooling. When you review a rule, you check each group for a different kind of error.

**Components.** The dark root box at the top is **Sigma rule (YAML)**, with the subtitle naming the kit file `rk_office_spawns_shell.yml`. Five child boxes sit beneath it. **Identity**, slate, lists `title, id, status, author, date`. **Context**, blue, lists `description, references, tags`. **logsource**, violet, lists `category, product, service`. **detection**, orange, lists `selections + condition`. **Triage hints**, green, lists `falsepositives, level`. The note under the diagram says that only logsource and detection become query text.

**Relationships and arrows.** Each arrow runs from the root to one child: the rule *is composed of* these five parts. There are no arrows between the children, but in practice two of them work together: **logsource** says *where* to look and **detection** says *what* to look for. The other three groups travel with the rule into the SIEM as metadata (rule name, severity, references) but do not change which events match.

**Execution flow.** When a converter processes the rule it reads **logsource** first, to decide which pipeline transformations apply (for example which index or log name to add), then renders **detection** into the target query language. **Identity**, **Context** and **Triage hints** are read by validators and by the people and platforms that manage the rule.

**Decision logic.** The diagram has no branches, but the colours encode the review questions. Violet and orange (**logsource**, **detection**) answer "will it match the right events?". Green (**Triage hints**) answers "what should an analyst do with a hit?". Slate and blue (**Identity**, **Context**) answer "can we track, version and justify this rule?".

**Technical interpretation.** `id` is a UUID that identifies the rule permanently, even if its title changes; deployment and deduplication tooling relies on it, so a copied rule must get a new one. `status: experimental` tells consumers that the rule is new and not yet proven in production. `tags` follow the `attack.` namespace convention: a tactic name (`attack.execution`) or a technique ID in lower case (`attack.t1204.002`, User Execution: Malicious File; `attack.t1059.001`, Command and Scripting Interpreter: PowerShell). `level: high` is the base severity that Module 5 compared with the triage helper's values.

**Practical example.** When R1 fired on WS-104 at 06:14, an analyst looking at a Sigma-based alert would see the title, the `high` level and the false-positive note about legitimate macros. That note tells the analyst what to rule out first: is there an approved macro for this user and document?

**Security implications.** Weak triage hints or a missing `falsepositives` entry push the cost of understanding a rule onto every analyst who meets it. Wrong `tags` distort coverage reports (Lesson 3). A wrong `logsource` is the most dangerous error, because it changes which data the query searches while the rule still looks correct.

**Key learning.** A Sigma rule is a detection plus its documentation: logsource and detection become the query, and everything else is what makes the rule reviewable, traceable and usable at triage time.

## logsource: where the rule applies

The `logsource` section names the kind of log a rule is written for, using up to three keys:

- **`category`** describes a type of event independent of the tool that records it, such as `process_creation`. Sysmon event 1, an EDR process event and Windows Security event 4688 can all be "process creation".
- **`product`** names the platform, such as `windows` or `linux`.
- **`service`** names a specific log within the product, such as `security` for the Windows Security event log.

The kit's two rules use the two common styles. `rk_office_spawns_shell.yml` uses `category: process_creation` with `product: windows`: it applies to *any* Windows process-creation source that provides `Image` and `ParentImage`. `rk_security_log_cleared.yml` uses `product: windows` with `service: security`: it applies to one specific log. Category-style rules are more portable; service-style rules are more precise about which log is meant.

The key point is that `logsource` is a *statement*, not a filter that the rule enforces by itself. Whether the resulting query actually restricts the search to that log depends on the processing pipeline used at conversion time. You will see the consequence in the conversion section below.

## detection: selections, values and modifiers

The `detection` section holds one or more named **selections** and exactly one `condition`. The names are your choice; prefixes such as `selection_` and `filter_` are conventions that make the condition readable. Three structural rules decide how a selection matches:

1. **A map is AND.** All field-value pairs inside one selection must hold for the same event.
2. **A list is OR.** A list of values under one field means "any of these".
3. **Plain values match the whole field, ignoring case.** `EventID: 1102` matches the value 1102 exactly; a string such as `'\WINWORD.EXE'` would have to equal the entire field unless a modifier says otherwise. Sigma string matching is case-insensitive by default, which matters for Windows paths (Lesson 1 showed the minisiem SQL achieving the same with `lower()`).

**Modifiers** change how values match. They are appended to the field name after a pipe. The kit uses `endswith`; others in everyday use include:

| Modifier | Meaning | Example |
| --- | --- | --- |
| `endswith` | The field ends with the value | `Image\|endswith: '\cmd.exe'` |
| `startswith` | The field begins with the value | `CommandLine\|startswith: 'powershell'` |
| `contains` | The value appears anywhere in the field | `CommandLine\|contains: ' -enc'` |
| `all` | Combined with a list: every value must match (AND instead of OR) | `CommandLine\|contains\|all:` followed by a list |
| `re` | The value is a regular expression | use sparingly: costly and backend-dependent |
| `cidr` | The field is an IP address inside the given range | `SourceIp\|cidr: '192.0.2.0/24'` |

Applying the rules to the kit file: `selection_parent` has one field, so it matches when `ParentImage` ends with `\WINWORD.EXE`. `selection_child` has one field with a two-item list, so it matches when `Image` ends with `\powershell.exe` *or* `\cmd.exe`. The leading backslash matters: `endswith: '\cmd.exe'` matches `C:\Windows\System32\cmd.exe` but not a hypothetical `notcmd.exe`. This is stricter than the minisiem SQL's `LIKE '%cmd.exe%'`, which is a contains match.

### The condition

The `condition` combines selections with `and`, `or`, `not` and parentheses. In the kit rule, `selection_parent and selection_child` means both selections must hold for the same event, which is exactly the parent-child relationship that Lesson 1 identified as the behaviour.

Two shorthand forms keep rules with many selections readable: `1 of selection_*` (at least one selection whose name matches the pattern) and `all of selection_*` (every such selection); `them` refers to all selections in the rule. The most important pattern in practice is the **filter**: a selection describing known-benign activity, removed with `and not`. Filters are how a rule records an approved exception instead of leaving every analyst to rediscover it.

Why two selections rather than one map with both fields? In this rule a single map with `ParentImage|endswith` and `Image|endswith` would mean the same thing, because a map is AND. Separate, named selections make the intent clearer, give each part a name that reviewers can discuss, and make it easy to add more parents or a filter later.

## The second kit rule: Security log cleared

`LAB_ASSETS/C08/rk_security_log_cleared.yml` is the Sigma form of R5:

```yaml
title: Windows Security Event Log Cleared
id: 3b8e5a71-2c4d-4e9f-b0a6-7d1c9e2f4a12
status: experimental
description: Detects clearing of the Windows Security event log (event 1102),
  which attackers use to remove evidence (RedKross Academy teaching rule).
references:
  - https://attack.mitre.org/techniques/T1685/005/
author: RedKross Academy
date: 2026-11-07
tags:
  - attack.t1685.005
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 1102
  condition: selection
falsepositives:
  - Administrators clearing logs during approved maintenance (should be rare
    when logs are forwarded to a SIEM)
level: high
```

The detection is the simplest possible: one selection with one field and one value, and a condition that is just that selection. All of the rule's precision comes from the combination of `service: security` and `EventID: 1102`; the same number in a different log could mean something else entirely. The `falsepositives` entry makes a useful operational point: when logs are forwarded to a SIEM, administrators rarely have any reason to clear them, so every hit deserves a question.

> [!IMPORTANT]
> **Pin and record the ATT&CK version, because IDs change (this one did).** This file is tagged `attack.t1685.005` and its reference points to that technique. That tag is current: in ATT&CK content version 20.1 the former Defense Evasion tactic was split into Stealth (TA0005) and Defense Impairment (TA0112), and clearing Windows event logs is now **T1685.005 Clear Windows Event Logs** under **Defense Impairment** (a sub-technique of T1685 Disable or Modify Tools). Older material, and many existing rules, cite the former ID **T1070.001**. The rule does not say which ATT&CK version it was mapped to, so before using its tag in a coverage report, check it against the version your team has pinned and record that version with the mapping. Lesson 3 covers mapping and versioning in detail.

Notice also that the rule has *no tactic tag*, while the first rule carries `attack.execution` alongside its technique IDs. Consistency of tagging across a rule set is a review item in Lesson 7.

## From rule to query: check, pipeline, backend

A Sigma rule does nothing until it is converted. Conversion in pySigma has three stages: the rule is parsed and validated, a processing pipeline adapts it to a deployment, and a backend renders the result as query text. Figure 2 shows the path, with the real outputs from the kit's rules.

{{figure C08-M07-L02-F2}}

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram traces one Sigma rule from a YAML file to a query a SIEM can run, and marks the stage where the most consequential decision (which pipeline to use) is made. It explains why the same rule can produce different, and sometimes wrong, queries.

**Components.** The flow runs from top to bottom through six steps. **rule.yml**, slate, is the input file. **Parse**, blue, turns YAML into a rule object. **Validate (sigma check)**, green, runs validators over structure, condition and tags. **Processing pipeline**, violet, maps `logsource` to log or index conditions and generic fields to platform fields. **Backend (Splunk)**, orange, renders the condition in SPL. **Query text**, dark, is the result, with the subtitle `source="WinEventLog:Security" EventCode=1102`.

**Relationships and arrows.** Each arrow passes the rule object to the next stage, so every stage works on the output of the one before. Validation does not change the rule; the pipeline does, by adding conditions and renaming fields before the backend sees them.

**Execution flow.** `sigma check` exercises the first three steps and stops. `sigma convert` runs the whole chain: with `-p splunk_windows` the pipeline stage is active; with `--without-pipeline` it is skipped and the backend renders the generic rule as it stands.

**Decision logic.** The key branch is at the pipeline step. For the log-cleared rule, skipping it produced `EventID=1102`, which searches every event with that ID in any log. Applying `splunk_windows` turned `service: security` into `source="WinEventLog:Security"` and renamed `EventID` to Splunk's `EventCode`. Validation is a second gate: a rule with a condition error fails at **Validate** and conversion refuses to continue.

**Technical interpretation.** The backend knows the query language but not your data; the pipeline is where knowledge of your data lives. A pipeline that matches someone else's indexing produces syntactically valid queries that miss your events.

**Practical example.** A Banyan analyst converts the log-cleared rule for the SOC's Splunk. If Banyan's Security log really is indexed with source `WinEventLog:Security` and field `EventCode`, the `splunk_windows` output is right. If Banyan's collector stores it differently, the analyst must use or write a pipeline that matches, then confirm with a test search that the query finds a known 1102 event.

**Security implications.** A wrong pipeline creates a silent false negative: the rule is deployed, reviewed and green on the dashboard, and never fires. A missing pipeline can create the opposite, an unscoped query that matches unrelated events. Both are found only by testing against real data (Lesson 4).

**Key learning.** `logsource` states intent; the processing pipeline makes it true for your data. Always convert with a pipeline that matches how your logs are stored, and verify the output.

### Validating with sigma check

Install the tools in a Python virtual environment inside your working copy of the kit, never system-wide:

```bash
python -m venv sigvenv
# Windows: sigvenv\Scripts\activate    Linux/macOS: source sigvenv/bin/activate
pip install sigma-cli pysigma-backend-splunk
```

`python -m venv sigvenv` creates an isolated environment in the folder `sigvenv`; activating it makes `pip` and `sigma` refer to that environment. `pip install` fetches sigma-cli and the Splunk backend. Then check the first kit rule:

```terminal
$ sigma check rk_office_spawns_shell.yml
Parsing Sigma rules
Checking Sigma rules

=== Summary ===
Found 0 errors, 0 condition errors and 0 issues.
No rule errors found.
No condition errors found.
No validation issues found.
```

`sigma check` takes one or more files or directories. It reports three classes of problem: **errors** (the YAML is not a valid rule), **condition errors** (the condition cannot be resolved) and **issues** (validator findings such as malformed tags or naming problems). The log-cleared rule produces the same clean summary.

To see the checker earn its keep, introduce two deliberate mistakes in copies of the rule. In the first copy, misspell a selection name in the condition (`selection_childs`):

```terminal
$ sigma check rk_office_cond_typo.yml
...
Found 0 errors, 1 condition errors and 0 issues.
...
| 1     | Detection 'selection_childs' not defined in detections in ...
```

(Output abridged; the tool prints the rule's full path where `...` appears.) Trying to convert that file fails with the same message, so a broken condition cannot reach a SIEM through the converter. In the second copy, shorten the technique tag to `attack.t1059.01`:

```terminal
$ sigma check rk_office_tag_typo.yml
...
issue=InvalidATTACKTagIssue severity=medium description=Invalid MITRE ATT&CK tagging rule=... tag=attack.t1059.01
...
Found 0 errors, 0 condition errors and 1 issues.
```

The tag validator catches malformed or unknown technique IDs using the ATT&CK data bundled with your pySigma version. Two limits follow. A clean check does not mean a tag is the *right* mapping for the behaviour; that is a judgement (Lesson 3). And because the bundled ATT&CK data changes between pySigma releases, the result for a given tag may differ between versions, which is one more reason to record the ATT&CK version a rule was mapped against.

### Converting to Splunk

```terminal
$ sigma convert -t splunk --without-pipeline rk_office_spawns_shell.yml
Parsing Sigma rules
ParentImage="*\\WINWORD.EXE" (Image IN ("*\\powershell.exe", "*\\cmd.exe"))
```

`-t splunk` selects the Splunk backend; `--without-pipeline` tells sigma-cli to render the rule with no field or log-source mapping. Read the output against the YAML: `endswith` became a leading `*` wildcard, the two-item list became `IN (...)`, and the `and` between selections became Splunk's implicit AND (a space). The backslashes are doubled because SPL string escaping requires it; this is correct, not a bug.

Without either option, sigma-cli refuses:

```terminal
$ sigma convert -t splunk rk_office_spawns_shell.yml
...
Error:
Processing pipeline required by backend! Define a custom pipeline or choose a predefined one.

Get all available pipelines for splunk with:
sigma list pipelines splunk
...
```

The refusal is deliberate: the tool makes you choose between a pipeline and an explicit statement that you do not want one. `sigma list pipelines` showed three Splunk pipelines in the tested installation: `splunk_windows` ("Splunk Windows log source conditions"), `splunk_sysmon_acceleration` and `splunk_cim` ("Splunk CIM Data Model Mapping"). Converting the log-cleared rule both ways shows why the choice matters:

```terminal
$ sigma convert -t splunk --without-pipeline rk_security_log_cleared.yml
Parsing Sigma rules
EventID=1102
$ sigma convert -t splunk -p splunk_windows rk_security_log_cleared.yml
Parsing Sigma rules
source="WinEventLog:Security" EventCode=1102
```

`-p` names the pipeline. The first query contains nothing from `logsource`: it would match an event 1102 from any log. The second restricts the search to the Security log and uses Splunk's field name. Pipelines can also remap fields entirely. With `-p splunk_cim`, the office rule became a query on Splunk's Common Information Model process fields:

```terminal
$ sigma convert -t splunk -p splunk_cim rk_office_spawns_shell.yml
Parsing Sigma rules
Processes.parent_process_path="*\\WINWORD.EXE" (Processes.process_path IN ("*\\powershell.exe", "*\\cmd.exe"))
```

Same rule, same backend, different field names, because the pipeline describes a different way of storing the same data. Use a pipeline only if it matches how your own data is indexed.

## Worked example: extending the rule with a filter

Lesson 1 suggested widening R1 to Excel and recording approved exceptions. In Sigma, both are small, reviewable edits. Copy the kit rule to `rk_office_spawns_shell_v2.yml`, give it a new `id` (generate one with `python -c "import uuid; print(uuid.uuid4())"`), and change the detection:

```yaml
detection:
  selection_parent:
    ParentImage|endswith:
      - '\WINWORD.EXE'
      - '\EXCEL.EXE'
  selection_child:
    Image|endswith:
      - '\powershell.exe'
      - '\cmd.exe'
  filter_approved:
    CommandLine|contains: '\finance\approved\'
  condition: selection_parent and selection_child and not filter_approved
```

The tested variant passed `sigma check` with no issues and converted as follows:

```terminal
$ sigma convert -t splunk --without-pipeline rk_office_spawns_shell_v2.yml
Parsing Sigma rules
(ParentImage IN ("*\\WINWORD.EXE", "*\\EXCEL.EXE")) (Image IN ("*\\powershell.exe", "*\\cmd.exe")) NOT CommandLine="*\\finance\\approved\\*"
```

The parent list became an `IN`, `contains` became wildcards on both sides, and `and not` became `NOT`. The change is easy to review as a diff: one new parent, one named filter.

The filter is also a deliberate teaching flaw. `CommandLine` is an **attacker-controlled value**: anyone who can start a process can include that folder string in its command line, and the filter would then hide the alert. A better exception keys on things the attacker controls less, such as the specific signed script, the approved host group or a combination of user and document, and is documented with an owner and an expiry date. Tuning and exceptions are developed in Lesson 5.

## Sigma and minisiem side by side

The kit expresses the same detection twice, and comparing them shows what translation must preserve:

| Aspect | minisiem R1 (SQL) | Sigma rule |
| --- | --- | --- |
| Where | `source='sysmon' AND event_id=1` | `category: process_creation`, `product: windows` |
| Parent match | `lower(parent_image) LIKE '%winword.exe%'` (contains) | `ParentImage\|endswith: '\WINWORD.EXE'` |
| Child match | Two `LIKE` tests joined by `OR` | A two-item list (OR) |
| Case | Explicit `lower()` | Case-insensitive by default |
| Metadata | Rule name only | Title, id, tags, level, false positives |

The SQL hard-codes the source and event ID that the Sigma rule leaves to a pipeline, and it uses a looser contains match. Neither is wrong for its purpose, but a translation that silently changes match semantics (contains versus ends-with, case-sensitive versus not) changes the rule's precision and recall. Check semantics after every conversion, not only syntax.

## Common mistakes and misconceptions

- **"Sigma is a SIEM" or "Sigma runs queries."** It is a description format; pySigma converts it, and the SIEM runs the result.
- **Assuming `logsource` filters the data.** It only does so through a pipeline. `EventID=1102` with no source restriction is the classic result.
- **Using any pipeline that makes the error go away.** A pipeline must match your indexing; otherwise you deploy a valid query that never fires.
- **Reusing an `id`.** Copied rules need a new UUID, or deployment tools will treat two rules as one.
- **Confusing map and list.** Two fields in one selection mean AND; two values under one field mean OR. Use `|all` when every value must match.
- **Filtering on attacker-controlled fields.** Exceptions written against command lines or file names can be imitated.
- **Treating a clean `sigma check` as proof of correctness.** It proves structure and tag syntax, not that the rule detects the behaviour or that tags are the right mapping.
- **Mixing tabs and spaces.** YAML requires consistent space indentation; a tab is a common parse error.

## Security implications, detection and defence

Sigma rules shape what the SOC can see, so treat the rule repository as a security asset. Restrict who can merge changes, require review, and run `sigma check` and conversion automatically on every change, so a broken condition or malformed tag never reaches production. A malicious or careless filter is effectively a blind spot that looks like a tuning decision.

Public rules carry the same risk as public code. A rule from a community repository or an advisory encodes someone else's log sources, field names and assumptions. Read it, convert it with your own pipeline, and test it on your data before trusting it. Conversely, publishing your own rules helps peers but also tells adversaries exactly what you match on; many SOCs share the behaviour while keeping thresholds and exceptions internal.

Converted queries also carry personal data concerns. Rules that pull user names, command lines or URLs into alerts should be limited to what triage needs, consistent with the DPDP Act 2023 principle of processing only what is necessary for the stated purpose.

## Best practices

- Keep one rule per file, named descriptively, with a unique UUID and an honest `status`.
- Name selections and filters for what they mean; prefer separate named selections over one large map when it aids review.
- Prefer `endswith` on full path components (with the leading backslash) to loose `contains` matches.
- Write `falsepositives` that tell an analyst what to rule out first; keep exceptions in named filters with an owner.
- Store rules in version control; run `sigma check` and conversion with your production pipeline in an automated pipeline on every change.
- Record the ATT&CK version used for tags, and re-check tags when ATT&CK releases change (Lesson 3).
- After conversion, compare the query's semantics with the rule's intent and test it against known data (Lesson 4).

## Key takeaways

- Sigma describes a log-based detection in portable YAML; pySigma and sigma-cli validate it and convert it into SIEM queries through backends and pipelines.
- A rule has five groups of fields: identity, context, `logsource`, `detection` and triage hints. Only `logsource` and `detection` shape the query.
- In `detection`, a map is AND, a list is OR, plain values match the whole field case-insensitively, and modifiers such as `endswith` and `contains` change matching. The `condition` combines named selections and filters.
- `sigma check` catches structural, condition and tag-format problems; it does not prove a rule detects what it claims.
- Without a pipeline, the log-cleared rule became `EventID=1102`; with `splunk_windows` it became `source="WinEventLog:Security" EventCode=1102`. The pipeline must match your data.
- The kit's `attack.t1685.005` tag is current: log clearing is T1685.005 Clear Windows Event Logs under Defense Impairment (TA0112); T1070.001 is the former ID found in older material. IDs change, so pin the ATT&CK version you map to and record it.
