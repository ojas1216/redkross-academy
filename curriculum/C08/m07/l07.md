## Introduction and conceptual foundation

By the time a detection reaches review it has already passed through several hands and several gates. Someone wrote a requirement, researched how the behaviour looks in the telemetry, wrote the logic, mapped it to ATT&CK and wrote tests that prove it fires on known-bad data and stays quiet on a near miss. It is tempting to think that a rule which passes its own tests is finished. It is not. Tests prove that the rule does what its author *intended*; they cannot prove that the author intended the right thing. A test written by the same person who wrote the rule shares the same blind spots: if the author forgot that PowerShell can be renamed, the tests will forget it too, and every test will pass.

**Rule review** is the step in the detection lifecycle where a second engineer, who did not write the rule, examines it against an agreed checklist before it is deployed. It is the detection-engineering equivalent of code review in software development, and it exists for the same reasons: a fresh pair of eyes catches assumptions the author can no longer see, the team's standards are applied consistently, knowledge spreads across the team instead of living in one person's head, and there is a recorded decision that someone other than the author judged the change safe to ship.

Review matters more in a SOC than in many software teams because the failure modes are quiet. A broken web page produces an error that someone reports. A broken detection produces *nothing*: the alert that should have fired simply does not, and nobody notices until an incident review asks why the intrusion ran for three weeks. The opposite failure is loud but equally harmful: a rule that fires hundreds of times a day on benign activity trains analysts to close its alerts without reading them, and the one true positive is closed with the rest. Review is the last cheap point at which either failure can be caught. Once a rule is live, fixing it costs analyst hours, missed detections or both.

This lesson teaches review as a disciplined, evidence-based activity rather than a rubber stamp. It sets out what a reviewer is responsible for, introduces a six-part checklist (logic, data, tests, metadata, ATT&CK tags and severity), and then applies that checklist to the two Sigma rules shipped in the course lab kit, `LAB_ASSETS/C08/rk_office_spawns_shell.yml` and `LAB_ASSETS/C08/rk_security_log_cleared.yml`, together with their minisiem translations and tests. The worked review produces real findings, including a severity inconsistency between a Sigma file and the triage script and an ATT&CK tag that a reviewer cannot confirm from memory and must verify against the ATT&CK version the team uses. The detection lab in the next lesson then asks you to put your own rule through the same checklist.

> [!NOTE]
> Review complements testing; it does not replace it. Lesson 4 covered how to build positive and negative test cases. Here the question is different: are those tests the *right* tests, and does everything around the logic (fields, tags, severity, documentation) hold up?

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Rule review | Examination of a new or changed detection by an engineer other than its author, against a written checklist, before deployment. |
| Author | The engineer who wrote or changed the rule and opened the change for review. |
| Reviewer | The engineer who examines the change and either approves it or requests changes. |
| Finding | One specific, evidenced problem raised by the reviewer, with a location and a proposed action. |
| Blocking finding | A finding that must be fixed before the rule may be deployed (for example, the rule cannot match real data). |
| Non-blocking finding | A finding that should be fixed or tracked but does not stop deployment (for example, a missing reference link). |
| Automated gate | A check that runs without a human, such as `sigma check` or the unit tests, and must pass before human review starts. |
| Rule metadata | Everything in a rule other than its detection logic: title, id, status, description, references, author, date, tags, false positives, level. |
| Level | The Sigma field that states the rule's severity: `informational`, `low`, `medium`, `high` or `critical`. |
| Severity mapping | The documented translation from a rule's Sigma level to the severity number used by the triage process. |
| Translation drift | A difference in behaviour between a portable rule (Sigma) and the query actually run in the SIEM after conversion or hand translation. |
| Detection as code | Managing detections like software: version control, review, automated tests and a deployment pipeline. |

## What a reviewer is responsible for

A reviewer is not a second author. The reviewer's job is not to rewrite the rule in the style they would have used, nor to approve it because the author is senior and the change looks small. The reviewer's job is to answer one question with evidence: **is this rule safe and useful to deploy, as written, into this SOC's data and this SOC's triage process?** Everything on the checklist is a way of breaking that question into parts that can be checked.

That question has three properties worth noticing. First, it is about *this* SOC. A Sigma rule that is perfectly correct in the abstract can be wrong for an environment whose logs do not carry the fields it relies on, or whose triage scale gives its level a meaning the author did not intend. Second, it is about the rule *as written*: the reviewer reviews the change in front of them, not the change they imagine the author meant. Third, it requires *evidence*. "Looks fine" is not a review. A reviewer who approves a rule should be able to say which checks they performed and what they found, and a reviewer who requests changes should be able to point to the exact line and explain why it is a problem.

Reviewers also need to know what is **out of scope**. A reviewer does not decide whether the SOC should detect this behaviour at all; that decision was made at the requirement stage (Lesson 6 covered how gaps are prioritised). A reviewer does not tune the rule for production volume on their own; tuning proposals go back to the author with data. And a reviewer does not deploy the rule; separation between the person who approves and the person who changes production is part of the control.

### Blocking and non-blocking findings

Not every finding is equally serious, and treating them as equal wastes everyone's time. A practical classification has three levels:

- **Blocking.** The rule cannot be deployed until this is fixed. Examples: the rule queries a field that does not exist in the SOC's data, so it can never fire; a test asserts the wrong thing; the rule would match a high-volume benign event and flood the queue; a suppression has no owner or expiry.
- **Should fix.** The rule works, but something material is wrong or missing and must be fixed soon, normally in the same change. Examples: severity inconsistent with the triage scale; an ATT&CK tag missing for a behaviour the rule plainly covers; an important branch of the logic with no test.
- **Note.** A suggestion or a known limitation to record. Examples: a reference link that would help analysts; a comment that an evasion is possible and is covered by another rule.

The classification is the reviewer's judgement, but it should be stated explicitly on every finding so that the author knows what must happen before approval.

## The peer review checklist

A checklist turns review from an act of memory into a repeatable procedure. Teams adapt the details, but most mature detection-engineering checklists cover the same six areas. Each area below lists the questions a reviewer asks and the evidence that answers them.

### 1. Logic

The logic check asks whether the condition actually expresses the behaviour stated in the requirement and description. The reviewer reads the detection block slowly and restates it in plain words: "this fires when the parent image ends with `\WINWORD.EXE` *and* the image ends with either `\powershell.exe` or `\cmd.exe`". If the plain-words restatement differs from the description, one of them is wrong.

Questions to ask:

- Does each named selection select what its name says, and does the `condition` combine them correctly (`and` versus `or`, `1 of`, `all of`, `not`)?
- Are list values combined as intended? In Sigma, a list of values under one field means *any of* them; separate fields in one selection must *all* hold.
- Which values in the logic are attacker-controlled? A process name can be changed by copying the binary; a parent-child relationship is harder to fake; a field such as the PE header's original file name survives a rename.
- If the rule exists in two forms (a Sigma file and a hand-written or converted SIEM query), do both forms mean the same thing? Translation drift is common: modifiers such as `endswith` become `LIKE` patterns, case sensitivity changes, and a missing log-source filter can widen the query.

### 2. Data

The data check asks whether the rule can work on the SOC's real telemetry. A logically perfect rule is useless if the event never reaches the SIEM or if the fields are named differently after parsing.

Questions to ask:

- Does the `logsource` correspond to a source the SOC actually collects, and is it mapped (by a processing pipeline or by hand) to the right index, table or source type?
- Does every field the rule uses exist in the parsed data, with the expected name and format?
- Does the converted query restrict itself to the intended log, or could it match a similar event from another source?
- Has the author shown evidence of a historical replay: how many hits over a realistic period, and what they were?

### 3. Tests

The test check asks whether the tests would catch the rule breaking. The reviewer does not merely confirm that the tests pass; that is what the automated gate is for. The reviewer asks whether the tests *cover the logic*.

Questions to ask:

- Is there at least one positive test per branch of the logic (every value in an *any-of* list that matters)?
- Is there a near-miss negative test for each condition, so that removing the condition would make a test fail?
- Are thresholds and time windows tested exactly at the boundary, on both sides?
- Do the tests exercise the query that will actually run in production, or only a translation of it?

### 4. Metadata

Metadata is what turns a query into something an analyst can act on at three in the morning. The reviewer checks it for completeness and for consistency with the logic.

Questions to ask:

- Are `title` and `description` accurate and specific, and does the description match what the logic actually does?
- Is the `id` a fresh UUID (not copied from another rule), and are `status`, `author` and `date` set?
- Do `references` support the mapping and help an analyst understand the behaviour?
- Does `falsepositives` list the realistic benign look-alikes the author found in research, and is there triage guidance somewhere the analyst will see it?

### 5. ATT&CK tags

Tags drive coverage reporting, so a wrong tag makes the coverage map lie. The reviewer checks tags in both directions: every tag must be justified by what the rule detects, and every technique the rule plainly detects should be tagged.

Questions to ask:

- Does each technique tag describe behaviour the rule actually observes, rather than what the attacker might be doing more broadly?
- Is there a technique the logic clearly covers but the tags omit?
- Is a tactic tag present and consistent with the techniques?
- Are the IDs valid **in the ATT&CK version the team has pinned**, and is that version recorded? ATT&CK changes between releases; an ID that was correct in an older release may be revoked or moved in a newer one.

### 6. Severity

Severity decides where the alert lands in the queue. The reviewer checks that the rule's declared severity is justified and that it translates consistently into the triage process.

Questions to ask:

- Is the Sigma `level` justified by the impact of the behaviour and the rule's confidence?
- Is there a documented mapping from Sigma level to the triage severity scale, and does this rule's entry in the triage configuration follow it?
- Would two rules with the same declared level receive the same severity in triage? If not, why not, and is the reason written down?

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the reviewer's checklist in one picture. It exists so that every review covers the same ground in the same order, and so that a missing area is visible as a missing tick rather than an unnoticed gap.

**Components.** The figure is drawn as six rows. Each row has a short label on the left naming a review area (Logic, Data, Tests, Metadata, ATT&CK tags and Severity) and, on the right, the concrete questions that area asks. The Logic row asks whether the condition matches the description and the requirement, whether the translation into the SIEM query means the same thing, and which values an attacker controls. The Data row asks whether the log source is collected and mapped, whether the fields exist after parsing, and whether the query is restricted to the intended log. The Tests row asks for a positive test per branch, a near-miss negative per condition, and boundary tests on thresholds and windows. The Metadata row covers title, description, id, references and false positives. The ATT&CK tags row asks whether tags are justified, complete and valid in the pinned version. The Severity row asks whether the level is justified and whether it maps consistently onto the triage scale.

**Relationships and arrows.** Each row has an arrow from the area label to its questions: the label is the heading, the questions are what the reviewer must answer under it. The rows are independent in the sense that a finding in one does not excuse skipping another, but they are ordered deliberately. Logic and Data come first because a rule that cannot match real data makes the rest moot. Tests come next because they are the evidence for the first two. Metadata, tags and severity come last because they matter only for a rule that works.

**Execution flow and decision logic.** A reviewer works down the rows. For each row the outcome is either "no findings" or one or more findings, each classified as blocking, should fix or note. Any blocking finding means the change returns to the author; should-fix findings normally return it too; notes may be recorded and the rule approved.

**Technical interpretation.** The six rows map onto the parts of a Sigma file and its surroundings: the `detection` block (Logic), the `logsource` block plus the pipeline and parser (Data), the test file (Tests), the descriptive fields (Metadata), the `tags` list (ATT&CK tags) and the `level` field together with the triage configuration (Severity).

**Practical example.** In the worked review later in this lesson, the Severity row catches that the Office-spawns-shell rule declares `level: high` while `triage.py` assigns it severity 3, and the ATT&CK tags row prompts a verification of the log-clearing rule's technique ID.

**Security implications.** A checklist that skips the Data row ships rules that never fire; one that skips Severity ships correct rules whose alerts are buried. Both are silent failures that only an incident reveals.

**Key learning.** A review is complete only when every row has been either ticked with evidence or turned into a classified finding.
