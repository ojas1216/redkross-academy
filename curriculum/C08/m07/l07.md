## Introduction and conceptual foundation

By the time a detection reaches review it has already passed through several hands and several gates. Someone wrote a requirement, researched how the behaviour looks in the telemetry, wrote the logic, mapped it to ATT&CK and wrote tests that prove it fires on known-bad data and stays quiet on a near miss. A rule that passes its own tests is still not finished. Tests prove that the rule does what its author *intended*, not that the author intended the right thing; tests by the same person share the same blind spots.

**Rule review** is the step in the detection lifecycle where a second engineer, who did not write the rule, examines it against an agreed checklist before it is deployed. It is the detection-engineering equivalent of code review in software development, and it exists for the same reasons: a fresh pair of eyes catches assumptions the author can no longer see, the team's standards are applied consistently, knowledge spreads across the team instead of living in one person's head, and there is a recorded decision that someone other than the author judged the change safe to ship.

Review matters in a SOC because the failure modes are quiet. A broken detection produces *nothing*: the alert that should have fired does not, and nobody notices until an incident review asks why the intrusion ran for three weeks. Review is the last cheap point at which that can be caught.

This lesson sets out what a reviewer is responsible for, introduces a six-part checklist (logic, data, tests, metadata, ATT&CK tags and severity), and applies it to the two Sigma rules in the course lab kit, `LAB_ASSETS/C08/rk_office_spawns_shell.yml` and `LAB_ASSETS/C08/rk_security_log_cleared.yml`, with their minisiem translations and tests. The worked review produces real findings, including a severity inconsistency between a Sigma file and the triage script and an ATT&CK tag that must be verified against the version the team uses. The detection lab in the next lesson puts your own rule through the same checklist.

> [!NOTE]
> Review complements testing; it does not replace it. Lesson 4 covered how to build positive and negative test cases. Here the question is different: are those tests the *right* tests, and does everything around the logic (fields, tags, severity, documentation) hold up?

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Rule review | Examination of a new or changed detection by an engineer other than its author, against a written checklist, before deployment. |
| Author | The engineer who wrote or changed the rule and opened the change for review. |
| Reviewer | The engineer who examines the change and either approves it or requests changes. |
| Finding | One specific, evidenced problem raised by the reviewer, with a location and a proposed action. |
| Blocking finding | A finding that must be fixed before the rule may be deployed (for example, the rule cannot match real data). |
| Non-blocking finding | A finding that should be fixed or tracked but does not stop deployment (for example, a missing reference link). |
| Automated gate | A check that runs without a human, such as `sigma check` or the unit tests, and must pass before human review starts. |
| Rule metadata | Everything in a rule other than its detection logic: title, id, status, description, references, author, date, tags, false positives, level. |
| Level | The Sigma field that states the rule's severity: `informational`, `low`, `medium`, `high` or `critical`. |
| Severity mapping | The documented translation from a rule's Sigma level to the severity number used by the triage process. |
| Translation drift | A difference in behaviour between a portable rule (Sigma) and the query actually run in the SIEM after conversion or hand translation. |
| Detection as code | Managing detections like software: version control, review, automated tests and a deployment pipeline. |

## What a reviewer is responsible for

A reviewer is not a second author. The reviewer's job is not to rewrite the rule in the style they would have used, nor to approve it because the author is senior and the change looks small. The reviewer's job is to answer one question with evidence: **is this rule safe and useful to deploy, as written, into this SOC's data and this SOC's triage process?** Everything on the checklist is a way of breaking that question into parts that can be checked.

The question is about *this* SOC: a Sigma rule correct in the abstract can be wrong for logs that lack its fields, or for a triage scale that gives its level another meaning. It is about the rule *as written*, not what the author meant. And it requires *evidence*: "looks fine" is not a review. Out of scope are whether to detect the behaviour at all (decided at the requirement stage), tuning on the reviewer's own initiative, and deployment, which stays separate from approval.

### Blocking and non-blocking findings

A practical classification has three levels, stated on every finding:

- **Blocking.** Cannot deploy until fixed: a field that does not exist, a test asserting the wrong thing, a rule that would flood the queue, a suppression without owner or expiry.
- **Should fix.** Works, but something material is wrong, normally fixed in the same change: severity inconsistent with triage, a missing tag, an untested branch.
- **Note.** A suggestion or known limitation to record, such as a possible evasion covered elsewhere.

## The peer review checklist

A checklist turns review from an act of memory into a repeatable procedure. Teams adapt the details, but most mature detection-engineering checklists cover the same six areas. Each area below lists the questions a reviewer asks and the evidence that answers them.

### 1. Logic

The logic check asks whether the condition actually expresses the behaviour stated in the requirement and description. The reviewer reads the detection block slowly and restates it in plain words: "this fires when the parent image ends with `\WINWORD.EXE` *and* the image ends with either `\powershell.exe` or `\cmd.exe`". If the plain-words restatement differs from the description, one of them is wrong.

Questions to ask:

- Does each named selection select what its name says, and does the `condition` combine them correctly (`and` versus `or`, `1 of`, `all of`, `not`)?
- Are list values combined as intended? In Sigma, a list of values under one field means *any of* them; separate fields in one selection must *all* hold.
- Which values in the logic are attacker-controlled? A process name can be changed by copying the binary; a parent-child relationship is harder to fake; a field such as the PE header's original file name survives a rename.
- If the rule exists in two forms (a Sigma file and a hand-written or converted SIEM query), do both forms mean the same thing? Translation drift is common: modifiers such as `endswith` become `LIKE` patterns, case sensitivity changes, and a missing log-source filter can widen the query.

### 2. Data

The data check asks whether the rule can work on the SOC's real telemetry. A logically perfect rule is useless if the event never reaches the SIEM or if the fields are named differently after parsing.

Questions to ask:

- Does the `logsource` correspond to a source the SOC actually collects, and is it mapped (by a processing pipeline or by hand) to the right index, table or source type?
- Does every field the rule uses exist in the parsed data, with the expected name and format?
- Does the converted query restrict itself to the intended log, or could it match a similar event from another source?
- Has the author shown evidence of a historical replay: how many hits over a realistic period, and what they were?

### 3. Tests

The test check asks whether the tests would catch the rule breaking. The reviewer does not merely confirm that the tests pass; that is what the automated gate is for. The reviewer asks whether the tests *cover the logic*.

Questions to ask:

- Is there at least one positive test per branch of the logic (every value in an *any-of* list that matters)?
- Is there a near-miss negative test for each condition, so that removing the condition would make a test fail?
- Are thresholds and time windows tested exactly at the boundary, on both sides?
- Do the tests exercise the query that will actually run in production, or only a translation of it?

### 4. Metadata

Metadata is what turns a query into something an analyst can act on at three in the morning. The reviewer checks it for completeness and for consistency with the logic.

Questions to ask:

- Are `title` and `description` accurate and specific, and does the description match what the logic actually does?
- Is the `id` a fresh UUID (not copied from another rule), and are `status`, `author` and `date` set?
- Do `references` support the mapping and help an analyst understand the behaviour?
- Does `falsepositives` list the realistic benign look-alikes the author found in research, and is there triage guidance somewhere the analyst will see it?

### 5. ATT&CK tags

Tags drive coverage reporting, so a wrong tag makes the coverage map lie. The reviewer checks tags in both directions: every tag must be justified by what the rule detects, and every technique the rule plainly detects should be tagged.

Questions to ask:

- Does each technique tag describe behaviour the rule actually observes, rather than what the attacker might be doing more broadly?
- Is there a technique the logic clearly covers but the tags omit?
- Is a tactic tag present and consistent with the techniques?
- Are the IDs valid **in the ATT&CK version the team has pinned**, and is that version recorded? ATT&CK changes between releases; an ID that was correct in an older release may be revoked or moved in a newer one.

### 6. Severity

Severity decides where the alert lands in the queue. The reviewer checks that the rule's declared severity is justified and that it translates consistently into the triage process.

Questions to ask:

- Is the Sigma `level` justified by the impact of the behaviour and the rule's confidence?
- Is there a documented mapping from Sigma level to the triage severity scale, and does this rule's entry in the triage configuration follow it?
- Would two rules with the same declared level receive the same severity in triage? If not, why not, and is the reason written down?

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the reviewer's checklist in one picture. It exists so that every review covers the same ground in the same order, and so that a missing area is visible as a missing tick rather than an unnoticed gap.

**Components.** The figure is drawn as six rows. Each row has a short label on the left naming a review area (Logic, Data, Tests, Metadata, ATT&CK tags and Severity) and, on the right, the concrete questions that area asks. The Logic row asks whether the condition matches the description and the requirement, whether the translation into the SIEM query means the same thing, and which values an attacker controls. The Data row asks whether the log source is collected and mapped, whether the fields exist after parsing, and whether the query is restricted to the intended log. The Tests row asks for a positive test per branch, a near-miss negative per condition, and boundary tests on thresholds and windows. The Metadata row covers title, description, id, references and false positives. The ATT&CK tags row asks whether tags are justified, complete and valid in the pinned version. The Severity row asks whether the level is justified and whether it maps consistently onto the triage scale.

**Relationships and arrows.** Each row has an arrow from the area label to its questions: the label is the heading, the questions are what the reviewer must answer under it. The rows are independent in the sense that a finding in one does not excuse skipping another, but they are ordered deliberately. Logic and Data come first because a rule that cannot match real data makes the rest moot. Tests come next because they are the evidence for the first two. Metadata, tags and severity come last because they matter only for a rule that works.

**Execution flow and decision logic.** A reviewer works down the rows. For each row the outcome is either "no findings" or one or more findings, each classified as blocking, should fix or note. Any blocking finding means the change returns to the author; should-fix findings normally return it too; notes may be recorded and the rule approved.

**Technical interpretation.** The six rows map onto the parts of a Sigma file and its surroundings: the `detection` block (Logic), the `logsource` block plus the pipeline and parser (Data), the test file (Tests), the descriptive fields (Metadata), the `tags` list (ATT&CK tags) and the `level` field together with the triage configuration (Severity).

**Practical example.** In the worked review later in this lesson, the Severity row catches that the Office-spawns-shell rule declares `level: high` while `triage.py` assigns it severity 3, and the ATT&CK tags row prompts a verification of the log-clearing rule's technique ID.

**Security implications.** A checklist that skips the Data row ships rules that never fire; one that skips Severity ships correct rules whose alerts are buried. Both are silent failures that only an incident reveals.

**Key learning.** A review is complete only when every row has been either ticked with evidence or turned into a classified finding.

## How a review runs

Review is a small workflow in its own right. In a detection-as-code setup the rule lives in version control, and a change is proposed as a pull request (or merge request) that contains the rule file, its tests and any configuration it touches, such as the triage metadata. The workflow then runs in a fixed order.

1. **Automated gates.** The pipeline runs `sigma check`, the unit tests and any linting; a failure goes straight back to the author.
2. **Read the requirement.** What behaviour, why, from which threat or gap.
3. **Work the checklist,** recording a finding wherever a question cannot be answered "yes, with evidence".
4. **Write findings** with file and line, evidence, proposed action and class.
5. **Author responds,** fixing or explaining with data.
6. **Re-review and approve;** the approval and findings stay in the change history.

`sigma check` validates structure, condition syntax and ATT&CK tags; it cannot see a level that disagrees with triage, a translation missing a filter or an untested branch. Those are human findings.

> [!IMPORTANT]
> A review that only re-runs the automated gates is not a review. If the gates pass and the reviewer has nothing to add, the reviewer should still record which checklist areas they examined and what evidence they looked at.

## Worked example: reviewing the kit's two Sigma rules

The course lab kit contains two teaching rules in Sigma format and their working translations in the minisiem SIEM. The rules were introduced in the previous module; here we review them as if they had just been submitted. All the commands below were run on a private copy of the kit (never inside the kit folder itself) with CPython 3.14.4, sigma-cli 3.0.2 and pySigma 1.3.3.

The material under review is:

| Artefact | Role in the review |
| --- | --- |
| `LAB_ASSETS/C08/rk_office_spawns_shell.yml` | Sigma rule: Word starting PowerShell or cmd.exe |
| `LAB_ASSETS/C08/rk_security_log_cleared.yml` | Sigma rule: Security log cleared (event 1102) |
| `LAB_ASSETS/C08/minisiem.py` | The SQL actually run: R1 `office_spawns_script`, R5 `log_cleared` |
| `LAB_ASSETS/C08/test_rules.py` | Unit tests for the minisiem rules |
| `LAB_ASSETS/C08/triage.py` | `RULE_META`: severity 1-4 and confidence per rule |

### Step 1: automated gates

First, the Sigma validator on both files:


`sigma check` takes one or more rule files (or directories) and runs pySigma's parser and its validators over them. "0 errors" means the YAML parsed into a valid rule; "0 condition errors" means every name in the `condition` refers to a defined selection; "0 issues" means no validator raised a problem. Then the unit tests:

```terminal
$ python -m unittest test_rules -v
test_explorer_spawns_powershell_is_not_matched (test_rules.R1.test_explorer_spawns_powershell_is_not_matched) ... ok
test_word_spawns_powershell (test_rules.R1.test_word_spawns_powershell) ... ok
test_five_users_then_success (test_rules.R2.test_five_users_then_success) ... ok
test_four_users_is_below_threshold (test_rules.R2.test_four_users_is_below_threshold) ... ok
test_spray_without_success (test_rules.R2.test_spray_without_success) ... ok
test_regular_small_requests (test_rules.R6.test_regular_small_requests) ... ok
test_variable_sizes_not_matched (test_rules.R6.test_variable_sizes_not_matched) ... ok

----------------------------------------------------------------------
Ran 7 tests in 0.002s

```

`-m unittest` runs Python's built-in test runner on the module `test_rules`; `-v` prints each test by name. All gates pass. This is exactly the point at which a careless review would approve both rules. The human review starts here.

### Step 2: reviewing rk_office_spawns_shell.yml (R1)

**Logic.** Restated in plain words, the Sigma rule fires when `ParentImage` ends with `\WINWORD.EXE` and `Image` ends with `\powershell.exe` or `\cmd.exe`. That matches the description ("Microsoft Word starting PowerShell or cmd.exe"). Sigma string matching is case-insensitive by default, which suits Windows paths. The minisiem translation R1 is not identical: it lowers both fields and uses `LIKE '%winword.exe%'`, a *contains* match rather than *ends with*. That is translation drift: a note. Both forms also key on the image *name*, which a renamed copy of PowerShell defeats; record it as a known limitation (a note), pointing to an original-file-name variant where telemetry supplies that field.

**Data.** The rule uses `logsource: category: process_creation, product: windows`, and minisiem reads Sysmon event 1 from the `sysmon` source. Both fields the rule uses exist in the dataset. No finding.

**Tests.** The R1 tests in `test_rules.py` cover Word starting PowerShell (positive) and Explorer starting PowerShell (near-miss negative). That is a good negative: it proves the parent condition matters. But the logic has a second branch, `cmd.exe`, with no positive test. If someone deleted `cmd.exe` from the rule during tuning, every test would still pass. There is also no test of a different letter case. Finding: should fix, add a Word-to-cmd.exe positive and an upper-case path variant.

**Metadata.** Title, id, status, description, author, date and false positives are present and accurate. `references` cites only T1204.002. Note: add a reference for the PowerShell technique and record the ATT&CK version used for the mapping.

**ATT&CK tags.** The tags are `attack.execution`, `attack.t1204.002` (User Execution: Malicious File) and `attack.t1059.001` (Command and Scripting Interpreter: PowerShell). Both are justified. But the rule also fires on `cmd.exe`, which is T1059.003 (Windows Command Shell), and that technique is not tagged. A coverage map built from these tags would show cmd.exe launched from Office as uncovered, when this rule in fact covers it. Finding: should fix, add `attack.t1059.003`.

**Severity.** This is the most consequential finding. The Sigma file declares `level: high`. In `triage.py`, `RULE_META` gives R1 a base severity of **3** on the 1-4 scale (with confidence 0.8). The log-clearing rule, R5, also declares `level: high` in its Sigma file, yet `RULE_META` gives R5 severity **4**. So the same declared level becomes two different triage severities, and nothing in the kit documents a mapping that explains the difference. Finding: should fix. Either the levels or the triage values are wrong, and the team needs a written level-to-severity mapping that both files follow.

The effect is measurable. `triage.py` computes priority as severity times confidence times asset criticality (3 for WS-104). With severity 3, R1 scores $3 \times 0.8 \times 3 = 7.2$, as the kit's saved `triage_output.txt` shows, tied with the VPN spray alert; with severity 4 it would score $9.6$ and rank clearly above it.

### Step 3: reviewing rk_security_log_cleared.yml (R5)

**Logic.** The rule selects `EventID: 1102` with `logsource: product: windows, service: security`. In the Windows Security log, event 1102 records that the audit log was cleared. The logic is minimal and correct for its purpose.

**Data.** Here the translation matters. The minisiem rule R5 is `SELECT ts, host, user FROM events WHERE event_id=1102`. It has no `source='windows'` restriction, so an event numbered 1102 from any other source would match. The previous module showed the Sigma-level version of the same problem: converting this rule without a processing pipeline produced a query for `EventID=1102` with nothing restricting it to the Security log. On today's dataset only one 1102 exists, so the bug is invisible. Finding: should fix, add the source restriction to R5 and convert the Sigma file with a pipeline that matches how the SOC indexes Security events.

**Tests.** `test_rules.py` has test classes for R1, R2 and R6 only. R5 has no test at all, positive or negative. Finding: blocking under most teams' standards, because "every rule has a positive and a near-miss negative" is the minimum bar. A good negative here is an event 1102 from a non-Security source, which would also have caught the data finding above.

**Metadata.** Present and accurate. The false-positive note (approved maintenance, which should be rare when logs are forwarded) is useful triage guidance.

**ATT&CK tags.** The only tag is `attack.t1685.005`. A reviewer who learned ATT&CK a few years ago will stop here: most published material, and most existing rules, map clearing the Windows event logs to **T1070.001** (Indicator Removal: Clear Windows Event Logs). The reviewer cannot confirm T1685.005 from memory or from those references, so this is raised as a finding to be verified, not as a guess in either direction. The right move is to check the tag against the ATT&CK version the team has pinned. pySigma's validator does exactly that, using MITRE's published ATT&CK data. Running it on two probe copies of the rule, one with the older ID and one with a deliberately invented ID, gives (output trimmed to the issue lines):

```terminal
$ sigma check tagprobe/probe_t1070.yml
| Count | Issue                 | Severity | Description                  |
| 1     | InvalidATTACKTagIssue | MEDIUM   | Invalid MITRE ATT&CK tagging |
$ sigma check tagprobe/probe_bogus.yml
issue=InvalidATTACKTagIssue severity=medium description=Invalid MITRE ATT&CK tagging tag=attack.t9999.999
```

The validator accepts `attack.t1685.005` (the unmodified rule passed with 0 issues) and rejects both `attack.t1070.001` and the invented `attack.t9999.999`. Querying the validator's loaded dataset directly showed ATT&CK version **20.1**, in which T1685.005 is "Clear Windows Event Logs" under the Defense Impairment tactic and T1070.001 is not an active technique. So the tag is correct for the version the tool uses. The finding does not disappear, it changes shape: the rule does not record which ATT&CK version it was mapped to, so the next reviewer will hit the same doubt, and any older content in the SOC that still uses T1070.001 now disagrees with this rule in the coverage map. The rule also has no tactic tag; the same validator accepted `attack.defense-impairment` and flagged the older `attack.defense-evasion` as invalid. Finding: should fix, record the ATT&CK version in the description, add the tactic tag, and open a ticket to re-map older content.

> [!TIP]
> A tag you cannot verify is a finding, but "unverified" is not the same as "wrong". Verify against the pinned ATT&CK dataset before asking the author to change anything, and record the version you checked against in the finding.

**Severity.** `level: high` with `RULE_META` severity 4 and confidence 0.9. Taken alone this is defensible: an attacker clearing the Security log on a finance workstation is serious. The problem is the inconsistency with R1 already recorded, so no separate finding.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure is the review's output: a findings register that the author can work through and that stays with the change as the record of the review. It shows that two rules which passed every automated gate still produced six findings once a human worked the checklist.

**Components.** The register is a table with four columns: Rule, Area, Finding and Action. The Rule column identifies which artefact the finding concerns, R1 (the Office-spawns-shell rule) or R5 (the log-cleared rule). The Area column names the checklist row that produced it (Severity, ATT&CK tags, Tests, Data). The Finding column states the evidenced problem in a few words; the Action column states what the author must do. Row colours encode the class: orange rows are should-fix findings, the red row is the blocking finding, and the violet row is the ATT&CK verification item.

**Relationships.** Read each row left to right: a rule, examined under one checklist area, produced one finding that maps to one action. Several rows point back to the same root cause in different files. The severity row involves both the Sigma `level` field and `RULE_META` in `triage.py`, and the R5 data row involves the minisiem SQL rather than the Sigma file. That is typical: the defect lives in the gap between artefacts, which is exactly where no single-file automated check looks.

**Execution flow and decision logic.** The register is filled in during the checklist pass and then sorted by class. Because one row is blocking (R5 has no tests), the change cannot be approved as a whole; the author fixes the blocking row and the should-fix rows, and the reviewer re-reviews only those.

**Technical interpretation.** The rows show the three kinds of defect review is best at catching: inconsistency between files (severity), incompleteness relative to the logic (the untagged cmd.exe technique and the untested cmd.exe branch), and translation drift (R5's SQL without a source filter). The ATT&CK row shows a fourth kind: knowledge that ages. The validator, run against ATT&CK 20.1, resolved the doubt; the residual finding is that the rule does not say which version it follows.

**Practical example.** Suppose the author responds by changing R1 to severity 4 in `RULE_META`. The reviewer re-runs `triage.py` and confirms that the R1 alert now ranks above the VPN spray alert, as the calculation in this lesson predicts, and that the team's new level-to-severity table is committed alongside it.

**Security implications.** Each finding, left unfixed, degrades detection quietly: a mis-ranked alert waits longer in the queue, an untagged technique shows as a coverage gap that may be "filled" with a redundant rule, an untested branch can be deleted unnoticed, and an unrestricted query can fire on the wrong log.

**Key learning.** Passing the gates proves a rule is well formed; only a checklist review proves it is consistent with the data, the tests, the ATT&CK version and the triage process around it.

## Writing review comments that get acted on

Good review comments share a shape: **location, observation, evidence, action, class**. "Severity seems off" gives the author nothing to do. "`rk_office_spawns_shell.yml` `level: high`, but `RULE_META['R1']` is 3 while R5, also `high`, is 4. Align both with a level-to-severity table. Should fix." can be fixed in ten minutes. Comment on the rule, not the person; ask where unsure, state facts where sure; and when the author answers with data, such as a replay, accept it and record why.

## Common mistakes and misconceptions

- **"The tests pass, so the rule is correct."** The R1 tests passed while the cmd.exe branch was untested.
- **Reviewing only the Sigma file.** R5's missing source filter and R1's severity mismatch both lived outside it.
- **Correcting ATT&CK IDs from memory.** The log-clearing tag that looked wrong was valid in the pinned version.
- **Rubber-stamping one-line changes.** Removing a list value or raising a threshold silently removes detection.
- **Reviewing your own rule.** Self-review shares the author's blind spots; rotate reviewers.

## Security implications, detection and defence

Review is a security control, not only a quality step. Detection content is a target for an insider or an intruder with repository access: deleting a list value, adding a broad suppression or lowering a severity can blind the SOC while every test passes. Mandatory second-person review, recorded in version control, makes such changes visible and attributable (separation of duties). The record is also evidence when an incident review asks why a detection did not fire, and it supports an Indian SOC's case, under CERT-In's directions, that monitoring is controlled. Suppressions deserve special scrutiny: each needs an owner, reason, ticket and expiry, as the one in `triage.py` has (`CHG-1042`, expiring 2026-12-31).

## Best practices

- Keep the checklist in the repository, linked from the pull-request template, and review the whole change: rule, conversion output, tests and triage configuration.
- Pin and record the ATT&CK version and validate tags against it; keep a written level-to-severity mapping.

## Key takeaways

- Review checks six areas (logic, data, tests, metadata, ATT&CK tags, severity) and classifies each finding; it starts only after the automated gates pass.
- The kit's rules passed every gate yet R1 declares `high` with triage severity 3 while R5's `high` is 4, R1 lacks a T1059.003 tag and cmd.exe test, and R5's SQL lacks a source filter and tests.
- Verify doubtful ATT&CK tags against the pinned version: `attack.t1685.005` was valid in ATT&CK 20.1 and `attack.t1070.001` was not, so the real finding was the unrecorded version.
