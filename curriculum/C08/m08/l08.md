## Lab objective and scope

This lab closes the module by working the Banyan Microfinance incident end to end, as the SOC's part of incident handling. Earlier labs analysed the same data from other angles: Module 4 read each log source and built a findings note, Module 5 triaged the alert queue, Module 6 graded the intelligence. Here the question changes from "what happened?" to "what does the incident team need from the SOC, and can we give it to them in time?". You will declare the incident and start the reporting clock, scope it, build the incident timeline, write containment advice, assemble a verifiable evidence package and write the incident report. If you ran the Lesson 7 tabletop, keep your after-action notes beside you: this lab shows which of the players' assumptions about the SOC were realistic.

By the end of the lab you will be able to:

1. Turn a triaged alert queue into an incident declaration with a recorded noticed time and a CERT-In deadline in UTC and IST.
2. Scope an incident with hunts and negative checks, and state the limits of each check.
3. Build an incident timeline from a single reproducible query, separating facts from inferences.
4. Write ordered, owned containment advice that preserves evidence.
5. Produce an evidence package with a correct SHA-256 manifest and custody records, verify it, and show that tampering is detected.

> [!IMPORTANT]
> **Authorisation and scope.** This lab uses only the synthetic Banyan dataset (`banyan_events.jsonl`) and the kit's own scripts, run on your own computer in a copy of the kit. Every person, host, domain and address is fictional; external addresses come from the RFC 5737 documentation ranges and domains end in `.example`. Containment in this lab is *advice written in a report*: you do not isolate, block or disable anything. In a real organisation, the SOC recommends containment and an authorised owner approves and executes it.

## Key terminology

| Term | Meaning in this lab |
| --- | --- |
| Declaration | The recorded decision that a set of events is an incident, with severity and time. |
| Noticed time | The time the organisation became aware of the incident; it starts the CERT-In six-hour clock. Here it is set to 08:30 UTC. |
| Scope | Every host, account, address and data set involved, and the checks showing what is *not* involved. |
| Negative check | A query whose empty result is itself a finding (for example, no other host contacted the bad domains). |
| Incident timeline | The ordered list of incident events, in UTC, each with its source and an inference label. |
| Containment advice | Ordered actions the SOC recommends, each with owner, evidence precaution and business impact. |
| Evidence package | The exported records, a SHA-256 manifest (`SHA256SUMS`) and custody entries (`custody.jsonl`). |
| Incident report | The written record for the incident lead, legal and later reviewers: summary, timeline, scope, actions, evidence and open questions. |

## How the lab is organised

The lab follows the order in which an incident team asks for things. First it needs to know whether this *is* an incident and how serious it is, because that decides who is paged and starts the legal clock. Then it needs scope, because containment of one host while the attacker holds another foothold only warns them. Then a timeline, which every other participant (legal, communications, forensics) will quote. Then containment advice, then evidence that will survive scrutiny, and finally the report that ties it together.

**Purpose.** The figure is the lab's route map: seven stages, top to bottom, each naming the kit tool or output that produces it. It matters because an incident team consumes the SOC's work in this order, and a SOC that produces a perfect timeline after the reporting deadline has failed the team.

**Relationships and arrows.** Each arrow means "this stage depends on the one above". Declaration depends on the alert picture; scope depends on knowing which host and account to start from; the timeline needs scope so that it includes the VPN thread as well as WS-104; containment advice needs both scope and timeline; the evidence package must capture what the timeline cites; the report quotes all of them.

**Execution flow.** Stages 1 and 2 should take minutes, because the clock runs from stage 2. In a real incident, stages 3 to 6 overlap: evidence export (stage 6) often starts as soon as scope is clear, before containment, so that isolation or resets cannot change what is preserved.

**Decision logic.** Stage 2 is a yes/no decision with a severity attached. Stage 3 produces a branch in the story: the WS-104 thread is confirmed, while the VPN thread (gopal's 06:46 UTC login from 203.0.113.66) is linked only by timing, so it is carried as a hypothesis in every later stage rather than merged into the confirmed facts.

**Technical interpretation.** Every stage is reproducible: the same dataset and commands give the same counts and hashes, which is what makes the report defensible.

**Practical example.** Legal asks at 08:50 UTC whether reporting is required. Because stage 2 recorded the noticed time and deadline, the SOC answers in one line and returns to scoping.

**Security implications.** Skipping stage 3 risks partial containment; skipping stage 6 leaves a report whose claims nobody can verify later.

**Key learning.** Work in the order the incident team needs the answers, and record the noticed time before anything else.

### Step 2: Declare and start the clock

The queue meets any reasonable declaration criteria: malicious code execution (Word starting PowerShell), unauthorised privileged access (a new local administrator), possible exfiltration (48.2 MB to an external file-sharing look-alike) and anti-forensics (the Security log cleared), all on a payments approver's workstation. Declare an incident and grade it with the Lesson 5 severity matrix; with confirmed compromise of a business-critical asset and possible personal-data exfiltration, it belongs in the highest or second-highest band of most matrices.

Record the noticed time. For this lab the SOC became aware at **08:30 UTC**, when Tier 1 opened the queue. The CERT-In Directions of April 2022 require specified incidents to be reported within six hours of noticing them, so:

$$08{:}30\ \text{UTC} + 6\ \text{h} = 14{:}30\ \text{UTC} = 20{:}00\ \text{IST}\quad(\text{IST} = \text{UTC} + 05{:}30)$$

The SOC does not decide whether the incident is reportable; legal does. The SOC's job is to give legal the noticed time, the deadline and accurate facts quickly, and to note in the case record when and to whom it gave them.

### Step 3: Scope the incident

Scope answers two questions: what is involved, and what have we checked that is *not* involved. Start with the kit's hunts, which look beyond the known indicators.

```terminal
$ python hunt.py
H1 beaconing candidates (>= 8 requests, interval CV < 0.2)
  WS-104 https://cdn-telemetry-sync.example/api/v2/ping n=18 mean_gap=300s cv=0.004
H2 parent-child pairs seen on only one host
  WINWORD.EXE -> powershell.exe hosts=1 n=1
H3 other hosts contacting known-bad domains
  none found
```

H1 looks for *any* host and URL pair with at least eight requests at near-constant intervals, not just the known C2 domain; only WS-104's beacon qualifies, with a coefficient of variation of 0.004 (almost perfectly regular). H2 stacks parent-child process pairs across the estate; the only pair seen on a single host is Word starting PowerShell. H3 checks whether any host other than WS-104 contacted the three bad domains; none did. These are negative findings, and they go into the report as such.

Next, three checks of your own on the other entities: the spraying address, the new account, and the endpoint telemetry.

```terminal
$ python minisiem.py search "SELECT COUNT(*) AS n FROM events WHERE src_ip='203.0.113.66' AND source<>'vpn'"
n
0
$ python minisiem.py search "SELECT COUNT(*) AS n FROM events WHERE user='svc_update' OR target_user='svc_update'"
n
2
$ python minisiem.py search "SELECT MAX(ts) AS last_sysmon FROM events WHERE source='sysmon'"
last_sysmon
2026-11-03T06:14:00Z
```

The spraying address appears in no source other than the VPN. The account `svc_update` appears only in its own creation (4720) and group addition (4732): there is no record of it logging on. And the last endpoint process event in the whole dataset is the PowerShell start at 06:14 UTC. That last result is a **telemetry gap**, not a finding of innocence: from 06:14 onwards the dataset cannot show what ran on WS-104, so "no further processes" means "no further process telemetry". Every negative check must be reported with its limit.

Finally, the VPN thread. Look at every event for gopal or his presumed laptop after the 06:46 login:

The VPN log records no session activity, so the data cannot say what the 06:46 session did. The link between this thread and WS-104 rests on timing alone: both occur within the same hour, but no shared host, address or account connects them.

**Key learning.** Draw every entity, mark every link as observed or hypothesised, and show the negative checks and their limits on the same picture.

### Step 4: Build the incident timeline

One query produces the timeline. It takes the incident window (06:00 to 09:00 UTC), keeps every non-proxy event on WS-104, every event from the spraying address, and only those WS-104 proxy URLs that no other host visited (the same "rare across the estate" idea as H2), then groups repeated activity into one row:

```terminal
$ python minisiem.py search "WITH k AS (SELECT ts, source, COALESCE(host, '-') AS host, user, CASE WHEN source='proxy' THEN url WHEN source='vpn' THEN 'vpn ' || outcome || ' from ' || src_ip WHEN source='sysmon' THEN 'process ' || image ELSE 'event ' || event_id || COALESCE(' ' || target_user, '') END AS activity FROM events WHERE ts >= '2026-11-03T06:00:00Z' AND ts < '2026-11-03T09:00:00Z' AND (src_ip = '203.0.113.66' OR (host = 'WS-104' AND (source <> 'proxy' OR url NOT IN (SELECT url FROM events WHERE source='proxy' GROUP BY url HAVING COUNT(DISTINCT host) > 1))))) SELECT MIN(ts) AS first_ts, MAX(ts) AS last_ts, COUNT(*) AS n, source, host, CASE COUNT(DISTINCT user) WHEN 1 THEN MIN(user) ELSE COUNT(DISTINCT user) || ' users' END AS user, activity FROM k GROUP BY source, host, activity ORDER BY first_ts"
first_ts | last_ts | n | source | host | user | activity
2026-11-03T06:12:00Z | 2026-11-03T06:12:00Z | 1 | proxy | WS-104 | divya | https://banyan-payroll-update.example/invoice.docm
2026-11-03T06:14:00Z | 2026-11-03T06:14:00Z | 1 | sysmon | WS-104 | divya | process C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
2026-11-03T06:17:00Z | 2026-11-03T07:42:02Z | 18 | proxy | WS-104 | divya | https://cdn-telemetry-sync.example/api/v2/ping
2026-11-03T06:42:00Z | 2026-11-03T06:42:49Z | 8 | vpn | - | 8 users | vpn failure from 203.0.113.66
2026-11-03T06:46:00Z | 2026-11-03T06:46:00Z | 1 | vpn | - | gopal | vpn success from 203.0.113.66
2026-11-03T07:02:00Z | 2026-11-03T07:02:00Z | 1 | windows | WS-104 | divya | event 4720 svc_update
2026-11-03T07:03:00Z | 2026-11-03T07:03:00Z | 1 | windows | WS-104 | divya | event 4732 svc_update
2026-11-03T08:12:00Z | 2026-11-03T08:12:00Z | 1 | proxy | WS-104 | divya | https://files-share-drop.example/upload
2026-11-03T08:17:00Z | 2026-11-03T08:17:00Z | 1 | windows | WS-104 | divya | event 1102
```

`COALESCE` supplies a dash for the VPN events' missing host; the `CASE` expression turns each event into a readable activity; the sub-query excludes any URL seen from more than one host; `GROUP BY source, host, activity` collapses the 18 beacons and the 8 spray failures into one row each. Nine rows cover 33 events. Keep the exact query in the case record, so that anyone can re-run it and get the same rows.

Turn the rows into the timeline the incident team will use, adding IST and an explicit label for each line: **observed** (directly in the log) or **inferred** (a conclusion drawn from observations).

### Step 5: Write the containment advice

Containment advice is ordered, owned and evidence-aware. Lesson 3's principles apply: preserve evidence first where it is safe to, never let collection delay stopping serious ongoing harm, and contain related footholds at the same time so that one action does not warn the attacker about the next. In the Banyan data the beacon has been silent since 07:42 and the upload finished at 08:12, so there is no sign of harm still in progress at 08:30; that allows a few minutes to start evidence collection before acting, but not hours.

| # | Action | Owner (approver) | Evidence precaution | Business impact |
| --- | --- | --- | --- | --- |
| 0 | "Do not touch, do not reboot WS-104" instruction to IT ops and service desk | Incident lead | Prevents loss of memory and files | None |
| 1 | Export and hash SIEM evidence for WS-104, WS-107 and the VPN (Step 6) | SOC Tier 2 | The evidence step itself | None |
| 2 | Network-isolate WS-104 with EDR (not power off) | IT ops (incident lead) | Isolation keeps memory for forensic imaging | Divya loses her PC: issue a clean replacement |
| 3 | At the same moment: reset divya's and gopal's passwords, revoke sessions and MFA tokens | Identity team (incident lead) | Record the time; existing VPN and session logs are already exported | Both users re-enrol |
| 4 | Block `cdn-telemetry-sync.example`, `banyan-payroll-update.example`, `files-share-drop.example` at proxy and DNS; block 203.0.113.66 at the VPN | Network team (incident lead) | Keep logging hits on the blocks: later attempts are evidence of other footholds | Low |
| 5 | Disable `svc_update`; delete only after forensic imaging | IT ops (incident lead) | Deleting first destroys the persistence evidence | None |
| 6 | Memory and disk imaging of WS-104, then rebuild from a known-good image | Forensics (Course 09) | Hash images; custody records | WS-104 out of service until rebuilt |

Two points need to be stated explicitly in the advice rather than left to the reader. Resetting a password alone may leave existing sessions and tokens valid, which is why action 3 includes revocation. And the indicator blocks in action 4 will not stop an attacker who switches infrastructure; they are a containment measure, not a sign that the incident is over. The advice is a recommendation. Record who approved each action and when, in the single incident log.

### Step 6: Assemble the evidence package

`evidence_export.py` exports the raw stored JSON for one host and a time window (06:00 to 09:00 UTC by default), writes a SHA-256 manifest and appends a custody entry. Export WS-104 and, because the triage helper places gopal on WS-107, that laptop too:

```terminal
$ python evidence_export.py CASE-0001 WS-104
exported 32 events -> evidence\CASE-0001\WS-104_2026-11-03_events.jsonl
sha256 8521c97cab10c667d87b01db92fa9c45a5f130dfc314fb49c622eaf1f2919acf
$ python evidence_export.py CASE-0001 WS-107
exported 10 events -> evidence\CASE-0001\WS-107_2026-11-03_events.jsonl
sha256 1ab3194ca5e6e692dfb9ea7331a969ec47240968555aad3711427edfec4f1868
$ cat evidence/CASE-0001/SHA256SUMS
1ab3194ca5e6e692dfb9ea7331a969ec47240968555aad3711427edfec4f1868  WS-107_2026-11-03_events.jsonl
```

The WS-104 hash matches the hash published for this export in the course library text, because the query, ordering and line endings are fixed: reproducibility is part of trustworthiness. The 32 events are 28 proxy, 1 process and 3 Windows events; the 10 WS-107 events are all routine proxy requests.

The manifest, however, now lists only WS-107. The script writes `SHA256SUMS` with `write_text`, which *replaces* the file on every run, while `custody.jsonl` is opened in append mode and keeps one entry per export (it now has two lines, each with its item, event count, SHA-256, query and UTC time). An analyst who ran two exports and then shipped `SHA256SUMS` as the package manifest would hand over a manifest that silently omits the most important item. This is a real behaviour of the kit's tool, and exactly the kind of detail a tabletop never reveals.

The VPN events cannot be exported with this tool at all, because it selects by host and VPN events have none. Save them with a search instead, then rebuild the manifest over every item from inside the case folder:

```terminal
$ python minisiem.py search "SELECT raw FROM events WHERE source='vpn' AND ts >= '2026-11-03T06:00:00Z' AND ts < '2026-11-03T09:00:00Z' ORDER BY ts" > evidence/CASE-0001/vpn_2026-11-03_events.txt
$ cd evidence/CASE-0001
$ sha256sum WS-104_2026-11-03_events.jsonl WS-107_2026-11-03_events.jsonl vpn_2026-11-03_events.txt > SHA256SUMS
$ cat SHA256SUMS
8521c97cab10c667d87b01db92fa9c45a5f130dfc314fb49c622eaf1f2919acf *WS-104_2026-11-03_events.jsonl
1ab3194ca5e6e692dfb9ea7331a969ec47240968555aad3711427edfec4f1868 *WS-107_2026-11-03_events.jsonl
7936f23ef9b779151e5500f4f577e83195406ffd6eb8ad91899dc67c344dccce *vpn_2026-11-03_events.txt
$ sha256sum -c SHA256SUMS
WS-104_2026-11-03_events.jsonl: OK
WS-107_2026-11-03_events.jsonl: OK
vpn_2026-11-03_events.txt: OK
```

The `*` before each name is `sha256sum`'s binary-mode marker, which Git for Windows writes; `sha256sum -c` accepts it. The VPN file holds a header line `raw` and the 9 VPN events of the window. Because `search` prints through the console, on Windows the file has CRLF line endings, so the same query on Linux would give a different hash: record the platform, the exact query and that the file is a search output (not a `custody.jsonl`-tracked export) in a manual custody note. On PowerShell, `Get-FileHash -Algorithm SHA256 <file>` gives the same digests in upper case.

Now prove that the manifest detects change. Work on a **copy**, never on the evidence itself:

```terminal
$ mkdir ../../check
$ cp WS-104_2026-11-03_events.jsonl ../../check/
$ grep WS-104 SHA256SUMS > ../../check/SHA256SUMS
$ cd ../../check
$ sed -i 's/48200000/482000/' WS-104_2026-11-03_events.jsonl
$ sha256sum -c SHA256SUMS
WS-104_2026-11-03_events.jsonl: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
```

Removing two digits from the upload size, the single most important number for the DPDP and CERT-In assessment, is detected at once. Delete the `check` folder afterwards (`cd .. && rm -r check`).

### Step 7: Write the incident report

The report is for the incident lead, legal and later reviewers. It states facts with sources, labels inferences, lists what is unknown and cites the evidence by hash. A model report, under 400 words:

```text
INCIDENT REPORT  CASE-0001  (TLP:AMBER, need-to-know)
Prepared by SOC Tier 2, 3 Nov 2026. All times UTC (IST = UTC+05:30).

1 SUMMARY
Finance workstation WS-104 (user divya, payments approver) was compromised
```

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| `no such table: events` | `load` was not run in this folder; run `python minisiem.py load` where `minisiem.db` should be. |
| `sha256sum -c` says "No such file or directory" | You are not inside `evidence/CASE-0001`, or the manifest has CRLF line endings; rebuild it with `sha256sum` in Git Bash. |
| The manifest lists only one file | Expected after several exports: the script overwrites `SHA256SUMS`. Rebuild it over all items (Step 6). |
| A different hash for the WS-104 export | The dataset was changed or regenerated; recopy `banyan_events.jsonl` from the kit and `load` again. |
| The VPN file hash differs from the lesson | Different platform line endings (CRLF on Windows, LF elsewhere); record your own hash and platform. |
| The shell alters the SQL | Keep each statement in one pair of double quotes with single quotes inside. |
