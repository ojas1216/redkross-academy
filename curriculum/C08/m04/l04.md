## Introduction and conceptual foundation

A firewall sits on a boundary and makes one decision, over and over: should this connection be allowed to cross? Every decision it logs becomes a line that says who tried to talk to whom, on which port, and what the firewall did about it. Module 2, Lesson 2 surveyed firewall logs as one network telemetry source among several. This lesson goes further and teaches you to **analyse** them: to read a raw line field by field, to understand what the firewall's state table and address translation do to what is recorded, to recognise the connection patterns that scans, malware and data theft leave behind, and to separate those from the far larger volume of harmless traffic that produces similar lines.

Firewall logs have a particular character. They are **content-blind**: a firewall that is not inspecting applications sees addresses, ports, protocol flags, byte counts and durations, never URLs, file names or commands. They are **voluminous**: a perimeter firewall on a modest network logs millions of decisions a day, and anything exposed to the internet receives a constant background of unsolicited probes. And they are **independent**: an attacker who controls a workstation cannot edit the firewall's log. That combination makes them poor at explaining *what* happened inside a connection and excellent at establishing *that* it happened, when, how often, and how much data moved. Analysts who understand that trade-off use firewall logs to confirm, scope and time-box activity first seen elsewhere, and to find patterns (regular beacons, outbound attempts on blocked ports, unusual volumes) that no single host log reveals.

Examples in this lesson use Banyan Microfinance's perimeter firewall `fw01`. Banyan's internet-facing address is `203.0.113.10` and its office network uses `10.40.0.0/16`. The C08 kit contains one real firewall line, in `LAB_ASSETS/C08/normalise_demo.py`, which we use first. Everything else is an **illustrative** sample written for this lesson with documentation addresses; the analysis commands shown were run against that sample and their output is reproduced exactly.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| 5-tuple | Source address, source port, destination address, destination port and protocol: the identity of a connection. |
| Stateful firewall | A firewall that tracks connections in a state table, evaluating the rule base for the first packet and then matching later packets to the existing session. |
| Allow / accept | The connection is permitted. |
| Drop / deny | The packet is discarded silently; the sender receives nothing. |
| Reject | The packet is refused with a reply: a TCP reset or an ICMP unreachable message. |
| Implicit (default) deny | The rule at the end of a rule base that refuses everything not explicitly allowed. Its logging often has to be switched on separately. |
| Session log | A log entry per connection, typically written at session start, end or both; the end record carries bytes and duration. |
| SNAT / PAT | Source NAT: rewriting internal source addresses (and ports, for port address translation) to the firewall's public address on the way out. |
| DNAT / port forward | Destination NAT: rewriting the public destination address of inbound traffic to an internal server's address. |
| Zone / interface | The network segment a packet arrived on or leaves by (for example `eth0` outside, `eth1` inside); it gives a log line its direction. |

## How a firewall decides, and what it writes

### State changes what gets logged

Almost every modern firewall is stateful. When the first packet of a new TCP connection arrives (a `SYN`), the firewall walks its rule base from the top and applies the first matching rule. If the rule allows the connection, the firewall creates an entry in its state table, and every later packet of that conversation, in both directions, is matched against the table rather than the rules. When the connection ends with `FIN` or `RST`, or sits idle past a timeout, the entry is removed.

This has a direct consequence for analysis. A firewall does not log every packet: it logs **decisions**. Next-generation firewalls usually write one record when a session starts, one when it ends, or both, depending on configuration. A Linux netfilter firewall logs only the packets that hit a rule with the `LOG` target, which administrators normally place in front of the rules that drop traffic. If you are asked "did 10.40.0.23 talk to 198.51.100.80 at 10:02?", the firewall can only answer if the relevant rule had logging enabled, and the most frequent gap in real investigations is exactly that: denied traffic was logged, allowed traffic was not.

### Drop, reject and what the other side sees

Drop and reject both refuse a connection, but they look different from outside. A dropped `SYN` gets no answer, so the sender eventually times out; a port scanner reports such a port as *filtered*. A rejected `SYN` gets an immediate reset or ICMP unreachable, so the sender knows at once; a scanner reports it as *closed*. Many perimeter policies drop rather than reject inbound traffic, both to give scanners less information and to avoid generating replies to spoofed packets. In the log both appear as refusals; the action field and the absence or presence of a reply in session records tell you which was used.

### The real line from the kit

The lab kit's line is in the netfilter `LOG` style, received through syslog:

```text
Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389
```

Module 2 read its fields once; three points matter for analysis. First, the word `DROP` is **not** written by the kernel's packet filter as a verdict. Netfilter's `LOG` target only logs; the text that precedes `IN=` is a prefix the administrator chose (`--log-prefix`) when writing the rule, and the packet was dropped by a separate rule. A prefix is only as truthful as the person who configured it, so rule names and prefixes should be checked against the rule base. Second, `IN=eth0` with no `OUT=` field shown means the packet arrived on the outside interface. Third, the destination is a private address, `10.40.0.5`: an inbound packet addressed to an internal host means the rule that logged it was evaluated after destination NAT, or on a path that routes to the internal network, so the analyst must know where in the rule chain the logging rule sits.

The kit's `normalise_demo.py` turns that line into ECS-style fields. The script's own output, run on an unchanged copy of the kit, is:

```terminal
$ python normalise_demo.py
{"@timestamp": "2026-11-03T06:46:21Z", "destination.ip": "10.40.0.5", "destination.port": 3389, "event.action": "drop", "event.module": "firewall", "host.name": "fw01", "network.transport": "tcp", "source.ip": "203.0.113.66"}
{"@timestamp": "2026-11-03T06:46:00Z", "event.action": "login", "event.module": "vpn", "event.outcome": "success", "source.ip": "203.0.113.66", "user.name": "gopal"}
```

The firewall timestamp `12:16:21` (IST, assumed by the script) becomes `06:46:21Z`. The second line is the VPN event from the same kit. Read together they make a short, important story: at 06:46:00 UTC the address `203.0.113.66` logged in successfully to the VPN as `gopal`, and 21 seconds later the same address tried to reach an internal host on RDP from the outside and was dropped. A single drop of port 3389 from the internet is background noise; the same address succeeding at the VPN seconds earlier turns it into part of a case. That is the analyst's basic move with firewall logs: an individual line rarely means much, but a line joined to other evidence by address and time often does.

### A fuller netfilter line

Real netfilter log lines carry more fields than the kit's abbreviated one. A line from the illustrative sample, written by a rule with the prefix `FW-DROP-IN`:

```text
Nov  3 10:20:01 fw01 kernel: FW-DROP-IN IN=eth0 OUT= SRC=192.0.2.77 DST=203.0.113.10 LEN=44 TTL=52 PROTO=TCP SPT=61000 DPT=21 SYN
```

`OUT=` is empty because the packet was destined for the firewall's own address (input) rather than forwarded. `LEN` is the IP packet length, `TTL` the remaining time-to-live, `SPT` the source port, and `SYN` the TCP flag that was set: this was the opening packet of a connection attempt. Real kernels write further fields (MAC addresses, TOS, IP ID, TCP window and others), which this sample omits for readability.

### Session logs from a next-generation firewall

Commercial firewalls write richer, session-oriented records, each vendor in its own format. The illustrative sample uses a vendor-neutral key-value layout to show the fields most of them share:

```text
2026-11-03T10:02:41+05:30 fw01 action=allow rule=OUT-WEB src=10.40.0.23 spt=51290 dst=198.51.100.80 dpt=443 proto=tcp nat_src=203.0.113.10 nat_spt=40112 bytes_out=1840 bytes_in=52211 duration=12 reason=tcp-fin
```

It records the decision (`action=allow`) and the rule that made it (`OUT-WEB`), the internal 5-tuple, the translated source address and port, the bytes in each direction, the duration in seconds, and why the session ended (`tcp-fin`: a normal close). The direction of the byte counters is defined relative to the initiator in this sample; in real products check the documentation, because "sent" and "received" are defined differently by different vendors, and getting it backwards turns a download into an exfiltration.

## Address translation: one connection, two identities

Network address translation is where many firewall investigations go wrong. Banyan's workstations use private addresses, and every outbound connection leaves with the firewall's single public address. To the outside world, every Banyan user is `203.0.113.10`.

**Purpose.** The sequence diagram follows one outbound HTTPS connection through source NAT, showing that the same conversation is known by two different 5-tuples on either side of the firewall, and that the firewall's own session log is the only record that holds both. This is the fact an analyst needs when an external party reports activity "from your address".

**Components.** There are four lanes. The blue **Workstation WS-104** lane is labelled with its internal address "10.40.0.23". The orange **Firewall fw01** lane is labelled "SNAT to 203.0.113.10". The slate **Web server** lane is the external destination "198.51.100.80". The dark **SIEM** lane on the right receives the log.

**Relationships and arrows.** Solid arrows are requests and dashed arrows are replies, all in time order from top to bottom. The first arrow runs from the workstation to the firewall, "SYN 10.40.0.23:51290 to 198.51.100.80:443". The second runs from the firewall to the web server, "SYN from 203.0.113.10:40112 (after SNAT)": the same packet, with source address and port rewritten. The dashed reply "SYN/ACK to 203.0.113.10:40112" comes back to the firewall, which sends the dashed "SYN/ACK to 10.40.0.23:51290 (reversed)" to the workstation, undoing the translation by looking it up in the state table. The arrow "data, then FIN: session closes" shows the conversation completing, and the final arrow from the firewall to the SIEM is the "Session-end log: src, nat_src, bytes, duration".

**Execution flow.** The translation is created when the first packet passes and is reversed for every reply until the session ends; only then, in a session-end configuration, is the record written.

**Decision logic.** There is one implicit decision: the first packet must match an allowing rule (`OUT-WEB` in the sample) before any translation entry exists. A denied first packet is never translated, so outbound denies are logged with the internal source address only.

**Technical interpretation.** Port address translation lets thousands of internal connections share one public address by giving each a distinct public source port. The pair "public address plus public port plus time" therefore identifies one internal connection, but only for as long as the firewall's records keep that mapping.

**Practical example.** A partner reports that `203.0.113.10:40112` connected to their server `198.51.100.80` at 10:02:41 IST. Searching the firewall's session log for `nat_spt=40112` around that time returns the line above, naming `10.40.0.23` and source port 51290. DHCP logs then tie `10.40.0.23` to WS-104 at that moment.

**Security implications.** Without translation records, every external report about Banyan's address is unattributable. Keep NAT session logs with accurate, synchronised time; a few minutes of clock error can map a report onto the wrong connection, because public ports are reused quickly.

**Key learning.** After NAT the outside world sees only the firewall's address and a port; the firewall's session log, joined on public port and time, is how you find the internal host.

## Connection patterns and what they mean

Single firewall lines are rarely conclusive. Analysis works on **patterns across many lines**: how one source's attempts spread across ports and hosts, how regular its timing is, how many bytes move and in which direction. The patterns below are the ones every SOC analyst should recognise, each paired with the benign activity that produces the same shape.

**Vertical port scan.** One source tries many destination ports on one host in a short time. In the log: the same `SRC` and `DST`, a run of different `DPT` values, `SYN` flags, all dropped, often within seconds. It is reconnaissance: the scanner is mapping which services a host offers.

**Horizontal sweep.** One source tries the same port on many hosts. In the log: the same `SRC` and `DPT`, many `DST` values. Sweeps look for one service (remote administration, file sharing, a newly vulnerable product) across an address range. Internet-wide sweeps of every public address are continuous, so a sweep against your public range is normal background; a sweep from an **internal** source across internal hosts is not, because it suggests a compromised machine looking for its next target.

**Outbound attempts on blocked ports.** An internal host repeatedly tries to reach the internet on a port policy forbids: SMB (445) or mail (25) from a workstation are classic examples. In the log: an internal `SRC`, the outbound interface, a deny, repeated. Malware that spreads over SMB or sends spam produces this pattern; so do misconfigured applications and laptops trying to reach a file share that is only available inside a home network.

**Regular small sessions (beaconing).** An internal host opens a short connection to the same external destination at a fixed interval, with nearly identical byte counts. In allowed-session logs this is the signature of command-and-control check-ins. Software update checks, telemetry and time synchronisation produce the same rhythm, which is why destination reputation, rarity across the estate and the presence of jitter matter.

**Large outbound volume.** A session with far more bytes sent than received, to a destination rarely seen before. It may be data theft; it is more often a backup, a cloud-storage sync or a video call.

**Out-of-state denies.** Packets with `ACK` or `PSH` flags but no matching state-table entry are dropped as invalid. They usually come from sessions that outlived the firewall's idle timeout, or from asymmetric routing where the firewall saw only one direction of a connection. They are noise to be understood, not attacks.

**Components.** There are three columns: **Pattern**, **Log signature** and **Benign look-alike**. The first two rows are red because they are direct evidence of probing. The next three are orange: they can indicate compromise but need context. The last is slate: it is usually operational noise.

**Relationships.** Each row reads left to right as a hypothesis test. The signature column says what to count ("one SRC, one DST, many DPT, seconds"; "one SRC, one DPT, many DST"; "internal SRC, DPT 445 or 25, denied, repeated"; "same DST, fixed interval, similar bytes"; "bytes out far above bytes in, rare DST"; "ACK or PSH without SYN, dropped"). The look-alike column names what produces the same counts innocently ("authorised vulnerability scan"; "internet background scanning"; "misconfigured app or roaming laptop"; "update checks, telemetry, NTP"; "backup, cloud sync, video call"; "idle timeout, asymmetric routing").

**Execution flow.** In practice an analyst works down the table after an initial count of drops or sessions by source: group by source, count distinct ports and destinations, measure intervals and byte ratios, then compare with the look-alike column before raising severity.

**Decision logic.** Direction is the branch that matters most. The same vertical scan is background when the source is on the internet and the target is a public address, and a serious finding when both are internal. Likewise, regular sessions to a well-known update service are expected, while the same rhythm to a destination no other host contacts is suspicious.

**Technical interpretation.** All six signatures use only fields a content-blind firewall records: addresses, ports, flags, timing and byte counts. That is why they work across vendors and survive encryption, and also why each needs corroboration from content-aware sources (proxy, DNS, endpoint) before it becomes a conclusion.

**Practical example.** In the illustrative sample, `192.0.2.77` matches the first row against `203.0.113.10`; `198.51.100.140` matches the second across Banyan's public addresses; `10.40.0.31` matches the third; `10.40.0.23` matches the fourth with its five-minute sessions to `198.51.100.200`, and also the sixth with one invalid `ACK PSH` packet. The worked example below derives each of these from the raw lines.

**Security implications.** Detection rules built from these signatures should carry the look-alikes as explicit exclusions with owners and expiry, so that the authorised scanner or the backup server does not become a permanent blind spot.

**Key learning.** A firewall pattern is a shape in addresses, ports, timing and bytes; name the shape, then rule out its benign twin before you call it an attack.

## Worked example: analysing a burst of drops

The illustrative netfilter sample contains 25 dropped packets logged by `fw01` between 10:20 and 10:27 IST. Three representative lines:

```text
Nov  3 10:20:01 fw01 kernel: FW-DROP-IN IN=eth0 OUT= SRC=192.0.2.77 DST=203.0.113.10 LEN=44 TTL=52 PROTO=TCP SPT=61000 DPT=21 SYN
Nov  3 10:25:05 fw01 kernel: FW-DROP-OUT IN=eth1 OUT=eth0 SRC=10.40.0.31 DST=198.51.100.9 LEN=44 TTL=128 PROTO=TCP SPT=49831 DPT=445 SYN
Nov  3 10:26:30 fw01 kernel: FW-DROP-INVALID IN=eth1 OUT=eth0 SRC=10.40.0.23 DST=198.51.100.80 LEN=44 TTL=128 PROTO=TCP SPT=51544 DPT=443 ACK PSH
```

The prefixes tell you which rule logged each packet: inbound drops, outbound drops and invalid-state drops. The interfaces confirm direction: `IN=eth0` is from the internet, `IN=eth1 OUT=eth0` is from the office towards the internet.

### Step 1: who is being dropped

```terminal
$ grep -o 'SRC=[^ ]*' fw.log | sort | uniq -c | sort -rn
     12 SRC=192.0.2.77
      8 SRC=198.51.100.140
      3 SRC=10.40.0.31
      1 SRC=203.0.113.66
      1 SRC=10.40.0.23
```

`grep -o` prints only the matching part of each line, here the `SRC=` field; the rest of the pipeline counts and ranks as in Lesson 3. Two external sources dominate. Two internal sources appear, which deserves more attention than their small counts suggest, because internal hosts should rarely be dropped at all.

### Step 2: how many ports, how many hosts

```terminal
$ awk '{for(i=1;i<=NF;i++){if($i~/^SRC=/)s=substr($i,5); if($i~/^DPT=/)d=substr($i,5)} print s, d}' fw.log | sort -u | awk '{n[$1]++} END{for(s in n) print n[s], s}' | sort -rn
12 192.0.2.77
1 203.0.113.66
1 198.51.100.140
1 10.40.0.31
1 10.40.0.23
```

The first `awk` walks every field of a line and keeps the values after `SRC=` and `DPT=`; `sort -u` removes duplicate source-port pairs; the second `awk` counts distinct ports per source. Changing `DPT=` to `DST=` in the same pipeline counts distinct destinations instead:

```terminal
$ awk '{for(i=1;i<=NF;i++){if($i~/^SRC=/)s=substr($i,5); if($i~/^DST=/)d=substr($i,5)} print s, d}' fw.log | sort -u | awk '{n[$1]++} END{for(s in n) print n[s], s}' | sort -rn
8 198.51.100.140
1 203.0.113.66
1 192.0.2.77
1 10.40.0.31
1 10.40.0.23
```

Now the sources sort themselves into the table's rows. `192.0.2.77`: twelve ports, one host, within three seconds: a **vertical scan** of Banyan's public address (ports 21, 23, 25, 110, 135, 139, 445, 1433, 3306, 3389, 5900 and 8080). `198.51.100.140`: one port (23, Telnet), eight hosts `203.0.113.11` to `203.0.113.18`: a **horizontal sweep**. Both were dropped and both are internet background unless something else connects them to Banyan. `203.0.113.66`: one RDP attempt, but the analyst recognises the address from the kit's VPN event and adds the line to that case. `10.40.0.31`: three outbound attempts on port 445 to one external address within nine seconds: **outbound to blocked port**, which needs an owner's explanation or an endpoint check. `10.40.0.23`: one invalid `ACK PSH` to a web server it had a session with: **out-of-state**, almost certainly an expired session.

### Step 3: timing in allowed sessions

Drops show what failed. To look for beaconing you need allowed-session logs. The illustrative session sample holds nine `allow` records; counting destinations gives:

```terminal
$ grep -o 'dst=[^ ]*' session.log | sort | uniq -c | sort -rn
      6 dst=198.51.100.200
      2 dst=198.51.100.80
      1 dst=192.0.2.150
```

Extracting the time and outbound bytes of each session to `198.51.100.200`, and the gap in seconds from the previous one:

```terminal
$ grep 'dst=198.51.100.200 ' session.log | awk '{split(substr($1,12,8),a,":"); t=a[1]*3600+a[2]*60+a[3]; for(i=1;i<=NF;i++) if($i~/^bytes_out=/) b=substr($i,11); if(p) print substr($1,12,8), t-p, b; else print substr($1,12,8), "-", b; p=t}'
10:00:04 - 612
10:05:04 300 612
10:10:05 301 618
10:15:04 299 612
10:20:04 300 612
10:25:05 301 612
```

`substr($1,12,8)` takes the `HH:MM:SS` part of the ISO timestamp, which is converted to seconds; the loop extracts `bytes_out`; each line prints the time, the gap since the previous session and the bytes sent. Six sessions from `10.40.0.23`, 300 seconds apart give or take one, each sending 612 or 618 bytes and receiving 1,460, each lasting one second. That is a **beacon**: a program on the host checking in every five minutes. The analysis does not say whether it is malicious. The next steps are to ask whether any other Banyan host talks to `198.51.100.200` (rarity), what the proxy and DNS logs say about the destination name, and what process on WS-104 owns the connection (endpoint telemetry).

> [!TIP]
> Regularity is easiest to see as gaps, not timestamps. A list of times looks random to the eye; a column of `300 301 299 300 301` does not. Real implants often add random jitter, so look for a narrow spread of gaps rather than identical ones.

## Benign look-alikes

| Looks like | Usually is | How to tell |
| --- | --- | --- |
| Thousands of inbound drops a day | Internet background scanning of every public address | Many unrelated sources, spread across ports, none followed by allowed sessions or other evidence |
| Vertical scan from one source | Your own vulnerability scanner or an authorised test | Source address and time window match the scan schedule or signed authorisation |
| Regular outbound sessions | Update checks, antivirus signatures, NTP, monitoring agents | Destination is contacted by many hosts, is a known vendor service, often on its documented port |
| Large outbound transfer | Backups, cloud sync, video conferencing | Known destination, scheduled time, known host role; confirm with the system owner |
| Outbound denies on 445 or 53 | A laptop or application configured for another network; a device using a hard-coded DNS server | Same host, same destination over days, matching a known application; endpoint confirms the process |
| Invalid-state drops | Expired idle sessions, asymmetric routing, failover between firewalls | Destinations the host had legitimate sessions with; spikes coincide with network changes |

## Common mistakes and misconceptions

- **"The firewall would have logged it."** Only rules with logging enabled write lines, and allowed traffic is the usual gap. Check the logging configuration before concluding that a connection did not happen.
- **Treating every inbound drop as an attack.** A drop means the control worked. Inbound drops matter when they connect to other evidence, as `203.0.113.66` did.
- **Ignoring internal sources.** An internal host being dropped, or scanning other internal hosts, is far more significant than an external scan, and perimeter firewalls never see east-west traffic at all.
- **Trusting prefixes and rule names blindly.** A netfilter prefix is free text chosen by an administrator; confirm against the rule base.
- **Losing the NAT mapping.** Searching for the public address alone cannot identify an internal host; join on public port and time.
- **Misreading byte directions.** Vendors define sent and received differently. Confirm before calling a transfer an exfiltration.

## Security implications, detection and defence

Useful firewall detections, all built on fields a content-blind firewall records:

1. **Internal scanning**: one internal source contacting many internal hosts or ports within minutes (lateral movement reconnaissance). Needs internal firewall or flow logs.
2. **Outbound policy violations**: repeated denied outbound connections from one internal host, especially on SMB, SMTP, or direct DNS that bypasses the resolver.
3. **Beaconing**: sessions from one host to one rare destination with a narrow spread of intervals and similar byte counts, over hours.
4. **Volume anomalies**: outbound bytes from one host to one rare destination far above that host's baseline.
5. **Correlated external sources**: an external address that is dropped at the firewall and also appears in VPN, web or authentication logs.
6. **Allowed after denied**: a source with many drops followed by an allowed session, which can mean it found an open path.

Controls that make firewall evidence better:

- Log allowed **and** denied traffic at least for the perimeter and for sensitive internal zones, including the default deny rule.
- Keep NAT session records and synchronise firewall clocks with NTP; forward logs centrally with time zones recorded, and retain them for the 180 days the CERT-In directions require.
- Apply **egress filtering**: permit only the outbound ports the business needs, so that malware's attempts become denies you can see.
- Segment the internal network with logging between zones, so east-west movement crosses a firewall.
- Keep the rule base documented, with meaningful rule names and log prefixes, and review it for rules that allow more than intended.

## Key takeaways

- Firewalls log decisions, not packets: what is recorded depends on which rules have logging enabled, and allowed traffic is the common gap.
- Drop gives no reply and reject gives a reset or ICMP unreachable; netfilter prefixes such as `DROP` are labels chosen by the administrator.
- After source NAT, the internal host is found only through the firewall's session log, joined on public port and time.
- Analyse patterns across lines: vertical scans, horizontal sweeps, outbound attempts on blocked ports, beacons, large outbound volumes and out-of-state drops.
- Every pattern has a benign twin; direction (internal or external), rarity and corroboration from other logs decide which story is true.
