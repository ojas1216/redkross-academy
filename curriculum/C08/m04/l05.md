## Introduction and conceptual foundation

Almost every connection a computer makes starts with a question: *what is the address of this name?* Before a browser opens `https://mail.banyan.example/`, before an update agent checks for a new version, and before a piece of malware contacts its controller, something on the machine asks a DNS resolver to translate a name into an address. The Domain Name System is therefore the most universal piece of network behaviour in any estate, and a resolver that records the questions it is asked holds a running diary of what every host is trying to reach.

Module 2, Lesson 2 introduced DNS logs as one network telemetry source among several and listed what a query log contains. This lesson is about **analysis**: reading DNS records field by field, knowing what normal looks like, and recognising the handful of patterns that mean something is wrong. Those patterns fall into three families:

1. **Failure patterns.** A burst of NXDOMAIN ("this name does not exist") answers, especially for names that look random, is the classic trace of malware that generates candidate domains with an algorithm and tries them until one answers.
2. **Shape patterns.** Query names with unusually long, high-entropy labels, or a host asking for hundreds of different subdomains of one parent domain, suggest that data is being carried *inside* the names themselves: DNS tunnelling.
3. **Volume and type patterns.** A workstation making a steady stream of TXT queries, or querying an outside resolver directly instead of the company resolver, is behaving unlike an ordinary desktop.

DNS is attractive to an adversary for the same reason it is valuable to a defender: it is everywhere and rarely blocked. Even a strict firewall lets workstations ask the internal resolver about names, and the resolver forwards the question to whichever server is authoritative for that name. If the adversary controls that server, the question itself becomes a message, as the first figure shows.

DNS analysis also has honest limits. The resolver sees *names and answers*, not the traffic that follows; encrypted DNS to an outside provider and hard-coded IP addresses leave no trace in its log. And a strange-looking name is not proof of compromise, because CDNs and cloud services generate random-looking names constantly. The analyst combines the shape of the name with **who asked, how often, what the answer was and what happened next**.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Stub resolver | The DNS client built into the operating system; it sends queries to a configured recursive resolver and caches answers. |
| Recursive resolver | The server (internal DNS server or a provider's) that finds an answer on the client's behalf by asking root, top-level-domain and authoritative servers in turn. This is where query logging normally happens. |
| Authoritative server | The server that holds the records for a zone (for example `banyan.example`) and gives the definitive answer for names in it. |
| QNAME, QTYPE | The queried name and the record type requested (A, AAAA, CNAME, MX, TXT, NS, PTR, SRV and others). |
| RCODE | The response code in the answer header: NOERROR (0), SERVFAIL (2), NXDOMAIN (3), REFUSED (5) are the ones an analyst meets daily. |
| NXDOMAIN | "Non-existent domain": the authoritative data says the name does not exist. |
| TTL | Time to live: how many seconds a resolver may cache an answer. |
| Label | One dot-separated part of a name. `ping.cdn-telemetry-sync.example` has three labels. |
| Registered domain | The part of a name that an organisation registers, for example `banyan.example` in `mail.banyan.example`; analysis often groups by it. |
| DGA | Domain generation algorithm: code that derives many candidate domain names (often from the date and a seed) so that malware can find its controller without a fixed name (MITRE ATT&CK T1568.002). |
| DNS tunnelling | Carrying data inside DNS queries and responses, usually by encoding it into subdomain labels and record data of a zone the adversary controls (ATT&CK T1071.004 for DNS as a command channel; T1572 for protocol tunnelling generally). |
| Shannon entropy | A measure of how unpredictable the characters of a string are, in bits per character; random strings score higher than words. |
| Encrypted DNS | DNS over TLS (DoT, TCP port 853) or DNS over HTTPS (DoH, inside ordinary HTTPS on port 443); both hide queries from on-path observers and from resolvers they bypass. |
| Passive DNS | A historical database of observed name-to-address answers, used to see what a domain resolved to in the past and which other names shared its addresses. |

## Where DNS records come from

DNS evidence reaches a SOC from three kinds of vantage point, and each answers a slightly different question.

**The recursive resolver.** An internal DNS server (Windows DNS, BIND, Unbound) or a protective DNS service can log every query it receives: one log covers every host that uses it. Its weakness is identity: it sees the **source IP address**, and behind a local forwarder every query appears to come from the forwarder, so attribution needs the forwarder's logs or DHCP leases.

**The network sensor.** A passive sensor such as Zeek, watching a copy of traffic, writes a `dns.log` with one entry per query and response pair. Its standard fields include `ts`, `uid`, the connection's `id.orig_h` / `id.resp_h` addresses and ports, `query`, `qtype_name`, `rcode_name`, the `answers` list and their `TTLs`, and flags such as `RD` (recursion desired) and `RA` (recursion available). A sensor sees DNS that bypasses the internal resolver, for example a workstation sending queries straight to an outside server on UDP port 53, which the resolver itself never sees.

**The endpoint.** Sysmon event ID 22 (DNSEvent), introduced in Module 2, Lesson 1, records a query made through the Windows DNS client with `QueryName`, `QueryStatus`, `QueryResults` and, crucially, the `Image` that made it. It is the only one of the three that can say *which process* asked. A resolver log can tell you that WS-104 looked up a strange name; Sysmon event 22 can tell you it was `powershell.exe` rather than the browser.

The analyst's working record is the same regardless of source. Normalised into the SIEM, a DNS event should carry at least: timestamp (UTC), client address and, if known, host and user, the queried name, the query type, the response code, the answers and their TTLs, and the resolver or sensor that observed it.

### Reading one record

The illustrative record below is written in the normalised style used in this course (it is not lab output; field names follow ECS-like conventions from Module 3):

```json
{
  "@timestamp": "2026-11-03T06:16:58Z",
  "source.ip": "10.40.0.23",
  "host.name": "WS-104",
  "dns.question.name": "cdn-telemetry-sync.example",
  "dns.question.type": "A",
  "dns.response_code": "NOERROR",
  "dns.answers": [{"data": "203.0.113.80", "ttl": 300}],
  "observer.name": "dns-resolver-01"
}
```

Read it as a sentence: *at 06:16:58 UTC, workstation WS-104 asked resolver dns-resolver-01 for the IPv4 address of `cdn-telemetry-sync.example`; the name exists and resolved to 203.0.113.80, cacheable for 300 seconds.* Every part of that sentence is a pivot. The name can be stacked across the estate (who else asked?). The answer address can be searched in firewall and proxy logs (who connected to it?). The timestamp can be lined up against the endpoint timeline (what process started just before?). The TTL hints at infrastructure: very short TTLs on names whose answers change constantly are one trait of fast-flux hosting (ATT&CK T1568.001), though many legitimate load-balanced services also use short TTLs.

### How recursion carries a question to its owner

To understand both DGA failures and tunnelling, you have to follow a query beyond the resolver. The internal resolver does not know the answer to most names; it finds the authoritative server for the zone and asks it. For a name under a zone the organisation does not control, the question is delivered, by design, to whoever runs that zone's authoritative server.

**Components.** There are four lanes, left to right. **Workstation WS-104** (blue, sub-label "stub resolver") is the client. **Internal resolver** (dark, "query log written here") is the organisation's recursive resolver and the trust anchor of the diagram: it is the one box the SOC controls and logs. **Root / TLD servers** (slate, "referrals only") are the public hierarchy. **Authoritative for t.example** (red, "whoever controls the zone") is the server that owns the zone being queried.

**Relationships and arrows.** Solid arrows are queries; dashed arrows are responses. The first arrow, "Query: <label>.t.example TXT?", goes from the workstation to the internal resolver. The resolver sends "Same query (recursion)" to the root and TLD servers and receives a dashed "Referral: ask ns1.t.example". It then sends "Query forwarded to ns1.t.example" to the authoritative server, which replies with a dashed "Answer: TXT data / or NXDOMAIN". Finally the resolver returns a dashed "Answer relayed (and cached for TTL)" to the workstation.

**Execution flow.** Time runs top to bottom through the six numbered messages: client query (1), recursion (2), referral (3), query to the authoritative server (4), answer (5), relay (6). The resolver logs at message 1 (query received) and, depending on its configuration, at message 6 (response sent).

**Decision logic.** The answer in message 5 takes one of two branches shown in its label. If the zone exists and the name is defined, the authoritative server returns data (here TXT). If the name does not exist, it returns NXDOMAIN. Both outcomes are visible to the resolver and therefore to the SOC.

**Technical interpretation.** The whole query name, including its leftmost labels, travels from the workstation to the authoritative server. If those labels contain encoded data, the zone's owner has received that data, and the TXT answer can carry data back. No direct connection between the workstation and the outside server ever happens; the internal resolver relays both directions. That is DNS tunnelling's mechanism in one picture, described here so that you can recognise it, not build it.

**Practical example.** In an authorised lab you might see WS-104 send several hundred TXT queries in ten minutes, each for a different long label under the same parent zone, all answered NOERROR. Every one of them would appear in the internal resolver's query log, attributed to 10.40.0.23.

**Security implications.** Controls sit on the dark box: force all workstations to use the internal resolver (block outbound UDP/TCP 53 and known DoT/DoH endpoints from workstations), log queries centrally, and apply protective DNS or response-policy blocking for known-bad zones. Detection looks for the shape and volume of the names in its log.

**Key learning.** The resolver relays the full name to the zone's owner, so the query name itself can be a message; the resolver's log is where that message becomes visible.

## What normal DNS looks like

A typical office workstation makes thousands of queries a day. Most are type A and AAAA, many answers are CNAME chains pointing a friendly name at a cloud or CDN host, and a small share are SRV, PTR and other types. The vast majority of answers are NOERROR, and a few hundred registered domains (the company's own, its SaaS providers, vendors, CDNs) account for nearly all queries.

Some normal behaviour looks alarming at first sight:

- **CDN and cloud names** contain hashes or identifiers, so they are long and high in entropy, but they sit under a few well-known parents, are asked by many hosts and resolve.
- **Security products** such as mail filters querying DNS blocklists put a reversed IP address in front of the list's zone; the labels are odd but the parent belongs to a known vendor and the client is a known server.
- **Typos and stale configuration** produce NXDOMAIN, but for readable names, from one host or application.
- **Browser probes**: some browsers query a few random single-label names at start-up to detect networks that rewrite NXDOMAIN answers, from every host, at launch.

No single property of a name is enough. **Rarity across the estate** (how many hosts asked), **parent-domain reputation and age**, **query rate and regularity**, **response code** and **the process that asked** together separate the odd-but-normal from the suspicious.

## Failure patterns: NXDOMAIN and domain generation algorithms

### Why malware generates domains

A fixed controller domain written into malware is a single point of failure for the adversary: once defenders block or seize it, every infected host goes silent. A domain generation algorithm removes that weakness by having each infected host compute a long list of candidate names every day, from a seed and the date, and try them in turn. The operator, who knows the algorithm, registers only one or a few of the day's names. To defenders the effect is that an infected host asks for dozens or hundreds of names that **do not exist**, and the resolver answers NXDOMAIN to nearly all of them, until one resolves.

### What it looks like in the log

The illustrative excerpt below shows the shape of a DGA burst from one client, in the column order of a resolver query log (time, client, name, type, response code, answer). It is constructed for teaching and is not lab output:

```text
06:20:01  10.40.0.23  qxv7rk2mzt9bwp.example      A  NXDOMAIN
06:20:01  10.40.0.23  h3pl0q8vzc1wke.example      A  NXDOMAIN
06:20:02  10.40.0.23  m9tyb4xw2rjd6n.example      A  NXDOMAIN
06:20:02  10.40.0.23  zk1c7vqe5h0aul.example      A  NXDOMAIN
06:20:03  10.40.0.23  w4ngr8tm2xps9f.example      A  NOERROR  198.51.100.14
```

The names are **unpronounceable**, of similar length, with **no history** in the estate; they arrive in a machine-speed **burst**; nearly all fail. The one success is the pivot: its answer, 198.51.100.14, is what to search for in firewall and proxy logs.

### Turning the pattern into a query

The defender's measurement is per client, per time window: the number of distinct names queried, the number and ratio of NXDOMAIN answers, and how many distinct names fail. A practical detection asks, for each client in each ten-minute window, whether NXDOMAIN answers exceed a threshold **and** account for most of that client's queries **and** span many distinct names. In SQL against a normalised DNS table (the same SQL style as the course's `minisiem.py`; this table does not exist in the lab dataset), it reads:

```sql
SELECT client_ip,
       COUNT(*)                                           AS queries,
       SUM(rcode = 'NXDOMAIN')                            AS nx,
       COUNT(DISTINCT qname)                              AS names,
       ROUND(1.0 * SUM(rcode = 'NXDOMAIN') / COUNT(*), 2) AS nx_ratio
FROM dns
WHERE ts >= :window_start AND ts < :window_end
GROUP BY client_ip
HAVING nx >= 25 AND nx_ratio >= 0.5 AND names >= 20
ORDER BY nx DESC;
```

Each condition removes a benign cause: `nx >= 25` ignores occasional typos, `nx_ratio >= 0.5` ignores busy servers with a few failures among many successes, and `names >= 20` ignores one application retrying one dead name. The thresholds are starting points to tune (Module 7), not constants.

> [!TIP]
> When a DGA alert fires, do not stop at the failures. Search the same client and window for the **NOERROR** answers to names that look like the failing ones. The success, its answer address and what the host did next are what turn a suspicious pattern into an incident.

## Shape patterns: long labels, entropy and many subdomains

### The limits that shape a tunnel

RFC 1035 limits a single DNS label to 63 octets and a whole name to 255 octets in wire format (about 253 characters written with dots). Ordinary names rarely approach these limits; a typical label is a short word or abbreviation. A tunnel that moves data upstream has to fit it into labels, so it tends to show **long labels close to the limit**, **several of them per name**, made of an encoding alphabet such as hexadecimal or Base32, and **a new name for every chunk**, because a repeated name would be answered from the resolver's cache and never reach the authoritative server. The downstream direction usually relies on record types that can carry arbitrary data, TXT above all, but also NULL or CNAME.

Those mechanics translate directly into four defender's measurements: **label length**, **character randomness**, **the number of unique subdomains per parent zone per client**, and **the query-type mix**.

### Measuring randomness: Shannon entropy

Shannon entropy summarises how unpredictable the characters of a string are:

$$H = -\sum_{i} p_i \log_2 p_i$$

where $p_i$ is the proportion of the string made up of character $i$. A string of one repeated character scores 0. A string whose characters are all different scores $\log_2$ of its length. A long string drawn uniformly from the 16 hexadecimal characters approaches 4 bits per character; English words usually score lower because some letters repeat.

The lab kit has no DNS data, but its proxy URLs contain domain names, and a short script (written for this lesson, `label_stats.py`, not part of the kit) computes the length and entropy of the leftmost label of each name given to it. Run in your own working copy, against four names from the dataset and two illustrative random names, its real output is:

```terminal

mail.banyan.example                                  len=  4 H=2.00
cdn-telemetry-sync.example                           len= 18 H=3.35
banyan-payroll-update.example                        len= 21 H=3.54
files-share-drop.example                             len= 16 H=3.50
qxv7rk2mzt9bwp.example                               len= 14 H=3.81

```

The arguments are the names to measure; the script prints the leftmost label's length (`len`) and entropy (`H`).

Entropy behaves as expected at the extremes: `mail` scores 2.00 and the 48-character hexadecimal label 3.95, near the 4-bit ceiling for hexadecimal. But entropy **alone does not separate** the dataset's malicious domains from random ones: `banyan-payroll-update` (3.54) and `files-share-drop` (3.50) are dictionary words, yet score almost as high as the random `qxv7rk2mzt9bwp` (3.81), because entropy rises with length for any varied text. Mature detections therefore combine entropy with label length, digit ratio and, above all, **rarity and volume**: one high-entropy lookup is noise; hundreds of different ones under one new parent zone from one client is a pattern.

### Many unique subdomains under one parent

The strongest tunnelling signal is structural. Group queries by client and registered domain and count the distinct full names. Normal browsing yields a handful per parent; a CDN parent may show dozens, spread across many clients. A tunnel produces hundreds or thousands under one parent, from one or a few clients, with few repeats. The total length of those names bounds how much data could have left: a thousand names carrying 150 encoded characters each is about 150 kilobytes of encoded text.

### Volume and type patterns

Ordinary desktops make few TXT queries. TXT serves email policy (SPF, DMARC) and domain verification, but those lookups come mainly from mail servers and admin tools. A sharp rise in TXT (or NULL) share from one workstation, to one parent zone, is the signal of a downstream channel.

Two further patterns concern **where** queries go:

- **Direct-to-internet DNS.** Queries on port 53 to an external address instead of the internal resolver mean misconfiguration or deliberate avoidance of its logging. Firewall logs (Lesson 4) reveal it.
- **Encrypted DNS to public providers.** DoH (HTTPS on 443) and DoT (TCP 853) are not malicious in themselves, but on a managed workstation they bypass DNS controls; defenders disable them by policy and block known public endpoints.

The rows, top to bottom, are **NXDOMAIN burst**, **Long high-entropy labels**, **Many subdomains, one parent**, **High TXT share**, **Direct or encrypted DNS** and **Newly seen domain**. Row tones encode weight: the first three rows are red, the strongest indicators of DGA or tunnelling once the look-alike is excluded; the next two are orange, behavioural anomalies that need context; the last is violet, a policy-style signal that matters most in combination with the others.

**Relationships.** Read each row left to right as a chain of reasoning: the pattern is observed, the log evidence defines it precisely, the look-alike is ruled in or out, and the next check produces the decision. Rows are not independent: a burst of failures followed by one success leads straight to a newly seen domain, and a tunnel usually shows "Many subdomains, one parent" and "High TXT share" together.

**Execution flow.** An analyst starts from whichever row raised the alert, works across it, then checks the other rows for the same client and parent zone in the same window. Several rows lighting up for one client and one zone is far stronger evidence than any single row.

**Decision logic.** The "Benign look-alike" column is the branch point. In the first row, typos and browser probes are ruled out when the names are random and only one client shows the burst. In the second and third rows, CDN and security-product lookups are ruled out when the parent zone is unknown, young and asked by one client only. For TXT share, SPF and DMARC checks are ruled out when the client is a workstation rather than a mail server. For direct or encrypted DNS, an unmanaged or misconfigured device is checked against the asset inventory.

**Technical interpretation.** Each row maps to a mechanism described above: DGAs produce failures because most generated names are never registered; tunnels produce long, unique, encoded labels because each chunk needs a fresh name of limited size; downstream data needs record types such as TXT; bypassing the resolver is the only way to escape its log.

**Practical example.** Suppose a protective DNS alert reports long high-entropy labels for 10.40.0.23. The table's next checks are: how many distinct names under that parent (third row), the TXT share (fourth row), whether any other host asked (rarity), and, through Sysmon event 22, which process made the queries.

**Security implications.** The table also implies the controls: central resolver logging makes the first four rows visible at all; blocking outbound DNS and public DoH/DoT forces queries into that log; protective DNS can refuse newly registered or known-bad zones.

**Key learning.** Every DNS indicator has an innocent twin; decide with rarity, parent-zone reputation, client role and the asking process, not with the name's appearance alone.

## Worked example: a domain-level view of the lab dataset

Banyan collected no resolver logs, itself a finding to record: nothing can prove or disprove whether WS-104 tried other names or a tunnel. But every proxy URL contains a **host name**, so the key DNS-style analyses (stacking names by host count, ordering by first sighting) can be practised on those.

Copy the kit to your own working directory first, never run it inside the course library folder, then load it:

```terminal
$ python minisiem.py load

```

Now extract the host name from each proxy URL and stack it. SQLite's `instr` finds the first `/` after the `https://` prefix (eight characters), and `substr` takes the text before it:

```terminal
$ python minisiem.py search "SELECT substr(url, 9, instr(substr(url,9),'/')-1) AS domain, COUNT(*) hits, COUNT(DISTINCT host) hosts, MIN(ts) first_seen FROM events WHERE source='proxy' GROUP BY domain ORDER BY hosts, first_seen"
domain | hits | hosts | first_seen
banyan-payroll-update.example | 1 | 1 | 2026-11-03T06:12:00Z
cdn-telemetry-sync.example | 18 | 1 | 2026-11-03T06:17:00Z
files-share-drop.example | 1 | 1 | 2026-11-03T08:12:00Z
news.example.com | 48 | 8 | 2026-11-03T03:19:00Z
cdn.example.org | 46 | 8 | 2026-11-03T03:31:00Z
crm.banyan.example | 37 | 8 | 2026-11-03T03:35:00Z
intranet.banyan.example | 37 | 8 | 2026-11-03T03:39:00Z
mail.banyan.example | 51 | 8 | 2026-11-03T03:42:00Z
maps.example.net | 45 | 8 | 2026-11-03T03:45:00Z
```

The options of the query, clause by clause: `substr(url, 9, ...)` skips the eight characters of `https://`; `COUNT(DISTINCT host)` is the rarity measure; `MIN(ts)` gives the first time each name appears in the data, a stand-in for "newly observed domain"; `ORDER BY hosts, first_seen` puts the rarest names first and orders them in time.

**Interpretation.** Six names are asked by all eight hosts from the first hours of the data: they are the baseline. Three names are seen from one host only, and their first-seen times form a story: `banyan-payroll-update.example` at 06:12, `cdn-telemetry-sync.example` at 06:17, `files-share-drop.example` at 08:12. If Banyan had resolver logs, each of these would have been preceded by a DNS query from 10.40.0.23 a moment earlier, and a newly-observed-domain rule on the resolver would have flagged all three on first sight, before a single byte of payload was exchanged.

A DNS view would add **names that never reached the proxy** (a fallback DGA or DNS channel) and the **answers**, whose addresses could be searched in firewall logs and passive DNS. It would not add the 48.2 MB upload or the 220-byte beacon sizes; those are proxy evidence, analysed in Lesson 6.

Note also that `banyan-payroll-update.example` is not random but a **brand lookalike**, and entropy did not flag it. Rarity, recency and imitation of `banyan.example` under a different registered domain do. A useful SOC check is "names containing our brand string that are **not** under our own registered domains".

## Common mistakes and misconceptions

- **"High entropy means malicious."** CDN and cloud host names are routinely high in entropy. Without rarity, parent-zone reputation and volume, entropy alone produces a flood of false positives, and as the worked output showed, it can also miss word-based malicious names.
- **"NXDOMAIN is an error, so it is noise."** A few NXDOMAINs are noise; a burst of NXDOMAINs for many different random names from one client is one of the clearest signs of DGA malware. Keep failed lookups in the log; some pipelines drop them to save volume.
- **"The resolver log shows the infected host."** It shows the source IP of the query, which may be a forwarder, a NAT address or a VPN concentrator. Attribute with the forwarder's own logs, DHCP leases and Sysmon event 22.
- **"No DNS alerts, so no DNS abuse."** A host using DoH to a public provider, an external resolver or hard-coded IP addresses produces no internal resolver entries at all. Absence of evidence is only meaningful when egress controls force DNS through the resolver.
- **"Block the domain and the case is closed."** A DGA produces new names daily. Blocking is containment; the process on the host must still be found.

## Security implications, detection and defence

DNS appears in several ATT&CK techniques that a SOC should have explicit coverage for: **T1071.004** (Application Layer Protocol: DNS) for command and control over DNS, **T1568.002** (Domain Generation Algorithms), **T1568.001** (Fast Flux DNS), **T1572** (Protocol Tunneling) and, for data leaving over DNS, **T1048** (Exfiltration Over Alternative Protocol). Each maps to a detection idea already met in this lesson: NXDOMAIN ratio for DGAs, label length and unique-subdomain counts for tunnelling, TXT share for downstream channels, short-TTL churn for fast flux.

Defence is layered around the resolver:

- **Make the resolver the only path.** Block outbound UDP and TCP 53 from everything except the designated resolvers; block DoT (TCP 853) outbound; disable or centrally configure DoH on managed browsers and operating systems, and block known public DoH endpoints. Only then do resolver logs mean "everything".
- **Log queries and responses centrally**, including NXDOMAIN, with UTC timestamps and the resolver's name, and keep them long enough for investigations. CERT-In's April 2022 directions require ICT system logs to be maintained for a rolling 180 days within India; DNS logs are part of that set for most organisations.
- **Use protective DNS or response policy zones** to refuse resolution of known-malicious and newly registered domains, and log every refusal as an alert source.
- **Add endpoint context.** Sysmon event 22 or EDR DNS telemetry ties queries to processes, which is the fastest way to separate a browser from an implant.
- **Respect privacy.** DNS logs reveal browsing habits and are personal data under India's DPDP Act 2023; restrict access and document the purpose.

> [!IMPORTANT]
> DNS tunnelling and DGA behaviour are studied here so that you can recognise them in logs. Reproducing them, even "just to test the detection", belongs only in an isolated lab you own, under written authorisation, with your own zone and resolver. Never send encoded data through a production or third-party resolver.

## Best practices

- Baseline per client role: servers, workstations and mail gateways have very different DNS profiles; one threshold for all of them guarantees noise.
- Group by **registered domain** as well as full name, so that thousands of unique subdomains collapse into one row per parent zone.
- Track **first seen** per registered domain across the estate.
- Pivot a suspicious name three ways: across hosts, into its answers, and into the endpoint process.
- Record DNS gaps explicitly in case notes, as with Banyan.

1. Load the dataset with `python minisiem.py load` and run the domain-stacking query from the worked example. Confirm that you see six names on eight hosts and three on one host.
2. Modify the query to add `MAX(ts) AS last_seen` and compute, for `cdn-telemetry-sync.example`, the span between first and last sighting. Compare it with the beacon window you will analyse in Lesson 6.
3. Recreate `label_stats.py` from the description in this lesson (a character counter and the entropy formula). Measure the nine domains from step 1 and rank them by entropy. Which malicious names fall below benign ones, and why?
4. Design, on paper, the normalised DNS table Banyan should collect, with each field's ECS-style name and the detection that needs it.
5. Write a query for that table counting distinct names per client and registered domain in a ten-minute window, and state the benign look-alike each threshold excludes.

## Key takeaways

- The resolver relays the full query name to the zone's authoritative server, so the name itself can carry data; the resolver's log is where defenders see it.
- DGA malware shows as bursts of NXDOMAIN for many random names from one client, followed by a success whose answer is the pivot.
- Tunnelling shows as long, encoded labels, many unique subdomains under one parent and a high TXT (or NULL) share, usually together.
- Entropy is a helper, not a verdict: it flags CDN names and can miss word-based lookalikes such as `banyan-payroll-update.example`; rarity, recency and client role decide.
- DNS logs are only complete when egress forces all queries through the resolver; record the gap when they are missing, as in the Banyan dataset.
