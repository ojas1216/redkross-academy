## Introduction and conceptual foundation

Module 2 taught you what Windows records: which event IDs exist, which log they land in, which audit policy subcategory produces them and how they reach the SIEM. Module 3 taught you how the SIEM stores, normalises, correlates and searches them. This lesson is about the step that comes after both: sitting in front of a set of Windows events and deciding what they *mean*. That is **event analysis**, and it is the core daily skill of the analyst.

Knowing that 4720 means "a user account was created" is recall. Analysis is being able to say of one particular 4720: "created from a payments approver's session, 48 minutes after Word started a hidden PowerShell, with a name imitating a service account, on a host where IT never creates accounts." Every clause comes from a field, a neighbouring event, a baseline or organisational knowledge; none of it is in the event ID alone.

Three ideas run through the whole lesson.

1. **Normal is local and must be measured.** A 4625 is a typo on one host and the first sign of a spray on another. An event is suspicious because it departs from what *this* host, account and time of day usually produce.
2. **Meaning lives in sequences.** Windows writes one event per action, and attackers need several actions. A single event is rarely conclusive; a chain sharing a host, account or logon session often is.
3. **Absence is evidence, but weak evidence.** An event that *should* be there and is not tells you something only if the source was collecting. Check whether the silence is the attacker's or the pipeline's.

The worked analyses use the course dataset for the fictional Banyan Microfinance, `LAB_ASSETS/C08/banyan_events.jsonl`, queried through the course SIEM `LAB_ASSETS/C08/minisiem.py`. You have met its Windows events before; here we ask different questions of them, the questions an analyst asks when the alert has fired and the case is now theirs. Work in your own copy of the kit, never in the original folder.

> [!NOTE]
> The Banyan events are synthetic and simplified: one flat JSON shape with Windows-style field names, not a raw export from Windows. Where a real event carries more (a Logon ID, a SID, a Sub Status), this lesson says so explicitly, so that you know which reasoning steps you would take on a real estate and which the lab data can support.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Baseline | A measured description of what a host, account or event type normally produces: which IDs, how many, at what times, with which field values. |
| Deviation | An event or pattern that differs from the baseline; the starting point of analysis, not its conclusion. |
| Actor (subject) | The account that *performed* an action. In Windows events this is usually the **Subject** section (`SubjectUserName`, `SubjectLogonId`). |
| Target | The account, group or object the action was performed *on*: the new account in a 4720, the group in a 4732. |
| Event chain | Two or more events linked by shared values (host, account, Logon ID, process) and ordered in time, read together as one activity. |
| Logon session | The security context that a 4624 creates; its Logon ID links that logon to later events performed within it. |
| Stacking | Counting how often each value or combination of values occurs across a population, so that rare combinations stand out. |
| Burst | Many events of one kind in a short interval, for example dozens of 4625s in a minute. |
| Dwell gap | The time between two linked events in a chain; short gaps suggest automation, long gaps suggest hands-on activity or waiting. |
| Disposition | The analyst's conclusion about an event or chain: benign, benign but noteworthy, suspicious (needs more evidence) or malicious. |

## A method for reading Windows events

Experienced analysts appear to "just see" what is wrong in a page of events. What they are actually doing is running a fixed set of questions very quickly. Writing the questions down makes the skill teachable and reliable at four in the morning.

**1. Frame the question.** An alert from rule R3 `new_local_admin` asks "was this account creation authorised?"; a hunt asks "has any workstation gained an unexpected administrator this week?" The question sets the hosts, accounts, time window and event IDs in scope.

**2. Inventory the evidence.** Count which event IDs and sources exist for the scope, from when to when. The inventory tells you what you *can* answer: without process-creation events you cannot say what ran.

**3. Establish the baseline.** Compare the host or account with its peers or its own history. The baseline converts "is this bad?" into the easier question "is this unusual?"

**4. Isolate the deviations.** The rare event ID, the unusual logon type, the account acting outside its role, the activity at the wrong hour. Each becomes a lead.

**5. Build the chain.** Pivot on the values a lead shares with other events (host, actor, target, Logon ID, process), order by time, and ask what objective each step serves.

**6. Check for absence.** Ask what you would expect to see if your reading were right, and whether it is there, and whether the source was collecting at the time.

**7. Add context and decide.** Bring in the change calendar, the asset's role and the user's job, then record a disposition with its evidence.

**Relationships and arrows.** Each downward arrow means "the output of this step is the input to the next". The loop arrow matters as much as the straight ones: a chain often reveals a new host or account, and that new entity needs its own inventory and baseline.

**Execution flow.** In practice the first three steps can take seconds for a familiar estate and the last three take most of the time. A Tier 1 analyst on a routine alert might run the whole flow in ten minutes; a hunt over a month of data might spend an hour on the baseline alone.

**Decision logic.** Two decision points are implicit. After **Isolate deviations**, if nothing departs from the baseline, the alert is usually benign and the analyst records why. After **Check for absence**, if an expected event is missing, the analyst must decide whether the source failed (a collection question for the engineering team) or the activity genuinely did not happen.

**Technical interpretation.** Each step maps onto a kind of query: an inventory is a `GROUP BY event_id`; a baseline is a stack across hosts; a deviation is a filter on the rare values; a chain is a pivot on a shared field ordered by time; an absence check is a query expected to return rows that returns none.

**Practical example.** For the Banyan alert R3 on WS-104, the question is "was `svc_update` created legitimately?"; the inventory shows WS-104 has four Windows event types where its peers have one or two; the baseline shows no other workstation creates accounts; the chain links the creation to a Word-spawned PowerShell 48 minutes earlier; the absence check finds no logon by the new account in the data. The worked analyses later in the lesson run each of these queries.

**Security implications.** Skipping the baseline produces false positives and analyst fatigue; skipping the absence check produces false confidence. Attackers benefit from both.

**Key learning.** Analyse Windows events in a fixed order: question, inventory, baseline, deviation, chain, absence, context. The conclusion is only as good as the weakest step you skipped.

## Reading fields: who did what to whom

The most frequent analytical error with Windows events is reading the wrong account. Many events name two or more accounts, and they play different roles.

In a **4624** (successful logon), the **Subject** is the local context that *requested* the logon (often the machine account or `SYSTEM`), while **New Logon** names the account that was actually logged on. In a **4720** (account created), the **Subject** is the account that created it and the **New Account** section (`TargetUserName`) names the account that was created. In a **4732** (member added to a security-enabled local group), the trap is sharper: `TargetUserName` holds the *group* name (for example `Administrators`, with `TargetDomainName` `Builtin` and `TargetSid` `S-1-5-32-544`), the **Member** section identifies the account being added, and for local accounts the member is often recorded only by its SID. An analyst who searches 4732 events for `TargetUserName = 'svc_update'` will find nothing and may wrongly conclude the account was never added to a group. In a **1102** (audit log cleared), the Subject is the account whose session issued the clear.

The Banyan dataset simplifies this into two flat fields, `user` (the actor) and `target_user` (the account acted on), with the group in a separate `group` field. Reading them explicitly, rather than trusting the column called `user`, is the first analytical habit to build:

```terminal
$ python minisiem.py load
loaded 340 events
$ python minisiem.py search "SELECT event_id, json_extract(raw,'$.user') AS actor, json_extract(raw,'$.target_user') AS target, json_extract(raw,'$.group') AS grp, ts FROM events WHERE source='windows' AND event_id IN (4720,4732,1102) ORDER BY ts"
event_id | actor | target | grp | ts
4720 | divya | svc_update | None | 2026-11-03T07:02:00Z
4732 | divya | svc_update | Administrators | 2026-11-03T07:03:00Z
1102 | divya | None | None | 2026-11-03T08:17:00Z
```

`json_extract(raw, '$.field')` reads a field from the original event stored in the `raw` column, so the query does not depend on how minisiem chose to normalise it. The result reads as three sentences: *divya* created *svc_update*; *divya* added *svc_update* to *Administrators*; *divya*'s session cleared the Security log. Whether divya the *person* did them is a separate question: the actor field names the account whose session acted, not who was at the keyboard, and the earlier Word-to-PowerShell event on the same host suggests something other than its owner was using that session.

Other fields carry most of the remaining meaning, and each answers a specific analytical question:

| Question | Field(s) to read | Events |
| --- | --- | --- |
| How did the account arrive? | Logon Type | 4624, 4625 |
| From where? | Source Network Address, Workstation Name | 4624, 4625, 4776 |
| Why did it fail? | Status, Sub Status | 4625 |
| Which session did this? | Subject Logon ID, matched to a 4624's New Logon ID | most Security events |
| Did the session hold admin rights? | Presence of a 4672 with the same Logon ID; Elevated Token | 4672, 4624 |
| Which program asked? | Process Name / New Process Name, Creator Process Name | 4624, 4688 |
| What exactly ran? | Process Command Line (only if command-line auditing is enabled) | 4688 |

A real 4720 also carries a `SubjectLogonId`. On a live estate you would find the 4624 on the same host with that New Logon ID and read its logon type and source: console, Remote Desktop from another machine, or a network logon from a management server? The Banyan events carry no Logon IDs, so the lab links events by host, actor and time. Say which you have in the case: "same host, same account, 48 minutes later" is correlation; "same Logon ID" proves one session.

## Normal and suspicious patterns by event family

Baselines differ between estates, but the *shape* of normal activity for each event family is consistent enough to learn.

| Family | Normal shape | Shapes that deserve a look |
| --- | --- | --- |
| Logons (4624, 4634, 4647) | Owner at own workstation (type 2, 7) during working hours; type 3 from known management and file servers; type 5 for services | Type 10 to a workstation from a peer workstation; type 3 by a user to many hosts in minutes; logons at unusual hours; a service account producing interactive logons |
| Failures (4625, 4771, 4776 failure, 4740) | Occasional single failures followed by success at the user's own host | Bursts; many accounts from one source; many 0xC0000064 (no such user); failures continuing after a lockout |
| Privileged sessions (4672, 4648) | 4672 for administrators and service accounts on systems they manage | 4672 for an account not known to be privileged; 4648 explicit-credential use from a user workstation to servers |
| Account and group changes (4720, 4722, 4724, 4728, 4732, 4756, 4738) | Created by IT accounts, from management hosts, during change windows, following a naming standard | Created from a user's session; added to Administrators or Domain Admins at once; names that imitate service or system accounts; creation then deletion within hours |
| Persistence (4698 scheduled task created, 4697 / System 7045 service installed) | Software deployment tools and patching, on schedules that recur across many hosts | A task or service on one host only; binaries in user-writable paths; commands that start script interpreters |
| Execution (4688, Sysmon 1) | The same parent-child pairs on many hosts | Office or browser processes starting shells or script engines; encoded or hidden command lines |
| Log integrity (1102, System 104, 4719) | Rare; tied to a documented change | Any clearing or audit policy change without a change record, especially after other deviations |

### Logons: type, source and time

A logon event answers *how* (logon type), *from where* (source address, workstation name) and *when*. Deviations are usually combinations: a type 10 (Remote Desktop) logon is ordinary on a jump server and unusual on a finance workstation; a type 3 logon from a management server is ordinary, while one from another user's laptop suggests lateral movement (ATT&CK T1021, Remote Services). Convert time before judging it: Banyan's morning logons at 03:07-03:50 UTC are 08:37-09:20 IST, exactly when the office opens.

### Failures: reading the shape, not the count

A single failed logon means almost nothing. Analytical value comes from the *shape* of a group of failures: how many accounts, how many sources, what status codes, what timing, and whether a success follows. Four shapes cover most of what a SOC sees, and they call for very different responses.

- **Typing error.** One or two failures by one account at its own host, status 0xC000006A, followed by a success or preceded by one. Benign.
- **Stale credential.** A service, scheduled task, mapped drive or phone still using an old password after a change. Repeated failures by one account from one source, often at a regular interval, usually status 0xC000006A, often ending in a lockout (4740 on the DC, whose Caller Computer Name points to the source). Operationally annoying, rarely malicious, but it must be fixed because it hides real attacks against the same account.
- **Brute force.** Many failures against one account (or a few) from one source in a short time, sometimes followed by a success or a lockout (ATT&CK T1110.001, password guessing). The success, if any, is the incident.
- **Password spray.** One or a few failures per account against many accounts from one source, or a small set of sources, often with mechanical spacing (ATT&CK T1110.003). Per-account counts stay below lockout thresholds, so only a view grouped by *source* reveals it. You analysed the Banyan VPN spray in Module 2; the same shape appears in 4625 and 4771 events when the target is Active Directory.

Status codes sharpen the reading. A spray using a list of guessed names produces many 0xC0000064 (user name does not exist); a spray using a harvested list of real names produces 0xC000006A. Failures against disabled accounts (0xC0000072) point to someone using an old directory list, including one that still holds former staff.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The table is a recognition aid for groups of failed Windows logons. Its purpose is to make the analyst classify failures by *shape* (accounts, sources, timing, outcome) before reacting to their *count*, because a hundred failures from a stale service credential are less dangerous than eight failures in a spray that ends in a success.

**Components.** There are five columns. **Pattern** names the shape. **Accounts x sources** gives the cardinality: how many accounts are involved and from how many sources. **Timing and status** gives the typical rhythm and the usual 4625 status code. **What follows** describes the typical outcome. **Reading** gives the analyst's disposition. The four rows are coloured by risk: **Typing error** is green (benign), **Stale credential** is slate (operational, needs fixing), **Brute force** is orange (attack against one account) and **Password spray** is red (attack against many accounts, hardest to see per account).

**Relationships.** The rows are ordered by how hard the pattern is to spot. A typing error is visible on one host. A stale credential is visible per account. A brute force is visible per account and per source. A spray is visible only when you group by source and count distinct accounts. The table's columns are, in effect, the `GROUP BY` clauses an analyst must run to tell the rows apart.

**Execution flow.** Faced with a group of failures, read across the columns left to right: first count accounts and sources, then look at timing and status codes, then look for what happened next (a success, a lockout, nothing). By the time you reach **Reading** the row should be clear.

**Decision logic.** The decisive branch is *what follows*. A typing error is followed by the user's own success at the same host. A stale credential is followed by a lockout and a help desk ticket. A brute force or spray followed by a success from the same source is a probable account compromise and is escalated at once; the same pattern with no success is still reported, because it shows the attacker's intent and target list.

**Technical interpretation.** On a domain, the same spray produces different events in different places: 4771 or failed 4768 on the domain controller for Kerberos, 4776 failures for NTLM, and 4625 on the machine that received the logon attempt. The cardinality test works on any of them, provided the source field is populated and parsed.

**Practical example.** The two Banyan 4625 events at 04:05 UTC belong to the first row: ben and hema, one failure each, at their own workstations, status 0xC000006A, both already logged on that morning. The VPN failures at 06:42 belong to the last row: eight accounts, one source, seven seconds apart, followed by a success for gopal.

**Security implications.** Rules that alert on "more than N failures per account" catch brute force and stale credentials but miss sprays entirely. A detection set needs both a per-account and a per-source distinct-account view, and lockout thresholds should be complemented by MFA so that a guessed password alone is not enough.

**Key learning.** Classify failures by accounts, sources, timing, status and outcome. The success that follows a pattern of failures matters more than the number of failures.

### Account, group and persistence changes

Account management is a small, high-value family: in a healthy estate it is rare, done by a few IT accounts from a few management hosts, and tied to joiners, movers and leavers. That makes deviations stand out. Three questions settle most cases. **Who acted?** An account change performed by an ordinary user, or from an ordinary user's workstation, is unusual by definition. **What was granted?** Creation followed within minutes by addition to `Administrators` (local) or to a privileged domain group (4728 global, 4756 universal) is the classic persistence-with-privilege pattern (ATT&CK T1136, Create Account, and T1098, Account Manipulation). **Does the name fit the standard?** Attackers choose names that look like they belong: `svc_update`, `backup_admin`, `support`. A name that imitates a service account but was created interactively on a workstation contradicts itself.

Scheduled tasks (4698, when the "Other Object Access Events" audit subcategory is enabled) and service installation (4697 in Security, 7045 in the System log) follow the same logic. Software deployment creates the same task or service on hundreds of hosts at once; an attacker creates it on one. Stack the task name or service binary path across hosts and the single-host entries come to the top.

### Log integrity events

Event **1102** (the audit log was cleared) is written into the Security log itself as the first record after the clearing. Clearing other logs, such as System or Application, is recorded as event **104** in the System log. Event **4719** records a change to the system audit policy, which is the quieter way to blind the Security log: rather than erasing what was recorded, stop recording. None of these has a routine reason to occur on a workstation outside a documented change, and all of them are strongest when read as the *end* of a chain: the attacker cleans up after doing something worth hiding (ATT&CK T1070.001, Clear Windows Event Logs, and T1562.002, Disable Windows Event Logging).

## Worked analysis 1: baselining the estate

The case opens with rule R3 `new_local_admin` firing for WS-104. Before reading the WS-104 events, the method says to inventory and baseline. In Banyan's estate the peers are the other seven workstations, so the first query profiles every host's Windows events:

```terminal
$ python minisiem.py search "SELECT host, COUNT(*) AS events, GROUP_CONCAT(DISTINCT event_id) AS ids FROM events WHERE source='windows' GROUP BY host ORDER BY events DESC, host"
host | events | ids
WS-104 | 4 | 4624,4720,4732,1102
WS-102 | 2 | 4624,4625
WS-108 | 2 | 4624,4625
WS-101 | 1 | 4624
WS-103 | 1 | 4624
WS-105 | 1 | 4624
WS-106 | 1 | 4624
WS-107 | 1 | 4624
```

`GROUP BY host` gives one row per workstation; `COUNT(*)` counts its Windows events; `GROUP_CONCAT(DISTINCT event_id)` lists the distinct event IDs it produced, which is a compact *event profile*. Sorting by count puts the busiest host first.

The baseline is unmistakable: a Banyan workstation produces one 4624 on a normal day, and sometimes a 4625. Five hosts show only the logon; two show a logon and a failure; one, WS-104, shows three event types that no other host produces at all. Even without knowing what 4720, 4732 and 1102 mean, the profile alone would tell you where to look. This is stacking applied to event IDs: the rare profile is the lead.

Next, the failures. Are WS-102 and WS-108 part of the story, or noise? The per-user view answers it:

```terminal
$ python minisiem.py search "SELECT user, MIN(CASE WHEN event_id=4624 THEN ts END) AS first_logon, SUM(event_id=4625) AS failures, MIN(CASE WHEN event_id=4625 THEN ts END) AS first_failure FROM events WHERE source='windows' AND event_id IN (4624,4625) GROUP BY user ORDER BY user"
user | first_logon | failures | first_failure
asha | 2026-11-03T03:36:00Z | 0 | None
ben | 2026-11-03T03:48:00Z | 1 | 2026-11-03T04:05:00Z
chen | 2026-11-03T03:50:00Z | 0 | None
divya | 2026-11-03T03:18:00Z | 0 | None
eshan | 2026-11-03T03:39:00Z | 0 | None
farah | 2026-11-03T03:07:00Z | 0 | None
gopal | 2026-11-03T03:33:00Z | 0 | None
hema | 2026-11-03T03:21:00Z | 1 | 2026-11-03T04:05:00Z
```

`MIN(CASE WHEN event_id=4624 THEN ts END)` picks the earliest successful logon per user, ignoring other rows; `SUM(event_id=4625)` counts failures, because in SQLite a comparison evaluates to 1 or 0. Read against the failure shapes: one failure each, after the user had already logged on successfully, at the user's own host (the earlier inventory showed the 4625s on WS-102 and WS-108, which are ben's and hema's machines), with status 0xC000006A. That is the "typing error" row. The shared timestamp is coincidence; nothing else connects them. Disposition: benign, and recorded as such so that the next analyst does not re-investigate them.

> [!TIP]
> Write the benign reasoning into the case even when it takes one line. "4625 x2 at 04:05 (ben WS-102, hema WS-108): single 0xC000006A each, after own successful 4624, own host; typos" saves the next shift ten minutes and shows a reviewer that the events were seen, not missed.

## Worked analysis 2: reading the WS-104 chain

With the baseline set, the WS-104 deviations become a chain. The actor/target query in the field-reading section has already established who did what to whom. Now put the chain in time order, measured from the start of the session it most plausibly belongs to, divya's 4624 at 03:18:

```terminal
$ python minisiem.py search "SELECT e.ts, e.source, e.event_id, CAST(ROUND((julianday(e.ts)-julianday(l.ts))*1440) AS INTEGER) AS min_after_logon FROM events e JOIN events l ON l.host=e.host AND l.event_id=4624 WHERE e.host='WS-104' AND e.event_id IN (1,4720,4732,1102) AND (e.event_id<>1 OR e.parent_image LIKE '%WINWORD%') ORDER BY e.ts"
ts | source | event_id | min_after_logon
2026-11-03T06:14:00Z | sysmon | 1 | 176
2026-11-03T07:02:00Z | windows | 4720 | 224
2026-11-03T07:03:00Z | windows | 4732 | 225
2026-11-03T08:17:00Z | windows | 1102 | 299
```

The query joins each WS-104 event (`e`) to the host's logon (`l`) and computes the difference in minutes: `julianday()` converts an ISO timestamp to a day number, so the difference multiplied by 1,440 is minutes, rounded to a whole number. The filter keeps the Sysmon process event only when Word is the parent, so the everyday application launches drop out.

Read the **dwell gaps**. Word starts PowerShell almost three hours into the working day, so nothing about the logon itself was unusual. The account is created 48 minutes later and made an administrator one minute after that, the rhythm of a scripted or practised operator. The log is cleared 74 minutes later. The steps serve execution, persistence, privilege and defence evasion. Each is explainable alone (an IT admin borrowing the desk, a help desk script, a clean-up), but every innocent explanation needs a *different* coincidence, while one hypothesis, an intruder operating through divya's session, explains all four.

Now the **absence check**. If `svc_update` was created for persistence, it may already have been used. Search every source for it:

```terminal
$ python minisiem.py search "SELECT ts, source, event_id, user, target_user FROM events WHERE user='svc_update' OR target_user='svc_update' OR raw LIKE '%svc_update%' ORDER BY ts"
ts | source | event_id | user | target_user
2026-11-03T07:02:00Z | windows | 4720 | divya | svc_update
2026-11-03T07:03:00Z | windows | 4732 | divya | svc_update
```

The `raw LIKE '%svc_update%'` clause searches the whole original event text, catching the name in any field minisiem did not normalise. Only the two creation events come back. That does **not** show the account was never used; it shows that no *collected* source recorded its use. Two facts weaken the absence. First, the WS-104 Security log was cleared at 08:17, so any event not yet forwarded by then would be gone; on a real estate you would check the forwarder's lag. Second, Windows collection looks thin after the clear:

```terminal
$ python minisiem.py search "SELECT MAX(ts) AS last_windows_event FROM events WHERE source='windows'"
last_windows_event
2026-11-03T08:17:00Z
$ python minisiem.py search "SELECT source, COUNT(*) n, MIN(ts), MAX(ts) FROM events WHERE host='WS-104' AND ts > '2026-11-03T08:17:00Z' GROUP BY source"
source | n | MIN(ts) | MAX(ts)
proxy | 14 | 2026-11-03T09:22:00Z | 2026-11-03T12:08:00Z
```

The 1102 is the last Windows event from *any* host, yet WS-104 kept producing proxy traffic until 12:08. In the synthetic dataset this is simply because Windows events were only generated for the morning; on a real estate the same result would be a collection question to raise immediately: is the Security log still forwarding from WS-104, from every host, or did something stop it? An analyst who reports "no further Windows activity after 08:17" without that caveat has mistaken a gap in visibility for a gap in activity.

Finally, **context**. Banyan's asset inventory (used by `triage.py`) records WS-104 as a finance workstation and divya as a payments approver; `triage_output.txt` ranks the R5 log-clearing alert first in the queue at priority 10.8 for that reason. No change record covers account creation on WS-104. Disposition: malicious, escalate, with the chain above as evidence, and with three open questions recorded for Tier 2: what the encoded PowerShell did, whether `svc_update` has been used anywhere, and whether Windows collection is still healthy.

## Doing the same on a live Windows host

In a real SOC you query the SIEM, but during incident response, or in your own Windows lab VM, you may need to read the local log directly. PowerShell's `Get-WinEvent` does this, and converting each event to XML exposes the named fields this lesson relies on:

```powershell
Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4732 } -MaxEvents 20 | ForEach-Object {
  $d = ([xml]$_.ToXml()).Event.EventData.Data
  [pscustomobject]@{
    Time   = $_.TimeCreated
    Actor  = ($d | Where-Object Name -eq 'SubjectUserName').'#text'
    Group  = ($d | Where-Object Name -eq 'TargetUserName').'#text'
    Member = ($d | Where-Object Name -eq 'MemberSid').'#text'
  }
}
```

`-FilterHashtable` passes the filter (log name, event IDs, optionally a `StartTime`) to the event log service, which is far faster than filtering afterwards with `Where-Object`. `-MaxEvents 20` returns the 20 newest matches. `ToXml()` gives the event's XML; each `Data` element has a `Name` attribute and a text value. The object built for each event puts actor, group and member side by side: the "who did what to whom" reading. Run these only on systems you own or are authorised to examine; on a compromised host the local log is a last resort, because the SIEM copy is the one the attacker could not clear.

## Common mistakes and misconceptions

- **Reading the wrong account.** Treating the Subject of a 4624 as the user who logged on, or the `TargetUserName` of a 4732 as the member added. Always ask which section a name comes from.
- **Judging by count.** Escalating fifty failures from a stale credential while missing eight failures in a spray. Shape, not count.
- **Treating one event as a verdict.** A single 4720 or even a 1102 can be legitimate. Build the chain and check the change record before you conclude.
- **Correlation presented as proof.** "Same host, same account, later" suggests one session; a matching Logon ID demonstrates it. Say which one you have.
- **Mistaking silence for innocence.** No events after a log clear, or for a new account, may reflect collection, not behaviour. Check source health before reporting absence.
- **Baselining against nothing.** Calling an event "unusual" without having looked at what peers or history produce.

## Security implications, detection and defence

Analysis depends on telemetry that the defender must deliberately enable. The patterns in this lesson need, at minimum: logon and logoff auditing on every host; account management and security group management auditing; command-line inclusion in 4688 or Sysmon process events; "Other Object Access Events" for scheduled tasks; and forwarding fast enough that a 1102 cannot erase events before they leave the host. Protect the pipeline as a security control: alert on 1102, System 104 and 4719, and on hosts that stop sending Security events.

Several patterns translate directly into low-noise detections: account creation from a non-IT host or account; privileged group addition within minutes of creation; any 1102 without a change ticket; per-source distinct-account failure counts. On the preventive side, removing local administrator rights from ordinary users (divya's session could not otherwise have created an administrator) and application control that stops Office from starting script interpreters would have broken the WS-104 chain early.

## Best practices

- Start every Windows case with an inventory and a peer baseline, and record both.
- Name actor and target in every finding ("divya created svc_update"), never just "user".
- Link events by Logon ID when the source provides it; say when you could not.
- Analyse in UTC; give local time in parentheses for people.
- Keep a short list of your estate's "never normal" events (1102 on workstations, accounts created outside IT) and review it each quarter.

## Key takeaways

- Event analysis is a method: question, inventory, baseline, deviation, chain, absence, context. Skipped steps cause most analytical errors.
- Normal is local. Measure it by stacking event IDs and field values across peers before calling anything unusual.
- Read every account in its role: Subject is the actor; in a 4732 the target is the group and the member is the account added.
- Classify logon failures by shape (accounts, sources, timing, status, outcome). A success after a spray is the incident.
- Meaning lives in chains. On WS-104, process execution, account creation, privilege grant and log clearing, each explainable alone, form one story together.
- Absence of events is evidence only when collection is known to be healthy; say so in the case.
