## Introduction and conceptual foundation

In a data centre, changing the infrastructure means touching it: racking a server, patching a cable, logging on to a switch console. In a public cloud, every change is an **API call**. Creating a virtual machine, opening a firewall port, making a storage bucket public, granting a user administrator rights, even turning logging off: each is a request to the provider's management interface, authenticated as some identity, and the provider can record every one. Cloud audit logs are those records. For a SOC they are a gift and a trap at the same time. A gift, because no on-premises environment has ever offered such a complete, centrally recorded history of who changed what. A trap, because much of it is not collected by default, it is spread across accounts, subscriptions, projects and regions, and an attacker who obtains the right identity can try to switch it off.

The previous lesson treated identity logs: who authenticated, how and from where. Cloud logs continue that story, because in the cloud identity *is* the perimeter. A stolen access key or a hijacked administrator session does not need malware to cause damage; it needs only API calls, and those calls are visible only in the cloud provider's logs. MITRE ATT&CK reflects this with techniques such as **T1078.004 Valid Accounts: Cloud Accounts** and **T1562.008 Impair Defenses: Disable or Modify Cloud Logs**, the second of which describes exactly the attacker who stops the trail before acting.

This lesson covers the three providers a SOC analyst is most likely to meet: **Amazon Web Services (AWS) CloudTrail**, **Microsoft Azure's Activity Log and resource logs** together with the Entra ID logs that govern access to Azure, and **Google Cloud's Cloud Audit Logs**. The aim is not to memorise every console screen, which change often, but to understand the stable concepts: control plane versus data plane, what is on by default and what must be enabled, how long the provider keeps it, which fields answer the investigator's questions, and which events should always raise an alert.

> [!NOTE]
> The Banyan Microfinance dataset used in this course has no cloud sources at all. That is deliberate and realistic: many small organisations run SaaS and some cloud workloads without sending a single cloud audit record to their SIEM. Part of this lesson's lab is recognising that gap.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Control plane | The management interface of a cloud service: requests that create, configure, change or delete resources and permissions. |
| Data plane | Operations on the content or function of a resource, such as reading an object from a bucket, querying a database or invoking a function. |
| Management event (AWS) | A CloudTrail record of a control-plane operation. |
| Data event (AWS) | A CloudTrail record of a data-plane operation, such as S3 object reads and writes; not recorded by default. |
| Trail (AWS) | A CloudTrail configuration that delivers events continuously to an S3 bucket (and optionally to CloudWatch Logs). An organisation trail covers every account in an AWS Organization. |
| Activity Log (Azure) | The subscription-level record of control-plane operations on Azure resources. |
| Resource logs (Azure) | Per-resource logs of data-plane and service-specific activity, collected only when a diagnostic setting sends them somewhere. |
| Diagnostic setting (Azure) | A configuration that routes a log category to a Log Analytics workspace, a storage account or an Event Hub. |
| Cloud Audit Logs (Google Cloud) | Google Cloud's audit records, in four types: Admin Activity, Data Access, System Event and Policy Denied. |
| Principal | The identity that made a request: a user, role, service account, service principal or managed identity. |

## Control plane and data plane

The distinction between control plane and data plane is the single most useful idea for reasoning about cloud logs, because every provider draws the same line and treats the two sides differently.

The **control plane** answers "what was done *to* the environment?" Creating a virtual machine, changing a security group, attaching a policy to a role, creating an access key, deleting a backup vault: these are low in volume, high in security value, and every provider records them by default in some form. If you collect nothing else from a cloud estate, collect this.

The **data plane** answers "what was done *with* the resources?" Reading a file from object storage, a row from a managed database or a secret from a key vault. These operations are high in volume, sometimes enormously so, and providers generally do not record them by default because of the cost and volume. Yet they are where data theft actually happens. An attacker who has read access to a storage bucket full of customer KYC documents need make no control-plane change at all; if data-plane logging is off for that bucket, the exfiltration leaves no trace in the audit logs.

The practical consequence is a deliberate decision, made per resource, about which data-plane logging to enable. A sensible rule is to enable it where the data is sensitive (customer records, financial data, secrets, backups) and accept its absence for low-value or public content. That decision should be written down, because during an incident the first question will be "can we tell whether this bucket was read?"

## AWS CloudTrail

CloudTrail records API activity in an AWS account, whether the request came from the web console, the command-line interface, an SDK or another AWS service.

**What is on by default.** Every account has **Event history**, which shows the last 90 days of management events in each region, viewable and searchable in the console. It requires no configuration, which is why it is so often the only CloudTrail evidence available when an investigation starts. But 90 days is short, it is per region, and it does not include data events.

**Trails.** For continuous collection you create a **trail**, which delivers log files to an S3 bucket, typically every few minutes. A multi-region trail captures every region, including the ones nobody uses, which is where an attacker might start resources hoping no one is looking. An **organisation trail**, created in the management account of an AWS Organization, applies to every member account, so a new account is covered from the moment it is created. Trails can also record **data events** (for example S3 object-level operations or Lambda function invocations) when they are explicitly selected, and **Insights** events that flag unusual API call volumes.

**Integrity.** CloudTrail can produce **log file integrity validation** digest files: hourly files that contain the hashes of the log files delivered and are themselves signed, so that an investigator can later prove whether a log file was modified or deleted after delivery. Enable it, and store the trail's bucket in a separate, locked-down security or log-archive account so that compromise of a workload account does not reach its own audit trail.

**Global services.** Some services, notably IAM and the global STS endpoint, are not regional. Their events are recorded in the US East (N. Virginia) region, `us-east-1`, which surprises analysts who search only the region where the organisation's workloads run. A multi-region trail captures them automatically.

### The anatomy of a CloudTrail record

Each event is a JSON object. The field names are stable and worth knowing exactly:

- `eventTime`: when the request was made, in UTC.
- `eventSource`: the service endpoint, such as `iam.amazonaws.com`, `s3.amazonaws.com` or `ec2.amazonaws.com`.
- `eventName`: the API action, such as `CreateUser`, `PutBucketPolicy` or `ConsoleLogin`.
- `awsRegion`: the region the request was made to.
- `userIdentity`: who made the request. Its `type` is one of values such as `Root`, `IAMUser`, `AssumedRole`, `FederatedUser` or `AWSService`, and it carries an `arn`, the `accountId` and, for temporary credentials, an `accessKeyId` and `sessionContext` showing the role that was assumed and whether MFA was used.
- `sourceIPAddress`: where the request came from; for calls made by AWS services on your behalf it contains the service name rather than an address.
- `userAgent`: the client used, which distinguishes the console, the CLI and particular SDKs.
- `requestParameters` and `responseElements`: what was asked for and what came back (for example the new user's name, or the policy document attached).
- `errorCode` and `errorMessage`: present when the call failed, for example `AccessDenied`. A run of `AccessDenied` errors from one principal across many services is a classic sign of a stolen credential being used to explore what it can do.
- `eventID`, `requestID`, `readOnly`, `eventType` and `recipientAccountId`: identifiers, whether the call only read state, the kind of event (`AwsApiCall`, `AwsConsoleSignIn`, `AwsServiceEvent`) and the account whose resources were affected.

Console sign-ins appear as `eventName` `ConsoleLogin` with `eventType` `AwsConsoleSignIn`; the result is in `responseElements.ConsoleLogin` (`Success` or `Failure`) and whether MFA was used is in `additionalEventData.MFAUsed`. A `ConsoleLogin` success for the `Root` identity type, or with `MFAUsed` set to `No` for an administrator, should always reach an analyst.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure breaks one CloudTrail record into its main fields and labels each with the investigative question it answers. Its purpose is to give the analyst a fixed reading order, so that a dense JSON object becomes a sentence: *who* did *what*, to *which service*, *where*, *when*, *from where*, *with what client*, *with what details* and *with what result*.

**Components.** Nine segments run left to right. **userIdentity** (top label "who", sub-label "type, arn, accountId, sessionContext") is the dark segment, because every judgement about a cloud event begins with the principal. **eventTime** ("when", "UTC, ISO 8601") follows. **eventSource** ("which service", "e.g. iam.amazonaws.com") and **eventName** ("what action", "e.g. CreateAccessKey") are orange because together they name the operation, and most detection rules key on them. **awsRegion** ("where", "global services: us-east-1") is next. **sourceIPAddress** ("from where", "address or AWS service name") and **userAgent** ("with which client", "console, CLI, SDK") describe the origin. **requestParameters / responseElements** ("details", "what was asked, what came back") is the wide blue segment, because its contents vary by API. The last segment, **errorCode** ("result", "absent on success; e.g. AccessDenied"), is red because failures are often the most telling part of an attacker's exploration.

**Relationships and arrows.** There are no arrows; the left-to-right order is the reading order. The segment widths are not byte sizes: the details segment is drawn widest because in a real record it is usually the largest and the most variable.

**Execution flow.** An analyst triaging a record reads the identity first (is this a human, a role, a service, root?), then the action and service (is this a high-risk operation?), then the time and origin (is this consistent with that principal's normal behaviour?), then the details (what exactly changed?) and finally the result (did it work?).

**Decision logic.** Two segments decide the most common branches. If `errorCode` is present, the action did not happen, but the attempt still reveals intent and capability. If `userIdentity.type` is `AssumedRole`, the real actor is one step back: `sessionContext` names the role and the session, and the analyst must find the earlier `AssumeRole` event to see who obtained that session.

**Technical interpretation.** CloudTrail records the API request at the service boundary. That is why it can record a denied request: the service received and evaluated it. It is also why `sourceIPAddress` can be an AWS service name, since the request may have been made by a service acting for the principal.

**Practical example.** Suppose a record shows `userIdentity.type` `IAMUser`, `eventSource` `iam.amazonaws.com`, `eventName` `CreateAccessKey`, `sourceIPAddress` 203.0.113.80, `userAgent` showing the CLI, and `requestParameters` naming a different user. Read as a sentence: a long-term IAM user, from an address outside the corporate range, used the CLI to create a new access key for *another* user. That is a persistence technique, and it should be escalated at once.

**Security implications.** Every segment can be used as a detection key, but `eventName` combined with `userIdentity` is the most powerful. Detection rules for trail tampering, new credentials and permission changes all start there.

**Key learning.** Read a cloud audit record as a sentence in a fixed order (who, when, which service, what, where, from where, how, details, result), and always resolve an assumed role back to the identity that assumed it.

### High-signal CloudTrail events

Some API actions are worth an alert almost wherever they occur, because legitimate use is rare and controlled:

| Category | Example `eventName` values | Why it matters |
| --- | --- | --- |
| Logging tampering | `StopLogging`, `DeleteTrail`, `UpdateTrail`, `PutEventSelectors` | An attacker blinding the defenders (T1562.008) |
| Detection tampering | `DeleteDetector` (GuardDuty) | Native threat detection switched off |
| New credentials | `CreateAccessKey`, `CreateLoginProfile`, `CreateUser` | Persistence through a new or second credential |
| Permission changes | `AttachUserPolicy`, `AttachRolePolicy`, `PutUserPolicy`, `PutRolePolicy` | Privilege escalation |
| Data exposure | `PutBucketPolicy`, `PutBucketAcl` | A bucket made readable to others |
| Network exposure | `AuthorizeSecurityGroupIngress` | A port opened to the internet |
| Key destruction | `ScheduleKeyDeletion`, `DisableKey` (KMS) | Data made unrecoverable; part of some ransomware patterns |
| Sign-in | `ConsoleLogin` by `Root`, or without MFA | The most powerful identities used in the weakest way |

## Microsoft Azure: Activity Log, resource logs and Entra ID

Azure splits its audit telemetry along the same control-plane and data-plane line, but with different names and a stronger dependence on configuration.

The **Activity Log** is the control-plane record for a subscription. Each entry records the **operation name** (in the form `Microsoft.<Provider>/<resourceType>/<action>`, such as `Microsoft.Compute/virtualMachines/write` or `Microsoft.Authorization/roleAssignments/write`), the **caller** (a user principal name or the ID of a service principal or managed identity), the **caller IP address**, the **status** of the operation (for example started, succeeded or failed), the **resource ID** affected, a **correlation ID** that groups the entries belonging to one operation, and a **category**. The categories include Administrative (create, update, delete and action operations), Security (alerts from Microsoft Defender for Cloud), Policy, Service Health, Resource Health, Alert, Autoscale and Recommendation. The Activity Log is kept by Azure for 90 days; to keep it longer or analyse it in a SIEM, a **diagnostic setting** must export it to a Log Analytics workspace, a storage account or an Event Hub.

**Resource logs** are the data-plane and service-specific logs of individual resources: Key Vault access to secrets, storage account reads and writes, SQL database auditing, network security group flow information and so on. They are **not collected at all** unless a diagnostic setting is created for each resource or enforced across subscriptions with Azure Policy. A Key Vault with no diagnostic setting will tell you nothing about who read its secrets.

**Entra ID logs** govern access to everything in Azure and Microsoft 365. The sign-in logs and audit logs described in Lesson 3 belong here: an attacker's path into Azure normally begins with an Entra sign-in, and a new role assignment shows up both in Entra audit logs (for directory roles) and in the Activity Log (for Azure resource roles). In a Log Analytics workspace these sources appear as separate tables, `AzureActivity`, `SigninLogs` and `AuditLogs` among them, and Microsoft Sentinel is built on the same workspace.

> [!TIP]
> The operation name pattern makes Azure detections readable. `.../write` creates or changes, `.../delete` removes, `.../action` performs an action. A rule for "any `Microsoft.Authorization/roleAssignments/write` outside the change window" covers every new Azure RBAC grant, whatever the resource.

## Google Cloud: Cloud Audit Logs

Google Cloud records audit events as log entries in Cloud Logging, with the audit details in a structured `protoPayload`. There are four audit log types:

- **Admin Activity**: API calls that modify configuration or metadata. Always written, cannot be disabled, no charge, and retained for 400 days.
- **Data Access**: API calls that read configuration or metadata, and calls that create, modify or read user-provided data. Disabled by default for most services (BigQuery is the well-known exception) because of volume; must be enabled per service, and retained for 30 days by default.
- **System Event**: actions taken by Google systems that modify resources, such as live migration of a VM. Always written.
- **Policy Denied**: requests denied because of a security policy, such as a VPC Service Controls perimeter. Written by default.

The fields analysts use most are `protoPayload.methodName` (the operation, for example `SetIamPolicy`), `protoPayload.serviceName`, `protoPayload.authenticationInfo.principalEmail` (who), `protoPayload.requestMetadata.callerIp` (from where), `protoPayload.resourceName` (what was affected), `protoPayload.authorizationInfo` (which permissions were checked and whether they were granted) and `protoPayload.status` (the result). The entry's `logName` tells you the type: it ends in `cloudaudit.googleapis.com%2Factivity` for Admin Activity and `cloudaudit.googleapis.com%2Fdata_access` for Data Access. To reach a SIEM, logs are routed by a **log sink**, commonly at the organisation level so every project is covered, to Pub/Sub, Cloud Storage or BigQuery.

The names differ but the shape is the same in every provider: an always-on control-plane record kept for a limited time, optional data-plane logs, a separate identity log, and a routing mechanism you must configure to keep anything longer or analyse it centrally.

**Purpose.** The table puts the three providers side by side against the same five questions, so that an analyst who knows one platform can find the equivalent log in another. It also makes visible the single most important operational fact about cloud logs: what you get without doing anything.

**Components.** The columns are **Question**, **AWS**, **Azure** and **Google Cloud**. The rows are the five questions. **Control plane** maps to "CloudTrail management events", "Activity Log" and "Admin Activity audit logs". **Data plane** maps to "CloudTrail data events", "Resource logs (diagnostic settings)" and "Data Access audit logs". **Identity / sign-in** maps to "ConsoleLogin + IAM/STS events", "Entra ID sign-in + audit logs" and "Cloud Identity / Workspace logs". **Default retention** reads "90 days Event history", "90 days Activity Log" and "400 days Admin Activity". **Route to SIEM** reads "Trail to S3 (org trail)", "Diagnostic setting to workspace / Event Hub" and "Log sink to Pub/Sub / Storage". The first two rows are tinted orange and blue to separate the always-valuable control plane from the selectively enabled data plane; the identity row is violet, the retention row red because it is where gaps appear, and the routing row green because it is the fix.

**Relationships and arrows.** There are no arrows; the relationship is horizontal equivalence. Reading a row across tells you, for example, that Azure resource logs are the counterpart of AWS data events and Google Data Access logs, and that all three are off by default for most resources.

**Execution flow.** When onboarding a new cloud environment, work down the table: confirm control-plane collection, decide which data-plane logs to enable, connect the identity logs, note the default retention, and configure the route into the SIEM with longer retention.

**Decision logic.** The data-plane row is the decision row. For each sensitive resource the question is "if this were read by an attacker, would we know?" If the answer is no, the corresponding cell is the setting to change.

**Technical interpretation.** Each provider stores a short, free, built-in history so that every customer has *something*; longer retention, data-plane volume and central analysis are the customer's responsibility under the shared responsibility model.

**Practical example.** A company running one AWS account and one Azure subscription discovers a suspicious IAM change from 120 days ago. Event history and the Activity Log both stop at 90 days, so without a trail and a diagnostic setting configured earlier, the evidence is gone. In India, the CERT-In directions of April 2022 require covered entities, including cloud service providers, to keep logs for 180 days; the default retention in two of the three columns does not meet that on its own.

**Security implications.** Every cell on the routing row is also an attack surface: deleting a trail, removing a diagnostic setting or deleting a sink are all control-plane actions, and should themselves be alerting events.

**Key learning.** All three providers record the control plane by default for a limited time and leave the data plane, long retention and SIEM delivery to you; configure them before you need them.

## Worked example: a coverage check and a first cloud record

### Step 1: what does the SIEM actually hold?

Before reasoning about cloud attacks, check whether you can see the cloud at all. In a copy of the course kit, with the dataset loaded into `minisiem.py` (`LAB_ASSETS/C08/minisiem.py`):

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS n FROM events GROUP BY source ORDER BY n DESC"
source | n

sysmon | 33
windows | 13
vpn | 10
```

Four sources and not one of them is a cloud audit log. If Banyan Microfinance ran its loan-origination application in a cloud account, or used Microsoft 365 for mail, then a change to that environment on 3 November would be invisible to this SOC. The course's own coverage exercise lists "no cloud audit logs" as one of the expected gaps. A gap of this kind should be recorded in the SOC's coverage map (Lesson 7 and Module 6) with an owner and a date, not just noticed.

### Step 2: read one record as a sentence

The record below is **illustrative**: it was written for this lesson to show the field layout, uses the AWS documentation account number `111122223333` and a documentation IP address, and is not output from the lab kit. Imagine Banyan has onboarded one AWS account and its organisation trail now feeds the SIEM.

{
  "eventVersion": "1.08",

    "type": "IAMUser",
    "principalId": "AIDAEXAMPLEPRINCIPAL",

    "accountId": "111122223333",

  "eventTime": "2026-11-03T07:20:00Z",
  "eventSource": "iam.amazonaws.com",
  "eventName": "CreateAccessKey",
  "awsRegion": "us-east-1",
  "sourceIPAddress": "203.0.113.80",
  "userAgent": "aws-cli/2.x",
  "requestParameters": { "userName": "finance-reports" },
  "responseElements": { "accessKey": { "userName": "finance-reports", "status": "Active" } },
  "readOnly": false,
  "eventType": "AwsApiCall",
  "managementEvent": true,
  "recipientAccountId": "111122223333"

Reading it in the order of Figure 1: a long-term IAM user named `ci-deploy`, normally used by the build pipeline, at 07:20 UTC, called IAM, the action `CreateAccessKey`, recorded in `us-east-1` because IAM is a global service, from 203.0.113.80, using the command-line interface, for a *different* user, `finance-reports`, and it succeeded (there is no `errorCode`, and the response shows an active key). Three things are wrong at once. A build identity has no business creating keys for a finance user; the source address is not the build system's; and the action gives whoever holds the new key a second, independent way into the account (persistence through T1098, Account Manipulation). The analyst's next queries follow from the fields: every event for `userIdentity.arn` `ci-deploy` in the last 30 days, every event from `sourceIPAddress` 203.0.113.80, and every event using the new access key ID (which appears in later records' `userIdentity.accessKeyId`).

### Step 3: normalise it alongside everything else

The kit's `LAB_ASSETS/C08/normalise_demo.py` shows how two different raw formats are turned into one schema with Elastic Common Schema field names. Its real output is:

```terminal
$ python normalise_demo.py
{"@timestamp": "2026-11-03T06:46:21Z", "destination.ip": "10.40.0.5", "destination.port": 3389, "event.action": "drop", "event.module": "firewall", "host.name": "fw01", "network.transport": "tcp", "source.ip": "203.0.113.66"}
{"@timestamp": "2026-11-03T06:46:00Z", "event.action": "login", "event.module": "vpn", "event.outcome": "success", "source.ip": "203.0.113.66", "user.name": "gopal"}
```

A CloudTrail record fits the same pattern: `eventTime` becomes `@timestamp`, `eventName` becomes `event.action`, `sourceIPAddress` becomes `source.ip`, the user name from `userIdentity` becomes `user.name`, `userAgent` becomes `user_agent.original`, the presence or absence of `errorCode` sets `event.outcome`, and the account and region go into `cloud.account.id` and `cloud.region` with `cloud.provider` set to `aws`. Once that is done, a single query by `source.ip` finds the address in the firewall, VPN and cloud records together. The original JSON must still be kept, because `requestParameters` and `sessionContext` rarely survive normalisation intact. Lesson 5 discusses field mapping in more depth.

## A practical investigation sequence for cloud events

When an alert or a tip points at a cloud environment, a consistent sequence prevents wasted effort:

1. **Confirm visibility.** Which accounts, subscriptions and projects are logged, since when, and with which data-plane logs? Check for gaps around the time of interest, and check whether logging was changed (`StopLogging`, a deleted diagnostic setting or sink).
2. **Resolve the principal.** Identify the human or workload behind the identity: for an assumed role, find the `AssumeRole` call; for a service principal, find its owner; for a key, find when and by whom it was created.
3. **Bound the activity.** List every action by that principal and from that source address in the window, across all regions.
4. **Separate reads from writes.** Control-plane writes show what changed and must be reverted; reads (and data-plane access where logged) show what may have been exposed.
5. **Check identity logs.** Lesson 3's sign-in logs show how the session was obtained.
6. **Preserve evidence.** Export the relevant records with their hashes before default retention expires (Module 4 covers evidence handling).

## Common mistakes and misconceptions

- **"The provider logs everything."** Control-plane history is kept briefly; data-plane logging is mostly off; nothing reaches the SIEM unless routed.
- **Searching one region.** Attackers use unused regions, and IAM events sit in `us-east-1`.
- **Stopping at the role.** An `AssumedRole` identity is a session, not a person. Follow it back.
- **Ignoring failures.** `AccessDenied` bursts are often the earliest sign of a stolen key being explored.
- **Keeping logs in the account they describe.** An administrator of that account can delete them. Use a separate log-archive account or subscription with restricted access and, for S3, Object Lock.
- **Treating `sourceIPAddress` as always an address.** For service-initiated calls it is a service name.

## Security implications, detection and defence

The detection priorities for cloud logs follow directly from the high-signal table: any change to logging or native threat detection; creation of users, keys and login profiles; policy attachments and role assignments; resources made public; root or break-glass account use; and console sign-ins without MFA. Add behavioural rules: a principal calling services it has never called, a burst of `AccessDenied` across services, and API calls from addresses outside the organisation's known ranges for identities that should only ever be used from inside them. Defences include an organisation-wide trail or equivalent enforced by policy so that new accounts are logged from creation, service control policies or Azure Policy that deny the disabling of logging, short-lived credentials (roles and federation) instead of long-term access keys, MFA for all human access, and a separate security account that holds the logs. Cloud logs record names, addresses and working patterns, so access to them should be restricted and their retention justified under the DPDP Act 2023, while meeting the CERT-In 180-day requirement where it applies.

## Best practices

- Enable organisation-level collection in every provider: an organisation trail in AWS, diagnostic settings enforced by Azure Policy, and an organisation-level log sink in Google Cloud.
- Decide data-plane logging per sensitive resource and record the decision.
- Store audit logs in a separate account or subscription with immutability and integrity validation.
- Normalise cloud fields into the SIEM's schema but always keep the raw record.
- Alert on changes to the logging pipeline itself.

## Key takeaways

- In the cloud every change is an API call; audit logs record the principal, action, target, origin and result of each one.
- Distinguish the control plane (on by default, high value) from the data plane (mostly off by default, where data theft happens).
- CloudTrail Event history keeps 90 days of management events; trails, data events and integrity validation must be configured. Azure's Activity Log keeps 90 days; resource logs need diagnostic settings. Google's Admin Activity logs are always on for 400 days; Data Access logs are mostly off.
- Read a record as a sentence in a fixed order, resolve assumed roles to the real identity, and never ignore failed calls.
- The logging pipeline is itself a target: alert on any attempt to stop, delete or redirect it.
