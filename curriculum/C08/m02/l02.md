## Introduction and conceptual foundation

Lesson 1 looked at telemetry from inside the host: which process ran, what it changed and which account it used. This lesson steps outside the host and looks at the wire. **Network telemetry** is everything the network infrastructure records about communication between systems: which address talked to which, over which protocol and port, for how long, how much data moved, which names were looked up, which web addresses were requested, and whether a security device thought any of it looked malicious.

Network telemetry has three properties that make it indispensable to a SOC, even in an organisation with excellent endpoint logging.

First, it is **independent of the endpoint**. An attacker who has administrative rights on a workstation can stop Sysmon, clear the Security log or tamper with an EDR agent. They cannot, from that workstation, edit the logs kept by the proxy, the firewall or the DNS resolver. Network logs are therefore a second witness, and frequently the one that survives.

Second, it **covers devices that cannot run agents**: printers, cameras, building systems, network appliances, unmanaged personal devices, and machines nobody knew existed. If a device communicates, the network sees it.

Third, almost every intrusion has to **communicate**. Malware must reach its operator (command and control), stolen data must leave (exfiltration), and an attacker moving between machines (lateral movement) creates connections that ordinary users do not. Those communications leave traces at network chokepoints even when their content is encrypted.

The price is that network telemetry rarely tells you *why*. A proxy log shows that workstation WS-104 uploaded 48 megabytes to an unfamiliar domain; it cannot show which process did it or which files were sent. Network and endpoint telemetry answer different questions, and the analyst's skill lies in joining them. This lesson explains what each network source records, where it is collected, what encryption does and does not hide, and how to read network events from the course lab dataset.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| 5-tuple | Source IP, destination IP, source port, destination port and transport protocol: the fields that identify one connection. |
| Firewall log | A record of connections a firewall allowed or denied, usually with the 5-tuple, the rule matched and the action. |
| NAT | Network Address Translation: rewriting addresses (and often ports) as traffic crosses a device, so that many internal hosts share one external address. |
| Web proxy / secure web gateway (SWG) | A device or service that forwards users' web requests and logs each one with URL, user, status, bytes and category. |
| DNS query log | A resolver's record of which client asked for which name, the record type, the response code and the answer. |
| Flow record | A summary of one conversation (addresses, ports, protocol, bytes, packets, start and end time) exported by a router, switch or sensor, without payload. |
| NetFlow / IPFIX | Cisco's flow export format (versions 5 and 9 are common) and its IETF-standard successor, IPFIX (RFC 7011). |
| NSM | Network Security Monitoring: passive sensors that record rich protocol metadata, for example Zeek. |
| IDS / IPS | Intrusion Detection / Prevention System: a sensor that matches traffic against signatures or anomalies and raises alerts (for example Suricata or Snort). |
| SNI | Server Name Indication: the host name a TLS client sends in its first handshake message, normally visible on the network. |
| Beaconing | Regular, automated check-ins from an infected host to its controller, typically small and periodic. |
| Egress | Traffic leaving the organisation's network for an external destination. |

## Where network telemetry is collected

Unlike endpoint telemetry, which every host produces about itself, network telemetry is produced only where a device or sensor can **observe** traffic. Choosing those observation points, usually called **vantage points**, is the first design decision, and it determines what can ever be seen.

- **Perimeter (north-south) chokepoints.** The internet firewall and the web proxy sit where internal traffic leaves for the internet. Everything egressing through them can be logged, which makes them the best place to catch command and control and exfiltration. They see nothing of traffic that never leaves the internal network.
- **Internal (east-west) segments.** Traffic between workstations, or from a workstation to a file server or domain controller, never crosses the perimeter. Internal firewalls, switches exporting flow records, and NSM sensors on internal links are needed to see lateral movement.
- **Infrastructure services.** DNS resolvers and DHCP servers are not chokepoints for data, but almost every connection begins with a DNS lookup and every dynamically addressed host gets its address from DHCP. Their logs are small, cheap and extraordinarily useful for attribution.
- **Cloud and remote.** Cloud networks produce their own flow logs (Lesson 4), and remote users may reach the internet directly rather than through the office proxy. A vantage-point design that assumes everyone sits behind the office firewall will miss them.

Sensors that are not inline (an NSM or IDS sensor) receive a copy of traffic from a switch's mirror (SPAN) port or a network tap. Inline devices (firewalls, proxies, IPS) see traffic because it passes through them, which also lets them block it.

## Network telemetry sources

### Firewall logs

A firewall decides, per connection, whether to allow or deny it according to its rule base, and can log that decision. A typical firewall log entry carries the timestamp, the device name, the action (allow, deny, drop, reject), the 5-tuple, the interface or zone, the rule that matched, and for allowed connections often bytes and duration when the session ends. Next-generation firewalls add application identification and the user, if they are integrated with the directory.

The course lab kit includes one raw firewall line, in `LAB_ASSETS/C08/normalise_demo.py`, in the style of a Linux netfilter log written through syslog:

```text
Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389
```

Read it field by field: `Nov  3 12:16:21` is a syslog timestamp with no year and no time zone (the kit treats it as IST, a problem Lesson 6 takes apart); `fw01` is the device; `kernel:` shows the log came from the kernel's packet filter; `DROP` is the action; `IN=eth0` is the interface the packet arrived on; `SRC` and `DST` are the source and destination addresses; `PROTO=TCP` is the transport; `DPT=3389` is the destination port, Remote Desktop. An external address attempting RDP to an internal host and being dropped is a common sight; its value increases sharply when the same source address appears elsewhere, as `203.0.113.66` does in the lab's VPN log (Lesson 3).

Two limitations matter. Denied connections are usually logged, but many organisations log **allowed** connections only partially because of volume, which removes exactly the evidence of an attack that succeeded. And where the firewall performs NAT, the address recorded on the outside is the shared external address; identifying the internal host requires the firewall's translation log or its pre-NAT fields.

### Web proxy and secure web gateway logs

Most user web traffic leaves an organisation through a web proxy or a cloud secure web gateway. Because the proxy handles each HTTP request on the user's behalf, it can record far more than a firewall: the full URL (or, for TLS that is not inspected, the destination host name and port from the `CONNECT` request), the HTTP method, the response status, bytes sent and received, the user agent, the content type, a URL category, the verdict of any malware or reputation check, and the authenticated user if the proxy requires authentication.

Proxy logs are usually the **largest** security log source by volume, and in the lab dataset they make up 284 of 340 events. They are the primary place to find phishing link clicks, malicious downloads, command-and-control traffic over HTTPS and uploads to file-sharing sites. Their main blind spot is anything that does not use the proxy: non-web protocols, devices configured to go direct, and remote users off the corporate network unless a cloud gateway follows them.

Whether a proxy can see full URLs inside HTTPS depends on **TLS inspection**. An inspecting proxy terminates the user's TLS session with a certificate the organisation's devices trust, inspects the request, and opens a second TLS session to the real server. This gives full visibility, but it is a significant privacy, legal and technical decision: banking, health and similar categories are normally exempted, and some applications break when inspected.

### DNS logs

Before a client connects to `cdn-telemetry-sync.example`, it usually asks a DNS resolver for the name's address. A resolver configured to log queries records the client address, the queried name, the record type (A, AAAA, MX, TXT and so on), the response code (NOERROR, NXDOMAIN for a name that does not exist, SERVFAIL) and often the answer. DNS logs are valuable because they reveal the **names** a host is trying to reach even when the subsequent connection is encrypted or uses a protocol the proxy never sees. Bursts of NXDOMAIN responses for random-looking names, very long query names, or unusually many TXT queries are classic indicators of malware using algorithmically generated domains or DNS tunnelling.

DNS logging has its own gaps. A client that uses an external resolver directly, or encrypted DNS such as DNS over HTTPS (DoH) to a public provider, bypasses the organisation's resolver and its logs. Many organisations therefore block outbound DNS except from their own resolvers. Sysmon event 22 (Lesson 1) complements resolver logs by tying each query to the process that made it.

### Flow records

A flow record summarises a conversation without its content. Routers, switches, firewalls and dedicated probes export flows in NetFlow (versions 5 and 9 are common), IPFIX (the IETF standard defined in RFC 7011) or vendor equivalents such as sFlow, which samples packets rather than tracking every flow. A flow record holds the 5-tuple, start and end times, byte and packet counts and, depending on the exporter, TCP flags and interface identifiers.

Flows are compact, cheap to keep for months and available almost anywhere in the network, including internal segments. They answer "who talked to whom, when, and how much?": an internal workstation connecting to dozens of other workstations on port 445, or a server sending an unusual volume to an external address at 03:00, stand out in flow data even without any payload. Their limitation is the mirror image of their strength: no URLs, no names, no content, and, if sampling is used, no guarantee that a short connection was recorded at all.

### Network security monitoring, IDS and packet capture

Passive sensors on a SPAN port or tap can record much richer metadata than flows. **Zeek**, the widely used open-source NSM tool, writes one log per protocol: `conn.log` (every connection, like a detailed flow record), `dns.log`, `http.log`, `ssl.log` (TLS handshakes, including the server name), `x509.log` (certificates) and `files.log` (files seen in transfer, with hashes), among others. Each connection receives a unique identifier (`uid`) that links its entries across these logs.

**IDS** sensors such as Suricata and Snort match traffic against signatures and raise alerts that name the rule, its identifier and the 5-tuple; Suricata can also write protocol metadata similar to Zeek's. Alerts are not raw telemetry: they are detections produced by someone else's logic, and they need the same validation as any SIEM alert (Module 4).

**Full packet capture** records the traffic itself. It is the ultimate evidence for what crossed the wire, but it is expensive to store, usually kept for days rather than months, captures personal data wholesale, and is of limited use for encrypted traffic. SOCs therefore capture selectively, at key points or on demand during an investigation.
