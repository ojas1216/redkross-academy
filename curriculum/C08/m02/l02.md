## Introduction and conceptual foundation

Lesson 1 looked at telemetry from inside the host: which process ran, what it changed and which account it used. This lesson steps outside the host and looks at the wire. **Network telemetry** is everything the network infrastructure records about communication between systems: which address talked to which, over which protocol and port, for how long, how much data moved, which names were looked up, which web addresses were requested, and whether a security device thought any of it looked malicious.

Network telemetry has three properties that make it indispensable to a SOC, even in an organisation with excellent endpoint logging.

First, it is **independent of the endpoint**. An attacker who has administrative rights on a workstation can stop Sysmon, clear the Security log or tamper with an EDR agent. They cannot, from that workstation, edit the logs kept by the proxy, the firewall or the DNS resolver. Network logs are therefore a second witness, and frequently the one that survives.

Second, it **covers devices that cannot run agents**: printers, cameras, building systems, network appliances, unmanaged personal devices, and machines nobody knew existed. If a device communicates, the network sees it.

Third, almost every intrusion has to **communicate**. Malware must reach its operator (command and control), stolen data must leave (exfiltration), and an attacker moving between machines (lateral movement) creates connections that ordinary users do not. Those communications leave traces at network chokepoints even when their content is encrypted.

The price is that network telemetry rarely tells you *why*. A proxy log shows that workstation WS-104 uploaded 48 megabytes to an unfamiliar domain; it cannot show which process did it or which files were sent. Network and endpoint telemetry answer different questions, and the analyst's skill lies in joining them. This lesson explains what each network source records, where it is collected, what encryption does and does not hide, and how to read network events from the course lab dataset.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| 5-tuple | Source IP, destination IP, source port, destination port and transport protocol: the fields that identify one connection. |
| Firewall log | A record of connections a firewall allowed or denied, usually with the 5-tuple, the rule matched and the action. |
| NAT | Network Address Translation: rewriting addresses (and often ports) as traffic crosses a device, so that many internal hosts share one external address. |
| Web proxy / secure web gateway (SWG) | A device or service that forwards users' web requests and logs each one with URL, user, status, bytes and category. |
| DNS query log | A resolver's record of which client asked for which name, the record type, the response code and the answer. |
| Flow record | A summary of one conversation (addresses, ports, protocol, bytes, packets, start and end time) exported by a router, switch or sensor, without payload. |
| NetFlow / IPFIX | Cisco's flow export format (versions 5 and 9 are common) and its IETF-standard successor, IPFIX (RFC 7011). |
| NSM | Network Security Monitoring: passive sensors that record rich protocol metadata, for example Zeek. |
| IDS / IPS | Intrusion Detection / Prevention System: a sensor that matches traffic against signatures or anomalies and raises alerts (for example Suricata or Snort). |
| SNI | Server Name Indication: the host name a TLS client sends in its first handshake message, normally visible on the network. |
| Beaconing | Regular, automated check-ins from an infected host to its controller, typically small and periodic. |
| Egress | Traffic leaving the organisation's network for an external destination. |

## Where network telemetry is collected

Unlike endpoint telemetry, which every host produces about itself, network telemetry is produced only where a device or sensor can **observe** traffic. Choosing those observation points, usually called **vantage points**, is the first design decision, and it determines what can ever be seen.

- **Perimeter (north-south) chokepoints.** The internet firewall and the web proxy sit where internal traffic leaves for the internet. Everything egressing through them can be logged, which makes them the best place to catch command and control and exfiltration. They see nothing of traffic that never leaves the internal network.
- **Internal (east-west) segments.** Traffic between workstations, or from a workstation to a file server or domain controller, never crosses the perimeter. Internal firewalls, switches exporting flow records, and NSM sensors on internal links are needed to see lateral movement.
- **Infrastructure services.** DNS resolvers and DHCP servers are not chokepoints for data, but almost every connection begins with a DNS lookup and every dynamically addressed host gets its address from DHCP. Their logs are small, cheap and extraordinarily useful for attribution.
- **Cloud and remote.** Cloud networks produce their own flow logs (Lesson 4), and remote users may reach the internet directly rather than through the office proxy. A vantage-point design that assumes everyone sits behind the office firewall will miss them.

Sensors that are not inline (an NSM or IDS sensor) receive a copy of traffic from a switch's mirror (SPAN) port or a network tap. Inline devices (firewalls, proxies, IPS) see traffic because it passes through them, which also lets them block it.

## Network telemetry sources

### Firewall logs

A firewall decides, per connection, whether to allow or deny it according to its rule base, and can log that decision. A typical firewall log entry carries the timestamp, the device name, the action (allow, deny, drop, reject), the 5-tuple, the interface or zone, the rule that matched, and for allowed connections often bytes and duration when the session ends. Next-generation firewalls add application identification and the user, if they are integrated with the directory.

The course lab kit includes one raw firewall line, in `LAB_ASSETS/C08/normalise_demo.py`, in the style of a Linux netfilter log written through syslog:

```text
Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389
```

Read it field by field: `Nov  3 12:16:21` is a syslog timestamp with no year and no time zone (the kit treats it as IST, a problem Lesson 6 takes apart); `fw01` is the device; `kernel:` shows the log came from the kernel's packet filter; `DROP` is the action; `IN=eth0` is the interface the packet arrived on; `SRC` and `DST` are the source and destination addresses; `PROTO=TCP` is the transport; `DPT=3389` is the destination port, Remote Desktop. An external address attempting RDP to an internal host and being dropped is a common sight; its value increases sharply when the same source address appears elsewhere, as `203.0.113.66` does in the lab's VPN log (Lesson 3).

Two limitations matter. Denied connections are usually logged, but many organisations log **allowed** connections only partially because of volume, which removes exactly the evidence of an attack that succeeded. And where the firewall performs NAT, the address recorded on the outside is the shared external address; identifying the internal host requires the firewall's translation log or its pre-NAT fields.

### Web proxy and secure web gateway logs

Most user web traffic leaves an organisation through a web proxy or a cloud secure web gateway. Because the proxy handles each HTTP request on the user's behalf, it can record far more than a firewall: the full URL (or, for TLS that is not inspected, the destination host name and port from the `CONNECT` request), the HTTP method, the response status, bytes sent and received, the user agent, the content type, a URL category, the verdict of any malware or reputation check, and the authenticated user if the proxy requires authentication.

Proxy logs are usually the **largest** security log source by volume, and in the lab dataset they make up 284 of 340 events. They are the primary place to find phishing link clicks, malicious downloads, command-and-control traffic over HTTPS and uploads to file-sharing sites. Their main blind spot is anything that does not use the proxy: non-web protocols, devices configured to go direct, and remote users off the corporate network unless a cloud gateway follows them.

Whether a proxy can see full URLs inside HTTPS depends on **TLS inspection**. An inspecting proxy terminates the user's TLS session with a certificate the organisation's devices trust, inspects the request, and opens a second TLS session to the real server. This gives full visibility, but it is a significant privacy, legal and technical decision: banking, health and similar categories are normally exempted, and some applications break when inspected.

### DNS logs

Before a client connects to `cdn-telemetry-sync.example`, it usually asks a DNS resolver for the name's address. A resolver configured to log queries records the client address, the queried name, the record type (A, AAAA, MX, TXT and so on), the response code (NOERROR, NXDOMAIN for a name that does not exist, SERVFAIL) and often the answer. DNS logs are valuable because they reveal the **names** a host is trying to reach even when the subsequent connection is encrypted or uses a protocol the proxy never sees. Bursts of NXDOMAIN responses for random-looking names, very long query names, or unusually many TXT queries are classic indicators of malware using algorithmically generated domains or DNS tunnelling.

DNS logging has its own gaps. A client that uses an external resolver directly, or encrypted DNS such as DNS over HTTPS (DoH) to a public provider, bypasses the organisation's resolver and its logs. Many organisations therefore block outbound DNS except from their own resolvers. Sysmon event 22 (Lesson 1) complements resolver logs by tying each query to the process that made it.

### Flow records

A flow record summarises a conversation without its content. Routers, switches, firewalls and dedicated probes export flows in NetFlow (versions 5 and 9 are common), IPFIX (the IETF standard defined in RFC 7011) or vendor equivalents such as sFlow, which samples packets rather than tracking every flow. A flow record holds the 5-tuple, start and end times, byte and packet counts and, depending on the exporter, TCP flags and interface identifiers.

Flows are compact, cheap to keep for months and available almost anywhere in the network, including internal segments. They answer "who talked to whom, when, and how much?": an internal workstation connecting to dozens of other workstations on port 445, or a server sending an unusual volume to an external address at 03:00, stand out in flow data even without any payload. Their limitation is the mirror image of their strength: no URLs, no names, no content, and, if sampling is used, no guarantee that a short connection was recorded at all.

### Network security monitoring, IDS and packet capture

Passive sensors on a SPAN port or tap can record much richer metadata than flows. **Zeek**, the widely used open-source NSM tool, writes one log per protocol: `conn.log` (every connection, like a detailed flow record), `dns.log`, `http.log`, `ssl.log` (TLS handshakes, including the server name), `x509.log` (certificates) and `files.log` (files seen in transfer, with hashes), among others. Each connection receives a unique identifier (`uid`) that links its entries across these logs.

**IDS** sensors such as Suricata and Snort match traffic against signatures and raise alerts that name the rule, its identifier and the 5-tuple; Suricata can also write protocol metadata similar to Zeek's. Alerts are not raw telemetry: they are detections produced by someone else's logic, and they need the same validation as any SIEM alert (Module 4).

**Full packet capture** records the traffic itself. It is the ultimate evidence for what crossed the wire, but it is expensive to store, usually kept for days rather than months, captures personal data wholesale, and is of limited use for encrypted traffic. SOCs therefore capture selectively, at key points or on demand during an investigation.

**Purpose.** The figure shows the path a workstation's traffic takes to the internet and to internal servers, and marks the device at each point that writes network telemetry. It matters because the logs available in an investigation are decided by where sensors were placed long before the incident.

**Components.** **Workstation WS-104** ("10.40.0.23, finance") is the client. **DNS resolver** ("query logs: client, name, type, rcode") and **DHCP server** ("lease logs: IP to host over time") are infrastructure services. **Web proxy / SWG** ("URL, user, status, bytes") handles web requests. **Perimeter firewall** ("5-tuple, action, rule, NAT") is the boundary to the slate **Internet** box ("203.0.113.0/24 and other external hosts"). **Internal file server** ("east-west destination") represents traffic that never leaves the network. **NSM / IDS sensor** ("Zeek logs, Suricata alerts") watches a mirrored copy of traffic, and **Flow exporter** ("switch / router: NetFlow, IPFIX") summarises conversations. All of them feed the dark **SIEM** box.

**Relationships and arrows.** Solid arrows from the workstation show traffic: "name lookup" to the resolver, "HTTP(S) requests" to the proxy, "SMB (port 445)" to the file server. The proxy forwards to the firewall ("egress"), and the firewall to the internet. The dashed arrow labelled "SPAN / tap copy" from the firewall to the NSM sensor shows that the sensor observes a copy rather than sitting inline. Each telemetry device has a "logs" arrow to the SIEM.

**Execution flow.** A typical web request runs left to right: the workstation resolves the name (DNS log), sends the request to the proxy (proxy log), the proxy's connection leaves through the firewall (firewall log, flow record), and the sensor records the session metadata (Zeek `conn.log` and `ssl.log`).

**Decision logic.** Two branches matter. A request that bypasses the proxy, for example a non-web protocol, appears only in firewall and flow logs. Traffic to the internal file server never reaches the proxy or the perimeter firewall, so only flow records, an internal sensor or the endpoint can see it.

**Technical interpretation.** Each hop sees a different identity for the same client: the proxy sees the internal address and possibly the user; the firewall, after NAT, may log only the shared external address; DHCP logs tie the internal address to a host name for a period of time. Correlation across the boxes is how an external observation is traced back to one machine.

**Practical example.** In the lab dataset, Banyan Microfinance collects only the proxy box: WS-104's requests appear with `src_ip` 10.40.0.23. The firewall line in `normalise_demo.py` illustrates the firewall box. There is no DNS, DHCP, flow or sensor data, so the beacon to `cdn-telemetry-sync.example` can be seen only because it travelled through the proxy.

**Security implications.** Attackers prefer paths that defenders do not observe: direct-to-internet protocols, encrypted DNS and internal movement. Vantage-point coverage should be reviewed against those paths, and egress that bypasses the proxy should be blocked or at least logged at the firewall.

**Key learning.** Every network log is a view from one vantage point; know which points you collect from, and which paths avoid them.

## What encryption hides and what it does not

Most traffic today is encrypted with TLS, and analysts sometimes conclude that network telemetry has become useless. It has not. Encryption hides **content**: the body of a web page, the parameters of an API call, the file being uploaded. It does not hide most **metadata**:

- **Who and where**: source and destination addresses and ports are visible to every device on the path.
- **Names**: the DNS query that preceded the connection, and the SNI host name in the TLS ClientHello, normally reveal the destination's name. (Encrypted Client Hello, where both sides support it, conceals the real SNI; encrypted DNS hides the query from network resolvers.)
- **Certificates**: in TLS 1.2 the server certificate is visible on the wire; in TLS 1.3 it is encrypted, though the SNI still usually identifies the destination.
- **Timing and volume**: when connections happen, how often, how long they last and how many bytes move in each direction.

Timing and volume alone are enough for two of the most important network detections. **Beaconing** shows as connections at regular intervals with near-identical sizes, which human browsing never produces. **Exfiltration** shows as an unusually large volume *sent* from an internal host to an external destination, which is the reverse of the usual pattern where clients mostly download.

## Attribution: from an address to a machine and a person

Network logs identify endpoints by IP address, and IP addresses are not identities. An analyst who sees a suspicious connection from `10.40.0.23` must establish which machine held that address **at that time** (DHCP lease logs, or the proxy's host field if it records one) and which user was logged on to it (endpoint logon events from Lesson 1, or the proxy's authenticated user). The same field name can also mean different things in different sources: in the lab's proxy events `src_ip` is the internal workstation; in its VPN events `src_ip` is the user's external address. Lesson 5 returns to this pitfall.

## Worked example: proxy telemetry in the lab dataset

Work in your own copy of `LAB_ASSETS/C08/`, after `python minisiem.py load` (Lesson 1). Each proxy event in `banyan_events.jsonl` carries `host`, `user`, `src_ip`, `url`, `status` and `bytes_out` (bytes sent by the client). Real gateways record more, such as method, bytes received, user agent and category; the lab keeps the fields the detections need.

### Volume per host

```terminal
$ python minisiem.py search "SELECT host, COUNT(*) n, COUNT(DISTINCT url) urls FROM events WHERE source='proxy' GROUP BY host ORDER BY n DESC LIMIT 3"
host | n | urls
WS-104 | 49 | 9
WS-108 | 40 | 6
WS-103 | 37 | 6
```

WS-104 is the busiest host and the only one in the top three that reached more than the six routine sites. Volume alone proves nothing, since a busy user is not a suspect, but three extra destinations are worth a look.

### Rarity: destinations by number of hosts

```terminal
$ python minisiem.py search "SELECT url, COUNT(*) hits, COUNT(DISTINCT host) hosts, SUM(bytes_out) total_out FROM events WHERE source='proxy' GROUP BY url ORDER BY hosts, hits"
url | hits | hosts | total_out
https://banyan-payroll-update.example/invoice.docm | 1 | 1 | 812
https://files-share-drop.example/upload | 1 | 1 | 48200000
https://cdn-telemetry-sync.example/api/v2/ping | 18 | 1 | 3960
https://crm.banyan.example/ | 37 | 8 | 72210
https://intranet.banyan.example/ | 37 | 8 | 79335
https://maps.example.net/ | 45 | 8 | 98467
https://cdn.example.org/ | 46 | 8 | 92774
https://news.example.com/ | 48 | 8 | 109424
https://mail.banyan.example/ | 51 | 8 | 103134
```

This is stacking (Lesson 1) applied to destinations. Six URLs are visited by all eight hosts; three are visited by one host only, and all three are WS-104's. Each tells a different story. `banyan-payroll-update.example/invoice.docm` imitates the company's own name and serves a macro-enabled Word document: the phishing download, at 06:12, two minutes before Word started PowerShell in Lesson 1. `cdn-telemetry-sync.example/api/v2/ping` has a harmless-sounding name but 18 hits of exactly 220 bytes (18 x 220 = 3,960). `files-share-drop.example/upload` received 48,200,000 bytes in one request, more than all the routine traffic of the whole company combined.

### Timing: is it a beacon?

The lab's rule R6 (`beacon_regular_small` in `minisiem.py`) groups proxy events by host and URL and fires when there are at least 10 hits whose sizes differ by less than 50 bytes. Running `python minisiem.py rules` prints, among the other rules:

```terminal
R6 beacon_regular_small: 1 hit(s)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

The tuple is host, URL, hits, minimum and maximum `bytes_out`. Size regularity is half the definition; timing is the other half. The kit's `hunt.py` computes the gaps between consecutive requests and their coefficient of variation (standard deviation divided by the mean; near 0 means machine-regular). Its saved output (`hunt_output.txt`) reads:

```text
H1 beaconing candidates (>= 8 requests, interval CV < 0.2)
  WS-104 https://cdn-telemetry-sync.example/api/v2/ping n=18 mean_gap=300s cv=0.004
```

A mean gap of 300 seconds with a CV of 0.004 means a check-in every five minutes, varying by a few seconds. The first request is at 06:17:00 and the last at 07:42:02. People do not browse like this; software on a timer does.

**Execution flow.** Read left to right: routine mail and intranet requests just after 06:00; the download at 06:12; the beacon starting at 06:17 and ticking every five minutes until 07:42; scattered routine browsing throughout; the upload at 08:12.

**Decision logic.** The analyst's question for each row is "regular or irregular, common or rare?" The routine row is irregular and common, which is how people behave. The beacon row is regular and rare, the signature of automation to an unknown destination. The bottom row is rare and singular, so it is judged by content type and size: a macro document arriving, a large volume leaving.

**Technical interpretation.** Because the proxy logs every request, the beacon is visible even though the dataset holds no payload. If the beacon had used jitter (random variation in the interval) the CV would rise, which is why hunts use a threshold (`cv < 0.2` in `hunt.py`) rather than demanding perfect regularity.

**Practical example.** Combined with Lesson 1's endpoint table, the timeline gives a joint story on WS-104: download at 06:12, Word starts PowerShell at 06:14, beaconing from 06:17, new administrator at 07:02-07:03, upload at 08:12, log cleared at 08:17. Neither source alone tells it.

**Security implications.** Exfiltration and command and control were visible only because egress went through a logging proxy. Rules such as R4 (`large_upload`, `bytes_out` over 10,000,000) and R6 turn these patterns into alerts.

**Key learning.** Encrypted traffic still has a rhythm and a size; regular small requests suggest a beacon, and an outsized upload suggests exfiltration.

## Common mistakes and misconceptions

- **"Encryption makes network logs useless."** Content is hidden; addresses, names, timing and volume usually are not, and they power beacon and exfiltration detection.
- **"An IP address is a host."** Addresses are reassigned by DHCP and hidden by NAT. Attribute with lease logs and endpoint logons for the exact time.
- **"The firewall logs everything."** Many firewalls log allowed traffic only partially, and nothing internal crosses the perimeter firewall.
- **"High volume means suspicious."** WS-104 was busiest, but the evidence was in rare destinations and regular timing, not raw counts.
- **"An IDS alert is a fact."** It is someone else's detection logic and needs validation like any alert.

## Security implications, detection and defence

- **Force egress through logging points.** Block direct outbound web and DNS from workstations so that the proxy and resolvers see everything.
- **Detect on metadata.** Alert on first-seen or rare domains, look-alike names of your own brand, periodic small connections and large outbound transfers.
- **Correlate with the endpoint.** A network anomaly becomes an incident when it is tied to a process and user (Sysmon events 3 and 22, EDR).
- **Protect the logs.** Proxy, firewall and DNS logs should be forwarded centrally and kept beyond the attacker's reach.

> [!IMPORTANT]
> Proxy and DNS logs reveal browsing habits and are personal data under India's DPDP Act 2023. TLS inspection and packet capture need a documented purpose, exemptions for sensitive categories and restricted access. CERT-In's April 2022 directions require ICT system logs to be maintained for a rolling 180 days within India; agree retention with legal and compliance.

## Best practices

- Collect proxy, DNS resolver, firewall (allowed and denied) and DHCP logs as a minimum network set.
- Add flow records or an NSM sensor on internal segments to see lateral movement.
- Record the authenticated user in proxy logs wherever possible.
- Keep all network devices on synchronised time (NTP) and log in UTC.
- Review vantage points whenever remote working, cloud or network design changes.

## Key takeaways

- Network telemetry is an independent second witness: firewall, proxy, DNS, DHCP, flow, NSM/IDS and packet capture each record a different view.
- What you can see depends on vantage points; perimeter devices miss internal movement, and traffic that bypasses the proxy or resolver is invisible to them.
- Encryption hides content but not addresses, names, timing or volume, which are enough to detect beaconing and exfiltration.
- Attributing an address to a host and user needs DHCP and endpoint evidence for the exact time.
- In the lab, three single-host destinations on WS-104 (a look-alike download, a 300-second 220-byte beacon and a 48.2 MB upload) complete the endpoint story from Lesson 1.
