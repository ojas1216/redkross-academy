## Introduction and conceptual foundation

Module 1 described the SOC as an organisation that turns alerts into decisions. Every one of those alerts starts as a record that some system wrote about itself. This module is about those records, which security operations calls **telemetry**: the data that systems emit about what they are doing. A SOC can only detect, investigate and prove what its telemetry recorded. If a process ran, a file was written or an account was created and nothing logged it, no amount of analyst skill will recover the fact later.

This lesson starts with the place where most intrusions actually happen: the **endpoint**. An endpoint is any computer that runs an operating system on behalf of a user or a service: laptops and desktops, servers, virtual machines and, increasingly, cloud workloads. Attackers can arrive by e-mail, a web page, a stolen password or a vulnerable service, but in almost every case they eventually need to *run something* on a machine, *change something* on it, or *use an account* on it. Endpoint telemetry is the record of exactly those three things: processes, changes and logons.

Endpoint telemetry has a special quality that the network and identity sources in the next two lessons lack. It sees activity **from inside the host**, after decryption and before any obfuscation can be removed by the network. A proxy log can tell you that a workstation downloaded a document from a strange domain; only the endpoint can tell you that, two minutes later, the word processor that opened the document started a hidden PowerShell process. That parent-child relationship is the single most valuable fact in this module's lab dataset, and it exists only in endpoint telemetry.

The cost of that view is volume. A busy workstation can generate thousands of events an hour if everything is switched on, most of them normal. An analyst rarely configures the logging, but must know what a given log *can* and *cannot* prove, and notice when something that should be there is missing.

> [!NOTE]
> This lesson covers what endpoint sources record and how to read them. Lesson 5 goes deeper into event fields and identifiers, Lesson 6 into timestamps, Lesson 7 into how events are collected and shipped, and Module 4 into detailed Windows and Linux log analysis.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Endpoint | A host running an operating system: workstation, laptop, server, virtual machine or cloud instance. |
| Telemetry | Data a system emits about its own activity, collected for monitoring and investigation. |
| Event log | A structured record of events kept by the operating system; on Windows, organised into channels such as Security, System and Application. |
| Event ID | The numeric identifier of an event type within a provider, for example 4624 (successful logon) in the Windows Security log. |
| Audit policy | The Windows setting that decides which security-relevant actions are written to the Security log. |
| Sysmon | System Monitor, a free Microsoft Sysinternals driver and service that records detailed process, network, file and registry activity to its own event channel. |
| Process creation event | A record that a new process started, ideally with its image path, command line, user and parent process. |
| Parent process | The process that started another process; the parent-child chain shows how an action came about. |
| Command line | The full text used to start a process, including its arguments. |
| ProcessGuid | Sysmon's unique identifier for one process instance; unlike a process ID, it is not reused. |
| EDR | Endpoint Detection and Response: a commercial agent that collects endpoint telemetry, detects threats and can act on the host. |
| auditd | The Linux audit daemon, which writes kernel audit records (for example of executed programs) according to configured rules. |

## The endpoint as an evidence source

It helps to think of an endpoint as producing four kinds of evidence, each answering a different investigative question.

**Execution: what ran?** Process creation records tell you which program started, when, as which user, from which parent, and with which arguments. Execution is the backbone of endpoint investigation because nearly every attacker action, from opening a malicious document to running a discovery command, is a process starting.

**Change: what was modified?** File creation, registry modification, service installation, scheduled task creation and account changes record the attacker's attempts to stay (persistence), to gain rights (privilege escalation) or to weaken defences. A change is often what turns a suspicious event into a confirmed incident, because it leaves something behind that has to be cleaned up.

**Access: who logged on, and how?** Logon and logoff events, privilege assignments and failed logons tell you which accounts used the machine, from where, and by which method (at the keyboard, over the network, over Remote Desktop). These overlap with the identity telemetry of Lesson 3, but the endpoint is where the logon actually takes effect.

**Defence: what did the protections see and do?** Anti-malware detections, EDR alerts, and the health of the logging itself (for example a cleared log) tell you whether the host's controls noticed something and whether anyone has tampered with them.

The rest of this lesson takes the sources that answer these questions one at a time.

## Windows event logs

Windows records events through the **Windows Event Log** service. Events are grouped into **channels**. The three classic channels are **Security**, **System** and **Application**; under "Applications and Services Logs" sit many more, each owned by a component (for example `Microsoft-Windows-PowerShell/Operational` and `Microsoft-Windows-Sysmon/Operational`). Each event has a provider, an event ID, a timestamp, a computer name, a level and a set of named data fields specific to that event type.

### The Security log and audit policy

The Security log is the most important built-in source for a SOC, and also the most misunderstood, because **what it contains depends entirely on the audit policy**. Windows does not log every security-relevant action by default; an administrator decides, usually through Group Policy's Advanced Audit Policy Configuration, which subcategories (logon, process creation, account management, and so on) are audited for success, failure or both. Two machines running the same version of Windows can therefore produce very different Security logs. When an analyst finds "no event", the first question is whether the event would have been audited at all.

The event IDs below are the ones a SOC analyst meets every day. They are stable, documented by Microsoft, and form the vocabulary of Module 4.

| Event ID | Channel | Meaning | Why the SOC cares |
| --- | --- | --- | --- |
| 4624 | Security | An account successfully logged on | Who used the host; the logon type shows how |
| 4625 | Security | An account failed to log on | Guessing, spraying, or a user's typo; the status code says why |
| 4672 | Security | Special privileges assigned to a new logon | An administrative-level logon |
| 4688 | Security | A new process has been created | Execution record (command line only if enabled) |
| 4697 | Security | A service was installed in the system | Common persistence and lateral movement trace |
| 4698 | Security | A scheduled task was created | Common persistence mechanism |
| 4720 | Security | A user account was created | Possible backdoor account |
| 4732 | Security | A member was added to a security-enabled local group | For example, a new local administrator |
| 1102 | Security | The audit log was cleared | Possible attempt to hide activity |
| 7045 | System | A service was installed | The System-log view of a new service |

Two details on this table deserve emphasis. First, **logon type** in 4624 and 4625 events distinguishes how the logon happened: type 2 is interactive (at the console), type 3 is network (for example accessing a file share), type 10 is RemoteInteractive (Remote Desktop), and type 5 is a service starting. The same account logging on as type 2 at the user's own desk and as type 10 from another workstation at midnight are very different stories. Second, a 4625 carries a **status** (and sub-status) code that explains the failure; `0xC000006A`, for instance, means the user name was valid but the password was wrong. That code is how analysts tell a mistyped password from an attempt against a non-existent account.

### Process creation in the Security log: event 4688

Event 4688 records every new process when the "Audit Process Creation" subcategory is enabled. It names the new process, its creator (parent) process, the account and the token elevation type. Crucially, the **command line is not included unless a separate policy setting is enabled** ("Include command line in process creation events"). Without it, a 4688 for `powershell.exe` tells you that PowerShell ran but not what it was asked to do, which is often the whole question. Many organisations discover this gap only during their first serious incident.

### PowerShell logging

Because PowerShell is both an essential administration tool and a favourite of attackers (MITRE ATT&CK technique T1059.001), Windows provides dedicated logging for it in the `Microsoft-Windows-PowerShell/Operational` channel. **Module logging** (event ID 4103) records pipeline execution details for the modules it is enabled for. **Script block logging** (event ID 4104) records the text of script blocks as PowerShell processes them. Script block logging matters to defenders because it captures code *as it is executed*: a command passed in Base64 with `-EncodedCommand` appears in the process command line as an unreadable string, but the script block that PowerShell actually runs is recorded in readable form. Both are off or limited by default and must be enabled by policy.

## Sysmon: detailed endpoint telemetry

The built-in Security log was designed for auditing, not for threat detection, and it leaves gaps: no network connection details tied to processes, no file hashes, no reliable way to tie a child process to exactly one parent instance. **Sysmon** (System Monitor), part of Microsoft's free Sysinternals suite, fills many of those gaps. It installs as a Windows service and a device driver, survives reboots, and writes its own events to the `Microsoft-Windows-Sysmon/Operational` channel. What it records is controlled by an XML configuration file that includes or excludes events by field values; organisations typically start from a well-maintained community configuration and tune it, because an unfiltered Sysmon produces enormous volume.

The Sysmon event types an analyst meets most often are:

| Sysmon event ID | Records | Typical use |
| --- | --- | --- |
| 1 | Process creation, with command line, hashes, parent and ProcessGuid | Execution and parent-child analysis |
| 3 | Network connection, tied to the process that made it | Which program talked to which address |
| 7 | Image loaded (a DLL loaded into a process) | Suspicious module loading |
| 8 | CreateRemoteThread | A process starting a thread inside another process |
| 10 | Process access | One process opening another, for example reading the memory of the logon process |
| 11 | File create | Dropped files and payloads |
| 12, 13, 14 | Registry object create/delete, value set, key/value rename | Persistence in Run keys and services |
| 22 | DNS query, tied to the process that made it | Which program resolved which name |

Sysmon's process creation event is richer than 4688. Alongside the image path and command line it carries the `User`, `IntegrityLevel`, configured file `Hashes`, `CurrentDirectory`, `OriginalFileName` from the file's version resource (useful when an attacker renames a binary), and the parent's `ParentImage` and `ParentCommandLine`. Most importantly it carries `ProcessGuid` and `ParentProcessGuid`. Windows reuses process IDs quickly, so "process 4312 started process 7720" can be ambiguous across a day; a ProcessGuid identifies exactly one process instance, which makes it the reliable key for joining a process to its network connections, file writes and children.

> [!TIP]
> Sysmon records activity; it does not block anything and it does not raise alerts on its own. It is a sensor. Detection happens later, in the SIEM rules of Module 3 and the detection engineering of Module 7.

## Linux and other endpoint sources

Linux endpoints log differently, but the four evidence questions are the same.

**Authentication logs.** On Debian and Ubuntu systems, authentication events from `sshd`, `sudo`, `su` and PAM are written to `/var/log/auth.log`; on Red Hat-family systems, to `/var/log/secure`. These lines show successful and failed SSH logons with source addresses, `sudo` commands with the invoking user and the command run, and session opening and closing. They are the Linux counterpart of 4624, 4625 and 4672.

**The systemd journal.** `journald` collects service and kernel messages in a structured binary journal, read with `journalctl`; many distributions also forward it to syslog, so an event may appear twice.

**auditd.** The Linux audit framework records kernel-level events according to rules the administrator writes, for example "record every `execve` system call" (every program executed) or "record every write to `/etc/passwd`". Records go to `/var/log/audit/audit.log` and carry the audit user ID (`auid`), which survives `sudo` and `su` and therefore still identifies the human who originally logged in. auditd is the closest Linux equivalent to Sysmon's process creation and file events, and it shares Sysmon's main challenge: badly scoped rules produce far more data than anyone can use.

**EDR agents.** Commercial Endpoint Detection and Response products (on Windows, Linux and macOS) collect much of the same telemetry through their own kernel or operating-system interfaces, add their own detections, and can act on the host: isolate it from the network, kill a process, quarantine a file. For the SOC, an EDR is both a telemetry source and a response tool. Its raw telemetry is often richer than Sysmon's, but it lives in the vendor's console and format, so a SOC must decide how much of it to forward to the SIEM and how long the vendor keeps it.

**Anti-malware and application logs.** Antivirus detections, application servers and databases also log on the endpoint; a detection that names a file path can be the event that confirms an incident.

## How endpoint telemetry reaches the SOC

Each of these sources writes locally first. A log that stays on the host can be cleared by an attacker with administrative rights or encrypted by ransomware, and nobody can search five hundred laptops one by one. Endpoint telemetry is therefore **collected** by an agent or forwarder (Windows Event Forwarding, a SIEM agent, an EDR sensor, or syslog on Linux) and sent to a central platform. **Relationships and arrows.** The arrows from Activity to each source are labelled with what that source observes. The arrows from the violet boxes into the Security log and Sysmon are labelled "filters": they mean that configuration, not the activity itself, decides whether an event is written. Every source then has an arrow to the collector labelled "events", and the collector has one arrow to the SIEM labelled "parsed, normalised". The EDR agent also has a dashed arrow back to the host labelled "response", because an EDR can act as well as observe.

**Execution flow.** Read the figure top to bottom: something happens on the host; the relevant source checks its configuration; if the event is in scope, it is written locally; the forwarder picks it up and sends it to the SIEM, where an analyst or a rule can find it.

**Decision logic.** Two decisions are hidden in the violet boxes. If process creation auditing is off, no 4688 is written; if the command-line setting is off, the 4688 exists but is missing its most useful field. If the Sysmon configuration excludes a process, Sysmon writes nothing for it. A third decision sits at the forwarder: a source that is recorded locally but not forwarded is invisible to the SOC until someone collects it from the host.

**Technical interpretation.** The sources overlap deliberately. A single PowerShell launch can produce a 4688, a Sysmon event 1, a 4104 script block record and an EDR process event. Overlap gives resilience at the price of volume and duplication.

**Practical example.** In the course lab dataset, the Banyan Microfinance workstations produce two of these sources: Windows Security events (4624, 4625, 4720, 4732 and 1102) and Sysmon-style event 1 records. The PowerShell, EDR and Linux boxes have no data in the lab, which is itself a lesson: an analyst working that dataset cannot read the decoded PowerShell script, because nobody collected 4104 events.

**Security implications.** An attacker with administrative rights can change audit policy, stop or reconfigure Sysmon, or clear a log (event 1102). Forwarding events off the host quickly limits what tampering can erase, and alerting when a source falls silent catches the rest.

**Key learning.** Endpoint evidence exists only if an activity was observed by a source, allowed by its configuration and shipped by the forwarder; check all three before concluding that something did not happen.

## Worked example: reading endpoint events in the lab dataset

The course lab kit contains one synthetic day of telemetry from the fictional Banyan Microfinance in `LAB_ASSETS/C08/banyan_events.jsonl`: 340 events from four sources, generated deterministically by `make_dataset.py` so that every learner sees identical data. Event field names follow Windows and Sysmon conventions, but the events are simplified and normalised into one flat JSON shape; they are not exported from a real product. `LAB_ASSETS/C08/minisiem.py` loads them into a SQLite table called `events` and lets you query it with SQL. Work in your own copy of the kit, never in the original folder.

First, load the data and count what each source contributes:

```terminal
$ python minisiem.py load
loaded 340 events
$ python minisiem.py search "SELECT source, COUNT(*) n FROM events GROUP BY source ORDER BY n DESC"
source | n
proxy | 284
sysmon | 33
windows | 13
vpn | 10
```

`load` reads the JSONL file and creates the table, copying common fields such as `ts`, `source`, `event_id`, `host`, `user`, `image` and `parent_image` into columns and keeping the whole original event in a `raw` column. `search` runs the SQL you pass in quotes and prints the result with `|` between columns. Endpoint sources (`sysmon` and `windows`) supply 46 of the 340 events, a small share by count but, as you will see, most of the decisive evidence.

Next, list which endpoint event types exist:

```terminal
$ python minisiem.py search "SELECT source, event_id, COUNT(*) n FROM events WHERE source IN ('windows','sysmon') GROUP BY source, event_id ORDER BY source, event_id"
source | event_id | n
sysmon | 1 | 33
windows | 1102 | 1
windows | 4624 | 8
windows | 4625 | 2
windows | 4720 | 1
windows | 4732 | 1
```

Read this as an inventory. All 33 Sysmon events are process creations. There are no Sysmon network, file or registry events and no PowerShell events, so any question about what the PowerShell process did *inside* the host must be answered from other sources or left open.

### Stacking parent-child pairs

A powerful first technique for process telemetry is **stacking**: grouping events by a pair of fields and counting how common each combination is. Normal software produces the same parent-child pairs on many hosts; an attack usually produces a rare one.

```terminal
$ python minisiem.py search "SELECT parent_image, image, COUNT(*) n, COUNT(DISTINCT host) hosts FROM events WHERE source='sysmon' GROUP BY parent_image, image ORDER BY n"
parent_image | image | n | hosts
C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | 1 | 1
C:\Windows\explorer.exe | C:\Program Files\App\excel.exe | 8 | 8
C:\Windows\explorer.exe | C:\Program Files\App\explorer.exe | 8 | 8
C:\Windows\explorer.exe | C:\Program Files\App\msedge.exe | 8 | 8
C:\Windows\explorer.exe | C:\Program Files\App\outlook.exe | 8 | 8
```

Four pairs appear exactly once on each of the eight workstations: the shell (`explorer.exe`) starting the user's everyday applications. (The synthetic dataset places these applications under a generic `C:\Program Files\App\` path; real installations use each vendor's own folder.) One pair appears once, on one host: Microsoft Word starting PowerShell. Word has no ordinary reason to start a command interpreter, so this is the classic indicator of a malicious document running a macro (ATT&CK T1204.002, user execution of a malicious file, leading to T1059.001, PowerShell). The lab kit's `hunt.py` reaches the same conclusion with its "parent-child pairs seen on only one host" hunt, whose saved output in `hunt_output.txt` reads `WINWORD.EXE -> powershell.exe hosts=1 n=1`.

Now look at that one event in full, as stored in the `raw` column:

```json
{"@timestamp": "2026-11-03T06:14:00Z", "command_line": "powershell.exe -NoP -W Hidden -EncodedCommand <redacted-for-course>", "event_id": 1, "host": "WS-104", "image": "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe", "parent_image": "C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE", "source": "sysmon", "user": "divya"}
```

Each field answers part of the execution question. `@timestamp` is 06:14 UTC (11:44 IST). `host` WS-104 and `user` divya identify where and as whom. `parent_image` and `image` give the chain. The `command_line` is where the intent shows: `-NoP` (no profile), `-W Hidden` (hidden window) and `-EncodedCommand` (a Base64-encoded script, replaced in the course data by a placeholder) are options that legitimate users rarely combine and that hide what is being run from a casual observer. The command line alone cannot tell you what the encoded script did; a 4104 script block event would have, which is why enabling PowerShell logging is a standard recommendation. Notice also what the simplified lab event lacks compared with a real Sysmon event 1: no `ProcessGuid`, no hashes, no `ParentCommandLine`. You could not, from this record alone, prove which Word document was open.

### The rest of the endpoint story

Finally, list the Windows Security events other than the routine morning logons:

```terminal
$ python minisiem.py search "SELECT ts, host, user, event_id, target_user, outcome FROM events WHERE source='windows' AND event_id!=4624 ORDER BY ts"
ts | host | user | event_id | target_user | outcome
2026-11-03T04:05:00Z | WS-102 | ben | 4625 | None | failure
2026-11-03T04:05:00Z | WS-108 | hema | 4625 | None | failure
2026-11-03T07:02:00Z | WS-104 | divya | 4720 | svc_update | success
2026-11-03T07:03:00Z | WS-104 | divya | 4732 | svc_update | success
2026-11-03T08:17:00Z | WS-104 | divya | 1102 | None | success
```

The two 4625 failures at 04:05 are interactive logons on the users' own workstations, and their raw events carry status `0xC000006A` (wrong password for a valid name): ordinary typos, included in the dataset deliberately as noise. The last three rows are not noise. On the same host as the Word-to-PowerShell event, an account named `svc_update` is created at 07:02 and added to the local `Administrators` group at 07:03 (the raw 4732 event carries `"group": "Administrators"`), and at 08:17 the Security log is cleared. A name that imitates a service account, created from a user's session rather than by IT, is a typical persistence trick (ATT&CK T1136.001, create local account); clearing the log is defence evasion (T1070.001, clear Windows event logs).

Note what the 1102 means for the analyst. Because the dataset's events were already in the SIEM, the clearing did not destroy them. Had the events existed only on WS-104, everything before 08:17 in its Security log would now be gone, and the 1102 itself would be the only trace.

**Key learning.** Endpoint telemetry answers "what ran, what changed and who did it"; read it per host, in time order, against a baseline from other hosts.

## Common mistakes and misconceptions

- **"No event means it did not happen."** It means no configured source recorded it, or the record was not forwarded. Check audit policy, Sysmon configuration and collection health before drawing that conclusion.
- **"4688 tells me what PowerShell did."** Without the command-line policy it does not even tell you the arguments, and even with it, an encoded command hides the script. Script block logging (4104) is what records the code.
- **"Process IDs identify processes."** Process IDs are reused; across a day, the same number can belong to several unrelated processes. Use Sysmon's ProcessGuid, or the EDR's own process identifier, to join events.
- **"Turn everything on."** Unfiltered Sysmon or broad auditd rules can overwhelm collection and licence budgets, and the important events drown. Log deliberately, starting from the execution, change and access questions.
- **"The EDR has it, so the SIEM does not need it."** EDR consoles often keep raw telemetry for a limited period and cannot be correlated with proxy or identity data. Decide explicitly which endpoint events must reach the SIEM.
- **"A user's name in the event means the user did it."** The event records the security context, not the person; malware launched from divya's session runs as divya.

## Security implications, detection and defence

Endpoint telemetry is the evidence attackers most want to destroy, because it records them most precisely. Defenders should therefore treat the logging itself as a protected asset.

- **Protect the sources.** Restrict who can change audit policy and Sysmon configuration; alert on event 1102 (Security log cleared) and on the Sysmon service stopping or its configuration changing (Sysmon logs its own state and configuration changes as events 4 and 16).
- **Ship quickly.** The shorter the delay between an event being written and it reaching the SIEM, the less a log clear or ransomware can erase.
- **Watch for silence.** A workstation that sends hundreds of events a day and then sends none is either switched off or tampered with. Lesson 7 covers source-health monitoring.
- **Baseline parent-child behaviour.** Office applications, PDF readers and browsers starting script interpreters (`powershell.exe`, `cmd.exe`, `wscript.exe`, `mshta.exe`) is one of the highest-value endpoint detections; the lab's rule R1 and the Sigma rule `rk_office_spawns_shell.yml` in the kit implement exactly that idea, and Module 7 develops it.
- **Prevent as well as detect.** Blocking macros in documents from the internet, constraining PowerShell, and removing local administrator rights from ordinary users reduce what the telemetry ever has to catch.

> [!IMPORTANT]
> Endpoint logs contain personal data: user names, file names, browsing-related process activity. Under India's Digital Personal Data Protection Act 2023, collection should have a defined purpose (security monitoring), access should be limited to those who need it, and retention should follow policy. CERT-In's April 2022 directions additionally require organisations to maintain logs of their ICT systems for a rolling 180 days within India. Agree retention with legal and compliance rather than guessing.

## Best practices

- Enable process creation auditing **with command lines**, and PowerShell script block logging, on every Windows endpoint.
- Deploy Sysmon (or an EDR with equivalent telemetry) with a maintained, version-controlled configuration, and review it when exclusions are added.
- On Linux, collect authentication logs and the journal, and add targeted auditd rules for program execution and changes to sensitive files.
- Make sure every endpoint event carries a reliable host name, user, timestamp in UTC and, for processes, a unique process identifier and the parent.
- Document, per source, what is collected and what is not.

## Key takeaways

- Endpoint telemetry records execution, change, access and the state of the host's defences; it sees activity from inside the host, which network sources cannot.
- The Windows Security log contains only what audit policy enables; 4624/4625 (logons and logon type), 4688 (process creation, command line only if enabled), 4720/4732 (account and group changes) and 1102 (log cleared) are core SOC event IDs.
- PowerShell script block logging (4104) records the code actually run, including commands passed encoded on the command line.
- Sysmon adds detailed process (1), network (3), file (11), registry (12-14) and DNS (22) events, with ProcessGuid for reliable joins; on Linux, auth logs, the journal and auditd fill the same roles; EDR adds detection and response.
- In the lab, stacking parent-child pairs isolates `WINWORD.EXE` starting `powershell.exe` on WS-104, followed by a new local administrator and a cleared Security log: a pattern no single event proves.
