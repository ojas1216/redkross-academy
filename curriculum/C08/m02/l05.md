## Introduction and conceptual foundation

The first four lessons of this module surveyed where security telemetry comes from: endpoints, networks, identity systems and cloud control planes. Each of those sources produces **events**, and every event, whatever its origin, is in the end a small bundle of named values: a time, a host, a user, an action, an outcome, perhaps an address, a process or a URL. Those named values are **fields**. An analyst never reads "a log" in the abstract; they read fields, filter on fields, count fields and join one source to another on fields. A detection rule is a statement about fields. A timeline is a sort on one field. A pivot is a search for the value of one field in other sources.

That makes field literacy one of the most practical skills in a SOC. It has two halves. The first is **field semantics**: knowing what a field actually means in the source that produced it, which is often not what its name suggests. A field called `src_ip` in a VPN log is the user's external address on the internet; in a web proxy log the same name holds the internal address of the workstation that made the request. A field called `user` in a Windows account-creation event is the person who *did* the creating, not the account that was created. Getting this wrong does not produce an error message. It produces a confident, wrong conclusion.

The second half is **normalisation**: mapping the many source-specific field names onto one common vocabulary so that a single search can span every source. If the firewall calls an address `SRC`, the VPN gateway calls it `clientIP` and the proxy calls it `src_ip`, an analyst hunting for one suspicious address must remember three names and three formats, and a correlation rule must be written three times. A normalised schema, such as the Elastic Common Schema (ECS) used throughout this course, gives all of them one name, `source.ip`, with one agreed meaning.

This lesson builds both halves using the course dataset, the one-day record of the fictional Banyan Microfinance, and the C08 lab kit's `normalise_demo.py`, which turns a raw firewall syslog line and a raw VPN JSON record into the same schema and so reveals a link invisible in the raw form. Module 3 returns to parsing and normalisation as SIEM engineering; here the focus is the analyst's view.

> [!NOTE]
> Timestamps are the most important field of all, and the most error-prone. They have their own lesson (Lesson 6). In this lesson `@timestamp` appears simply as "when the event happened, in UTC".

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Event | One record emitted by a source about one occurrence: a logon, a process start, a connection, an HTTP request. |
| Field | A named value inside an event, such as `host`, `user` or `bytes_out`. |
| Field semantics | What a field's value actually denotes in a given source: whose address, which user, measured in what unit. |
| Raw event | The event as the source wrote it: a syslog text line, a JSON object, a Windows XML record. |
| Parsing | Extracting fields from a raw event (for example with a regular expression or a JSON decoder). |
| Normalisation | Renaming and reformatting parsed fields to a common schema so that equivalent values share one name and format. |
| Schema | A documented set of field names, types and meanings, such as ECS or the Open Cybersecurity Schema Framework (OCSF). |
| ECS | Elastic Common Schema: an open field-naming specification that groups fields into dotted *field sets* such as `source.*`, `user.*`, `event.*`. |
| Entity | A thing an investigation tracks across events: a user, a host, an IP address, a process, a session. |
| Identifier | A field that names an entity, and so can be used to join events (user name, host name, IP, process GUID, logon ID). |
| Pivot | Taking a value found in one event and searching for it in other events or sources. |
| Enrichment | Adding context that the source did not record, such as asset owner, user department or IP geolocation. |

## The anatomy of an event

Different sources record different things, but almost every security event answers some subset of the same six questions. Thinking in these families, rather than in one product's field names, is what lets an analyst read an unfamiliar log quickly.

**When.** The time of the occurrence; some events carry several times (start, end, collection, indexing), which Lesson 6 untangles.

**Where.** The system on which the event was observed: a host name, device, agent identifier or cloud account. "Where" is the *observer*, not always the system acted upon: a firewall event is recorded on `fw01` but describes traffic between two other machines.

**Who.** The identity responsible: a user name, a domain and security identifier (SID), a service account, a cloud principal. Many events contain more than one identity, and the distinction between the **subject** (the identity performing the action) and the **target** (the identity acted upon) is one of the most important in field semantics.

**What.** The action itself: an event ID (Windows 4624, Sysmon 1), an action verb (`drop`, `login`, `create`), an HTTP method and URL, a DNS query name, a cloud API call name. "What" is often encoded as a number whose meaning lives in the vendor's documentation rather than in the event.

**How.** The mechanism and context: process image, command line, parent process, logon type, protocol, user agent, authentication method. These fields turn "something happened" into "this is how it happened", and they are where most behavioural detections look.

**Outcome.** Whether the action succeeded: `success` or `failure`, an HTTP status code, an allow or deny decision, an error code. An outcome field is the difference between an attempt and an achievement, and a SOC treats the two very differently.

Alongside these six, every event should carry **provenance** fields that say which source and which parser produced it (`source` in the course dataset, `event.module` and `event.dataset` in ECS). Provenance matters because, as the next section shows, the meaning of a field depends on where it came from.

## Field semantics: the same name, different meanings

A field name is a label chosen by a developer. It is a hint about the meaning, not a definition. The definition lives in the source's documentation and in how the source is deployed. Here are three pairs of real records from the Banyan dataset.

A VPN record:

```json
{"@timestamp": "2026-11-03T06:46:00Z", "country": "??", "outcome": "success", "source": "vpn", "src_ip": "203.0.113.66", "user": "gopal"}
```

A proxy record:

```json
{"@timestamp": "2026-11-03T03:26:00Z", "bytes_out": 3411, "host": "WS-104", "source": "proxy", "src_ip": "10.40.0.23", "status": 200, "url": "https://news.example.com/", "user": "divya"}
```

In the VPN record, `src_ip` is the address on the public internet from which someone connected to Banyan's VPN gateway. In the proxy record, `src_ip` is the private, internal address of workstation WS-104 as seen by the proxy. Both are "the source IP" in the narrow sense that they are the source of the connection the device observed, but they describe completely different things. A search for `src_ip = 10.40.0.23` will never match a VPN record, and a rule that treats every `src_ip` as "the attacker's address" will misfire on proxy traffic. Notice also the VPN record's `country` value of `??`: the gateway could not geolocate the address. An unknown value is information too, but it is not the same as a country code, and a rule that checks `country != "IN"` will treat `??` as foreign, which may or may not be what the author intended.

Now two Windows records from the same workstation, one minute apart:

```json
{"@timestamp": "2026-11-03T07:02:00Z", "event_id": 4720, "host": "WS-104", "outcome": "success", "source": "windows", "target_user": "svc_update", "user": "divya"}
{"@timestamp": "2026-11-03T07:03:00Z", "event_id": 4732, "group": "Administrators", "host": "WS-104", "outcome": "success", "source": "windows", "target_user": "svc_update", "user": "divya"}
```

Event 4720 is Windows "a user account was created"; 4732 is "a member was added to a security-enabled local group". In both, `user` is the **subject**: the account under whose authority the action was performed. `target_user` is the **object**: the new account `svc_update`, which was created and then added to the local Administrators group. An analyst who reads `user: divya` as "divya's account was created" has the story backwards. The correct reading is that something acting as divya created a new account and made it an administrator, which in context (Module 3 and 4 show the whole chain) is attacker persistence. The original Windows event records this distinction as separate *Subject* and *New Account* (or *Member*) sections; any parser that flattened both into one `user` field would have destroyed it.

Semantic traps of this kind fall into a few recurring patterns:

| Pattern | Example | What goes wrong |
| --- | --- | --- |
| Perspective | `src_ip` external on VPN, internal on proxy | Pivots and rules match the wrong population. |
| Subject vs target | `user` vs `target_user` in 4720/4732 | The victim and the actor are swapped in the narrative. |
| Observer vs participant | `host: fw01` on a firewall drop | The firewall is mistaken for one end of the connection. |
| Direction and unit | `bytes_out` counted from the client | "Upload" and "download" are inverted; bytes read as kilobytes. |
| Placeholder values | `src_ip: "-"` on an interactive logon, `country: "??"` | Placeholders are counted as real values or compared as strings. |
| Encoded meaning | `logon_type: 2`, `event_id: 4732` | The number is ignored because its meaning is not in the event. |
| Missing versus false | Sysmon has no `outcome` at all | A rule on `outcome = "failure"` silently excludes the source. |

The placeholder row deserves a closer look. Banyan's interactive logons (Windows logon type 2, a user at the keyboard) record `src_ip` as the literal string `-`, because a local logon has no remote address. A "distinct source addresses per user" query would count `-` as an address, and a join on `src_ip` would link every local logon to every other. Normalise placeholders to a true null at ingestion.

The way to defeat all of these traps is the same: for every source you analyse, keep a short **field dictionary** that says, for each field, what it denotes, whose perspective it reflects, its type and unit, which values are placeholders, and which event types populate it. Most SOCs keep these alongside their parser configurations. Building one is part of this lesson's lab.

**Technical interpretation.** These differences are not source errors; each device describes the world from where it sits. **Practical example.** Searching the Banyan dataset for `203.0.113.66` in `src_ip` returns the VPN spray against eight users. Searching proxy `src_ip` for it returns nothing, correctly, because proxy `src_ip` only ever holds internal addresses.

**Security implications.** Misread fields cause false negatives (rules that never match) and false narratives (actor and victim swapped). Both survive peer review unless someone checks the dictionary.

**Key learning.** A field name is a hint, not a definition: confirm what each field means in each source before you pivot, join or alert on it.

One more collision in the same dataset makes the point sharply. The proxy's `status` field holds an HTTP status code (`200` on all 284 proxy events). The Windows source also has a `status` field, but on the two failed logons (event 4625 on WS-102 and WS-108 at 04:05 UTC) it holds `0xC000006A`, a Windows NTSTATUS code that Microsoft documents for 4625 as a correct user name with a wrong password. A dashboard that charts "status values" across sources would put an HTTP success and a Windows authentication failure on the same axis. Encoded fields like this need their meaning looked up, written into the field dictionary, and ideally translated into a readable field during normalisation.

## Identifiers: the fields that join events together

Most investigations are a chain of pivots: from an alert to a user, from the user to a host, from the host to a process, from the process to a network destination. Each link in that chain is an **identifier** field shared by two events. Choosing the right identifier, and knowing how stable it is, is what separates a sound timeline from a coincidence.

| Identifier | Typical fields | Stability and caveats |
| --- | --- | --- |
| User | `user`, domain, SID, cloud principal ID | Names can be reused or renamed; SIDs and cloud object IDs are stable. Case and domain prefixes (`BANYAN\divya` vs `divya@banyan.example`) differ by source. |
| Host | host name, agent ID, MAC address | Host names are reused after rebuilds; agent IDs are unique per installation. |
| IP address | `src_ip`, `dst_ip` | Changes with DHCP leases, NAT and VPN pools; one address can be many hosts over a day. Always join on IP *with a time window*. |
| Process | PID, Sysmon ProcessGuid | PIDs are reused by the operating system; Sysmon's ProcessGuid is designed to identify one process instance. |
| Session | Windows Logon ID, VPN session ID, web session cookie | Ties many events to one authenticated session; scoped to one system. |
| Object | file hash, URL, domain, registry key | Stable across hosts; ideal for "where else has this appeared?" pivots. |

The general rule is to **join on the most specific stable identifier available**, and to add time as a second key whenever the identifier can be reassigned. An IP address on its own is a weak join: `10.40.0.23` was WS-104 at 03:26 UTC in the proxy log, but a DHCP lease change could hand that address to another machine later in the day. Process IDs are weaker still. Sysmon includes a `ProcessGuid` precisely because a numeric PID may belong to a completely different program a few minutes later.

The Banyan dataset is simplified (it records `host` and `user` directly on every endpoint and proxy event), but it already shows a cross-source chain. The proxy event that downloads `invoice.docm` on WS-104 and the Sysmon event at 06:14 UTC, in which `WINWORD.EXE` launches `powershell.exe` with `-EncodedCommand` as user divya, share the identifiers `host: WS-104` and `user: divya`. That shared pair, together with the short time gap, is what lets Module 3's correlation rule link the download to the execution.

## Normalised schemas: one vocabulary for every source

Field dictionaries make each source understandable. Normalisation makes them *searchable together*. The idea is that a parser for each source does two jobs: it extracts fields from the raw event, and it renames and reformats them into a shared schema. After that, the SIEM, the detection rules and the analysts speak only the schema.

### How ECS is organised

The Elastic Common Schema is an open specification maintained by Elastic. Its central design choice is the **field set**: a group of fields describing one kind of entity, named with a dotted prefix. A handful of field sets cover most of what a SOC analyst uses every day:

| Field set | Example fields | What it describes |
| --- | --- | --- |
| Base | `@timestamp`, `message`, `tags` | When the event happened (UTC) and the original text. |
| `event.*` | `event.module`, `event.dataset`, `event.action`, `event.outcome`, `event.category`, `event.kind` | What kind of event this is, which source produced it, what happened and whether it succeeded. |
| `source.*` / `destination.*` | `source.ip`, `source.port`, `destination.ip`, `destination.port` | The two ends of a network connection, from the initiator's point of view. |
| `host.*` | `host.name`, `host.ip`, `host.os.*` | The host on which the event was observed. |
| `user.*` | `user.name`, `user.domain`, `user.id`, `user.target.name` | The identity involved; `user.target.*` holds the identity acted upon. |
| `process.*` | `process.executable`, `process.command_line`, `process.pid`, `process.parent.executable` | The process and its parent. |
| `network.*` | `network.transport`, `network.protocol` | Protocol details of a connection. |
| `url.*` / `http.*` | `url.full`, `url.domain`, `http.response.status_code` | Web requests and responses. |

Three properties make this useful. First, **names carry semantics**: `source.ip` means the initiator of a connection, so the VPN's external client address and the proxy's internal client address can both live in `source.ip` *because* both are initiators, while the host that recorded the event lives separately in `host.name`. Second, **some fields have controlled values**: ECS defines `event.outcome` with the allowed values `success`, `failure` and `unknown`, so rules no longer need to know that one product writes `SUCCESS`, another `Succeeded` and a third a numeric code. Third, **subject and target are separate fields**: a 4720 account-creation event can map the creator to `user.name` and the new account to `user.target.name`, preserving the distinction that the raw Windows record makes.

ECS is not the only schema. The **Open Cybersecurity Schema Framework (OCSF)** is a vendor-neutral, open-source schema organised around event categories and classes, adopted by a number of security vendors and cloud services; many SIEMs also have their own data models. For an analyst the choice of schema matters less than its consistent use: one schema, applied to every source, documented, and enforced at ingestion.

Each feeds its own parser: **from_syslog()** (regular expression, IST to UTC) and **from_vpn_json()** (JSON decode and rename). These are the two functions in `normalise_demo.py`. Both parsers feed the central node **ECS-style event**, which lists the shared names `@timestamp (UTC)`, `source.ip`, `event.module` and `event.action`. The final node, **One search: source.ip = 203.0.113.66**, is the payoff, and it is drawn dark because it is the outcome that matters.

**Relationships and arrows.** Arrows run left to right in the direction of data flow: raw event to parser, parser to normalised event, normalised event to search. The edge from the firewall parser is labelled **SRC to source.ip** and the edge from the VPN parser **clientIP to source.ip**: two different raw names converging on one schema name. The final edge is labelled **matches both events**.

**Execution flow.** Each raw event is parsed independently at ingestion; the parsers know nothing about each other. Correlation happens later, at search time, and only works because both parsers chose the same target name.

**Decision logic.** There are no drawn branches, but there is an implicit failure path: if either parser had used a different name for the address, the search would silently return one event instead of two.

**Technical interpretation.** The firewall parser also performs a type conversion (the port becomes the integer `3389`) and a time conversion (local IST to UTC with a `Z` suffix); the VPN parser lower-cases `SUCCESS` to `success`. Normalisation is renaming plus formatting plus value control.

**Practical example.** In the lab output below, the firewall drop of a remote desktop attempt and a successful VPN login, both from `203.0.113.66`, sit 21 seconds apart once both are in UTC and share `source.ip`.

**Security implications.** A normalisation mistake is a detection gap that raises no error. Parsers deserve change control and testing, and parse-failure counts deserve monitoring (Module 3).

**Key learning.** Normalisation turns many vocabularies into one, so a single query can follow an entity across every source.

## Worked example: normalising two sources with the lab kit

The C08 lab kit's `LAB_ASSETS/C08/normalise_demo.py` is a 24-line script that makes the mechanism above concrete. It contains two raw events taken from the Banyan storyline and one parser function for each. Copy the kit to a working directory of your own first; never run scripts inside the course library or the `LAB_ASSETS` folder.

```bash
mkdir -p ~/c08-work && cp LAB_ASSETS/C08/normalise_demo.py ~/c08-work/
cd ~/c08-work
```

`mkdir -p` creates the working directory (and does not complain if it already exists); `cp` copies the script so that anything you change stays in your own folder.

### The two raw inputs

```python
RAW_SYSLOG = "Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389"
RAW_JSON = '{"time":"2026-11-03T06:46:00Z","service":"vpn","user":"gopal","clientIP":"203.0.113.66","result":"SUCCESS"}'
IST = timezone(timedelta(hours=5, minutes=30))
```

The first is a Linux kernel firewall message in classic syslog style: a month, a day and a time with **no year and no time zone**, the host name `fw01`, the action `DROP`, and a series of `KEY=value` tokens. `SRC` and `DST` are the packet's source and destination addresses, `PROTO` the transport protocol and `DPT` the destination port (3389 is the default port of Microsoft's Remote Desktop Protocol). The second is a JSON record from the VPN gateway, already in UTC (the trailing `Z`), but using its own names: `time`, `service`, `clientIP`, `result`. The constant `IST` encodes India Standard Time as a fixed offset of five hours thirty minutes, which is how the firewall's clock was configured.

### The firewall parser

```python
def from_syslog(line, year=2026, tz=IST):
    m = re.match(r"(\w{3})\s+(\d+) (\d\d:\d\d:\d\d) (\S+) kernel: (\w+) .*SRC=(\S+) DST=(\S+) PROTO=(\w+) DPT=(\d+)", line)
    ts = datetime.strptime(f"{year} {m[1]} {m[2]} {m[3]}", "%Y %b %d %H:%M:%S").replace(tzinfo=tz)
    return {"@timestamp": ts.astimezone(timezone.utc).isoformat().replace("+00:00", "Z"),
            "event.module": "firewall", "event.action": m[5].lower(), "host.name": m[4],
            "source.ip": m[6], "destination.ip": m[7], "network.transport": m[8].lower(),
            "destination.port": int(m[9])}
```

The regular expression captures nine groups: month, day, time, host, action, and the four `KEY=value` tokens. `\s+` after the month tolerates the double space that classic syslog uses before single-digit days (`Nov  3`). The parser then supplies the two facts the raw line omits: the **year** (a parameter defaulting to 2026) and the **time zone** (IST). `strptime` builds the date and time, `replace(tzinfo=tz)` declares it to be IST, and `astimezone(timezone.utc)` converts it to UTC. Finally each captured value is placed under its ECS-style name: the device becomes `host.name` (the observer), `SRC` becomes `source.ip`, `DPT` becomes the integer `destination.port`, and the action and transport are lower-cased.

### The VPN parser

```python
def from_vpn_json(text):
    d = json.loads(text)
    return {"@timestamp": d["time"], "event.module": d["service"], "event.action": "login",
            "event.outcome": d["result"].lower(), "user.name": d["user"], "source.ip": d["clientIP"]}
```

JSON needs no regular expression; `json.loads` returns a dictionary. The work is pure renaming: `clientIP` becomes `source.ip`, `user` becomes `user.name`, and `result` is lower-cased into the controlled value `event.outcome`. The parser also *adds* a field the source did not state, `event.action: "login"`, because the parser author knows what kind of record this gateway emits.

### Interpreting the output

Read the two lines as an analyst would. Both events now have `source.ip: 203.0.113.66`. Both have a UTC `@timestamp`, and the firewall's local `12:16:21` has become `06:46:21Z`. The VPN login succeeded at `06:46:00Z`. So, **21 seconds after the address 203.0.113.66 logged in to the VPN as gopal, a connection attempt from that same address to port 3389 on the internal host 10.40.0.5 was dropped by the firewall.** In raw form these two facts were in different formats, with different names for the address and different clocks; nobody scanning either log alone would have connected them. Normalised, one query on `source.ip` returns both, adjacent in time.

Note what the output does *not* contain: the firewall event has no `user.name`, because a packet filter does not know who sent the packet. Normalisation does not invent information; getting from an address to a person still needs a pivot through an identity source, here the VPN log.

Note also how fragile the time conversion is. If the parser had assumed the firewall's clock was UTC, the drop would have been stamped `12:16:21Z`, five and a half hours after the VPN login, and the link would have vanished. Lesson 6 is about exactly this risk.

### Mapping the Banyan fields

The same thinking applies to the whole course dataset. The table below is a field dictionary entry for each Banyan field, with the ECS-style name a parser would map it to. It is an exercise in semantics as much as in renaming.

| Banyan field | Source(s) | ECS-style name | Note on meaning |
| --- | --- | --- | --- |
| `@timestamp` | all | `@timestamp` | Event time in UTC (already normalised). |
| `source` | all | `event.module` | Provenance: which source produced the event. |
| `host` | windows, sysmon, proxy | `host.name` | The workstation that recorded or made the request. |
| `user` | all | `user.name` | The acting identity (subject). |
| `target_user` | windows | `user.target.name` | The account acted upon in 4720/4732. |
| `event_id` | windows, sysmon | `event.code` | Vendor event number; meaning needs lookup. |
| `outcome` | windows, vpn | `event.outcome` | Already `success`/`failure`. |
| `src_ip` | vpn, proxy | `source.ip` | External client (VPN) or internal workstation (proxy); the field name is shared because both are initiators. |
| `src_ip` = `-` | windows | (null) | Placeholder on local logons; drop rather than map. |
| `image`, `parent_image` | sysmon | `process.executable`, `process.parent.executable` | Full paths of the process and its parent. |
| `command_line` | sysmon | `process.command_line` | As recorded; may be redacted or truncated by the source. |
| `url` | proxy | `url.full` | Full requested URL. |
| `status` | proxy | `http.response.status_code` | HTTP status. |
| `status` | windows | (source-specific field) | NTSTATUS code on 4625; must not be merged with HTTP status. |
| `bytes_out` | proxy | `source.bytes` | Bytes sent by the client, so large values suggest uploads. |
| `country` | vpn | `source.geo.country_iso_code` | `??` means unknown; map to null, not to a country. |

Two rows have no clean ECS target (the Windows `status` code and the `-` placeholder); a good mapping document records such decisions rather than forcing values into misleading fields.

## Common mistakes and misconceptions

**"The field name tells me what it means."** It tells you what a developer called it. Always confirm against source documentation, and against real sample events, before writing a rule.

**Treating missing and false as the same.** A rule that alerts on `event.outcome: failure` silently ignores every source that has no outcome field. Ask "which sources populate this field?" before asking "which events match?".

**Assuming normalisation is lossless.** Parsers drop unknown fields and truncate long values. Keep the raw event (ECS provides `event.original`) so disputed values can be checked.

**Comparing placeholders.** Strings such as `-`, `N/A`, `??` or `0.0.0.0` are not values. Counting or joining on them creates phantom entities.

## Security implications, detection and defence

Fields are the attack surface of detection. Every rule, dashboard and hunt depends on fields being present, correctly named and correctly understood, so every failure in that chain is a potential blind spot.

**Silent parse and mapping failures.** If a vendor changes its log format after an upgrade, a parser may stop extracting `source.ip`. Events still arrive, so volume dashboards look normal, but every rule on that field stops matching. Defence: monitor per-source parse-error rates and the fill rate of critical fields (the percentage of events in which the field is populated), and alert when either changes sharply.

**Attacker-influenced fields.** Some fields are supplied by the remote party rather than measured by the sensor: HTTP user agents, requested host names, user names typed at a login prompt, and, on the endpoint, command-line strings an attacker composes. Treat them as claims. Rules should prefer fields the sensor measures itself (the observed source address of a TCP connection, the image path the operating system loaded) and should never assume that a self-reported value is honest. Values that will be displayed in a SIEM console should be escaped, since crafted strings can be designed to mislead an analyst or to break a parser.

**Redaction and privacy.** Fields such as command lines, URLs and user names can carry personal data. Under India's Digital Personal Data Protection Act 2023, the SOC is processing personal data when it stores them, so access to raw fields should be limited to those who need it and retention should follow policy. The Banyan dataset redacts the encoded PowerShell command (`<redacted-for-course>`), which is also a reminder that a redacted field can still be analysed for its *shape* (here, `-NoP -W Hidden -EncodedCommand` launched by `WINWORD.EXE`).

## Best practices

- Build a field inventory and field dictionary for every source before writing detections on it; record meaning, perspective, type, unit, placeholders and populating event types.
- Normalise to one schema (ECS, OCSF or your platform's model) at ingestion, and keep the raw event alongside the normalised one.
- Map subject and target identities to separate fields; never flatten them.
- Use controlled values for outcome, action and category fields so that rules do not depend on vendor spelling.
- Convert placeholders to nulls and document why.
- Join on stable identifiers (GUIDs, SIDs, agent IDs) where available, and add a time window to every join on an IP address or PID.
- Monitor parse errors and critical-field fill rates as health metrics.
- Treat parser and mapping changes as code: review, test against saved sample events, and version them.

## Key takeaways

- Every event is a set of fields answering when, where, who, what, how and outcome, plus provenance; read logs by these families, not by product names.
- Field semantics depend on the source: `src_ip` is external on the VPN and internal on the proxy; `user` is the subject and `target_user` the object in account-management events; `status` means HTTP in one source and NTSTATUS in another.
- Placeholders (`-`, `??`) and missing fields are not values; handle them explicitly.
- Identifiers join events; prefer stable ones and always add time to joins on IPs and PIDs.
- ECS-style normalisation gives equivalent values one name and controlled formats, so a single search spans every source, as `normalise_demo.py` shows by linking a firewall drop and a VPN login from `203.0.113.66` 21 seconds apart.
- Normalisation does not create information; it only makes recorded information comparable, and its mistakes fail silently.
