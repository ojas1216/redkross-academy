## Introduction and conceptual foundation

Every investigation ends as a story told in time order: first this happened, then that, then the attacker did this. The story is only as good as the clocks behind it. If two sources disagree about when something happened, the analyst can conclude that an effect came before its cause, miss a link between two events that were seconds apart, or place an incident outside the time window that a rule or a regulator cares about. Lesson 5 showed that fields must be read with care; the timestamp is the field where carelessness does the most damage, because a wrong time is still a perfectly well-formed time. Nothing looks broken.

The course library's fictional teaching scenario "the one-hour offset" shows the failure in miniature. At a fictional insurer, firewall logs recorded in local time with no offset were merged with EDR logs recorded in UTC, without conversion. The team concluded that the attacker exfiltrated data *before* the phishing email that started the intrusion had even arrived: an impossible sequence. Once both sources were normalised to UTC the sequence made sense. The fix the scenario prescribes is the theme of this lesson: normalise at ingestion and record time zones.

This lesson builds the problem in layers: UTC, local time and offsets (using India Standard Time, because the course's fictional Banyan Microfinance operates in India); the formats times take in logs, with a short Python demonstration; clocks that are actually wrong (drift, skew, NTP); the several times one event carries; and the pitfalls of putting events in order.

> [!IMPORTANT]
> The working rule for a SOC is short: **store and compare in UTC, with an explicit offset; display local time only as a labelled convenience.** Everything else in this lesson explains why the rule exists and what goes wrong when it is broken.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| UTC | Coordinated Universal Time, the international reference time scale; it does not change with seasons. |
| Offset | The difference between a local time and UTC, written `+05:30` or `-04:00`. |
| Time zone | A region's rules for its offset, including any daylight-saving changes; an offset is one value, a zone is a set of rules. |
| IST | India Standard Time, UTC+05:30 all year (India does not observe daylight saving time). |
| ISO 8601 | International standard for date and time representation, e.g. `2026-11-03T06:46:00Z`. |
| RFC 3339 | An internet profile of ISO 8601 used by many protocols and logs; requires a full date, time and offset. |
| `Z` | Suffix meaning an offset of zero (UTC), sometimes called "Zulu" time. |
| Naive timestamp | A date and time with no offset or zone; it does not identify a single instant. |
| Aware timestamp | A date and time with an offset; it identifies one instant. |
| Unix epoch time | Seconds (or milliseconds) since 1970-01-01T00:00:00Z. |
| Clock drift | The gradual divergence of a system clock from true time. |
| Clock skew | The difference between two clocks at a given moment. |
| NTP | Network Time Protocol, which synchronises clocks over a network (version 4 is specified in RFC 5905; it uses UDP port 123). |
| Event time | When the occurrence happened, according to the source. |
| Ingest time | When the event reached the collection pipeline or the SIEM. |

## UTC, local time and offsets

A timestamp names an instant. "12:16:21" does not, because the same wall-clock reading happens at different instants in different places. "12:16:21 in India on 3 November 2026" does, and so does "06:46:21 UTC on 3 November 2026", and they are **the same instant**: IST is five hours thirty minutes ahead of UTC, so subtracting 05:30 from an IST time gives the UTC time.

$$t_{\text{UTC}} = t_{\text{local}} - \text{offset}$$

For IST the offset is $+05{:}30$. So 14:05 IST is 08:35 UTC, and 00:20 IST on 4 November is 18:50 UTC on 3 November: conversions can cross the date line, which is a frequent source of "the event is on the wrong day" confusion in daily reports.

IST is unusually easy to work with because it has one fixed offset all year. Many other zones change offset for daylight saving time. That has two consequences for an analyst. First, the offset for a given zone depends on the date, so "London time" is UTC+00:00 in winter and UTC+01:00 in summer. Second, on the day clocks go back, one local hour happens twice, so a local timestamp in that hour is ambiguous; on the day clocks go forward, one local hour never happens at all. A SOC that monitors offices in several countries, or a managed security service provider (MSSP) with clients abroad, meets these cases every year. Storing in UTC makes them disappear: UTC never repeats or skips an hour.

Why UTC rather than IST as the common clock? Cloud audit logs, SaaS platforms and many appliances record UTC by default, and the parties a SOC works with (vendors, other SOCs, CERT-In, foreign partners) need a shared reference. Converting to IST for a management report is fine, provided the column is labelled and the UTC value stays beside it, which is exactly what this module's lab asks for.

## How times are written in logs

Even when every clock is right and every source uses UTC, timestamps arrive in many shapes. A parser must recognise each one and convert it to one canonical form.

### ISO 8601 and RFC 3339

The canonical form in this course, and in ECS's `@timestamp`, is an ISO 8601 / RFC 3339 string such as `2026-11-03T06:46:00Z`. Its parts are the date (`2026-11-03`, year-month-day), a `T` separator, the time (`06:46:00`), optional fractional seconds (`06:46:00.123`), and an offset: `Z` for UTC, or `+05:30` for IST. The same instant can be written as `2026-11-03T12:16:00+05:30`. The year-first order removes the day-month ambiguity of formats like `03/11/2026` (3 November in India and the UK, 11 March in the United States), and the explicit offset removes the zone ambiguity.

### Classic syslog

Traditional BSD-style syslog, described in RFC 3164, stamps messages like `Nov  3 12:16:21`: a month abbreviation, a space-padded day and a time. There is **no year and no time zone**. The receiver has to assume both. RFC 5424, the newer syslog protocol, replaced this with an RFC 3339 timestamp that carries the year, fractional seconds and offset, but many devices still emit the old format. The firewall line in the C08 kit's `normalise_demo.py` is classic syslog, and Lesson 5 showed its parser supplying the year (2026) and the zone (IST) from configuration. If either assumption is wrong, every event from that device is wrong by the same amount. A parser that assumes the current year will also misdate old events replayed in January, which is a known trap when importing December logs after the new year.

### Windows event logs

Windows records event times internally as UTC (the `SystemTime` attribute of the `TimeCreated` element in the event XML is a UTC value), while Event Viewer *displays* them in the viewing machine's local time. An analyst who copies times from the Event Viewer screen into a case note, without noting the viewer's zone, has created exactly the naive timestamp this lesson warns against. Export the XML or use a collector that preserves the UTC value.

### Unix epoch values

Many APIs, databases and cloud services use Unix time: a count of seconds since 1970-01-01T00:00:00Z. It is compact, unambiguous and sorts numerically, but it is unreadable to humans and comes in different units. A 10-digit value (such as `1793688360`) is usually seconds; a 13-digit value is usually milliseconds, and some systems use microseconds or nanoseconds. Misreading the unit produces dates in 1970 or tens of thousands of years in the future, which is at least obvious; misreading a zone is not.

**Execution flow.** At ingestion each event is parsed, its offset determined (from the event itself or from documented source configuration), and the time converted to UTC before storage. Comparison and sorting happen afterwards, on UTC values only.

**Decision logic.** The single decision is whether the offset is known. If yes, the conversion is exact. If no, the parser must use a documented assumption for that source, and the assumption must be tested; a wrong guess shifts every event from the source by the same amount.

**Technical interpretation.** Conversion changes the representation, not the instant: `12:16:21+05:30` and `06:46:21Z` are equal values. A naive time is not a value of this kind at all; Python, as the demonstration below shows, refuses to compare it with an aware one.

**Practical example.** In the Banyan storyline, an analyst who loaded the firewall drop as `12:16:21Z` would see the remote desktop attempt five and a half hours after the VPN spray and would not connect them. The library's revision scenario makes the same point: a 5.5-hour discrepancy between two timelines is the signature of an IST time treated as UTC.

**Security implications.** Wrong offsets break correlation rules whose windows are minutes long, mislead incident timelines and can misstate when an incident was noticed, which matters for reporting deadlines.

**Key learning.** Two clocks agree only after both are converted to UTC with a known offset; a timestamp without an offset is a guess.

## Worked example: conversions and two classic errors in Python

The conversions above are easy to get wrong by hand and easy to get right in code, provided the code uses time-zone-aware values. The short script below, written for this lesson and run in a working folder of your own (CPython 3.14.4), uses the same two Banyan events as `normalise_demo.py`.

```python
from datetime import datetime, timezone, timedelta
IST = timezone(timedelta(hours=5, minutes=30))

fw = datetime(2026, 11, 3, 12, 16, 21, tzinfo=IST)          # firewall, local IST
vpn = datetime.fromisoformat("2026-11-03T06:46:00Z")         # VPN, UTC
print("firewall IST :", fw.isoformat())
print("firewall UTC :", fw.astimezone(timezone.utc).isoformat())
print("vpn UTC      :", vpn.isoformat())
print("gap (s)      :", (fw - vpn).total_seconds())

naive = datetime(2026, 11, 3, 12, 16, 21)                    # same clock reading, no offset
try:
    print(naive < vpn)
except TypeError as e:
    print("naive vs aware:", e)

mixed = ["2026-11-03T06:46:21Z", "2026-11-03T12:15:30+05:30", "2026-11-03T06:46:00Z"]
print("string sort  :", sorted(mixed))
print("instant sort :", sorted(mixed, key=datetime.fromisoformat))

print("epoch s      :", int(vpn.timestamp()))
print("from epoch ms:", datetime.fromtimestamp(1793688360000 / 1000, tz=timezone.utc).isoformat())
```

```terminal
$ python -I ts_demo.py
firewall IST : 2026-11-03T12:16:21+05:30
firewall UTC : 2026-11-03T06:46:21+00:00
vpn UTC      : 2026-11-03T06:46:00+00:00
gap (s)      : 21.0
naive vs aware: can't compare offset-naive and offset-aware datetimes
string sort  : ['2026-11-03T06:46:00Z', '2026-11-03T06:46:21Z', '2026-11-03T12:15:30+05:30']
instant sort : ['2026-11-03T12:15:30+05:30', '2026-11-03T06:46:00Z', '2026-11-03T06:46:21Z']
epoch s      : 1793688360
from epoch ms: 2026-11-03T06:46:00+00:00
```

**Reading the output line by line.**

- `timezone(timedelta(hours=5, minutes=30))` defines a fixed +05:30 offset; attaching it with `tzinfo=IST` makes the firewall time *aware*. `astimezone(timezone.utc)` converts it, and the result, `06:46:21+00:00`, matches the `@timestamp` that `normalise_demo.py` produced.
- `datetime.fromisoformat` parses the VPN's ISO 8601 string, including the `Z` suffix, into an aware UTC value.
- Subtracting two aware values gives the true interval between the instants: **21 seconds**, even though one was written in IST and the other in UTC. Python compares instants, not wall-clock readings.
- The naive value, the same `12:16:21` without an offset, cannot be compared with an aware one: Python raises `TypeError: can't compare offset-naive and offset-aware datetimes`. That refusal is a feature. Many tools are less strict and silently treat a naive time as UTC or as the machine's local time, which is how the 5.5-hour error enters a timeline.
- The **string sort** puts `12:15:30+05:30` last, because text comparison sees "12" after "06". The **instant sort**, which parses each string first, puts it first: 12:15:30 IST is 06:45:30 UTC, half a minute before the VPN login. ISO 8601 strings sort correctly as text only when they share one format and one offset. The library's Module 3 lab warns of exactly this when correlating on string timestamps.
- The last two lines convert between ISO form and epoch time. `timestamp()` returns seconds, so the VPN login is `1793688360`; a 13-digit millisecond value must be divided by 1000 before conversion, otherwise the result is wildly out of range.

> [!TIP]
> In any script that handles log times, make every datetime aware on the way in, convert to UTC immediately, and only format for display on the way out. If a value arrives naive, decide its zone explicitly and record that decision in the case notes.

## Clocks that are wrong: drift, skew and NTP

Everything so far assumed that each source's clock was right and only its notation differed. Real clocks are not always right. A computer keeps time with a crystal oscillator whose frequency varies slightly with temperature and age, so an unsynchronised clock **drifts**, gaining or losing seconds per day. Virtual machines can jump in time when they are paused, restored from a snapshot or migrated. A device whose battery-backed clock fails may boot believing it is years in the past. The difference between two clocks at a given moment is **skew**, and from an analyst's point of view skew between sources is indistinguishable from a time-zone error, except that it is usually smaller, not a round number, and changes over time.

### How NTP keeps clocks honest

The Network Time Protocol synchronises clocks across a network. NTP servers are arranged in **strata**: stratum 0 devices are reference clocks such as GPS receivers or atomic clocks; stratum 1 servers are directly attached to them; stratum 2 servers synchronise from stratum 1, and so on. A client exchanges timestamped packets with one or more servers, estimates the network delay and its own offset, and gradually adjusts its clock (slewing it rather than jumping, where possible, so that time does not run backwards). On Linux, the work is done by daemons such as chrony or systemd-timesyncd; on Windows, by the Windows Time service (W32Time). In an Active Directory domain, member computers synchronise from domain controllers, domain controllers from the domain hierarchy, and the PDC emulator of the forest root domain should be configured to synchronise from a reliable external source.

Accurate time is a security dependency in its own right. **Kerberos** authentication rejects requests when the clocks of client and domain controller differ by more than a tolerance (five minutes by default in Windows domains), so a badly skewed machine cannot log on. TLS certificate validation depends on the current date, and time-based one-time passwords depend on the current time. For logging, the requirement is explicit in India: the CERT-In Directions of 28 April 2022 require service providers, intermediaries, data centres, body corporates and government organisations to connect to the NTP servers of the National Informatics Centre (NIC) or the National Physical Laboratory (NPL), or to NTP servers traceable to them, for synchronising the clocks of their ICT systems. The same Directions require logs to be retained for 180 days and specified incidents to be reported within six hours of noticing them, and both obligations assume that the times in those logs can be trusted.

### Detecting skew

Skew leaves traces an analyst can spot:

- **Impossible sequences.** An effect that appears before its cause across two hosts (a file received before it was sent, a logon recorded before the authentication it depends on) is a strong hint, provided time zones have already been ruled out.
- **Anchor events.** Events that are known to be simultaneous, such as both ends of the same network connection or the same authentication recorded on client and domain controller, reveal the offset between the two sources.
- **Event time versus ingest time.** If a source's event times are consistently *later* than the time the SIEM received them, its clock is ahead: events cannot arrive before they happen.
- **Platform health checks.** The library's Module 3 lists clock skew among standard SIEM health checks, alongside ingestion rates and parse errors.

On the systems themselves, administrators can check synchronisation status with each platform's own tools (for example `timedatectl` on systemd-based Linux or `w32tm /query /status` on Windows); in a SOC these checks are better automated as monitoring than performed by hand.

## One event, several times: event time and ingest time

Even with perfect clocks and perfect offsets, one event carries several different times, and confusing them causes a separate family of mistakes. ECS names them clearly:

| ECS field | Meaning |
| --- | --- |
| `@timestamp` | When the event originated, according to the source: the **event time**. |
| `event.created` | When the event was first read by an agent or by the pipeline. |
| `event.ingested` | When the event arrived in the central data store: the **ingest time**. |
| `event.start` / `event.end` | When an activity with duration (a connection, a session) began and ended. |

In a healthy pipeline the gap between event time and ingest time is seconds. It grows when something delays collection: a laptop that is offline or off the corporate network, an agent buffering during a network outage, a cloud provider that delivers audit logs in batches, a forwarder queue that backs up under load. These delays are normal and legitimate, and an investigation must be built on event time. But SIEM searches and scheduled rules often select data by the time it was indexed, or run over a fixed window of recent event time, and late-arriving events can fall between the windows.

**Relationships and arrows.** Solid arrows are actions; dashed arrows are replies. The first arrow, from the endpoint to the agent buffer, is labelled **Sysmon 1 written, @timestamp 06:14:00Z**. The next, from the agent to the SIEM, is **Send fails: network down, event queued**. The rule then queries the SIEM (**06:15 run: @timestamp in last 5 min**) and receives the dashed reply **no match: event not yet ingested**. Later the agent delivers its queue (**07:40 reconnect: queue sent, event.ingested 07:40Z**). The rule runs again (**07:45 run: @timestamp in last 5 min**) and the dashed reply is **misses it: 06:14 is outside the window**.

**Execution flow.** The event exists from 06:14 but is invisible to the SIEM until 07:40. Every rule run between those times finds nothing because the data is absent; every run after 07:40 finds nothing because its event-time window has moved on. The event is stored and searchable by hand, but no alert ever fires.

**Decision logic.** The outcome depends on which time the rule selects by. Selecting by ingest time (with the event's own `@timestamp` still used for the timeline) catches the event at the 07:45 run. So does a look-back window long enough to cover the source's expected delay, with de-duplication of repeated matches.

**Technical interpretation.** Event time answers "when did it happen?"; ingest time answers "when could we have known?". Both are needed: the first for the narrative, the second for measuring detection delay and for making sure scheduled searches see every event once.

**Practical example.** For the Banyan intrusion, the case timeline should place the PowerShell execution at 06:14 UTC (11:44 IST) whatever its ingest time, and a review should record the 86-minute gap as a collection delay.

**Security implications.** Attackers do not need to cause this gap; ordinary laptops create it every day. Rules on intermittently connected sources need ingest-time scheduling or generous look-backs, and pipelines need lag monitoring.

**Key learning.** Build timelines on event time, schedule detections with ingest delay in mind, and keep both times on every event.

## Putting events in order: the pitfalls

A timeline is a sort, and sorting time values looks trivial. The traps are in the data, not the algorithm.

**Sorting text instead of instants.** As the demonstration showed, ISO strings with different offsets sort wrongly as text. So do mixed formats (`2026-11-03 06:46:00` with a space against `2026-11-03T06:46:00Z` with a `T`) and any format that does not put the year first. Sort on parsed, UTC-normalised values, or on strings only after every value has been rewritten into one identical format.

**Mixed precision.** One source records whole seconds, another milliseconds, a third microseconds. An event stamped `06:46:21` and one stamped `06:46:21.900` may in reality be in either order, because the first could have happened anywhere within that second. Do not read sequence into differences smaller than the coarsest precision involved.

**Ties.** Many events share a timestamp, especially at one-second precision: the Banyan dataset has two failed logons on different workstations both at `04:05:00Z`. A sort leaves ties in arbitrary or input order. Within one source, use the source's own sequence number to break ties where one exists (Windows event logs number records with an `EventRecordID`, for instance); across sources, a tie means "same second, order unknown".

**Skew across hosts.** Within one host, events usually keep their true order even if the clock is off, because the error applies equally to all of them. Across hosts, a skew of a few seconds can reverse cause and effect. Treat cross-host orderings closer than the known skew as uncertain.

**Sorting by the wrong time.** A timeline sorted by ingest time shows the order in which the SIEM *learned* of events, which, for a laptop that reconnected late, can put its morning activity after its afternoon activity. Always state which time a timeline is sorted on.

**Local times in reports.** IST conversion for management can cross the date line (20:00 UTC on 3 November is 01:30 IST on 4 November); keep both columns.

## Common mistakes and misconceptions

**"The SIEM handles time zones automatically."** It handles them correctly only when the parser knows each source's offset. For sources that send naive times, someone must configure the zone, and that configuration is a frequent and silent failure.

**"All our servers are in India, so local time is fine."** Cloud logs, SaaS logs, partner data and many appliances are UTC by default, and an MSSP's clients may span zones. A SOC that standardises on local time will eventually merge it with UTC without noticing.

**Copying times from a viewer.** Consoles and viewers often display local time. Times copied from a screen into a case note must carry the zone, or be taken from the raw UTC value.

**Ignoring the year.** Classic syslog has none; a parser that supplies the current year misdates old logs replayed around the new year.

**Treating a 5.5-hour gap as real.** When two sources disagree by exactly the IST offset (or any other whole offset), suspect a zone error before building a theory around the gap.

## Security implications, detection and defence

Time is evidence, and like any evidence it can be wrong by accident or by intent.

**Accidental error** is the common case: wrong zones, drift, unsynchronised appliances, late-arriving events. Its cost is real. Correlation rules that depend on order or on short windows (such as the "spray then success" rule in Module 3, which requires the failures to come before the success) fail to fire; incident timelines misstate the order of attacker actions; and the time at which the organisation could first have noticed an incident, which matters for CERT-In's six-hour reporting expectation, may be wrongly stated.

**Deliberate manipulation** is rarer but must be considered. An attacker with administrative rights can change a host's clock so that later events appear at misleading times, and can alter file-system timestamps on files they touch. Windows records a change of system time as Security event **4616** ("The system time was changed"), and Linux systems can audit calls that set the clock through the audit subsystem; both are worth collecting and alerting on outside maintenance windows. The Banyan storyline ends with event 1102 (the audit log cleared on WS-104), a reminder that attackers do try to erase their timeline. The defence in both cases is the same: forward logs off the host quickly to a central store with its own trusted clock, so that the SIEM's `event.ingested` time provides an independent record of when each event was received, and so that later tampering on the host cannot rewrite what has already been collected.

**Defensive controls**, in summary:

- Synchronise every system to an approved NTP hierarchy (traceable to NIC or NPL for entities covered by the CERT-In Directions), and monitor synchronisation status and offset as a health metric.
- Normalise every timestamp to UTC with an explicit offset at ingestion; keep the original raw timestamp string for verification.
- Record both event time and ingest time on every event and monitor the gap per source.
- Collect and alert on system-time-change events and on audit-log clearing.
- Document, per source, its timestamp format, zone, precision and expected delay.

## Best practices

- Store, compare and sort in UTC; display local time only in labelled columns next to UTC.
- Write timestamps in ISO 8601 / RFC 3339 with an offset; never write a naive time in a case note.
- Make every datetime aware at the moment it is parsed; reject or flag naive values rather than guessing silently.
- State which time a timeline is sorted on, and its precision.
- Break ties with source sequence numbers where they exist; treat cross-source orderings closer than the known skew as uncertain.
- Schedule detections with ingest delay in mind (ingest-time selection or adequate look-back with de-duplication).
- Test each parser's time handling with a known sample event whose correct UTC value you have worked out by hand.

## Key takeaways

- A timestamp identifies an instant only when it has an offset; UTC with an explicit offset is the SOC's common clock, and IST is a fixed UTC+05:30.
- ISO 8601 / RFC 3339 (`2026-11-03T06:46:00Z`) is the canonical form; classic syslog lacks year and zone, Windows stores UTC but displays local time, and epoch values come in seconds or milliseconds.
- Naive and aware times cannot be compared safely; Python refuses outright, many tools silently guess.
- Clocks drift; NTP keeps them honest, Kerberos depends on it, and the CERT-In Directions require synchronisation to NIC or NPL-traceable time.
- Event time (`@timestamp`) builds the narrative; ingest time (`event.ingested`) shows when the SOC could know, and late-arriving events can slip past scheduled rules.
- Sort on parsed UTC instants, respect precision and ties, treat small cross-host gaps as uncertain, and always state which time a timeline uses.
