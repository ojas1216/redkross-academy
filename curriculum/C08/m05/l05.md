## Introduction and conceptual foundation

Every SOC lives with false positives. A detection rule is a hypothesis written in code: "if these fields take these values, something bad is probably happening". The world is larger than any rule author can imagine, so legitimate activity will sometimes satisfy the hypothesis. How a SOC handles those alerts decides whether its detections stay useful or slowly go blind.

Lesson 4 taught validation: asking what else would be true if an alert were real, and checking whether it is. This lesson deals with the alerts that fail that test, or that pass it but turn out to be authorised. It covers four connected skills:

- **Classifying correctly.** "Not malicious" is not one outcome but two. A *false positive* means the rule matched something it was never meant to match. A *benign true positive* means the rule worked exactly as designed and the activity really happened, but it was authorised. The difference decides what you do next.
- **Suppressing safely.** Some benign patterns recur every day. A documented suppression with an owner, a reason, a scope and an expiry stops them from flooding the queue without hiding anything else.
- **Feeding tuning back.** A false positive is evidence about a rule. The analyst's job is to turn it into a precise tuning request for detection engineering (Module 7, Lesson 5 covers the engineering side), not to fix it silently in the queue.
- **Recognising over-suppression.** Every exclusion is a place an attacker can stand without being seen. The worst outcome of false-positive handling is not wasted time; it is a real intrusion filtered out before any human looks at it.

The lab work uses `LAB_ASSETS/C08/triage.py`, the helper that ranks the work queue in Lessons 1 to 3. It contains one real, documented suppression. You will run it in a temporary copy of the kit, add a benign event that the suppression is meant to catch, watch it work, and then deliberately widen the suppression to see an attacker's persistence step disappear from the queue.

### Why false positives matter more than they seem

A single false positive costs a few minutes. The damage comes from volume and from what volume does to people. When most alerts from a rule are noise, analysts learn, quite rationally, to close that rule's alerts quickly. That habit is called *alert fatigue*, and it is the mechanism by which a real alert gets dismissed: not through negligence on the day, but through months of training by a noisy rule.
The opposite failure is just as real. A team under pressure to reduce noise can add exclusions until the queue is quiet. A quiet queue looks like a healthy SOC, but it may only mean the SOC has stopped looking. False-positive handling is therefore a balancing act with two failure modes, and the skill this lesson teaches is to reduce noise while keeping every reduction narrow, recorded and reversible.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| True positive (TP) | The rule detected what it was written to detect, and the activity is malicious or violates policy. |
| Benign true positive (BTP) | The rule detected what it was written to detect and the activity really happened, but it is authorised, for example an approved administrator action or a scheduled penetration test. |
| False positive (FP) | The rule matched something it was not meant to match, because of a flaw in the rule's logic, a wrong assumption about the environment or bad data. |
| False negative (FN) | Malicious activity the rule should have detected but did not. Over-suppression manufactures false negatives. |
| Undetermined | The evidence is insufficient to decide. The analyst records what is missing; this is a valid disposition, not a failure. |
| Suppression | A documented condition that stops a specific, known benign pattern from producing alerts (or from reaching the queue), with an owner, a reason, a scope and an expiry. |
| Exclusion | A permanent change to the rule's logic that removes a pattern from what the rule matches. Owned by detection engineering and reviewed like code. |
| Tuning | Any change to a rule, its threshold, its context or its suppressions made to improve its precision while preserving its coverage. |
| Alert fatigue | The loss of attention and care that follows repeated exposure to low-value alerts. |
| Precision (of a rule) | The share of its alerts that are true positives, TP / (TP + FP + BTP) when benign hits count as noise for the queue. |

Disposition labels vary between SOCs and products. Some teams fold benign true positives into "false positive", and some use "benign" or "expected activity". Learn the distinction behind the labels, then use your employer's terms. What matters is that the case record makes clear *why* the alert was not acted on.

## Classifying the alert: two questions in order

The cleanest way to separate the dispositions is to ask two questions, always in the same order.

**Question 1: did the rule match what it was written to detect?** Read the rule, not just its name. `R3 new_local_admin` in `minisiem.py` is written as "a Windows event with ID 4720 or 4732", that is, an account was created or a member was added to a security-enabled local group. If such an event really occurred, the rule matched its intent, whatever the reason behind the event. If instead the alert fired because the parser put the wrong value into `event_id`, or because the rule's condition is broader than its intent, the answer is no, and the alert is a false positive.

**Question 2: is the activity authorised, and can you prove it?** Only if question 1 is "yes" does authorisation matter. An approved change ticket, a maintenance window, a signed-off penetration test or a documented service behaviour makes the alert a benign true positive. No such record makes it a true positive, to be investigated or escalated (Lesson 6).

The order matters for two reasons. First, it stops a common error: closing a real event as "false positive" because the user is trusted. An IT administrator creating an account at 02:00 did create an account; the rule was right. Whether the act was authorised is a separate question with a separate kind of evidence. Second, the two outcomes lead to different fixes. A false positive says the rule is wrong and should change. A benign true positive says the rule is right but the environment contains expected instances of the behaviour; the rule should usually stay as it is, and at most a narrow suppression is added for the documented case.

### Examples from the lab rules

The six rules in `minisiem.py` give useful practice, because each has a plausible benign or erroneous trigger.

| Rule | What a FP would look like | What a BTP would look like |
| --- | --- | --- |
| R1 office_spawns_script | A parser maps the grandparent process into `parent_image`, so a user's own PowerShell window appears to come from Word. | A finance macro, approved and signed, that launches a reporting script. |
| R3 new_local_admin | The rule's ID list catches an event ID added by mistake, for an unrelated action. | The build account `itadmin` adds a runner account under change CHG-1042. |
| R4 large_upload | `bytes_out` is populated with downloaded bytes by a misconfigured parser, so large downloads look like uploads. | A user sends an approved 40 MB file to an auditor's sharing site. |
| R6 beacon_regular_small | A legitimate monitoring agent's heartbeat: regular and small, but not command and control. | Rarely applicable: the rule's intent is C2, so legitimate regular traffic is a mismatch of intent, not an authorised instance of it. |

These are illustrative scenarios, not events in the dataset. The R6 row shows that the line between FP and BTP depends on how the rule's intent is written. If R6 is documented as "detect machine-regular small requests", a heartbeat is a BTP; if it is documented as "detect command-and-control beaconing", the same heartbeat is a FP. This is one reason every rule needs a written description of its intent: without it, two analysts can disagree about the disposition of the same alert and both be right.

> [!IMPORTANT]
> "The user is an administrator" and "the host is a server" are context, not authorisation. Authorisation is a record: a change ticket, an approved request, a test plan, a documented service. If you cannot point to one, the disposition is not benign; at best it is undetermined, and you ask the owner.

**Key learning.** Ask "did the rule do its job?" before "was this allowed?", and accept only a record as proof of "allowed".

## Handling a false positive

A false positive is closed, but closing it is the smaller part of the work. The analyst holds the best evidence anyone will ever have about why the rule misfired: the exact event, the field values and the reason they do not mean what the rule assumed. That evidence must leave the analyst's head and reach detection engineering in a form they can act on.

### What the closure record must say

A false-positive closure that reads "FP, closed" is worthless to the next analyst and to the rule owner. A useful record answers five questions:

1. **Which rule and which alert?** Rule ID and version, alert ID, time.
2. **Why is it false?** The specific mismatch, such as "`parent_image` holds the grandparent process because the agent's parent field was empty and the parser fell back", not "looks normal".
3. **What evidence shows that?** The raw event, or the field values side by side with what the rule expected.
4. **How often?** Is this the first occurrence, or the fortieth this week? Recurrence turns a nuisance into a tuning priority.
5. **What change is proposed?** A concrete suggestion (fix the parser mapping, add a condition, raise a threshold), clearly marked as a proposal for the rule owner to evaluate.

Case-note discipline in general is the subject of Lesson 7; the point here is that a false positive is a finding about the detection, and it deserves the same evidence standard as a finding about an attacker.

### The tuning feedback loop

Tuning is not the analyst's decision alone, and in most SOCs the analyst does not edit production rules. The analyst records the false positive and raises a tuning request; detection engineering reproduces it, decides on the change, tests it against stored data (both the false positive and known true positives) and deploys it through review; the analyst then sees the result in the queue and confirms it. Module 7 covers rule testing and tuning in depth. From the queue side, the useful tuning options are:

| Option | When it fits | Main risk |
| --- | --- | --- |
| Fix the data | The FP comes from parsing or normalisation, not from the rule. | Other rules using the same field change behaviour too, usually for the better. |
| Tighten the logic | The rule is broader than its intent, for example a process name alone instead of a parent-child pair. | A tighter condition may miss a variant the broad one caught. |
| Adjust a threshold | The rule counts or measures, and the real baseline is higher than assumed. | Attackers who stay just under the new threshold are missed. |
| Lower priority, not visibility | The behaviour is suspicious on some assets and normal on others. | Low-priority alerts still need someone to look; this is the safest option. |
| Scoped suppression | A specific, documented benign pattern recurs (more often a BTP than a FP). | Scope creep and forgotten suppressions; see below. |

The fourth row deserves emphasis. `triage.py` already demonstrates the idea: its `priority()` function multiplies rule severity, confidence and asset criticality. Lowering a rule's confidence after measured false positives, or recording that an asset is low criticality, pushes the alert down the queue without hiding it. A hidden alert can never be found by a curious analyst; a low-priority one can.

> [!TIP]
> Track false positives per rule, not per analyst. The rule with forty FPs a week is a detection-engineering problem; the analyst who closes them is doing their job. Rule precision belongs with the SOC metrics introduced in Module 1, Lesson 7.

## Documented suppressions

A suppression is the right tool when a known, legitimate pattern will keep firing a correct rule. The rule should stay unchanged, because the same behaviour from anyone else is still interesting, but the specific documented instance should not consume an analyst every time it occurs.

### The anatomy of a safe suppression

Every suppression needs six things. Missing any of them turns a control into a blind spot.

| Element | Why it is needed |
| --- | --- |
| Rule | A suppression applies to one rule. A "global" allowlist for a user or host across all rules hides everything that entity might ever do. |
| Match condition | The narrowest set of fields that identifies the benign pattern: the account and the host and, where possible, the target or command. |
| Reason | The business justification, in words another analyst can check. |
| Reference and owner | A change or ticket number, and a named person or team who vouches for the pattern and is asked when it is reviewed. |
| Expiry | A date after which the suppression stops working unless someone renews it on purpose. |
| Audit trail | Who added it, when and who reviewed it, plus a record of every match it suppressed. |

The last element is often overlooked. A good suppression does not delete the alert silently; it records that a suppressed match occurred. If an attacker later uses the suppressed account, the evidence is still there for a hunter or an investigator.

### The suppression in the lab kit

`triage.py` holds its suppressions in one list, with a comment stating the policy:

```python
# Suppressions: (rule, field, value, reason, expiry) - every entry has an owner ticket.
SUPPRESS = [("R3", "user", "itadmin", "approved build account, CHG-1042", "2026-12-31")]
```

Read it element by element. The rule is `R3` (new local admin). The match condition is the field `user` equal to `itadmin`. The reason is "approved build account". The reference is change `CHG-1042`, through which the owner can be found. The expiry is 31 December 2026. The code that applies it, inside the main loop, is:

```python
if any(r == rid and hit.get(f) == v for r, f, v, *_ in SUPPRESS):
    print("suppressed", rid, hit)
    continue
```

For each rule hit, it checks whether any suppression names this rule and whether the hit's field equals the suppressed value. If so, it prints a `suppressed` line (the audit trail) and skips the hit with `continue`, so the hit never reaches the priority queue. The `*_` collects the remaining tuple elements, the reason and the expiry, and ignores them. Keep that detail in mind; it returns in lab run 4.

**Technical interpretation.** A suppression is a negative rule, evaluated before any analyst sees anything. Its scope is the set of all events it would match, now and in the future. The left entry's scope is the build account's group changes under R3. **Security implications.** The right column turns a detection into a generator of false negatives. The controls are peer review of every suppression, a policy that `host` or `user` alone is not an acceptable condition for high-severity rules, mandatory expiry, and periodic reports of what each suppression matched. The `suppressed` lines are what make that report possible.

**Key learning.** Make each suppression exactly as wide as the documented benign pattern, give it an owner and an expiry, and keep a record of what it hides.

### Lab run 4: an expiry that is only a comment

Return to the detail noted earlier: the matching code unpacks `r, f, v, *_`, so the reason and the expiry are never read. In the kit, the expiry is documentation, not enforcement. To prove it, make a copy of `triage.py` in which only the expiry changes to a date already past, `2026-10-31`, and run it against the 341-event dataset:

```terminal
$ python triage_expired_noenforce.py
suppressed R3 {'ts': '2026-11-03T05:40:00Z', 'host': 'BLD-01', 'user': 'itadmin', 'target_user': 'build_runner'}
10.8  R5 log_cleared             host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
```

(Only the first two lines are shown; the rest of the queue is the same as in run 2.) The expired suppression is still suppressing. This is how real environments accumulate suppressions that outlive the change, the project and sometimes the employee who added them. The fix is to make the expiry part of the match. A copy named `triage_expiry.py` adds `from datetime import date` and changes the check to:

```python
if any(r == rid and hit.get(f) == v and date.fromisoformat(exp) >= date.today()
       for r, f, v, _reason, exp in SUPPRESS):
```

`date.fromisoformat()` parses the `YYYY-MM-DD` string and the comparison keeps the suppression active up to and including its expiry day. With the past expiry, the benign alert returns to the queue (last two lines shown):

```terminal
$ python triage_expiry.py
 3.6  R6 beacon_regular_small    host=WS-104 (finance workstation) user=None (?) ip=n/a
 3.6  R3 new_local_admin         host=BLD-01 (unknown asset) user=itadmin (?) ip=n/a
```

The returned alert is low in the queue, because `BLD-01` is not in the `ASSETS` table and gets the default criticality, and `itadmin` is not in `USERS`, so its role prints as `?`. Its reappearance is the intended prompt: either the owner renews CHG-1042's suppression with a new date, or the activity should no longer be happening. Failing open in this way, back to visibility, is the safe direction for a suppression to fail.

Note also that this version has a stricter contract: every entry must now carry a valid date, so the "too noisy" host entry from run 3, with its empty expiry, makes the script stop with `ValueError: Invalid isoformat string: ''` as soon as it checks an R3 hit on WS-104 (tested in the same temporary copy). That is a feature. A suppression without an expiry should not load at all.

### A second silent failure: the field that is not there

The match uses `hit.get(f)`, the field names in the rule's *output*, and not every rule outputs the same fields. `R2 vpn_spray_then_success` returns `src_ip`, `users_failed`, `success_user` and `ts`, with no `user` column, and `R6 beacon_regular_small` returns `host`, `url`, `hits`, `min_b` and `max_b`. A suppression written as `("R2", "user", "gopal", ...)` would never match anything, because `hit.get("user")` is `None` for every R2 hit. Unlike over-suppression, this failure is noisy rather than blind: the analyst who requested it keeps seeing the alert and believes the tooling is broken. Test every new suppression against stored data, both a sample it should hide and a sample it must not hide, before relying on it. This is the same discipline Module 7 applies to rules.

## Common mistakes and misconceptions

- **"False positive" as a synonym for "not important".** A real, authorised event is a benign true positive. Labelling it FP sends detection engineering to "fix" a rule that works.
- **Treating identity as authorisation.** "It was the admin" is context. The disposition depends on a record of approval.
- **Closing without a reason.** A closure with no evidence cannot be audited, cannot inform tuning and cannot be reopened intelligently when an investigation later touches the same entity.
- **Suppressing in the queue what should be fixed in the data.** If the FP comes from a parser error, a suppression hides the symptom for one rule while the bad field misleads every other rule and every investigator.
- **Wide conditions.** Suppressing by host, by subnet, by department or by process name alone. Attackers run on the same hosts and use the same tools as administrators; living-off-the-land techniques depend on exactly that.
- **Permanent suppressions.** An entry with no expiry is a decision made once and never revisited.
- **Unreviewed changes.** One analyst adding a suppression at 03:00 on their own authority. Suppressions are security changes and deserve the four-eyes principle.
- **Believing a quiet queue is a healthy one.** A sudden drop in a rule's alert volume is as worth investigating as a sudden rise; it may mean a suppression, a broken parser or a stopped log source.

## Security implications, detection and defence

Suppressions and exclusions are configuration that decides what the SOC cannot see, so they are themselves an attack surface. An insider with SIEM rights, or an intruder who reaches the SIEM, can add an exclusion for their own account or host and act unobserved. Defend the suppression list like any other privileged configuration:

- **Access control.** Only a small group can change suppressions, through a reviewed change process, ideally with the list stored in version control so every change has an author, a reviewer and a diff.
- **Change alerting.** A change to the suppression list, or to a rule's exclusions, should itself raise an alert or at least appear in a daily report reviewed by someone other than the author.
- **Visibility of suppressed matches.** Keep suppressed hits searchable. A hunter asking "what did our suppressions hide this month?" should get an answer in one query; the `suppressed` lines in the lab are the miniature version of that.
- **Periodic review.** Review each suppression before its expiry with its owner. Remove dead ones (lab run 1), narrow wide ones (run 3) and enforce expiry (run 4).
- **Coverage awareness.** Each suppression reduces coverage of an ATT&CK technique on some scope. Record that, so coverage assessments (Module 7, Lesson 6) reflect what is really monitored.

## Best practices

1. Ask the two classification questions in order: intent first, authorisation second.
2. Accept only a record (change, ticket, test plan, documented service) as proof of authorisation.
3. Record every FP with the rule, the mismatch, the evidence, the frequency and a proposed change.
4. Prefer fixing data and logic, then lowering priority, and use suppression last.
5. Scope every suppression to one rule and the narrowest identifying fields; never host or user alone for a high-severity rule.
6. Give every suppression a reason, a reference, an owner and an enforced expiry, and log what it suppresses.
7. Test new suppressions against stored data, with samples they should and should not hide.
8. Monitor per-rule alert volume for unexpected drops as well as spikes.

## Key takeaways

- A false positive means the rule matched the wrong thing; a benign true positive means it matched the right thing, which happened to be authorised. They lead to different fixes.
- Ask "did the rule do its job?" before "was it allowed?", and accept only a record as proof of "allowed".
- Every false positive is evidence about a rule; record it precisely and feed it to detection engineering instead of muting it.
- In the lab, the kit's scoped suppression hid one benign event and nothing else, while a host-wide one hid the attacker's `svc_update` account.
- The kit stores an expiry but does not enforce it; an expiry only protects you if the matching code checks it.
- Suppressions decide what the SOC cannot see. Keep them narrow, owned, expiring, reviewed, logged and protected.
