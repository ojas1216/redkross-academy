## Lab objective and scope

This lab puts the whole of Module 5 to work on one alert queue. You will build the queue with the course's triage helper, decide the order in which to work it, and then take every alert through the same loop: enrich it, validate it against the raw events, give it a disposition, and write a case note that another analyst could continue from. At the end you will group the alerts into cases, export the evidence with a hash and produce a short queue summary for the shift lead.

The queue is small on purpose. Seven alerts let you do every step properly, with real queries and real output, instead of skimming. The skill being practised is not speed but **defensible decisions**: every disposition you write must be backed by a fact you can re-run, every inference must carry a confidence level, and every time must be in UTC. Lesson 7's rules for case notes apply throughout.

By the end of the lab you should be able to say, from evidence you produced yourself: which alerts are true positives and why, which belong together, which questions are still open, and where the evidence is with its hash.

> [!IMPORTANT]
> **Authorisation and scope.** Everything in this lab runs on your own computer against a synthetic dataset about a fictional organisation, Banyan Microfinance. All names, hosts and addresses are fictional; IP addresses use private ranges and the RFC 5737 documentation ranges, and domains end in `.example`. No network connection is made and no tool touches any real system. Work only in your own copy of the lab kit, never inside the course library folder.

## Key terminology

| Term | Meaning in this lab |
| --- | --- |
| Queue | The list of alerts awaiting triage, here printed by `triage.py` in priority order. |
| Priority score | `severity x confidence x asset criticality`, computed by `triage.py` from its `RULE_META` and `ASSETS` tables. |
| Enrichment | Context added to an alert from outside the event: asset role, user role, IP classification, intelligence matches. |
| Validation | Checking the raw events behind an alert for what else would be true if it were real. |
| Disposition | True positive (TP), benign true positive (BTP), false positive (FP) or undetermined. |
| Case | A group of alerts that share entities and time, investigated and documented together. |
| Scoping | Checking whether the activity extends beyond the entities already known. |

## How the lab works

The triage helper `LAB_ASSETS/C08/triage.py` sits on top of the course SIEM, `minisiem.py`. It imports minisiem's six saved correlation rules (R1 to R6), runs each against the loaded events, drops any hit that matches a documented suppression, enriches each remaining hit from three small tables (assets, users and each user's primary host), computes the priority score and prints the queue sorted highest first. Real SOCs pull the same context from a CMDB and an identity provider; here the tables are hard-coded so that you can read them.

The helper stops where an analyst's work begins. It does not look at the raw events, does not decide whether anything is real, does not group related alerts and writes no notes. Those are the steps you will perform, in a fixed loop, for every alert in the queue.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the route through the lab. It shows the triage loop you apply to each alert, framed by the steps that come before it (building and ordering the queue) and after it (grouping, evidence and handover). Its point is that triage is a repeatable procedure, so every alert receives the same scrutiny regardless of its score.

**Components.** The graph runs top to bottom through eight rounded boxes. *Load + build queue* (slate) is `minisiem.py load` followed by `triage.py`. *Order the work* (violet) is the decision about which alert to take first. Four boxes form the per-alert loop: *Enrich* (blue: asset, user, IP, intelligence), *Validate* (orange: raw events around the alert, the step that turns a score into evidence), *Disposition* (violet: TP, BTP, FP or undetermined, with confidence) and *Write the note* (green: CHECKED, FOUND, ASSESS, NEXT). After the loop come *Group + scope* (blue: cases by shared entities and a search for other hosts) and *Export evidence + summary* (dark: SHA-256, custody entry and a queue summary for the shift lead).

**Relationships and arrows.** Each solid arrow means "the output of this step is the input of the next". Enrichment supplies the questions validation must answer; validation supplies the facts the disposition rests on; the disposition and its facts are what the note records. The dashed arrow from *Write the note* back to *Enrich*, labelled "next alert", closes the loop. The solid arrow from *Write the note* to *Group + scope*, labelled "queue empty", is the only way out of it: you group, export and summarise once every alert has a note.

**Execution flow.** You run the first two steps once, the four loop steps seven times (once per alert) and the last two steps once. Grouping is placed after the loop in the diagram for clarity, but as you will see you start noticing shared entities from the second alert onwards and record them in each note's NEXT line.

**Decision logic.** The Disposition step is the branch point. A true positive moves into a case and, under Lesson 6's criteria, is escalated; a benign true positive or false positive is closed with its reason; an undetermined alert stays open with the missing evidence named. None of those branches skips the note.

**Technical interpretation.** Every step except *Order the work* and *Disposition* is backed by a command in this lab: `triage.py` builds the queue, `ioc_match.py` and the helper's tables enrich, `minisiem.py search` validates, `hunt.py` scopes and `evidence_export.py` exports. The two judgement steps are yours.

**Practical example.** For the R2 alert, *Enrich* adds the user's role and flags that the host was inferred; *Validate* runs the VPN query that shows eight failures from one address in under a minute followed by one success; *Disposition* is TP with high confidence; *Write the note* records those facts and opens CASE-0002.

**Security implications.** Skipping *Validate* is the classic triage failure: alerts are closed or escalated on their score alone. Skipping *Group + scope* hides the story, because each alert looks smaller than the incident it belongs to.

**Key learning.** One loop, applied to every alert: enrich, validate, decide, write. Order the queue by priority, but reconstruct the story by time.

## Lab steps

### Step 1: Build the queue

```terminal
$ python triage.py
10.8  R5 log_cleared             host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 7.2  R2 vpn_spray_then_success  host=WS-107 (sales laptop) user=gopal (standard) ip=external (documentation range in this lab)
 7.2  R1 office_spawns_script    host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 4.5  R4 large_upload            host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 3.6  R6 beacon_regular_small    host=WS-104 (finance workstation) user=None (?) ip=n/a
```

`triage.py` takes no arguments. Each line is one rule hit: the priority score, the rule ID and name, the host with its asset role, the user with their role, and a classification of the source IP. Any hit removed by a suppression would be printed first as a `suppressed` line; with the original dataset there are none. This output is identical to the kit's saved `triage_output.txt`; if yours differs, your dataset or script has been changed.

Check two scores by hand against the tables in the script, so that you trust the arithmetic. R5 has severity 4 and confidence 0.9 in `RULE_META`, and WS-104 has criticality 3 in `ASSETS`: 4 x 0.9 x 3 = 10.8. R6 has severity 2 and confidence 0.6 on the same host: 2 x 0.6 x 3 = 3.6. R2 scores 4 x 0.9 x 2 = 7.2 because WS-107 has criticality 2.

Before you touch any alert, read the queue for what the helper has *inferred*. Three fields are not observations:

- `host=WS-107` on R2 comes from the `PRIMARY_HOST` table. VPN events carry no host.
- `user=None (?)` on R6 is a gap, not a finding: the rule groups by host and URL and never selects the user.
- `ip=n/a` on R1, R3, R4, R5 and R6 means the rule's query did not select a source IP column, not that there was no IP.

### Step 2: Order the work

The queue says R5 first. That is right for *urgency*: a cleared Security log on a payments approver's workstation is the most severe signal, and it suggests someone is covering tracks. But the queue order is not the order of events. Six of the seven alerts share WS-104 and `divya`, which already tells you they are probably one story, and stories are understood forwards in time.

A sensible plan, recorded as the first note in your shift log:

1. Take R5 first and validate it quickly, because if it is real it triggers escalation immediately (Lesson 6).
2. Take R2 next: same score as R1, but it involves a different user, an external address and possibly a live remote session, so it may need its own case.
3. Work the WS-104 alerts (R1, R3 x2, R4, R6) in time order, so that each one's validation builds on the previous.

### Step 3: R5 log_cleared (score 10.8)

**Enrich.** WS-104 is the finance workstation; `divya` is a payments approver (from `ASSETS` and `USERS` in `triage.py`). Event ID 1102 is Windows' "audit log was cleared" event.

**Validate.** Look at every non-proxy event on the host, and check whether any other host cleared its log:

```terminal
ts | source | event_id | user | target_user
2026-11-03T03:18:00Z | windows | 4624 | divya | None
2026-11-03T03:29:00Z | sysmon | 1 | divya | None
2026-11-03T04:31:00Z | sysmon | 1 | divya | None
2026-11-03T04:50:00Z | sysmon | 1 | divya | None
2026-11-03T05:14:00Z | sysmon | 1 | divya | None
2026-11-03T06:14:00Z | sysmon | 1 | divya | None
2026-11-03T07:02:00Z | windows | 4720 | divya | svc_update
2026-11-03T07:03:00Z | windows | 4732 | divya | svc_update
2026-11-03T08:17:00Z | windows | 1102 | divya | None
$ python minisiem.py search "SELECT host, ts, user FROM events WHERE event_id=1102"
host | ts | user
WS-104 | 2026-11-03T08:17:00Z | divya
```

The first query lists the host's Windows and Sysmon events in time order (the `<>` operator means "not equal"); the second checks the whole estate for 1102. The log clear at 08:17:00Z is the last event on the host, and it follows an account creation and group change an hour earlier. It is the only 1102 in the dataset.

**Disposition.** TP, high confidence. A Security log clear is never routine on a user workstation, and here it follows other alerts on the same host. The event's user field shows the activity ran under `divya`'s account; whether `divya` personally did it is a separate question (an attacker running code in her session would produce the same record).

### Step 4: R2 vpn_spray_then_success (score 7.2)

**Enrich.** Run the intelligence matcher, which compares a small fictional feed with the events:

```terminal
$ python ioc_match.py
MATCH    domain cdn-telemetry-sync.example       conf= 85 hits= 18 first=2026-11-03T06:17:00Z src=ISAC-A TLP:AMBER
MATCH    domain banyan-payroll-update.example    conf= 70 hits=  1 first=2026-11-03T06:12:00Z src=internal TLP:GREEN
```

Each line gives the match status, indicator type and value, the feed's confidence (0-100), the number of matching events, the first match time, the source and the TLP label. The output does not print each indicator's context; that is in the `FEED` table at the top of the script. The spraying address 203.0.113.66 is listed by ISAC-A for "password spraying against VPNs", confidence 60, with 9 hits. Keep this output: it enriches R1, R6 and R4 as well.

**Validate.** Pull every VPN event from that address, then every VPN event for `gopal`:

One failure for each of the eight accounts, seven seconds apart, then a success for `gopal` three minutes later from the same address: the shape of a password spray that found one working password. On its own it proves nothing; this could be `gopal` working from home. But once the credential is known to be compromised, every later session with it is suspect until the user confirms it.

**Disposition.** TP, high confidence that the `gopal` credential is compromised; method unknown. It goes into its own case, CASE-0002, because nothing yet connects it to WS-104. Record the link to the WS-104 activity as a low-confidence hypothesis, not a fact.

### Step 5: R1 office_spawns_script (score 7.2)

**Validate.** The `command_line` field is not one of minisiem's columns, so read it from the raw JSON with SQLite's `json_extract` function, then look at the host's web activity around the alert:

```terminal
$ python minisiem.py search "SELECT ts, json_extract(raw,'$.parent_image') AS parent, image, json_extract(raw,'$.command_line') AS cmd FROM events WHERE source='sysmon' AND host='WS-104' AND lower(parent_image) LIKE '%winword%'"
ts | parent | image | cmd
2026-11-03T06:14:00Z | C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | powershell.exe -NoP -W Hidden -EncodedCommand <redacted-for-course>
$ python minisiem.py search "SELECT ts, url, bytes_out FROM events WHERE host='WS-104' AND source='proxy' AND url NOT LIKE '%ping%' AND ts >= '2026-11-03T06:10:00Z' AND ts < '2026-11-03T08:20:00Z' ORDER BY ts"
ts | url | bytes_out
2026-11-03T06:12:00Z | https://banyan-payroll-update.example/invoice.docm | 812
2026-11-03T06:40:00Z | https://mail.banyan.example/ | 1134
2026-11-03T07:19:00Z | https://cdn.example.org/ | 1250
2026-11-03T07:44:00Z | https://intranet.banyan.example/ | 1450
2026-11-03T08:02:00Z | https://mail.banyan.example/ | 3177
2026-11-03T08:11:00Z | https://mail.banyan.example/ | 2607
2026-11-03T08:12:00Z | https://files-share-drop.example/upload | 48200000
```

`json_extract(raw,'$.field')` pulls one field from the stored JSON; `AS` names the output column; `lower(...) LIKE '%winword%'` makes the match case-insensitive. The second query deliberately excludes the beacon URL so that the rest of the host's browsing is readable. The `NOT LIKE` filter is safe here only because the query is restricted to `source='proxy'`, where every event has a URL; on the full table it would silently drop events whose URL is NULL.

Two minutes after a macro-enabled document (`.docm`) was downloaded from a look-alike of the company's own name, Word started PowerShell with a hidden window (`-W Hidden`), no profile (`-NoP`) and an encoded command. The course has redacted the command content; in a real case, decoding it from endpoint telemetry would be a Tier 2 task.

**Disposition.** TP, high confidence: code execution from a macro document. The look-alike domain is on the internal intelligence list (confidence 70).

### Step 6: R6 beacon_regular_small (score 3.6)

The lowest score in the queue, and one of the most important alerts. **Validate** with the hunt script's beaconing statistics:

```terminal
$ python hunt.py
H1 beaconing candidates (>= 8 requests, interval CV < 0.2)
  WS-104 https://cdn-telemetry-sync.example/api/v2/ping n=18 mean_gap=300s cv=0.004
H2 parent-child pairs seen on only one host
  WINWORD.EXE -> powershell.exe hosts=1 n=1
H3 other hosts contacting known-bad domains
  none found
```

H1 computes the gaps between requests for every host and URL pair and reports pairs whose coefficient of variation (standard deviation divided by mean) is below 0.2. Eighteen requests with a mean gap of 300 seconds and a CV of 0.004 are machine-regular: something on WS-104 called the same URL every five minutes, starting at 06:17:00Z, three minutes after PowerShell started. The domain is on the ISAC-A feed as command-and-control for a loader seen in finance-sector phishing (confidence 85, TLP:AMBER, so the note inherits TLP:AMBER).

**Disposition.** TP, high confidence: command-and-control beaconing. Record why the score was low (rule severity 2, confidence 0.6) as feedback for detection engineering: in context this alert was worth far more than its number.

### Step 7: R3 new_local_admin, two hits (score 5.4 each)

**Validate.** The Step 3 query already showed both events: at 07:02:00Z event 4720 (a user account was created) for `svc_update`, and at 07:03:00Z event 4732 (a member was added to a security-enabled local group), with the raw event naming the group `Administrators`. Both ran under `divya`'s account, 48 minutes after PowerShell started. The name imitates a service account, a common way of hiding persistence in plain sight. Check whether the new account was ever used:

```terminal
$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE user='svc_update'"
COUNT(*)
0
```

No event in the dataset was performed *by* `svc_update`. That is a bounded statement: it covers this dataset's sources, not the host's full history after 08:17:00Z, and the cleared Security log means some Windows events on WS-104 may be missing.

**Disposition.** TP, high confidence: persistence through a new local administrator. The two hits are **one activity**, create then elevate, so write one note that covers both alert IDs. Counting them as two incidents would inflate the queue metrics; closing one as a "duplicate" without a note would lose the group change.

### Step 8: R4 large_upload (score 4.5)

```terminal
WS-107 | 3999
WS-102 | 3991
WS-106 | 3880
WS-105 | 3825
```

`GROUP BY host` gives one row per host and `ORDER BY 2 DESC` sorts by the second column, largest first. Every other host's largest request is under 4,000 bytes. **Disposition.** TP, *medium* confidence of exfiltration. The proxy recorded the size and destination, not the content. What the 48.2 MB contained is the most important open question for the incident, because it decides whether personal data was involved and whether notification obligations apply.

### Step 9: Scope, group and export

**Scope.** H3 in the `hunt.py` output (Step 6) searched for any host other than WS-104 contacting the three suspicious domains and found none. Record it with its limit: hosts whose traffic bypasses the proxy are not covered. H2 found the Word-to-PowerShell pair on only one host.

**Group.** Six alerts (R1, R6, R3 x2, R4, R5) share WS-104 and `divya` within two hours: **CASE-0001**. R2 involves a different account and an external address, with no event linking it to WS-104: **CASE-0002**, cross-referenced from CASE-0001 as a possible link.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The table is the end state of the lab: every alert in the queue, the single fact that decided it, its disposition and the case it belongs to. It is the summary a shift lead reads first, and the checklist a reviewer uses to confirm nothing was skipped.

**Components.** Five columns: *Alert* (rule ID and name), *Score* (from `triage.py`), *Deciding fact* (the validated observation), *Disposition* and *Case*. Six rows, because the two R3 hits share one row. The rows keep the queue order from Step 1, so the table can be checked against the helper's output line by line. Rows are toned by what they are: red for the alerts that point to compromise of WS-104 or the VPN account, orange for R4, whose confidence is only medium, and violet for R6, the lowest-scored alert, singled out as the lesson of the queue.

**Relationships.** Read across each row: score, then evidence, then decision. The *Case* column shows the grouping: five rows map to CASE-0001 and one, R2, to CASE-0002. The absence of a row linking the two cases is deliberate; the link is a hypothesis recorded in the case notes, not a finding.

**Execution flow.** The table is filled one row at a time as each pass of the triage loop ends, which is why it exists before the case records are finished. A row with an empty *Disposition* cell is an alert still in the loop.

**Decision logic.** Every disposition is TP, but the confidence differs. R4 is medium because the upload's content is unknown. All others are high because at least two independent facts agree, for example the download and the Office-to-PowerShell process start for R1.

**Technical interpretation.** Compare the *Score* column with the importance of each row. R6, the beacon, scored 3.6, the lowest in the queue, yet the hunt statistics (CV 0.004) and the ISAC-A intelligence match made it one of the strongest signals of compromise. The score combines rule-level severity and confidence with asset criticality; it cannot know about corroboration across sources. That is the analyst's contribution.

**Practical example.** A shift lead reading this table at 09:30Z knows immediately that the queue is clear, that two cases are open and escalated, and that the most urgent open questions are the upload content and the `gopal` sessions.

**Security implications.** If the queue had been worked strictly by score with a cut-off, for example "investigate 5.0 and above", R4 and R6 would never have been validated, and the exfiltration and command-and-control channel would have been missed. Priority orders the work; it must not decide what is ignored.

**Key learning.** Work every alert in the queue to a written disposition. Scores tell you where to start; validated facts tell you what happened.

## Interpreting the results

Taken together, the queue tells a story that no single alert told. In time order: a macro document downloaded at 06:12:00Z, executed hidden PowerShell at 06:14:00Z, and the host beaconed to a command-and-control domain from 06:17:00Z. A local administrator account was created at 07:02:00Z, 48.2 MB left the host at 08:12:00Z and the Security log was cleared at 08:17:00Z. Separately, at 06:42Z, an external address sprayed the VPN and gained access as `gopal`.

Three things stand out. First, the order of the queue was almost the reverse of the order of events: the alert at the top (R5) was the last thing the attacker did. Second, the lowest-scored alert (R6) was among the most informative. Third, the helper's enrichment needed correcting twice: `host=WS-107` was a lookup, and `user=None` on R6 was a gap in the rule, not a finding. Those corrections belong in the notes and as feedback to detection engineering.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `loaded` count is not 340 | Dataset modified or appended to | Re-copy the kit into a fresh folder |
| Extra `suppressed` lines or extra R3 hits | Dataset or `SUPPRESS` table changed | Compare with `triage_output.txt`; re-copy the kit |
| `no such column: command_line` | Field is only in the raw JSON | Use `json_extract(raw,'$.command_line')` |
| `no such table: events` | `minisiem.py load` not run in this folder | Run `load` first, from the same directory |
| `sha256sum: command not found` (Windows) | No Git Bash or similar | Use `Get-FileHash -Algorithm SHA256 <file>` in PowerShell |
| Hash of a saved search differs from a colleague's | CRLF versus LF line endings | Record platform and method with the hash |

## Cleanup

Delete `minisiem.db` and the `evidence` folder from your working copy when you have finished, or delete the whole working folder. Nothing outside it was changed. If you keep your notes, keep the evidence files with them: a note that references a hash is only useful while the file exists.

## Reflection and checklist

Before you consider the lab complete, check each item:

- Every alert in the queue has a written note with CHECKED, FOUND, ASSESS and NEXT.
- Every time in your notes is UTC with a `Z`.
- Every fact cites a query or an evidence item; every inference has a confidence level.
- `host=WS-107` is labelled as an asset-mapping lookup, and the R6 user gap is recorded.
- The two R3 hits are covered by one note.
- Negative results (H3, `svc_update` usage) are recorded with their limits.
- Both cases list evidence with SHA-256 hashes, and the VPN gap in the host export is written down.
- Next steps have owners.

Then answer for yourself: which alert would you have closed too early if you had worked by score alone, and what in your notes would let a reviewer see that you did not?

## Key takeaways

- Triage is one loop applied to every alert: enrich, validate, decide, write.
- Queue order is about urgency; investigation order is about time. Use both.
- Scores combine rule and asset properties; only validation across sources reveals that a 3.6 beacon matters more than its number.
- Enrichment can be wrong or inferred. Label lookups and gaps as such.
- Related alerts become one case; a duplicate pair of hits is one activity with one note.
- Evidence exports have blind spots. Save what the export misses and record how, including the platform for any hash.
