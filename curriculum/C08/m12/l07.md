## Detection goal

Design a defensive review rule for a successful VPN authentication preceded by failures for multiple distinct identities from the same observed source. The purpose is to elevate an identity question. It cannot identify the operator, establish account compromise, or link a workstation incident by itself. Use only the given synthetic authentication records. In this lesson you will define the bounded correlation, check positive and negative controls, and explain how a real SOC would verify the result through its owning service.

The rule uses a five-minute window preceding the success and a minimum of five distinct identities with failures. Those are teaching thresholds. Selecting a threshold depends on the environment, typical legitimate activity, collection and the acceptable review workload. A source may serve several users through shared egress. A narrower detector can miss distributed activity, while a broader one may create excessive review. The exercise's fixed input allows you to reason about the chosen contract before proposing any operational tuning.

## Define the grouping and time semantics

Group failed authentications by the recorded source address for the same eligible authentication service. The small fixture contains only one VPN source. An implementation across services would also need to preserve which service and scope own the records, and avoid combining unrelated tenants. For each successful authentication, evaluate failures strictly earlier than it and no more than three hundred seconds before it. The condition includes an event exactly five minutes earlier and excludes the simultaneous case when causality cannot be inferred from time. Define how to handle source clock error instead of silently treating unreliable values as precise.

Count distinct failed identities. Repeated failures for one identity may warrant a different rule but should not satisfy this particular diversity criterion on their own. Retain the actual source event identities so the analyst can distinguish duplicates from additional observations. These are complementary controls. Counting distinct identities protects the threshold interpretation. Deduplicating repeated source receipts protects event accounting and can improve performance and accuracy when later stages count or link records.

The result should include success identity, time, address, count and a reference to the failure evidence. Do not assume the success identity is present among the failed ones. This rule's purpose is to look for a success after a diverse pattern in the same source and time scope. A stricter rule that also requires a matching failed identity would ask a different question. In the supplied fixture the eight failed identities and the eventual successful one are intentionally distinct, which makes the difference testable.

## Execute the supplied synthetic test

The array below expands the capstone summary into fictional individual records for this test. It includes additional synthetic examples for threshold evaluation. These expanded records are not more evidence for the paper case in Lesson 4. Run this standalone Python script locally. It parses times and evaluates the selected records in memory without contacting any service.

```python
from collections import defaultdict

events = [
    ("08:10:00", "203.0.113.60", "STAFF-100", "failure", "v01"),
    ("08:10:07", "203.0.113.60", "STAFF-200", "failure", "v02"),
    ("08:10:14", "203.0.113.60", "STAFF-300", "failure", "v03"),
    ("08:10:21", "203.0.113.60", "STAFF-400", "failure", "v04"),
    ("08:10:28", "203.0.113.60", "STAFF-500", "failure", "v05"),
    ("08:10:35", "203.0.113.60", "STAFF-600", "failure", "v06"),
    ("08:10:42", "203.0.113.60", "STAFF-700", "failure", "v07"),
    ("08:10:49", "203.0.113.60", "STAFF-800", "failure", "v08"),
    ("08:10:49", "203.0.113.60", "STAFF-800", "failure", "v08"),
    ("08:14:00", "203.0.113.60", "STAFF-382", "success", "v09"),
    ("08:15:00", "198.51.100.40", "STAFF-410", "failure", "v10"),
    ("08:16:00", "198.51.100.40", "STAFF-411", "success", "v11"),
]

def seconds(clock):
    hour, minute, second = map(int, clock.split(":"))
    return 3600 * hour + 60 * minute + second

failures = defaultdict(list)
seen = set()
duplicate_receipts = 0
for clock, address, identity, outcome, event in sorted(events):
    if event in seen:
        duplicate_receipts += 1
        continue
    seen.add(event)
    time = seconds(clock)
    if outcome == "failure":
        failures[address].append((time, identity))
    elif outcome == "success":
        preceding = {
            user for stamp, user in failures[address]
            if 0 < time - stamp <= 300
        }
        state = "review_identity" if len(preceding) >= 5 else "below_threshold"
        print(clock, address, identity, len(preceding), state)
print("Duplicate receipts:", duplicate_receipts)
```

The verified output is:

```text
08:14:00 203.0.113.60 STAFF-382 8 review_identity
08:16:00 198.51.100.40 STAFF-411 1 below_threshold
Duplicate receipts: 1
```

The data includes one deliberately repeated event ID for the same source and exact row. It is accounted for once in the correlation. The eight distinct failures precede the first observed success by less than five minutes and reach the minimum count. The other address has only one preceding distinct failed identity. A yes-or-no verdict without these counts would be harder to review. The result also shows the identity on each success so the next owner can determine which account needs verification and which remains below this rule's threshold.

## Work the negative cases

Try a written variation with five failures for the same identity in one minute and a success two minutes later. The rule should count one distinct identity and stay below the stated threshold. That does not mean repeated failures on one account are never suspicious. It means this detector focuses on a different pattern. Describe the independent monitoring that might notice concentrated failures without changing the interpretation of this test. A good classifier is explicit about the observations it was meant to select.

Try a second source variation. Suppose four valid failed identities are observed for one address and one for another. A successful record at the first address should see only four preceding identities. Pooling across all addresses would create a different candidate and may wrongly correlate unrelated events. Work out a separate policy if the environment requires cross-source reasoning. For this test, preserve the exact group definition. If two VPN services reuse a shared NAT address, keep their namespace visible rather than trusting the address by itself.

Now try a boundary variation. Add a failed identity exactly five minutes before a success. It can count in this exercise. Move it one second earlier and it no longer counts. Move it to the same instant as the success and it does not meet the preceding condition. These controlled examples help a reviewer find off-by-one errors and faulty timestamp normalisation. The sample uses one day's UTC values. At midnight or across several dates, conversion to seconds since the start of the day would be insufficient. A deployed implementation needs full timestamps and tests across day boundaries.

## Investigate the result without overclaiming

For a candidate, collect the source's specific verification context. Ask whether the common source belongs to known egress and whether the successful identity's session was expected. An approved operational test or shared service can explain some record patterns. Compare the date, source identity and evidence of which work was authorised. A generic explanation about shared addresses should not automatically clear an anomalous session. Likewise, multiple failures followed by success can justify prompt review without proving which credentials were used. Keep those limits in the analyst handoff.

When there is no provider access, record the missing source and ask the authorised identity owner to review. ?No session activity in checked logs? and ?could not check session activity? describe different states. Link the result to the original success and grouped failure evidence. If another case concerns a workstation, examine a shared verified client or session link before grouping. Temporal overlap can produce a useful hypothesis but the rule groups authentication evidence, not endpoint evidence. This conclusion remains true even if both cases are urgent.

Keep legitimate exclusions reviewed and scoped. If a recurring training service supplies an approved synthetic pattern, label its expected activity with the relevant environment, window and source. Do not use one confirmed exception to erase all future candidates for a common address. A review team can compare positive ground truth, approved routine activity and unsupported cases before changing thresholds. Preserve enough context to verify outcomes when an exception or known baseline becomes stale.

## Define deployment evidence as a paper exercise

Write additional test cases for missing identity, malformed time, unverified collection and conflicting duplicate identities. The miniature code presumes valid strings in a fixed fixture and has no production-grade parser. A real workflow should report invalid or missing fields and avoid treating an unavailable source as clean. Ask how it would handle arrival order. A repeated event can arrive with a new ingestion time. If event time and source identity remain the same, it should not become an additional distinct failure. If a late source record changes the history of an existing success, document how the reviewer sees the corrected assessment.

Decide how to store and expire grouped history in a deployment without changing the training code. The local example holds all rows in a small list and compares a defined lookback. A streaming system needs bounded memory, an event identity strategy, and a way to re-evaluate near the window boundary when valid late data arrives. The policy should state the permitted sources, retention, expiry and notification and approval boundaries. These are design questions, not proof that the toy example implements them. A clear handoff calls out these limits alongside the known positive and negative results.

## Use the count to explain rather than hide context

A report with a verified count can still conceal the source of that count. Name the address group, time basis, distinct identity field and exact inclusion rule. Explain that the fixture intentionally gives the later successful identity a value not present among the preceding failures. A reviewer should not reinterpret the rule as proving that account was targeted in the failed set. If a future rule narrows to successes involving the failed identities, document the different question and rerun the original fixture. The first candidate might change, and that would be an intended design difference only if the revised acceptance criteria say so.

Test how correlation changes under duplicate and late delivery. One source event can be received twice, but a separate genuine failure by the same identity should remain as a different event. Counting distinct identities can still yield the same threshold outcome in both situations. That does not make identical event IDs and distinct repeat failures equivalent for auditing. Record enough detail to diagnose delivery duplication separately. In a lab report, include the printed duplicate count and a brief account of which row it represents.

Consider late arrival more carefully. In a saved dataset sorted by UTC, a late-delivered event can be placed in its occurrence window. An online pipeline may have already issued a result based on what arrived at the time. Policy must define whether a late valid record revises a previous result, creates a follow-up note or is routed for review because its age exceeds accepted bounds. Preserve the historical and corrected results if the change affects an analyst decision. The difference between old evidence and late ingestion can also inform a telemetry reliability review.

## Evaluate the proposed rule with reviewers

Give one reviewer the original two outputs and ask what data those lines support. The first demonstrates a sample success after eight distinct preceding failures from the same recorded source. The second shows one preceding identity and falls below this rule's threshold. The output cannot establish a live session or a person's intent, and it is based on sample expansion rather than a provider audit. The reviewer should reference the same day and source when describing coverage. If they use the example to supply missing facts about the paper case, reintroduce the boundary between tests and evidence.

Let a second reviewer propose a change to the threshold. A lower minimum might catch more variations but could increase manual review where many clients share egress. A higher minimum may reduce workload and also suppress signals important to the owning team. Ask for evidence from appropriate benign and investigated cases before committing either choice. Review which address groups and services are included and whether client identity data supports a stronger grouping. Always define how investigators can see what was filtered and who approves changes affecting visibility.

Finally, discuss what to do when a source changes its status encoding. A parser that treats any unknown value as success could create meaningless candidates, while one discarding it silently may hide a gap. The workflow should validate recognized outcomes and route unresolved records with a reason. In the lab the data is already valid and the code does not model repair of corrupt records. This is a boundary to record in the handoff and a valuable next engineering test. The exercise demonstrates controlled, reviewable logic without pretending to cover every production condition.

## Key takeaways

- Count distinct failed identities for the same source within a documented preceding interval.
- Check exact identity and event scope before grouping or retry handling.
- Test boundary times, repeated identities, separate sources and coverage gaps.
- Route the observed candidate for verification rather than assuming compromise or linkage.
