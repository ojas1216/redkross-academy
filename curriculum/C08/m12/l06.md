## Detection goal

Turn the FIN-21 process observation into a defensive review rule. The exercise uses synthetic records to test a sensor-observed parent and child relationship. It does not generate the behaviour or run a suspicious process. The intended result is an analyst review candidate with an evidence reference. A process relationship by itself does not prove that a document caused it or that the resulting operation was harmful. The rule should capture a meaningful observation and help the SOC look for corroboration.

Start with the detection question: ?Which valid endpoint records show an Office application starting a process in the defined script-interpreter category?? Define the category as part of a reviewed mapping. In this exercise, the records are already normalised into short category names. An actual deployment would need to validate the mapping against its own schema and authorised application inventory. Use the sensor's parent and child fields, not a shared device name or time alone. The rule is for process observations, so proxy rows are outside its supported input scope even if they contain similarly named fields.

## Set an input and output contract

Require source type, asset identity, source event identity, parent category and child category. In a live system, record the event time and clock basis as well, especially if analysts review groups of observations in intervals. The mock is a one-record classification with no temporal join, and the rows omit time. A missing asset or event identity limits source attribution and repeat handling. It should produce an input review result rather than an alert about an arbitrary device. A row from another source type should be accounted for separately rather than silently trusted or dismissed.

The primary result should carry the exact sensor and event reference. Preserve what triggered the rule and note the expected follow-up. An analyst can compare document and user evidence, legitimate business activity and other sensor records. A review rule that recommends these checks supports consistency. It must not bypass the scope and approval process for consequential controls. The matching result in this exercise requests review, and the simulation cannot isolate any endpoint.

Use stable identity to handle delivery repeats. In the supplied data the combination of endpoint source and event identity represents the same observation. Real schemas can reuse identifiers across devices, tenants or days; inspect source guarantees before choosing a key. If it is not globally unique for a given source, use the necessary source scope and identity. In a test, compare a duplicate receipt with another distinct observation that happens to have the same parent and child classes. The first should link to the original record. The second should remain visible to analysts.

## Specify test cases before running

P3 is an Office-to-viewer event and P4 uses the script category under a different parent. These control rows test each side of the rule independently. P5 lacks an asset identity. It must remain a repair or review finding even though its categories would match. P6 is a proxy row and must not act as a substitute for endpoint process evidence. Write your expected classifications on a worksheet before looking at the result.

Think about the reported output and the evidence proving it. The test should show exactly one new candidate for P1 and one repeat linked to it, two category negatives, one missing input and one unsupported input. No branch needs to execute a process. The distinctions are more informative than a binary rule result. An unsupported source cannot establish a negative process finding. A data gap still needs ownership. A category negative means only that the specific pair did not match in an otherwise eligible record. These meanings guide both review and metrics.

## Run the local checks

Use the following Python with the supplied fixture. The code classifies text values and prints results. It has no system or network calls.

```python
events = [
    ("P1", "endpoint", "FIN-21", "office", "script", "E-301"),
    ("P2", "endpoint", "FIN-21", "office", "script", "E-301"),
    ("P3", "endpoint", "FIN-21", "office", "viewer", "E-302"),
    ("P4", "endpoint", "OPS-03", "management", "script", "E-407"),
    ("P5", "endpoint", "", "office", "script", "E-408"),
    ("P6", "proxy", "FIN-21", "office", "script", "E-409"),
]

seen = set()
for label, source, asset, parent, child, event in events:
    if source != "endpoint":
        state = "unsupported_source"
    elif not asset or not event or not parent or not child:
        state = "review_input"
    elif (source, event) in seen:
        state = "duplicate_receipt"
    else:
        seen.add((source, event))
        state = (
            "review_process_pair"
            if parent == "office" and child == "script"
            else "no_pair_match"
        )
    print(label, state)
```

```text

P2 duplicate_receipt
P3 no_pair_match
P4 no_pair_match
P5 review_input
P6 unsupported_source
```

Check the conditions against the expected states. A repeated source event ID with different observed attributes deserves reconciliation rather than a casual duplicate disposition. The toy rules assume that exact event IDs do not change facts. A production implementation should examine contradictory records and identity guarantees. It should retain the event date and collection source, and verify the scope in which an ID is unique. Note these boundaries in your report. ## Review quality and false positives

A particular legitimate tool might create a similar relationship during approved work. The rule should present a candidate with enough evidence to investigate. An approved change record, software identity, parent and child details and execution context can distinguish several ordinary cases. If the team later proposes tuning, examine a known legitimate event and the original positive and compare scope. A broad exception for all events on a workgroup could obscure unexpected behaviour. Consider adding explicit context for review before suppressing anything. Preserving the source lets analysts verify the match when the exception no longer applies.

Collection determines coverage. The detector does not see a device with missing endpoint telemetry. Delayed events might arrive after the analyst has already briefed the case. A report based on the detector should state which sources and interval were checked, and whether its required fields were present. An absence of review candidates does not establish the absence of the behaviour throughout the environment. Write a monitoring request for WKS-05's delayed feed and note how that uncertainty affects a fleet-wide conclusion.

An investigation can use more than this one rule. A related document request may strengthen an endpoint case, and subsequent unexpected destination records can guide scoping. This detection does not claim those sequences when it observes a single process event. If the SOC adds a separate correlation, document its fields and time window and test against unrelated events on the same device. Keep the evidence from the individual observations available for analysts. The case may find reasons to act even when a correlation rule did not run, so a monitoring gap should not replace independent judgement.

## Reason from a detector result to analyst action

A useful detector output names the observed parent, child, asset and source event. It also points to the result state and next owner. A new candidate might lead to asking the endpoint owner for added context or checking related sources in the local case. The scope of the output matters. If it says suspected process behaviour, preserve the category definitions and don't call it a confirmed document verdict. If it only says no match, state which source and condition were evaluated. In a mixed audit where some records were invalid, count and route those separately.

A peer should review the design without using any live target. Ask them to predict what happens when an otherwise relevant pair comes from a proxy row, when it arrives twice from the same endpoint event and when its asset identity is missing. A detector that treats those three records as three separate incidents did not meet the exercise contract. A detector that hides them all also fails evidentiary accounting.
