## Introduction and conceptual foundation

An unauthenticated scan sees a system the way an outsider does: through open ports, banners and the responses services give to anonymous probes. That view is essential, because it is the attacker's starting point, but it is also shallow and frequently wrong. Most of the software on a server never listens on a network port. A vulnerable library, an outdated browser on a jump host, a kernel missing a privilege-escalation fix or a weak local configuration is invisible from the network. And for the services that do listen, the scanner can only guess their patch level from what they choose to announce.

An **authenticated scan** (also called a credentialed scan) solves both problems by giving the scanner a valid account on the target. The scanner logs in, reads the installed package list, file versions, registry values and configuration settings, and compares them with advisories. The result is a more complete and more accurate picture: more true findings, because local software is now visible, and fewer false positives, because the scanner reads the actual installed package rather than inferring it from a banner.

This lesson explains how authenticated scanning works internally, how to set it up safely in OpenVAS for Linux and Windows lab hosts, how to read the difference between the two views, and how to manage the very real risk of handing a scanner privileged credentials.

> [!IMPORTANT]
> Scan credentials are client secrets. Accept them only through the channel agreed in the Rules of Engagement, store them encrypted, use them only against in-scope hosts during the agreed window, and confirm in writing that the client has disabled or rotated them at the end of the engagement. In this course, create your own scan accounts on lab VMs you own.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Authenticated (credentialed) scan | A scan in which the scanner logs in to the target to inspect local software and configuration. |
| Local security check (LSC) | A check that compares locally gathered data, usually package versions, with vendor advisories. |
| Package inventory | The list of installed packages and versions, for example from `dpkg` on Debian-family systems or `rpm` on Red Hat-family systems. |
| Backporting | Applying a security fix to an older upstream version, so the package is fixed although its upstream version number looks vulnerable. |
| Scan account | A dedicated account created only for scanning, with the minimum privileges needed. |
| Credential failure | A scan in which the login did not succeed, so local checks silently did not run. |
| Compliance / policy audit | An authenticated scan comparing configuration with a benchmark rather than looking for CVEs. |

## Two views of the same host

Consider a single Linux lab server. From the network it exposes SSH on port 22 and a web server on port 80. An unauthenticated scan can read the SSH banner, the HTTP `Server` header, the TLS configuration if any, and whatever the web application reveals. From these it infers product versions and flags CVEs whose affected range includes those versions.

Logged in, the same scanner can read the full package list (often several hundred packages), the running kernel version, configuration files and file permissions. It can therefore report a vulnerable compression library used by many programs, an outdated interpreter, a kernel flaw, or an insecure SSH daemon setting, none of which an outsider can see. It can also *clear* the false alarm on the web server: the banner may say an old upstream version, but the installed package's distribution release contains the backported fix.

**Execution flow.** In practice you run the unauthenticated scan first, because it represents the attacker's real starting point and has no dependency on credentials. You then add credentials to the same target and run again. Comparing the two reports shows which findings an outsider can reach and which require a foothold.

**Decision logic.** If the authenticated scan confirms a finding the unauthenticated scan raised, it becomes stronger evidence. If the authenticated scan shows the fixed package installed, the remote finding is a likely false positive. If a finding appears only in the authenticated scan, it is real but needs local access, which affects its CVSS Attack Vector and its priority.

**Technical interpretation.** The left column relies on what services *say*; the right column relies on what the system *is*. Package databases and the registry are authoritative records maintained by the operating system's own tooling, which is why local checks earn high Quality of Detection values in OpenVAS.

**Practical example.** A lab Debian VM shows an SSH banner whose upstream version appears in a CVE's affected range. The unauthenticated result is based on that banner. The authenticated scan reads the installed `openssh-server` package version, compares it with the Debian security tracker's fixed version for that CVE and reports nothing, because the fix was backported. Meanwhile the authenticated scan adds three findings for local libraries that were never visible remotely.

**Security implications.** The right column requires trust: the scanner holds credentials and logs in to every host. A compromised scanner, or credentials left active after the engagement, would hand an attacker a privileged key to the estate. Least privilege, dedicated accounts and tight handling rules are therefore mandatory.

**Key learning.** Unauthenticated scans show what an attacker can reach; authenticated scans show what is actually installed. Use both, and use the inside view to confirm or dismiss outside guesses.

## How authenticated checks work internally

### Linux and Unix targets over SSH

For Linux and other Unix-like systems, OpenVAS connects over SSH using a username and password or, preferably, an SSH key. Once connected it runs a series of read-only commands to identify the distribution and release, gather the package inventory and collect specific files. The gathered data is stored in the scan's knowledge base. Local security checks then compare each installed package version with the fixed versions published in the distribution's own security advisories; in current Greenbone releases the Notus scanner performs this comparison in bulk.

The key technical point is that the comparison uses the *distribution's* version string and the *distribution's* advisories. Debian, Ubuntu, Red Hat and others all publish which package release fixes each CVE. Because the check compares like with like, backported fixes are handled correctly, which is the single biggest reduction in false positives an assessment can make.

Most package-inventory commands can be run by an ordinary user, so a non-root account is often sufficient for local security checks. Some checks need to read files that only root can read; Greenbone's documentation describes which, and a scan account can be granted narrowly scoped `sudo` rules for them if the client agrees. Never use the root account itself.

### Windows targets over SMB

For Windows, OpenVAS authenticates over SMB (TCP 445) and reads the registry and file versions remotely. Windows checks examine installed updates, product versions recorded in the registry and the version resources of specific files. This requires an account with administrative rights on the target, because the information lives in protected parts of the registry and administrative shares, and the Remote Registry service must be available during the scan.

Windows *User Account Control* applies remote restrictions to *local* administrator accounts by default: when a local administrator logs in over the network, the session receives a filtered token without administrative rights, so remote checks fail. The usual and safer solution in a domain is to use a dedicated domain account that is a member of the local Administrators group on the in-scope hosts. Disabling the remote restriction for local accounts weakens a defence against lateral movement and should not be done casually on client systems.

### Other credential types

OpenVAS also supports credentials for VMware ESXi hosts and SNMP communities for network devices, and client certificates for some services. The principle is always the same: authenticate, gather authoritative local data, compare it with advisories.

**Components.** There are four lanes. *OpenVAS scanner* initiates everything. *Lab host (sshd)* is the in-scope Linux VM. *Knowledge base (Redis)* holds the facts gathered during the scan. *Advisory data (feed)* holds the distribution advisories with fixed package versions.

**Relationships and arrows.** Solid arrows are requests; dashed arrows are replies. The scanner opens an SSH session with the scan account's key; the host accepts the login. The scanner then runs read-only commands to identify the OS release and list installed packages; the host returns the release and the package list. The scanner writes these facts to the knowledge base. Local checks read the facts back, look up fixed versions in the advisory data, and the comparison produces a result.

**Execution flow.** Authenticate, identify the distribution, collect the inventory, store facts, compare with advisories, record results. Every later local check depends on the first two replies: if the login fails, nothing after it happens.

**Decision logic.** The critical branch is at login. If authentication fails (wrong key, account locked, SSH configured to refuse the account), the scanner records an informational log result saying so and continues with remote checks only. The report still looks complete, with no obvious error, unless you check the authentication status. The second branch is the comparison: installed version lower than the advisory's fixed version produces a result; equal or higher produces none.

**Technical interpretation.** The comparison follows the distribution's version-ordering rules (Debian and RPM version strings have defined comparison algorithms, including epochs and release suffixes), not simple string comparison. That is why the check correctly treats a backported release as fixed even though its upstream number is "older".

**Practical example.** Scanning a lab Ubuntu VM at `192.168.56.103` with a key-based scan account: the sshd logs show an accepted public-key login for that account from the scanner's address `192.168.56.101`, followed by a burst of short command executions and a logout. The report shows high-QoD package results and an informational entry confirming that authenticated checks ran.

**Security implications.** The host's authentication logs record every scan login, which gives defenders a clear signal to monitor: logins by the scan account from anywhere other than the scanner, or outside the window, should alert. Restricting the key to the scanner's source address enforces this technically.

**Key learning.** Authenticated scanning is login, inventory, compare; always verify that the login actually succeeded before trusting a quiet report.

## Step-by-step worked example: a key-based scan account on a lab VM

The following steps prepare a Debian or Ubuntu lab VM you own for authenticated scanning from a Kali scanner at `192.168.56.101`.

On the lab VM, create a dedicated, non-root account:

```bash
sudo useradd --create-home --shell /bin/bash gvmscan
sudo passwd --lock gvmscan
```

- `useradd --create-home --shell /bin/bash gvmscan` creates the account with a home directory (needed for `~/.ssh`) and a login shell (the scanner runs commands through it).
- `passwd --lock gvmscan` locks password authentication, so the only way in is the SSH key you will install.

On the scanner, generate a dedicated key pair:

```bash
ssh-keygen -t ed25519 -f ~/gvmscan_key -C "lab scan account"
```

- `-t ed25519` chooses a modern, compact key type.
- `-f ~/gvmscan_key` writes the private key to that file and the public key to `~/gvmscan_key.pub`.
- `-C` adds a comment identifying the key's purpose. Protect the private key with a passphrase when prompted; OpenVAS lets you store the passphrase with the credential.

Install the public key on the lab VM, restricted to the scanner's address. Add one line to `/home/gvmscan/.ssh/authorized_keys` (owned by `gvmscan`, mode 600, in a directory of mode 700):

```text
from="192.168.56.101" ssh-ed25519 AAAA...rest-of-public-key... lab scan account
```

The `from=` option tells sshd to accept this key only from the scanner's address, so a stolen copy of the key is useless elsewhere.

Test from the scanner before involving OpenVAS, because a failed login is far easier to diagnose here:

```bash
ssh -i ~/gvmscan_key gvmscan@192.168.56.103 'cat /etc/os-release; dpkg-query -W openssh-server'
```

`-i` selects the private key. The remote command prints the distribution identification file and asks the package database for the installed `openssh-server` version; `dpkg-query -W` prints the package name and its version separated by a tab. If this works as the unprivileged account, the scanner's inventory commands will work too.

In GSA, create the credential under **Configuration > Credentials** with type *Username + SSH Key*, username `gvmscan`, the private key file and its passphrase. Edit the target from Lesson 3, attach the credential to *SSH* on port 22, and run the task again. When the scan is complete, look in the results (including Log-level entries) for the informational result confirming whether SSH authentication succeeded and local security checks were enabled. If it reports a failure, return to the manual `ssh` test.

## Comparing unauthenticated and authenticated results

Run both scans against the same target and compare the exports. Expect three patterns:

1. **Findings in both** are strengthened: the remote observation is now backed by a package version.
2. **Findings only in the unauthenticated scan** are frequently banner-based results for packages whose installed version contains a backported fix. Investigate each; most will become documented false positives (Lesson 5).
3. **Findings only in the authenticated scan** are real but involve software not reachable from the network. Score them honestly: many become Attack Vector Local rather than Network, which lowers the CVSS score, but they remain important because an attacker who gains any foothold can use them to escalate.

Report both views. Clients need to know which weaknesses an outsider can reach today and which await an attacker who gets in.

## Common mistakes and misconceptions

- **Trusting a quiet authenticated report.** A credential failure produces a report that looks clean. Always confirm authentication succeeded.
- **Using root or a domain administrator.** Use a dedicated account with the minimum rights that the checks need.
- **Leaving credentials active.** Scan accounts should be enabled for the window and disabled or rotated afterwards, with written confirmation.
- **Weakening Windows protections to make scans work.** Prefer a domain account in the local Administrators group to disabling UAC remote restrictions for local accounts.
- **Ignoring account lockout.** Repeated failed logins from a misconfigured credential can lock accounts across the estate.
- **Assuming authenticated means intrusive.** Authenticated checks are read-only inventory and configuration reads; they are usually *less* disruptive than remote probing.

## Security implications, detection and defence

Authenticated scanning concentrates trust in the scanner. If the scanner host is compromised, the attacker inherits a credential that can log in to every in-scope host. Mitigate this with a hardened, dedicated scanner, encrypted credential storage, key-based authentication restricted by source address, narrowly scoped privileges, short credential lifetimes and monitoring.

Defenders should treat scan accounts as privileged identities: alert on any use outside the scanner's address or the scheduled window, review their group memberships regularly, and include them in privileged-access reviews. In India, where the DPDP Act 2023 obliges organisations to protect personal data with reasonable security safeguards, a scanner that can log in to systems holding personal data falls squarely within that obligation; the engagement's evidence-handling plan should say how scan results containing host details will be stored and destroyed.

## Best practices

1. Run an unauthenticated scan first, then an authenticated scan of the same target.
2. Use a dedicated scan account with least privilege; never root or a domain administrator.
3. Prefer SSH keys restricted to the scanner's address for Linux; use a domain account in local Administrators for Windows.
4. Test credentials manually before the scan and check the authentication status in every report.
5. Limit credential lifetime to the engagement window and confirm disablement in writing.
6. Monitor scan-account logins and alert on unexpected use.
7. Report which findings are reachable remotely and which need local access.

## Practical applications / lab exercise (authorised lab only)

**Objective:** measure the difference between unauthenticated and authenticated views of one lab host you own.

1. Create the `gvmscan` account and restricted key on a Debian or Ubuntu lab VM, as above.
2. Confirm the manual `ssh` test returns the OS release and a package version.
3. Create an SSH credential in GSA and attach it to the existing target.
4. Run the authenticated scan and confirm in the results that SSH authentication succeeded.
5. Export both reports as CSV and classify every result into the three patterns described above.
6. For one finding that appears only in the unauthenticated scan, use the package version and the distribution's security tracker to decide whether it is a false positive. Record your evidence.
7. Lock or delete the `gvmscan` account and remove the key when finished.

## Key takeaways

- Authenticated scans log in and read the authoritative package inventory, configuration and registry.
- They find local weaknesses invisible from the network and remove banner-based false positives caused by backporting.
- Linux checks use SSH (preferably a restricted key and a non-root account); Windows checks use SMB with administrative rights.
- Always verify that authentication succeeded; a credential failure produces a deceptively clean report.
- Scan credentials are high-value secrets: least privilege, short lifetime, monitoring and written confirmation of disablement.
