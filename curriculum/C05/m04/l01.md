## Introduction and conceptual foundation

Modules 2 and 3 produced an exposure map: which hosts answer, which ports are open, which services and versions sit behind them, and which paths an application exposes. That map tells you *what exists*. It does not yet tell you *what is wrong*. Vulnerability assessment is the phase that turns an inventory into a list of candidate weaknesses, each one named, scored and checked for truth. The automated vulnerability scanner is the workhorse of that phase, and this lesson explains what a scanner actually does internally, why it is so useful, and why its output is never the final word.

A vulnerability scanner is a program that compares what it can observe about a target with a large, curated knowledge base of known weaknesses. The knowledge base is a collection of individual tests, often called *plugins*, *checks* or, in the OpenVAS world, *Network Vulnerability Tests (NVTs)*. Each test encodes one question: "is this service running a version affected by a particular advisory?", "does this web server answer a particular request in a way that reveals a known flaw?", "is this protocol configured with a weak option?". The scanner's job is to decide which tests apply to which services, run them efficiently and safely, and record the answer together with how confident it is.

It is worth stating early what a scanner is *not*. It is not a penetration tester. It does not understand that invoice 1002 belongs to a different customer from the person asking for it, it does not know that the administrator account is the most valuable thing in the application, and it has no idea whether the server it is probing is a test box or the system that runs a hospital's pharmacy. Scanners are superb at breadth and repetition and weak at meaning. A professional uses them for exactly what they are good at, then applies human judgement to the rest.

> [!IMPORTANT]
> Scanning is active testing. A vulnerability scan sends thousands of crafted requests and can crash fragile services, fill logs, lock accounts and trigger incident response. Run scans only against systems named in a signed authorisation and Rules of Engagement (Module 1), inside the agreed window, and only in an isolated lab you own while you are learning. In India, unauthorised access or probing of a computer resource can attract liability and criminal charges under the IT Act 2000 (for example sections 43 and 66).

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Vulnerability | A weakness in software, configuration or design that can be exploited to violate a security property (confidentiality, integrity, availability). |
| Vulnerability scanner | A tool that automatically tests targets against a knowledge base of known weaknesses and reports candidate findings. |
| Check / plugin / NVT | One encoded test in the scanner's knowledge base, with its own detection logic, metadata and severity. |
| Feed | The regularly updated distribution of checks and reference data (advisories, CVE and CPE data) that a scanner consumes. |
| Fingerprinting | Identifying a product and version from observable traits: banners, headers, protocol behaviour, file hashes. |
| Unauthenticated (remote) scan | A scan that sees only what the network exposes, as an outside attacker would. |
| Authenticated (credentialed) scan | A scan that logs in to the target and inspects installed software and configuration from the inside (Lesson 4). |
| False positive | A reported finding that is not actually present or exploitable (Lesson 5). |
| False negative | A real weakness the scanner failed to report. |
| Detection confidence | The scanner's own estimate of how reliable a result is; OpenVAS calls this Quality of Detection (QoD). |

## How a scanner works internally

Every mainstream network vulnerability scanner, whether open source or commercial, follows the same broad pipeline. Understanding the stages lets you predict where errors come from.

### Stage 1: target discovery

The scanner first decides which addresses in its target list are alive. It uses the host-discovery techniques you met in Module 3: ICMP echo, TCP probes to common ports, ARP on a local segment. This stage matters more than beginners expect. If discovery wrongly concludes a host is down (because a firewall drops ICMP, for example), the scanner silently skips it and the report will show *nothing* for that host. Silence is not safety; it may be a discovery failure. Most scanners therefore let you choose the alive test, including an option to treat every listed host as alive.

### Stage 2: port and service detection

For each live host the scanner enumerates open ports from a configured port list and then identifies the service on each port. It reads banners, sends protocol-specific probes and compares responses with signatures. The output of this stage is a set of facts, often stored in a per-host *knowledge base*: "TCP 22 is SSH, OpenSSH, version string X", "TCP 443 speaks TLS with these protocol versions", "TCP 8099 is HTTP and sends `Server: NilgiriPortal/0.9 Python/3.14.4`".

### Stage 3: check selection

A good scanner does not fire every one of its tens of thousands of checks at every port. It uses the knowledge base to select only relevant checks: SSH checks for SSH services, web checks for HTTP services, Windows checks only where Windows has been detected. Checks declare dependencies ("run me only if the product-detection check found Apache") so that the knowledge base drives the order. This is why the quality of stage 2 controls the quality of everything that follows: a mis-identified service attracts the wrong tests.

### Stage 4: test execution

The selected checks run. They fall into a few families that differ sharply in reliability:

- **Version comparison.** The check reads a version (from a banner, a header or, in an authenticated scan, the package database) and compares it with the affected range in an advisory. This is fast and safe but only as good as the version information.
- **Active probing.** The check sends a request designed to elicit behaviour that only a vulnerable implementation exhibits, without causing harm. This is stronger evidence because it tests behaviour rather than labels.
- **Configuration checks.** The check inspects settings: supported TLS versions and cipher suites, missing HTTP security headers, anonymous FTP enabled, default credentials accepted.
- **Intrusive checks.** A small number of checks can disrupt a service (for example denial-of-service tests). Reputable scanners mark these and disable them in default policies; you enable them only with explicit written approval.

### Stage 5: result recording

Each check that fires produces a result: the host and port, the vulnerability name, references (CVE, vendor advisory), a severity (normally a CVSS score, Lesson 2), a description, the evidence the check observed, a suggested solution and a confidence value. Results are what you will triage, validate and eventually report.

**Relationships and arrows.** The arrows run strictly forward, because each stage consumes the previous stage's output. The side notes on the stages carry the key dependency: check selection is driven by what service detection recorded. The feed is shown as a separate input to selection because the checks are data that changes daily, independent of the scanner engine.

**Execution flow.** The scanner reads the target list, discovers live hosts, enumerates ports and services, selects checks, executes them, and writes results. Real scanners run many hosts in parallel, but each host passes through the same stages in this order.

**Decision logic.** Two decisions hide inside the pipeline. In discovery, a host judged dead is dropped and receives no checks. In selection, a check whose prerequisites are not met is skipped. Both decisions are sources of false negatives: a filtered ping or a wrongly identified service removes tests that should have run.

**Technical interpretation.** Internally, detection checks write facts into the knowledge base and vulnerability checks read them. A version-comparison check might read the stored banner fact for HTTP on port 8099, compare a version string with an affected range and raise a result. An active check opens its own connection and inspects the response. The confidence attached to the result reflects which of these methods produced it.

**Practical example.** Point a scanner at the lab target on `127.0.0.1:8099`. Discovery finds the loopback host alive. Service detection records HTTP with the header `NilgiriPortal/0.9 Python/3.14.4`. Check selection picks web-server checks. Execution reports the version disclosure and the missing security headers, both configuration observations. It almost certainly will not report the insecure direct object reference on `/invoice`, because no check in any feed knows that invoice 1002 belongs to someone else.

**Security implications.** Each stage generates traffic that defenders can detect: bursts of connections, unusual user agents, requests for paths that do not exist. In an authorised test this is expected and should be coordinated with the client's monitoring team. In an organisation's own environment, scanning from a dedicated, documented scanner host lets the security operations centre whitelist it and still alert on scanning from anywhere else.

**Key learning.** A scanner is a pipeline whose output is only as good as its discovery and fingerprinting stages; treat every result as a candidate whose evidence you must understand.

## Where the evidence comes from: detection methods compared

Because the five stages share one engine, the difference between a trustworthy result and a misleading one usually lies in the *detection method* the individual check used. A professional reads every result with one question in mind: what did the scanner actually observe? **Purpose.** The table ranks the detection methods a scanner uses by the strength of the evidence they produce. It matters because the method, not the severity number, tells you how much to trust a result before you validate it.

**Components.** The columns are *Method*, *What is observed*, *Evidence strength* and *False-positive risk*. The rows are *Banner or header version*, *Remote behaviour probe*, *Configuration observation*, *Authenticated package check* and *Safe proof of exploit*. Row colours move from red for the weakest evidence to green for the strongest.

**Relationships and arrows.** There are no arrows in a table; the relationship is the ordering. Reading from top to bottom, evidence moves from a *label the target chose to send* to *behaviour the target cannot fake*. The false-positive column moves in the opposite direction.

**Execution flow.** In a real scan several methods may contribute to a single result. A typical flow is that a banner check raises a candidate, then either an active probe confirms it remotely, an authenticated check confirms it from the package database, or a human performs a minimal safe proof during controlled verification (Module 5).

**Decision logic.** The table implies a rule: the weaker the method, the more validation the result needs before it is reported. A banner-only result must be confirmed or labelled "potential, unverified". A configuration observation such as a missing header is usually directly verifiable with one request. A safe proof is already validated.

**Technical interpretation.** Banners are strings chosen by the administrator or the software vendor. Linux distributions routinely *backport* security fixes into an older upstream version number, so the banner still shows the "vulnerable" version even though the package is patched. Administrators also edit or remove banners. Behavioural probes and package checks avoid both problems because they test the code or the installed package directly.

**Practical example.** In the lab, `LAB_ASSETS/C05/enumerate.py` observed the header `NilgiriPortal/0.9 Python/3.14.4` on every endpoint. That is a *banner observation*: useful as a lead and as an information-disclosure finding, but on its own it proves nothing about exploitable flaws. By contrast, `verify.py` sent `admin/admin` and received an administrator role, which is a *safe proof*: the strongest row of the table.

**Security implications.** For defenders, suppressing version banners reduces casual fingerprinting but must not be mistaken for patching. For testers, over-trusting banners is the single largest source of false positives in scan reports and of lost credibility with clients.

**Key learning.** Always ask which detection method produced a result; a severity score attached to a banner guess is still a guess.

## Step-by-step worked example: what a scanner sees on the lab target

Before you meet a full scanner in Lesson 3, it is instructive to look at the raw observations that any scanner would start from. The course lab kit contains a scoped enumerator that performs the first stages of the pipeline (service detection and path probing) against the authorised loopback target only.

```bash
python target/app.py &
python enumerate.py
```

The first command starts the deliberately vulnerable Nilgiri Parts Portal (fictional) on `127.0.0.1:8099`; the trailing `&` runs it in the background. The second runs `LAB_ASSETS/C05/enumerate.py`, which refuses any non-loopback host in code. The saved, execution-tested output is:

```terminal
$ python enumerate.py
============================================================
SCOPED ENUMERATION  target=127.0.0.1:8099 (in scope)
============================================================
[tcp] 127.0.0.1:8099 open

path           code   content-type               server
------------------------------------------------------------
/              200    application/json           NilgiriPortal/0.9 Python/3.14.4
/login         404    application/json           NilgiriPortal/0.9 Python/3.14.4
/admin         403    application/json           NilgiriPortal/0.9 Python/3.14.4
/invoice       400    application/json           NilgiriPortal/0.9 Python/3.14.4
/robots.txt    200    text/plain                 NilgiriPortal/0.9 Python/3.14.4
/status        404    application/json           NilgiriPortal/0.9 Python/3.14.4
/health        404    application/json           NilgiriPortal/0.9 Python/3.14.4
/backup        404    application/json           NilgiriPortal/0.9 Python/3.14.4
/config        404    application/json           NilgiriPortal/0.9 Python/3.14.4
/.git          404    application/json           NilgiriPortal/0.9 Python/3.14.4

notes:
  - Server header discloses the software/version (an exposure).
  - /robots.txt is readable and lists paths meant to be hidden.
  - record these in your asset inventory; verify, do not assume.
```

Read this output the way a scanner's check-selection stage would.

1. **The TCP line** is the discovery and port-detection result: the host is alive and port 8099 is open.
2. **The `server` column** is a fingerprint. A scanner would record product `NilgiriPortal` version `0.9` and select any checks associated with that product. Because the portal is fictional, no feed contains checks for it, which illustrates an important point: custom, in-house applications receive almost no product-specific coverage from scanners.
3. **The status codes** describe behaviour. `/admin` returning 403 shows an access-controlled resource exists. `/invoice` returning 400 without parameters suggests it expects input, which is exactly where the lab's verbose-error and IDOR findings live. `/login` returns 404 to a GET request because it accepts POST, a reminder that path probing with one method misses functionality.
4. **The notes** are the scanner-like conclusions: version disclosure and a readable `robots.txt`. Both are low-severity *configuration* results.

What is *missing* is as instructive. Nothing in this output reveals the default administrator credential, the IDOR, or the internal detail leaked by the error page. A generic scanner might find the default credential if its feed has a credential-guessing check for this product (it will not, for a custom portal) and might flag the error page through a generic error-pattern check. The IDOR requires understanding ownership, which only a human, or a test written specifically for this application, can do. This is why the four confirmed findings in `data/verify_output.txt` came from targeted verification, not from generic scanning.

## Scanner families and deployment models

Network vulnerability scanners are only one family. A complete assessment programme usually combines several.

| Family | What it examines | Typical examples |
| --- | --- | --- |
| Network / infrastructure scanner | Hosts, services, protocols, OS and package versions | OpenVAS (Greenbone), commercial network scanners |
| Web application scanner (DAST) | Running web applications: injection, XSS, headers, session handling | OWASP ZAP, commercial DAST tools |
| Static analysis (SAST) | Source code, without running it | Language-specific analysers |
| Software composition analysis (SCA) | Third-party libraries and their known CVEs | Dependency checkers in build pipelines |
| Configuration / compliance scanner | Settings against a benchmark (for example CIS Benchmarks) | Policy-audit modes of scanners |
| Cloud posture scanner | Cloud account configuration | Cloud security posture management tools |

Scanners are also deployed in different ways. A **remote network scan** runs from a scanner host across the network. An **agent-based** approach installs a small agent on each endpoint that reports local inventory, which works for laptops that are rarely on the corporate network. **Passive** scanning watches traffic and infers vulnerable versions without sending probes at all, useful for fragile operational technology. In a penetration test you will normally run remote scans, unauthenticated and, when the client provides credentials, authenticated.

## Coverage: why scanners miss things

It helps to think of a scanner's coverage as the intersection of three sets. The first is *what the scanner can reach*: hosts that passed discovery and ports in the configured port list. The second is *what the scanner can identify*: services whose product and version it fingerprinted correctly. The third is *what the feed knows about*: weaknesses someone has already researched, published and encoded as a check. A finding appears in the report only when all three overlap.

Each set has predictable gaps. Reach is limited by firewalls, by port lists that skip unusual ports and by hosts that only answer from certain source networks. Identification is limited by custom software, stripped banners and services behind reverse proxies that present the proxy's identity rather than the application's. Knowledge is limited to *known* issues: a flaw that nobody has reported, or a weakness in the client's own code, has no check. Business-logic flaws such as the lab's IDOR fall outside the third set by definition, because they depend on the meaning of data rather than on a product version.

When you plan an assessment, use these three sets as a checklist. Ask how you will widen reach (a full TCP port list for key hosts), improve identification (authenticated scanning, manual banner review) and compensate for the knowledge gap (manual testing of authentication, authorisation and input handling). The scan is the start of the analysis, not its end.

## Common mistakes and misconceptions

- **"The scan found nothing, so the system is secure."** A clean report means no *known, detectable* issue was reported. Discovery failures, filtered ports, unsupported custom applications and logic flaws all produce silence.
- **"The scanner said Critical, so it is Critical."** Severity is attached to the check, not proven on your target. A banner-based Critical on a backport-patched server is a false positive with a big number on it.
- **"More checks are always better."** Enabling intrusive checks against production can cause outages. Default policies exclude them for good reason.
- **Scanning out of scope.** Typing a /16 instead of a /24 can put thousands of third-party addresses in the target list. Always paste the target list from the signed scope document and review it before starting.
- **Forgetting the feed.** A scanner with a feed that has not synchronised for weeks cannot know about recent advisories. Record the feed version in your working notes.
- **Treating scanning as the test.** Clients pay for a penetration test because they want the issues scanners miss. A scan export renamed as a report is not a penetration test.

## Security implications, detection and defence

From a defender's point of view, a vulnerability scan is a noisy, recognisable activity. Intrusion detection systems flag the burst of connections and the characteristic probe requests; web application firewalls block many web checks; account-lockout policies can be triggered by credential checks. In an engagement you agree in advance whether the client's monitoring should be informed (so that alerts are recognised) or left uninformed (to test detection), and you record the scanner's source address so any alert can be matched to your activity.

Organisations defend themselves against hostile scanning by reducing what can be fingerprinted (minimal banners, closed unused ports), by detecting scanning patterns at the perimeter, and above all by running their *own* authorised scanning programme so that they find and fix known weaknesses before an attacker's scanner does. For Indian organisations, regulators and sector bodies frequently expect periodic vulnerability assessments, and the DPDP Act 2023 requires data fiduciaries to take reasonable security safeguards to protect personal data; a documented scanning and remediation programme is one practical way to show such safeguards exist.

## Best practices

1. Start from the signed scope: paste targets from the authorisation document and keep exclusions explicit.
2. Synchronise the feed before every engagement and record its version and date.
3. Use a safe default policy; enable intrusive checks only with written approval and an agreed window.
4. Choose the alive test deliberately; if ICMP is filtered, consider treating listed hosts as alive.
5. Run unauthenticated and, where provided, authenticated scans, and compare them (Lesson 4).
6. Throttle concurrency against fragile or production systems.
7. Read the evidence of every result before you rely on it, and validate before reporting (Lesson 5).
8. Supplement scanning with manual testing of business logic, access control and authentication.

## Key takeaways

- A vulnerability scanner runs a pipeline: discovery, service detection, check selection, test execution, result recording.
- The quality of discovery and fingerprinting controls the quality of every later result.
- Detection methods differ in evidence strength: banners are weakest, behavioural probes and package checks stronger, a safe proof strongest.
- Scanners provide breadth and repeatability; they miss logic flaws such as IDOR and know nothing about business context.
- Every scan is active testing and needs written authorisation, a defined scope and coordination with the client.
