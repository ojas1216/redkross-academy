## Introduction and conceptual foundation

Lesson 1 described the scanner pipeline in the abstract. This lesson makes it concrete with OpenVAS, the open-source network vulnerability scanner developed by Greenbone and distributed as part of the **Greenbone Community Edition**. The name "OpenVAS" originally referred to the whole framework and is still widely used that way; strictly, it is now the name of the scanner engine, and the full stack is the Greenbone Vulnerability Management (GVM) framework. You will find OpenVAS packaged in Kali Linux, available as official Greenbone community containers, and embedded in Greenbone's commercial appliances.

OpenVAS is worth learning in depth for three reasons. It is free and open, so you can study exactly how it behaves. Its architecture is typical of professional scanners, so the concepts transfer directly to commercial products. And its workflow (targets, tasks, results, overrides, reports) is the same workflow a vulnerability-management team runs every week. By the end of this lesson you should be able to explain what each component does, configure and run a scan of an authorised lab host, read the results critically and export a report.

> [!WARNING]
> Configure OpenVAS targets only with addresses listed in your signed scope. In this course, that means an isolated lab you own: for example a Kali VM and a deliberately vulnerable VM on a VirtualBox host-only network such as `192.168.56.0/24`, or the course's loopback target. A full scan sends tens of thousands of probes; pointing it at an address you do not own or are not authorised to test is unlawful in India under the IT Act 2000 and in most other jurisdictions.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Greenbone Community Edition | The free distribution of Greenbone's vulnerability-management framework, including the OpenVAS scanner. |
| NVT | Network Vulnerability Test: one check in the feed, written mostly in NASL (Nessus Attack Scripting Language), identified by an OID. |
| Feed | The Greenbone Community Feed: NVTs, SCAP data (CVE and CPE), CERT advisories (CERT-Bund, DFN-CERT) and data objects such as scan configs and port lists. |
| gvmd | The Greenbone Vulnerability Manager daemon: central service that stores configuration and results and schedules scans. |
| GMP | Greenbone Management Protocol: the XML-based protocol clients use to talk to gvmd. |
| GSA / gsad | Greenbone Security Assistant: the web user interface, served by the `gsad` daemon. |
| ospd-openvas | The Open Scanner Protocol (OSP) wrapper through which gvmd controls the OpenVAS scanner. |
| Target | A named set of hosts plus a port list, alive test and optional credentials. |
| Task | A scan job that binds a target to a scan config and a scanner, and produces reports. |
| Scan config | A policy selecting which NVT families and preferences to use, for example "Full and fast". |
| QoD | Quality of Detection: a percentage expressing how reliable a result's detection method is. |
| Override | A rule that changes the severity of matching results, including marking them as false positives. |

## How OpenVAS is built

### The components

The Greenbone stack separates management from scanning, which is why it can scale from a single laptop to many distributed sensors.

- **Greenbone Security Assistant (GSA)** is the browser interface. The `gsad` daemon serves it and translates user actions into GMP requests. On Kali the interface is served locally on port 9392 by default.
- **gvmd** is the manager. It holds every object you create (targets, credentials, tasks, schedules, overrides), stores scan results in a **PostgreSQL** database, and imports the SCAP and CERT data from the feed so that it can link results to CVEs and advisories.
- **ospd-openvas** sits between gvmd and the scanner, speaking OSP. It receives scan requests, launches the scanner and returns results.
- **The OpenVAS scanner** (`openvas`) executes NVTs against the targets. During a scan it keeps a per-host knowledge base in **Redis**, which is exactly the knowledge base described in Lesson 1: detection NVTs write facts, and vulnerability NVTs read them.
- **Notus** is the component in current releases that performs local security checks by comparing the package list gathered during an authenticated scan with advisory data, which is faster and more precise than running one script per package (Lesson 4).
- **The feed** supplies all of the above with content. It is synchronised from Greenbone's servers and updated frequently.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure shows the architecture of the Greenbone Community Edition: how a click in the web interface becomes probes against a target and how results return. It matters because troubleshooting OpenVAS almost always means identifying which component is not doing its job.

**Components.** *Analyst browser* is you. *GSA web UI (gsad)* serves the interface and speaks GMP. *gvmd (manager)* stores objects and results in *PostgreSQL*. *ospd-openvas* is the OSP wrapper. *openvas scanner* runs NVTs and keeps its per-host knowledge base in *Redis*. *Feed sync* supplies NVTs, SCAP and CERT data and data objects. *Authorised lab target* is the only system the scanner should ever touch.

**Relationships and arrows.** Control flows from the browser to gsad to gvmd over GMP, then from gvmd to ospd-openvas over OSP, and from ospd-openvas to the scanner. Probes flow from the scanner to the target. Results flow back along the same chain to gvmd, which writes them to PostgreSQL. The feed arrows point into gvmd (SCAP, CERT data and data objects) and into the scanner (NVTs), because both consume feed content.

**Execution flow.** You create a target and task in GSA; gvmd stores them. When you start the task, gvmd sends the target, port list, credentials and selected NVTs to ospd-openvas, which starts the scanner. The scanner discovers hosts, fills Redis with facts, runs the relevant NVTs and streams results back. gvmd matches results to CVE and CERT data and makes them available as a report.

**Decision logic.** The main decisions happen inside the scanner: the alive test decides whether a host is scanned at all, and NVT dependencies on knowledge-base facts decide which tests run. At the manager level, the minimum QoD filter and any overrides decide which results you see and at what severity.

**Technical interpretation.** Because gvmd and the scanner are separate, a common failure is a scanner whose NVTs have synchronised while gvmd's SCAP or data objects have not, leaving scan configs missing or results without CVE links. Checking that each feed component is current is the first troubleshooting step.

**Practical example.** On a Kali lab VM, you browse to the GSA on port 9392, create a target for the vulnerable VM at `192.168.56.102`, and start a "Full and fast" task. If the task stays at "Requested" and never moves, the problem lies between gvmd and ospd-openvas or the scanner, not in your target settings.

**Security implications.** The scanner host holds credentials for authenticated scans and a database full of vulnerability data about your client: it is a high-value asset. Keep the web interface bound to localhost or a management network, protect the admin account, and delete client data at the end of the engagement as the Rules of Engagement require.

**Key learning.** OpenVAS separates the manager (gvmd with PostgreSQL) from the scanner (openvas with Redis), joined by OSP and fed by the Greenbone feed; each scan crosses every one of these components.

### Data objects that shape a scan

Several objects in gvmd determine what a scan actually does.

- **Port lists** define which ports are scanned. Built-in lists include "All IANA assigned TCP" and "All IANA assigned TCP and UDP". Custom lists use the syntax `T:` for TCP and `U:` for UDP ranges, for example `T:1-1024,8099`.
- **Alive tests** decide how hosts are judged up: ICMP ping, TCP-ACK or TCP-SYN service ping, ARP ping, combinations of these, or "Consider Alive", which skips discovery and scans every listed host.
- **Scan configs** select NVT families and preferences. "Full and fast" is the usual default; it relies on knowledge-base facts to skip irrelevant tests, and it runs with *safe checks* enabled so that tests known to be disruptive are not executed. Other built-in configs such as "Discovery" or "Host Discovery" only gather information.
- **Credentials** store usernames, passwords, SSH keys or SNMP communities for authenticated scans; you attach them to the target.
- **Schedules** run a task automatically, useful for recurring internal scanning but rarely needed in a penetration test.

## The OpenVAS scan workflow

A professional scan follows the same sequence every time, and each step leaves an auditable record in gvmd.

1. **Prepare and verify the installation.** Synchronise the feed and confirm the installation is healthy before the engagement window opens.
2. **Create the target.** Enter only the in-scope addresses, choose the port list and alive test, attach credentials if the scan is authenticated, and add any explicit exclusions.
3. **Create the task.** Bind the target to the "OpenVAS Default" scanner and a scan config. Set the minimum QoD and, for production systems, reduce the number of concurrently scanned hosts and NVTs per host.
4. **Run and monitor.** Start the task within the agreed window and watch progress. Stop immediately if the target or network behaves unexpectedly, as the Rules of Engagement require.
5. **Review results.** Filter by severity and QoD, read the detection method and evidence of each result, and group duplicates.
6. **Validate and annotate.** Confirm or dismiss results (Lesson 5). Record dismissals as *overrides* (for example, set to False Positive) with a justification, and add *notes* where context is useful.
7. **Report.** Export the report in a machine-readable format (XML or CSV) for your own processing and a readable one (PDF) if needed, then build your assessment report from validated results (Lesson 8).
8. **Rescan after remediation.** Run the same task again and compare reports with a *delta report*, which shows new, fixed and changed results.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure lays out the end-to-end workflow an analyst follows in OpenVAS, from a healthy installation to a validated report and a rescan. It matters because skipping a step (most often feed verification or validation) is the root cause of most poor scan reports.

**Components.** *Sync and check setup* covers feed synchronisation and the installation self-check. *Create target* records hosts from the scope, the port list, the alive test and credentials. *Create task* binds the target to a scan config and scanner. *Run and monitor* is the active phase inside the agreed window. *Review results* filters by severity and QoD and reads evidence. *Validate, override, note* turns raw results into trustworthy ones. *Export report* produces XML, CSV or PDF. The loop back labelled *rescan after fixes, compare with a delta report* closes the cycle.

**Relationships and arrows.** Each arrow is a dependency: you cannot create a meaningful task without a target, and you cannot validate results that have not been reviewed. The loop arrow from the final step back to running the task shows that the same task object is reused for retesting, which is what makes delta reports possible.

**Execution flow.** Sync, check, target, task, run, review, validate, export, then later rescan and compare. Steps two and three happen once per engagement; steps four to seven happen once per scan.

**Decision logic.** Two decisions dominate. During monitoring, if the target shows distress (slow responses, crashes, alerts the client did not expect) you stop the task and consult the client contact. During validation, each result becomes confirmed, false positive (recorded as an override with a reason) or unverified (reported with that label).

**Technical interpretation.** Overrides and notes are stored in gvmd and apply to matching results in future reports, so a false positive dismissed with a reason in the first scan stays dismissed in the rescan. Delta reports compare two reports of the same task, which is why rescans should reuse the original task rather than creating a new one.

**Practical example.** In a lab, you scan a deliberately vulnerable VM on `192.168.56.102`, find a high-severity result for an outdated web server based on its banner, and an authenticated rescan shows the installed package includes the fix. You override the first result as a false positive with a note citing the package version, and the delta report after the client's other fixes shows the remaining results as fixed.

**Security implications.** The workflow is also an audit trail. Targets prove what you were authorised to scan, task history proves when, and overrides prove why a result was dismissed. Protect this record and include the relevant parts in your evidence.

**Key learning.** OpenVAS work is a repeatable loop of prepare, target, task, run, review, validate, report and rescan; the validation and rescan steps are what make the output trustworthy.

## Step-by-step worked example (authorised lab)

The commands below install and operate the Greenbone Community Edition from the Kali Linux packages. Output varies between releases and is long, so it is described rather than reproduced; the course lab kit does not include an OpenVAS capture, and you should not trust any "expected output" you cannot reproduce on your own installation.

```bash
sudo apt update
sudo apt install gvm
sudo gvm-setup
sudo gvm-check-setup
sudo gvm-start
```

- `apt install gvm` installs the Kali meta-package that pulls in gvmd, gsad, ospd-openvas, the openvas scanner, Redis and PostgreSQL configuration.
- `gvm-setup` initialises the database, creates the administrator account, prints its generated password once (record it in your password manager) and performs the first feed synchronisation, which can take a long time.
- `gvm-check-setup` runs a sequence of self-tests and reports whether each component and feed is present and current, ending with a statement that the installation appears to be OK or with the fix for the first problem it found.
- `gvm-start` starts the services and opens the interface; `gvm-stop` stops them at the end of a session.

Browse to `https://127.0.0.1:9392` and sign in. The interface uses a self-signed certificate, so expect a browser warning on first use in the lab.

### Creating the target and task

In GSA, choose **Configuration > Targets** and create a target:

| Field | Lab value | Why |
| --- | --- | --- |
| Name | `lab-vuln-vm` | A clear, reusable name. |
| Hosts | `192.168.56.102` | Only the in-scope host. |
| Exclude hosts | blank | Use for out-of-scope addresses inside a range. |
| Port list | All IANA assigned TCP | A sensible default for a first scan. |
| Alive test | ICMP, TCP-ACK Service and ARP Ping | Several methods reduce missed hosts. |
| Credentials | none (first scan) | Unauthenticated view first; Lesson 4 adds SSH. |

Then choose **Scans > Tasks** and create a task named `lab-vuln-vm full and fast`, select the target, the "OpenVAS Default" scanner and the "Full and fast" scan config. Leave the minimum QoD at its default of 70 per cent for now. Start the task with the play button and watch the progress column move from *Requested* to *Queued*, *Running* and finally *Done*.

To scan the course's own loopback target instead, run OpenVAS on the same machine as `LAB_ASSETS/C05/target/app.py`, set Hosts to `127.0.0.1`, create a custom port list `T:8099`, and choose the "Consider Alive" test. Expect only a handful of configuration results (version disclosure, missing headers), which reinforces Lesson 1's point that generic feeds know nothing about custom applications.

### Scripting with GMP

Everything in the web interface is a GMP request to gvmd, so it can be automated with Greenbone's `gvm-tools` package:

```bash
gvm-cli --gmp-username admin --gmp-password "$GVM_PASS" socket --xml "<get_version/>"
gvm-cli --gmp-username admin --gmp-password "$GVM_PASS" socket --xml "<get_tasks/>"
```

- `--gmp-username` and `--gmp-password` authenticate to gvmd; reading the password from an environment variable avoids typing it, but it still appears in the process list while the command runs, so prefer a protected `gvm-tools` configuration file on shared machines.
- `socket` selects a connection over gvmd's local Unix socket (alternatives are `tls` and `ssh` for remote managers).
- `--xml` sends a raw GMP command. `<get_version/>` returns the protocol version, a safe connectivity test; `<get_tasks/>` returns every task with its status.

Note that the gvmd socket is normally accessible only to the `_gvm` user and its group on Kali; if you receive a permission error, run the command as a user in that group rather than loosening the socket's permissions.

## Reading OpenVAS results

Each result in a report carries more information than the severity badge suggests, and reading all of it is what separates analysis from transcription.

- **Severity** is a CVSS score taken from the NVT (and therefore from the referenced CVE where there is one). A severity of 0.0 is shown as *Log*: informational output such as a detected service or OS.
- **QoD** expresses how the result was detected. Greenbone defines QoD types with fixed values; for example a result proved by an exploit is 100 per cent, one based on an authenticated package check is 97 per cent, one based on a remote banner is 80 per cent, and one based on a banner known to be unreliable (for instance because distributions backport fixes) is 30 per cent. The default filter hides results below 70 per cent, which removes the least reliable detections from view; they are still stored, and you may choose to review them.
- **Summary, insight and affected software** explain the weakness and the versions involved.
- **Detection result** shows what the scanner actually observed, such as the banner or version it found. This is the evidence you must read before trusting the result.
- **Detection method** names the NVT and its OID, so you can look up precisely what it does.
- **Solution** gives the vendor fix or workaround, with a solution type such as vendor fix, mitigation or workaround.
- **References** list CVE IDs, CERT-Bund and DFN-CERT advisories and vendor links.

## Common mistakes and misconceptions

- **Scanning with a stale feed.** Run the self-check before every engagement; an out-of-date feed produces false negatives for recent CVEs.
- **Reading only the severity column.** The detection result and QoD tell you whether the severity is trustworthy.
- **Deleting false positives.** Use overrides with a written reason instead, so the decision is auditable and persists into rescans.
- **Creating a new task for the retest.** Reuse the original task so delta reports work.
- **Exposing the GSA on all interfaces.** Keep it on localhost or a management network.
- **Assuming "Done" means complete coverage.** Check the host count in the report: hosts that failed the alive test are missing silently.

## Security implications, detection and defence

From the target's side, an OpenVAS scan is easy to recognise: a single source address opening connections to every port in the list, then sending recognisable probe patterns. Coordinate with the client's monitoring team, give them your scanner address and window, and keep a log of start and stop times. If the client's security operations centre detects and blocks the scan, that is a finding about their detection capability, not a failure, provided it was agreed in the Rules of Engagement how such blocks would be handled.

Treat the scanner itself as sensitive infrastructure. It stores credentials, client vulnerability data and, through the feed, executes code from an external source; apply updates, restrict access to the web interface and database, and wipe client data according to the evidence-handling rules from Module 1.

## Best practices

1. Verify installation health and feed currency before each engagement and record the feed date.
2. Build targets from the signed scope only, with explicit exclusions.
3. Start with an unauthenticated "Full and fast" scan, then add an authenticated scan (Lesson 4).
4. Throttle concurrency against production or fragile systems and agree a window.
5. Review results by reading the detection result and QoD, not just severity.
6. Record every dismissal as an override with a justification.
7. Export XML or CSV for your own analysis and keep the raw export with your evidence.
8. Reuse the task for rescans and use delta reports to show what changed.

## Practical applications / lab exercise (authorised lab only)

**Objective:** install the Greenbone Community Edition in your lab, scan one authorised host and triage the results.

1. On a Kali VM attached to a host-only network, install and set up GVM as above; confirm `gvm-check-setup` reports success.
2. Create a target for one deliberately vulnerable VM that you own, with the port list and alive test from the table.
3. Create and run a "Full and fast" task and record its start and end times.
4. Export the report as CSV. Count the results by severity, then list the ten highest results with their QoD values.
5. For each of the ten, write the detection method (banner, active probe, package check) and whether you would trust it without further validation.
6. Stop the services with `sudo gvm-stop` when finished.

## Key takeaways

- OpenVAS is the scanner of the Greenbone Community Edition; gvmd manages, ospd-openvas bridges, openvas scans, PostgreSQL and Redis store, and the feed supplies content.
- Targets, port lists, alive tests, credentials, scan configs and tasks together define exactly what a scan does.
- The workflow is prepare, target, task, run, review, validate, report and rescan with delta reports.
- Severity comes from CVSS; QoD expresses detection reliability, and the default filter hides results below 70 per cent.
- Overrides with reasons, not deletions, are how false positives are recorded.
