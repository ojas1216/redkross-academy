## Introduction and conceptual foundation

Everything in this course is practised in a lab, and the lab is where most beginners' real mistakes happen. Not dramatic mistakes, but quiet ones: a deliberately vulnerable application left listening on every network interface of a laptop on café Wi-Fi; a scanner pointed at the wrong address range because a variable was mistyped; a virtual machine bridged onto the office network; a "test" tool that turns out to contain something nobody inspected. Each of these turns a safe exercise into a risk to someone else's systems, to your own computer, or to you legally. Lesson 5 showed that an unauthorised connection to someone else's computer can be an offence under the IT Act 2000 regardless of intent; a lab that leaks traffic is exactly how a learner ends up there.

Lab safety is the engineering answer to that problem. Its central idea is simple: **make the safe action the default and the unsafe action hard**. A safe lab does not rely on the tester always being careful. It is built so that even a careless command cannot reach anything outside the lab, and so that the lab can be reset to a known-clean state at any moment.

This lesson treats the lab the way a professional treats a test environment, in four parts:

1. **Isolation by design**: network topologies that cannot route to anyone else's systems.
2. **Containment in code**: targets that bind only to loopback, and tools that refuse out-of-scope hosts before they send a single packet.
3. **Recoverability**: snapshots, clean baselines and cleanup, so mistakes are cheap to undo.
4. **Operating discipline**: stop conditions, protecting the host, and the specific rules for handling a deliberately vulnerable application.

The course lab kit in `LAB_ASSETS/C05/` is a worked example of all four, and you will see each control in its real source code and real output.

> [!CAUTION]
> The kit's target, `target/app.py`, is deliberately insecure: it accepts a default administrator password and returns other customers' invoices without any check. It is safe only because it listens on loopback. Never change its address, never copy it to a server, and never run it on a machine you do not control.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Lab | An environment you own and control, built solely for practising security testing, with no path to systems you are not authorised to test. |
| Isolation | Network and system separation that prevents lab traffic from reaching, or being reached from, other networks. |
| Loopback | The virtual interface by which a host talks to itself: `127.0.0.0/8` in IPv4 (normally `127.0.0.1`) and `::1` in IPv6. Packets sent to it never leave the machine. |
| Binding | The address a server socket listens on. A server bound to `127.0.0.1` accepts connections only from the same machine; one bound to `0.0.0.0` accepts them on every interface. |
| Allowlist | A list of explicitly permitted values; anything not on the list is refused. The opposite of a blocklist. |
| Fail closed | A design in which uncertainty or error leads to refusal rather than to permission. |
| Host-only network | A virtual network shared between the host and its virtual machines, with no route to the physical network. |
| Internal network | A virtual network shared only between virtual machines, not even with the host. |
| Snapshot | A saved point-in-time state of a virtual machine (disk and optionally memory) that can be restored. |
| Stop condition | A pre-agreed event that requires all testing to halt immediately until it is resolved. |

## The principle: independent layers of containment

A professional lab never relies on a single control. Each layer is designed on the assumption that the one before it might fail:

- **Procedure**: the lab has its own written scope and rules, exactly like a real engagement. The kit's `scope.md` names one in-scope target (`127.0.0.1`, TCP 8099), lists what is out of scope and defines stop conditions.
- **Network**: the lab network cannot route anywhere else.
- **Target**: the vulnerable service listens only where it is meant to be reached.
- **Tool**: the testing tools check scope themselves and refuse anything else.
- **Recovery**: if something goes wrong anyway, the environment can be restored to a clean state.

This is defence in depth applied to the tester's own work. If you mistype an address, the tool refuses it. If you use a different tool that has no scope check, the network does not route the traffic. If the target is somehow exposed, it is exposed only on an isolated network. The rest of this lesson takes the layers in turn.

## Designing an isolated lab network

Most practice labs run on virtualisation software on the learner's own computer. Every mainstream hypervisor offers several ways to connect a virtual machine (VM) to a network, and choosing the right one is the single most important lab-safety decision. The names differ slightly between products (VirtualBox, VMware Workstation, Hyper-V), but the concepts are common:

| Mode | What the VM can reach | Who can reach the VM | Lab use |
| --- | --- | --- | --- |
| Bridged | The physical network and, through it, the internet, as a peer of the host | Anyone on the physical network | Never for vulnerable targets |
| NAT | Outbound to the physical network and internet, through the host | Normally nobody from outside | Only for an attacker VM that must download updates, and disconnected during testing |
| Host-only | The host and other VMs on the same host-only network | The host and those VMs | Good default for target and tester VMs |
| Internal / private | Only other VMs on the same internal network | Only those VMs | Strongest isolation; use for malware or untrusted images |

The rules that follow from the table:

- **Vulnerable targets never get a bridged adapter.** A bridged VM is, for practical purposes, another computer plugged into the same network as your laptop. If that network is a home, office, hostel or café network, every other device on it can reach your deliberately vulnerable service.
- **Avoid dual-homed VMs during testing.** A VM with both a NAT adapter and a host-only adapter is a bridge between the lab and the internet. Download what you need first, then disconnect the NAT adapter before testing starts.
- **Use private or documentation address ranges** for the lab network (for example `192.168.56.0/24`, a common default for host-only networks, or another private range), and write the range into your lab scope so you can recognise anything outside it immediately.
- **Disable conveniences that cross the boundary** when the lab contains anything untrusted: shared folders, a shared clipboard and drag-and-drop between host and VM.
- **Verify, do not assume.** After building the network, check from inside the target VM that it cannot reach the internet or your physical network, and from the host that the target is reachable only on the lab interface.

**Relationships and arrows.** The solid arrows are the permitted paths: from the host's tools to the loopback target, from the host to the host-only network, and from the Tester VM to the Target VM across that network. The dashed arrows labelled **blocked: no bridged or NAT adapter** run from the Host-only network towards the Physical LAN and the Internet; they show connections that the design deliberately prevents.

**Execution flow.** A session starts on the host: you start the target, confirm it is listening only where intended, and run tools against it. In the VM variant, you restore the Target VM's snapshot, start both VMs on the host-only network and test from the Tester VM.

**Decision logic.** The key decision is the adapter mode for each VM. Host-only or internal keeps the dashed arrows blocked; bridged or NAT would turn them into real paths, which is why the figure marks them as forbidden.

**Technical interpretation.** Loopback is the strongest isolation available without any configuration, because the operating system never places loopback traffic on a physical interface. Host-only networking achieves similar isolation for multi-machine labs, with the hypervisor providing a virtual switch that has no uplink.

**Practical example.** In this course you need only the loopback zone: `python target/app.py` serves on `127.0.0.1:8099`, and `enumerate.py`, `verify.py` and `retest.py` connect to it from the same machine. Later modules that need several machines use the host-only pattern.

**Security implications.** The most common real-world lab failure is a vulnerable VM left on a bridged adapter. Defenders on shared networks sometimes discover such labs because they appear as new hosts offering unusual services. Isolation protects both the network you sit on and you.

**Key learning.** Put vulnerable targets on loopback or a host-only or internal network, never on a bridged adapter, and verify that nothing in the lab can reach the physical LAN or the internet.

## Loopback-only targets

### What binding means

When a server starts, it asks the operating system to listen on a particular address and port. The address decides who can connect:

- **`127.0.0.1`** (or `::1` in IPv6): only programs on the same machine. Packets addressed to loopback are delivered internally by the operating system and never reach a network card.
- **A specific interface address**, such as a host-only adapter's `192.168.56.1`: anyone who can reach that network.
- **`0.0.0.0`** (or `::`): every interface the machine has, now and in future, including Wi-Fi and any VPN.

A deliberately vulnerable service bound to `0.0.0.0` on a laptop is exposed to every network the laptop joins. Bound to `127.0.0.1`, the same service cannot be reached from anywhere else, whatever network the laptop is on.

The kit's target makes this decision in code, not in a configuration file a learner might edit by accident. In `LAB_ASSETS/C05/target/app.py`:

```python
HOST, PORT = "127.0.0.1", 8099
...
srv = ThreadingHTTPServer((HOST, PORT), Handler)
```

`ThreadingHTTPServer` is the Python standard library's HTTP server; the tuple `(HOST, PORT)` is the address it binds. Because `HOST` is the loopback address, the operating system refuses connections arriving on any other interface. The hardened version, `target/app_fixed.py`, does the same on port 8100.

Be aware that convenience tools often default the other way. Python's own `python -m http.server`, for example, binds to all interfaces unless you pass `--bind 127.0.0.1`. Always check the binding of anything you start in a lab.

### Confirming the binding

Never assume a service is listening where you think it is; check. Starting the target prints its banner and address (these two lines come from the `print` calls in `app.py`):

```terminal
$ python target/app.py
AUTHORISED LAB TARGET - Nilgiri Parts Portal. Fictional and deliberately vulnerable. For use only on your own machine.
listening on http://127.0.0.1:8099 (loopback only) - Ctrl-C to stop
```

Then, from a second terminal, ask the operating system what is actually listening. On Windows, in a Git Bash shell:

```terminal
$ netstat -ano | grep :8099
  TCP    127.0.0.1:8099         0.0.0.0:0              LISTENING       13372
```

`netstat -a` lists all connections and listening ports, `-n` shows numeric addresses instead of names, and `-o` adds the owning process ID (13372 here; yours will differ). `grep :8099` keeps the line for the lab port (in `cmd` or PowerShell use `findstr :8099` instead). The column that matters is the local address: `127.0.0.1:8099` means loopback only. If you ever see `0.0.0.0:8099` there, the service is exposed on every interface: stop it immediately. On Linux, `ss -ltnp` gives the equivalent view (`-l` listening sockets, `-t` TCP, `-n` numeric, `-p` owning process).

## Scope enforcement in the tools

The target's binding protects other people from your lab. The tools' scope checks protect other people from your *mistakes*. Every network tool in the kit starts by checking the host it was given against an allowlist, and refuses anything else before it opens a connection. From `LAB_ASSETS/C05/enumerate.py`:

```python
ALLOWED_HOSTS = {"127.0.0.1", "localhost"}

def in_scope(host):
    return host in ALLOWED_HOSTS
...
    if not in_scope(args.host):
        print("REFUSED: %s is out of scope. This lab tool runs only against "
              "the loopback target you own (127.0.0.1)." % args.host,
              file=sys.stderr)
        return 2
```

`retest.py` performs the same check on its `--host` argument. `verify.py` goes further: it has no host option at all, because `HOST` is fixed to `127.0.0.1` in the script, and it still checks the allowlist before running. The design choices are worth studying because they are the same ones you should make in any tool you write.

**It is an allowlist, not a blocklist.** The tool does not try to list forbidden addresses (an impossible task); it lists the only permitted ones. Anything not on the list, including a typing error, is refused.

**It fails closed.** The check is an exact string match. `127.0.0.2` is technically a loopback address too, but it is not on the list, so it is refused. Refusing something harmless is a small cost; permitting something harmful is not.

**It checks before acting.** The refusal happens before any socket is opened, so an out-of-scope address never receives even a connection attempt.

**It distinguishes outcomes by exit code.** A refusal exits with status 2. If the host is in scope but the target is not running, the tool exits with status 1 and a different message ("service not reachable - start target/app.py first"). Scripts that chain the tools can tell "you asked for something forbidden" from "the lab is not up".

Here is the real behaviour when the kit's tools are given a documentation address, `192.0.2.10`, that is not in scope:

```terminal
$ python -I enumerate.py --host 192.0.2.10
REFUSED: 192.0.2.10 is out of scope. This lab tool runs only against the loopback target you own (127.0.0.1).
$ echo $?
2
$ python -I retest.py --host 192.0.2.10
REFUSED: out of scope.
$ echo $?
2
```

`--host` names the target; `-I` runs Python in isolated mode, so that nothing in the current directory or environment can change which modules the tool imports; `echo $?` prints the exit status of the previous command. Both tools refused with status 2 and sent nothing.

One limitation is worth understanding. The name `localhost` is on the allowlist as a string, and it is the operating system's resolver that turns it into an address. On a normally configured machine it resolves to loopback (RFC 6761 reserves the name for exactly that), but a tampered hosts file could point it elsewhere. That is why the tool check is one layer among several, not the only one: the binding of the target and the isolation of the network still hold.

The second decision diamond is **Target reachable on loopback?** ("TCP connect, 1-second timeout"). The slate box **Stop, exit 1** ("start target/app.py first") is the "lab not running" result. The dark final box, **Run safe checks** ("read-only, evidence to data/"), is the only path that touches the target.

**Relationships and arrows.** The arrow labelled **no** from the first diamond leads to the refusal; the arrow labelled **yes** leads to the reachability test. From the second diamond, **no** leads to the exit-1 stop and **yes** leads to the checks. No arrow leads from a refusal back into the flow: a refused run ends.

**Execution flow.** Parse the arguments, check scope, check reachability, then run. The order matters: scope is checked before reachability, so not even the TCP connection used to test reachability is attempted against an out-of-scope host.

**Decision logic.** Two binary decisions, each failing closed. An unknown host is refused; an unreachable in-scope target stops the run rather than retrying or searching elsewhere.

**Technical interpretation.** The first check is a set-membership test on a string; the second is a short `socket.connect` with a timeout. Both are cheap, and neither depends on the network being configured correctly.

**Practical example.** `python -I enumerate.py --host 192.0.2.10` takes the **no** branch and prints the REFUSED message with status 2. `python -I enumerate.py` with the target stopped takes **yes**, then **no**, and exits 1. With the target running it reaches **Run safe checks** and produces the endpoint map saved in `data/enumerate_output.txt`.

**Security implications.** Professional testing tools rarely enforce scope this strictly by default, which is why testers maintain target lists from the signed scope and why firms review tool configurations. Building the check into your own scripts is cheap insurance against the most common cause of out-of-scope testing: a typing error.

**Key learning.** Check scope against an allowlist before acting, fail closed, and make refusal a distinct, scriptable outcome.

## Snapshots and a clean baseline

A lab is only safe if mistakes are cheap to undo. For VM-based labs, the tool is the **snapshot**: a saved state of the VM's disk (and, optionally, its memory) that can be restored in seconds.

- **Take a baseline snapshot** of each target VM after building and before any testing, and name it clearly (for example `baseline-clean`).
- **Restore before each session** so that every exercise starts from the same state. This also makes results reproducible: a finding observed on the baseline can be observed again.
- **Restore after anything unexpected**: a crash, a configuration you did not intend, or any sign that the VM is doing something you did not start.
- **Remember what snapshots are not.** They are not backups (they usually live on the same disk as the VM), and they preserve whatever was in the VM when taken, including any secrets. A memory snapshot can contain passwords and keys in clear.

The course's loopback lab needs no snapshots because it changes nothing persistent: the target holds its data in memory, the tools are read-only against it, and `scope.md` notes that nothing is written outside the process. Stopping `app.py` and restarting it returns it to its original state. That is itself a design lesson: the safest lab component is one with no persistent state to corrupt.

## Stop conditions in the lab

Lesson 4 introduced stop conditions for engagements. A lab needs them too, written down before you start. Section 6 of the kit's `scope.md` sets two: stop immediately if any activity would reach a system not listed as in scope, or if the target behaves unexpectedly. A practical lab list extends these:

- any traffic, alert or log entry suggesting the lab has reached a network or host outside it;
- a target bound to anything other than its intended address;
- a tool behaving differently from its documentation or saved outputs;
- the host becoming unstable (resource exhaustion, unexpected processes or firewall prompts);
- any sign of real personal data or real credentials in a lab that is meant to be fictional.

When a stop condition triggers: stop the tools and the target, note the time and what you observed, restore to the baseline, and find the cause before resuming. In a real engagement you would also inform the client contact; in the lab, you write it in your activity log (Lesson 6).

> [!TIP]
> A firewall prompt asking whether to allow a lab program to accept connections on public or private networks is a warning sign. A loopback-bound service does not need it. Deny the prompt and check the binding.

## Protecting the host

The host computer is part of the lab's security boundary, and it is usually also the computer you use for everything else.

- **Keep the host patched** and its own firewall enabled; the lab is no excuse to weaken the machine around it.
- **Run lab tools as an ordinary user**, not as an administrator. None of the kit's tools needs elevated rights, and an ordinary account limits what any mistake or misbehaving tool can affect.
- **Inspect before you run.** The kit uses only the Python standard library, so you can read every line. Treat third-party tools, images and downloads as untrusted until you know what they do, keep them in their own folder, and run them inside a VM.
- **Keep lab and personal data apart.** Do not run labs from folders that sync to personal cloud storage, and never use real passwords or real personal data in a lab.
- **Account for what you start.** Know which processes and VMs are running, stop them at the end of each session, and confirm they have stopped.

## Handling the kit's deliberately vulnerable app

`target/app.py` (the Nilgiri Parts Portal) deserves its own rules because it is designed to be insecure. Its weaknesses, which you will verify and report in this course, are a default `admin`/`admin` credential, an insecure direct object reference on `/invoice`, a verbose error that leaks an internal query, a `robots.txt` listing hidden paths, a server version header and missing security headers. Everything in it is fictional.

- **Run it only on your own machine**, only bound to `127.0.0.1:8099`, and only while you are using it.
- **Never edit `HOST`**, never expose it through a port forward, tunnel or reverse proxy, and never deploy it or reuse its code in any real application.
- **Confirm the binding each time** with `netstat` or `ss`, as shown above.
- **Point the tools at it and nothing else.** The hardened `app_fixed.py` on port 8100 is the only other target, used by `retest.py` to confirm the fixes.
- **Stop it when finished** with Ctrl-C (or by stopping the background process) and delete `data/`, as the kit's README instructs.

## Step-by-step: a safe lab session

1. Read `LAB_ASSETS/C05/scope.md` and confirm the in-scope target: `127.0.0.1`, TCP 8099.
2. Start the activity log with the time and "source 127.0.0.1".
3. Start the target with `python target/app.py` and check that the banner reports `127.0.0.1:8099 (loopback only)`.
4. In a second terminal, run `netstat -ano` (filtered for `:8099`) or `ss -ltnp` and confirm the local address is `127.0.0.1:8099`.
5. Prove the scope guard works: run `python -I enumerate.py --host 192.0.2.10` and confirm `REFUSED` and exit status 2.
6. Run `python -I enumerate.py` and compare the endpoint table with `data/enumerate_output.txt`, which begins `SCOPED ENUMERATION  target=127.0.0.1:8099 (in scope)` and `[tcp] 127.0.0.1:8099 open`.
7. Stop the target with Ctrl-C, confirm with `netstat` that nothing listens on 8099, delete `data/` if you are finished, and close the log.

## Common mistakes and misconceptions

- **"It's only on my laptop, so it's isolated."** A laptop is on whatever network it joins. Binding, not location, decides exposure.
- **"NAT keeps the VM safe."** NAT limits inbound connections but gives the VM outbound access to everything; a misdirected scan from a NAT VM leaves your network.
- **"My tool has a scope option, so I'm covered."** A scope option only helps if it is set correctly and fails closed. Keep the network layer too.
- **"Snapshots are my backup."** They share the VM's disk and preserve its secrets. Back up separately and treat snapshots as sensitive.
- **"Lab targets are harmless."** A deliberately vulnerable service is harmful by design if anyone else can reach it.

## Security implications, detection and defence

From the defender's side, unsafe labs are visible. A newly appearing host offering an unusual web service on a corporate or campus network, a workstation listening on `0.0.0.0` on a high port, or a burst of connection attempts from a learner's machine towards an external range are all things a security team may detect, and investigate as a possible intrusion. Endpoint tools can list listening sockets across a fleet; firewalls log outbound scans. A learner who builds labs safely never generates these events.

For organisations, the same principles govern internal training and test environments: separate network segments with no route to production, deny-by-default firewall rules between them, inventories of test hosts, and scheduled teardown.

## Best practices

- Write a scope and stop conditions for your lab, as for any engagement.
- Bind vulnerable services to loopback, or place them on host-only or internal networks; never bridged.
- Verify every binding and every network path rather than assuming it.
- Build scope allowlists into your own tools; fail closed and refuse before sending anything.
- Snapshot target VMs before each session and restore after anything unexpected.
- Run tools as an ordinary user, inspect what you run, and keep lab data separate from personal data.
- Stop every target and VM at the end of the session and confirm they have stopped.

## Key takeaways

- A safe lab makes the safe action the default: independent layers of procedure, network isolation, target binding, tool scope checks and recovery.
- Use loopback or host-only or internal networks for targets; never bridged adapters, and no dual-homed VMs during testing.
- A server bound to `127.0.0.1` cannot be reached from any other machine; verify bindings with `netstat` or `ss`.
- The kit's tools check an allowlist before acting, fail closed, and refuse out-of-scope hosts with exit status 2 before sending any packet.
- Snapshot and restore VMs, define stop conditions, protect the host, and handle the deliberately vulnerable app as exactly what it is.
