## Introduction and conceptual foundation

The Domain Name System and domain registration data are the two oldest and most reliable passive sources a tester has. DNS exists so that the whole internet can find an organisation's services: its web servers, mail servers and verification tokens must be published for anyone to look up, or they would not work. Registration data exists so that a domain or an address block can be traced to the registrar and organisation responsible for it. Both are public by design, both are queried millions of times a second for ordinary reasons, and both tell a careful reader a great deal about the shape of an organisation's infrastructure.

This lesson explains how DNS resolution works and why ordinary lookups count as passive, which record types carry reconnaissance value and what each reveals, how a tester reads mail-related records, why zone transfers are active work, and how WHOIS and its modern replacement RDAP present registration data. Throughout, the examples use the reserved names `example.com` and the fictional `nilgiriparts.example`, and addresses from the documentation ranges reserved by RFC 5737, so that nothing you type while practising can reach a real organisation.

You met DNS in Course 02 as a protocol. Here the question is different: not "how does a name resolve?" but "what can someone outside learn from the answers, and what should the owner stop publishing?"

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Zone | The portion of the DNS namespace that one set of authoritative servers is responsible for, such as `nilgiriparts.example` and the names under it. |
| Authoritative server | A name server that holds the zone's records and answers for them with authority. |
| Recursive resolver | A server that accepts a client's question and walks the DNS hierarchy to find the answer, caching it for the record's TTL. |
| Stub resolver | The small resolver built into an operating system that forwards questions to a recursive resolver. |
| Resource record (RR) | One entry in a zone: a name, a type (A, MX, TXT ...), a TTL and the data. |
| TTL | Time to live: how many seconds a resolver may cache a record. |
| Zone transfer (AXFR) | A request for a full copy of a zone, intended for secondary name servers (RFC 5936). |
| WHOIS | The original text-based registration lookup protocol, served on TCP port 43 (RFC 3912). |
| RDAP | Registration Data Access Protocol: the structured JSON-over-HTTPS successor to WHOIS, standardised in the RFC 7480 series. |
| Registry / registrar | The registry runs a top-level domain (for `.in`, NIXI); registrars sell names under it to registrants. |
| RIR / NIR | Regional and national internet registries that allocate address blocks; APNIC serves the Asia-Pacific region and IRINN is India's national registry under it. |

## How DNS resolution works and who sees the query

When a tester types `dig www.example.com`, the tool sends one question to a recursive resolver. Everything after that happens between the resolver and the DNS hierarchy. The figure shows the full path for an uncached name.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The sequence shows how a single lookup travels through the DNS hierarchy and, crucially for reconnaissance, which parties see whose address. It explains why ordinary DNS queries are treated as passive collection.

**Components.** Five lanes run left to right. **Tester's stub resolver** is the operating system or `dig` on the tester's machine. **Recursive resolver** is the ISP's or a public resolver. **Root server** is one of the root name servers that know where every top-level domain is delegated. **.com TLD server** knows which name servers are authoritative for each `.com` domain. **example.com authoritative** holds the actual zone.

**Relationships and arrows.** Solid arrows are questions; dashed arrows are replies. The tester's stub sends only one question, to the recursive resolver. The resolver then asks the root, which replies with a **referral** (the name servers for `.com`, not the final answer). It asks the TLD server, which replies with a referral to the domain's name servers. Finally it asks the authoritative server, which returns the **A record** with its TTL. The resolver passes the answer back to the stub and caches it.

**Execution flow.** Steps run top to bottom in time order. On a second lookup within the TTL, the resolver answers from its cache and none of the lanes to its right are contacted at all.

**Decision logic.** Each server either answers authoritatively or refers the resolver one level down the tree. There is no branch in which the authoritative server learns the tester's own address: it sees only the resolver.

**Technical interpretation.** This is iterative resolution performed by the resolver on the client's behalf (recursive service). Authoritative servers are frequently operated by DNS hosting providers rather than by the organisation itself, so even the last hop may not reach the target's own infrastructure.

**Practical example.** In an authorised external test of a client that owns `example.com`, running `dig +short www.example.com A` through your normal resolver produces the client's published web address without any packet from you reaching the client's network. Sending `dig @ns1.example.com example.com AXFR` instead talks directly to the client's name server and is active work.

**Security implications.** Because defenders cannot see who queries their records through resolvers, everything in a public zone must be treated as known to adversaries. The mitigation is to publish only what must be public, keep internal names in internal zones, and monitor authoritative logs for zone transfer attempts and unusual query bursts.

**Key learning.** A normal lookup is seen by resolvers and authoritative servers, not by the tester's target network; whatever a zone publishes, assume everyone has read it.

## Record types and what they reveal

A zone file is a plain text list of resource records. The following fictional zone illustrates what a small company might publish. It is configuration data written for this lesson, using the `.example` reserved top-level domain (RFC 2606) and documentation addresses.

```text
$ORIGIN nilgiriparts.example.
$TTL 3600
@        IN SOA   ns1.nilgiriparts.example. hostmaster.nilgiriparts.example. (
                  2026110801 7200 900 1209600 3600 )
@        IN NS    ns1.nilgiriparts.example.
@        IN NS    ns2.dnshost.example.
@        IN A     203.0.113.20
www      IN CNAME @
portal   IN A     203.0.113.21
vpn      IN A     203.0.113.30
@        IN MX    10 mail.nilgiriparts.example.
mail     IN A     203.0.113.25
@        IN TXT   "v=spf1 ip4:203.0.113.25 include:_spf.mailvendor.example -all"
_dmarc   IN TXT   "v=DMARC1; p=quarantine; rua=mailto:dmarc@nilgiriparts.example"
@        IN TXT   "examplecrm-site-verification=3f9a1c"
@        IN CAA   0 issue "ca.example"
```

Each line follows the pattern *name, class, type, data*. `@` stands for the zone origin itself. The SOA record's numbers are the serial, refresh, retry, expire and minimum TTL values. Read the zone as an outsider would and the following picture appears.

| Type | Example above | What it reveals to a tester |
| --- | --- | --- |
| SOA | `ns1 ... hostmaster ...` | Primary name server and a contact mailbox naming convention; the serial often encodes a date of last change. |
| NS | `ns1.nilgiriparts.example`, `ns2.dnshost.example` | Who runs DNS: here one self-hosted server and one DNS provider. |
| A / AAAA | `portal`, `vpn`, `mail` | Host names and addresses; names such as `vpn` and `portal` signal remote-access and customer-facing services. |
| CNAME | `www` | Aliases; CNAMEs pointing to third-party platforms reveal suppliers (and, if left dangling, takeover risks: lesson 4). |
| MX | `10 mail.nilgiriparts.example.` | Where mail is delivered and therefore which mail platform the company uses. |
| TXT (SPF) | `v=spf1 ... include:_spf.mailvendor.example -all` | Every system and vendor allowed to send mail for the domain. |
| TXT (DMARC) | `_dmarc` | The mail-authentication policy and where reports go. |
| TXT (verification) | `examplecrm-site-verification=...` | SaaS products the organisation has verified ownership with. |
| CAA | `0 issue "ca.example"` | Which certificate authorities may issue certificates for the domain (RFC 8659). |
| PTR | (in the reverse zone) | The name an address maps back to; reverse names often expose naming conventions. |

### Reading mail records

Mail records reward careful reading. SPF (RFC 7208) is published as a TXT record that begins `v=spf1`. Its mechanisms list permitted senders: `ip4:` names an address or range, `include:` pulls in another domain's SPF policy (typically a mail provider or marketing platform), and the final `-all` says that any other sender should fail. An SPF record with several `include:` entries is effectively a list of suppliers that handle the company's email. DMARC (RFC 7489) is published at the name `_dmarc` under the domain; `p=` gives the policy (`none`, `quarantine` or `reject`) and `rua=` the address for aggregate reports. From a defensive angle, a missing or `p=none` DMARC policy is itself a finding, because it makes the domain easier to spoof in phishing.

## Querying DNS: commands and options

`dig` (from the ISC BIND tools) is the standard command-line client. `nslookup` is available on Windows and gives similar answers. Against an authorised target, typical passive queries look like this:

```bash
dig example.com NS
dig +short example.com MX
dig +noall +answer example.com TXT
dig -x 192.0.2.10
```

- The first form asks for the record type named after the domain (`NS`). Without a type, `dig` asks for `A`.
- `+short` prints only the answer data, one record per line, which is convenient for scripts.
- `+noall +answer` turns off every output section and then turns the answer section back on, so you see the full records (name, TTL, class, type, data) without the header and statistics.
- `-x 192.0.2.10` performs a reverse lookup: `dig` builds the name `10.2.0.192.in-addr.arpa` and asks for its PTR record.

All four go to the resolver configured on your machine. Adding `@server` (for example `dig @ns1.example.com example.com SOA`) sends the question directly to a named server instead, which moves the action towards the active end of the spectrum because you are now talking to the target's infrastructure.

> [!NOTE]
> The `.example` top-level domain and the addresses in 192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24 are reserved for documentation and are not delegated or routed on the public internet. The zone above is therefore read here as data. To practise live queries, run a local DNS server in your own lab and load such a zone into it.

### Zone transfers: an active test

A zone transfer copies an entire zone from a primary server to a secondary. It is requested with the query type AXFR, as in `dig @ns1.example.com example.com AXFR`. A correctly configured server only allows transfers to its own secondaries and refuses everyone else; a misconfigured one hands any requester a complete list of names, including ones never intended to be public. Testing this is a direct request to the client's name server, so it belongs in the active column, must be explicitly permitted by the rules of engagement, and is normally performed once per authoritative server. The finding, if the transfer succeeds, is the misconfiguration; the remedy is to restrict AXFR by address or with transaction signatures (TSIG).

## Registration data: WHOIS and RDAP

Registration data answers a different question from DNS: not "where are the services?" but "who is responsible for this name or address block, and since when?" For a tester, it confirms ownership (an important input to scope validation), shows the registrar and the name servers registered at the parent, and gives creation and expiry dates that can distinguish a long-established domain from a lookalike registered last week.

### WHOIS

WHOIS (RFC 3912) is a very simple protocol: the client opens TCP port 43 on a WHOIS server, sends a query line and reads back free-form text. The `whois` command-line client follows referrals between registry and registrar servers. Its weakness is the format: every registry chose its own layout, so output is hard to parse reliably, and there is no standard way to express that a field has been withheld.

### RDAP

RDAP was designed by the IETF to replace WHOIS. It runs over HTTPS, returns structured JSON, supports standard error codes and can express redaction and differentiated access. Its specifications are a series beginning with RFC 7480 (HTTP usage), including the query format, the JSON response format and the bootstrap mechanism (RFC 7484) that tells a client which server is authoritative for a given top-level domain or address range. ICANN has required RDAP from generic top-level domain registries and registrars, and the regional internet registries, including APNIC, offer RDAP for address and autonomous-system data. ### Visual Walkthrough & Architectural Breakdown

**Purpose.** This sequence shows how a client finds the right RDAP server and retrieves registration data for a domain. It matters because it explains where the answers come from, why some fields are blank, and why registration data, like DNS, is collected passively from third parties.

**Components.** Four lanes appear. **Tester (RDAP client)** is a browser, `curl` or a dedicated client. **IANA bootstrap file** is the published JSON registry that maps top-level domains to RDAP base URLs. **Registry RDAP** is the server run by the top-level domain's registry. **Registrar RDAP** is the server run by the registrar that sold the name.

**Relationships and arrows.** The first solid arrow fetches the bootstrap file (`dns.json`); the dashed reply returns the registry's base URL for the domain's top-level domain. The client then sends `GET /domain/example.com` to the registry. The registry's dashed reply is a JSON object with status values, events (registration, expiration, last changed), name servers and the sponsoring registrar, and it may include a link to the registrar's own RDAP record. Following that link produces the registrar's reply, where contact entities appear, often redacted.

**Execution flow.** Bootstrap first, then registry, then optionally registrar. Clients typically cache the bootstrap file, so in practice the first step is rare.

**Decision logic.** If the bootstrap file has no entry for a top-level domain, the client has no standard RDAP server to ask and must fall back to WHOIS or the registry's documentation. If the registrar's data is redacted, the client receives the object with the personal fields withheld rather than an error.

**Technical interpretation.** RDAP reuses ordinary HTTP semantics: a missing object returns 404, rate limiting returns 429, and responses are JSON with standard member names, which makes them suitable for automation and inventory tooling.

**Practical example.** During an authorised external test, the client says it owns `example.com` and a newly discovered `example-portal.example`. RDAP shows the first registered years ago through the client's usual registrar and the second registered last month through a different one. That discrepancy is a scope question: the second domain may be a lookalike belonging to someone else, so it is parked and raised with the client rather than tested.

**Security implications.** Registration data supports scope validation and phishing-domain monitoring. Organisations should register domains under a corporate entity rather than an employee, use role mailboxes, enable registrar locks, and watch for lookalike registrations.

**Key learning.** RDAP finds the authoritative registry through IANA's bootstrap data and returns structured, sometimes redacted, registration facts; use them to confirm ownership, not to profile people.

### What has changed: redaction

Since 2018, driven largely by the EU General Data Protection Regulation, registrars and registries for generic top-level domains have redacted most personal contact data from public output. You will usually see the registrar, the dates, the status codes and the name servers, while the registrant's name, address and phone are withheld or replaced by a privacy service. This is a feature, not an obstacle: a tester's job is to confirm that a domain belongs to the client, and the client can confirm that directly. Trying to unmask a redacted registrant is not reconnaissance of the target's systems; it is investigation of a person, and it is outside a penetration test unless the contract explicitly says otherwise.

### Address registration data

The same protocols answer questions about IP address blocks. An address lookup against a regional registry returns the allocation the address belongs to, the organisation it was allocated to and abuse contact roles. For scope validation this is essential: an address that a client lists as "ours" might in fact belong to a cloud or hosting provider who has assigned it to the client temporarily. Testing such an address may also need the provider's rules to be followed (Module 1, lesson 2).

## Step-by-step worked example

You are preparing a passive DNS and registration summary for an authorised test of `example.com`, for which the client has signed scope. You run the four queries from the command section, an RDAP lookup and a WHOIS lookup, and record results in a structured note, one line per fact, with its source and the time of the query.

```text
fact: authoritative name servers        source: dig example.com NS            class: passive
fact: mail exchanger(s)                 source: dig +short example.com MX     class: passive
fact: SPF senders and includes          source: dig +noall +answer example.com TXT
fact: reverse name for 192.0.2.10       source: dig -x 192.0.2.10             class: passive
fact: registrar, created, expires       source: RDAP /domain/example.com      class: passive
fact: zone transfer refused/allowed     source: dig @ns AXFR (if RoE permits) class: ACTIVE
```

The template separates the fact from its source and labels the one active test explicitly, so that the reviewer can see which actions touched the client. Lesson 7 develops this into full reconnaissance documentation.

## Common mistakes and misconceptions

**Confusing a referral with an answer.** When querying servers directly, a referral (an authority section listing name servers) is not a negative result; it means "ask further down".

**Treating a resolved address as owned.** An A record proves that the zone owner points a name at an address, not that the address belongs to the client. Shared hosting, content delivery networks and cloud services mean that many unrelated organisations can sit behind one address. Validate address ownership before any active step.

**Reading stale data as current.** Cached answers and historical datasets may be out of date by the length of a TTL or by years. Note when each fact was observed.

**Attempting AXFR casually.** A zone transfer is a direct request to the target and is active.

**Profiling registrants.** Registration contacts, when visible, are personal data. Record that a domain is registered to the client; do not compile information about the individual.

## Security implications, detection and defence

For defenders, DNS and registration data are the cheapest exposure to fix and the easiest to forget.

- **Minimise public zones.** Keep internal host names in internal zones (split-horizon DNS). A public name such as `jenkins-test` or `old-vpn` is an invitation.
- **Restrict zone transfers** to known secondaries and sign them with TSIG; log and alert on refused AXFR requests.
- **Review TXT records** periodically and remove verification tokens for services no longer used.
- **Publish strong mail authentication.** SPF ending in `-all`, a DMARC policy moving to `quarantine` or `reject`, and DKIM signing reduce spoofing.
- **Use CAA** to restrict which certificate authorities may issue for the domain.
- **Protect registrations.** Corporate registrant, role mailboxes, registrar lock, multi-factor authentication on the registrar account, and expiry monitoring. An expired domain re-registered by someone else inherits whatever trust the old one had.

## Best practices

- Query through a resolver for passive work; use `@server` only when the rules of engagement allow direct contact.
- Record each fact with source, time and the exact command.
- Confirm ownership of every domain and address with the client before it enters active scope.
- Use RDAP where available for structured, parseable output.
- Use reserved names and documentation addresses in every example, test and training note.

## Key takeaways

- DNS publishes, by design, where an organisation's services are; ordinary lookups through a resolver are passive.
- NS, MX, TXT (SPF, DMARC, verification tokens), CNAME and CAA records reveal suppliers and services; PTR records reveal naming conventions.
- Zone transfer tests and direct queries to the target's name servers are active and need authorisation.
- RDAP is the structured successor to WHOIS; much personal registration data is redacted, and the purpose of lookups is ownership confirmation, not profiling.
- Defenders should minimise public zones, restrict AXFR, enforce mail authentication and protect their registrations.
