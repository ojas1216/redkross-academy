## Introduction and conceptual foundation

Module 2 ended with an inventory: a list of hosts, names and endpoints that reconnaissance *predicted* would exist. Module 3 begins the active phase of the engagement, where the tester stops reading about the target and starts sending packets to it. The very first active question is the simplest one: **which of the in-scope addresses actually have a live system behind them?** That question is called *host discovery* (older texts say "ping sweeping"), and getting it right shapes everything that follows. A host that is wrongly marked down is never port scanned, never enumerated and never reported, so a weakness on it survives the test. A host that is wrongly marked up wastes hours of scanning time against empty address space.

Host discovery is also the point at which most out-of-scope accidents happen. A typo in a range, a stale target list or a misunderstood CIDR boundary can turn a lawful test into unauthorised access to someone else's computer resource, which in India is an offence under sections 43 and 66 of the Information Technology Act, 2000. That is why this lesson treats the target list as carefully as the probes themselves. Every technique here is performed only against hosts named in a signed authorisation, and in this course that means your own loopback interface (127.0.0.1) or an isolated lab network you built yourself. Example addresses in this lesson come from the documentation ranges 192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24, which are reserved by RFC 5737 precisely so that books can use them without pointing at anybody's real network.

> [!IMPORTANT]
> Authorisation comes before the first packet. If an address is not listed in the signed scope (for this course, `LAB_ASSETS/C05/scope.md`), it is not probed, not "just pinged", not "quickly checked". Host discovery is active testing.

The lesson explains how a host can be detected at three different layers of the network stack, what Nmap does by default and why, how to build and verify a target list before scanning, how defenders see discovery traffic, and how to record the result so that the next lesson (port scanning) starts from evidence rather than assumptions.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Host discovery | Determining which addresses in a scope respond as live systems, before deeper scanning. |
| Probe | A packet or connection attempt sent to provoke a response that proves the target exists. |
| ARP request | A layer-2 broadcast asking "who has this IPv4 address?"; only works on the local segment (RFC 826). |
| ICMP echo request | The "ping" message (ICMP type 8); a live host normally replies with an echo reply (type 0) (RFC 792). |
| TCP SYN / ACK probe | A TCP segment sent to a port; any reply (SYN/ACK or RST) proves a host is present. |
| Up / down | Nmap's verdict on a host: up means at least one probe produced a response from it. |
| False negative | A live host marked down because every probe used was filtered. |
| Target list | The machine-readable list of in-scope addresses that every tool reads from. |
| Exclusion list | Addresses inside a range that must not be touched (production gateways, third-party hosts). |

## Why discovery is its own phase

It is tempting to skip discovery and port scan every address directly. On a scope of three hosts that is reasonable. On a scope of several thousand addresses it is not: a full port scan of an empty address costs time-outs on every port, while a discovery probe costs one or two packets. Discovery is therefore an *efficiency* filter. It is also a *safety* filter, because the smaller the set of hosts you scan deeply, the smaller the chance that an aggressive scan lands on something fragile that nobody told you about.

Discovery also produces its own findings. A host that the client's asset register does not list, but which answers on the network, is an unmanaged asset, and unmanaged assets are exactly where patching and monitoring fail. Conversely, a host that the register lists but which never answers might have been decommissioned, renumbered or moved behind a filter; each of those is worth a line in the report. In other words, discovery compares the client's belief about its network with the network's behaviour, and the differences are evidence.

## How host discovery works

A system can reveal its presence at several layers. Each layer has a different reach (where the probe can travel) and a different chance of being filtered. Understanding the layers is what lets you choose probes deliberately instead of trusting a default blindly.

### Layer 2: ARP on the local segment

When the tester's machine sits on the same Ethernet or Wi-Fi segment as the targets, the most reliable proof of life is the Address Resolution Protocol. Before any IPv4 packet can be delivered on a local link, the sender must learn the destination's MAC address, so it broadcasts an ARP request and the owner of the address answers. Host firewalls almost never block ARP, because blocking it would break the host's own networking. That makes ARP discovery fast and close to free of false negatives, with one hard limit: ARP does not cross a router. On a routed scope, ARP only ever tells you about the local gateway.

For IPv6 the equivalent mechanism is Neighbor Discovery (NDP, RFC 4861), which uses ICMPv6 neighbour solicitations rather than broadcasts. The practical consequence for testers is significant: an IPv6 /64 subnet contains 2^64 addresses, so sweeping it address by address is not feasible. IPv6 discovery relies on other sources instead, such as the client's address plan, DNS records, DHCPv6 logs and multicast queries on the local link.

### Layer 3: ICMP probes

Across routers, the classic probe is the ICMP echo request. A live host with default settings replies with an echo reply. ICMP also defines timestamp requests and (historically) address-mask requests, which some hosts answer even when echo is blocked. ICMP probing is cheap, but it is also the most commonly filtered: many perimeter firewalls and host firewalls drop inbound echo requests by policy. A host that ignores ping is not a host that does not exist, and treating "no ping reply" as "down" is the single most common discovery error.

### Layer 4: TCP and UDP probes

The most robust routed technique is to send a TCP segment to a port that is likely to be allowed through the filtering, for example 80 or 443 on a web-facing scope. The trick is that the tester does not need the port to be *open*. A SYN sent to an open port provokes a SYN/ACK; a SYN sent to a closed port provokes a RST. Either reply proves that a live host sent it. An ACK segment sent out of the blue provokes a RST from a live host regardless of port state, which is useful against filters that only block new inbound connections. UDP probes work the other way round: a closed UDP port usually triggers an ICMP port-unreachable message, which again proves the host is there, while an open UDP port often stays silent.

### What Nmap does by default

Nmap is the standard open-source scanner, and its default discovery behaviour encodes the reasoning above. When run with raw-packet privileges against hosts on the local Ethernet segment, it uses ARP. Against routed IPv4 targets with privileges, its default discovery probe set is an ICMP echo request, a TCP SYN to port 443, a TCP ACK to port 80 and an ICMP timestamp request; a reply to any one of them marks the host up. Without privileges it cannot craft raw packets, so it falls back to ordinary TCP connection attempts to ports 80 and 443. Knowing this default matters, because when the default probes are all filtered, Nmap reports the host as down and moves on.

**Relationships.** Read each row from left to right as a cause and effect. The option in the second column causes a packet to be sent; the third column is the only thing that turns "no idea" into "host up". The fourth column tells you when an absence of reply is meaningless. For example, the *ICMP echo* row shows `-PE` producing an *echo reply*, with the warning that echo is often dropped at perimeters.

**Execution flow.** In practice Nmap sends several of these probes in parallel to each address and marks the host up as soon as any one reply arrives. A host is marked down only when every probe has timed out, including retransmissions.

**Decision logic.** The key decision the table supports is *which* probes to add when the default set is likely to be filtered. On a local segment, ARP alone is enough. On a routed scope with web servers, adding TCP SYN probes to the ports the client says are exposed raises confidence. When the scope document guarantees that every listed host exists, `-Pn` skips discovery entirely.

**Technical interpretation.** The TCP rows work because a live TCP/IP stack is obliged by the protocol (RFC 9293) to answer unexpected segments, either by continuing a handshake or by resetting. That obligation is far harder for an administrator to remove than an ICMP filter rule, which is why TCP probes survive filtering more often.

**Practical example.** In an isolated lab on 192.0.2.0/24 where every host drops ICMP, a default discovery from a routed position may still find the web servers via the TCP probes to 443 and 80, but would miss a database server that exposes only port 5432. Adding `-PS5432` to the run brings it back.

**Security implications.** Every probe in the table is visible to a network sensor. Defenders who see a single source sending echo, SYN and ACK probes to many sequential addresses within seconds are looking at discovery (MITRE ATT&CK T1595, Active Scanning, from outside; T1018, Remote System Discovery, from inside).

**Key learning.** Silence is not absence. Choose probes based on what the target's filtering is likely to allow, and record which probes you used so that a "down" verdict can be judged later.

## Building the target list safely

The probe choice is only half of host discovery; the other half is deciding exactly which addresses are probed. Professional testers never type ranges directly into a scanner during an engagement. They build a target file from the signed scope, review it, expand it to see exactly which addresses it contains, remove exclusions, and only then feed it to the tools. Every tool in the engagement reads the same file, so a correction made once applies everywhere.

Nmap supports this workflow directly. `-iL file` reads targets from a file (one address, range or CIDR block per line). `--exclude` takes a comma-separated list of hosts to skip, and `--excludefile file` reads exclusions from a file. The `-sL` option performs a *list scan*: it expands the targets into individual addresses and prints them (performing reverse-DNS lookups unless `-n` is given) **without sending any packets to the targets themselves**. A list scan is the safest possible rehearsal, because it shows you precisely what a real run would touch. If the list scan shows 512 addresses when the scope document says 256, you have found a CIDR typo before it became an incident.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The flow shows the safe procedure that turns a signed scope into a verified list of live hosts. It matters because the dangerous mistakes in discovery are rarely about probes; they are about pointing correct probes at the wrong addresses.

**Components.** There are six steps. *Signed scope* is the authorisation document (for this course, `scope.md`). *Target file* is the machine-readable copy that tools read. *List scan (-sL)* expands the file without sending packets to targets. *Review and exclude* compares the expanded list with the scope and applies the exclusion list. *Discovery (-sn)* sends the live probes. *Live-host list* is the evidence output, highlighted as the outcome that the next lesson consumes.

**Relationships and arrows.** Each arrow is a hand-off of a file, not just an idea: the scope becomes a target file, the target file becomes an expanded list, the reviewed list becomes the input to discovery, and discovery writes the live-host list. The feedback arrow drawn from the final step back up the flow, labelled *unexpected result: return to review before probing again*, represents re-checking when discovery surprises you, for example when a host answers that was expected to be decommissioned.

**Execution flow.** The order is strict. No packet leaves the tester's machine for a target until the review step has been completed and recorded. Only the *Discovery* step is active; the first four steps are paperwork and dry runs.

**Decision logic.** At the review step the tester asks two questions: does the expanded count match the scope document, and is every exclusion actually excluded? A "no" to either stops the process and sends the tester back to the target file. During discovery, a host that is missing but expected leads to a second, broader probe set rather than an immediate "down" verdict.

**Technical interpretation.** `-sL` relies on Nmap's own target-parsing code, which is the same code a real scan uses, so the dry run is a faithful preview. `-sn` tells Nmap to perform host discovery and then stop, rather than continuing into a port scan.

**Practical example.** A lab scope lists 192.0.2.0/25 (128 addresses) with 192.0.2.1 (the lab router) excluded. The tester writes `192.0.2.0/25` to `targets.txt` and `192.0.2.1` to `exclude.txt`, runs a list scan with `-iL targets.txt --excludefile exclude.txt -sL -n`, confirms the count is 127, and only then runs discovery.

**Security implications.** The procedure is a control against the scenario in this course's case study, where a mistyped range swept production hosts and triggered an incident. Defenders benefit too: the agreed target file can be shared with the client's monitoring team so they can tell authorised discovery from a real attack.

**Key learning.** Verify the target list without touching the targets, then probe. A dry run costs seconds; an out-of-scope sweep can end an engagement.

## Step-by-step workflow and worked example

The commands below assume an isolated lab network you own on 192.0.2.0/24 (substitute your own lab range) and, for the hands-on part, the course lab target on loopback. Read every flag explanation before running anything.

```bash
# 1. Dry run: expand the target list, no packets to the targets
nmap -sL -n -iL targets.txt --excludefile exclude.txt

# 2. Host discovery only, default probes, show why each host is up
nmap -sn -n --reason -iL targets.txt --excludefile exclude.txt -oA disc_default

# 3. Add TCP SYN probes to ports the scope says are exposed
nmap -sn -n --reason -PS22,443,5432 -iL targets.txt --excludefile exclude.txt -oA disc_syn
```

Flag by flag:

- `-sL` performs a list scan: it lists each target address and does not send probes to the targets.
- `-n` disables DNS resolution, which keeps the run quiet (no lookups to the client's DNS servers) and faster. Use `-R` instead when you want reverse DNS for every address.
- `-iL targets.txt` reads targets from the file; `--excludefile exclude.txt` removes listed hosts.
- `-sn` means host discovery only: no port scan follows.
- `--reason` adds the reason for each verdict, such as which reply type marked the host up. That reason is evidence you will want in your notes.
- `-PS22,443,5432` adds TCP SYN discovery probes to the listed ports. The related `-PA` (TCP ACK), `-PU` (UDP), `-PE` (ICMP echo), `-PP` (ICMP timestamp) and `-PR` (ARP) select the other probe families.
- `-oA disc_default` writes the results in Nmap's normal, XML and grepable formats at once, using the given base name. Lesson 7 explains why you always keep machine-readable output.

There is no saved Nmap output in the course lab kit, so this lesson does not reproduce one; when you run these commands in your own lab, the output you capture is your evidence. What the lab kit *does* include is a minimal, single-target liveness check. `LAB_ASSETS/C05/enumerate.py` opens one TCP connection to the agreed port before it sends a single HTTP request, which is host discovery reduced to its smallest safe form: "is the in-scope service there at all?" Run with the lab target stopped, the tool reports exactly that and exits with status 1:

```terminal
$ python enumerate.py --port 8099
============================================================
SCOPED ENUMERATION  target=127.0.0.1:8099 (in scope)
============================================================
service not reachable - start target/app.py first
```

With the target started (`python target/app.py`), the saved execution-tested output (`data/enumerate_output.txt`) begins:

```terminal
$ python enumerate.py
============================================================
SCOPED ENUMERATION  target=127.0.0.1:8099 (in scope)
============================================================
[tcp] 127.0.0.1:8099 open
```

**Interpreting it.** The `[tcp] ... open` line is a positive liveness result: a full TCP handshake completed with the in-scope address, so the host is up and the agreed service is listening. The "not reachable" result is ambiguous on its own (the host could be down, the service stopped, or a filter in the way), which is exactly the ambiguity a real discovery run has; on loopback the explanation is simply that the target process was not running. Notice that the tool states its scope assumption in the banner line (`(in scope)`) before doing anything. That habit, printing the target and the scope decision at the top of every output, makes evidence self-describing.

## Common mistakes and misconceptions

- **"No ping reply means the host is down."** ICMP is the most commonly filtered probe. Always ask which probes were used before trusting a "down" verdict.
- **Skipping the list scan.** Ranges are easy to mistype: 192.0.2.0/23 contains twice as many addresses as 192.0.2.0/24, and half of them may belong to another organisation.
- **Using `-Pn` everywhere "to be thorough".** Skipping discovery makes Nmap port scan every address as if it were live. On a large scope of mostly empty space this multiplies scan time and traffic; use it when the scope guarantees the hosts exist or when discovery has proven unreliable for specific hosts.
- **Forgetting DNS.** Without `-n`, Nmap performs reverse lookups that reach the client's DNS infrastructure. That is usually acceptable, but it should be a deliberate choice recorded in your notes.
- **Assuming a stable result.** Laptops sleep, virtual machines are created and destroyed, and DHCP leases change. A discovery result is a snapshot with a timestamp, not a permanent fact.
- **Trying to sweep IPv6 like IPv4.** A /64 cannot be enumerated address by address; work from the client's address plan, DNS and local-link multicast instead.

## Security implications, detection and defence

From the defender's side, host discovery is one of the earliest observable stages of an intrusion. MITRE ATT&CK catalogues it as T1595 (Active Scanning) when performed from outside and T1018 (Remote System Discovery) when performed from a foothold inside the network. Typical signals include one source touching many addresses in a short time, sequential address order, identical probe patterns across hosts (echo plus SYN 443 plus ACK 80 plus timestamp is a recognisable signature), and unsolicited ACK segments that match no existing connection. Network intrusion-detection systems and flow analytics detect these patterns well; host firewalls log dropped probes.

Defensive controls fall into three groups. **Reduce what answers:** drop unsolicited inbound ICMP and TCP at the perimeter where business needs allow, segment internal networks so a single compromised host cannot reach every subnet, and remove or isolate unmanaged assets that discovery reveals. **Detect what probes:** alert on fan-out patterns from a single source, and correlate internal sweeps with endpoint telemetry, because an internal sweep from a workstation is a strong compromise indicator. **Know your own estate:** run authorised discovery against your own networks regularly and compare the result with the asset register, because the gaps are where attackers find forgotten systems.

> [!WARNING]
> In India, the CERT-In Directions of April 2022 list targeted scanning or probing of critical networks and systems among the incident types organisations must report. An unannounced or out-of-scope sweep can therefore trigger a mandatory incident report at the client. Agree the testing window, source addresses and target file with the client's security team in advance.

## Best practices

1. Derive the target file from the signed scope, keep it under version control, and reference its hash in your notes.
2. Always perform a list scan (`-sL -n`) and compare the address count with the scope before any active probe.
3. Maintain an explicit exclusion file and pass it to every tool.
4. Choose discovery probes for the environment: ARP on local segments, mixed ICMP and TCP probes across routers, and TCP SYN probes to known-exposed ports when ICMP is filtered.
5. Use `--reason` and save output with `-oA` so every "up" or "down" verdict can be justified later.
6. Record start and end times and the source address you scanned from; the client's monitoring team will ask.
7. Treat unexpected live hosts as findings to confirm with the client, not as new targets to explore.

## Key takeaways

- Host discovery decides which in-scope addresses receive deeper testing; a false negative hides a host from the entire engagement.
- Probes work at layer 2 (ARP, local only), layer 3 (ICMP, often filtered) and layer 4 (TCP/UDP, most robust across routers). Silence is not absence.
- Nmap's default routed probe set with privileges is ICMP echo, TCP SYN to 443, TCP ACK to 80 and ICMP timestamp; on a local segment it uses ARP.
- Build, expand (`-sL`) and review the target list before sending a single probe, and pass an exclusion file to every tool.
- Discovery is visible (ATT&CK T1595 and T1018), so coordinate with the client and record your source, times and probe choices.
- The lab kit's `enumerate.py` demonstrates the minimal form: one TCP connect to the in-scope port, refusing everything outside scope.
