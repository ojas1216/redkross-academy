## Introduction and conceptual foundation

Lesson 1 set out the principles that make forensic work defensible: preserve the original, work on verified copies, record every action and keep conclusions within what the data supports. This lesson asks a narrower question that every one of those principles depends on: **what kind of thing is this item of evidence?** An examiner who cannot answer that question cannot say how the item should be packaged, what a hash of it proves, how quickly it can change, who else holds a copy, or how far back anyone can vouch for its state.

Digital evidence differs from most physical evidence in three ways that drive the rest of this lesson. First, it is **latent**: nobody can read a disk or a log by looking at it, so every observation passes through hardware and software, and the examiner must be able to say which. Second, it is **fragile and easily changed**: switching a device on, opening a file or re-exporting a mailbox can alter data or metadata, often without any visible sign. Third, it is **copyable without loss**: a verified copy can be bit-for-bit identical to the original, which is what allows examiners to work on copies at all, but it also means many "versions" of an item can exist, and each one needs its own history.

Because of these properties, it is not enough to label something "the laptop" or "the logs". A practitioner classifies an item along several independent axes at once: where the data came from, how stable it is, whether it is an original, a copy or something derived from one, and how the record came into existence. Each axis answers a different practical question, and mistakes usually come from collapsing two of them together, for example treating a provider's export as if it were the provider's live system, or treating a parsed timeline as if it were the disk it was parsed from.

The lesson uses a fictional case throughout. **Kestrel Freight Pvt Ltd** (a fictional logistics company in Pune) suspects that a confidential tender-pricing spreadsheet was sent to a competitor. The company's legal team has authorised an internal investigation with a written scope, and IT operations has handed a set of items to the forensic lab. You will classify those items, review the intake receipt, and then read the course's own acquisition transcript as an example of how a disk image becomes an evidence record.

> [!NOTE]
> This lesson is about recognising and recording evidence types. It does not teach collection from live systems. Acquisition methods, write blocking and imaging are covered in Module 2, and the order of volatility is the subject of Lesson 3. Indian legal handling is covered in Lesson 4; nothing here is legal advice or a statement about admissibility.

## Key terminology

| Term | Meaning in this course |
| --- | --- |
| Evidence item | A distinct thing received, collected or created in a case and given its own identifier, such as a laptop, a USB drive, an export file or a printed page. |
| Physical item | A tangible object that holds or displays data: a device, storage medium or paper document. It is handled, packaged and sealed as an object. |
| Digital data | The bits held by a physical item or a service. It is examined through tools, never directly. |
| Persistent (non-volatile) data | Data that survives loss of power, such as files on a disk or records in a log file. |
| Volatile data | State that exists only while a system runs, such as the contents of memory or current network connections. It is lost or changed when the system stops. |
| Original | The source as it existed in its original location, for example the laptop's internal disk. |
| Forensic copy | A copy of the original made by a documented process and verified against it, usually with a cryptographic hash. |
| Working copy | A further copy of a verified forensic copy, used for analysis so that the forensic copy is never handled routinely. |
| Derived artefact | Output produced by processing evidence: a parsed timeline, an extracted file, a carved fragment, a report table. |
| Provider export | Data produced for the lab by someone else's system or staff, such as a mail-platform export or a firewall log export. The lab receives it, it does not collect it. |
| Metadata | Data about data: file-system timestamps and sizes, document properties, message headers, log fields that describe an event. |
| Artefact | A trace left by a system or user activity. It becomes **evidence** when it is relevant to a question in the case. |
| Integrity anchor | The earliest reliable record of an item's state, for example a seal number on a bag or a hash recorded at acquisition. |

## Why classifying evidence matters

Classification is not paperwork for its own sake. Each classification decision has a practical consequence.

- **Handling.** A sealed laptop is stored as a physical object with its seal number and photographs. A CSV export is stored as a file with a recorded hash. A printed page may also matter to examiners in other disciplines, so it must not be handled in a way that damages it.
- **Integrity claims.** What a hash proves depends on when it was first recorded and what object it covers. The same hash value can support a strong statement for one item and only a narrow statement for another.
- **Completeness.** A full device image can answer questions nobody had thought of at collection time. A targeted export answers only the questions its filter allowed for. Knowing which you hold tells you which conclusions are available.
- **Independence.** Two copies of the same export agreeing with each other show only that the copy worked. Two independent sources recording the same event corroborate each other. Without classification, the difference is easy to miss.
- **Disclosure and privacy.** Items differ in how much unrelated personal data they hold. Recording the type helps the lab limit access and processing to what the authorised purpose needs. That supports the organisation's own policies and any data-protection obligations that apply, which in India may include the Digital Personal Data Protection Act, 2023; Lesson 4 deals with the legal side.

## Classifying by source: where the data lives

NIST Special Publication 800-86, *Guide to Integrating Forensic Techniques into Incident Response*, organises its practical chapters around four sources of data: **data files**, **operating systems**, **network traffic** and **applications**, followed by a chapter on combining data from multiple sources. The publication was written for incident-response teams in organisations rather than for courts, and it predates much of today's cloud and mobile practice, but its source categories remain a useful planning checklist because they force an examiner to ask where else a relevant record might be held.

**Data files** are the documents, spreadsheets, images, archives and other files that users and programs create. In the Kestrel case, the pricing spreadsheet itself is a data file, wherever copies of it exist. Files carry content and two kinds of metadata: what the file system records about them (names, sizes, timestamps, location) and what the file format embeds inside them (for example, document properties written by an office application).

**Operating-system data** is what the OS records about its own operation and its users: configuration, account information, logs of logons and services, records of attached devices, and the volatile state of a running system such as processes and network connections. On the Kestrel laptop this category may show which user accounts were active and whether removable media were attached. Module 4 and Module 5 cover the Windows artefacts in detail.

**Network traffic** evidence is what devices on the network recorded about communications: firewall and proxy logs, flow records and, where it was captured, packet data. Crucially, these records are usually held **outside** the endpoint under investigation. A question such as "did the spreadsheet leave the network?" may be answerable only from records on a firewall or a mail platform, not from the laptop at all.

**Application data** is what particular programs store: a mail client's local cache, a browser's history database, a chat application's message store, a database's transaction log, or the audit log of a software-as-a-service platform. Application data often crosses the other categories: a mail platform's audit log is application data, held on someone else's system, describing a network event.

Thinking by source protects against the most common planning gap, which is to treat the seized device as the whole case. If the only items in the lab are those that happened to be on the suspect's desk, the examiner should ask which other sources, held by IT, a service provider or another business unit, would record the same activity from a different vantage point.

## Classifying by form and stability

The second axis is what the evidence physically is and how quickly it can change.

**Physical items** are devices, storage media and documents. They are identified by observable features (make, model, serial number, asset tag, colour, markings), packaged, sealed and photographed. The data inside a sealed device has not yet been examined, and the receipt should not describe it as if it had been. A USB drive marked "32 GB" should be recorded as *marked* 32 GB; the capacity the device actually reports is established later, at acquisition, and may differ from the label.

**Persistent data** survives power loss: files on disks, log files, databases. It is stable in the sense that it does not vanish at shutdown, but it is not frozen. Logs rotate and overwrite old entries, retention settings delete records after a period, and normal use of a running system changes timestamps and frees space that can later be reused. The practical consequence is that persistent evidence held by other parties, such as firewall logs, has a time limit even though it is "non-volatile".

**Volatile data** exists only while a system runs: memory contents, running processes, current network connections, and similar state. Once power is removed it is gone. RFC 3227, *Guidelines for Evidence Collection and Archiving*, made the ordering of collection by volatility a widely cited principle, and Lesson 3 covers it. For this lesson the key point is a recording discipline: if a device arrives powered off, as the Kestrel laptop did, the receipt should say so, and the report must not later imply that information was available from memory when it never was.

**Documents and printouts** sit at the boundary. A printed copy of the pricing spreadsheet found on a desk is a physical item that displays data. It may be relevant in its own right (who printed it, when, and where was it found?), but it is not a substitute for the digital file: it carries none of the file's metadata, and it shows only what was printed.

## Classifying by provenance: originals, copies and derivatives

The third axis is the item's relationship to the original source. This is where most integrity errors happen, because the different generations of an item look alike.

The **original** is the source in its original location: the laptop's internal storage, the firewall's own log store, the mail platform's mailbox. An examiner rarely analyses the original directly. Instead, a **forensic copy** is made by a documented process and verified against the source, and further **working copies** are made from the verified forensic copy for day-to-day analysis. The SWGDE *Best Practices for Computer Forensic Acquisition* treats acquisition as a planned and documented activity whose result is verified; this lesson relies on it only for that general point, and learners should read the current version for its specific recommendations. Module 2 covers how acquisitions are actually performed.

**Derived artefacts** are produced by processing evidence: a timeline built by a parser, a file extracted from an image, a list of keyword hits, a screenshot of a tool's display, the tables in a report. A derived artefact is only as good as the source it came from and the process that made it. For that reason, the record for any derived artefact should name the source item and its hash, the tool and version used, and the settings that matter, so that a second examiner could re-create it from the same verified source.

**Provider exports** are a special case of provenance. When IT operations exports a mailbox or a firewall log and hands the file to the lab, the lab receives a copy made by someone else's process, often filtered by date, user or event type. The lab can verify that the file it holds matches what the provider says it exported, if the provider recorded a hash or manifest. It cannot, from the file alone, show that the export captured everything relevant on the provider's system. That limitation belongs in the record from day one.

## Classifying by how the record came to exist

The fourth axis concerns the origin of the content itself. It matters for interpretation rather than handling.

**User-created content** is what a person deliberately wrote or saved: the text of an email, the figures in a spreadsheet, a chat message. It tells you what someone expressed, but on its own it does not reliably tell you who that someone was, because accounts are shared, devices are left unlocked and documents are edited by several people.

**System-generated records** are produced automatically by software without anyone choosing their content: a logon event, a firewall connection record, a file-system timestamp. They are often treated as more objective, and they are less prone to deliberate wording, but they depend on configuration and clocks. A log records what the system was configured to record, in the time basis it was configured to use. A missing log entry may mean that nothing happened, or that logging was not enabled for that event.

**Hybrid records** mix both. A document's "author" property is written by the application from the user name configured in it, which may have been set by whoever installed the software, inherited from a template, or edited later. It is application metadata about user-created content, and it is a lead to corroborate rather than an identification in itself.

A related distinction is between **content** and **metadata**. The same spreadsheet has content (the pricing figures), embedded metadata (properties stored inside the file) and file-system metadata (name, size and timestamps recorded by the file system). These are written by different layers at different moments. After a file is copied, edited or moved between systems, it is normal for them to disagree. A disagreement is a fact to explain, not a reason to discard one of them, and Module 3 explains how each file system records its timestamps.

## Corroboration and independence

Classifying by source and provenance pays off when you weigh evidence. Suppose the Kestrel laptop's operating-system records show a removable drive being attached on 11 March, and the USB drive E-02, when examined, contains a copy of the pricing spreadsheet. These are two independent sources, one on the host and one on the medium, recording related facts, and together they support a stronger inference than either alone.

Now suppose IT operations sends the firewall CSV twice, once by internal transfer and once on a disc, and the two files have the same hash. That agreement proves only that the two copies are identical. They are one source, not two, and they cannot corroborate each other. The same applies to a working copy agreeing with a forensic copy: it confirms the copying process, nothing about the events.

A useful test is to ask, for any two items that agree, whether they could both be wrong for the same reason. Two copies of one export share every error in that export. A host record and a firewall record would require two separate systems to be wrong in a matching way.

## Evidence you receive versus evidence you collect

Many items in a modern case are not collected by the forensic examiner at all. They are **received**: exported by an IT team, produced by a service provider, handed over by a manager. The receipt is therefore an evidence record in its own right. It fixes what arrived, from whom, when, in what condition and with what integrity reference.

### Reviewing the receipt

A good intake review reads each line and asks what the record does and does not establish.

1. **E-01, the laptop.** It is a physical item; nothing about its contents is known yet. "Powered off" is a recorded state, which means no volatile state from before shutdown is available from this item. The receipt should not, and does not, list files or users.
2. **E-02, the USB drive.** "Marked 32 GB" is correctly recorded as a marking. Its reported capacity and contents will be established when it is acquired.
3. **E-03, the mailbox export.** On intake the lab computes the archive's SHA-256 offline on the received file and compares it with the manifest. If they match, the lab's copy is tied to the file the provider says it exported. The match says nothing about whether the export's filter, here the pricing-team mailbox for 1 to 12 March, captured every relevant message. If the investigation later needs February, a new export must be requested within the authorised scope.
4. **E-04, the firewall CSV.** No integrity reference was supplied, so the lab's own hash at intake is the first anchor. The reviewer should ask IT operations, in writing, who exported the file, when, with what filter, and in what time basis the timestamps are written. Without the time basis, correlating firewall records with IST times elsewhere in the case is guesswork.
5. **E-05, the printout.** It is a physical document and is kept as one, in its own envelope. It may be relevant to questions that digital examination cannot answer, and it should not be handled in ways that would prevent other examinations. It does not replace the digital spreadsheet.
6. **The phone.** The note records a boundary. If messages on E-03 later suggest the phone was used, the examiner records that observation and refers it to the authorising party. Collecting it is a scope decision, not an examiner's improvisation.

> [!IMPORTANT]
> A hash computed at intake proves the item's state from intake onwards. It cannot vouch for anything that happened to the item before the lab received it. Record who can vouch for the earlier period, or record that nobody can.

## Reading the course acquisition transcript as an evidence record

The course kit includes a saved transcript of a practice acquisition of a 16 MiB lab source. It is reproduced here exactly as supplied. The transcript records section headings and results; it does not show the commands that were run, so this lesson does not reproduce or guess them. Module 2's acquisition lab works through the process itself.

```text
== 1. hash source before acquisition
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

Read as an evidence record, the transcript shows the provenance classes from earlier in this lesson in miniature:

- **Section 1** records the source, labelled `suspect.dev`, with a 64-hex-character value. A SHA-256 digest is 256 bits, which is 64 hexadecimal characters. This is the reference value that later generations are checked against.
- **Section 2** records the digest of the data stream as it was written to the image file. It matches section 1, so the data read during acquisition matched the source as hashed before it.
- **Section 3** re-reads the stored file `evidence.dd` and records both its digest and its size, 16,777,216 bytes (16 MiB). The match shows the file at rest holds what was read. `evidence.dd` is the **forensic copy**.
- **Section 4** creates `working.dd`, a **working copy**, and verifies it against the same value.
- **Section 5** deliberately changes one byte of the working copy. The digest changes completely, and a byte comparison against `evidence.dd` locates the difference. The comparison reports `char 100001` for a change at offset 100000 because offsets count from zero while the comparison counts bytes from one. The `line 1` part counts newline bytes and has no meaning for a disk image.
- **Section 6** records an MD5 digest of the forensic copy. The heading itself states the reason: legacy compatibility only. MD5 is 128 bits (32 hexadecimal characters) and practical collisions are known, so SHA-256 remains the primary integrity value.

**Execution flow.** The transcript's sections 1 to 6 map onto the graph in order: hash the source, acquire with a stream hash, verify the stored file, make and verify a working copy, alter it, and record MD5.

**Decision logic.** At each solid arrow the implicit question is "do the digests match?". Where they match, the new item inherits the anchor of the one before. Where they do not, as after the edit, the item has left the verified family and must not be used as if it were the forensic copy.

**Technical interpretation.** A digest match is strong evidence of bit-identity with what was hashed earlier. It does not show that the right source was chosen, that the source was unaltered before section 1, or that the source contained everything the case needed.

**Practical example.** If a Kestrel analyst's working copy of the laptop image were accidentally modified by a tool, re-hashing it against the forensic copy would expose the change exactly as section 5 does, and the analyst would make a fresh working copy from the forensic copy.

**Security implications.** Keep the forensic copy read-only and access-logged, analyse only working copies, and re-verify after any suspected change.

**Key learning.** Each generation needs its own check back to the anchor; a derived artefact is trustworthy only through the verified copy it came from.

## Common mistakes and misconceptions

- **"The hash proves the evidence is authentic."** A hash proves that two sets of bits are identical, with overwhelming probability. It says nothing about whether the right item was collected, whether it was altered before it was first hashed, or whether the content means what someone claims.
- **Treating an export as the system.** A mailbox export is a filtered copy of a mailbox made at a particular time. Saying "the mailbox contains no messages to the competitor" when only an export for 1 to 12 March was examined is an overstatement.
- **Counting copies as corroboration.** Identical copies of one source are one source.
- **Describing contents on a receipt.** The intake receipt records what was observed: labels, seals, condition. Contents are established by examination, later, and recorded in the examination notes.
- **Ignoring the time basis.** Records from different systems are often written in different time zones or with unsynchronised clocks. A firewall in UTC and a receipt in IST differ by five and a half hours.
- **Discarding inconvenient metadata.** When embedded document properties and file-system timestamps disagree, both are facts. Explain the difference rather than choosing the one that fits a theory.
- **Letting derived output drift from its source.** A timeline CSV with no record of which image it came from, or which tool version produced it, cannot be re-created or checked.
- **Reading tool test reports as guarantees.** The NIST Computer Forensics Tool Testing (CFTT) Program develops test methods for forensic tool functions and publishes reports on how particular tool versions behaved under test. A report describes the tested version and conditions; it is not a certification, and it does not replace the lab's own checks of the version and configuration it actually uses. This course makes no claim that any tool is validated.

## Security implications, detection and defence

Evidence is itself an asset to protect. A lab that classifies items well can also defend them well.

- **Protect the anchors.** Store forensic copies read-only, separate from working areas, with access restricted and logged. Keep recorded hash values in a location that the people handling the copies cannot silently edit.
- **Detect change by re-verification.** Re-hash forensic copies on a schedule and before reporting, and re-hash working copies after using any tool that could write to them. Section 5 of the transcript shows how decisively a single changed byte is detected.
- **Limit personal data.** Mailboxes, device images and chat stores contain unrelated personal data. Restrict who can see each item, process only what the authorised purpose needs, and record those decisions.
- **Preserve provider-held evidence early.** Firewall, proxy and platform logs are persistent but subject to retention limits. Identifying them as relevant sources early, and asking the holder to preserve them under the authorised scope, prevents silent loss.
- **Keep scope boundaries visible.** Recording items that were *not* received, such as the phone in the Kestrel case, protects both the investigation and the people involved.

## Best practices

1. Give every item its own identifier, and give new generations (images, working copies, exports of exports) their own identifiers linked to their parent.
2. Classify each item on all four axes: source, form and stability, provenance, and origin of content.
3. Record the integrity anchor at the earliest possible moment, and record who can vouch for the period before it.
4. For received items, record who produced them, when, by what process, with what filter and in what time basis.
5. Use SHA-256 as the primary integrity value; record MD5 only where an older record or partner requires it.
6. Keep the forensic copy untouched; analyse working copies; re-verify after any suspected change.
7. Record the tool, version, settings and source hash for every derived artefact.
8. State limitations in the record as soon as they are known, not only in the final report.

## Practical exercises (paper and offline only)

These exercises use the fictional Kestrel records and the course transcript. They need no access to any real system. Where a hash is computed, it is computed offline on a file the learner owns.

**Exercise 1: Classify the intake.** For each of E-01 to E-05, write one line giving its source category (file, OS, network, application, or physical document), its form and stability, and its provenance (original, forensic copy, working copy, derived artefact, or provider export). Then list two sources that are *not* in the intake but would record whether the spreadsheet left the network.

*Model answer.* E-01 and E-02 are physical items holding originals whose data is persistent; E-01 is powered off, so no volatile state is available. E-03 is application data in the form of a provider export with a manifest. E-04 is network evidence in the form of a provider export without a manifest. E-05 is a physical document displaying file content. Missing sources include the mail platform's own audit or transport records and any web proxy records, each held by IT operations and requestable only within scope.

**Exercise 2: Write the follow-up request.** Draft the written questions the lab should send IT operations about E-04. A good answer asks who exported it, the export time, the filter applied, the time basis of the timestamps, whether the firewall clock is synchronised, and whether the original log store remains preserved.

**Exercise 3: Interpret the transcript.** Using only the transcript, answer: which file is the forensic copy; which section first shows the stored file matches the source; why section 5's comparison reports 100001; and why the MD5 line does not replace the SHA-256 values. Then state one thing the transcript cannot tell you, such as who ran it, when, or what physical source `suspect.dev` represents.

**Exercise 4: The forwarded screenshot.** A Kestrel HR manager forwards a screenshot of a chat message apparently sent by the employee. Classify it, explain why it is a derived presentation rather than the record itself, and write the scope question you would put to the authorising party about obtaining the message in its native form from the platform's administrator. Keep the screenshot as a received item with its own identifier.

**Exercise 5: Your own offline check.** Take a file you created yourself, compute its SHA-256 with a tool already on your own computer, make a copy, change one character in the copy, and hash both again. Record the four values and a one-sentence statement of what the comparison proves and what it does not.

## Key takeaways

- Classify every item on several axes at once: where the data lives, how stable it is, whether it is an original, copy or derivative, and how its content came to exist.
- NIST SP 800-86's four sources (files, operating systems, network traffic and applications) are a planning checklist: ask where else the same activity was recorded.
- An item's integrity anchor is the earliest reliable record of its state. A hash at intake vouches only from intake onwards.
- Provider exports are filtered copies made by someone else. Verify them against any manifest and record their filter and time basis.
- Identical copies confirm copying, not events. Corroboration needs independent sources.
- Derived artefacts are only as reliable as the verified source and the recorded process behind them.
