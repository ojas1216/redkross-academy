## Introduction and conceptual foundation

The first seven lessons of this module set out the rules of forensic work: preserve the original, prefer the most volatile evidence first, handle evidence within the law, keep an unbroken chain of custody, write down everything you do, and behave ethically when you see other people's data. A lab is where those rules become physical arrangements. Before you can claim that an examination did not change the evidence, you need a place to keep originals that analysis tools never touch. Before you can state which tool produced a result, the tool's version has to be written down somewhere. Before you can say that a digest proves two files are identical, you need to have watched your own hashing routine report a match on identical data and a mismatch on changed data. This lesson builds that place and those habits.

A forensic lab is not a collection of expensive software. It is a controlled environment with four properties. It is **isolated**, so that evidence cannot leak out and nothing from outside can alter it. It is **organised**, so that originals, working copies, exports, notes and reports live in separate, predictable places. It is **inventoried**, so that every tool and version used in a case can be named later. It is **checked**, so that you have evidence from known test data that your verification routine works before you rely on it for real evidence. The Module 2 acquisition lab and every later lab use this workstation.

NIST Special Publication 800-86, *Guide to Integrating Forensic Techniques into Incident Response*, describes the forensic process in four phases: collection, examination, analysis and reporting. It also treats preparation as part of building a forensic capability: policies, procedures, trained staff and ready tools come before the first case, not during it. Lab setup is that preparation, scaled down to one learner's workstation. The SWGDE *Best Practices for Computer Forensic Acquisition* treats acquisition as a documented process. Where possible, the source is protected from change, and the acquired data is verified, usually with hash values. Your lab has to support both of those things before Module 2 asks you to do them.

> [!IMPORTANT]
> **Scope and authorisation for this lab.** Everything in this lesson takes place on a computer or virtual machine that you own or are formally permitted to use for training. The only evidence is the synthetic material supplied with the course kit, plus small text files you create yourself. You do not collect data from any other system, account, phone or network. You do not image a real disk, and you do not use anyone else's personal data. If an employer provides the workstation, get written permission for this training use and keep it in your notes folder.

The running example is a fictional company, Nilgiri Freight Pvt Ltd, which is setting up a small DFIR training lab for its internal response team. One trainee examiner, A. Rao, is building the workstation, and a senior examiner reviews the work. Their records appear throughout the lesson. All of them are fictional training records.

## Key terminology

| Term | Precise meaning in this course |
| --- | --- |
| Analysis workstation | The isolated computer or virtual machine where evidence is examined. It holds the evidence store, the tools and the notes. |
| Original (master) | The first stored copy of an evidence item, which is never opened by analysis tools. Every other copy is made from it and checked against it. |
| Working copy | A copy made from the original for examination, with a digest that has been checked against the original before use. |
| Digest (hash value) | The fixed-length output of a cryptographic hash function such as SHA-256. Identical input gives an identical digest. Any change to the input gives, in practice, a different digest. |
| Manifest | A file that lists the expected digest for each file in a folder, so that a tool can recheck all of them in one pass. |
| Intake receipt | The signed record made when an item enters the lab. It states what was received, from whom, when (in UTC), the digest the supplier stated and the digest computed on arrival. |
| Tool inventory | The list of every tool used in the lab, with its version, where it came from, the digest of the installer or package and the date it was installed. |
| Known-answer check | Running your routine on test data whose correct result is already known, to show that the routine detects both a match and a change. |
| Tool testing (validation) | A formal programme that tests a tool against written requirements with controlled test sets, such as NIST's Computer Forensics Tool Testing (CFTT) programme. A known-answer check on your own workstation does not count as tool validation. |
| Isolation | Technical separation of the workstation from networks, cloud sync, shared folders and other uncontrolled paths that could change or expose evidence. |

The difference between a known-answer check and tool validation matters for the whole course. The NIST CFTT programme develops tool specifications, test methods and test data, and it publishes reports on how specific tool versions behaved in specific test cases. A report like that is useful background. It applies to the version and the test cases it describes, and it does not certify the tool for every use. This course makes no claim that any tool you install has been tested by CFTT or anyone else. Your known-answer check is a smaller, honest claim: on this workstation, on this date, with this version, the routine gave the expected answers on known data.

## The lab architecture: zones and one-way flows

The most important design decision in a forensic lab is the direction in which evidence moves. Originals flow in only one direction: they arrive, are checked, and are stored. Nothing is ever written back to them. Working copies are made from originals and checked against them. Analysis tools only ever open working copies. Anything a tool produces goes to an exports area, where it is hashed and logged before a report cites it. The notes log runs alongside every step, but it records actions and never holds evidence itself.

On disk, this becomes a fixed folder layout for each case. Folder names start with numbers so that they sort in workflow order in any file manager.

| Folder | Holds | Rule |
| --- | --- | --- |
| `00_receipts` | Intake receipts and supplier documents | Receipts are amended by adding an entry, never overwritten |
| `01_originals` | One sub-folder per evidence item | Set read-only after the intake digest is confirmed; never opened by analysis tools |
| `02_working` | Working copies made from originals | Each copy is re-hashed and compared before use; it can be thrown away and remade |
| `03_exports` | Files that tools extract or produce | Every export is hashed and logged with the tool and version that produced it |
| `04_notes` | The case log, written in UTC | Entries are added in time order; late entries are marked as late |
| `05_reports` | Draft and final reports | Reports cite digests and tool versions from the other folders |
| `06_tools` | Tool inventory and installer digests | Updated whenever a tool is added, upgraded or removed |

The layout encodes the custody and documentation rules from Lessons 5 and 6. A reviewer who opens any case folder knows where to look for the receipt, the original, the copy that was actually examined, and the record that links them.

**Decision logic.** The diagram has one branch: whether the digests match at intake. If they match, the item is stored. If they do not, it is held aside, and the mismatch is recorded and reported to the supplier before any analysis starts.

**Technical interpretation.** Separating the zones lets one check carry a lot of weight. Because the original is never opened, its digest at the end of a case should equal its digest at intake. Because each working copy is verified against the original, results from the copy can be traced back to it.

**Practical example.** A. Rao receives the kit's synthetic file `suspect.dev`, confirms that its SHA-256 digest matches the value on the receipt, and stores it under `01_originals/ITEM-01`. The trainee then copies it to `02_working`, re-hashes the copy, and opens only the copy in the analysis tools.

**Security implications.** The isolated VM box and the one-way arrows are the controls. If a cloud-sync client or a shared folder were attached to the originals, there would be an unrecorded path that could change or expose evidence. That path does not appear in the diagram because it must not exist.

**Key learning.** Evidence moves one way, from receipt to original to verified copy to tools to exports. Each move is either verified with a digest or written in the log.

## Building the workstation

This section sets up the workstation in the order the Nilgiri Freight lab used. None of these steps collects data from a live system. They prepare an empty, controlled environment and check it using files you already have.

### Step 1: choose the host and isolate it

Use a dedicated virtual machine on a computer you control. A virtual machine has two practical advantages. First, you can take a **snapshot** of the clean, configured state and return to it after each lab. Second, you can switch off its network adapter and its integration features in one place. Turn off clipboard sharing, drag-and-drop and shared folders between the host and the guest. These features are convenient, but they are also unrecorded paths through which files can move. Turn off the guest's network once the tools are installed. Synthetic evidence does not need the internet, and later modules handle sample material that must not reach a network.

A snapshot is a recovery point for the *analysis environment*. It is not a forensic image of anything, and it never replaces the digests of evidence items. Name snapshots with a date and purpose, such as `2026-11-21 clean baseline after tool install`. Record each snapshot in the case log so that a reviewer knows which environment state an examination started from.

### Step 2: install and inventory the tools while connected, then disconnect

Collect your tools in a separate staging step. Download each tool from its official project, compare the published digest of the installer or package with the digest you compute, and only then install it. Write each tool into the inventory in `06_tools` with these fields:

| Field | Why the reviewer needs it |
| --- | --- |
| Tool name and purpose | Shows why the tool is in the lab at all |
| Exact version string, as the tool itself reports it | Reports have to name the version that produced a result |
| Source (official project name) | Shows that the software came from a known origin |
| Digest of the installer or package | Shows that the installed software is the software you meant to install |
| Install or upgrade date (UTC) | Lets a reviewer match tool changes to case dates |
| Known-answer check date and result | Links the version to your own check |

When the inventory is complete, disconnect the network and take the clean-baseline snapshot. If you need a tool later in the course, reconnect for a staging step, add it to the inventory, and take a new snapshot. Never install software in the middle of an examination without recording it.

### Step 3: set the clock and the time zone

Set the analysis VM's time zone to UTC, and write every case-log entry in UTC. Evidence from different sources records time in different zones and formats. Converting everything to one reference zone at the point of note-taking removes a whole class of errors from later timeline work. At the start of each session, write the workstation's displayed time next to a trusted reference time, so that any drift is on record. The clock does not have to be perfect. It has to be known.

### Step 4: create the case folder layout

Create the seven numbered folders from the table above under a case folder named after the training case, for example `C09-LAB-01`. Separate folders per case are the simplest way to stop one case's files from appearing in another case's report.

Keep the evidence store on storage that only the analysis VM uses. Where your platform supports it, encrypt that storage at rest. Encryption protects confidentiality if the disk is lost. It does nothing for integrity, which is the digests' job.

### Step 5: record a fictional intake receipt

When an item arrives, the receipt is written first. Here is the Nilgiri Freight receipt for the kit's synthetic test file. It is a fictional training record. Its digest field repeats the SHA-256 value that the original C09 acquisition transcript reports for `suspect.dev` in step 1.

```text

Receipt ID       NF-LAB-RCPT-0001
Case             C09-LAB-01 (training; synthetic data only)
Organisation     Nilgiri Freight Pvt Ltd (fictional) DFIR training lab
Item             ITEM-01  suspect.dev

Received from    Course kit maintainer (role)
Received by      A. Rao, trainee examiner
Received (UTC)   2026-11-21 09:40
Stated SHA-256   e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21
Intake SHA-256   recorded from the examiner's own tool at intake
Comparison       all 64 hexadecimal characters compared; result recorded
Stored at        01_originals/ITEM-01/
Signed           handed over (signature)   received (signature)
```

Notice what the receipt does not do. It does not claim that the file is a complete or accurate copy of any real device. A digest only shows that the stored file is identical to whatever was hashed when the supplier stated the value. Whether that file was the right file is a separate question, answered by the supplier's own records. This limit applies throughout the course.

### Step 6: a file-based manifest check on your own data

Before you rely on digests for evidence, prove to yourself that your routine catches a change. Create three small text files of your own in a scratch folder (not in `01_originals`), for example a short note, a list and a paragraph. Write a manifest of their SHA-256 digests, check it, change one character in one file, and check it again.

On a Linux analysis VM with GNU coreutils:

```bash
sha256sum note.txt list.txt para.txt > manifest.sha256
sha256sum -c manifest.sha256
```

The first command computes a SHA-256 digest for each named file and redirects the lines, each in the form *digest, two spaces, file name*, into `manifest.sha256`. In the second command, `-c` (check) tells `sha256sum` to read the manifest, recompute each listed file's digest, and report each file as matching or failing. The second run, after your one-character edit, should report a failure for exactly the file you changed. If it does not, your routine is not doing what you think, and you must find out why before Module 2.

On a Windows analysis VM, PowerShell has a built-in cmdlet:

```powershell
Get-FileHash -Algorithm SHA256 .\note.txt
```

`Get-FileHash` computes a digest of the file at the given path, and `-Algorithm SHA256` selects the algorithm explicitly rather than relying on the default. PowerShell displays the digest in uppercase hexadecimal, while `sha256sum` prints lowercase. Hexadecimal digits are not case-sensitive, so `E3A7` and `e3a7` are the same value. Compare digests in a way that ignores case, and compare every character, not just the first and last few.

This lesson does not reproduce the output of these commands, because the course kit did not capture them. Write the results you see into your own case log.

### Step 7: snapshot, record and clean up

When the manifest check passes and fails as expected, delete the scratch files, write the result in the inventory's known-answer column, and take a snapshot. The workstation is now ready for Module 2.

## Reading the known-answer transcript

The original C09 kit transcript for the acquisition lab is your reference for what correct verification looks like. Module 2 explains the acquisition itself. Here it serves a narrower purpose: it shows the results that a working hashing and comparison routine should produce. Read it now so that the values are familiar when you produce your own. The text below is the complete transcript as supplied with this lesson (`C09/rk_c09_acquire_lab_output.txt`), reproduced without changes.

```text
== 1. hash source before acquisition
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

The transcript records results, not the exact command lines. Its step headings name the approach: step 2 passes the data through `dd` and `tee` so that the image file and the hash are produced in one pass. The commands themselves belong to Module 2, and this lesson does not reconstruct them.

**Step 1** hashes the source before anything else happens. That gives a reference value that does not depend on the acquisition. **Step 2** reports a digest computed on the data stream as it was written. That digest equals the step 1 value, so the bytes that passed through the pipeline were the source bytes. **Step 3** hashes the image file as stored on disk. That is a separate check on the write to storage, and it also records the size: 16,777,216 bytes, which is exactly 16 MiB (16 × 1,024 × 1,024). **Step 4** shows that the working copy is identical to the image. **Step 5** is the deliberate failure test. After a one-byte change, the working copy's digest no longer resembles the original at all. A byte-by-byte comparison then reports the first difference at character 100,001. The change was made at offset 100,000, and offsets count from zero while this comparison counts from one, so both numbers describe the same byte. The "line 1" part counts newline bytes, which carry no meaning in a disk image. **Step 6** adds an MD5 value and labels it as being for legacy compatibility only.

If your kit supplies exactly the same synthetic file, your SHA-256 digests should equal these values character for character. If your copy of the kit generates the file afresh, your values may differ. In that case, the check is whether *your* steps 2 to 4 equal *your* step 1, and whether *your* step 5 differs.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** This table turns the six steps of the original transcript into a checklist for lab setup. Each row asks one question about your workstation: does this part of the verification routine do its job? The table matters because a routine that has never been seen to fail cannot be trusted when it reports success.

**Components.** The table has four columns: *Step*, *Transcript result*, *What it confirms* and *Lab-setup check*. Its six rows follow the transcript in order. Rows 1 to 3, shaded blue, cover the reference digest, the stream digest and the stored image with its size of 16777216 bytes. Row 4, shaded green, covers the verified working copy. Row 5, shaded red, is the deliberate one-byte change. Row 6, shaded slate, is the MD5 line. The digests are shortened to their first eight characters in the table only to save space. In real work you compare all 64.

**Relationships.** The rows depend on each other. Rows 2, 3 and 4 only mean something because row 1 recorded a reference value first. Row 5 only means something because row 4 showed the copy matched before the change. The *What it confirms* column says what each result shows, and the *Lab-setup check* column says what that result tells you about the workstation's own routine.

**Execution flow.** Read the rows from top to bottom. Record the reference, confirm the data in transit, confirm the stored file, confirm the copy, show that a change is caught, and then note the legacy digest.

**Decision logic.** Rows 1 to 4 expect equality, and any mismatch stops the lab. Row 5 expects inequality, so a match there would be the failure. It would mean either that the change was never made or that the routine is hashing the wrong file. Row 6 never decides anything on its own.

**Technical interpretation.** A cryptographic digest is designed so that any change to the input, even a single byte, produces an output with no visible relationship to the original. Row 5's `16d816db…` against row 4's `e3a74e55…` shows this. The byte comparison in row 5 adds the location of the difference, which a digest can never tell you.

**Practical example.** During the Nilgiri Freight setup, the senior examiner asked A. Rao to show row 5 working on the trainee's own scratch files. Rao changed one character, ran the manifest check, saw exactly one failure, and wrote the result in the inventory's known-answer column.

**Security implications.** Row 6 reflects a real limitation. MD5 is no longer collision-resistant, so it should not be the only integrity record for new work. It can still help when an older system or document only lists MD5 values. Row 3's size line is a quick sanity check, but a matching size proves nothing about content on its own.

**Key learning.** Trust a verification routine only after you have seen it report equality on identical data and inequality on changed data. Record both results.

## Case exercises

Work through each case in your notes before reading the suggested resolution. Each one reflects a mistake that labs make.

**Case 1: the uppercase digest.** The supplier's receipt shows the SHA-256 value for `suspect.dev` in uppercase, copied from a PowerShell window. A. Rao's Linux tool prints lowercase. A colleague wants to record a mismatch. *Resolution:* hexadecimal is not case-sensitive. Compare all 64 characters while ignoring case. If they agree, the digests match. Note in the log which tool produced each value.

**Case 2: an MD5-only receipt.** A second training item arrives with a receipt that lists only an MD5 value, `9330805010f0e235779d131b854f2295`, for `evidence.dd`. *Resolution:* compute the MD5 to compare with the receipt, because that is the only stated value, and also compute and record SHA-256 at intake. From then on, use the SHA-256 value as the main reference in the lab. Record in the log that the supplier only gave MD5.

**Case 3: a changed working copy.** Partway through an exercise, a re-check of `working.dd` gives `16d816db…` instead of `e3a74e55…`. *Resolution:* the original in `01_originals` is unaffected, and its digest should still match the receipt. Stop using the changed copy. Record what was observed and when. Make a new working copy from the original and verify it before continuing. If possible, find out what changed the copy, such as a tool that writes to files it opens. Then record that tool's behaviour in the inventory.

**Case 4: "16 MB" on the receipt.** A receipt describes an item as "16 MB", but the stored file is 16,777,216 bytes. *Resolution:* 16,777,216 bytes is 16 MiB in binary units. In decimal units, 16 MB would be 16,000,000 bytes. The data has not changed. The description is imprecise. Add an amendment to the receipt that gives the exact byte count, and keep the original wording.

**Case 5: a tool upgrade mid-case.** A tool offers an update during an exercise. *Resolution:* do not upgrade in the middle of an examination. If an upgrade is needed, finish or pause the examination, perform the upgrade in a recorded staging step, update the inventory, repeat the known-answer check, take a new snapshot, and note in the case log which results came from which version.

**Case 6: the synced folder.** A reviewer finds that the host's cloud-storage client is syncing the folder that contains `01_originals`. *Resolution:* this is a confidentiality problem and an uncontrolled change path. Stop the sync, record the finding, re-verify every original against its receipt digest, and move the evidence store to storage that only the analysis VM uses. For synthetic data the consequence is a lesson. For real personal data, it could be a reportable data-protection incident.

## Common mistakes and misconceptions

- **"A matching digest proves the tool is validated."** A matching digest shows that two pieces of data are identical. It says nothing about whether the tool parses file systems or artefacts correctly. Formal testing, such as the NIST CFTT programme, is a separate activity tied to specific versions and test cases.
- **"The read-only attribute protects the evidence."** A read-only flag guards against accidents. Any user or process with sufficient rights can remove it. Digests detect change. Permissions only reduce the chance of it.
- **"A VM snapshot is a backup of the evidence."** A snapshot preserves the analysis environment. Evidence integrity rests on originals, receipts and digests.
- **"Comparing the first and last few characters is enough."** It is quicker, but it is not a comparison. Compare the whole value, ideally by machine.
- **"An MD5 match means nothing."** For identifying a file against an older record, an MD5 match is still informative. The weakness is that someone can deliberately construct different data with the same MD5, so MD5 should not be the only integrity record for new work.
- **Editing receipts or notes in place.** Corrections are added as dated amendments, and the original entry stays readable.
- **Opening originals "just to look".** Some tools write metadata or lock files. Open working copies only.

## Security implications, detection and defence

A forensic workstation holds data that is sensitive by definition, so it attracts the same threats as any sensitive system. Later modules introduce suspicious executables and real-world artefact types, even in synthetic form. That is the main reason for isolation: a file under examination must not be able to reach a network or the host. Disabling shared folders, clipboard sharing and the guest network removes the most common paths. Running each session from a known snapshot means that anything an exercise leaves behind is discarded.

Confidentiality matters as much as integrity. In real casework, evidence often contains personal data, and in India the Digital Personal Data Protection Act 2023 is relevant to how that data is handled. This course's lab uses only synthetic data so that you can practise without that exposure, which is why you must not bring in images of your own or other people's devices. Encrypting the evidence store at rest and restricting the analysis VM to its examiner reduce the impact of a lost disk or a shared computer.

The lab can also detect some of its own problems. Rechecking the manifests of `01_originals` at the start and end of each session reveals unexpected changes. Comparing the tool inventory with what is actually installed reveals unrecorded software. Gaps in the case log's time sequence reveal missing records. Lesson 4 covers the legal handling of electronic evidence in India. A well-kept lab produces the records that legal processes rely on, but no lab setup can guarantee that a court will accept any particular item.

## Best practices

- Use one dedicated, isolated analysis VM with a recorded clean-baseline snapshot.
- Install tools only from official projects, verify installer digests and record exact versions.
- Never let analysis tools open `01_originals`.
- Record SHA-256 as the main digest, and add MD5 only where an older record requires it.
- Show that your routine detects a change before you rely on it to detect no change.

## Key takeaways

- A forensic lab is defined by isolation, organisation, an inventory and checks, not by its software.
- Evidence moves one way, from receipt to original to verified copy to tools to exports, with every move verified or recorded.
- A digest proves that two pieces of data are identical. It does not prove that a tool is correct or that the right source was hashed.
- The original transcript shows both outcomes your routine must produce: equality in steps 1 to 4 and a detected change in step 5.
- SHA-256 is the main reference. MD5 is kept only for compatibility with older records.
- Lab records support later legal processes, but they are never a guarantee of admissibility.
