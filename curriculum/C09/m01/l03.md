## Introduction and conceptual foundation

Every piece of digital evidence has a lifetime. A value in a CPU register lasts nanoseconds. A row in the kernel's process table lasts as long as the process runs. A file on disk survives reboots but can be overwritten next week. A backup tape in a vault may last a decade. When an examiner arrives at a running system, all of these exist at once, and every minute that passes, and every action the examiner takes, shortens the life of the most fragile of them. **Order of volatility** is the principle that turns this observation into a rule of practice: collect the evidence that will disappear soonest first, and the evidence that will last longest last.

The principle sounds obvious, but it is routinely broken under pressure. An administrator sees odd outbound traffic and reboots the server "to clear it". A helpdesk technician runs an anti-virus scan that rewrites access times across the disk. An investigator pulls a laptop's power cable and only later learns that its disk was encrypted and the key existed only in memory. Each of these people meant well, and each destroyed evidence that no later tool can bring back. The order of volatility exists so that the first person to touch a system knows, in advance, what they are about to lose.

Lesson 1 set out the principles of forensic work: integrity, documentation, repeatability and minimal intrusion. Lesson 2 catalogued the kinds of evidence an investigation can draw on, from endpoint disks to cloud audit logs. This lesson puts those evidence types in time order. It explains the order of volatility as written in RFC 3227, why each layer sits where it does, and what the RFC tells you to avoid. It then examines the decision every responder faces at a running machine: collect live, accepting that you change the system, or power it down and collect "dead", accepting that you lose what was in memory. Module 2 teaches the acquisition techniques themselves (imaging, write blockers, hashing and the live versus dead acquisition procedures) and Module 6 teaches memory analysis; here the aim is the reasoning that decides what to collect, in what order, and at what cost.

> [!NOTE]
> RFC 3227 is a Best Current Practice document from 2002. Its examples (tar, xcopy, "archival media") show its age, but its principles have not changed and it remains the reference that forensic standards, training courses and court-facing reports cite for collection order. Read it as a statement of principles, not as a list of current tools.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Volatility | How quickly a piece of data changes or disappears on its own, or as a side effect of normal system activity, once collection begins. |
| Order of volatility | The sequence in which evidence sources are collected, from most volatile to least, so that the fragile data is captured before it is lost. |
| Volatile data | Data that exists only while a system is powered and running: CPU state, memory, process and network tables, kernel state. |
| Non-volatile data | Data that survives power loss: disk contents, firmware settings, remote logs, backups and archives. |
| Live collection | Collecting evidence from a system while it is running, using tools that execute on or interact with the system. |
| Dead collection | Collecting evidence from a system after it has been powered off, typically by imaging its storage through a write blocker. Also called post-mortem or static acquisition. |
| Footprint | The changes an examiner's own actions make to the system under examination: processes started, memory overwritten, files and timestamps touched. |
| Live response | A minimal, scripted live collection of volatile state (processes, connections, users, clock) run when full memory capture is not possible or as a complement to it. |
| Clock offset | The difference between a system's clock and an accurate reference (normally UTC), recorded so that times from different sources can be aligned. |

## What makes evidence volatile

Volatility is not a property of the data itself but of the place it is stored and of how the system uses that place. Three forces shorten the life of evidence.

**Loss of power.** Main memory (DRAM), CPU registers and caches hold data only while powered. Switching a computer off erases them for practical purposes. Everything the operating system keeps in memory goes with them: the list of running processes, open network connections, the ARP cache, logged-in sessions, the clipboard, decrypted copies of encrypted files and, critically, encryption keys for any volume that is currently unlocked.

**Normal churn.** Even on a system nobody touches, data is constantly replaced. The kernel recycles process identifiers and memory pages, connection tables age out idle entries, ARP entries expire after minutes, temporary directories are cleaned, logs rotate and old log files are deleted, and file systems reuse free clusters. Churn means that volatile and semi-volatile evidence decays even if the power stays on.

**Interaction.** Anything that runs on the system, including the examiner's tools, competes for memory, starts processes, opens files and may update timestamps. A careless collection can overwrite exactly the freed memory pages or unallocated disk space that held the evidence. Interaction also includes the attacker: an intruder who notices a responder may delete files, kill processes or trigger a clean-up routine.

The order of volatility ranks evidence sources by how strongly these forces act on them. It is a ranking of *expected lifetime*, which is why it is a guide and not an absolute law: on a particular system, a log file that rotates every hour may be more urgent than a process that will run for a week.

## The RFC 3227 order of volatility

RFC 3227, "Guidelines for Evidence Collection and Archiving" (D. Brezinski and T. Killalea, February 2002, also published as BCP 55), sets out in its section 2.1 an example order of volatility for a typical system. From most volatile to least, it lists:

1. Registers, cache.
2. Routing table, ARP cache, process table, kernel statistics, memory.
3. Temporary file systems.
4. Disk.
5. Remote logging and monitoring data that is relevant to the system in question.
6. Physical configuration, network topology.
7. Archival media.

Each layer is worth understanding, because the reason a layer sits where it does tells you how to handle it.

**Registers and cache** are the CPU's working state. They change billions of times a second, cannot be read meaningfully by ordinary software from outside the processor's current context, and are lost the moment execution moves on. In practice no responder collects them directly; their place at the top of the list is a reminder that some evidence is gone before anyone arrives. What survives of them, if anything, is whatever the system has spilled into memory.

**Routing table, ARP cache, process table, kernel statistics and memory** form the layer that matters most in modern practice. The routing table and ARP cache record which networks and neighbouring hosts the system has been talking to, and ARP entries expire within minutes. The process table lists what is running, with parent processes, command lines and open handles. Kernel statistics include counters and state such as loaded modules and network socket tables. Memory as a whole holds all of that plus injected code, decrypted data, credentials in use, command history held by shells, and keys for unlocked encrypted volumes. Much of what an attacker does in memory leaves no trace on disk, so this layer often holds the only evidence of how an intrusion operates.

**Temporary file systems** sit between memory and disk. On Linux, `/tmp` is often a `tmpfs` mount that lives in memory and disappears at reboot; `/run` and `/dev/shm` are similar. On Windows, temporary folders are on disk but are emptied by clean-up tasks and installers. Attackers like these locations because they are writable by ordinary users and are expected to be messy. Their contents are lost on reboot (memory-backed) or on the next clean-up (disk-backed).

**Disk** is the first layer that reliably survives power loss. It holds the file system, deleted but unoverwritten data, swap or page files, hibernation files, logs, registry hives and application databases. Disk evidence is far more durable than memory, but not permanent: the system keeps writing, free space is reused, and logs rotate. Module 3 covers what survives on each file system and why.

**Remote logging and monitoring data** is evidence about the system that is stored somewhere else: a SIEM, a central syslog server, an EDR console, firewall and proxy logs, cloud audit logs. It is less volatile than local disk because the attacker on the host usually cannot reach it, and it is typically retained for a defined period. That period is the threat: SIEM retention, cloud audit log default retention and log-server rotation all delete it on a schedule. A responder who forgets to place a preservation hold on remote logs can lose them weeks into an investigation, which is why this layer appears in every collection plan even though it is "low" volatility.

**Physical configuration and network topology** describe how the system is connected: cabling, switch ports, VLANs, which wireless network it joined, attached devices. These change only when someone changes them, but they matter for interpreting everything else, and they are easy to disturb by moving equipment. Photographs and diagrams made at the scene preserve them.

**Archival media** (backups, tapes, offline copies, snapshot archives) are the least volatile. They are designed to last, and they often hold earlier states of the system that help establish when a change happened. They are collected last because they are in no danger.

> [!IMPORTANT]
> The RFC calls its list an *example* for a typical system. Apply the principle, not the list blindly: identify the evidence that matters for your questions, estimate how long each source will survive on *this* system, and collect in order of that estimate. A one-hour log rotation or a seven-day cloud log retention can move a "low volatility" source to the front of the queue.

**Purpose.** The diagram represents the RFC 3227 example order of volatility as a stack of seven layers. It matters because it is the reasoning behind every collection plan in this course: the first item you collect is chosen from the top of this stack, and every action you take at a running system is judged by which layers it threatens.

**Components.** Reading from the top, the layers are: **Registers, cache** (sub-labelled "nanoseconds; rarely collectable"), **Routing, ARP, process table, kernel stats, memory** ("lost at power-off; live collection"), **Temporary file systems** ("tmpfs, /tmp, /dev/shm"), **Disk** ("survives reboot; image it"), **Remote logging and monitoring** ("SIEM, syslog, EDR, cloud audit"), **Physical configuration, topology** ("cabling, ports, VLANs") and **Archival media** ("backups, tapes, snapshots"). Colour carries meaning: the top two layers are red because they are lost first, temporary file systems are orange, disk is blue as the normal working source of evidence, remote logs violet, physical configuration slate, and archival media green because it is the safest.

**Relationships.** Each layer is less volatile than the one above it. The stack is not a dependency diagram; a lower layer does not depend on a higher one. It is an ordering of expected lifetime under the three forces described above: power loss, churn and interaction.

**Execution flow.** Collection proceeds from top to bottom. In practice the responder skips registers and cache, captures memory and live state first, then temporary file systems (which a memory capture or live response often covers), then images the disk, then exports and places holds on remote logs, records physical configuration, and finally requests archives.

**Decision logic.** The ordering is an example, not a fixed algorithm. If a remote log source has a short retention, it may be preserved early, often in parallel by a colleague, because preserving it does not touch the system under examination at all. Parallel work by different people is how real teams follow the order without leaving lower layers to expire.

**Technical interpretation.** The dividing line that matters most falls between the second and fourth layers. Everything above **Disk** exists only while the system runs; **Disk** and below survive power-off. That line is exactly where the live versus dead collection decision sits, which the second figure in this lesson examines.

**Practical example.** At Tamarind Logistics, web01 shows unexplained outbound traffic. The responder captures memory and runs a live-response script (layer 2, which also reads layer 3 state), images the virtual disk (layer 4), asks the SIEM administrator to export and hold web01's authentication and proxy logs (layer 5), photographs and records the virtual network configuration (layer 6), and requests the last two nightly backups (layer 7).

**Security implications.** Most evidence destruction in real incidents happens at the top two layers: reboots, "clean-up" by administrators and anti-virus remediation. Attackers know this and keep tools in memory and temporary locations. Organisations reduce the risk by writing the order into their incident playbooks and by forwarding logs off the host so that layer 5 exists at all.

**Key learning.** Collect from the top of the stack down, adjusted for the real lifetime of each source on the system in front of you. The line between memory and disk is where the most evidence is lost and where the most important decision is made.


## What RFC 3227 tells you to avoid

The RFC pairs its ordering with a short list of things to avoid, and each one maps to a common real-world mistake.

**Do not shut down until collection is complete.** Powering off ends the top layers at once, and many systems run shutdown scripts that delete temporary files or wipe caches. An attacker can also install a shutdown hook that destroys their own tools. A shutdown is sometimes the right decision, but it should be a decision, made after the volatile layers have been collected or deliberately given up, not a reflex.

**Do not trust the programs on the system.** On a compromised host, the attacker may have replaced or hooked the very utilities a responder would use to list processes or connections, so that they hide the attacker's activity. Responders therefore run trusted tools from protected, write-protected media or a validated live-response kit, and they prefer collection methods that do not depend on the suspect operating system's own reports, such as full memory capture or a hypervisor-level snapshot.

**Do not run programs that change the access times of every file.** The RFC's example is an archiving tool that walks the whole disk. Any broad sweep that reads every file, including some anti-virus scans and casual searches, can rewrite access timestamps across the system and erase a useful part of the timeline. Disk evidence is best collected by imaging, which reads the device without opening each file through the file system.

**Beware of disconnecting the network as a reflex.** Removing external avenues for change is sensible, but the RFC warns that simply disconnecting or filtering a system may trigger a "deadman switch" that destroys evidence when the attacker's connection drops. Isolation should be deliberate, recorded and, where possible, done at the switch or firewall after volatile collection.

The RFC's collection procedure adds two habits that are easy to forget: record the extent of the system's clock drift, and document each step as you take it. Both connect directly to Lessons 5 and 6.

## Recording the clock

Every timestamp collected from a system is expressed in that system's idea of the time, and that idea may be wrong. Before or during collection, the responder records the system clock alongside an accurate reference, normally UTC from a trusted source, and notes the offset. If `web01` reports 06:31:12 when the reference says 06:29:40, every local timestamp from that machine runs 92 seconds fast, and the timeline in the report must say whether times have been corrected. The offset is itself evidence: a clock that has been changed recently may explain events that otherwise look impossible, and it must be recorded before a reboot or a time-synchronisation service quietly corrects it.

## Live or dead: the decision at a running machine

The most important decision in this lesson sits on the line between memory and disk in Figure 1. A responder facing a running machine has a small number of options, and each keeps some layers and gives up others. **Leaving the system running and isolating it** keeps memory and live state but lets the system keep changing, and the attacker may notice. A **graceful shutdown** loses memory and lets the operating system write to disk on its way down. A **hard power-off** loses memory but freezes the disk at its last write, at the risk of losing data still in caches. **Hibernation** writes memory into a file on disk, which preserves some of it but overwrites part of the disk and, on encrypted volumes, leaves it behind the encryption. **Capturing memory first, then deciding** keeps the most, at the cost of a small, recorded footprint from the capture tool.

Encryption changes the calculation more than any other factor. A laptop with full-disk encryption that is running and unlocked holds its volume key in memory. Once it is powered off, the disk image is ciphertext unless a recovery key is available from the organisation's key escrow. Checking for encryption, and for a recovery key, before anyone touches the power is one of the first things a responder records.

Virtual machines and cloud workloads change the options again. A hypervisor can often snapshot a running guest, including its memory, without running any tool inside it. That avoids the "do not trust the programs on the system" problem, because the evidence is collected from outside the suspect operating system. Cloud provider logs live in the remote-logging layer, and some platforms keep their default event history for only about 90 days unless it is exported. For those sources the urgent action is a preservation export, not anything on the instance itself.

There are five rows: keep running and isolate, capture memory then decide, graceful shutdown, hard power-off and hibernate. The capture-first row is green because it keeps the most, the shutdown rows are red because they give up memory, and the other rows are orange because their value depends on the situation.

**Relationships.** Reading down any column shows the trade-off for one layer. Memory is kept in full only in the first two rows; hibernation keeps part of it, inside a file on the disk. The encryption column follows the memory column, because an unlocked volume's key lives in memory. The disk column shows that no option leaves the disk entirely untouched while the machine is running.

**Execution flow.** A responder works through the table in order: is anything in memory needed for the questions in this case? Is there unlocked encryption without a recovery key? Can the business tolerate the machine running a little longer? If memory matters, capture it first. Then choose how to stop the machine, or whether to leave it running in isolation.

**Decision logic.** If the disk is encrypted and no recovery key exists, shutting down before capture can make the whole disk unreadable, so capture-first is strongly favoured. If the system is actively causing harm, containment can come first, and the lost layers are recorded as a known consequence.

**Technical interpretation.** A hard power-off is not "better" than a graceful shutdown or the reverse. It trades the risk of shutdown scripts and log writes against the risk of losing cached writes, and the right choice depends on the system and the threat.

**Practical example.** A Tamarind finance laptop is found running and unlocked, with full-disk encryption and no recovery key in escrow. The responder records the screen and clock, captures memory to an external drive, then keeps the laptop running and isolated until the IT team confirms that a recovery key can be generated.

**Security implications.** Attackers who expect responders to pull the plug keep their tools only in memory. Playbooks that default to memory capture for suspected intrusions remove that advantage.

**Key learning.** Every option keeps some layers and loses others. Choose by the questions in the case, the encryption state and the harm, and write down what was given up.

## Worked example: a collection plan, on paper

This is an offline planning exercise for the fictional `web01` virtual server. No systems are touched. The questions are whether the customer list left the organisation and how the copy was created.

1. Record the situation: the time against a UTC reference, the system clock and its offset, the people present and the authority for the work.
2. Ask the virtualisation team for a snapshot of the running guest that includes memory. This captures layers 2 and 3 from outside the guest. If no snapshot is possible, run a validated live-response kit from protected media, and record its expected footprint.
3. In parallel, ask the SIEM administrator to export and preserve web01's authentication, proxy and flow records for the past 30 days, because the central log retention is 45 days and the investigation may run for weeks.
4. Image the virtual disk from the snapshot or after shutdown, and hash it as Module 2 describes.
5. Record the virtual network configuration and firewall rules that applied to web01.
6. Request the last two nightly backups, because they show whether the stray file existed before the suspicious night.

The plan follows the RFC order, but steps 2 and 3 happen at once because they are done by different people and step 3 does not touch the server. Each step names its reason, which is what a reviewer will ask for.

## Common mistakes and misconceptions

- **"Pull the plug to stop the attack."** This destroys memory and, on encrypted systems, may lock the disk. Isolate first where the harm allows.
- **"Remote logs are safe, so they can wait."** Retention deletes them on a schedule. Place holds early.
- **"The order is fixed."** RFC 3227 gives an example. Real lifetimes on the system in front of you decide the order.
- **"The system's own tools are fine for a quick look."** On a compromised host they may lie. Use trusted tools or collection from outside the guest.
- **"A quick anti-virus scan will tell us what happened."** A full scan touches every file and can rewrite access times across the disk.
- **"Time is time."** Without a recorded offset, timestamps from different systems cannot be aligned with confidence.

## Security implications, detection and defence

Attackers adapt to responders' habits. Memory-only tools, staging in temporary directories, log clearing on the host and shutdown hooks all exploit the top of the volatility stack. Defenders answer by moving evidence down the stack before an incident happens: forwarding logs to central storage, enabling endpoint telemetry that records process starts and connections as they happen, keeping hypervisor snapshot procedures ready, and escrowing encryption recovery keys. When the evidence already exists in layer 5, losing layer 2 is far less damaging.

## Best practices

- Write the order of volatility into the incident playbook, adjusted for your own systems' log rotation and retention.
- Check for encryption and recovery keys before any decision about power.
- Capture memory before shutting down whenever the case questions may depend on it.
- Run only trusted tools from protected media, or collect from outside the guest.
- Record the clock offset against UTC before the system is rebooted or resynchronised.
- Place preservation holds on remote logs on day one, assigned to a named person.
- Record every action that changes the system, and what was knowingly given up.

## Key takeaways

- Volatility is expected lifetime under power loss, churn and interaction, not a fixed property of data.
- RFC 3227 orders evidence from registers and memory down to archival media. Treat it as an example and adjust for the real system.
- Avoid shutting down before collection, trusting the suspect system's programs, running whole-disk sweeps and disconnecting reflexively.
- Record the system clock offset against UTC.
- Every way of handling a running machine keeps some layers and loses others. Encryption makes memory capture especially valuable.
- Remote logs are low in volatility but expire on retention schedules, so preserve them early and in parallel.
