## Introduction and conceptual foundation

Plugging a storage device into a computer looks passive, but it is not. As soon as a modern operating system sees a new disk, it may read the partition table, try to mount every volume it recognises, update file-system metadata, replay an unfinished journal, create housekeeping folders, start an indexing service or hand the volume to an antivirus scanner. Each of those actions can send write commands to the device. On an ordinary disk nobody notices. On an evidence disk, every one of them is a change made by the examiner rather than by the people whose actions are under investigation, and usually nobody records it.

A write blocker is the control that stops this. It sits between the examiner's computer (the host) and the evidence storage device, lets read operations through and prevents operations that would modify the device. The previous lesson separated file exports from volume and device captures. A device capture is only as trustworthy as the protection the source had while it was attached. The next lesson, on hashing, covers how digests show that a copy matches what was read. This lesson sits between the two. It explains what write blocking protects, how it works and how a laboratory earns confidence in a particular blocker. Just as importantly, it covers what a write blocker does not protect.

Three ideas run through the lesson. First, a write blocker controls commands crossing an interface, not files or intentions. Second, protection has to be in place before the first connection, because no later check can recover a state that was never recorded. Third, you earn confidence in a blocker by testing a specific unit, firmware and configuration and recording the result. A brand name, or a statement that a product is "forensically sound", is not enough.

> [!IMPORTANT]
> This lesson is about protecting evidence you are authorised to handle. It uses a fictional organisation, fictional receipts and one real file-based transcript from the course kit. It does not teach collection from live systems, and nothing here is a legal guarantee that evidence will be admitted. The legal handling requirements are covered in Module 1, Lesson 4.

## Key terminology

| Term | Meaning in this lesson |
| --- | --- |
| Host | The examiner's workstation that issues commands to storage. |
| Protected (evidence) device | The storage device whose contents must not change. |
| Write blocker | A hardware unit or host software that forwards read-type operations to the protected device and stops operations that would modify it. |
| Hardware write blocker | A separate physical unit, often called a forensic bridge, with a host-side connection and one or more device-side ports. Its own firmware enforces blocking, independent of the host operating system. |
| Software write blocker | Code running on the host, such as a driver or operating-system policy, that intercepts modifying operations before they reach the device. |
| Modifying operation | Any command that changes stored data or device state. This covers writes, and also erase, trim or deallocate, firmware download and some configuration changes. |
| Pass-through information | Data the device reports about itself, such as model, serial number and reported capacity, which the blocker should relay unaltered. |
| Reference (test) media | A sacrificial device with known contents and a recorded hash, used only to check that a blocker behaves as expected. |
| Pre-use check | The laboratory's own short test of a blocker before casework, recorded against the unit's serial number and firmware. |
| Mode | Some blockers can be switched between read-only and read-write. The mode at the moment of connection is what matters. |

## Why protection must come before the first connection

A hash value is a snapshot. It describes exactly the bytes that were read at the moment they were read. Suppose the operating system wrote to the device in the thirty seconds between connection and the first hash. The first hash then faithfully records the altered state, and every later hash will agree with it. The matching hashes show a consistent copy of changed evidence, and nothing in the digests reveals that the change happened.

This is the core reason write blocking is a preparation step rather than a repair step. If the blocker is attached after the device has already been connected directly, the examiner can no longer show what the device held before it was attached. The same applies if the blocker is switched from read-write to read-only once the device is visible to the host. The honest response is to record exactly what happened. Later hashes cannot cover the gap.

Consider a short fictional case. An analyst at Kestrel Freight Pvt Ltd (fictional) receives a laptop drive in a sealed bag. Wanting to "just check it is the right disk", they connect it to their workstation through a plain USB adapter, see the volume label and disconnect it. Only then do they attach it through the laboratory's bridge for imaging. The image hashes verify perfectly. The problem is not the image but the unrecorded minute of direct connection: the analyst cannot say whether the workstation mounted the volume and updated anything. The defensible course is to declare the direct connection in the notes, keep the verified image and let the reviewer judge its effect. Leaving it out is not defensible.

> [!WARNING]
> "I only looked at it" is not a protected state. Identify a device from its labels, the custody record and the blocker's pass-through information, not by connecting it directly.

## How a write blocker works

### Commands, not files

Storage devices do not receive "open file" or "delete document" requests. They receive commands over an interface: ATA commands over SATA, SCSI commands over SAS and over most USB mass-storage devices, and NVMe commands over PCIe. A file-system driver on the host turns "save this document" into a series of block writes, and the device sees only the writes. A write blocker therefore works at the same level as the device. It examines each command crossing the interface and decides whether to forward it.

Read commands are forwarded and their data returned. Identification and status queries are forwarded so the host can see what is attached. Commands that change stored data or device state are stopped, and that category is wider than "write". Trim or deallocate commands tell a solid-state drive that blocks are no longer in use. Erase commands wipe media. A firmware download replaces the drive's own code, and some configuration commands change the capacity the device reports. All of them can change what a later read returns, so a blocker must treat them as modifying.

Underneath this sits a design question. A blocker can forward only the commands it recognises as safe and refuse everything else. Or it can refuse only the commands it recognises as dangerous and forward everything else. The first design fails closed: an unfamiliar command is stopped. The second fails open: an unfamiliar command reaches the evidence. Examiners rarely see a vendor's internal logic, which is one reason why independent testing and the laboratory's own checks matter.

### Hardware write blockers

A hardware blocker is a separate unit. The evidence drive connects to a device-side port, the unit connects to the host, and the blocking logic runs in the unit's firmware. Because the decision is made outside the host, it does not depend on the host's operating system, drivers or configuration, and it is in place before the host sees the device at all. Many units also power the drive, so the examiner controls when it is powered on, and many show the current mode on an indicator.

Hardware blockers have their own limits. Each one supports specific interfaces, so an NVMe drive needs a unit, or a tested combination of unit and adapter, that handles NVMe. Firmware can change behaviour, so the firmware version is part of the unit's identity. Some units have a read-write mode because laboratories sometimes need to prepare destination media. That convenience becomes a risk if the mode is wrong when the evidence is connected.

### Software write blockers

A software blocker runs on the host as a driver, filter or operating-system policy. It is useful where a hardware unit cannot attach, and NIST SP 800-86 describes both hardware and software write-blockers as ways to keep media from being written to during collection. The trade-off is dependence on the host. Protection exists only when the software is installed, enabled and loaded before the device appears. It covers only the paths the software intercepts, and only on the operating-system version and configuration that were checked. An update to the host can change any of these. A software blocker therefore needs the same pre-use checks as a hardware unit, recorded against the host build as well as the software version.

### Things that look like write blocking but are not

- **Read-only mounting.** Mounting a volume read-only is a file-system instruction, not a device control. Some file systems may still replay a journal on mount, and any other program on the host can still open the raw device.
- **Media lock switches.** The sliding tab on a full-size SD card is a mechanical signal read by the card slot. The reader or host is expected to honour it, but the card itself does not enforce it.
- **Opening files read-only.** An application's read-only flag governs that application only, not the operating system's mounting and housekeeping.
- **Policy alone.** A written rule saying "do not write to evidence" is necessary, but it does not stop an automatic process.

**Relationships and arrows.** Solid arrows are commands or forwarded commands. Dashed arrows are replies. Look at which lanes each arrow connects. Read and identification traffic crosses the full width from host to drive and back. The modifying command ends at the blocker, and the only reply to it comes from the blocker, not the drive.

**Execution flow.** Time runs downwards. First, the host sends **Read sectors (LBA range)**. The blocker forwards it, the drive answers with **Sector data**, and the blocker returns **Same data, unaltered**. Second, the host sends **Write / trim / erase command**. The blocker does not forward it and replies **Refused: form varies by product**. Third, the host sends **Identify / capacity query**. It is forwarded, the drive answers **Model, serial, reported capacity**, and the blocker relays those values unchanged.

**Decision logic.** The single branch is inside the green lane: is this command on the blocker's list of safe operations? If it is, it is forwarded. If it is not, it goes no further. The diagram does not show the alternative design that blocks only known-bad commands, because that design would let an unfamiliar command through to the dark lane.

**Technical interpretation.** The refusal label is deliberately vague. Products differ in how a stopped command appears to the host, and some host logs can even show a write that looks completed. For this reason, the result of a pre-use check is the reference media's hash, not the host's log. The third exchange matters as much as the first. If the blocker altered identity or capacity information, the receipt would describe the wrong device.

**Practical example.** At Kestrel Freight (fictional), the analyst attaches a seized SATA drive through bridge WB-07. The host immediately attempts a mount and a metadata update. Those writes stop in the green lane. The acquisition tool then issues reads, and the drive's model and serial appear on screen for the receipt.

**Security implications.** The blocker removes the host as a source of change. It does nothing about change from other sources, which is the subject of the next figure. A unit that forwarded a single unlisted command would be a silent failure, so it must be tested and its firmware recorded.

**Key learning.** A write blocker decides per command at the interface. Reads and identity pass through unaltered, and modifying commands never reach the evidence drive.

## What a write blocker does not control

A blocker governs one thing: commands sent from the host to the protected device through that blocker. Many of the acquisition problems that reach review fall outside that boundary. Naming them stops an examiner from writing "write-blocked" as though it settled every question.

- **The drive's own internal activity.** A solid-state drive's controller manages its memory internally, and once powered it may carry out background maintenance that no host command started. A blocker can stop the host from sending trim commands, but it cannot switch off the controller. This is a reason to record the power-on time and acquire promptly. It is not a reason to distrust every SSD image.
- **Failing media.** A degrading drive can return different data for the same sector on different reads. If a source hash changes between two reads through a working blocker, the cause may be the drive rather than a write.
- **Coverage.** A blocker relays what the device reports, but it does not make the capture complete. If the capacity the drive reports is smaller than its specification suggests, record the difference and escalate it under the laboratory's procedure. The blocker does not resolve it.
- **Encryption.** Blocking preserves encrypted data exactly as stored. Whether the content can later be read depends on lawful access to keys, which is a separate question.
- **The destination.** The blocker protects the source and does nothing for the destination drive. A wrong-target mistake while preparing or writing the image is prevented only by labelling, procedure and a check of device identity before any write.
- **Changes before attachment.** Anything that happened before the blocker was in the path, including a direct connection or a read-write mode at connection, is outside what the blocker can vouch for.
- **Sources with no blocking point.** Running memory, a live server that must stay up, a network share and a cloud account cannot be placed behind a blocker. In those acquisitions the examiner's actions do touch the system. They are defended by documenting each action and its expected footprint, which Lesson 5 covers in detail.

**Relationships.** The two columns describe the same acquisition from different sides. Every item on the left is a host action stopped or relayed at the interface. Every item on the right either starts somewhere other than the host (the SSD controller, failing media), happens somewhere other than the source (the destination drive), happens at a time other than the protected window (changes before the blocker was attached), or has no interface to block (live memory, network shares, cloud).

**Reading order.** Read the left column first as the positive claim. **Host write commands to the source**, **Trim / deallocate and erase commands**, **Firmware download and config changes** and **OS mounting and housekeeping writes** are all stopped. **Relaying identity and read data intact** is the pass-through duty. Then read the right column as the list of follow-up questions a reviewer will ask.

**Decision logic.** For each concern raised in review, ask which column it belongs to. If it is on the left, the evidence is the blocker's identity, firmware, mode and pre-use check. If it is on the right, the evidence lies elsewhere: power-on times, repeated-read results, capacity comparisons, destination labelling, the custody timeline or a live-action log.

**Technical interpretation.** **SSD controller background maintenance** sits on the right because the drive can act on its own once powered. **Unstable reads from failing media** sits there because the source itself can be inconsistent. **Capacity not reported by the device** is there because the blocker relays reports and cannot add sectors the drive does not expose.

**Practical example.** A reviewer reads a Kestrel Freight receipt that says only "write-blocked: yes". Using this diagram, they ask four follow-up questions: when was the SSD powered on, does the reported capacity match the model's specification, how was the destination disk identified, and was there any connection before the bridge? The receipt answers none of them, so the reviewer returns it for completion.

**Security implications.** Overstating what a blocker achieves is a credibility risk rather than a technical one. A report that claims more than the blocker can show invites a challenge to every other claim in it.

**Key learning.** "Write-blocked" answers one question about the source. Record the answers to the other questions separately.

## Testing and trusting a particular blocker

The NIST Computer Forensics Tool Testing (CFTT) Program develops specifications and test methods for forensic tool functions, including write blocking, and publishes reports on individual tools tested against them. A CFTT report describes a particular product, version and configuration, and what was observed, including any anomalies. It is evidence about the item that was tested. It is not a certification of a brand, and it is not a promise about later firmware. Read the report for the exact item, and if your unit differs, say so in your notes.

Practitioner guidance takes the same line. SWGDE's *Best Practices for Computer Forensic Acquisition* treats write protection of the source and thorough documentation of the acquisition as core practice. It expects tools and equipment to be verified as working before use. Consult the current published version for its exact wording. Neither document turns a blocker into a guarantee.

When this course examines a blocker, it uses four questions. They are the course's own framing, not quotations from a standard:

1. Are modifying commands stopped before they reach the device?
2. Is the data returned by reads complete and unaltered?
3. Is identifying information, such as model, serial and capacity, relayed unchanged?
4. Are errors from the device reported to the host rather than hidden?

Independent test reports address questions like these in depth. The laboratory's own pre-use check addresses the first in a narrower way, on the day and with the unit it will actually use. The check uses reference media: a sacrificial device with known contents and a recorded hash, kept only for this purpose. The examiner attaches it through the blocker exactly as in casework and lets the host do whatever it normally does on connection. They then disconnect it, hash it again directly and compare. The record shows the unit's serial number, firmware, the interface used, the host, the date, both hash values and the result.

Interpret the result narrowly. A pass shows that, under those conditions, no change reached the reference media. It does not show that every possible command is blocked, which is why the check complements independent testing rather than replacing it. A fail takes the unit out of service, and the failure itself is recorded. Before concluding that the blocker leaked, rule out a degrading reference device by repeating the check with known-good media.

Inventory control supports all of this. Register each unit by serial number. Repeat the pre-use check when a unit comes back from repair, when its firmware is updated, when it has been on loan, or whenever its history is unclear. A unit that cannot be matched to a check record should not be the protection named on a receipt.

**Relationships and arrows.** The arrows run straight down, and each step depends on the one above it. There is no arrow back from acquisition to mode setting. That absence is the point of the procedure: once the evidence is connected, the mode at connection cannot be changed after the fact.

**Execution flow.** The first two steps involve no evidence at all. They establish that this unit, at this firmware, behaved as expected today. The mode is set third, before the evidence is attached fourth. Identity is recorded fifth, from the blocker's pass-through information, so the receipt describes the physical item. Acquisition and hashing follow, and the receipt closes the sequence.

**Decision logic.** There are two implicit stop points. If the register shows no usable check, or the reference media's hash changes, the procedure stops at the violet box and the unit is withdrawn. If the reported capacity in the fifth box does not match the model's specification, the examiner records it and escalates. The blocker does not decide this.

**Technical interpretation.** The order puts every step that touches the evidence after the green control. If any contact with the evidence happens before the mode is confirmed, that is a departure from the procedure, and the dark box exists to record such departures honestly.

**Practical example.** At Kestrel Freight (fictional), the register shows WB-07's last check on 2 October at firmware 2.3.0, but the unit now reports 2.4.1. The analyst runs the violet step against the reference drive, records a pass at 2.4.1 and continues. The receipt names both firmware versions.

**Security implications.** A procedure that leaves records at every step makes silent errors visible. A gap in the sequence, such as a missing pre-use record or a mode set after connection, is exactly what a reviewer will look for.

**Key learning.** Prove the blocker, set it, then connect. Every box produces a record, and a missing record is a gap.

## Worked example: what the kit transcript shows, and what it does not

The C09 acquisition kit includes a saved transcript of a small file-based acquisition, supplied here as `C09/rk_c09_acquire_lab_output.txt`. It is reproduced exactly below. No write blocker was involved: `suspect.dev` is a 16 MiB file standing in for a device. The transcript records only section headings and outputs, not the commands that produced them, so this lesson does not reconstruct the commands.

```text
== 1. hash source before acquisition
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

| Step | What it supports | What it does not support |
| --- | --- | --- |
| 1 | The SHA-256 of `suspect.dev` at the time it was hashed. | Anything about the source's state before that moment. |
| 2 and 3 | The image file holds the same bytes as the stream that was read. Its size is 16,777,216 bytes (16 MiB). | That no write reached the source, because no second source hash appears. |
| 4 | The working copy started identical to the image. | Anything about the source. |
| 5 | A one-byte change gives a completely different SHA-256. `cmp` counts bytes from 1, so offset 100000 is reported as char 100001. Its "line" count is not meaningful for binary data. | Where or why a change happened in a real case. |
| 6 | An MD5 value is available for systems that still need it. SHA-256 remains the verification value. | Any extra integrity beyond the SHA-256 values. |

Two lessons for write blocking follow from this transcript. First, the first hash anchors everything, so the protection has to precede it. Second, the transcript contains no post-acquisition hash of the source. In a device case, you would record that hash as a separate entry on the receipt, together with the blocker details, which a file transcript like this cannot supply.

## Case exercises

These cases are fictional. Discuss each one before reading the commentary.

**Case 1: the dock with new firmware.** A unit's register entry shows its last pre-use check at an older firmware. The unit now reports a newer version after a vendor update.
*Commentary:* The old check and any test report for the old firmware describe a different configuration. Run and record a new pre-use check before casework, and name both versions on the receipt.

**Case 2: the locked card.** An intake note says an SD card was "protected by its lock tab" while it was imaged in a desktop reader.
*Commentary:* The tab is a signal that the reader is expected to honour, not a control enforced by the card. The receipt names no tested protection. Record that, establish whether a tested blocker configuration was available for the reader, and do not describe the card as write-blocked.

**Case 3: the drifting SSD.** An SSD is imaged through a tested bridge. The source hash taken after imaging differs from the one taken before, but the image verifies against its stream hash.
*Commentary:* Do not conclude straight away that the blocker failed or that someone tampered with the drive. Record both values and the power-on period. Consider drive-internal activity, and test the unit again on reference media. The image remains a verified copy of what was read during acquisition, and the report must state the mismatch.

## Common mistakes and misconceptions

- **"The hashes match, so nothing was written."** Matching hashes show consistency from the first hash onwards. They say nothing about what happened before it.
- **"Read-only mount is a software write blocker."** It is a file-system setting, and other paths to the device remain open.
- **"It is a NIST-validated blocker."** CFTT publishes test reports for specific items. It does not issue blanket validation, and a report does not carry over automatically to other firmware.
- **"Write-blocked means the image is complete."** Blocking and coverage are separate questions.
- **Switching the mode after connection.** Switching to read-only after the device has appeared leaves the connection window unprotected.
- **Trusting the host log in a pre-use check.** Products differ in how refusals appear to the host. The reference media's hash is the result.

## Security implications, detection and defence

From a defender's point of view, a write blocker is an integrity control with its own failure modes. Failures are detected by pre-use checks on reference media, by comparing pass-through identity with the physical label, and by reviewing receipts for gaps in order and content. Exposure is reduced by keeping an inventory of units by serial number and firmware, buying equipment through known channels, re-checking after repair or loan, and separating evidence ports from destination-preparation work. The biggest residual risk is human: a convenience connection, a wrong mode or a receipt that claims more than the records show.

## Best practices

- Set and record read-only mode before any evidence is connected.
- Run and record a pre-use check for the specific unit, firmware and host.
- Record model, serial and reported capacity from pass-through information.
- Record source hashes before and, where practical, after acquisition. Report any mismatch rather than explaining it away.
- Use SHA-256 as the verification value. Treat MD5 as compatibility only.
- Describe the protection precisely in reports, without guarantees or claims of validation.

## Practical application: offline receipt review (authorised lab only)

**Objective.** Check a fictional acquisition receipt against the original kit transcript and the receipt's own internal logic, using only the files in front of you.

**Scope and authorisation.** This is a paper exercise on fictional records. There is no device, no live system and no collection. The receipt imagines that `suspect.dev` had been a drive attached through a bridge. The real transcript involved no blocker.

```text
FICTIONAL ACQUISITION RECEIPT - Kestrel Freight Pvt Ltd (fictional)
Case: KF-2026-014        Item: KF-014-03        Examiner: A. Rao
Write blocker: WB-07, hardware bridge, firmware 2.4.1
Tool register: last pre-use check 2026-10-02, firmware 2.3.0, PASS
Mode: bridge in RW at connection; switched to RO before imaging
10:39 IST  Pre-acquisition source SHA-256:
           e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21
10:42 IST  Evidence connected via WB-07
10:44 IST  Image evidence.dd written, size 16777216 bytes
           Image MD5 (primary verification):
           9330805010f0e235779d131b854f2295
           Image SHA-256 (secondary):
           e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f12
Post-acquisition source SHA-256: verified identical
Write-blocked: yes
```

**Steps.**

1. Compare every hash and size on the receipt, character by character, with the transcript.
2. Check that the times run in a possible order.
3. Check the blocker's identity, firmware and mode against the pre-use record and the procedure in Figure 3.
4. Check each claim against the records that would support it.
5. Write a short review note listing each finding and the action you would request.

**Expected findings.**

- The image SHA-256 ends `...a60f12`, but the transcript shows `...a60f21`. Record the discrepancy, re-verify against the original record and amend it openly. Do not correct it silently.
- The source hash is timed before the evidence was connected. One of the times is wrong.
- The firmware in use differs from the firmware of the last pre-use check, and no new check is recorded.
- Read-write mode at connection leaves the connection window unprotected. This must be declared.
- MD5 is labelled primary. SHA-256 should be the verification value.
- "Post-acquisition source SHA-256: verified identical" gives no value, and the transcript contains no such hash. The claim is unsupported.

**Clean-up.** Nothing was created except your note. File it with the exercise.

**Reflection checklist.**

- Could you trace every value on the receipt to a source record?
- Did you separate claims about the blocker from claims about the copy?
- Did your note request corrections without guessing the right values?

## Key takeaways

- A write blocker decides per command at the storage interface. Reads and identity pass through, and modifying commands, including trim, erase and firmware changes, are stopped.
- Protection must be in place before the first connection, because the first hash records whatever state it finds.
- Read-only mounts, media lock tabs and written policies are not write blockers.
- A blocker does not control drive-internal activity, failing media, coverage, encryption, the destination or sources with no blocking point.
- Confidence comes from a recorded pre-use check of the specific unit and firmware, supported by independent test reports for the exact item. It does not come from claims of validation.
