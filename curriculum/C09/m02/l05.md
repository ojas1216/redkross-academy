## Introduction and conceptual foundation

An examiner walking up to a computer at the start of an investigation faces a question that cannot be undone once answered: is this system acquired while it is running, or after it has been powered off? The first approach is called **live acquisition**, the second **dead** or **static acquisition**. The vocabulary sounds binary, but the decision is really about which evidence the investigation can afford to lose, because every option destroys something.

A powered-off disk is the most stable evidence source digital forensics has. It can be read twice, through a write blocker, and should give the same bytes both times; a failing drive is the usual exception, and the examiner records it when it happens. That repeatability is what makes the hash comparisons of the previous lessons meaningful: the digest of the image can be compared with the digest of the source, and anyone who later doubts the image can, in principle, read the source again. The price is that everything held only in electrical state disappears at power-off: the contents of memory, open network connections, the list of running processes, logged-in sessions and, critically, the keys that keep an encrypted volume unlocked.

A running system holds exactly that volatile evidence, but reaching it means using the system itself. Any tool the examiner runs is loaded into the system's memory, uses its operating system and leaves traces. The source changes while it is being read, so the acquisition can never be repeated and the result can never be compared with "the source" afterwards. Live acquisition trades repeatability for access.

This lesson builds on three earlier ones. Order of volatility (M01 L03) explains *why* some evidence must be collected first. Imaging concepts (L01 of this module) separates file exports from volume and device captures and explains what a digest can and cannot prove. Hashing (L03) shows how a digest detects change. Here those ideas meet a practical choice. You will not learn collection commands for running systems in this lesson; those belong to supervised specialist work in M06 and to the tools your organisation has tested for itself. You will learn how to make the decision, how to record it and how to review someone else's record of it.

> Every acquisition in this course is performed only with written authorisation, within a documented scope, on systems the organisation owns or is lawfully entitled to examine. ## Key terminology

| Term | Precise meaning in this lesson |
| --- | --- |
| Dead (static) acquisition | Acquisition of storage media from a system that is powered off, normally by connecting the media to a forensic workstation through a write blocker. |
| Live acquisition | Acquisition of data from a system while it is running, so the collection depends on the system's own hardware, operating system or both. |
| Volatile data | Data that exists only while the system is powered and running: memory contents, network connections, running processes, logged-on sessions, cached keys. |
| Live logical acquisition | Copying selected files or folders from a mounted, running volume, as the operating system presents them. It does not include unallocated space. |
| Examiner footprint | The changes an examiner's own actions make to a running system: loaded tools, created processes, written files, new log entries. |
| Smear | Inconsistency inside a memory capture caused by memory contents changing while the capture is being taken, so different parts of the file reflect slightly different moments. |
| Acquisition record | The examiner's contemporaneous written account of what was acquired, how, when, by whom, why that method was chosen, and the digests produced. |

## What "dead" and "live" really mean

### Dead (static) acquisition

In a dead acquisition the evidence media is not being driven by its own operating system. Typically a disk is removed, or the system is left powered off and its storage reached in a controlled way, and the media is connected to a forensic workstation through a hardware write blocker (L02). The workstation reads every addressable sector into an image, the image is hashed, and the source can be hashed independently for comparison.

The strengths follow directly from the stillness of the source. The acquisition is **repeatable**: a second examiner, months later, can read the same disk and should obtain the same digest. It is **comprehensive** at the level of the device: unallocated space, deleted entries, slack and partition gaps all come with the image, because the reading tool asks for sectors, not files. And it is **independent** of the suspect operating system: analysis happens on the examiner's workstation, which parses raw structures rather than asking a possibly compromised system what it contains.

The weaknesses are just as direct. Nothing that lived in memory survives. If the disk is encrypted and the key was only present while the system was running, the image may contain nothing but ciphertext. And getting the system into a powered-off state is itself an action with consequences, covered under *The shutdown question* below.

### Live acquisition

A live acquisition works on a running system. The examiner may capture volatile state (memory, connections, process information), or may copy files from mounted volumes while they are accessible. In both cases the system's own components do part of the work. Even when the examiner brings tools on external media, the program runs on the suspect processor, is loaded into the suspect memory and asks the suspect kernel for data.

Three consequences follow. First, **the source changes during collection**. Memory is rewritten constantly, files are opened and closed, logs grow. Second, **the examiner leaves a footprint**: a new process, memory pages overwritten by the tool, perhaps cache or log entries, depending on the operating system. Third, **the result is only as trustworthy as what the running system reports**. Malicious software that hides files or processes from the operating system can hide them from a tool that relies on that operating system too.

None of these makes live acquisition improper. They make it a method whose limits must be written down. A defensible live acquisition is minimal (it collects what the scope requires and no more), documented (every action and time is recorded so the footprint can later be told apart from activity that was already there) and directed off the system (output is written to examiner-controlled media, never to the evidence disk).

### Hybrid: the usual real case

Most real decisions are not "live or dead" but "live, then dead". A running workstation in scope for an intrusion may have its memory captured first, because memory is the most volatile evidence. It is then shut down in a recorded way and its disk is imaged statically. The memory capture provides what only a running system holds. The disk image provides the repeatable, comprehensive copy. Each covers a gap in the other, and the acquisition record explains the order.

## Why the hash means something different in each mode

The earlier lessons established that a cryptographic digest such as SHA-256 detects any change to a sequence of bytes. In a dead acquisition that property supports a strong statement: *the image contains the same bytes as the source device presented at the time of reading*. The statement holds because the source can be hashed separately and the two digests compared.

In a live acquisition that comparison is impossible. There is no stable "source" to hash. If an examiner hashed a running system's memory twice, the results would almost certainly differ, because memory changed in between. If they hashed a mounted volume that the operating system is writing to, the same problem applies. So the digest of a live capture supports a narrower statement: *this output file has not changed since the moment it was hashed*. That is still valuable, because it protects the capture from later alteration and anchors the chain of custody (M01 L05). But it says nothing about whether the capture faithfully represents the system, and it cannot be "verified against the source".

This difference is where acquisition records most often overstate. A record that says "memory image verified against source" describes something that cannot have happened. The accurate wording is that the output file was hashed at a stated time, on stated media, and that later hashes of the same file match.

Memory captures add a further limit: **smear**. A capture of several gigabytes takes time, and the system keeps running while it is taken. Pages read near the start reflect an earlier moment than pages read near the end. A structure that spans both may look inconsistent. Smear is not tampering and not a tool fault. It is a property of capturing a moving source, and analysts in M06 learn to recognise it.

## The shutdown question

If a running system will eventually be imaged statically, someone must take it from running to off. That transition is an acquisition decision in its own right.

A **graceful shutdown**, through the operating system's normal procedure, lets the system close files, flush caches and write its own shutdown records. That tidiness has a cost. The operating system and any software on it, including malicious software, get a chance to act. Temporary files may be deleted, logs written and, in an intrusion, shutdown-triggered clean-up may run. **Removing power abruptly** prevents those actions but risks leaving file systems in an inconsistent state and loses any data still waiting in write caches.

NIST SP 800-86 discusses this trade-off. It notes that collecting volatile operating-system data should happen before a system is shut down, and that the shutdown method itself affects what remains. The guidance does not reduce to one rule for every system, and this lesson does not claim one. The right choice depends on the operating system, the role of the system, the scope and the organisation's tested procedures. The professional obligation is to choose deliberately, to record the method and time, and to record the reason.

Some systems should not be shut down at all, or not by the examiner. A production database serving an entire company, a safety-related controller, a virtual host running dozens of unrelated guests or a storage array whose disks only make sense when assembled may be outside the examiner's authority to power off. In those cases a **live logical acquisition** of the specific in-scope data, carried out by an authorised specialist and documented, may be the only acceptable option. Its limitation must be recorded: a logical copy contains the files the operating system shows, not the deleted or unallocated material a device image would include.

Encryption sharpens the question. If a full-disk-encrypted laptop is found running and unlocked, powering it off returns the disk to ciphertext. For organisation-owned devices, the right first step is often to ask the asset owner whether a recovery key is held in the organisation's key management. If it is, static acquisition after shutdown may still be workable. If it is not, the live logical copy may be the only readable form of the in-scope data. This is a decision about lawful access the organisation already has. It is never a reason to attempt to defeat a protection.

## Deciding at the scene

SWGDE's Best Practices for Computer Forensic Acquisitions addresses both powered-off and running systems and treats documentation of the examiner's actions as part of the acquisition itself. Read together with NIST SP 800-86, it supports a disciplined sequence rather than a reflex. Confirm authority and scope. Observe and record the system's state before touching it. Decide whether volatile or unlocked data is in scope. Decide whether the system may be taken offline. Record every outcome.

**Relationships and arrows.** Solid arrows are the main path. The labels *off*, *on*, *yes* and *no* name the answer that leads along each branch. The single dashed arrow, labelled *then*, runs from the live capture to *Can it be taken offline?*. It shows that capturing volatile data does not end the decision: the examiner still has to settle what happens to the disk.

**Execution flow.** A system that is off goes straight to *Leave it off*: switching on a powered-off system to "have a look" would change it for no evidential gain. A running system reaches the volatile-data question. If volatile or unlocked data is in scope, it is captured first. Whether or not that happened, the next question is whether the system may be taken offline.

**Decision logic.** If the system may be taken offline, the path goes through *Documented shutdown* and joins *Leave it off*, so the disk is acquired statically. If it may not, the path ends at *Live logical acquisition*, the narrower copy whose limits must be stated. Both terminal outcomes feed *Acquisition record*.

**Technical interpretation.** The graph encodes the order of volatility: the volatile question comes before the shutdown question because the shutdown destroys volatile state. It also separates two different live activities. Capturing volatile state is one; copying files from a running volume because the system cannot stop is another.

**Practical example.** At Kestrel Freight, the finance workstation is on, has an encrypted volume mounted and may be taken offline after hours. Its route is *on*, then *yes*, then *then*, then *yes*: live capture, documented shutdown, static image. The shared file server is on but cannot be taken offline. Its route is *on*, then *no*, then *no*: a targeted live logical acquisition.

**Security implications.** Skipping the authorisation precondition leaves every later step without authority, however careful it is technically. Skipping the record makes a sound decision impossible to defend.

**Key learning.** The route through the graph is itself evidence. Write down which branch was taken and why.

## Worked example: reading the original acquisition transcript

This course does not teach you to run collection commands against systems. It does teach you to read the output of a supervised acquisition and decide what it proves. The transcript below is the original output supplied with this lesson (`original-transcript.txt`, quoted unchanged). It records a **static** acquisition in a lab: a 16 MiB lab source named `suspect.dev` stands in for a device. The transcript contains section headings and outputs only. It does not include the commands, so none are reproduced or reconstructed here.

```text
== 1. hash source before acquisition
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

How to interpret it:

- **Section 1** records a SHA-256 of the source before anything else happens. That is possible only because the source is static. Nothing is writing to it between this read and the next.
- **Section 2**'s heading states that the image was written and hashed in a single pass, with the stream split by `tee`. The stream digest is the digest of the bytes that were read.
- **Section 3** hashes the stored file `evidence.dd` and reports its size, 16,777,216 bytes (exactly 16 MiB). The file digest is the digest of what was actually written to storage. Equality between sections 1, 2 and 3 supports the strong dead-acquisition statement: the stored image holds the same bytes as the source.
- **Section 4** makes a working copy for analysis and verifies it. Analysts work on `working.dd`, never on `evidence.dd`.
- **Section 5** deliberately changes one byte of the working copy at offset 100000. The digest changes completely to `16d816db...7f2c`. The comparison reports `char 100001` because it counts bytes from 1, so it names the byte at zero-based offset 100000. The `line 1` part only means no newline byte appeared before that position; it carries no meaning for a disk image.
- **Section 6** adds an MD5 of `evidence.dd` for legacy compatibility. No MD5 of the source was recorded, so this value can only be compared with future MD5s of the same file. It is not an independent source verification.

What this transcript **cannot** show is a live acquisition. If the source had been a running system's memory, section 1 would have no stable meaning. A hash taken "before acquisition" would describe a state that no longer existed by section 2. The equality you see here is the signature of a still source.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The flow restates the transcript as six stages so that the reasoning about each digest is visible at a glance. It is a reading aid for real output, not a recipe. It names no commands beyond the transcript's own heading.

**Components.** Six boxes run top to bottom, numbered as in the transcript. *1 Hash the source* is slate, because it describes the original. *2 Acquire and hash in one pass* is blue, the acquisition itself, with the sub-label *dd -> tee; stream: e3a74e55...0f21* taken from the section heading and output. *3 Verify the image file* and *4 Verify the working copy* are green, the confirmations, with sub-labels giving the file names, the shortened digest and, for step 3, *16777216 bytes*. *5 One-byte change at offset 100000* is red, the deliberate alteration, with sub-label *working.dd: 16d816db...7f2c; cmp: char 100001*. *6 MD5 for legacy records only* is slate again, a supplementary value.

**Relationships and arrows.** The arrows run downward in the order of the transcript. They represent sequence in time, not data passing between boxes. The image in step 3 is not produced by step 1 but by step 2.

**Execution flow.** Read the shortened digests down the column: four identical SHA-256 values in steps 1 to 4, then a different one in step 5. The full 64-character values are in the transcript block above. When comparing in practice, compare the full values, not the shortened forms in the figure.

**Decision logic.** The flow has no branches, but it implies a check at each green box. If step 3 or step 4 had shown a different digest, the stage would fail, and the image or copy would be re-made from a verified source before any analysis.

**Technical interpretation.** The green steps mean something only because the slate step 1 was possible: a static source can be hashed independently. Step 5 shows the other side. A single altered byte gives an unrelated digest, which is why the digest proves change but cannot locate it. The byte-by-byte comparison in step 5 does that.

**Practical example.** In Case 1 below you review a fictional acquisition record that quotes this transcript. Use the flow to check each digest and size the record claims against the corresponding box and the full transcript line.

**Security implications.** The red box shows why analysis happens on a working copy. An accidental write during analysis damages only `working.dd`, and the comparison against `evidence.dd` proves it.

**Key learning.** Matching digests from source to image are a property of dead acquisition. In live work, expect the hash to protect the output from the moment it is taken, and nothing earlier.

## Case exercises (fictional receipts, offline review)

The three cases share one fictional organisation, Kestrel Freight, a logistics company with an office in Pune. Its incident response team has written authorisation from the company's management to examine company-owned systems in scope for a suspected data-handling incident. Each "receipt" is a handwritten-style acquisition record created for this lesson. None is tool output. Review each as a text file on your own workstation and write your findings in your lab notebook. No system is touched.

### Case 1: static image of a returned laptop (training rehearsal)

Before imaging the real 512 GB drive of a returned laptop, the examiner rehearses the procedure on the 16 MiB lab source from the transcript and writes the record below.

```text
FICTIONAL ACQUISITION RECORD KF-AR-01 (training material, not tool output)
Item: lab source suspect.dev (rehearsal for KF-LT-031, received powered off, sealed bag KF-B-114)
Mode: dead acquisition rehearsal; the real drive goes through write blocker WB-02
Source SHA-256 (before): as transcript section 1
Image: evidence.dd, size 16777216 bytes; SHA-256 as transcript section 3
Working copy: working.dd, verified, as transcript section 4
MD5: as transcript section 6, "verifies source"
Examiner: R. Iyer  Witness: S. Khan
```

Check each claim against the transcript. Sizes and SHA-256 references agree. The final MD5 claim is wrong: the transcript holds no MD5 of the source, so the MD5 only identifies `evidence.dd`. The correction is a one-line amendment, signed and dated, not an edit of the original line.

### Case 2: live capture on the finance workstation

```text
FICTIONAL ACQUISITION RECORD KF-AR-02 (training material, not tool output)
Item: KF-WS-07, found powered on, user session unlocked, encrypted data volume mounted
Reason for live work: volume key present only while running; recovery key not held by IT
Memory capture: written to external examiner drive KF-X-03
Capture hash: recorded 14:52 IST, "matches source memory"
Live logical copy: in-scope folders of mounted data volume, to KF-X-03, hashed 15:10 IST
Shutdown: after capture, method recorded on page 2
Clock: workstation clock compared with reference clock: not recorded
```

Two issues stand out. "Matches source memory" describes an impossible verification; the accurate statement is that the output file was hashed at 14:52 IST on KF-X-03. The missing clock comparison means later timeline work (M11) cannot correct the workstation's timestamps against real time. The reasoning for live work, the order (memory first, then the logical copy, then shutdown) and the off-system output are sound.

### Case 3: the shared file server

```text
FICTIONAL ACQUISITION RECORD KF-AR-03 (training material, not tool output)
Item: KF-FS-02 (fs02.kestrel.example, 192.0.2.40), production; owner refused downtime in writing
Mode: live logical acquisition of share \Finance\Q3 only
Output: logical container on KF-X-04, hashed on completion
Limitations: none
```

The mode fits the decision graph: running, cannot be taken offline, targeted copy. The error is "Limitations: none". A live logical copy excludes deleted and unallocated content and reflects the share as the server's operating system presented it during the copy. Those limits must be stated.

## Common mistakes and misconceptions

- **"Dead acquisition is always the forensically sound choice."** It is the most repeatable. It is not sound if it throws away the only readable copy of encrypted data or the only trace of memory-resident activity that the scope required.
- **"Live acquisition contaminates evidence, so it is inadmissible."** A documented, minimal, necessary live acquisition is a recognised practice. What most often weakens it is a missing or overstated record, not the method itself. This course gives no legal guarantees: admissibility is decided case by case (see Legal handling in India, M01 L04).
- **Writing live output to the evidence disk.** Saving captures on the system's own drive can overwrite deleted data the investigation may need and mixes examiner files with suspect files.
- **Assuming a write blocker protects a running system.** A write blocker sits between a disk and a workstation. It does nothing to stop a running operating system writing to its own disks.
- **Claiming source verification for volatile data.** There is no second read of memory to compare against.
- **Powering on a system found off.** It boots the operating system, changes the disk and gains nothing.
- **Treating a tool's reputation as validation.** The NIST Computer Forensics Tool Testing (CFTT) programme publishes test methods and reports describing how specific tool versions behaved in specific test cases. A report is evidence about that version under those tests. It is not a certification and not a substitute for your laboratory's own verification. This lesson makes no claim that any tool is validated.

## Security implications, detection and defence

Live acquisition happens on hostile ground. A compromised system may hide processes or files from the operating system interfaces a tool depends on. Some malicious software watches for analysis activity or for shutdown. Responders defend against this in three ways. They combine sources: memory, disk and external logs such as network or identity-provider records can contradict a lying host. They keep tool execution minimal and recorded, so unexpected behaviour can be spotted. And they analyse captures on separate workstations rather than on the suspect system.

The examiner's own footprint must be distinguishable from the intruder's. Recording each action with a time against a reference clock is what lets an analyst later say "this process at 14:41 was ours". Without that, examiner activity can be mistaken for attacker activity, or an attacker's activity can be dismissed as the examiner's.

Defenders can prepare before an incident. Hold recovery keys for organisation-owned encrypted devices in managed escrow, so the live-versus-dead decision is not forced by encryption alone. Agree in advance which production systems may be taken offline and who may authorise it. Keep forensic tools, tested by the laboratory for its own use, on examiner-controlled media, and keep the procedures that say when each may be used.

## Best practices

- Confirm written authorisation and scope before deciding anything; record who gave it.
- Photograph and note the system's state on arrival: power, screen, connected media, network.
- Leave powered-off systems off.
- If live work reveals material outside the written scope, record it and refer it to the authorising party before collecting anything.
- Collect volatile evidence first when it is in scope, then decide the power state.
- Choose and record the shutdown method and the reason for it.
- Write live output only to examiner-controlled media; hash it on completion and record the time.
- Compare the system clock with a reference clock and record the offset.
- State the limits of every live or logical acquisition explicitly.
- Word integrity claims precisely: "image matches source" only for static sources; "output unchanged since hashing" for live captures.
- Correct records by signed, dated amendment, never by overwriting.

## Key takeaways

- Dead acquisition gives repeatable, comprehensive, independently verifiable images but loses all volatile state and may lose access to encrypted data.
- Live acquisition reaches volatile and decrypted data at the cost of repeatability, an examiner footprint and dependence on a possibly compromised operating system.
- In dead work the image hash can be compared with the source; in live work the hash only protects the output from the moment it was taken.
- Shutdown is an acquisition decision: graceful and abrupt methods each change what survives.
- The usual real answer is hybrid (volatile first, then static), and the acquisition record must explain the route taken.
