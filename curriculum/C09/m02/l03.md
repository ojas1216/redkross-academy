## Introduction and conceptual foundation

An examiner who hands over a forensic image is making a quiet promise: the bytes in this file are the bytes that were read from the source, and nothing has changed them since. Nobody can inspect sixteen million bytes by eye, let alone a few terabytes, so the promise needs a compact, repeatable check. That check is the cryptographic hash. It reduces any amount of data to a short fixed-length value, the digest. Anyone holding the same data and the same algorithm can recompute the digest and compare it with the recorded one.

Hashing ties this module together. Imaging (lesson 1) produces the copy, container formats (lesson 4) store digests inside it, and verification (lesson 6) compares digests at each hand-over. This lesson explains what a hash function guarantees, how to read a real verification transcript, what a match does and does not prove, and how to respond when values disagree. Every check shown runs offline against image files or copies already held in the lab.

> [!IMPORTANT]
> A hash is evidence *about* evidence. It is only as trustworthy as the record that holds the reference value, the person who wrote it and the custody of both. Treat recorded digests with the same care as the image itself.

## Key terminology

| Term | Precise meaning in this lesson |
| --- | --- |
| Hash function | A deterministic algorithm that maps input of any length to an output of fixed length. |
| Digest (hash value) | The output of a hash function, usually written as hexadecimal characters. |
| Cryptographic hash | A hash function designed so that finding inputs with chosen or matching digests is computationally infeasible. |
| Reference value | The digest recorded at a known point (for example at acquisition) against which later copies are compared. |
| Verification | Recomputing a digest and comparing it with the reference value. |
| Preimage resistance | Given only a digest, it is infeasible to find any input that produces it. |
| Second-preimage resistance | Given a specific input, it is infeasible to find a *different* input with the same digest. |
| Collision resistance | It is infeasible to find *any* two different inputs that share a digest. |
| Avalanche effect | A small change in input produces a digest that looks unrelated to the original. |
| Known-file set | A list of digests of files already identified, used to include or exclude files during review. |

## How a cryptographic hash function works

### Fixed-length output from any input

A hash function reads its input in fixed-size blocks and updates an internal state as each block is processed. When the input ends, the function pads the last block and emits the state as the digest. SHA-256, for example, works on 512-bit blocks, and its padding also records the input length. However large the input, the digest length never changes. SHA-256 always produces 256 bits, written as 64 hexadecimal characters. MD5 produces 128 bits, or 32 characters, and SHA-1 produces 160 bits, or 40 characters. The SHA-2 family, which includes SHA-256 and SHA-512, is specified by NIST in FIPS 180-4. SHA-3 is specified in FIPS 202.

Two consequences follow. First, hashing is one-way and lossy. A 64-character digest cannot contain a 16 MiB image, so the digest cannot be used to rebuild the data, and no key exists that would "decrypt" it. Hashing is not encryption. Second, because there are vastly more possible inputs than possible digests, collisions must exist mathematically. Security does not depend on collisions being absent. It depends on their being infeasible to find.

### The three resistance properties

The three resistance properties in the terminology table answer three different questions an adversary might ask.

- **Preimage resistance.** "Here is a digest. Can I produce data that matches it?" For evidence work this matters little, because the examiner already holds the data.
- **Second-preimage resistance.** "Here is a specific evidence image. Can I build a different image with the same digest?" This is the property that protects an image that has already been hashed and recorded. If it failed, someone could substitute altered evidence that still verifies.
- **Collision resistance.** "Can I make *any* two different files that share a digest?" This is a weaker goal for the attacker, because they choose both inputs. It is also the property that has failed for older algorithms.

The difference between the last two matters in practice. A collision attack does not let someone match the digest of an image you have already recorded. It does let someone who controls the data *before* it is hashed prepare two different files with one digest. One example is a party who supplies a document that is later collected. That party could hand over one version and later produce the other. Forensic practice therefore avoids algorithms with practical collision attacks even though they may still resist second preimages.

### Why the avalanche effect matters to an examiner

A well-designed hash function behaves as though every output bit depends on every input bit. Change one byte, and on average about half the output bits flip. The new digest bears no visible resemblance to the old one. This is what makes hashing a sensitive integrity check, since no change is too small to detect. It also means the digest says nothing about *how much* changed or *where*. A one-byte edit and a wholesale replacement produce equally different digests. Locating a change needs other tools, such as a byte comparison or piecewise hashing, described later.

## Choosing an algorithm

| Algorithm | Digest length | Status for evidence integrity |
| --- | --- | --- |
| MD5 | 128 bits (32 hex) | Practical collisions have been published since 2004. Record it only for compatibility with older records or partners. |
| SHA-1 | 160 bits (40 hex) | A practical collision was publicly demonstrated in 2017, and NIST has announced its retirement. Avoid it as the primary value. |
| SHA-256 | 256 bits (64 hex) | A widely used choice for verification. No practical collision or second-preimage attack is known. |
| SHA-512 | 512 bits (128 hex) | Same family as SHA-256 with a longer digest. Sometimes faster on 64-bit hardware. |
| SHA3-256 | 256 bits (64 hex) | A different internal design from SHA-2, useful where a lab wants algorithm diversity. |

Some labs record two algorithms: SHA-256 as the primary value, plus MD5 or SHA-1 only where an older tool, a partner agency or an earlier receipt uses it. Recording a second value does no harm, provided the weaker one is never treated as the stronger check.

Guidance documents age. NIST SP 800-86, *Guide to Integrating Forensic Techniques into Incident Response*, was published in 2006, years before the public SHA-1 collision. Its principle still stands: compute digests of acquired data and use them to verify copies. Read any algorithm examples in documents of that era against later cryptanalysis rather than as a fixed choice.

> [!NOTE]
> A standard algorithm is not the same as a tested implementation. That SHA-256 is well specified says nothing about whether a particular program, version or script computes it correctly on your platform. Labs check their own tools against published test values and their own procedures. Reports from the NIST Computer Forensics Tool Testing (CFTT) programme describe how specific tool versions behaved in specific tests. They are not certificates for other versions or for your configuration.

A simple self-check uses the example values published with the standard. The SHA-256 of the three-byte ASCII input `abc` is `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`. A lab can hash a file containing exactly those three bytes, with no trailing newline, and compare. A trailing newline from a text editor is a common cause of a false failure. This check confirms that the tool computes the algorithm. It does not test how the tool handles large files, read errors or devices.

## Where hashing sits in acquisition

An acquisition is a chain of copies: source, image, archive copy, working copy, perhaps a copy sent to another party. Each hand-over is a point where bytes could be lost, truncated, reordered or altered, by accident or on purpose. A *hash checkpoint* is a point where the digest is computed and recorded or compared. The SWGDE *Best Practices for Computer Forensic Acquisition* treats verifying the acquired data, and documenting that verification, as part of acquisition itself rather than an optional extra.

Typical checkpoints are:

1. **Source before acquisition**, where the source can be read in a stable state. This gives a reference value independent of the imaging step.
2. **During acquisition**, hashing the stream as it is read. This costs no extra read pass over the source.
3. **Image file after writing**, which confirms that what reached storage equals what was read.
4. **Each derived copy**, such as an archive copy, a working copy or a copy for disclosure, before anyone relies on it.

Not every source allows every checkpoint. A running system's memory, or a mounted volume that is still being written, changes between reads. Hashing it twice gives two different values, and neither is "wrong". Such sources are covered in lesson 5, live versus dead acquisition. There, the digest of the *captured file* becomes the reference, and the notes explain why the source could not be re-verified.

The C09 acquisition kit includes a short verification run, reproduced below exactly as recorded in the original transcript supplied for this lesson. It records stage headings and output lines. ```text

```text
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

How to read it, stage by stage:

- **Stage 1** gives the reference value for the source labelled `suspect.dev`. The 64-character value is a SHA-256 digest.
- **Stage 2** heading describes the image being written and hashed in a single pass, with the stream split between the image file and the hash calculation. The digest of the *stream* equals stage 1, so what was read matched the earlier read of the source.
- **Stage 3** hashes the *file on disk*. Matching stage 2 shows the stored bytes equal the bytes that passed through the stream. A failing write or a full disk would show up here. The size line, 16,777,216 bytes, is exactly 16 MiB (2²⁴ bytes), or 32,768 sectors of 512 bytes.
- **Stage 4** verifies the working copy before analysis begins. Analysis starts from bytes identical to the image.
- **Stage 5** deliberately changes one byte of the working copy, at zero-based offset 100,000, to demonstrate detection. The digest differs from the receipt. The second line is the format of the `cmp` byte-comparison utility. It reports the first difference as "char 100001" because `cmp` counts bytes from 1. The "line 1" part counts newline bytes, which has little meaning for a disk image.
- **Stage 6** computes MD5 for the image, labelled in the transcript as legacy compatibility only. It is 32 hexadecimal characters, as expected for a 128-bit digest.

Two limits are worth noticing. The transcript does not show the source being hashed again *after* acquisition. Doing so, where the source is stable, would provide an additional check that its final readable bytes match the initial read. Stage 6 also gives MD5 for `evidence.dd` only, so there is no MD5 for the source to compare it with. Neither limit makes the run wrong. They are the kind of gap a reviewer looks for.

**Key learning.** A digest is meaningful only as a comparison against a protected reference value computed with the same algorithm. Compare the full value, not a prefix.

## What a matching hash does and does not establish

When a recomputed SHA-256 digest equals the reference value, the examiner may say that the copy contains the same sequence of bytes as the data hashed when the reference was recorded. The chance that a different file matches by accident is negligible. No practical way is known to construct one deliberately for SHA-256.

A match does **not** establish any of the following:

- **That the data was acquired lawfully or within scope.** Authority and scope are separate records, covered in module 1.
- **That the source was complete or read correctly.** If a drive returned errors and the tool substituted zeros for unreadable sectors, the image and its digest are self-consistent but do not represent those sectors. The acquisition log, not the digest, records this.
- **That the content is authentic or means what someone claims.** A planted file verifies as perfectly as a genuine one. Hashing protects the copy from the reference point onwards, not the history before it.
- **That the tool worked correctly in every respect.** The digest shows the output is stable. It does not test how the tool handled every sector of the source.
- **That the reference value itself is genuine.** If the reference is stored where it can be edited, a match only proves that two editable values agree.

The careful wording for a report is therefore narrow. Here is an example: "The SHA-256 digest of the working copy, computed on [date], equals the digest recorded on the evidence receipt at acquisition." Avoid wording such as "the hash proves the evidence is genuine", which claims more than the check supports.

## Handling a mismatch

Mismatches happen, and most have ordinary causes. The response should be calm, documented and in a fixed order. The aim is to find out *which* value or copy is wrong without destroying the record that a discrepancy occurred.

First, establish whether the two values are like-for-like. A SHA-256 value will never match an MD5 value. A value copied by hand may have a transposed character. A receipt may hold only the first characters. Upper-case and lower-case hexadecimal represent the same value. Windows PowerShell prints upper case and most Unix tools print lower case. If the comparison was not like-for-like, record the error and repeat it properly.

Second, compare the size of the copy with the recorded size. A shorter file usually means an interrupted transfer or a full disk. A longer one may mean something was appended. Either way the copy, not the original, is the suspect.

Third, check the other copies. If the archived master still matches the receipt, only one derived copy is affected. Quarantine it, record what happened and make a fresh copy from the verified master. If the master itself no longer matches, the situation is serious. Stop work on the item, preserve everything as it is and escalate to the case lead.

At no stage should anyone recompute a digest and overwrite the reference "so the paperwork agrees". The discrepancy is itself a fact the case must be able to explain.

## Recording hashes: the evidence receipt

A digest is useful only if it is recorded where it cannot quietly change, alongside enough context to repeat the check. Lesson 6 of module 1 covers documentation in general. For hashing specifically, a receipt should record:

- the item identifier and the exact file name or names hashed
- the algorithm name for each value
- the full digest, never a prefix
- the size in bytes
- who computed it, with what tool and version, and when
- where the reference copy is stored

The example below is a fictional training record. It copies the values from the lab transcript but is not tool output.

```text
EVIDENCE RECEIPT - fictional training record
Organisation:  Kaveri Freight Pvt Ltd (fictional)
Case:          KFL-TRN-2026-014
Item:          ITEM-03, image file evidence.dd from source labelled suspect.dev
Size:          16,777,216 bytes
SHA-256:       e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21
MD5 (compat):  9330805010f0e235779d131b854f2295
Computed by:   Examiner A. Rao (fictional), lab workstation LAB-WS-02
Stored at:     Evidence store shelf E2, archive copy 1 of 2
Signed:        A. Rao / witnessed: S. Menon (fictional)
```

Keep the receipt separate from the image. A text file containing the digest, saved in the same writable folder as the image, protects against accidental damage but not against deliberate change. Anyone who can alter the image can alter the text file beside it. The reference value belongs in the case record, on the signed receipt and, where the lab supports it, in a system with access logging.

Hash values can also matter when electronic records are certified for Indian proceedings. Module 1, lesson 4 covers legal handling in India, and this lesson makes no claim about what any court will accept. For this lesson, the practical point is simple: record the algorithm and the full value at acquisition, so whoever prepares any later certificate or statement has accurate information.

## Offline file-based checks

Verification in the lab is a file operation on an image or copy that is already held. None of the commands below reads a device or a live system. Each is shown with its options explained. No outputs are shown, because none were recorded in this lesson's source transcript. Lesson 8, the acquisition lab, works from the kit itself.

On a Linux analysis workstation, GNU coreutils provides `sha256sum`:

```bash
sha256sum evidence.dd
sha256sum -c evidence.dd.sha256
```

- The first line prints the SHA-256 digest of the file followed by its name.
- `-c` (check) reads a manifest file in which each line holds a digest and a file name. The tool recomputes each listed file and reports whether it matches. The manifest is only as trustworthy as its storage, so compare it with the receipt before relying on it.

On Windows, PowerShell's `Get-FileHash` cmdlet does the same:

```powershell
Get-FileHash -Path .\evidence.dd -Algorithm SHA256
```

- `-Path` names the file to hash.
- `-Algorithm SHA256` selects the algorithm. SHA256 is also the default, but stating it makes the note unambiguous.
- The digest is printed in upper-case hexadecimal. Compare it with a lower-case receipt without regard to case.

A lab may also keep a small script that reads the file in chunks, so memory use stays flat for large images, and compares the result with an expected value given on the command line:

```python
import hashlib
import sys


def sha256_of(path, chunk=1024 * 1024):
    digest = hashlib.sha256()
    with open(path, "rb") as handle:
        for block in iter(lambda: handle.read(chunk), b""):
            digest.update(block)
    return digest.hexdigest()


expected = sys.argv[2].strip().lower()
actual = sha256_of(sys.argv[1])
print("MATCH" if actual == expected else "MISMATCH", actual)
```

- `open(path, "rb")` opens the file read-only in binary mode. The script never writes to the evidence.
- The 1 MiB chunk size affects only speed and memory, not the result.
- `.lower()` removes the upper-case and lower-case difference before comparison.

Before a lab relies on a script like this, it should check it against published test values and against a second tool on the same file, and it should record that check. Writing a script does not validate it.

### Piecewise hashing

A single digest over a whole image says *whether* anything changed. It does not say where. Some acquisition workflows also record digests over fixed-size pieces, for example every 1 MiB. The 16 MiB image in the transcript would then have sixteen piece digests. If the whole-image value later fails, the piece digests show which regions changed. That narrows the question and can show whether damage is confined to one area. Piece digests cannot recreate the original data, and they cannot say whether a change was accidental or deliberate.

## Other uses of hashes in an investigation

**Known-file filtering.** NIST's National Software Reference Library publishes digests of files from known software distributions. Matching file-level digests against such a set lets an analyst set aside ordinary operating-system and application files and focus on the rest. A lab can also keep its own sets of files already identified in earlier cases. A match means "same bytes as a catalogued file", not "harmless". Catalogued software can still be misused.

**File-level versus image-level digests.** The digest of an image covers every byte of the image. It does not provide digests of the individual files inside it. When files are exported for a report or for disclosure, hash each exported file and record those values too. This is how a recipient can check the specific files they received.

**Similarity rather than identity.** Integrity hashes deliberately give unrelated values for near-identical inputs, so they cannot find a document that differs by one paragraph. Similarity methods such as fuzzy hashing (context-triggered piecewise hashing) are designed for that job. They answer a different question and must never be used as an integrity check.

**Containers.** A container format such as E01 (lesson 4) adds headers, metadata and often compression around the acquired data. The digest of the container *file* therefore differs from the digest of the media data it holds. Tools that read the container recompute the media-data digest for comparison. Always say which of the two a value refers to.

## Common mistakes and misconceptions

- **Comparing a prefix.** Eight matching characters are not a verification.
- **Comparing across algorithms.** An MD5 receipt and a SHA-256 recomputation can never match. `E3A7…` and `e3a7…`, by contrast, are the same value.
- **Believing a match proves authenticity.** It proves sameness of bytes from the reference point onwards.
- **Re-hashing a live source and expecting agreement.** Changing sources give changing digests, and the notes must say so.
- **Assuming "the tool is standard, so it is validated".** Validation is specific to a tool version, configuration and test, and it is recorded, not assumed.

## Security implications, detection and defence

Hashing is a detective control. It does not prevent change, but it makes undetected change very unlikely if the reference is protected. Its main threats are to the reference value and the process around it.

- **Tampering with the record.** Defend it with signed paper or electronic receipts, case-management entries with access logs, and two independent copies of the reference in different custody.
- **Weak algorithms.** A party who prepares data before it is collected could exploit MD5 collisions. Use SHA-256 or stronger as the primary value.
- **Silent corruption in storage.** Media degrade and transfers fail. Re-verifying archived images on a schedule turns silent corruption into a recorded event while good copies still exist.
- **Process shortcuts under pressure.** Verification skipped "just this once" is the most common failure. A checklist that requires the recomputed value to be written down, not just ticked, makes the shortcut visible.

## Best practices

1. Use SHA-256 or stronger as the primary algorithm. Record weaker values only for compatibility, labelled as such.
2. Record the full digest, the algorithm, the size and who computed it, with which tool version and when.
3. Hash at every hand-over: acquisition, archiving, working copy, transfer and disclosure.
4. Keep the reference value separate from the image and under its own custody.
5. Compare like-for-like, ignore hexadecimal case and compare the full value.
6. On a mismatch, follow the fixed order: comparison, size, master copy. Never overwrite a record.
7. Check your hashing tools against published test values and record the check. Cite tool-testing reports only for what they actually tested.
8. Write report conclusions about hashes narrowly: same bytes as recorded, no more.

## Key takeaways

- A cryptographic hash turns any data into a fixed-length digest. Any change, however small, produces an unrelated value.
- Second-preimage resistance protects an image already recorded. Collision resistance matters when someone controls data before it is hashed, which is why MD5 and SHA-1 are compatibility values only.
- A match shows the bytes are the same as when the reference was recorded. It does not show lawfulness, completeness, authenticity or tool correctness.
- The reference value is only as strong as its record and custody. Keep it separate from the image.
- Handle mismatches from the cheapest explanation to the most serious, work from a verified master and never overwrite a record.
