## Introduction and conceptual foundation

The previous lessons covered what an image is, how a write blocker keeps the source unchanged while it is read, and how a cryptographic digest lets you show later that a copy still matches what was read. This lesson deals with the next practical decision: in what form are the acquired bytes stored? The two answers you will meet most often are the raw image, often called a dd image after the Unix utility that popularised it, and the Expert Witness Compression Format, usually called E01 after the extension of its first segment file.

The choice matters less for what the image can contain than for what travels with it. A raw image and an E01 image of the same disk can hold exactly the same sequence of bytes from the source. They differ in everything around those bytes: whether the data is compressed, whether it is broken into segments, where the case details live, where the acquisition hash is recorded and how a later reader checks it. Those differences decide how an examiner verifies the evidence, how a colleague or an opposing expert opens it, and which mistakes are likely.

Throughout this lesson, keep one distinction in mind. There is the **media stream**, meaning the bytes read from the source in order from the first sector to the last, and there is the **container**, meaning the file or set of files used to store that stream. For a raw image the container and the stream are the same thing. For an E01 image they are not, and most E01 confusion comes from forgetting that.

NIST SP 800-86 describes collecting data in a way that preserves its integrity and using message digests to show that copies match the original. SWGDE's *Best Practices for Computer Forensic Acquisitions* likewise treats verification and documentation as part of the acquisition rather than optional extras. Neither document requires one storage format. Both formats discussed here can support a sound acquisition, and both can be undermined by careless handling.

## Key terminology

| Term | Meaning in this lesson |
| --- | --- |
| Media stream | The ordered bytes read from the source, from the first sector to the last sector read. |
| Container | The file or set of files that stores the media stream, with or without additional structure. |
| Raw image | A container whose content is the media stream and nothing else. Common extensions are `.dd`, `.raw`, `.img` or a numbered series. |
| Split raw image | A raw stream cut into consecutive pieces. Joined in order, the pieces form the original stream. |
| EWF / E01 | Expert Witness Compression Format. The first segment file is `.E01`, later ones `.E02`, `.E03` and onward. |
| Segment file | One file of a multi-file image. |
| Chunk | The unit in which E01 stores media data. Common tools default to 64 sectors of 512 bytes, which is 32 KiB. |
| Media hash | A digest computed over the media stream. This is the value that can be compared with the source. |
| Container hash | A digest of an image file as it is stored on disk. It is useful for transfer checks. When the container adds structure, it cannot be compared with the source. |
| Sidecar record | A separate document kept with an image: hashes, sizes, case details and the acquisition log. |

## The raw image: the bytes and nothing else

### What a raw image contains

A raw image is the simplest possible container. Byte 0 of the file is byte 0 of the source, byte 1 is byte 1, and the file ends where the read ended. There is no header, no footer, no compression and nothing that identifies the case, the examiner or the date. If the source held 16,777,216 bytes, a complete raw image holds 16,777,216 bytes.

That simplicity is the format's main strength. Almost every forensic tool can read a raw image because there is nothing to interpret, and the format does not depend on any vendor's documentation. It also gives raw images a property that is easy to take for granted: **the hash of a complete, single-file raw image is the hash of the media stream**. If the acquisition read every byte correctly, hashing the image file produces the same value as hashing the source. The worked example later in this lesson shows exactly that in the course kit's transcript.

The price of simplicity is size and context. A raw image is as large as the area that was read, whether that area holds documents or millions of zeroed sectors. Some storage systems can store long runs of zeros sparsely, but that is a property of the storage, not of the format, and a sparse file can lose that saving when it is copied to other media.

Unreadable sectors are a further limit. When a sector cannot be read, the raw file has no field in which to say so. Depending on the tool and its settings, the acquisition may write filler bytes, often zeros, at that position so that later offsets stay aligned with the source. Inside the image, filler looks exactly like a sector that really contained zeros. Only the acquisition log tells the two apart, which is why the log belongs with the image.

### Split raw images

Raw images are often split into fixed-size pieces, for example to fit storage with file-size limits or to make transfers easier to resume. Names such as `.001`, `.002` and `.003` are common, but the naming is a convention of the tool that wrote them. The pieces have no headers. Only their names and the order in which you join them hold them together.

Three rules follow from that. First, record the number of pieces, the size of each and the total size, so that a missing or truncated piece is visible before anyone tries to verify a hash. Second, the hash that matches the source is the hash of the whole stream, computed over all pieces joined in order. A hash of `.002` on its own matches nothing on the source. Third, per-piece hashes are still worth recording, because if the whole-stream check fails after a transfer they show which piece was damaged. Without them, you only know that something in the set is wrong.

### What a raw image cannot tell you

Ask a raw image who made it, when, from which device, with which tool, with which errors and with which expected hash, and it has no answer. Every one of those facts has to live outside the image: in the acquisition log, the evidence receipt, the examiner's contemporaneous notes and the chain-of-custody record described in Module 1. The file system timestamps on the image file are not a substitute, because copying, restoring or moving the file can change them.

A raw image separated from its sidecar records is still a faithful copy of bytes, but it has lost its context. Defensively, that means sidecar records must be created at acquisition time, stored with the image and also kept somewhere the image's custodian cannot silently rewrite.

## The Expert Witness format (E01)

### Origins and documentation

The Expert Witness format is generally traced to ASR Data's Expert Witness software and became widely known through EnCase, whose evidence files use it. It was not published as an open standard. Much of the public, detailed knowledge of its structure comes from the libewf project's documentation, which many open-source tools build on. In practice, different programs write slightly different variants. Compatibility depends on the tool, its version and the options used, so test that a recipient's tool can open the image before you rely on it.

### Inside an E01 segment file

An E01 image is a set of one or more segment files. Each segment file begins with a signature and its segment number, and the rest of the file is a chain of *sections*. Each section starts with a small descriptor naming its type and pointing to the next section. The summary below is simplified from libewf's notes on the E01 variant. Section names and their exact arrangement vary with the program and version that wrote the file.

- **Header sections** carry the case metadata recorded at acquisition, such as case number, evidence number, examiner and notes, stored compressed.
- **A volume section** describes the media: bytes per sector, number of sectors, sectors per chunk and chunk count.
- **Sectors sections** carry the media data itself, chunk after chunk.
- **Table sections** list where each chunk begins. A second copy is commonly kept so that damage to one table can be survived.
- **Hash and digest sections**, typically in the last segment, store the media hash computed during acquisition: MD5, and SHA-1 in later writers.
- **An error section** (`error2` in libewf's description), when present, lists sector ranges that could not be read during acquisition.
- **A closing section** either says that another segment follows or that the image is complete.

That error section is a real difference from raw. A raw file cannot say which sectors were unreadable, while an E01 writer can record them inside the image. Treat that list like the other embedded records: useful, but to be checked against the acquisition log rather than trusted on its own.

**Purpose.** The diagram lays out the main parts of an E01 image as a single row of boxes, read from left to right, so that you can see where case metadata, media data and the acquisition hash physically sit. It is drawn widest because in a real image it is almost the entire file. The second blue box, **table / table2**, lists the chunk offsets. The dark **hash / digest** box holds the media hash, and the slate **done / next** box on the far right closes the segment.

**Relationships.** The labels above the boxes show where each part normally appears. Header and volume information appear at the start of the image, while sectors and tables appear in every segment that carries data. The hash and the closing *done* appear only in the last segment. Middle segments end with *next* instead.

**Execution flow.** A reading tool opens the first segment, checks the signature, reads the metadata and the volume geometry, then uses the tables to find any chunk it needs. To verify, it decodes every chunk in order, which rebuilds the media stream, hashes that stream and compares the result with the dark hash box.

**Technical interpretation.** Only the orange box contains source bytes, and even those are stored compressed in most images. Everything else is structure the writing tool added. The optional error section is left out of the drawing to keep the row readable, but it is structure of the same kind. Hashing a `.E01` file therefore hashes signature, metadata, tables and compressed chunks together. That value belongs to that one file and is not comparable with the hash of the source.

**Practical example.** In the kit's 16 MiB lab source, 32 KiB chunks would give 512 chunks in the sectors area. That is a calculation from the transcript's size, not tool output. If those chunks were written to two segments and the second segment went missing, the dark hash box would be missing too. The image could then no longer verify itself.

**Security implications.** The violet metadata box and the dark hash box are written by the acquiring tool, but nothing stops a later program from rewriting them. They are records, not seals. Copy the media hash into the out-of-band receipt at acquisition time.

**Key learning.** An E01 image is the media stream wrapped in structure. The media hash describes the orange data once it is decoded, never the file that contains it.

### Chunks, compression and checksums

E01 stores media data in chunks, commonly 32 KiB each. Each chunk is either compressed with the zlib (deflate) method or stored uncompressed when compression would not help. The tables record where each chunk starts, so a tool can jump to any offset in the media, decode only the chunk it needs and avoid reading the image from the beginning. Random access across a compressed image is what makes E01 usable for analysis.

Compression ratios depend on the content, not the format. Long zeroed or repetitive regions shrink dramatically. Encrypted volumes, media files and existing archives hardly shrink at all, because their bytes already look random. An E01 image of a lightly used, unencrypted disk may be a small fraction of the source size. An E01 image of a fully encrypted disk of the same capacity may be almost as large as the source. Plan storage from the source size and treat any compression saving as a bonus, not a promise.

Each chunk is also protected by an Adler-32 checksum in the E01 variant: stored after the data for an uncompressed chunk, and built into the zlib stream for a compressed one. When a tool reads a chunk and the checksum does not match, it knows which 32 KiB region of the media is damaged, rather than only that the image as a whole has failed. That localisation helps with a failing archive disk. Adler-32 is not a cryptographic function, though. It detects accidental damage. It does not show that nobody deliberately changed the data, because anyone who alters a chunk can recompute its checksum.

### Case metadata: useful, but self-declared

The header sections typically hold fields such as case number, evidence number, a description, the examiner's name and free-text notes, along with details the tool records itself, such as acquisition date, the acquiring system's operating system and the software version. That makes an E01 image largely self-describing, which is a real advantage when an image is found on an archive shelf years later.

Every one of those values, however, was either typed by a person or read from the acquiring computer's clock. The container preserves a mistyped case number exactly as faithfully as a correct one, and it records a wrong clock as confidently as a right one. Treat the embedded metadata as a convenient copy of facts that must also appear in contemporaneous notes and the receipt. When you receive an E01 image, compare its header fields with the receipt. A mismatch does not prove anything sinister, but it must be explained and recorded before analysis begins.

### The stored hash and what it proves

At the end of acquisition, the tool writes the media hash it computed into the last segment. Verification later repeats the work: the tool decodes every chunk, recomputes the media hash and reports whether it equals the stored value.

A successful verification shows that the media stream, as it decodes now, matches the value stored in the file. It does not show that the stored value is what was computed on the day, because anyone able to rewrite the file could rewrite the stored hash as well. The defensive answer is the same as for raw images. Record the media hash outside the image, on the receipt and in the case log, at the time of acquisition. Then compare later results with that external record, not only with the image's own opinion of itself.

The algorithms matter as well. The E01 variant stores MD5, and later writers add SHA-1. Both algorithms have published collision attacks, as the Hashing lesson explained. If your laboratory's policy requires SHA-256, compute it over the media stream and record it in the sidecar, unless your tool's documentation shows that it stores SHA-256 and you have checked that it does.

### EWF variants and neighbouring formats

EnCase 7 introduced a newer evidence file format, Ex01, with features such as optional encryption, together with Lx01 for logical evidence. Not every tool that reads E01 reads Ex01, so check the recipient's tooling before choosing it. Logical evidence files such as L01 hold selected files and their metadata, not the media stream. They are a valid way to collect specific items, but they are not a full image and cannot be verified against a whole-device hash. Other image containers exist, such as the open AFF4 family. They are outside the scope of this lesson, and the same media-hash and container-hash reasoning applies to them.

## Two hashes that must never be confused

Everything so far comes down to one rule: **compare like with like**. For a complete raw image, the file hash and the media hash are the same number, because the file is the stream. For a split raw image, the media hash is the hash of the pieces joined in order. For an E01 image, the hash of any `.E01` file is a container hash. It depends on compression level, metadata, segment size and tool version. Two E01 images of the same disk made with different settings have different container hashes and identical media hashes.

Container hashes are still useful, just for a different question. When you copy an E01 set to an archive, hashing each segment file before and after the copy shows that each file arrived intact. That check is quick and does not need forensic software. It only answers "did these files survive the transfer?", never "does this image match the source?"

The slate node **Not comparable** is where that mistake should lead. Both methods feed one decision node, **Same as the receipt value?**, whose *yes* branch reaches the green **Values match** node and whose *no* branch reaches the orange **Values differ** node: the two outcomes of a valid comparison.

**Relationships and arrows.** Arrows run from the recorded hash to the container type, from the container type to a method, from either method into the one comparison, and from the comparison to an outcome. The dashed arrow from the E01 node to the red node is labelled *common mistake*. Its only continuation is the slate *Not comparable* node, which is where that path stops. Nothing leads from the red node to a match or a mismatch.

**Execution flow.** Start with the receipt value. Identify the container. For raw, hash the single file, or the pieces in order, and compare. For E01, have a tool decode the chunks and hash the stream, or export the stream and hash that, then compare.

**Decision logic.** A match supports the statement that this copy holds the recorded stream. A difference sends you to the orange node's sub-label: check that you used the right recorded value, the right image set and the right piece order before treating it as a possible change, then escalate and record it.

**Technical interpretation.** Both green methods produce a hash of the same thing, the media stream, which is why both may meet the dark node's value. The red method hashes structure plus compressed data, a different input altogether.

**Practical example.** An intake technician hashes `CASE-07.E01` with SHA-256, compares it with the SHA-256 media value on the receipt and sees a mismatch. On the diagram, that is the dashed red path. The correct next step is not to report alteration but to go back to the E01 node and take the green route.

**Security implications.** False alarms waste time, and repeated false alarms train staff to ignore real ones. A written intake procedure that names the comparison method for each format prevents both.

**Key learning.** Only a media hash can be compared with a media hash. A container hash answers transfer questions only.

## Raw and E01 compared

| Property | Raw image | E01 image |
| --- | --- | --- |
| Content | Media stream only | Media stream in chunks, plus structure |
| Size | Equal to the area read | Usually smaller. Depends on how compressible the content is |
| Case metadata | None. Kept in sidecar records | Embedded header fields, self-declared |
| Stored hash | None. Kept in sidecar records | MD5 (and SHA-1 in later writers) of the media stream |
| Damage localisation | Only with per-piece hashes | Per-chunk Adler-32 checksums |
| Unreadable sectors | Not recorded in the file. Only the log shows them | Can be listed in an error section. Check against the log |
| Reading | Almost any tool | Tools with EWF support; check variant compatibility |
| File hash equals source hash? | Yes, for a complete single file | No. Decode the stream and hash it |
| Typical failure | Lost sidecar, missing piece | Container hash compared with media hash, missing last segment |

Neither column is the "forensically correct" one. Raw images give maximum compatibility and transparent verification. E01 images give compactness and self-description. A laboratory should state in its procedures which formats it uses and when, so that the choice in a given case is an application of policy rather than an improvisation.

## Worked example: reading the kit's acquisition transcript

The C09 lab kit includes an execution-tested raw acquisition transcript. It is reproduced below exactly as saved, with each stage's heading and results. The transcript shows results only, not the commands that produced them. This lesson does not reconstruct those commands. The acquisition procedure is practised later in the module under the lab kit's instructions. The kit contains no E01 transcript, so no E01 tool output appears in this lesson.

```text
== 1. hash source before acquisition
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  suspect.dev
== 2. acquire: dd -> tee -> image file and hash in one pass
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd (stream)
== 3. verify image file
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  evidence.dd
size 16777216 bytes
== 4. working copy for analysis; verify
e3a74e55ea5520102b3b9458e4fd1eeec4c9a92958082c68953b754e44a60f21  working.dd
== 5. one-byte change in working copy at offset 100000
16d816db2d0761c01f8a6d0e8d88870f98a1bbdbf5bae5c95d99a26c9bb47f2c  working.dd
evidence.dd working.dd differ: char 100001, line 1
== 6. md5 alongside sha256 (legacy compatibility only)
9330805010f0e235779d131b854f2295  evidence.dd
```

**Stage 1** records a SHA-256 baseline of the lab's source, named `suspect.dev`. The transcript does not say what kind of object that is. Treat it as the lab's stand-in for a device.

**Stage 2** hashes the bytes as they flow to the image file during the same read, which is what "in one pass" and the `(stream)` label indicate. The value equals stage 1, so the bytes delivered by the read match the baseline.

**Stage 3** hashes the image file at rest and reports its size. The value again equals stage 1. This is the raw-format property in action: the file is the stream, so the file hash is the media hash. The size, 16,777,216 bytes, is exactly 16 MiB. At 512 bytes per sector that would be 32,768 sectors. The transcript does not state a sector size, so that figure is a calculation.

**Stage 4** shows that a working copy made for analysis also matches. Analysis then happens on the copy, never on `evidence.dd`.

**Stage 5** deliberately changes one byte in the working copy, at offset 100000. The digest changes completely. A byte comparison then reports `char 100001`. The two numbers are consistent if the heading counts from 0 and the comparison counts bytes from 1, which is the usual convention for that kind of comparison report. The transcript does not state the heading's numbering, so read this as the most likely explanation rather than a fact recorded in the output. `line 1` only means that no newline byte occurred before that point, which has no meaning for a disk image. The lesson is that a digest tells you *that* something changed, while a byte comparison against the verified image tells you *where*.

**Stage 6** adds an MD5 of `evidence.dd`, labelled legacy compatibility only. It is 32 hexadecimal characters (128 bits) against SHA-256's 64 (256 bits).

Now connect the transcript to E01. Suppose the same stream had been stored as an E01 image. No such image exists in the kit, so this is reasoning, not output. Because `evidence.dd` *is* the media stream, its MD5, `9330805010f0e235779d131b854f2295`, is the MD5 of the stream. A correct E01 of the same stream should therefore store and verify to that MD5 value, and a SHA-256 of its decoded stream should equal `e3a74e55…0f21`. Hashing the `.E01` file itself would give some other value, which would prove nothing either way.

## Converting between formats

Images are sometimes converted: raw to E01 to save archive space, or E01 to raw for a recipient whose tools need raw input. A conversion creates a new copy, so treat it like one. Record who converted what, when and with which tool and version. Keep the original until the new copy is verified. Verify the new copy by its media hash against the hash recorded at acquisition, not against the previous container.

Two details are easy to miss. When you convert E01 to raw, the header metadata does not travel. Export the tool's report of the header fields into the sidecar first. When you convert raw to E01, the case fields and the date recorded in the new header describe the conversion, not the original acquisition. Note that in the case log, so that nobody later reads the E01's date as the acquisition date.

## Case exercises (fictional)

The organisations, people and records below are fictional. They are written as paper receipts and contain no tool output.

### Case 1: the intake "mismatch"

Harbourline Freight (fictional) sends the laboratory an E01 image of a laptop drive. The evidence receipt reads:

| Field | Entry on the receipt |
| --- | --- |
| Case / item | HLF-2026-031 / item 03, internal SSD |
| Format | E01, segment files `HLF031-03.E01` to `HLF031-03.E07` |
| Media MD5 recorded at acquisition | Value M |
| Media SHA-256 recorded at acquisition | Value S |
| Segment file hashes | Not recorded |
| Dispatched / received | 12 Nov 2026 / 14 Nov 2026, sealed bag HLF-B-118 |

An intake technician computes SHA-256 of `HLF031-03.E01`, finds that it is not value S and writes "evidence altered in transit" on the intake form.

*Work it through.* The technician compared a container hash of one segment with a media hash of the whole stream. The mismatch is expected and says nothing about alteration. The correct checks are: confirm all seven segments are present, run the tool's E01 verification and compare the media MD5 with value M, and compute SHA-256 of the decoded stream and compare it with value S. Because the sender recorded no segment file hashes, a transfer check per file is not possible. That gap goes on the intake form and back to the sender as a procedural improvement. The technician's note must be corrected by a dated addition, not erased.

### Case 2: the split raw image with a gap

Tarangini Textiles (fictional) supplies a split raw image. The receipt lists four pieces: three of 2,147,483,648 bytes and a last piece of 1,073,741,824 bytes, total 7,516,192,768 bytes, with a whole-stream SHA-256 of value T. The delivery drive holds `.001`, `.002` and `.004`, totalling 5,368,709,120 bytes.

*Work it through.* The size check alone shows that 2,147,483,648 bytes are missing, exactly one full piece, and the names show which. The whole-stream hash cannot be checked, and nobody should try to "repair" the stream by padding or reordering. Record the discrepancy, keep the delivered pieces sealed as received and request the missing piece from the sender's verified master. Once `.003` arrives, hash the four pieces joined in order and compare with value T.

### Case 3: choosing a format

Meridian Co-operative Credit Society (fictional) needs a 1 TB internal disk preserved for a long retention period. Archive space is limited, and an external reviewer, whose tools are not yet known, may need a copy. The disk is not encrypted and is mostly empty.

*Work it through.* E01 is attractive here: a mostly empty, unencrypted disk should compress well, and embedded metadata helps a future archivist. The unknown reviewer is a compatibility risk, but it can be managed. Record the media hashes externally, and if the reviewer needs raw, export the stream and verify it against those hashes. If the disk had been fully encrypted, the space argument would weaken considerably. Either way, write the reason for the choice in the case log.

### Case 4: the header that disagrees with the receipt

Kestrel Diagnostics Ltd (fictional) hands over an E01 image with this receipt:

| Field | Entry on the receipt |
| --- | --- |
| Case / item | KDL-2026-114 / item 02, USB external disk |
| Acquired | 03 Nov 2026, 10:40 IST, by examiner R. Iyer |
| Format | E01, single segment `KDL114-02.E01` |
| Media MD5 / SHA-256 recorded at acquisition | Value K1 / value K2 |

The examiner's tool reports these header fields: case number `KDL-2026-141`, examiner `R. Iyer`, acquisition date 02 Nov 2026 23:10. Verification of the stored MD5 passes, and a SHA-256 of the decoded stream equals value K2.

*Work it through.* The media hashes agree with the out-of-band receipt, so the stream is the one recorded at acquisition. The header differences are a separate question. The case number looks like a transposition when it was typed. The date is 11 hours 30 minutes earlier, which could be a clock on the acquiring computer set to another time zone or simply wrong. Neither explanation is proven by the image. Record both differences on the intake form, ask the acquiring examiner to explain them from their contemporaneous notes and add that explanation to the case log. Do not edit the header to make it agree, because that would create a new, undocumented version of the exhibit.

## Common mistakes and misconceptions

- **Comparing an E01 file hash with a source hash.** This produces a mismatch every time and proves nothing.
- **Treating "verification passed" as proof against tampering.** The stored hash is inside the file it describes. Compare with the external record.
- **Treating header metadata as authenticated.** It is what someone typed or what a clock said.
- **Losing a raw image's sidecar.** The bytes survive and the context does not.
- **Ignoring the last segment.** In E01 it carries the stored hash and closes the image.
- **Promising storage from compression.** Ratios follow content. Encrypted media barely compresses.
- **Calling a logical evidence file an image.** It holds selected files, not the media stream.
- **Believing the format decides admissibility, or that a tool is "approved".** NIST's Computer Forensics Tool Testing programme publishes test reports on specific tool versions against its test specifications. It does not certify tools in general, and this course makes no claim that any tool is validated. Admissibility questions under Indian law are covered in Module 1, not decided by a file extension.

## Security implications, detection and defence

An image contains everything that was readable on the source: personal data, stored secrets, confidential business records and deleted material. Treat it as at least as sensitive as the original device. Data-protection duties, such as those under India's DPDP Act 2023, and confidentiality obligations may apply to it; how they apply in a given case is a question for your organisation's legal adviser, not for the file format. Store images encrypted at rest, restrict access to named case staff and log that access. Ex01's optional encryption is one mechanism. Encrypted evidence storage, covered in the Storage lesson, is another.

Detecting tampering depends on records the image cannot rewrite: media hashes on the signed receipt and in the case log, kept on separate, access-controlled storage, with periodic re-verification of archived images against those records. A verification result that changes between two checks with no recorded handling event is an incident to investigate, not a curiosity.

Image files from outside the laboratory are also untrusted input to complex parsers. Keep forensic tools updated, open external images on isolated analysis workstations and never open evidence images in a mode that can write to them. Work on a verified working copy, as stages 4 and 5 of the transcript show. That way, an accidental change is detectable and the verified image remains untouched.

## Best practices

1. Record the media hash, using SHA-256 and any legacy algorithm your procedures require, outside the image at acquisition time.
2. For raw images, create the sidecar at acquisition: hashes, piece count and sizes, total size, error log, case details.
3. For E01 images, check that the header fields match the receipt and that every segment is present before verifying.
4. Verify by media hash. Use container hashes only for transfer and storage checks, and record them per segment file.
5. Treat every conversion as a new copy: document it, verify it against the acquisition record, and keep the original until that verification succeeds.
6. Confirm that the recipient's tools read the chosen format and variant before dispatch.
7. Write the format policy down and record in each case why it was applied.

## Sources and limits of this lesson

- NIST SP 800-86, *Guide to Integrating Forensic Techniques into Incident Response* (https://csrc.nist.gov/pubs/sp/800/86/final): collection with integrity preservation and use of message digests to verify copies.
- SWGDE, *Best Practices for Computer Forensic Acquisitions* (17-F-002, https://www.swgde.org/documents/published-complete-listing/17-f-002-2-1/): verification and documentation as part of acquisition.
- NIST Computer Forensics Tool Testing programme: test specifications and reports for specific tool versions. These are not general certification.
- E01 section names (including the error section), chunk size defaults and checksum details follow the libewf project's public description of the format and are simplified here. Individual tools may differ.
- The only lab output in this lesson is the C09 kit transcript reproduced above. Statements about a hypothetical E01 of the same stream are reasoning, not observed output.

## Key takeaways

- A raw image is the media stream and nothing else, so its file hash is the media hash. Everything else about it lives in sidecar records.
- An E01 image wraps the media stream in segments, compressed chunks, metadata, tables and a stored hash. Its file hash is a container hash.
- Compare only media hashes with the acquisition record. Use container hashes for transfer checks.
- Embedded metadata and stored hashes are records written by software, not seals. Keep the authoritative hash outside the image.
- Choose the format by written policy, record the reason, and verify every conversion as a new copy.
