## What an image represents

A finance team finds two different versions of an invoice register in its shared folder. The investigator is authorised to examine the register and its immediate history. The laptop that synchronised the folder also contains years of unrelated personnel records. Someone proposes copying the entire disk because a complete image sounds like the safest choice. What would that copy preserve? Would it answer the question? Is the investigator authorised to collect it? These are three different decisions. This lesson uses a fictional document dispute and the Academy's file-based lab to show how to make each decision explicit.

A forensic image represents the bytes an acquisition method could read through a particular interface, within a stated range and under stated conditions. Imagine placing a numbered sheet over a device's exposed storage addresses. A successful raw image of that range has a corresponding position for each readable byte. A copy of a named file has a different promise. Its first byte is the first byte the file system returned for that file. Its position in the copy tells you nothing by itself about the file's original disk address. Neither promise says who wrote an invoice or when a person read it.

At intake, give the source a durable identifier and state the question in terms of observable evidence. “Find out what happened” is difficult to turn into a scope decision. “Compare the two surviving versions and determine whether the available history records a change to the bank-account field between Monday and Wednesday” is more useful. Now a reviewer can distinguish sources that might answer the question from sources that simply happen to be available. A server-side version history may be more informative about this change than a large local disk image.

## Choose a collection boundary

A device-level acquisition reads an address range presented by a device or another source, such as a disk image used for training. The result can include partition metadata, file-system structures, allocated file contents and sectors that the file system regards as unallocated. Whether any deleted file can be recovered depends on what those sectors contain at collection time. Reuse, device behaviour, encryption and unreadable regions all matter. Promise the address range actually captured rather than a recovery result that only a later examination could establish.

A volume-level image may capture a complete logical address range inside a partition or mapped volume. In that sense it can include unallocated space *within the volume*. A file-level logical acquisition reads selected objects through a file-system or application interface. Those are distinct uses of the term “logical”. If the acquisition note only says “logical image”, ask how bytes were selected. A copy of one mounted volume's address space and a directory of named documents may both come from the same laptop, yet support very different examinations.

Suppose the relevant register lives on an encrypted volume. A copy made through an authorised unlocked file-system view can contain readable document bytes. An image of the underlying encrypted sectors can contain ciphertext at the corresponding physical addresses. Both copies can be technically sound. Their hashes need not agree because they represent different inputs. Record the interface that supplied each stream and which view was available at the time. If a recovery process or professional decision about live collection is necessary, refer it to the assigned examiner under the case authority.

A targeted export may be more proportionate and more informative. A document service can expose revision identifiers and server-side timestamps that never appear on the synchronised laptop. Conversely, a current-version export might omit earlier revisions or locally staged changes. Ask what the export includes before choosing it. Record the account or service role used, the selection criteria, the time zone, the export time and any stated retention window. A missing revision outside that window cannot show that the document was never edited.

## Separate the source, the master and the working copy

The source is the object or interface you received authority to acquire. The preserved master is the accepted acquisition retained under the case's storage controls. A working copy is derived for examination. Use meaningful case identifiers for all three. File names alone are unreliable identifiers when multiple directories contain a file called image.dd. Record the relationship explicitly, for example that work item W1 was created from master M1, which represents the acquisition of source S1. Each relationship should have an operator, time and verification record.

A transfer and a verification are different events. A status display that says “copy complete” may establish that the program reached its end without a reported error. It does not establish that you selected the correct source or that the destination contains the bytes you intended. A digest recorded from a stream as it is copied is useful. Reading back the destination and independently computing its digest checks a different part of the path. Record which object each calculation read and when. If a tool reports a verification pass, find what it compared before explaining it to someone else.

Read this figure from the authorised source at the top to the review copy at the bottom. The first box is deliberately a decision about scope. Before an operator can promise a match, the operator needs to know what is to match what. For the invoice case, that might mean a versioned export of two files. The second box represents the acquisition as a read from that chosen boundary. Place a source identifier, a description of the interface and a count of readable bytes next to it. If two examiners used different interfaces to the same underlying storage, those labels prevent them from presenting different byte streams as contradictory copies of a single object. The next box concerns the preserved master. Its strongest evidence is an independent read of the stored result compared with the expected digest for the same stream, together with the log of any read or write errors.

The bottom box is where examination begins. Its separate position matters when a review tool changes a derivative. In the training fixture the working copy changes by a single byte. The resulting mismatch calls for a note about that derivative and a check of the preserved master. It does not, by itself, show that the original source was altered. Follow the identifiers back up the diagram to find the object whose integrity can actually be tested.

Try tracing a second route mentally. If there were no stored source length and the operator selected only half the authorised range, the last two boxes could still agree perfectly. A matching copy of a truncated stream remains truncated. The top two boxes therefore supply information that the hashes in the bottom two cannot recover. A peer reviewing the receipt should be able to ask both questions independently: did the method collect the right thing, and did the stored bytes survive the transfer?

## Interpret partial reads and gaps

A device may report errors at some addresses while returning bytes normally elsewhere. Different tools and settings can retry, stop, skip a range or substitute a pattern. A later reader of a flat image may be unable to distinguish a substituted zero from a zero actually returned by the device. The acquisition log therefore belongs with the output. It should identify affected ranges and the tool's handling of those ranges. If error information was lost, say so. Treat claims about content in those regions as unresolved.

Consider an examiner who receives an image of the expected length and a SHA-256 digest that matches the acquisition report. The report also lists two unreadable sectors replaced with a documented fill pattern. The image may be a verified copy of the *produced stream*. It still contains two regions for which the source bytes were not obtained. Keep both facts in the conclusion. A reviewer interested only in a document stored elsewhere may be able to use the image despite the limitation, while a reviewer whose question concerns those very sectors cannot answer it from this acquisition.

There are also gaps that produce no error message. A mounted volume may exclude another partition, a storage service may return only the current version, or a file-level method may omit timestamps or permissions. These are properties of the chosen method, not necessarily tool failures. State exclusions in ordinary language. “No earlier copy was in the two-version export supplied by the service” gives a reader a narrower and more supportable answer than “no earlier copy existed.” For a changing source, the time needed to read the selection also matters; its beginning and end need not describe one instantaneous system state.

## Compare two proposed acquisition receipts

Receipt A reads “Full image copied and verified. No issues.” Receipt B gives the source identifier, the interface, the selected extent, the start and finish times, the tool and version, the number of bytes returned and the method used to read back the master. It lists one unreadable extent and links to the error log. B describes a limitation. It nevertheless provides a better basis for review because a second examiner can determine whether that limitation affects their own question. A cannot support even the claim of completeness until the missing details are restored from reliable records.

Ask a partner to test B against a different question. The first investigator may care only about the final invoice document, while the second wants to compare the history of a separate account on the same system. Scope sufficient for the first question may exclude the evidence needed for the second. The second examiner should request additional authority or another source through the case owner. A technical ability to read more data is not a change to the scope already recorded. Note requests and decisions separately from the actions an operator actually performed.

Time is another common source of ambiguity in receipts. An export's creation time, a document's recorded modification time, and the time the examiner received the file describe different events. Include an explicit UTC offset or agreed time zone for each and preserve the original value where appropriate. If a source clock was not checked, avoid rounding a comparison into a claim that one action necessarily happened first. For the invoice case, service revision identifiers may answer an ordering question more directly than two workstation clocks that have never been compared.

## Exercise and model reasoning

Read this fictional receipt: “Source S4, finance share export, Monday at 09:00; master and review copies match. The submitted file is the only invoice ever created.” List three questions before accepting the final sentence. You could ask whether the export includes deleted versions, which directories or service accounts it covers, and whether the operator compared the result with any independent revision history. You could also request the time zone and byte counts. Matching copies support continuity of the selected export. They give no basis for a claim about every invoice ever created.

For a second exercise, imagine that the working copy matches the expected value but the master in storage does not. Write a first response that preserves both objects. An appropriate response records the identifiers, algorithms, reader settings and observed digests, retains the discrepant files, and asks for an independent read of each from its documented location. Check that the expected value belongs to this case item before interpreting the mismatch. Neither object becomes the preferred source simply because its name says master or because the analyst has already examined it.

Finally, give a colleague your acquisition decision for the two-version invoice dispute. Identify the source most likely to distinguish the two versions, one reason an additional source might be required, and one conclusion that must remain open. A strong answer begins with the authorised server revision history, asks whether local unsynchronised changes matter, and leaves the identity of the person making an edit open unless a separate reliable record supports it. The colleague should be able to follow your evidence choices without assuming that a hash, a login name or an accurate clock proves personal authorship.

## Key takeaways

Name the object, interface and boundary before comparing digests. Preserve the acquisition log alongside the master and distinguish a verified output from a complete source. Record unreadable regions, known exclusions and uncertainty about changing systems. The most useful acquisition receipt tells a later examiner which questions the evidence can answer and where an additional source is necessary.
