## Introduction

A SOC automation programme needs metrics that explain whether responders are doing better work and where the process is failing. The number of runs alone describes activity. It does not reveal whether cases were handled faster, whether scoped protective actions took effect, or whether missing evidence was accidentally treated as a negative result. Decide what the metric should help a particular owner change before choosing how to calculate it.

There are three useful populations: incoming work, executions and verified effects. Incoming work includes the eligible cases or alerts under review. Executions include delivery attempts, replays and tests. Effects are the distinct actions shown to have happened within approved scope, such as one case draft or a confirmed protective change. Their counts need not be equal. In fact, a workflow can correctly receive two events, run three times and produce only one new prevention effect. When those figures appear without labels, a reader may mistake repeat processing for greater protection.

## Define time intervals

An incident team might measure from alert receipt to case assignment, from approval request to recorded decision, from approved execution request to observed effect, or from observed effect to independent verification. These intervals describe different bottlenecks. Record timestamps for events with well-defined meanings. If a change to the platform collapses ?requested? and ?verified? into a single time field, a historical comparison can show an apparent performance improvement while removing the time required to prove the outcome. Document the event definition and schema version beside the metric.

Use a common time standard and pay attention to late events. Occurrence time comes from the source. Receipt time describes when the intake recorded delivery. Execution start time is an engine event. A source record may be generated well before it is delivered and may have an unreliable clock. Calculate automation latency using known engine or intake timestamps, and preserve source time when analysing detection delay. A negative result should trigger a data-quality check rather than silently being converted to zero. Differences in collection can be more diagnostic than the headline summary.

Define when to treat a pending result as still open. If an event has no verification timestamp, do not make its latency zero. It is an incomplete observation. A useful report provides the count of pending cases and the oldest age alongside latency statistics for verified cases. Otherwise slow or difficult cases disappear from the summary because they are the ones still open. An operational owner can compare the aged pending set with the approved escalation time and act on the relevant cases.

## Select and label denominators

A rate needs a numerator and a denominator that apply to the same population. For example, a verified action rate for approved requests equals verified unique actions divided by unique approved requests in a defined set. That is different from successful runs divided by all executions. It excludes denied actions from the first denominator because no action should happen for them. It does not imply denied decisions were unimportant. Track denials and expiries separately to see where the requests or approver availability need review.

For routine case creation, decide whether a duplicate receipt should count as incoming workload. Counting it helps the engine owner understand delivery pressure. It should not count as a second primary case unless evidence supports that distinction. Report both the delivery count and unique event count if the difference matters. An intake change that reduces duplicate deliveries can lower execution count without reducing coverage. Conversely, a retry bug can inflate successful run figures while creating unnecessary case work. Use identifiers that track unique intent for case effects and separate run IDs for engine work.

Consider what happens when one report mixes training runs, dry-runs and live case data. A mock workflow can complete quickly because it uses a local fixture. Including it in the same latency distribution as approved operations can mislead. Record environment and cohort. In the Academy lab, explicitly label every simulated result. In operations, compare cases with similar policy, urgency and routing, or publish separate groups. If there are too few comparable observations, state that and include the sample size rather than claiming a trend.

### Visual Walkthrough & Architectural Breakdown

The first row is an intake interval. It begins at a recorded receipt and ends at assignment to an owner. A successful lookup can speed that assignment, but a missing field may route it to a review queue. The measure describes elapsed time to ownership and can be meaningful even before a protective action is proposed. The next row is the approval interval. It starts when an eligible person can actually review the request and ends at the recorded decision. If the lead never responds, keep the request in the pending or expired counts. An accurate approval histogram should not make unreviewed requests disappear.

The third row concerns confirmed execution. It starts at the moment the authorised service received or accepted a scoped request, and stops when a source reports the expected effect. The next row measures verification. For some controls a result from the target service may provide adequate verification; for another operation a separate reviewer must check scope and state. The table separates the timestamps so teams can identify which stage needs attention. It also shows why a completed green execution is insufficient by itself. The engine can finish after queuing the response even while the target has not applied it.

The final row concerns quality. Outcomes such as rework, duplicates and unwanted effects should be tracked alongside speed. Imagine the intake system cuts assignment time from ten minutes to four by discarding alerts for unknown devices. A raw speed chart would improve for retained cases. A quality review would show unhandled eligible alerts and a lower coverage rate. This figure encourages the reader to pair latency with case accounting. A good dashboard should let an owner trace an anomaly back to the relevant source and correct the real bottleneck or control error.

## Work a small metric example

Take a fictional shift with ten unique eligible alerts received as thirteen delivery attempts. Three deliveries repeat earlier event identifiers. Nine of the ten eligible alerts produce confirmed case drafts or valid links, and one remains in review because the asset cannot be resolved. The report can say that all thirteen deliveries were recorded, ten unique alerts were eligible, nine have confirmed case routing and one is open. The ratio for confirmed routing among eligible alerts is nine tenths, or 90 percent, at the reporting time. Eleven or thirteen as a denominator would answer a different question. Use an explicit cutoff and show the open item separately.

Now suppose that four cases led to scoped protective requests. One was denied, one expired, and two were approved. One approved action is verified, and the other is acknowledged but not confirmed effective. A verified effect rate among approved requests is one of two, or 50 percent, at the recorded cutoff. Across all four requests the outcome distribution is one denied, one expired, one approved with unverified effect and one verified. Showing both views tells the lead which case needs further action. A workflow score based on how many cases reached an approval screen would not say whether protection occurred.

Next compare intake latency for five finished cases. Their assignment intervals in minutes are 2, 3, 4, 9 and 25. The median is 4 minutes. The mean is 43 divided by 5, or 8.6 minutes. The difference prompts an owner to review the longer cases rather than declaring the average typical. A single pending case at 40 minutes is a different observation and should be listed as open for 40 minutes at the cutoff. Do not add it to the finished latency distribution as if assignment had occurred. If the audience needs a percentile for a small sample, document the chosen calculation or show the exact ordered times.

## Pair speed with outcome quality

A faster process can create more mistakes if it reduces the evidence available to an approver. Add a measure for rework or overturned decisions. For example, sample cases the intake workflow labeled ready and check whether their evidence references are present, their destination is permitted and their grouping is sound. A single duplicate case audit is more useful if it explains the key mismatch, scope and owner. Define the sampling frame so the reader knows whether it includes only easy cases or a representative set.

Track exceptional outcomes that should remain rare. An effect outside approved scope is an incident to review rather than a small percentage to smooth away. A duplicate response effect should lead the workflow owner to inspect the repeat behaviour and whether the initial effect was reconciled correctly. Watch for unknown reason codes, manual work hidden outside the case store and late follow-up from dependencies. A strong dashboard has stable categories and points to evidence that supports action. Time series should be understandable when mapped back to changes in the process.

Avoid creating incentives to declare fewer open cases at the cost of accurate reporting. If a team measures only time to closure, operators may close cases while verification is outstanding. Pair closure time with the count of reopened cases, delayed verification or remaining exposure. A quarterly review can compare shifts or process revisions using the same definitions and include case mix or severity where it changes the interpretation. The point is to improve decision quality and capacity, and the numbers are a way to test that improvement.

## Report results to different owners

An incident lead needs a short view of current pending requests, age, severity context and owners. A workflow engineer needs branch counts, source failures, retries, unclassified states and affected versions. A privacy or governance reviewer may need approval audit completeness and evidence of controlled sharing. Each view can come from the same underlying records with different aggregation and access. Do not build a management view that contains raw employee information by default. Use the case reference when a restricted reviewer needs individual details.

Summarise what changed after a workflow revision. For example: ?Median assignment time fell in the approved comparison cohort, and verified case routing remained above the earlier baseline. Unknown ownership cases remain open in two locations, with the inventory owner investigating.? The sentence distinguishes the overall metric from an outstanding gap. Attach the measurement interval, sample size and definition. Include data exclusions known to affect comparisons. If source collection changed during the comparison, call out that change rather than attributing every difference to the automation engine.

## Exercise and acceptance criteria

Use the fictional shift results above to write a one-page dashboard proposal. The first section reports intake volume, unique alerts, repeats and documented dispositions. The second uses two time intervals with exact endpoints and gives an owner for open cases. The third reports the approval and verified-effect distribution and includes one example of a harmful incentive. Build a compact set of notes a manager could read without seeing any individual identifiers.

Give the draft to a peer. Ask them to calculate the routing rate and verified action rate using your definitions. If they choose a different denominator, clarify the population. Ask them to find the review cutoff and identify how an open case enters the report. Finally, provide a new variation in which the formerly open intake case is assigned to an analyst after the cutoff. The case should appear open in the original report and assigned in a later report. That sequence is correct even if it increases the later sample's assignment latency. Review the result as evidence of honest process measurement.

## Use a worksheet to compare two shifts

Suppose the site pilots automatic assignment on one shift while another continues with manual intake. A direct comparison of elapsed time can mislead if one shift receives fewer high-impact cases or a different alert source. Define which inputs were eligible for both methods, how you establish comparable work, and what time window is justified. You may want to show each workload mix and stratify by source or priority before drawing an overall conclusion. This makes the exercise more honest than declaring whichever median is smaller to be the better process. Where a difference in coverage cannot be accounted for, report it as an uncertainty.

For the first shift, also record the fraction of cases with complete source and owner references after assignment. This fraction measures a concrete quality attribute needed by the oncoming analyst. For the second shift, apply the same definition. Note how pending work appears alongside both denominators. An increase in automation throughput accompanied by missing evidence can make later case investigation slower. Ask a reviewer to inspect a few cases from each path and count which actually fulfilled both ownership and traceability criteria. The numerical summary should not substitute for this evidence.

Treat a sudden change in event counts as a diagnostic clue. It can be caused by a change in eligibility, a new duplicate sender, a source that stopped reporting, or a correction to counting. A revised dashboard should record the schema and processing revision. If the result uses different data definitions, include separate time series or describe the break in comparability. In a monthly review, show the measure owner and next investigation for any unexplained change. A graph without provenance may suggest a security trend when the underlying problem was evidence collection.

## Work one additional quality example

In a fictional validation sample, compare six routed alerts. Five have evidence and owner attached, while the sixth has only an assigned queue. The routing count is six if the assignment state is confirmed. The completeness count is five. A detail review shows the sixth event came from a source that changed its identifier format. That result gives the workflow owner a likely correction and a new regression case. Do not change the definition of completion simply to make the two counts align. State that assignment remains valid and evidence linkage is incomplete.

Now imagine the missing case was excluded from the sample because only fully populated records were eligible for export. The apparent completeness rate becomes one hundred percent but the real failure has disappeared from measurement. Trace where the export filters records and choose a denominator that accounts for those failures. A governance reviewer can require open and malformed records to appear in a separate total. This is one practical way to prevent improving a dashboard by narrowing its view while no operational problem has been solved.

Discuss who will track the exceptions and what response they require. The receiving queue may already have enough information to act manually, while the workflow owner corrects the mapping. Assign both responsibilities explicitly. A dashboard should help people decide whether they need to pause a workflow, fix a source or simply change the documentation. If a measure cannot distinguish those choices, define a smaller set of diagnostic signals that can be tied back to the actual decisions.

## Key takeaways

- Define the population, recorded endpoints and cutoff before reporting a number.
- Distinguish delivery attempts, unique incoming work and verified effects.
- Preserve open work, data gaps and reason codes alongside completed-case statistics.
- Check whether gains in speed preserved quality, coverage and scoped authority.
