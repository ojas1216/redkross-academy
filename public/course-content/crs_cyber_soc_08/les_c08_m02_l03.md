## Introduction and conceptual foundation

Every meaningful action in an organisation's IT estate is carried out by an identity: a person, a service account, a workstation's computer account, an application registered in a cloud tenant. Before that identity can read a file, approve a payment or change a firewall rule, some system has to decide who it is (**authentication**) and what it may do (**authorisation**). Identity logs are the records those systems keep of their decisions. They answer questions no other telemetry source answers as directly: who tried to get in, from where, using which method, whether they succeeded, and what kind of session they were given.

For a long time the SOC's attention centred on malware and network traffic. That balance has shifted. Attackers increasingly *log in rather than break in*: a stolen or guessed password, a session token lifted from a browser, or an approved multi-factor prompt gives them a legitimate session that looks, at the network and endpoint level, like normal work. MITRE ATT&CK captures this in technique **T1078 Valid Accounts**, which appears under several tactics (initial access, persistence, privilege escalation and defence evasion) precisely because a valid account serves the attacker at every stage. When an adversary uses valid credentials, the only place the deception is visible may be the identity trail: an unusual source address, an unusual logon type, a burst of failures before the success, or a new authentication method registered at three in the morning.

This lesson covers the three families of identity telemetry a SOC analyst meets daily:

1. **Windows and Active Directory authentication events**, written to the Security event log on workstations, servers and domain controllers.
2. **Identity provider (IdP) sign-in logs** from cloud directories such as Microsoft Entra ID (formerly Azure Active Directory) and similar services, which record sign-ins to cloud and SaaS applications along with multi-factor and conditional access results.
3. **Remote access logs**, in particular VPN authentication records, which sit at the boundary between the internet and the internal network.

The previous lessons in this module covered endpoint logs (what ran on a host) and network logs (what crossed the wire). Identity logs connect those two worlds to a *person*. Lesson 5 will look at event fields in general and Lesson 6 at timestamps; here we focus on what identity events mean, where each one is written, and how an analyst reads them during triage. Throughout, the worked examples use the course dataset for the fictional Banyan Microfinance (`LAB_ASSETS/C08/banyan_events.jsonl`), which contains 13 Windows Security events and 10 VPN events among its 340 records.

> [!NOTE]
> Identity logs record *claims that were checked*, not intentions. A successful logon proves that the correct secret was presented, not that the rightful owner presented it. Much of identity analysis is the work of deciding whether a technically valid authentication was a legitimate one.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Authentication | Verifying that an identity is who it claims to be, for example by checking a password, certificate or second factor. |
| Authorisation | Deciding what an authenticated identity may access or do. |
| Identity provider (IdP) | A service that authenticates users and issues assertions or tokens that applications trust, such as Microsoft Entra ID or an on-premises AD FS server. |
| Logon session | The security context Windows creates after a successful logon; identified locally by a Logon ID. |
| Logon ID | A hexadecimal identifier for one logon session on one machine, used to tie a logon event to later events in the same session and to its logoff. |
| Logon type | A number in Windows logon events describing *how* the logon happened (at the console, over the network, as a service, through Remote Desktop, and so on). |
| Kerberos | The default authentication protocol in Active Directory domains; the domain controller's Key Distribution Centre (KDC) issues a ticket-granting ticket (TGT) and then service tickets. |
| NTLM | An older challenge-response authentication protocol still used when Kerberos cannot be, for example when a server is reached by IP address or outside the domain. |
| Sign-in log | An IdP's record of an authentication attempt to an application, including outcome, client, location and MFA or policy result. |
| Conditional access | Policy evaluated at sign-in time that can require MFA, block access or require a compliant device based on conditions such as location or risk. |
| Password spraying | Trying one or a few common passwords against many accounts, staying under per-account lockout thresholds (ATT&CK T1110.003). |

## Windows authentication events

Windows records authentication activity in the **Security** event log, provided the relevant audit policy subcategories are enabled (Logon, Logoff, Special Logon, Credential Validation, Kerberos Authentication Service and Kerberos Service Ticket Operations among them). Course 03 Module 7 covered audit policy configuration; here we concentrate on reading the events.

The single most important idea is **where each event is written**. An authentication in a domain involves at least two machines, the one being logged on to and the domain controller that vouches for the account, and each writes its own, different event. Analysts who search for a user's logons only on domain controllers, or only on workstations, see half the picture.

### The core event IDs

| Event ID | Meaning | Where it is written |
| --- | --- | --- |
| 4624 | An account was successfully logged on | The machine that was logged on to (workstation, server, or a DC when the DC itself is the target) |
| 4625 | An account failed to log on | The machine where the logon was attempted |
| 4634 / 4647 | An account was logged off / user initiated logoff | The machine that held the session |
| 4648 | A logon was attempted using explicit credentials | The machine where a process supplied different credentials (for example "run as") |
| 4672 | Special privileges assigned to new logon | The machine logged on to, when the new session holds administrator-equivalent privileges |
| 4768 | A Kerberos authentication ticket (TGT) was requested | Domain controller |
| 4769 | A Kerberos service ticket was requested | Domain controller |
| 4771 | Kerberos pre-authentication failed | Domain controller |
| 4776 | The computer attempted to validate the credentials for an account (NTLM) | The machine holding the account database: a DC for domain accounts, the local machine for local accounts |
| 4740 | A user account was locked out | Domain controller (for domain accounts) |

Account-management events are not authentication events, but they belong in the same mental drawer because attackers who obtain an identity often create or empower another one: **4720** (a user account was created), **4728** and **4732** (a member was added to a security-enabled global or local group respectively), and **1102** (the audit log was cleared). The Banyan dataset contains 4720, 4732 and 1102 on WS-104 within an hour of one another, which is the core of CASE-0001 from Module 1.

### Reading a 4624: subject, logon information and new logon

A 4624 record is divided into sections, and confusing them is a classic beginner's error.

- **Subject** identifies the account *on the local machine* that requested the logon. For a network logon this is usually the null SID or the machine itself; for an interactive logon it is often the local system's account. It is not the user who logged on.
- **Logon Information** carries the **Logon Type** and, on current Windows versions, fields such as whether the token is elevated and whether the logon was a restricted-admin or virtual account logon.
- **New Logon** identifies the account that was actually logged on: account name, domain, the **Logon ID** of the new session, and a Logon GUID that can link the session to Kerberos events on the DC.
- **Process Information** names the process that requested the logon.
- **Network Information** gives the workstation name, **source network address** and port where the request came from. For an interactive logon at the console this is empty or a dash, which is exactly what the Banyan dataset shows (`"src_ip": "-"`).
- **Detailed Authentication Information** names the logon process and the **authentication package** (Kerberos, NTLM or Negotiate), plus the NTLM version where relevant.

When you correlate, the Logon ID is the key that ties a 4624 to the 4672 that may follow it (the session got admin privileges), to object-access or process-creation events in the same session, and to the 4634 that ends it. It is local to one machine and resets on reboot, so it is never a cross-host identifier.

### Logon types

The logon type tells you *how* an account arrived, and it often matters more than the account name.

| Type | Name | Typical cause |
| --- | --- | --- |
| 2 | Interactive | Keyboard and screen at the machine itself |
| 3 | Network | Access to a share, a printer, or a remote management interface over the network |
| 4 | Batch | A scheduled task running under stored credentials |
| 5 | Service | A service starting under its configured account |
| 7 | Unlock | Unlocking a locked workstation |
| 8 | NetworkCleartext | Network logon where the password was sent in clear to the authenticating service (for example basic authentication to IIS) |
| 9 | NewCredentials | A process cloned the current token but uses different credentials for outbound connections ("run as" with the network-only option) |
| 10 | RemoteInteractive | Remote Desktop / Terminal Services |
| 11 | CachedInteractive | Interactive logon using cached domain credentials when no DC was reachable |

Baselines are built per type. A finance workstation will show many type 2 and type 7 logons by its owner, some type 3 logons from management servers, and type 5 for services. A type 10 logon to that workstation from another user's laptop, or a type 3 logon by a service account that normally only ever produces type 5, is the kind of deviation that deserves a look. Every Windows logon in the Banyan dataset is type 2, one per user per workstation in the morning, which is what a quiet, office-based estate should look like.

### Failure reasons in 4625

A 4625 carries a **Status** and **Sub Status** code explaining why the logon failed. A handful are worth recognising on sight:

| Code | Meaning | What it suggests |
| --- | --- | --- |
| 0xC000006A | Correct user name, wrong password | Typing errors, or guessing against a real account |
| 0xC0000064 | User name does not exist | Guessing account names, or a stale script |
| 0xC0000234 | Account is locked out | Lockout already triggered; something kept trying |
| 0xC0000072 | Account is disabled | Use of a leaver's or decommissioned account |
| 0xC000006D | Generic "bad user name or authentication information" | Look at the Sub Status for the specific reason |

The difference between 0xC000006A and 0xC0000064 is analytically valuable. A burst of 0xC0000064 failures means someone is trying names that do not exist, which legitimate users rarely do. A burst of 0xC000006A across many different accounts means someone knows (or has guessed) valid names and is trying passwords against them.

### Kerberos and NTLM events on the domain controller

When a domain user signs in at a workstation, the workstation does not check the password itself. It asks the domain controller. With Kerberos, the client first sends an **AS-REQ** to the KDC; if pre-authentication succeeds, the KDC returns a TGT and writes **4768** on the DC. The client then requests a service ticket for each service it uses, including the workstation itself, and the DC writes **4769** for each. Only when the target machine accepts the service ticket does *that* machine write **4624**. If the password is wrong, the DC writes **4771** (pre-authentication failed, typically with failure code 0x18) or a 4768 with a failure result, and the workstation writes **4625**.

Two fields in these DC events are worth knowing. The **Client Address** shows which machine asked for the ticket, which turns the DC into a central record of where each account is being used across the estate. The **Ticket Encryption Type** in 4769 shows which cipher protects the service ticket; modern domains use AES (0x12 for AES256), and a burst of 4769 requests for many service accounts using RC4 (0x17) from one client is a well-known signal of an attempt to obtain service tickets for offline password cracking (ATT&CK T1558.003, Kerberoasting). The defence is strong, long, managed service-account passwords and removing RC4 where possible; the detection is exactly this field.

NTLM is different. The server that receives an NTLM logon passes the challenge-response to the machine that owns the account, and that machine writes **4776**. For a domain account this is a DC; for a local account it is the server itself. NTLM leaves no ticket trail, so the 4776 on the DC and the 4624 (with authentication package NTLM) on the target are the evidence. A rise in NTLM use where Kerberos is expected is often worth investigating, because some credential-abuse techniques depend on it.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure shows a single, ordinary Kerberos sign-in and file-share access, and marks which event ID each step produces and on which machine. Its purpose is to make the analyst's first rule concrete: one human action leaves records in several places, and the evidence must be collected from all of them.

**Components.** There are four lanes. **Asha (user)** is the person at the keyboard. **WS-101 (workstation)** is her Windows client. **DC01 (domain controller)**, with the sub-label "KDC: AS + TGS", is the dark lane because it is the trust anchor for the domain. **FS01 (file server)**, sub-labelled "SMB share", is the service she uses later.

**Relationships and arrows.** The first arrow, "Ctrl+Alt+Del: user name + password", runs from Asha to WS-101: the credential enters the system at the console. The next arrow, "AS-REQ with pre-auth", goes from WS-101 to DC01, and the dashed reply "AS-REP: TGT (DC logs 4768)" returns. A second request, "TGS-REQ for host/WS-101", produces the dashed reply "service ticket (DC logs 4769)". The arrow "session created: 4624 type 2 on WS-101" runs from WS-101 back to Asha, showing that only now does the workstation record the logon. Later, "TGS-REQ for cifs/FS01" and its reply (another 4769 on the DC) precede the final arrow "AP-REQ: open share (FS01 logs 4624 type 3)" from WS-101 to FS01.

**Execution flow.** Read top to bottom: credential entry, TGT, service ticket for the workstation, interactive session, service ticket for the file server, network logon on the file server. A single morning sign-in followed by one share access therefore produces at least one 4768, two 4769s and two 4624s on three different machines.

**Decision logic.** The diagram shows the success path. If the password were wrong, the flow would stop at the second arrow: DC01 would write 4771 (or a failed 4768) and WS-101 would write 4625 with status 0xC000006A. If FS01 were reached by IP address rather than name, Kerberos could not find a matching service principal name and the client would fall back to NTLM, so DC01 would write 4776 instead of 4769 and the 4624 on FS01 would show the NTLM package.

**Technical interpretation.** The DC events describe *requests for tickets*, not sessions. The 4624 events describe *sessions*. That is why the logon type appears only on WS-101 and FS01: the DC does not know whether the ticket will be used at a console or over the network.

**Practical example.** Suppose an analyst sees a 4624 type 3 for Asha on FS01 at 02:00, when she is not at work. The figure says where to look next: a 4769 on DC01 for `cifs/FS01` around the same time will name the **client address** that asked for the ticket. If that address is not WS-101, the session did not come from Asha's desk.

**Security implications.** Collecting Security logs only from domain controllers gives the ticket trail but not the logon types or the target-side sessions; collecting only from workstations misses the central record of where an account is used. Both are needed, and the DCs are the minimum.

**Key learning.** In a domain, the DC records ticket requests (4768, 4769, 4771, 4776) and the target records sessions (4624, 4625 with a logon type); correlate them by account, time and client address.

### Linux and other systems

Linux authentication is recorded by PAM and the services that use it. On Debian and Ubuntu systems the classic file is `/var/log/auth.log`; on Red Hat-family systems it is `/var/log/secure`; on systemd hosts the same messages are in the journal. For SSH the lines that matter most are `Accepted password for`, `Accepted publickey for`, `Failed password for` and `Invalid user`, each followed by the account and the source address. The same reading rules apply: separate failures on real accounts from failures on non-existent ones, and note the method (password versus key) of each success, because a server that normally sees only key-based logons should not suddenly accept a password.

## Identity provider sign-in logs

When users sign in to cloud and SaaS applications through single sign-on, the authentication happens at the **identity provider**, not at the application. The IdP's sign-in log is therefore the authoritative record of access to every application federated with it. Microsoft Entra ID is the example most Indian enterprises meet, and its concepts transfer to other IdPs.

### What a sign-in record contains

An Entra ID sign-in record answers, for one attempt: **who** (user principal name and object ID), **to what** (the application and the resource), **from where** (IP address and the location derived from it), **with what** (client application, browser or operating system, and device details including whether the device is registered or compliant), **how** (the authentication requirement, single-factor or multifactor, and the methods used), **under which policy** (conditional access policies evaluated and their result) and **with which outcome** (a status and an error code on failure). A correlation ID ties together the several records that a single interactive sign-in can produce.

Entra separates sign-ins into categories. **Interactive user sign-ins** are those where the user presented a credential. **Non-interactive user sign-ins** are performed by a client on the user's behalf using a token it already holds, such as a mail client refreshing its access; they are numerous and easy to ignore, but they are where token reuse from an unexpected location becomes visible. **Service principal** and **managed identity** sign-ins record applications authenticating as themselves. Directory changes, such as a user being added to a role or a new MFA method being registered, are recorded separately in the **audit log**, which is the IdP's equivalent of 4720 and 4732.

Failure codes are specific to the IdP. In Entra ID, error **50126** means an invalid user name or password, the cloud counterpart of 0xC000006A. Rather than memorising lists, an analyst should keep the vendor's error-code reference to hand and learn the handful that dominate their own tenant's failures.

### Patterns in sign-in data

Because the IdP sees every application, it is the natural place to detect credential attacks:

- **Password spraying** (T1110.003): failures across many users from one source or a small set of sources, each user tried once or twice, often against legacy protocols that do not support MFA.
- **Brute force or guessing** (T1110.001): many failures against one account.
- **Credential stuffing** (T1110.004): many accounts, each tried with a different password taken from an earlier breach, typically from many sources.
- **MFA request generation** (T1621): repeated MFA push prompts to one user, hoping they approve one to make the prompts stop. The sign-in log shows a sequence of sign-ins that passed the first factor and then awaited or failed MFA, ending in a success.
- **Unfamiliar or impossible travel**: a success from a location or network the user has never used, or two successes from locations too far apart for the time between them. These are heuristics; VPNs, mobile networks and cloud proxies cause false positives, so they are triage prompts, not verdicts.

> [!IMPORTANT]
> A first-factor success followed by an MFA failure means the password is known to someone. Even if the MFA held, the password must be treated as compromised and reset, and the user contacted through a separate channel.

## VPN and remote access logs

A VPN concentrator is an authentication point exposed to the whole internet, which makes it one of the most attacked identity surfaces an organisation has. Its logs typically record the user name, the **external source address** of the client, the outcome, the authentication method (password, certificate, MFA via RADIUS or SAML to the IdP), the internal address assigned to the session, and session start, end, duration and bytes. When the VPN delegates authentication to the IdP, the same attempt also appears in the IdP's sign-in log, and the two can be correlated.

Note what VPN logs usually lack: a host name. The concentrator sees a remote client, not an asset in the inventory. The Banyan lab's own triage script says so in a comment (`PRIMARY_HOST = {"divya": "WS-104", "gopal": "WS-107"}  # VPN events carry no host`), mapping users to their usual laptops so that alerts can be shown against an asset. Lesson 5 returns to a related pitfall: `src_ip` in a VPN record is the user's external address, whereas in a proxy record it is the internal workstation.

The second query is the identity analyst's most useful pivot: group by **source**, count **distinct users**. One address failed against eight different accounts, one attempt each, seven seconds apart and in alphabetical order, then succeeded as gopal three minutes later. That shape (many users, few attempts per user, one source, mechanical timing) is password spraying, and the final success is what turns a noisy nuisance into an incident. The dataset's country field for 203.0.113.66 is `??`, meaning the lookup could not place it. The later 13:33 session for gopal from 198.51.100.104, geolocated to India, fits his normal remote working, and Module 4 shows why an expired intelligence match on that address must not be acted on.

Two identity facts make the spray more serious than its own records show. First, divya's name is among the failures at 06:42:21, yet the Windows log shows her logged on at WS-104 since 03:18: someone other than divya was trying her account. Second, gopal's account was already in use on WS-107 that morning, so the successful VPN session from an unplaced address is a second, concurrent use of his identity. The kit's rule R2 encodes the pattern:

```sql
SELECT s.src_ip, COUNT(DISTINCT f.user) AS users_failed, s.user AS success_user, s.ts
FROM events s JOIN events f ON f.src_ip = s.src_ip
WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn'
  AND f.outcome='failure' AND f.ts <= s.ts
GROUP BY s.src_ip, s.user, s.ts HAVING users_failed >= 5
```

It joins every VPN success to earlier VPN failures from the same address and fires when at least five distinct users failed first. Running `python minisiem.py rules` reports `R2 vpn_spray_then_success: 1 hit(s)` with the tuple `('203.0.113.66', 8, 'gopal', '2026-11-03T06:46:00Z')`.

**Purpose.** The figure places the Banyan VPN events on a five-and-a-half-minute timeline so that the shape of a password spray is visible at a glance. Tabular output hides rhythm; a timeline makes it obvious.

**Components.** The horizontal axis runs from 06:41:30 to 06:47:00 UTC. There are three rows. The red row, **VPN failures from 203.0.113.66**, sub-labelled "8 users, one try each, 7 s apart", carries eight ticks packed into the first quarter of the window. The orange row, **gopal**, sub-labelled "failure 06:42:42, success 06:46:00", carries two ticks: one inside the cluster and one far to the right. The violet row, **divya**, sub-labelled "failure while logged on at WS-104 since 03:18", carries a single tick inside the cluster.

**Relationships and arrows.** There are no arrows; the relationship is alignment in time. The gopal and divya ticks line up exactly with ticks in the red row because they are the same events, viewed per user. The gap between the cluster and gopal's second tick is the three minutes in which the operator of 203.0.113.66 stopped spraying and returned with one account.

**Execution flow.** Left to right: eight failures in 49 seconds, silence, one success. That is the typical spray sequence: try one password against a list of accounts, then use whichever account accepted it, sometimes after a second round.

**Decision logic.** The rule's question is "did at least five distinct users fail from this source before a success from it?" The red row answers yes (eight), and the orange row supplies the success. Had the failures been eight attempts against gopal alone, the per-user rows would show a dense cluster on one line and the pattern would be guessing (T1110.001) instead, caught by a different threshold.

**Technical interpretation.** Spraying is designed to stay under lockout thresholds: one attempt per account rarely locks anything. That is why per-account counting misses it and per-source distinct-user counting catches it. A sprayer who rotates through many addresses defeats per-source counting too, which is why IdPs add per-tenant and per-password-hash views.

**Practical example.** The analyst working CASE-0002 would confirm with gopal by phone that he did not connect at 06:46, revoke the VPN session, reset his password, require MFA for VPN if it was missing, and check divya's account for further attempts. The link between CASE-0002 and CASE-0001 on WS-104 remains a hypothesis based on timing only.

**Security implications.** The spray succeeded because one account had a guessable password and the VPN accepted a single factor. Blocking the address is the weakest response; MFA on the VPN and a banned-password list are the strongest.

**Key learning.** Count distinct users per source, not failures per user, to see a spray; and treat the first success after a spray as a likely compromise until proven otherwise.

## Common mistakes and misconceptions

- **Reading the Subject as the user.** In a 4624 the account that logged on is under New Logon; the Subject is the local requester.
- **Treating every 4625 as an attack.** Single wrong-password failures at a user's own console after a success are normal. Look for patterns: many users, non-existent names, odd sources, odd hours.
- **Searching only the domain controllers.** They hold ticket requests, not logon types or target-side sessions.
- **Ignoring non-interactive sign-ins.** In cloud IdPs these are where stolen tokens are replayed.
- **Using Logon ID across hosts.** It is local to one machine and one boot.
- **Assuming MFA makes passwords irrelevant.** A first-factor success is still a compromised password, and MFA fatigue and token theft bypass the prompt.
- **Trusting geolocation as fact.** It is a database lookup that is often wrong for mobile, VPN and cloud addresses.

## Security implications, detection and defence

Identity detections that repay their tuning effort include: distinct-users-per-source failure counts (spraying); failures on non-existent accounts; success after a run of failures; logon types unusual for the account (service accounts logging on interactively, type 10 to workstations); 4672 sessions for accounts not in the administrator baseline; 4720 and group-membership changes (4728, 4732) outside change windows; RC4 service-ticket requests in bulk; new MFA method registrations followed by sign-ins from new locations; and any 1102 audit-log clear. Defences are mostly identity hygiene: MFA everywhere, especially on VPN and email; blocking legacy authentication that cannot do MFA; banned-password lists and lockout policies tuned so that spraying is slow; tiered administration so that privileged accounts never log on to ordinary workstations; and managed service-account passwords. In India, the CERT-In directions of April 2022 require covered entities to keep logs for 180 days within Indian jurisdiction and list unauthorised access and identity-related compromises among reportable incidents, so identity logs are also a compliance record. Because they contain personal data (names, locations, working patterns), their collection and access should follow the purpose-limitation and security duties of the DPDP Act 2023.

## Best practices

- Collect Security logs from every domain controller, every server and, ideally, every workstation, with the logon, credential validation and Kerberos audit subcategories enabled.
- Ingest IdP sign-in logs (interactive and non-interactive) and audit logs, and VPN authentication logs, into the same SIEM, with users normalised to one form.
- Baseline per account type: humans, administrators, service accounts and applications behave differently.
- Always pivot both ways: by user (what did this account do?) and by source (what else did this address try?).
- Contact users through a separate channel before concluding that an unusual success was theirs.

## Key takeaways

- Identity logs show who authenticated, how, from where and with what result; they are the main evidence when attackers use valid accounts (T1078).
- In Windows domains the DC records ticket and credential-validation requests (4768, 4769, 4771, 4776) and the target records sessions (4624, 4625) with a logon type; you need both.
- Logon type and failure status codes turn a list of logons into a story; learn types 2, 3, 4, 5, 7, 10 and 11 and the common 4625 statuses.
- IdP sign-in logs add application, device, MFA and conditional access context, and they are where spraying, MFA fatigue and token reuse appear.
- VPN logs carry external addresses but no host; in the Banyan dataset they reveal a password spray from 203.0.113.66 against eight users that ended in a success for gopal.
