## Introduction and conceptual foundation

A single event rarely proves anything. One failed VPN login is a typo. One PowerShell process is an administrator at work. One large upload is a sales team sending a brochure. Attacks become visible when events are read *together*: eight different accounts failing from one address in fifty seconds and then one of them succeeding; a Word document starting PowerShell and the same workstation beginning to contact a rare domain every five minutes; a new local administrator, a large upload and a cleared security log on one host within two hours. **Correlation** is the part of a SIEM that reads events together, by applying rules that relate events across **sources**, across **time** and across shared **entities** such as a user, a host or an address.

Correlation is where the previous three lessons pay off or fail. Ingestion decides whether the events arrive at all; parsing decides whether their fields can be read; normalisation decides whether the same address, user or host is stored under the same name in every source. A correlation rule is, mechanically, a join or an aggregation on those normalised fields within a time constraint. If one source stored the address as `clientIP`, or kept local time, or wrote `-` for "unknown", the join quietly returns nothing, and an empty result looks exactly like "no attack".

This lesson studies correlation through the six rules of the lab's teaching SIEM, `LAB_ASSETS/C08/minisiem.py`, run against the Banyan Microfinance dataset (`banyan_events.jsonl`, 340 synthetic events from Windows Security, Sysmon-style endpoint, web proxy and VPN sources, with a scripted intrusion hidden among routine activity). Because minisiem stores events in SQLite, every rule is a plain SQL statement you can read line by line. Splunk SPL, Microsoft Sentinel KQL, Elastic's query languages and Wazuh rules express the same logic with different syntax; the concepts transfer directly.

> All rule outputs in this lesson come from running the kit's own scripts on a copy of the kit in a private working folder, on synthetic data. Always copy the kit before running it; never run anything inside the course library folder, and never point lab rules at systems you are not authorised to monitor.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Correlation rule | Saved logic that relates two or more events (or many events of one kind) and raises an alert when the relationship holds. |
| Entity | The thing events are joined on: a user, host, IP address, process ID or session. |
| Time window | The period within which related events must fall for the rule to fire. |
| Threshold rule | Fires when a count, sum or distinct count within a window reaches a limit. |
| Sequence rule | Fires when event A is followed by event B (on the same entity) within a window. |
| Combination rule | Fires when events from different sources share an entity within a window. |
| Absence rule | Fires when an expected event or source is missing for a period. |
| Sliding window | A window that moves with each event ("the last 10 minutes"). |
| Tumbling window | Fixed, non-overlapping buckets ("10:00-10:10, 10:10-10:20"). |
| Look-back | How far back a scheduled rule searches each time it runs. |
| Entity risk aggregation | Accumulating hits from many rules on one entity and alerting when the total is high. |

| Rule | Logic | Pattern |
| --- | --- | --- |
| R1 office_spawns_script | Sysmon process start where the parent is `WINWORD.EXE` and the child is PowerShell or cmd | Single event, two conditions on one record |
| R2 vpn_spray_then_success | VPN success preceded by failures for 5 or more distinct users from the same address | Sequence plus distinct-count threshold, joined on address |
| R3 new_local_admin | Windows event 4720 (account created) or 4732 (member added to a security-enabled local group) | Single event |
| R4 large_upload | Proxy request with more than 10,000,000 bytes sent | Single event, value threshold |
| R5 log_cleared | Event 1102 (the audit log was cleared) | Single event |
| R6 beacon_regular_small | Proxy requests grouped by host and URL: 10 or more hits whose sizes vary by under 50 bytes | Aggregation over many events |

R1, R3, R4 and R5 each look at one record at a time. They are valuable signatures, but each is ambiguous alone: administrators create accounts, analysts clear logs on test machines, and some macros legitimately start scripts. R2 and R6 are true multi-event logic: R6 summarises a whole population of proxy requests, and R2 relates *two kinds* of event to each other in time. The strongest correlation, which the later sections build, connects the single-event hits to each other through the entity they share.

## Anatomy of a sequence rule: R2

R2 is the course's canonical correlation rule. It detects a password spray (one source trying a common password against many accounts) that ends in a successful login, the moment at which a noisy but harmless attempt becomes a compromised account. Here it is exactly as it appears in `minisiem.py`:

```sql
SELECT s.src_ip, COUNT(DISTINCT f.user) AS users_failed, s.user AS success_user, s.ts
FROM events s JOIN events f ON f.src_ip = s.src_ip
WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn'
  AND f.outcome='failure' AND f.ts <= s.ts
GROUP BY s.src_ip, s.user, s.ts HAVING users_failed >= 5
```

Read it as a pipeline of decisions:

1. **Two roles for one table.** The `events` table is used twice, under the aliases `s` (candidate successes) and `f` (candidate failures). A self-join is how SQL relates events to other events of the same table.
2. **The entity.** `ON f.src_ip = s.src_ip` pairs every success with every failure from the same address. This line is only correct because normalisation put the VPN's client address into one field; it also inherits that field's meaning (for the VPN, the external address of the client).
3. **The event types.** The `WHERE` clause keeps only VPN successes on the `s` side and VPN failures on the `f` side, using the normalised `outcome` values `success` and `failure`.
4. **The order.** `f.ts <= s.ts` keeps only failures at or before the success. This works because `ts` is a UTC ISO 8601 string, which sorts correctly as text; with mixed time zones it would silently be wrong.
5. **The grouping.** `GROUP BY s.src_ip, s.user, s.ts` produces one candidate per success, and `COUNT(DISTINCT f.user)` counts how many *different* accounts failed from that address beforehand. Counting distinct users, not failures, is what distinguishes a spray (many accounts, few tries each) from one person mistyping a password ten times.
6. **The threshold.** `HAVING users_failed >= 5` keeps candidates where at least five accounts failed.

The single result row, `('203.0.113.66', 8, 'gopal', '2026-11-03T06:46:00Z')`, says that eight distinct accounts failed from `203.0.113.66` and then `gopal` logged in successfully from it at 06:46:00 UTC. The raw events behind it are easy to list:

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows how R2 turns two streams of ordinary VPN events into one alert. It matters because nearly every sequence rule in any SIEM has the same skeleton: two event types, an entity join, an order or window condition, a grouping and a threshold.

**Components.** At the top are two blue inputs, *VPN successes (s)* and *VPN failures (f)*, the two roles the self-join gives the one `events` table. They feed an orange *Join on src_ip* box, the entity. Below it a violet *Time condition* box carries `f.ts <= s.ts`. A violet *Group per success* box counts distinct failed users. A violet *users_failed >= 5?* box, drawn as a rounded decision box, holds the threshold. Two outcomes leave it: a dark *Alert* box with the real result (`203.0.113.66`, 8 users, `gopal`) and a slate *No alert* box.

**Relationships and arrows.** All arrows point downward, the direction data flows through the query: each stage receives the rows the stage above it kept. The two arrows leaving the threshold box are labelled *yes* and *no*.

**Execution flow.** The engine first pairs every success with every failure from the same address, then discards failures that came after the success, then groups the remaining pairs per success and counts distinct users, and finally applies the threshold.

**Decision logic.** There is one explicit branch, the threshold. There is also an implicit one at the time condition: a failure after the success is discarded, so a spray that continues after the compromise does not inflate the count. Notice what is *absent* from the diagram: a lower bound on time. As written, R2 counts failures from the same address at any earlier moment, which the next section corrects.

**Technical interpretation.** A self-join can be expensive: every success is paired with every earlier failure from the address. On a day's lab data that is trivial; on a production VPN with millions of events, real SIEMs bound the join with a time window and an index on time, which is why minisiem creates `idx_ts` at load time.

**Practical example.** In the lab, eight failures from `203.0.113.66` between 06:42:00 and 06:42:49 join to `gopal`'s success at 06:46:00. The count of 8 passes the threshold of 5 and the dark *Alert* box is reached.

**Security implications.** The threshold and the distinct count are design choices an adversary may try to stay under, for example by spraying fewer accounts per address or spreading attempts across many addresses. Defenders answer with additional rules on other entities (failures per *account* across many addresses) and with controls that make a sprayed password useless, above all multi-factor authentication on the VPN.

**Key learning.** A sequence rule is entity join, plus order, plus count, plus threshold; every one of those parts depends on normalised fields and UTC time.

## Time windows: the most important number in a rule

R2's time condition says only "before". If an address failed against five accounts in January and one of them logged in successfully in November, R2 would still fire. On one day of data that never happens; on a year of data in a production SIEM it produces false positives and, worse, a join that grows without limit. Every correlation rule needs a **window**: an upper bound on how far apart the related events may be.

You can test a windowed version of R2 in your copy of minisiem without editing the script, using the `search` subcommand. SQLite's `julianday()` converts an ISO timestamp to a fractional day number, so a difference of `10/1440.0` days is ten minutes:

```terminal
$ python minisiem.py search "SELECT s.src_ip, COUNT(DISTINCT f.user) AS users_failed, s.user AS success_user, s.ts FROM events s JOIN events f ON f.src_ip = s.src_ip WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn' AND f.outcome='failure' AND f.ts <= s.ts AND julianday(s.ts) - julianday(f.ts) <= 10/1440.0 GROUP BY s.src_ip, s.user, s.ts HAVING users_failed >= 5"
src_ip | users_failed | success_user | ts
203.0.113.66 | 8 | gopal | 2026-11-03T06:46:00Z
```

With a ten-minute window the rule still finds the spray. Now shrink the window to two minutes by changing `10/1440.0` to `2/1440.0` and run it again:

```terminal
$ python minisiem.py search "SELECT s.src_ip, COUNT(DISTINCT f.user) AS users_failed, s.user AS success_user, s.ts FROM events s JOIN events f ON f.src_ip = s.src_ip WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn' AND f.outcome='failure' AND f.ts <= s.ts AND julianday(s.ts) - julianday(f.ts) <= 2/1440.0 GROUP BY s.src_ip, s.user, s.ts HAVING users_failed >= 5"
src_ip | users_failed | success_user | ts
```

A header and no rows: the attack is missed. The last failure was at 06:42:49 and the success at 06:46:00, three minutes and eleven seconds later, so no failure lies within two minutes of the success. Nothing about the data changed; one number in the rule did. This is the central tension of window design:

- **Too short** and real attacks whose steps are spread out (a human attacker pausing to try the stolen credential, a scheduled task, a slow spray) fall outside the window and are missed.
- **Too long** and unrelated events are joined together, false positives rise, and the query becomes expensive because it must hold more events in memory.

Windows should be set from evidence, not guessed: how far apart are the steps in real incidents and in tests of this behaviour, and how long are the gaps in legitimate activity? Module 6 treats rule tuning and testing properly, using the kit's `test_rules.py`, which already tests R2 with a spray of five users (must match) and of four users (must not).

### Sliding and tumbling windows

The windowed R2 above uses a **sliding** window: for each success it looks back exactly ten minutes from that event. Many SIEM threshold rules instead count events in **tumbling** windows, fixed buckets such as each clock-aligned ten minutes. A quick way to see tumbling buckets in minisiem is to group on the first fifteen characters of the timestamp, which is the date, hour and tens-of-minutes digit:

```terminal
$ python minisiem.py search "SELECT src_ip, substr(ts,1,15) AS ten_min, COUNT(*) AS failures, COUNT(DISTINCT user) AS users FROM events WHERE source='vpn' AND outcome='failure' GROUP BY src_ip, ten_min"
src_ip | ten_min | failures | users
203.0.113.66 | 2026-11-03T06:4 | 8 | 8
```

All eight failures fall in the 06:40-06:50 bucket, so a tumbling rule such as "5 or more distinct users failing from one address in a ten-minute bucket" would fire here. But tumbling windows have a well-known blind spot: a burst that straddles a bucket boundary is split in two. Had the same eight failures run from 06:48 to 06:52, each bucket might have held four, and a threshold of five would never be reached in either. Sliding windows avoid the boundary problem at higher computational cost, and platforms that use buckets often compensate by overlapping them or by running a scheduled search whose look-back is longer than its interval.

## Combination rules: correlating across sources

Sequence rules like R2 relate events from one source. The most valuable correlations relate events from *different* sources that share an entity, because they combine independent pieces of evidence. R1 (from endpoint telemetry) says a Word document started PowerShell on `WS-104`. R6 (from the web proxy) says `WS-104` is making small, regular requests to a rare URL. Each alone is moderate evidence. Together, on the same host, close in time and in the right order, they describe a malicious document installing something that calls home.

This query joins the R1 condition to proxy requests to the beaconing domain from the same host within sixty minutes *after* the process started:

```terminal
$ python minisiem.py search "SELECT p.host, p.ts AS process_ts, MIN(b.ts) AS first_beacon, COUNT(b.ts) AS beacons_60m FROM events p JOIN events b ON b.host = p.host WHERE p.source='sysmon' AND p.event_id=1 AND lower(p.parent_image) LIKE '%winword.exe%' AND b.source='proxy' AND b.url LIKE '%cdn-telemetry-sync.example%' AND b.ts > p.ts AND julianday(b.ts) - julianday(p.ts) <= 60/1440.0 GROUP BY p.host, p.ts"
host | process_ts | first_beacon | beacons_60m
WS-104 | 2026-11-03T06:14:00Z | 2026-11-03T06:17:00Z | 12
```

The join key is `host`, filled by both Sysmon and the proxy (the field coverage matrix in Lesson 3 confirmed this). The first beacon came three minutes after PowerShell started, and twelve beacons followed within the hour. The `lower()` call matters: the raw parent path is `WINWORD.EXE` in capitals, and a case-sensitive comparison would miss it.

> [!IMPORTANT]
> A combination rule needs a join key that both sources fill with the same value. Host names, user names and addresses must be normalised to one representation (case, domain prefix, FQDN or short name) before they can be correlated. Check coverage before writing the rule, not after it fails to fire.

It overlaps in time with the WS-104 activity but shares no entity with it in the data; any link between the two (for example, the sprayer and the document sender being the same actor) would have to come from enrichment or threat intelligence, not from a join.

**Decision logic.** Each correlation rule is a question about this picture. R2 asks: within one row, is a cluster of failures followed by a success on the same address? The combination query asks: across the red rows, does a beacon follow the process start on the same host within sixty minutes? An entity risk rule asks: how many different rows hold hits for this one host within the incident window?

**Technical interpretation.** The picture only lines up because every source was normalised to UTC. Had the Windows events been left in IST, their ticks would sit five and a half hours to the right, apparently after the working day.

**Practical example.** An analyst triaging R5 (log cleared at 08:17) alone sees one suspicious event. Pulling the WS-104 rows for the preceding two hours shows the download, process, beacons, new admin and upload, the full intrusion.

**Security implications.** The regular beacon row is a gift to the defender only while it continues; the 1102 tick shows the attacker trying to remove local evidence, which is why the SIEM's central copy of the logs matters.

**Key learning.** Correlate on shared entities in UTC time; events that overlap in time but share no entity are coincidence until other evidence connects them.

## Entity risk aggregation: correlating alerts, not events

Writing a pairwise rule for every combination of behaviours does not scale: six rules give fifteen possible pairs, and real SOCs run hundreds of rules. A widely used alternative is to correlate the *rule hits themselves* by entity. Each rule contributes to the entity it names, and an alert is raised when one entity accumulates hits from several different rules within a period. Commercial platforms implement this under names such as risk-based alerting or entity behaviour scoring; the idea can be shown in a single query.

This query gathers the hits of R1, R3, R4 and R5 (the rules whose results carry a host) and counts how many *distinct* rules fired per host:

```terminal
$ python minisiem.py search "SELECT host, COUNT(DISTINCT rule) AS rules_fired, MIN(ts) AS first, MAX(ts) AS last FROM (SELECT 'R1' AS rule, host, ts FROM events WHERE source='sysmon' AND event_id=1 AND lower(parent_image) LIKE '%winword.exe%' AND (lower(image) LIKE '%powershell.exe%' OR lower(image) LIKE '%cmd.exe%') UNION ALL SELECT 'R3', host, ts FROM events WHERE source='windows' AND event_id IN (4720, 4732) UNION ALL SELECT 'R4', host, ts FROM events WHERE source='proxy' AND bytes_out > 10000000 UNION ALL SELECT 'R5', host, ts FROM events WHERE event_id=1102) GROUP BY host"
host | rules_fired | first | last
WS-104 | 4 | 2026-11-03T06:14:00Z | 2026-11-03T08:17:00Z
```

The inner `UNION ALL` stacks the hits of four rules into one list with a `rule` label; the outer query groups by host. One host, `WS-104`, triggered four different rules within two hours and three minutes. Counting *distinct* rules rather than hits is deliberate: R3 fired twice for one account creation, and two hits of one rule are weaker evidence than one hit each of four unrelated rules. R6 is left out of this query only because it groups by host and URL without a timestamp column; in a real implementation it would contribute too.

The benefit for the SOC is twofold. Individual low-confidence rules can be kept running without each one paging an analyst, and the single alert that does reach the queue arrives with its story already assembled. Module 4 shows the kit's `triage.py`, which takes the next step and scores each hit by rule severity, confidence and asset criticality.

## Absence rules: correlating what did not happen

Some of the most important correlations look for missing events: a server that has not sent a log for an hour, a backup job that did not report completion, an endpoint agent that stopped checking in. Attackers who disable logging, and failures that silently break a pipeline, both look like silence. The first step is to know when each source was last seen:

```terminal
$ python minisiem.py search "SELECT source, MIN(ts) AS first_seen, MAX(ts) AS last_seen, COUNT(*) AS n FROM events GROUP BY source"
source | first_seen | last_seen | n
proxy | 2026-11-03T03:19:00Z | 2026-11-03T12:32:00Z | 284
sysmon | 2026-11-03T03:13:00Z | 2026-11-03T06:14:00Z | 33
vpn | 2026-11-03T06:42:00Z | 2026-11-03T13:33:00Z | 10
windows | 2026-11-03T03:07:00Z | 2026-11-03T08:17:00Z | 13
```

Look at Sysmon: its last event is the malicious PowerShell start at 06:14, while the proxy keeps reporting until 12:32. In this synthetic dataset that is an artefact of how the generator was written (it only creates routine process events in the morning), so do not read it as part of the attack. But it is exactly the shape an absence rule exists to catch: an endpoint source that goes quiet at the moment of a compromise while other sources show the host is still active. An absence rule compares each source's last-seen time, ideally per host, with its expected reporting interval, and alerts when the gap is too long. Notice that the Windows source's last event is the 1102 log clearance; on a real host, clearing the log locally does not remove copies already forwarded to the SIEM, which is one of the strongest arguments for central collection.

## Running correlation in production

Correlation in a real SIEM runs in one of two ways. **Streaming** (real-time) engines evaluate each event as it arrives against the state of open windows; they alert within seconds but must hold window state in memory. **Scheduled** rules run a search every few minutes over a look-back period; they are simpler and can use the full query language, but they alert only on the next run. Both must handle three practical problems:

- **Late-arriving events.** A laptop offline for an hour uploads its events in a batch. A scheduled rule whose look-back equals its interval may never see those events inside a window, so look-backs are usually longer than intervals, with de-duplication to avoid alerting twice.
- **Clock skew.** If a source's clock is wrong, its events fall outside windows they belong in. Monitor the difference between event time and ingestion time per source.
- **Cost.** Joins over long windows and high-volume sources are expensive. Narrow the inputs first (filter to the event types the rule needs), then join.

## Common mistakes and misconceptions

- **"More rules means more detection."** Single-event rules without correlation flood the queue; analysts learn to ignore them. Prefer fewer, well-correlated rules and entity aggregation.
- **No upper bound on time.** As R2 shows, "before" is not a window. Every join needs a maximum gap.
- **Joining on a field one source does not fill.** A host-based rule cannot see VPN logins; check the field coverage matrix first.
- **Case and format mismatches.** `WINWORD.EXE` versus `winword.exe`, `WS-104` versus `ws-104.banyan.example`. Normalise, or compare case-insensitively.
- **Counting events instead of distinct entities.** Ten failures by one user is a typo pattern; one failure each for ten users is a spray. Choose the count that matches the behaviour.
- **Treating an empty result as proof of safety.** A rule that returns nothing may be broken. Test rules with known-bad events, as Module 6 does.

## Security implications, detection and defence

Correlation rules encode assumptions, and a well-informed adversary will try to operate outside them: spreading actions over longer periods than the window, staying under thresholds, or using different addresses so that no single entity accumulates enough hits. Defenders respond in layers rather than by chasing every variant: rules on several entities for the same behaviour (per address, per account, per host), longer-horizon aggregation that looks at days rather than minutes, absence rules that notice disabled telemetry, and above all preventive controls that make the behaviour fruitless. Multi-factor authentication on the VPN turns R2's scenario from a compromise into a failed attempt; application control that prevents Office from starting script interpreters removes R1's scenario at its source.

Correlation rules and their thresholds are themselves sensitive. Store them under access control and version history, because a rule silently disabled or a threshold raised from 5 to 500 is as effective for an attacker as deleting logs, and far less visible. Changes to detection content should be reviewed and recorded like changes to production code.

## Best practices

- Start every rule from a behaviour and the entity it is about, then choose the window and threshold from evidence.
- Give every join an explicit time window and filter inputs before joining.
- Correlate across sources on normalised entities; confirm coverage before writing the rule.
- Count distinct entities where the behaviour is about breadth (spray, scanning) and events where it is about volume.
- Use entity risk aggregation so that low-confidence rules contribute without each one paging an analyst.
- Add absence rules for every critical log source.
- Test each rule with a known-bad event and a near-miss benign event, and keep the tests with the rule.

## Key takeaways

- Correlation relates events across sources, time and shared entities; it is a join or aggregation on normalised fields within a time window.
- The main patterns are threshold, sequence, combination across sources, absence and entity risk aggregation.
- R2 joins VPN successes to earlier failures on the same address and counts distinct users; in the lab it returns `203.0.113.66`, 8 users, `gopal` at 06:46:00Z.
- The window is the most sensitive parameter: the same R2 fires with a ten-minute window and misses with a two-minute window because the success came 3 minutes 11 seconds after the last failure.
- Combining R1 with the proxy beacons on host `WS-104` shows the first beacon three minutes after PowerShell started; aggregating hits by host shows four distinct rules on `WS-104` in just over two hours.
- Rules encode assumptions an adversary may try to avoid, so layer entity views, absence rules and preventive controls, and protect detection content like code.
