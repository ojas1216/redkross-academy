## Introduction and conceptual foundation

An alert arrives with very little in it. The VPN rule `R2 vpn_spray_then_success` in the course SIEM reports one line: the address `203.0.113.66`, the number 8, the user `gopal` and a timestamp. Nothing in that line says whether `gopal` is an intern or the chief financial officer, whether his laptop holds customer records, whether `203.0.113.66` has ever been seen before, whether anyone in the sector has reported it, or whether `gopal` normally connects from somewhere else. Yet every one of those facts changes what the analyst should do next. **Enrichment** is the work of attaching that missing context to an alert, so that the decision the analyst makes is a decision about the real situation and not about a bare log line.

Module 3 introduced enrichment as a stage of the SIEM pipeline: the place where asset, identity, geolocation and intelligence data are joined to events, either when they are ingested or when they are searched. That lesson was about *where* context is added. This lesson is about *how an analyst uses it during triage*: which questions to ask of each entity in an alert, which sources answer them, how much to trust each answer, and where the analyst must stop because the next lookup would leak information or intrude on someone's privacy more than the alert justifies.

Severity and priority (Lessons 1 and 2) depend on enrichment, and so does validation (Lesson 4): you cannot judge whether a login is normal for a user until you know what normal looks like for that user. Enrichment does not decide anything by itself; it makes the decision possible.

> [!NOTE]
> Enrichment answers "who and what are these entities, and how much do they matter?" Validation (Lesson 4) answers "did the thing the rule describes really happen, and is it malicious?" Keep the two questions apart. A perfectly enriched alert can still be a false positive, and a confirmed attack on an asset with no inventory record is still an attack.

Throughout this lesson we use the Banyan Microfinance dataset from the course lab kit (`LAB_ASSETS/C08/banyan_events.jsonl`, loaded by `minisiem.py`), the kit's triage helper `LAB_ASSETS/C08/triage.py`, which joins rule hits to small asset and identity tables, and its intelligence matcher `LAB_ASSETS/C08/ioc_match.py`, which compares a fictional indicator feed with the events. All three were run in a temporary copy of the kit, and every output shown is exactly what they printed.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Entity | A thing an alert is about that can be looked up: a host, a user account, an IP address, a domain or URL, a file hash, a process. |
| Enrichment | Attaching context from sources outside the alert to its entities, so that the analyst can judge impact and likelihood. |
| Asset context | Facts about a device from an asset inventory or CMDB: owner, function, criticality, location, exposure. |
| Identity context | Facts about an account from the directory or identity provider: department, role, privilege level, account type. |
| Geolocation | An estimate of the country or city associated with an IP address, taken from a commercial or open database. Approximate by design. |
| ASN | Autonomous System Number: the identifier of the network operator that announces the IP prefix on the internet (an ISP, a cloud provider, a hosting company). |
| Indicator (IOC) | An observable value, such as a domain, IP address or file hash, that an intelligence source associates with malicious activity. |
| Confidence | The source's own estimate (here 0-100) of how likely the indicator is to be malicious. |
| Expiry (valid until) | The date after which the source no longer vouches for the indicator. |
| Prevalence | How many hosts or users in your own environment have seen an entity. Rare entities deserve more attention than common ones. |
| Baseline | What is normal for an entity: usual hours, usual locations, usual processes, usual volume. |
| Provenance | Where an enrichment value came from and when it was last updated. |

## Why enrichment changes the decision

Consider two alerts in which Microsoft Word starts PowerShell. In the first, the host is a developer's test virtual machine, the user is a macro developer, and the PowerShell start happens every working day. In the second, the host is `WS-104`, the user `divya` approves payments, and nothing like it has ever been seen on that host. The detection logic is the same; the first may be a benign true positive, the second is the opening move of the incident in this course's dataset.

Enrichment changes three things about an alert:

1. **Impact.** What would be lost if this were real? A payments approver's workstation in the finance team has more value to an attacker, and more consequence for the organisation, than a kiosk in reception. Asset and identity context answer this.
2. **Likelihood.** How probable is it that this is malicious? A domain that a sector information-sharing group has linked to a phishing campaign raises likelihood; an address that belongs to the organisation's own vulnerability scanner lowers it. Network context, threat intelligence and history answer this.
3. **Scope.** Is this one host or many? A rare domain seen by one workstation is a different problem from one that the whole office reaches every day. Prevalence answers this.

This is why the lab kit's priority score multiplies rule severity and confidence by asset criticality, a value that comes from the asset inventory and not from the alert.

## The enrichment sources

A SOC analyst draws on a small number of source families. Each answers a different question and goes stale in a different way.

### Asset context

The asset inventory (often a configuration management database, CMDB) records what each device is: its owner, its function, how critical it is to the business, where it sits on the network and whether it is exposed to the internet. Criticality is the value triage uses most. It is usually a small ordinal scale agreed with the business, so that "3" on a finance workstation means the same thing in every alert.

The risk with asset data is **staleness**. A server decommissioned last year and still listed as "low criticality", or a new database never entered at all, produces wrong priorities quietly. An analyst should treat "unknown asset" as a finding in its own right: something on the network that nobody has recorded is worth a question.

### Identity context

The directory or identity provider (IdP) records who an account belongs to and what it can do: department, job role, privilege level, whether it is a person or a service account, when it was created, and recent changes such as an MFA method reset. Identity context is what tells you that `divya` is a payments approver, which matters far more than her name.

Two cautions apply. Accounts are not people: a compromised account behaves like its attacker, not its owner. And identity data is personal data: the analyst needs the role and privilege level, rarely anything else.

### Network context

For an IP address, the first question is simply **internal or external**. An internal address leads to a host and an owner through DHCP, VPN or EDR records. An external address leads to three further questions:

- **Geolocation**: which country, and occasionally which city, a commercial database associates with the address. It is an estimate built from registration data and measurements, and it is often wrong at city level.
- **ASN and network owner**: which operator announces the address range. "A residential broadband provider", "a large cloud platform" and "a small hosting company" tell different stories, and the ASN often says more than the country.
- **Reputation and intelligence**: whether any feed or sharing community has reported the address, and with what confidence.

Geolocation and ASN have limits. VPN services, cloud platforms, mobile carriers and carrier-grade NAT put many unrelated users behind the same addresses, and an attacker can rent infrastructure in any country. A login from a hosting provider's range for a user who has only ever used home broadband is worth noting; neither value is attribution.

> [!IMPORTANT]
> The addresses in this course come from documentation ranges (RFC 5737), which no real network uses, so they have no real geolocation or ASN. The dataset's VPN events carry a synthetic `country` field instead: `IN` for routine sessions and `??` (unknown) for the spraying address. In the SIEM it lives only in the raw event, because `minisiem.py` does not normalise it into a column. Never invent geolocation or ownership for an address; if your source returns nothing, record "unknown".

### Threat intelligence

Intelligence enrichment checks the alert's entities against indicators that other people have reported: domains, IP addresses, URLs and file hashes, each with a source, a confidence and a validity period. Module 6 covers intelligence in depth (indicator types, confidence scales, feeds, sharing rules). In triage you need the analyst's view: a match is evidence, weighted by how good and how current the indicator is, and the absence of a match is not evidence of safety.

### History and prevalence

Your own data is often the best enrichment source. For each entity, ask:

- **Prior alerts and cases.** Has this host, user or address appeared in an earlier alert? Was it closed as benign, and why?
- **First seen.** When did the environment first see this domain or address? Something first seen today is more interesting than something seen every day for a year.
- **Prevalence.** How many hosts or users have touched it? One is rare; all of them is normal.
- **Baseline.** Does this user normally log in at this hour, from this kind of network, and run these processes?

History is free, private and specific to your environment, which no external feed can be.

### Vulnerability context

Finally, the vulnerability management system can say whether the host is missing a patch relevant to the alert. An exploit attempt against a service that is fully patched is less urgent than the same attempt against a host that is known to be vulnerable, although it still deserves recording.

## The enrichment workflow in triage

Enrichment in triage follows the same sequence. First, **extract the entities** the alert names: for `R2`, the user `gopal`, the address `203.0.113.66` and the time `06:46Z`; for `R1`, the host `WS-104`, the user `divya` and the process path. Second, apply a **privacy check** before anything leaves the SIEM: decide which lookups are internal, which go to external services, and what the minimum data is for each. Third, query the **context sources** for each entity. Finally, attach the answers to the alert as an **enriched record**, with each value's source and age, so that the next analyst can see not only what you know but how you know it.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure shows how one alert becomes an enriched alert during triage: which entities are pulled out, which gate they pass, which context sources answer, and what the analyst ends up holding. It matters because enrichment done in a different order, or without the gate, either leaks data or produces context nobody can trust.

**Components.** At the top, the orange box **Alert: R2 vpn_spray_then_success** is the raw rule hit. Below it the blue box **Extract entities** lists what the hit names: `gopal`, `203.0.113.66` and `06:46Z`. The violet box **Privacy check** is a control step: minimum data, internal sources first, no submission of internal data to public services. The five context sources sit in a row beneath it: **Asset (CMDB)** for owner, function and criticality; **Identity (IdP)** for department, role and privilege; **Network** for internal or external, geolocation and ASN; **Threat intel** for `ioc_match.py` matches with confidence and expiry; and **History** for prior alerts, first seen, prevalence and baseline. At the bottom the dark box **Enriched alert** is the outcome: every value carries its source and age.

**Relationships and arrows.** The arrows run one way, from the alert down to the enriched alert. Entities flow into the privacy check, the check fans out to every source, and every source feeds the enriched record. No arrow runs back into the alert: enrichment adds context alongside the evidence; it never edits the event that fired.

**Execution flow.** Extract, check, look up, attach. The internal sources (asset, identity, history) are cheap and private, so they are queried first; external lookups come last and only for what internal sources could not answer.

**Decision logic.** The privacy check is where the analyst decides what may leave. An internal hostname or a username should never go to a public reputation service. An external address or a public domain usually may, through an approved, logged service. A file belonging to a user is not uploaded to a public sandbox at all without authority.

**Technical interpretation.** In the lab kit, `triage.py` performs the asset and identity steps with Python dictionaries (`ASSETS`, `USERS`, `PRIMARY_HOST`) and a small `ip_context()` function that classifies addresses as internal or external. `ioc_match.py` performs the intelligence step. History is a `minisiem.py search` over the same events.

**Practical example.** For `R2`, the identity source returns *Sales, standard*; the asset source returns *WS-107, sales laptop, criticality 2* through the `PRIMARY_HOST` mapping; the network step returns *external*; intelligence returns a match on `203.0.113.66` at confidence 60; history shows that `gopal`'s only other VPN session that day came from a different address at `13:33Z`.

**Security implications.** Every source is now part of your detection system. A stale CMDB mis-prioritises; a poisoned feed creates false alarms or false comfort; an uncontrolled external lookup can reveal to an attacker that you have noticed them.

**Key learning.** Enrich internal-first, through a privacy gate, and record where each value came from. Context without provenance is just a claim.

## Worked example: enriching the morning's alerts

The lab kit's triage helper runs every `minisiem` rule, joins each hit to its asset and identity tables, and sorts the queue by priority. Run it in your own copy of the kit, never inside the course library folder:

```terminal
$ python minisiem.py load
loaded 340 events
$ python triage.py
10.8  R5 log_cleared             host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 7.2  R2 vpn_spray_then_success  host=WS-107 (sales laptop) user=gopal (standard) ip=external (documentation range in this lab)
 7.2  R1 office_spawns_script    host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 4.5  R4 large_upload            host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 3.6  R6 beacon_regular_small    host=WS-104 (finance workstation) user=None (?) ip=n/a
```

`load` builds the SQLite database `minisiem.db` from `banyan_events.jsonl`; `triage.py` takes no arguments and reads that database. Each line gives the priority score, the rule, then the enrichment the helper added: the host and its function from `ASSETS`, the user and their role from `USERS`, and the address class from `ip_context()`.

Read the enrichment critically:

- **Every value has a source, and some sources are weaker than others.** The host for `R2` is not in the VPN event at all; VPN events carry no host. The helper filled in `WS-107` from a `PRIMARY_HOST` table that maps users to their usual device. That is an assumption, not an observation. In production you would link a VPN session to a device through VPN client, DHCP or EDR records, and you would write down which method you used.
- **Missing values are normal.** `R6` groups proxy events by host and URL, so its hit has no user and the helper prints `user=None (?)`. Enrichment must tolerate gaps, and an analyst must not read "no user" as "no user involved".
- **Criticality drives the order.** Six of the seven lines involve `WS-104`, criticality 3, and the payments approver. The same rules firing on an unlisted host would take the helper's default criticality of 2 and fall down the queue.
- **`ip=n/a` is honest.** Host-based events have no remote address to classify, and the helper says so rather than guessing.

### History and prevalence from your own data

The quickest enrichment is a search of your own events. Two questions matter for the morning's alerts: how widespread are the suspicious domains, and what does `gopal`'s VPN use normally look like?

```terminal
$ python minisiem.py search "SELECT url, COUNT(DISTINCT host) AS hosts, COUNT(*) AS hits, MIN(ts) AS first_seen FROM events WHERE url LIKE '%banyan-payroll-update.example%' OR url LIKE '%cdn-telemetry-sync.example%' OR url LIKE '%files-share-drop.example%' GROUP BY url"
url | hosts | hits | first_seen
https://banyan-payroll-update.example/invoice.docm | 1 | 1 | 2026-11-03T06:12:00Z
https://cdn-telemetry-sync.example/api/v2/ping | 1 | 18 | 2026-11-03T06:17:00Z
https://files-share-drop.example/upload | 1 | 1 | 2026-11-03T08:12:00Z
$ python minisiem.py search "SELECT ts, user, src_ip, outcome FROM events WHERE source='vpn' AND outcome='success' ORDER BY ts"
ts | user | src_ip | outcome
2026-11-03T06:46:00Z | gopal | 203.0.113.66 | success
2026-11-03T13:33:00Z | gopal | 198.51.100.104 | success
```

`search` runs one SQL statement against the `events` table and prints a header row and pipe-separated results. `COUNT(DISTINCT host)` is the prevalence; `MIN(ts)` is the first time the environment saw the URL.

The first result is classic rare-entity enrichment: each of the three domains was reached by exactly **one host** in the whole organisation, and each was first seen within the same two hours of the incident window (the dataset holds a single day, so a real first-seen check would search much further back). The office reaches `mail.banyan.example` from every workstation; nothing else reaches these. The second result gives `gopal`'s VPN pattern for the day. His only other successful session came at `13:33Z` from `198.51.100.104`, with the synthetic country `IN`, which fits the routine pattern of staff connecting from home later in the day. The `06:46Z` session from `203.0.113.66`, country `??`, does not. One day of data is a thin baseline; a real SOC would look back weeks.

> [!TIP]
> Prevalence is one of the strongest triage signals and costs nothing. Before you look a domain up anywhere else, count how many of your own hosts have contacted it, and when the first one did.

## Threat-intelligence lookups

An intelligence lookup asks whether anyone else has reported an entity as malicious. The lab kit's `ioc_match.py` holds a small fictional feed of five indicators, each with a type, a value, a confidence from 0 to 100, a `valid_until` date, a source, a line of context and a TLP marking that limits how it may be shared. It compares the feed with the events in `minisiem.db` as of a fixed date, 3 November 2026, and reports what matched. Run it after `minisiem.py load`:

```terminal
$ python ioc_match.py
MATCH    domain cdn-telemetry-sync.example       conf= 85 hits= 18 first=2026-11-03T06:17:00Z src=ISAC-A TLP:AMBER
MATCH    domain banyan-payroll-update.example    conf= 70 hits=  1 first=2026-11-03T06:12:00Z src=internal TLP:GREEN
MATCH    ipv4   203.0.113.66                     conf= 60 hits=  9 first=2026-11-03T06:42:00Z src=ISAC-A TLP:GREEN
EXPIRED  ipv4   198.51.100.104                   conf= 40 hits=  1 first=2026-11-03T13:33:00Z src=open feed TLP:CLEAR
         expired indicator still matches: review before acting
no match sha256 9f2c...e1a0                      conf= 90 hits=  0 first=- src=vendor TLP:AMBER
```

The script takes no arguments. Domains are matched against the `url` field, IPv4 indicators against `src_ip`. The columns are the status, the indicator type and value, the source's confidence, the number of matching events, the first matching timestamp, the source and the TLP marking.

Each line teaches a different part of interpreting intelligence:

- **`cdn-telemetry-sync.example`, confidence 85, 18 hits.** A sector information-sharing group (ISAC-A) reports it as command-and-control for a loader seen in finance-sector phishing. Banyan is a microfinance company, so the context fits; the confidence is high; and history already showed the domain is reached by one host only. This match should raise the priority of `R6` and `R1` and send the analyst straight to validation. It is marked TLP:AMBER, so the indicator and its context may be shared inside the organisation on a need-to-know basis but not posted publicly.
- **`banyan-payroll-update.example`, confidence 70, 1 hit.** The source is *internal*: Banyan's own team noted this look-alike domain when it was registered on 29 October. Internal intelligence is often the most relevant there is, because it is about you.
- **`203.0.113.66`, confidence 60, 9 hits.** Reported for password spraying against VPNs. The nine hits are exactly the eight failures and one success behind `R2`. A confidence of 60 on an IP address is moderate: addresses are cheap for attackers to change and are often shared. The match supports the `R2` alert; it does not prove who is behind it.
- **`198.51.100.104`, EXPIRED.** The indicator's validity ended on 30 June 2026, it came from an open feed at confidence 40, and its context reads "scanning (old, shared hosting)". It still matches one event: `gopal`'s routine evening VPN session with country `IN`. An analyst who acted on every match would now treat a normal employee login as an attack. The script's warning, "review before acting", is the right instruction: an expired, low-confidence indicator on shared infrastructure is at most a reason to look, never a reason to block or to accuse.
- **`9f2c...e1a0`, no match.** The vendor's hash for the malicious `invoice.docm` has confidence 90, yet it produced zero hits. That is not reassurance. The dataset contains no file hashes at all, so the lookup could never have matched. A "no match" is only meaningful when you know the data you searched could have contained the indicator.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure is a decision graph for interpreting the result of an indicator lookup. It matters because a match is the most persuasive-looking enrichment an analyst can get, and also the easiest to over-trust.

**Components.** The orange box at the top, **Indicator lookup**, is the run of `ioc_match.py` against the SIEM events. It has two outcomes. The slate box **No match** (sub-label: the sha256 case, because the dataset holds no hashes) leads to the violet box **Absence is not evidence**, which tells the analyst to check telemetry coverage. The violet decision box **Still valid on the as-of date?** handles matches. Its "no" branch reaches the slate box **EXPIRED: review before acting**, illustrated by `198.51.100.104` matching a routine VPN session. Its "yes" branch reaches a second violet decision, **Confidence, source, specificity?** That decision branches to the blue box **Weak: context only** (low confidence, shared hosting, generic scanning) and to the red box **Strong: raise priority** (illustrated by `cdn-telemetry-sync.example` at confidence 85 from ISAC-A). All roads that remain open end in the dark box **Validate in raw events**, which is Lesson 4.

**Relationships and arrows.** Solid arrows are the main path. The dashed arrows from the weak and expired outcomes to validation show that those results may still be investigated, but only with other evidence carrying the weight. No arrow leads from any intelligence box straight to "incident" or "block": intelligence never closes the loop on its own.

**Execution flow.** Look up; if nothing matched, ask whether a match was even possible; if something matched, check validity first, then quality, then hand over to validation.

**Decision logic.** Validity comes before confidence because an expired indicator's confidence is out of date by definition. Confidence and specificity come before action because a high-confidence, campaign-specific domain and a low-confidence address on shared hosting are different kinds of evidence even when both say "MATCH".

**Technical interpretation.** `ioc_match.py` implements the first decision literally: it compares `valid_until` with its `AS_OF` date and prints `EXPIRED` even when rows match. The confidence judgement is left to the analyst, as it should be.

**Practical example.** In the Banyan data, the strong path applies to `cdn-telemetry-sync.example` and `banyan-payroll-update.example`, the moderate path to `203.0.113.66`, the expired path to `198.51.100.104`, and the no-match path to the vendor hash.

**Security implications.** Over-trusting matches causes wrongful blocks and accusations; under-trusting them wastes good intelligence. Treating "no match" as clean hides attacks in exactly the data you do not collect.

**Key learning.** A match is evidence weighted by validity, confidence and fit; a non-match means nothing until you know it could have matched.

## Privacy and operational limits

Enrichment is a form of looking more closely at people and systems, and it has limits that a professional respects every time.

**Minimum necessary personal data.** Identity enrichment needs the role, department and privilege level, perhaps the manager for escalation. It does not need home addresses, salary, health information or performance records. India's Digital Personal Data Protection Act, 2023 requires personal data to be processed for a lawful purpose and protected with reasonable safeguards; within the SOC that means pulling only what the alert justifies, keeping it inside the case, and following your organisation's retention rules. Monitoring an individual beyond what an alert requires is a matter for HR and legal, not for triage.

**Nothing internal goes to public services.** Public reputation sites, search engines and online sandboxes keep what you submit, and some make submissions visible to others. Never paste internal hostnames, usernames, internal URLs or documents into them. An external domain or address may be checked through an approved service that your SOC has assessed; a file from a user's mailbox is analysed in an internal or contracted sandbox under the procedures Module 9 describes.

**Passive, not active.** Visiting a suspicious domain, resolving it from the corporate network or scanning the address that attacked you can alert the attacker that they have been noticed, and touching third-party systems without authorisation can be an offence under the IT Act 2000. Enrichment uses recorded data and reputable third-party records only. Anything active belongs to authorised investigation, in an isolated lab.

**Respect sharing markings.** The TLP marking on each indicator governs where its context may go. TLP:AMBER context from ISAC-A can inform your case notes and your internal escalation; it does not go into a public ticket, a vendor forum or a message to a customer. Module 6 covers TLP 2.0 in full.

## Common mistakes and misconceptions

- **"The IP is in India, so it is the user."** Geolocation is an estimate; VPNs, cloud platforms and carrier-grade NAT break the link between address and person.
- **Treating every match as confirmation.** The expired `198.51.100.104` match lands on a routine login.
- **Treating "no match" as clean.** The vendor hash cannot match data that holds no hashes.
- **Trusting enrichment without provenance.** The `PRIMARY_HOST` mapping in `triage.py` is an assumption, not an observation.
- **Ignoring your own data.** Prevalence and history are often more decisive than any external lookup, and they leak nothing.
- **Over-collecting personal data.** Enrichment that reads like a profile of an employee is a privacy problem and rarely helps triage.

## Security implications, detection and defence

Enrichment sources are part of the attack surface. An attacker who can edit the CMDB can make a critical server look unimportant; a feed that is poisoned or simply careless can make a legitimate service look malicious and cause the SOC to block its own business. Defend the sources as you would any detection component: restrict who can change asset criticality and identity attributes, log those changes, review intelligence sources for quality, expire indicators automatically, and alert when a feed suddenly produces many more matches than usual.

External enrichment services need approved accounts, API keys kept in a secrets manager, and a record of what was submitted. Automated enrichment (Module 11) multiplies both value and risk: one badly written playbook can submit every alert's entities to a public service.

Enrichment can also hide attacks: an address range labelled "trusted partner" enriches every alert from it into a low priority. Such labels deserve owners, reasons and expiry dates, like the suppression entry in `triage.py`.

## Best practices

1. Extract and enrich every entity in the alert, not just the first.
2. Query internal sources first: inventory, identity, SIEM history and prevalence.
3. Record the source and age of every enrichment value in the case.
4. Read validity, confidence, source and TLP before acting on a match; check coverage before trusting a non-match.
5. Send nothing internal to public services, and collect only the personal data the alert requires.
6. Report stale or missing inventory and identity data as findings.

## Key takeaways

- Enrichment attaches asset, identity, network, intelligence and history context to an alert's entities, changing its impact, likelihood and scope, and therefore its priority.
- Internal sources come first: they are cheap, specific and private. Prevalence and first-seen counts from your own SIEM are among the strongest signals there are.
- Every enrichment value needs provenance; some, like a user-to-host mapping, are assumptions and must be recorded as such.
- Intelligence matches are weighted by validity, confidence, source and fit; an expired match can land on a normal login, and a "no match" means nothing if the data could not have matched.
- Geolocation and ASN are hints, not attribution.
- Enrichment has limits: minimum personal data, nothing internal to public services, passive lookups only, respect for TLP.
