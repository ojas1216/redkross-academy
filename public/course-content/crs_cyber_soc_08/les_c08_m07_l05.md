## Introduction and conceptual foundation

A detection rule is never finished on the day it is deployed. It meets an environment its author only partly understood, and within weeks its alerts tell a story about the rule itself: some rules prove sharp and quiet, others fire dozens of times a day on activity nobody cares about. **Tuning** is the engineering discipline of reading that story and changing the rule so that it alerts on what it was written to detect, and as little else as possible, without losing the attacks it was meant to catch.

Module 5, Lesson 5 looked at the same problem from the queue. There you learned to tell a false positive from a benign true positive, to write a false-positive record that a detection engineer can act on, and to build a documented, expiring suppression. This lesson picks up where that one stopped: the tuning request has arrived on the detection engineer's desk. What does the engineer measure, how do they decide which kind of change to make, and how do they make that change without breaking the rule or silently blinding it?

The lesson is organised around four questions:

1. **How good is the rule now?** Precision measured per rule, from dispositions, over enough alerts to mean something.
2. **Why is it noisy?** The cause decides the fix: bad data, logic broader than its intent, a threshold or window that does not match the real baseline, or a genuine benign pattern.
3. **What is the narrowest change that removes the noise?** Narrowing logic, re-setting a threshold or window from evidence, lowering priority, or (as a last resort) a scoped suppression.
4. **How is the change controlled?** Version control, tests that must still pass, replay against stored data, peer review, staged deployment and monitoring afterwards.

All practical work uses the course kit, `LAB_ASSETS/C08/`: `minisiem.py` (the teaching SIEM and its rules R1 to R6), `test_rules.py` (the rules' unit tests, the subject of Lesson 4) and `banyan_events.jsonl` (the synthetic Banyan Microfinance day). Two small scripts and a handful of synthetic events were written for this lesson; each is shown in full and labelled.

Tuning is a security activity, not housekeeping. Every change alters what the SOC can see, and a hurried change without tests can remove the attack along with the noise; nobody will notice, because a rule that no longer fires produces no complaint.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Precision | The share of a rule's alerts that were worth an analyst's attention: TP / (TP + FP), with benign true positives counted as noise when the question is queue value. |
| Recall (detection rate) | The share of real occurrences of the behaviour that the rule caught. It cannot be measured from the alert queue alone, because misses never appear there. |
| Alert volume | Alerts per rule per day (or week). With precision, it gives the analyst time a rule consumes. |
| Baseline | The measured normal behaviour of the field a rule tests: typical counts, sizes, intervals and their spread. |
| Threshold | A numeric boundary in a rule: a count, a size, a distinct-value count. |
| Window | The maximum time span over which events are related or counted. |
| Narrowing | Changing the rule's logic so that it matches its intent more exactly, for everyone. |
| Suppression | Stopping a specific, documented benign instance from alerting while the rule stays unchanged (Module 5, Lesson 5). |
| Regression test | A test that proves a change did not break what already worked, such as a known-bad sample that must still match. |
| Replay | Running a changed rule over stored historical data to see how its alert count and precision would have changed. |
| Change control | The governed path a rule change follows: request, version control, testing, review, deployment, monitoring and rollback. |

## Measuring alert precision

Tuning starts with a number, not a feeling. "R6 is noisy" is a complaint; "R6 raised 140 alerts in the last 30 days, 131 closed as false positive or benign, precision 0.06, about 7 analyst-hours" is a tuning case. The number comes from the dispositions analysts already record. If the SOC follows the Module 5 discipline, each closed alert carries a label (TP, FP, BTP, undetermined) and the rule ID, so precision per rule is a simple grouped count over the case system.

Several details make the measurement honest:

- **Measure per rule.** A SOC-wide false-positive share (Module 1, Lesson 7 computed one with `soc_metrics.py`) shows there is a noise problem; only per-rule precision shows where.
- **Decide what counts as noise.** For queue value, benign true positives are noise; for rule correctness they are not errors. The fix differs: an FP points at logic or data, a BTP at context or a suppression.
- **Exclude undetermined alerts from the ratio, but report them.** Many undetermined closures signal an evidence problem, a different defect.
- **Use enough alerts and a long enough period.** Five alerts are anecdote. A rule that fires twice a month needs a quarter's data, and seasonal patterns (month-end jobs, patch days) need a full cycle.
- **Pair precision with volume.** Precision 0.10 at two alerts a month is cheap; precision 0.50 at two hundred a day is not.

Precision can also mislead the other way: a very precise rule may simply be so narrow that it catches one variant. Recall cannot be read from the queue, because misses never become alerts; it is estimated by testing against known-bad samples and emulation (Lesson 4), by independent hunting and by incident review. Tuning that raises precision while quietly cutting recall is the failure this lesson is designed to prevent.

### A threshold sweep

A **threshold sweep** runs the same rule at several parameter values and scores each result. `sweep.py`, written for this lesson (not part of the kit), scores R4 at five upload thresholds and R6 at four combinations of minimum hit count and maximum size range:

```python
"""Threshold sweep for R4 and R6 (written for M7 L5; not part of the kit)."""
import sqlite3

con = sqlite3.connect("minisiem.db")
BAD = ("banyan-payroll-update.example", "cdn-telemetry-sync.example", "files-share-drop.example")


def score(rows, url_col):
    tp = sum(1 for r in rows if any(d in r[url_col] for d in BAD))
    fp = len(rows) - tp
    prec = f"{tp / len(rows):.2f}" if rows else "n/a"
    return len(rows), tp, fp, prec


print("R4 large_upload: bytes_out > T")
print("T          alerts  TP  FP  precision")
for t in (10_000_000, 3_900, 3_500, 3_000, 2_000):
    rows = con.execute("SELECT ts, host, url FROM events WHERE source='proxy' AND bytes_out > ?",
                       (t,)).fetchall()
    print(f"{t:<10} %6d %3d %3d  %s" % score(rows, 2))

print("R6 beacon_regular_small: hits >= N AND size range < W")
print("N   W      alerts  TP  FP  precision")
for n, w in ((10, 50), (10, 3_000), (10, 3_500), (5, 3_500)):
    rows = con.execute("""SELECT host, url FROM events WHERE source='proxy' GROUP BY host, url
                          HAVING COUNT(*) >= ? AND MAX(bytes_out) - MIN(bytes_out) < ?""",
                       (n, w)).fetchall()
    print(f"{n:<3} {w:<6} %6d %3d %3d  %s" % score(rows, 1))
```

The R4 query is the kit's rule with its constant replaced by a parameter (`?`), and the R6 query is the kit's rule with both constants parameterised. `score()` counts a hit as a true positive when its URL contains a storyline domain. Run it after `minisiem.py load`:

```terminal
$ python sweep.py
R4 large_upload: bytes_out > T
T          alerts  TP  FP  precision
10000000        1   1   0  1.00
3900            5   1   4  0.20
3500           32   1  31  0.03
3000           64   1  63  0.02
2000          142   1 141  0.01
R6 beacon_regular_small: hits >= N AND size range < W
N   W      alerts  TP  FP  precision
10  50          1   1   0  1.00
10  3000        2   1   1  0.50
10  3500        3   1   2  0.33
5   3500       33   1  32  0.03
```

At the kit's 10,000,000 bytes R4 raises one alert, the exfiltration. At 3,900, just under the routine maximum, four routine requests join it; at 2,000, over half of routine traffic alerts. The true-positive count never changes, because the real upload is far above every threshold tried. That is a well-separated signal: a wide band (roughly 4,000 bytes to 48 MB) in which the rule is precise and complete, and the engineer chooses a value inside it with margins on both sides.

In the R6 block, widening the size range to 3,000 lets WS-103's requests to `cdn.example.org` qualify, 3,500 adds its intranet traffic, and dropping the count to five as well produces 33 alerts for one beacon. Parameters interact, and loosening two at once multiplies the noise. A sweep is cheap, so there is no excuse for choosing a threshold by intuition.

> [!IMPORTANT]
> A sweep measures precision against the data you have. It says nothing about attacks that are not in that data. An attacker who uploads 9 MB at a time passes under R4's 10 MB threshold on every request. The baseline tells you how low you can go before noise explodes; the threat model tells you how low you need to go. When the two conflict, the answer is usually a second rule (for example, total bytes per host and destination per hour), not a threshold that drowns the queue.

## Diagnosing the cause before choosing the change

A tuning request usually arrives with a proposed fix ("add WS-103 to the exclusions"). The engineer's first job is to set the proposal aside and find the cause, because the same symptom, too many alerts, has several different causes and each has a different correct change. Module 5, Lesson 5 listed the options as the analyst sees them; here they are ordered as the engineer should test them, from the most general fix to the most specific.

1. **Is the data wrong?** If a field is empty, mis-parsed or means something different on one source, the defect is in the pipeline. Fix the parser or normalisation (Module 3); every rule using the field benefits.
2. **Is the logic broader than its intent?** If the rule matches activity that does not fit its own description in any environment, narrow the logic. The title is the specification: R6 is `beacon_regular_small`, so activity that is not regular and persistent over time is outside its intent.
3. **Are a threshold or window out of line with the measured baseline?** If the logic is right but its numbers were guessed, re-set them from a sweep and from the spacing of real attack steps.
4. **Is it a specific, known, authorised instance?** If the behaviour matches the rule's intent but this instance is approved, it is a benign true positive. Use a scoped, owned, expiring suppression as Module 5 described, or enrichment that lets triage close it in seconds.
5. **Otherwise**, lower its priority or confidence for the low-value context rather than hiding it.

Each step is more specific, and less durable, than the one before. Starting from the bottom (the natural instinct under pressure) produces a growing pile of suppressions around a rule whose real defect was never fixed.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the detection engineer's triage of a tuning request: a series of questions that leads from a measured problem to the narrowest durable fix. It matters because the most common tuning error is not a wrong threshold but the wrong *kind* of change, typically a suppression applied to what is really a data or logic defect.

**Components.** At the top is a slate box, **Noisy rule**, with the sub-label *measured precision and volume*: the input is a number from the dispositions, not a complaint. Four violet decision boxes follow: **Is the data wrong?**, **Logic broader than intent?**, **Threshold or window off baseline?** and **Known authorised instance?** Each has an outcome box: **Fix parser or normalisation**, **Narrow the logic**, **Re-set from measured baseline** and **Scoped suppression** (with the sub-label *owner, reason, expiry*). An orange box, **Lower priority, keep visible**, catches the cases where none of the questions is answered yes. All outcomes lead to one dark box, **Tests, replay and review**.

**Relationships and arrows.** A *yes* arrow leaves each decision box to its fix; a *no* arrow leads to the next question. Every fix box has an arrow into **Tests, replay and review**, which is the point of the diagram's shape: no route reaches production without passing through the same gate.

**Execution flow.** The engineer asks the questions in order and stops at the first *yes*. The order runs from the most general change, a data fix that improves every rule using the field, to the most specific, a suppression that covers one documented pattern.

**Decision logic.** Each question needs evidence to answer. *Is the data wrong?* is answered by reading the raw events behind the false positives and comparing them with the normalised fields. *Logic broader than intent?* is answered by comparing the alert with the rule's own title, description and ATT&CK mapping (Lesson 3). *Threshold or window off baseline?* is answered by a sweep. *Known authorised instance?* is answered only by a record of approval with an owner, never by the identity of the user.

**Technical interpretation.** Each fix is a scope statement. A parser fix changes a field for every consumer; narrowing changes one rule for every entity; a new threshold changes one rule's sensitivity for every entity; a suppression changes one rule for one entity pattern. The further down the chain, the smaller the scope and the higher the maintenance cost per alert removed.

**Practical example.** In the next section, R6 fires on WS-102's twelve identical 180-byte requests to `crm.banyan.example` within one minute. The data is correct, so the first answer is *no*. A one-minute burst is not a beacon in any environment, so the second answer is *yes*, and the fix is to narrow the logic. A sanctioned agent that polls an update server every five minutes all day would instead reach the fourth question, because that really is regular, small and persistent.

**Security implications.** Every fix removes alerts; each must be justified with evidence and must not remove the behaviour the rule exists to catch. The common gate is the control: tests prove that known-bad samples still match, and replay shows how volume and precision change before anyone relies on the change.

**Key learning.** Find the cause first and make the most general fix that removes it; suppress only a specific, authorised instance, and send every change through the same test and review gate.

## Narrowing logic: the R6 burst

R6 is written as an aggregation over the whole data set: per host and URL, ten or more requests whose sizes vary by less than 50 bytes. Its name promises a *beacon*, a periodic check-in over time, but the query never looks at time. Any burst of identical small requests satisfies it, and modern web applications produce such bursts routinely (status polling, retries, health checks).

To reproduce the false positive, make a second working copy of the kit (here `change/`) and append twelve synthetic proxy events: WS-102 (user ben, whose workstation address in the dataset is 10.40.0.21) requesting a CRM status endpoint every five seconds for one minute, 180 bytes each. The last appended line is:

```json
{"@timestamp": "2026-11-03T09:30:55Z", "bytes_out": 180, "host": "WS-102", "source": "proxy", "src_ip": "10.40.0.21", "status": 200, "url": "https://crm.banyan.example/api/status", "user": "ben"}
```

The other eleven are identical apart from their timestamps, 09:30:00 to 09:30:50 in steps of five seconds. Reload and run the rules (only R6 is shown):

```terminal
$ python minisiem.py load
loaded 352 events
$ python minisiem.py rules
R6 beacon_regular_small: 2 hit(s)
    ('WS-102', 'https://crm.banyan.example/api/status', 12, 180, 180)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

The loader counts 340 + 12 = 352 events and R6 now has a false positive beside the real beacon. A suppression for `host = WS-102` or for the CRM URL would hide it, and would also hide a real beacon from that host or to that URL later. Neither addresses the cause: the rule's "beacon" has no time dimension.

The narrowing adds one condition to R6's `HAVING` clause in the working copy of `minisiem.py`: the requests must span at least 30 minutes.

```sql
SELECT host, url, COUNT(*) AS hits, MIN(bytes_out) AS min_b, MAX(bytes_out) AS max_b
FROM events WHERE source='proxy'
GROUP BY host, url HAVING hits >= 10 AND max_b - min_b < 50
  AND (julianday(MAX(ts)) - julianday(MIN(ts))) * 1440 >= 30
```

`julianday()` converts timestamps to fractional days, so the difference times 1,440 is the span in minutes. Thirty minutes comes from the threat model, not the burst: a five-minute beacon passes it after seven check-ins, and a useful implant stays in contact far longer. Rerun:

```terminal
$ python minisiem.py rules
R6 beacon_regular_small: 1 hit(s)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

(Only R6 is shown.) The burst is gone and the real beacon remains. The change brings the rule closer to its own name, applies to every host and needs no exception list.

## Thresholds and windows

Module 3, Lesson 4 showed R2's window mechanics: ten minutes finds the spray, two minutes misses it, because the last failure (06:42:49) is 3 minutes 11 seconds before the success (06:46:00). The engineering questions that follow are how to choose the numbers and how to protect them.

### Setting numbers from evidence

A threshold or window sits between two distributions, legitimate use and attacks, and both must be measured.

- **The benign side** comes from the baseline, such as the R4 sweep. For R2 it is how many distinct accounts normally fail from one address; a shared NAT address such as a guest Wi-Fi gateway is the kind of fact a baseline uncovers.
- **The attack side** comes from incidents, tests and threat intelligence. For R2 it is the spacing of real spray-and-login sequences. In the lab dataset that spacing can be measured directly:

```terminal
$ python minisiem.py search "SELECT s.user AS success_user, s.ts AS success_ts, MIN(f.ts) AS first_fail, MAX(f.ts) AS last_fail, ROUND((julianday(s.ts) - julianday(MIN(f.ts))) * 86400) AS secs_from_first, ROUND((julianday(s.ts) - julianday(MAX(f.ts))) * 86400) AS secs_from_last FROM events s JOIN events f ON f.src_ip = s.src_ip WHERE s.source='vpn' AND s.outcome='success' AND f.source='vpn' AND f.outcome='failure' AND f.ts <= s.ts GROUP BY s.src_ip, s.user, s.ts"
success_user | success_ts | first_fail | last_fail | secs_from_first | secs_from_last
gopal | 2026-11-03T06:46:00Z | 2026-11-03T06:42:00Z | 2026-11-03T06:42:49Z | 240.0 | 191.0
```

This is R2's join with the count replaced by first and last failure times (`* 86400` converts days to seconds). One sample is not a distribution, but it gives a floor: any window under about three minutes misses the only spray seen. Set the window comfortably beyond the slowest known attack sequence, then sweep the benign side; if noise appears, improve the entity or condition rather than shortening the window.

Attackers adapt to known numbers: four accounts per address, or an hour's wait before using the password, defeats R2. The defence is layered rules over other entities and time scales and controls such as multi-factor authentication, not extreme numbers; coverage across rules is Lesson 6's subject.

## Change control for rules

Detection rules are code that decides what humans see, and deserve production-code controls. In the detection-as-code model of Lesson 2, each rule lives in version control with its tests, and every change follows one path.

1. **Request with evidence**: rule and version, measured precision and volume, sample alerts and the analysts' false-positive records.
2. **Reproduce** the noise on stored data. A change that cannot be reproduced cannot be verified.
3. **Change in version control**: rule and test changes together on a branch, the commit citing the ticket. Sigma records this in metadata: a `modified` date and a `status` moving from `experimental` through `test` to `stable`.
4. **Unit tests**: every must-match, must-not-match and boundary test passes.
5. **Replay** over a representative period of stored data, the only way to see which past true positives the change would have removed.
6. **Peer review and approval** of the diff, tests and replay (Lesson 7).
7. **Staged deployment**: the new version runs alongside the old one, or at low priority, for a defined period.
8. **Monitor and be ready to roll back.** A rule whose hits drop to zero after a change is investigated, not celebrated; rollback is a revert.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows the controlled path from a tuning request to a monitored production rule. It matters because tuning is a change to what the SOC can see, and every uncontrolled change is a potential blind spot that nobody notices until an incident review.

**Components.** Eight steps run from top to bottom. A slate **Tuning request** (sub-label *precision, volume, FP records*) starts the path. A blue **Reproduce on stored data** follows. A violet **Branch: rule + tests** (sub-label *commit cites the ticket*) holds the change. An orange **Unit tests** step (sub-label *must-match, must-not, boundary*) and an orange **Replay** step (sub-label *volume and precision over past data*) are the two evidence gates. A violet **Peer review and approval**, a blue **Staged deployment** (sub-label *status test, low priority or shadow*) and a dark **Monitor and roll back if needed** complete the path.

**Relationships and arrows.** Each solid arrow means "only after the previous step succeeds": a failing test or a replay that loses a true positive sends the change back, not forward. A dashed feedback arrow runs from the last step back to **Tuning request**, labelled *post-deployment evidence opens the next request*.

**Execution flow.** In the R6 example: the request cites the WS-102 burst; it is reproduced with twelve appended events; the branch contains the `HAVING` change and the two test edits; the suite runs (first FAILED, then 8 tests OK); a replay over the dataset shows R6 dropping from two hits to one with the real beacon kept; a reviewer approves; the new R6 runs at test status; its alert volume and precision are watched.

**Decision logic.** The two orange gates carry the decisions. Unit tests answer "does the rule still do what its specification says?"; replay answers "what will it do to the queue, and which past true positives would it have missed?" Either can stop the change.

**Technical interpretation.** The path is the software engineering idea of continuous integration applied to detections. Tests run automatically on every proposed change; review is recorded; deployment is reversible because every version is kept.

**Practical example.** The R2 two-minute window would stop at **Unit tests** with `FAILED (failures=1)`. The kit's unwindowed R2 would stop at the same gate once the stale-failure test is added, which is how a gap in the specification becomes visible.

**Security implications.** Each step defends against a specific failure: reproduction against fixing the wrong problem, tests against breaking detection, replay against losing true positives, review against one person's blind spot or a malicious insider quietly disabling a rule, and monitoring against effects nobody predicted. Skipping the path for an "urgent" noise reduction is how many SOCs lose a detection without knowing it.

**Key learning.** A rule change is complete only when it has passed tests and replay, been reviewed, been deployed reversibly and been measured afterwards.

## Common mistakes and misconceptions

- **Tuning by intuition** instead of a sweep on stored data and attack-side evidence.
- **Treating precision as the goal.** A rule narrowed to one known variant has traded recall for a tidy number.
- **Suppressing a logic defect.** Excluding the noisy host instead of fixing a definition that is wrong for everyone.
- **Bypassing a failing test.** The R6 failure was an out-of-date fixture; the R2 two-minute failure was a real loss of detection. Only investigation tells them apart.
- **Changing several parameters at once.** Parameters interact; change one, measure, then the next.
- **No record of why.** An undocumented threshold will be changed again by the next person who finds it noisy.

## Security implications, detection and defence

Tuning is attractive to an adversary. An insider, or an attacker who has reached the SIEM console, achieves more by quietly widening a suppression or raising a threshold than by any endpoint evasion. The controls are the change path itself: version control, mandatory review and a monitored audit trail of rule and suppression changes. Changes made outside the pipeline should raise an alert.

Two health signals belong on every detection engineering dashboard: **rules that stopped firing** after a change or a parser update, which may be broken rather than successful, and **suppression growth** per rule with the events each matched. A noisy rule that guards a critical technique, such as clearing the Security log (R5), deserves engineering effort to make it precise, not a suppression that makes it quiet; Lesson 6 turns this into a method for deciding where effort matters most.

## Best practices

- Review per-rule precision and volume on a schedule, worst rules first.
- Diagnose in order (data, logic, numbers, authorised instance) and prefer the most general durable fix.
- Set numbers from a baseline sweep and real attack spacing, with margins, and document the rationale.
- Pair every rule change with test changes; test both sides of every number.
- Replay before deploying, deploy in stages, monitor afterwards and keep rollback a revert.

## Key takeaways

- Tuning changes what the SOC can see; it is held to the same evidence, testing and review standard as writing a rule.
- Measure per-rule precision and volume from dispositions over enough alerts; precision says nothing about what the rule misses.
- Find the cause before the fix: wrong data, logic broader than intent, numbers off baseline, or an authorised instance, in that order.
- A sweep on stored data shows how parameters drive precision; the threat model decides how far they may be loosened or tightened.
- Narrowing R6 with a time span removed a burst false positive for every host, and a test change recorded why.
- Tests guard the numbers: the two-minute R2 window failed the suite, and a new stale-failure test exposed the kit rule's missing window.
- Change control (request, reproduce, branch, test, replay, review, staged deployment, monitoring) is what keeps tuning from becoming a silent loss of detection.
