## Introduction and conceptual foundation

A web proxy stands between an organisation's users and the web. Every request a browser, an update agent or an implant makes over HTTP or HTTPS is handed to the proxy, which decides whether to allow it, forwards it, and writes a log line. Because nearly all modern command and control, malware delivery and data theft travel over web protocols, the proxy's log is often the single most valuable network source a SOC has. It is also the largest: in the Banyan Microfinance lab dataset, proxy events are 284 of the 340 events.

Module 2, Lesson 2 surveyed what proxies record and used three quick analyses on the lab data (volume per host, destinations by number of hosts, and the beacon timeline) to show that proxy metadata can expose a beacon and an exfiltration. This lesson goes further, from survey to method. It covers:

- **The anatomy of a proxy record**, field by field, including the traps: which direction a "bytes" field counts, what a `CONNECT` line can and cannot tell you, and why the status code in a log is sometimes the proxy's, not the website's.
- **What TLS inspection changes** in the log, and what an analyst can still conclude without it.
- **A repeatable analysis workflow** of six questions (rarity, content, rhythm, volume, scope and endpoint pivot), each answered with a real query against the lab dataset using `minisiem.py` and `hunt.py`.
- **How proxy evidence becomes a case**: building a minute-by-minute timeline for WS-104 and stating clearly what the proxy proves and what it does not.

The guiding idea is that a proxy log is a record of *intent made visible*. A person browsing produces irregular requests to popular sites with modest uploads. Software on a timer produces regular requests. Data theft produces an upload out of all proportion to the user's normal behaviour. None of this needs the content of the traffic; it needs the right fields, a baseline and disciplined questions.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Explicit proxy | A proxy that clients are configured to use (by policy, PAC file or WPAD); the browser sends its requests to the proxy deliberately. |
| Transparent proxy | A proxy that intercepts traffic redirected to it by the network, without client configuration. |
| Secure web gateway (SWG) | A proxy, on premises or in the cloud, that adds policy: URL categories, reputation, malware scanning, data loss prevention. |
| `CONNECT` | The HTTP method a client uses to ask a proxy for a raw tunnel to `host:port`, normally to carry HTTPS. Without inspection, the proxy logs the `CONNECT` and the tunnel's totals, not the requests inside it. |
| TLS inspection | The proxy terminates the client's TLS session with a certificate the managed devices trust, inspects the request, and opens its own TLS session to the server. Also called TLS interception or SSL inspection. |
| Bytes out / bytes in | Data sent by the client towards the server (upload) and received from the server (download). W3C extended log format calls them `cs-bytes` and `sc-bytes` (client-to-server, server-to-client). |
| Status code | The HTTP response status. A proxy may log the origin server's status (200, 404) or its own (403 when policy blocks, 407 Proxy Authentication Required). |
| URL category | The SWG's classification of a destination (news, webmail, file sharing, newly registered, uncategorised and so on). |
| User agent | The client software's self-description in the `User-Agent` header; easy to forge, but its absence or oddity is informative. |
| Beacon | Repeated, usually small requests from an implant to its controller at a near-regular interval. |
| Coefficient of variation (CV) | Standard deviation divided by the mean; for request gaps, near 0 means machine-regular timing. |

## Anatomy of a proxy record

### The fields that matter

Proxy products differ in format, but a good record answers the same questions. **When** (timestamp, ideally UTC, and request duration). **Who** (client IP, authenticated user if the proxy requires authentication, and host name if the gateway records it). **Where** (URL or, for uninspected HTTPS, the `CONNECT` host and port; destination IP). **How** (method: GET, POST, PUT, CONNECT; user agent; referer). **What happened** (status code, the proxy's action such as allowed or blocked, the category and any reputation or malware verdict). **How much** (bytes in each direction, and content type).

The widely deployed Squid proxy illustrates the classic layout. Its native `access.log` format writes, per line: a Unix timestamp with milliseconds, the elapsed time in milliseconds, the client address, a result code and HTTP status pair (for example `TCP_MISS/200`), a byte count, the method, the URL, the user identity, the hierarchy code and peer, and the content type. The byte count in that default format is the size of the reply delivered **to the client**, so a default Squid log is good at showing downloads and poor at showing uploads; measuring uploads needs a custom log format that records request sizes. Other gateways log both directions explicitly. Before writing any volume detection, the first question for a new proxy source is always: **which direction does this byte field count?**

### The lab's proxy record

The lab keeps only the fields its detections need. One real line from `banyan_events.jsonl`:

```json
{"@timestamp": "2026-11-03T06:12:00Z", "bytes_out": 812, "host": "WS-104", "source": "proxy", "src_ip": "10.40.0.23", "status": 200, "url": "https://banyan-payroll-update.example/invoice.docm", "user": "divya"}
```

Here `bytes_out` is defined as bytes sent by the client, which is the right direction for exfiltration analysis. The `host`, `user` and `src_ip` fields arrive already joined, which real proxies often do not provide: many log only the client IP, leaving attribution to DHCP and logon evidence. `minisiem.py` stores `ts`, `host`, `user`, `src_ip`, `url` and `bytes_out` as columns; `status` is not one of its normalised columns, but the whole original event is kept in a `raw` column, so it can be read with SQLite's `json_extract(raw, '$.status')`.

Missing from the lab, and worth asking for in production: method, bytes in, content type, user agent, category, action and the destination IP. Several of the techniques below would be stronger with them, and the lesson notes where.

### Status codes: whose answer is it?

A status in a proxy log can come from two places. When the proxy forwards a request, it usually records the origin server's status: 200 for success, 3xx redirects, 404 not found, 5xx server errors. When the proxy itself answers, it records its own: **407** means the client must authenticate to the proxy, and many products use **403** (or a vendor-specific code or action field) when a policy blocks the request. Patterns follow from this:

- A host producing a steady stream of **407** responses is usually software that is not proxy-aware or lacks credentials. That is often a broken updater, but implants that cannot authenticate to the proxy look exactly the same, and their regular 407s are a beacon pattern in their own right.
- A rise in **policy blocks** for one host, especially to uncategorised or newly registered domains, means something is trying destinations the user would not.
- Many **404s** to varied paths on one external host can mean an automated tool probing for a resource.

In the lab dataset, every proxy event is a success, which you can confirm with a real query:

```terminal
$ python minisiem.py search "SELECT json_extract(raw,'$.status') AS status, COUNT(*) n FROM events WHERE source='proxy' GROUP BY status"
status | n
200 | 284
```

The query reads the status from the raw JSON, groups by it and counts. A single status value means the lab cannot teach status-based detection from data; the attacker's requests all succeeded, so their evidence is in rarity, rhythm and volume, which is exactly where the workflow below looks.

### What TLS inspection changes

Most web traffic is HTTPS, and what the proxy can log depends on whether it inspects it.

*Figure 4.11: What a proxy logs for HTTPS, without and with TLS inspection. The fields an analyst gets from an uninspected CONNECT tunnel compared with an inspected HTTPS request.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram compares two proxy log records for the same HTTPS request, one written without TLS inspection and one with it. It matters because analysts constantly over- or under-estimate what their proxy can see; the set of fields available decides which of this lesson's techniques are possible.

**Components.** Two columns are joined by "vs". The left column, **Without TLS inspection** (slate), lists what an uninspected `CONNECT` tunnel yields: "CONNECT cdn-telemetry-sync.example:443", "Host and port only: no path, no query", "Tunnel totals: bytes each way, duration", "Inner HTTP status and method unseen", and "Timing and rarity still visible". The right column, **With TLS inspection** (blue), lists "Full URL: /api/v2/ping", "Method, status, content type", "Per-request bytes out and in", "User agent and referer", and "Malware and DLP scanning possible".

**Relationships.** Each line in the left column has a richer counterpart in the right. The host name is present in both; the path, method and per-request detail appear only on the right. The last line on each side is the important asymmetry: inspection adds content-level controls, but timing and rarity survive even without it.

**Execution flow.** Without inspection, the browser sends `CONNECT host:443` to the proxy, the proxy opens a TCP tunnel and relays encrypted bytes until it closes, then writes one record for the whole tunnel. With inspection, the proxy completes TLS with the client, reads each HTTP request, forwards it over its own TLS session, and writes one record per request.

**Decision logic.** The analyst's question is "which column is my data in?" If the left, beacon detection must use tunnel timing and sizes, and a long-lived tunnel may hide many requests in one record. If the right, per-request rhythm, content type and upload size are all available. Mixed estates are common, because organisations exempt categories such as banking and health from inspection.

**Technical interpretation.** The host in an uninspected `CONNECT` comes from the client's request line and normally matches the TLS server name, but the proxy cannot verify what happens inside the tunnel. Inspection makes the proxy a party to the encryption, which is why it needs trusted certificates on managed devices and why certificate-pinned applications may fail through it.

**Practical example.** The lab's proxy records carry full HTTPS URLs such as `https://cdn-telemetry-sync.example/api/v2/ping`, so Banyan's proxy is in the right-hand column. Without inspection the same beacon would appear as repeated `CONNECT cdn-telemetry-sync.example:443` lines, still regular and still rare, so H1 and R6-style logic would still work on tunnel sizes and timing.

**Security implications.** Inspection is a privacy and legal decision as well as a technical one: under India's DPDP Act 2023, decrypted browsing data is personal data, so purpose, exemptions and access controls must be documented. Where inspection is not used, invest in timing, rarity and volume analytics, and in the DNS evidence of Lesson 5.

**Key learning.** Inspection adds paths, methods and content controls; rarity, timing and volume remain visible either way, and they are what catch most beacons and uploads.

## A six-question workflow for proxy analysis

Proxy logs are too large to read line by line. An analyst who opens a week of proxy data without a method drowns in it. A workflow of six questions, asked in order, turns the volume into a short list of leads and then into evidence. The figure summarises the workflow with the answers the lab dataset gives for WS-104; the sections after it work through each question with real queries.

![Figure 4.12: Six questions for proxy analysis, applied to WS-104](/assets/courses/cyber-08/v2/C08-M04-L06-F2.svg)

*Figure 4.12: Six questions for proxy analysis, applied to WS-104. A top-to-bottom proxy analysis workflow annotated with what each step found in the Banyan lab dataset.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is a top-to-bottom procedure for analysing proxy logs, annotated with what each step found in the Banyan dataset. It shows that each question narrows the field and that the final step leaves the proxy entirely, because a proxy log alone cannot say which process acted.

**Components.** Six steps run from top to bottom. **1 Rarity** (slate) has the sub-label "domains by host count: 3 on one host only". **2 Content** (blue) reads "file types and lookalikes: invoice.docm at 06:12". **3 Rhythm** (orange) reads "interval CV: 18 pings, 300 s, cv=0.004". **4 Volume** (red) reads "bytes_out vs baseline: 48,200,000 at 08:12". **5 Scope** (violet) reads "other hosts, same domains: none found". **6 Pivot to endpoint** (dark) reads "process, account, logs: WINWORD.EXE to powershell.exe". The dark tone marks the step that produces the case's conclusion.

**Relationships and arrows.** Arrows run downward from each step to the next. They mean "feeds the next question", not "always happens next": the rare destinations found in step 1 are the inputs to steps 2 to 4, and the suspicious ones from steps 2 to 4 are the inputs to the scope check in step 5.

**Execution flow.** Start broad, with rarity across the whole estate. Narrow to the rare destinations and ask what kind of content they served (step 2), whether contact was machine-regular (step 3) and whether data left in quantity (step 4). Then widen again: are other hosts touching the same infrastructure (step 5)? Finally cross into endpoint telemetry to find the process and account responsible (step 6).

**Decision logic.** Each step is a filter with a question. Rare but irregular and small, with a normal content type: probably a niche but legitimate site; note it and move on. Rare and regular: a beacon candidate. Rare and large outbound: an exfiltration candidate. Scope finding other hosts turns a single-host case into a campaign and changes its severity.

**Technical interpretation.** The steps rely on different statistics: distinct counts (rarity), string matching (content), dispersion of time gaps (rhythm), comparison with a baseline (volume) and set membership (scope). They are independent views, so agreement between them is strong evidence, and a determined adversary who defeats one (for example by adding jitter) rarely defeats all.

**Practical example.** For Banyan, every step returns something on WS-104: three rare domains; a macro-enabled document from a lookalike domain; an 18-request, five-minute beacon; a 48.2 MB upload; no other hosts involved; and on the endpoint, Word starting PowerShell two minutes after the download.

**Security implications.** The workflow maps onto existing lab detections: steps 3 and 4 are automated by rules R6 and R4 in `minisiem.py` and hunt H1 in `hunt.py`, step 5 by hunt H3. A SOC that automates steps 1 to 5 leaves the analyst's time for step 6 and the judgement it requires.

**Key learning.** Narrow with rarity, characterise with content, rhythm and volume, widen with scope, and prove with the endpoint.

### Question 1: which destinations are rare?

Rarity, the number of distinct hosts that visited a destination, is the cheapest and most powerful first cut. Module 2 ran it by full URL, and Lesson 5 ran it by domain name with first-seen times; both found the same three destinations on WS-104 alone (`banyan-payroll-update.example`, `cdn-telemetry-sync.example` and `files-share-drop.example`), against six domains used by all eight hosts. In a real estate with thousands of users, the same query run over 30 days, grouped by registered domain, typically reduces millions of requests to a few hundred rare destinations, which can then be filtered by category (uncategorised and newly registered first).

### Question 2: what content did they serve, and do they imitate anything?

Content type is the proxy's best clue to delivery. The lab has no content-type field, so the URL's file extension stands in for it. The query below looks for extensions commonly used to deliver malware (macro-enabled Office documents, executables, archives, scripts):

```terminal
$ python minisiem.py search "SELECT url, ts, bytes_out FROM events WHERE source='proxy' AND (url LIKE '%.docm' OR url LIKE '%.exe' OR url LIKE '%.zip' OR url LIKE '%.js')"
url | ts | bytes_out
https://banyan-payroll-update.example/invoice.docm | 2026-11-03T06:12:00Z | 812
```

`LIKE '%.docm'` matches any URL ending in `.docm`; the `OR` list can be extended with the extensions your estate cares about. One hit, from a rare domain whose name imitates the company's own `banyan.example`, named like a finance document and fetched by a finance user. Note `bytes_out` is only 812: this was a download, so the request was small. The size of the file itself would be in a bytes-in field, which the lab does not keep. Real gateways also record the MIME type and, where scanning is enabled, a malware verdict; both are stronger than an extension, which an adversary can choose freely.

### Question 3: is the contact machine-regular?

A beacon is software checking in on a timer, so its signature is regularity. The kit's hunt H1 groups proxy events by host and URL, computes the gaps between consecutive requests, and reports any series of at least eight requests whose gap coefficient of variation is below 0.2:

```terminal
$ python hunt.py
H1 beaconing candidates (>= 8 requests, interval CV < 0.2)
  WS-104 https://cdn-telemetry-sync.example/api/v2/ping n=18 mean_gap=300s cv=0.004
H2 parent-child pairs seen on only one host
  WINWORD.EXE -> powershell.exe hosts=1 n=1
H3 other hosts contacting known-bad domains
  none found
```

H1's line reads: 18 requests, a mean gap of 300 seconds, CV 0.004. The CV is the standard deviation of the gaps divided by their mean, so 0.004 of 300 seconds is a spread of roughly one second; the timestamps confirm gaps such as 06:17:00, 06:22:01, 06:27:03. Human browsing to any site has CVs far higher, because people read, get distracted and leave.

Why a threshold of 0.2 rather than "exactly regular"? Many implants add **jitter**, a random variation of the interval, precisely to defeat naive regularity checks. A 300-second beacon with 20 percent jitter still has a CV well under 1, and still has the other beacon traits: rare destination, small and constant sizes, persistence through the day regardless of the user's activity. Mature hunts therefore score several features together. The lab's rule R6 adds size regularity (at least 10 hits with sizes within 50 bytes); its real output is `('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)`, every request exactly 220 bytes.

A complementary check is persistence within a window. This real query counts, per host and URL, the requests made during the beacon's lifetime and keeps only pairs with five or more:

```terminal
$ python minisiem.py search "SELECT host, url, COUNT(*) hits FROM events WHERE source='proxy' AND ts BETWEEN '2026-11-03T06:17' AND '2026-11-03T07:43' GROUP BY host, url HAVING hits >= 5"
host | url | hits
WS-104 | https://cdn-telemetry-sync.example/api/v2/ping | 18
```

In that 86-minute window no person on any of the eight hosts visited any one site five times; only the beacon did. Popular destinations such as webmail can also be visited often, which is why rarity (Question 1) is applied first: a regular series to a domain all hosts use is usually an update or sync service.

### Question 4: did data leave in quantity?

Exfiltration over the web (ATT&CK T1567, with T1567.002 for cloud storage) shows up as outbound volume that is large for the destination, the user and the time. Compare each host's typical and maximum upload:

```terminal
$ python minisiem.py search "SELECT host, user, COUNT(*) n, ROUND(AVG(bytes_out)) avg_out, MAX(bytes_out) max_out FROM events WHERE source='proxy' GROUP BY host ORDER BY max_out DESC LIMIT 4"
host | user | n | avg_out | max_out
WS-104 | divya | 49 | 984961.0 | 48200000
WS-107 | gopal | 28 | 2040.0 | 3999
WS-102 | ben | 28 | 2315.0 | 3991
WS-106 | farah | 32 | 2441.0 | 3880
```

Every other host's largest single request is under 4,000 bytes. WS-104's is 48,200,000. Note what the average does: WS-104's mean upload of 984,961 bytes is a statistic distorted by one event, and on its own would mislead you into thinking the host uploads a megabyte per request. For volume baselines, prefer the maximum, percentiles or per-destination totals to the mean.

To put the upload in proportion, sum every other proxy request in the dataset:

```terminal
$ python minisiem.py search "SELECT SUM(bytes_out) FROM events WHERE source='proxy' AND url NOT LIKE '%files-share-drop%'"
SUM(bytes_out)
560116
```

All the other 283 proxy requests from the whole company together sent 560,116 bytes. The single upload to `files-share-drop.example/upload` is about 86 times that. The lab's rule R4 automates this check with a fixed threshold (`bytes_out > 10000000`); its real output is `('2026-11-03T08:12:00Z', 'WS-104', 'divya', 'https://files-share-drop.example/upload', 48200000)`. A fixed threshold is easy to explain but blunt: in production it is usually combined with a per-user baseline and a destination category, because legitimate large uploads to the organisation's own sanctioned storage are common, while uploads to an uncategorised file-sharing site seen for the first time that day are not.

### Question 5: is anyone else involved?

Scope decides severity. If other hosts contacted the same infrastructure, the case is a campaign, and the containment advice changes. H3 searches every host other than WS-104 for the three known-bad domains, and its output above reads `none found`. The query behind it uses `url LIKE '%://cdn-telemetry-sync.example/%'` and its siblings; matching the scheme separator and trailing slash prevents a lookalike such as `cdn-telemetry-sync.example.org` from creating a false match, a small but real lesson in writing indicator searches.

Scope searches should use every indicator the case has produced, not only domains: the destination IP addresses (from DNS answers or the proxy's destination-IP field), the exact URL path `/api/v2/ping` on other domains, the user agent if logged, and the 220-byte request size. Lesson 5's DNS view would add any host that merely *resolved* the names without connecting.

### Question 6: what does the endpoint say?

The proxy proves that requests left WS-104 with divya's identity attached. It does not prove that divya made them, nor which program did. Step 6 crosses to endpoint telemetry for the same host and minutes. H2 in the hunt output already pointed at the answer, `WINWORD.EXE -> powershell.exe`, a parent-child pair seen on one host only, first met in Module 2, Lesson 1. The next section joins the two sources into one timeline.

The file names would come from endpoint file-access telemetry or the destination service, neither of which is in the dataset. Similarly, the beacon's purpose (command and control) is an inference from its rhythm, rarity and the PowerShell start, a strong one but an inference.

## Common mistakes and misconceptions

- **"Bytes means upload."** In many default formats, Squid's native log among them, the byte count is the reply sent to the client. Check the field definition before writing any exfiltration rule.
- **"The proxy's user is the person."** The authenticated user is the account whose credentials or session the request carried. Software running in that user's session, an implant included, inherits the same identity. The lab's beacon is logged as divya; that does not mean divya clicked anything after 06:12.
- **"Average upload per host is a good baseline."** One large event distorts a mean, as WS-104's 984,961-byte average shows. Use maxima, percentiles or per-destination totals.
- **"No inspection, no detection."** Uninspected `CONNECT` records still carry host, timing and tunnel volume; rarity, rhythm and volume analysis work on them.
- **"Status 200 means safe."** All the attacker's lab requests returned 200. Success codes are evidence that the activity worked, not that it was benign.
- **"Block the domain and close the alert."** Blocking `cdn-telemetry-sync.example` stops one channel; the process that beaconed is still on the host, and the scope check must still run.
- **"Proxy logs cover all egress."** Traffic that bypasses the proxy (direct connections, non-web protocols, remote users off the network without a cloud gateway) is invisible to it; firewall logs (Lesson 4) must show such traffic is blocked or at least recorded.

## Security implications, detection and defence

Proxy evidence covers several ATT&CK techniques directly: **T1071.001** (Application Layer Protocol: Web Protocols) for HTTPS command and control, **T1105** (Ingress Tool Transfer) for tools downloaded after compromise, **T1204.002** (User Execution: Malicious File) for the document fetched by the user, **T1567** and **T1567.002** (Exfiltration Over Web Service, to cloud storage) and **T1041** (Exfiltration Over C2 Channel) when data rides the beacon itself. The lab's R4 and R6 rules and H1 and H3 hunts are compact implementations of four of the six workflow questions.

Defensive controls that make proxy analysis possible and useful:

- **Force egress through the proxy.** Block direct outbound HTTP and HTTPS from workstations at the firewall, so the proxy log is complete. Extend coverage to remote users with a cloud SWG or always-on VPN.
- **Require authentication** where practical, so that requests carry a user identity; record the host name too if the gateway can.
- **Log both byte directions, method, status, content type, user agent, category, action and destination IP**, in UTC, and forward them centrally.
- **Use categories and reputation**: block or warn on newly registered and uncategorised domains, and restrict uploads to sanctioned file-sharing services. Data loss prevention can inspect uploads where TLS inspection is in place.
- **Decide TLS inspection deliberately**, with documented exemptions (banking, health and similar), restricted access to decrypted data, and a legal basis recorded under the DPDP Act 2023. Retain logs to meet CERT-In's 180-day requirement for ICT system logs.

> [!WARNING]
> Proxy logs reveal what individuals read and where they bank, shop and seek medical help. Access to them should be role-based and audited, queries should have a case or hunt reference, and analysts must not browse colleagues' histories out of curiosity. Misuse of personal data can breach the DPDP Act 2023 and the organisation's own policy.

## Best practices

- Write down the field definitions of every proxy source when it is onboarded: byte direction, whose status code, time zone, and whether user and host are present.
- Run rarity by registered domain over a long window (30 days) and prioritise rare destinations that are uncategorised or newly registered.
- Score beacons on several features together (rarity, interval CV, size regularity, persistence) so that jitter alone does not defeat detection.
- Baseline uploads per user and per destination category, and treat first-time large uploads to unsanctioned storage as high priority.
- Scope with every indicator a case produces, written to avoid substring false matches, as H3's patterns do.
- End every proxy-based finding with an endpoint pivot, and word conclusions at the strength the proxy evidence supports.

## Key takeaways

- A proxy record answers when, who, where, how, what happened and how much; know which direction your byte field counts and whose status code it holds before writing detections.
- Without TLS inspection you lose paths and content, not rarity, timing or volume; most beacons and uploads are caught on those.
- The six-question workflow (rarity, content, rhythm, volume, scope, endpoint pivot) turned 284 proxy events into one case on WS-104: a lookalike `.docm` download, an 18-request 300-second beacon with CV 0.004, and a 48,200,000-byte upload about 86 times all other proxy uploads combined.
- Proxy identity is the session's identity, not proof of a person's action; the endpoint pivot shows which process acted.
- Conclusions from proxy logs must be stated at the evidence's strength: the proxy proves that data left and where it went, not what it was.
