## Introduction and conceptual foundation

The first six lessons of this module taught you to read individual log sources. Reading is half the job; the other half is asking the logs a question and getting back an answer you can defend, which in every SOC means writing a query.

Module 3 Lesson 6 (Searching) introduced the mechanics: time ranges, filters, aggregations, stacking and pivots in the course's teaching SIEM, `minisiem.py`. This lesson is about **precision**. A query is a measuring instrument. When an analyst writes "no other host contacted the beacon domain", the sentence is only as good as the query behind it. A query that silently drops events, matches events it should not, or counts the same event several times produces a number that looks authoritative and is wrong, and that number goes into a case note and an escalation.

Query writing therefore has three parts: turning a vague analytical question into a **specification**; expressing it without the classic traps (type mismatches, substring matches that catch look-alikes, time boundaries that exclude the event you care about, joins that multiply rows, exclusions that one missing value breaks); and **testing** the query against cases where you already know the answer.

All examples are real SQL run with `minisiem.py search` against the course dataset: 340 synthetic Banyan Microfinance events (Windows Security, Sysmon-style endpoint, web proxy and VPN) for 3 November 2026, all times UTC, with outputs shown unedited. SPL and KQL equivalents are named where they are well established; the traps exist in every query language.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Analytical question | The question in plain language that the query must answer, written down before the query. |
| Query specification | The question restated as population, condition, grain, window and output. |
| Population | The events the query is allowed to consider: which sources and which time range. |
| Predicate | A condition that each event either satisfies or not (`source='proxy'`). |
| Grain | What one row of the result represents: one event, one host, one host and domain pair, one hour. |
| False match | An event or row the query returns that does not satisfy the question's intent. |
| Missed match | An event that satisfies the intent but which the query fails to return. |
| Precision (of a query) | The share of returned results that are genuine matches. |
| Recall (of a query) | The share of genuine matches that the query returns. |
| Anchored match | A comparison tied to a field's structure (a whole domain, the start of a URL) rather than a substring anywhere. |
| Half-open interval | A time range written as `start <= ts < end`, which includes the start and excludes the end. |
| Join fan-out | Row multiplication when each row on one side of a join matches several rows on the other. |
| Anti-join | A query for rows that have no matching row elsewhere ("accounts never created"). |
| CTE | Common table expression, a named sub-result introduced with `WITH name AS (...)`. |
| Window function | A function such as `LAG()` that reads neighbouring rows without collapsing them (`OVER (PARTITION BY ... ORDER BY ...)`). |
| Known positive / known negative | A test case where you already know the query must, or must not, return a result. |

## From question to specification

A shift lead asks "did the phish hit anyone else?"; an alert says "beacon_regular_small on WS-104". Neither is yet something a query can answer, because each leaves open what counts, over what period and at what level of detail. The discipline is to write a short specification first, in five parts, each preventing a specific error.

**1. Population: which events may count.** Name the sources and the time range. "Did the phish hit anyone else?" concerns proxy events (who requested the look-alike domain) and perhaps endpoint events, from before the first known click until now. Too narrow and you miss matches; too broad and the query is slow and sweeps in unrelated history.

**2. Condition: the precise predicate.** "Hit the phishing domain" becomes "the request's host part equals `banyan-payroll-update.example`", not "the URL contains `banyan`" (you will see below why). Test the field that carries the meaning, in the right type and letter case.

**3. Grain: what one result row is.** One event, one host, one host and domain pair, one hour? "Anyone else" is about hosts and users, so the grain is one row per host and user, with a count and first and last time. The grain decides your `GROUP BY` and, if you join, what must not be multiplied.

**4. Window: how events relate in time.** Some questions relate events to each other: "within fifteen minutes before the log was cleared", "every five minutes". State the window explicitly, including whether its edges are inclusive.

**5. Output: what the reader needs.** Usually the entity, a count, first and last time and one or two distinguishing fields. Output that cannot be read at a glance often means the grain is wrong.

The query is then tested against **known positives** (cases it must find) and **known negatives** (benign cases it must not return), and checked with its final filter removed, before it goes into the case notes.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows the path from a loosely worded analytical question to a saved, documented query that can be relied on as evidence. It matters because most wrong answers in investigations come not from bad syntax but from a step in this path being skipped: the population was never stated, the condition was a guess, or the query was never tested.

**Components.** Seven rounded boxes run from top to bottom. **Analytical question** (orange) is the starting point, with the example "did the phish hit anyone else?". **Population** (slate) names the sources and time range. **Condition** (blue) holds the precise predicates on normalised fields. **Grain** (violet) states what one result row represents. **Window and output** (blue) covers relationships in time plus the fields, sort and limit. **Test** (green) runs the query against known positives and known negatives. **Saved, documented query** (dark) is the outcome: the query text, its specification and its result, recorded with the case. A feedback arrow runs from the last box back to the first, labelled "failed test or new question: refine the specification".

**Relationships and arrows.** Each downward arrow means "the previous decision constrains this one". The grain cannot be chosen until the condition is known, because the condition determines which entities appear; the output cannot be designed until the grain is fixed. The feedback arrow carries two kinds of traffic: a test that failed (the query missed a known positive or returned a known negative) and a result that raises a new question.

**Execution flow.** In practice the first five boxes take a minute or two of thought and a few lines in the case notes. The test box is where time is spent: run the query, run it again without its final `HAVING` or threshold, run it against an event you know about. Only when those checks agree does the query move to the dark box.

**Decision logic.** At **Test** the analyst decides between three outcomes: the query is precise enough to record; it returns false matches, so the condition must be anchored more tightly; or it misses a known positive, so the population, type or time boundary must be fixed. Each failure loops back to the box responsible.

**Technical interpretation.** In SQL the boxes map onto clauses. Population is the `FROM` and the time part of `WHERE`; condition is the rest of `WHERE`; grain is `GROUP BY` (or its absence); window is a time predicate, a windowed join or a window function; output is `SELECT`, `ORDER BY` and `LIMIT`. In SPL or KQL the same decisions appear as the index or table, the time picker, `where` stages and `stats` or `summarize ... by`.

**Practical example.** For "did the phish hit anyone else?" the population is proxy events for the lab day; the condition is "extracted domain equals `banyan-payroll-update.example`"; the grain is one row per host and user; the output is a count and first time. The known positive is WS-104 and divya, already confirmed by the alert. The answer, one row for WS-104, is recorded with the query.

**Security implications.** An untested query that returns nothing is indistinguishable from a tested query that proves absence. Investigations are closed on "no other hosts affected" statements, so this path is a control against missed scope, not a formality.

**Key learning.** Write the specification before the query, and test the query on what you already know before you trust it on what you do not.

## Conditions that mean what you think

Most false and missed matches come from conditions that look right and are not. Three traps recur in every query language: comparing values of the wrong type, matching substrings where the meaning lives in a structured part of a field, and time boundaries that fall in the wrong place.

### Types: a number is not a string

Windows event IDs arrive from the collector as JSON numbers, and minisiem stores them as SQLite integers. A question such as "how many accounts were created?" written with the event ID in quotes gives a confident wrong answer:

```terminal
$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE event_id='4720'"
COUNT(*)
0

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE event_id=4720"
COUNT(*)
1

$ python minisiem.py search "SELECT typeof(event_id), COUNT(*) FROM events GROUP BY 1"
typeof(event_id) | COUNT(*)
integer | 46
null | 294
```

The text `'4720'` and the integer `4720` are different values to SQLite here, because the `events` table was created without declared column types and so does not convert one into the other. The third query is the diagnostic: `typeof()` shows that the 46 Windows and Sysmon events hold integers and the 294 proxy and VPN events hold no event ID at all. Other platforms coerce types silently or map fields differently per source, so the portable habit is to check a field's stored type before filtering on it, especially for identifiers that look numeric: event IDs, ports, status codes.

### Substrings: matching the meaning, not the characters

A URL is not a string of characters with no structure; it has a scheme, a host, a path and a query. An analyst who wants "Banyan's internal sites" and writes a substring test gets something else:

```terminal
$ python minisiem.py search "SELECT url, COUNT(*) FROM events WHERE url LIKE '%banyan%' GROUP BY url"
url | COUNT(*)
https://banyan-payroll-update.example/invoice.docm | 1
https://crm.banyan.example/ | 37
https://intranet.banyan.example/ | 37
https://mail.banyan.example/ | 51
```

The fourth row is the phishing look-alike, chosen by the attacker precisely because it contains `banyan`. Used to exclude "internal traffic", this query would have removed the request that started the intrusion. In reverse, an indicator search by a short fragment returns far more than the indicator:

```terminal
$ python minisiem.py search "SELECT url, COUNT(*) FROM events WHERE url LIKE '%cdn%' GROUP BY url"
url | COUNT(*)
https://cdn-telemetry-sync.example/api/v2/ping | 18
https://cdn.example.org/ | 46
```

Sixty-four rows, of which 18 are the beacon and 46 are an ordinary content delivery site that all eight workstations use. The query's precision is 18 out of 64, about 28 per cent, and an analyst reading the count alone would overstate the scale of the beaconing more than threefold.

The fix is to compare the part of the field that carries the meaning. For URLs that is the host part. The dataset's URLs all begin with `https://`, which is eight characters, so the domain is the text from character 9 up to the next `/`:

```terminal
$ python minisiem.py search "SELECT substr(url, 9, instr(substr(url, 9), '/') - 1) AS domain, COUNT(*) AS n FROM events WHERE source='proxy' GROUP BY domain ORDER BY n DESC"
domain | n
mail.banyan.example | 51
news.example.com | 48
cdn.example.org | 46
maps.example.net | 45
intranet.banyan.example | 37
crm.banyan.example | 37
cdn-telemetry-sync.example | 18
files-share-drop.example | 1
banyan-payroll-update.example | 1
```

`substr(url, 9)` drops the scheme, `instr(..., '/')` finds the next slash, and the outer `substr` keeps what lies before it. Now "Banyan's internal sites" becomes `domain LIKE '%.banyan.example'` (a suffix test that requires the dot) and "the beacon" becomes `domain = 'cdn-telemetry-sync.example'`, which returns exactly 18. This extraction is a teaching shortcut that works only because every URL here uses `https://` and has a path; production SIEMs parse URLs into fields at ingest (Module 3 Lesson 2), and you should query those.

One more `LIKE` detail: `_` matches exactly one character, so `target_user LIKE 'svc_%'` matches `svc_update` but equally `svcXupdate`. Where an underscore must be literal, use an escape clause or an exact comparison.

### Time boundaries: inclusive edges on text timestamps

Times in minisiem are ISO 8601 strings in UTC, such as `2026-11-03T07:02:00Z`. String comparison orders them correctly only when both sides use the same full format. A natural-looking range "from 06:00 up to and including 07:02" written with short strings misses events:

```terminal
$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE host='WS-104' AND ts BETWEEN '2026-11-03T06:00' AND '2026-11-03T07:02'"
COUNT(*)
15

$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE host='WS-104' AND ts >= '2026-11-03T06:00:00Z' AND ts < '2026-11-03T07:03:00Z'"
COUNT(*)
17

$ python minisiem.py search "SELECT ts, host, url FROM events WHERE ts LIKE '2026-11-03T07:0%' ORDER BY ts"
ts | host | url
2026-11-03T07:02:00Z | WS-104 | None
2026-11-03T07:02:02Z | WS-104 | https://cdn-telemetry-sync.example/api/v2/ping
2026-11-03T07:03:00Z | WS-104 | None
2026-11-03T07:07:01Z | WS-104 | https://cdn-telemetry-sync.example/api/v2/ping
2026-11-03T07:08:00Z | WS-103 | https://intranet.banyan.example/
```

The short upper bound `'2026-11-03T07:02'` sorts before `'2026-11-03T07:02:00Z'`, because a string that is a prefix of another sorts first. So `BETWEEN` excluded both events in the 07:02 minute, and one of them is the 4720 event that created the `svc_update` account, the most important event in that window. The second query uses a **half-open interval** in the full stored format: it includes the start, excludes the end, and ends at 07:03:00 to cover the whole 07:02 minute. Half-open intervals also tile cleanly: consecutive windows never count an event twice or drop one on the boundary. Native timestamps and time pickers on real platforms remove the string-prefix trap but not the boundary question, so record the exact range and zone in the case notes.

## Choosing the grain

The wrong grain answers a different question. Take "which workstation sent more than 1 MB in total to a destination that no other workstation uses?" Population: proxy events for the day. Condition: destination breadth of one host and total bytes over 1,000,000. Grain: one row per host, user and domain. Two grains are involved: breadth belongs to a domain, the byte total to a host and domain pair. CTEs keep them separate:

```terminal
$ python minisiem.py search "WITH e AS (SELECT host, user, ts, bytes_out, substr(url, 9, instr(substr(url, 9), '/') - 1) AS domain FROM events WHERE source='proxy'), breadth AS (SELECT domain, COUNT(DISTINCT host) AS hosts FROM e GROUP BY domain) SELECT e.host, e.user, e.domain, COUNT(*) AS requests, SUM(e.bytes_out) AS bytes_out, MIN(e.ts) AS first_ts FROM e JOIN breadth b ON b.domain = e.domain WHERE b.hosts = 1 GROUP BY e.host, e.user, e.domain HAVING SUM(e.bytes_out) > 1000000"
host | user | domain | requests | bytes_out | first_ts
WS-104 | divya | files-share-drop.example | 1 | 48200000 | 2026-11-03T08:12:00Z
```

The first CTE, `e`, defines the population and derives the domain once. The second, `breadth`, works at the domain grain and counts distinct hosts. The final query joins the two on domain, so every proxy event knows how widespread its destination is, then groups at the host, user and domain grain and applies the byte threshold in `HAVING`, because the total exists only after grouping.

Now test it. Removing the final `HAVING` shows what the threshold removed:

```terminal
$ python minisiem.py search "WITH e AS (SELECT host, user, ts, bytes_out, substr(url, 9, instr(substr(url, 9), '/') - 1) AS domain FROM events WHERE source='proxy'), breadth AS (SELECT domain, COUNT(DISTINCT host) AS hosts FROM e GROUP BY domain) SELECT e.host, e.user, e.domain, COUNT(*) AS requests, SUM(e.bytes_out) AS bytes_out, MIN(e.ts) AS first_ts FROM e JOIN breadth b ON b.domain = e.domain WHERE b.hosts = 1 GROUP BY e.host, e.user, e.domain"
host | user | domain | requests | bytes_out | first_ts
WS-104 | divya | banyan-payroll-update.example | 1 | 812 | 2026-11-03T06:12:00Z
WS-104 | divya | cdn-telemetry-sync.example | 18 | 3960 | 2026-11-03T06:17:00Z
WS-104 | divya | files-share-drop.example | 1 | 48200000 | 2026-11-03T08:12:00Z
```

Three single-host destinations exist; the threshold keeps only the 48.2 MB upload. The beacon's 18 requests totalled 3,960 bytes, so a volume query never catches a beacon; that needs an interval query. And a per-event threshold would miss an upload split into many 900 KB requests, which summing at the pair grain catches.

## Joins without surprises

A join relates events: a Windows event and the web requests around it, a VPN success and the failures before it. Joins are also the easiest way to produce a number that is simply wrong.

### Fan-out: rows multiply

Each Windows event on WS-104 joined to each proxy event on WS-104 by host alone:

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) FROM events WHERE host='WS-104' GROUP BY source"
source | COUNT(*)
proxy | 49
sysmon | 5
windows | 4

$ python minisiem.py search "SELECT COUNT(*) FROM events w JOIN events p ON p.host = w.host WHERE w.source='windows' AND p.source='proxy' AND w.host='WS-104'"
COUNT(*)
196
```

Four Windows events and 49 proxy events produce 196 joined rows, because the only join condition is the host; any `COUNT(*)` or `SUM(bytes_out)` over that result counts each proxy request four times. This is **fan-out**, and it is why rule R2 counts `COUNT(DISTINCT f.user)`. The defences: bound the join with a time window, and count distinct values or aggregate each side before joining.

### Windowed joins: only the rows that relate

The question "what web activity preceded each account-management or log-clearing event on the host, within fifteen minutes?" has a grain of one row per Windows event and a window of fifteen minutes before it. A `LEFT JOIN` keeps every Windows event even if no proxy event qualifies:

```terminal
$ python minisiem.py search "SELECT w.ts, w.event_id, w.target_user, COUNT(p.ts) AS proxy_15m_before, COUNT(DISTINCT p.url) AS urls FROM events w LEFT JOIN events p ON p.host = w.host AND p.source='proxy' AND p.ts < w.ts AND julianday(w.ts) - julianday(p.ts) <= 15/1440.0 WHERE w.source='windows' AND w.event_id IN (4720, 4732, 1102) GROUP BY w.ts, w.event_id ORDER BY w.ts"
ts | event_id | target_user | proxy_15m_before | urls
2026-11-03T07:02:00Z | 4720 | svc_update | 3 | 1
2026-11-03T07:03:00Z | 4732 | svc_update | 3 | 1
2026-11-03T08:17:00Z | 1102 | None | 3 | 2
```

`julianday()` converts each timestamp to a fractional day, so `15/1440.0` is fifteen minutes. The window conditions sit in `ON`, not `WHERE`: in a `LEFT JOIN`, a `WHERE` condition on the right-hand table discards unmatched rows and turns it back into an inner join. Expanding the last row:

```terminal
$ python minisiem.py search "SELECT w.ts, w.event_id, p.ts AS proxy_ts, p.url FROM events w JOIN events p ON p.host = w.host AND p.source='proxy' AND p.ts < w.ts AND julianday(w.ts) - julianday(p.ts) <= 15/1440.0 WHERE w.source='windows' AND w.event_id = 1102 ORDER BY p.ts"
ts | event_id | proxy_ts | url
2026-11-03T08:17:00Z | 1102 | 2026-11-03T08:02:00Z | https://mail.banyan.example/
2026-11-03T08:17:00Z | 1102 | 2026-11-03T08:11:00Z | https://mail.banyan.example/
2026-11-03T08:17:00Z | 1102 | 2026-11-03T08:12:00Z | https://files-share-drop.example/upload
```

The Security log was cleared five minutes after the 48.2 MB upload. The windowed join made that relationship visible without reading 49 proxy events.

### Anti-joins: the NULL that empties a result

Questions about absence ("which accounts were not created today?", "which hosts have never contacted this domain?") are anti-joins. The intuitive `NOT IN` form has a well-known trap:

```terminal
$ python minisiem.py search "SELECT COUNT(DISTINCT user) FROM events WHERE user NOT IN (SELECT target_user FROM events)"
COUNT(DISTINCT user)
0

$ python minisiem.py search "SELECT COUNT(DISTINCT user) FROM events e WHERE NOT EXISTS (SELECT 1 FROM events c WHERE c.target_user = e.user)"
COUNT(DISTINCT user)
8
```

The subquery returns `target_user` for all 340 events, and 338 of them are NULL. `x NOT IN (list)` is true only if `x` is known to differ from every element; against NULL the result is unknown, so no row qualifies. `NOT EXISTS` asks whether any row matches, and NULLs never match, so it returns the eight Banyan users. Filtering NULLs out of the subquery also fixes `NOT IN`, but `NOT EXISTS` is the safer default. KQL's `join kind=leftanti` expresses the same anti-join directly.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram compares three imprecise conditions with the precise conditions that answer the same questions, using the real row counts from the Banyan dataset. It matters because each imprecise form runs without error and returns a plausible number, which is exactly why it survives into case notes.

**Components.** There are two code panels. The left panel, in red, is titled **Imprecise: a confident wrong answer**. The right panel, in green, is titled **Precise: says what the question means**. Each panel contains three short blocks separated by blank lines, and each block begins with a comment line stating the intent, then the condition, then a result line giving the real row count. Highlighted text marks the part of each condition that causes or fixes the problem.

**Relationships.** The blocks pair across the panels row by row. The first pair is the indicator search: `url LIKE '%cdn%'` returns 64 rows on the left, while comparing the extracted domain with `cdn-telemetry-sync.example` returns 18 on the right. The second pair is the time boundary: the short-string `BETWEEN` returns 15 rows and excludes the 07:02 events, while the half-open interval in full format returns 17. The third pair is the anti-join: `NOT IN` against an unfiltered subquery returns 0, while `NOT EXISTS` returns the 8 accounts.

**Execution flow.** Reading top to bottom follows the order of this lesson: a substring condition, a time condition, then an exclusion that depends on another query. In each case the left form is what an analyst types first and the right form is what a reviewer should insist on.

**Decision logic.** Each pair embodies one decision rule. If the meaning lives in a part of a field, compare that part, not a substring of the whole. If a range must include an edge, use a half-open interval in the stored format and move the end. If an exclusion list can contain NULL, use `NOT EXISTS` or filter NULLs out.

**Technical interpretation.** The first trap is a precision failure (false matches inflate the count). The second is a recall failure (missed matches at the boundary). The third is a logic failure caused by SQL's three-valued logic, in which a comparison with NULL is neither true nor false. Other platforms show the same failures with different syntax: substring operators such as KQL's `contains`, time pickers with inclusive or exclusive edges, and exclusion lookups that behave unexpectedly on empty fields.

**Practical example.** An analyst asked "how much beaconing was there?" who used the left-hand indicator search would report 64 requests from eight hosts; the right-hand search reports 18 requests from WS-104 only, which changes the incident's scope from estate-wide to one workstation.

**Security implications.** Precision failures waste responders' time and erode trust in the SOC's numbers; recall failures and logic failures are worse, because they close questions that should stay open. An exclusion that returns zero reads as reassurance when it is really a broken query.

**Key learning.** A query that runs is not a query that is right: anchor conditions to the meaningful part of a field, write half-open time ranges, and use NULL-safe exclusions.

## Time windows inside the query

Beyond the windows of Module 3 Lesson 4, two time techniques answer questions a plain filter cannot: bucketing, to compare periods, and reading the previous event, to measure intervals.

### Buckets: comparing one entity with everyone

"Was WS-104's web activity unusual, and when?" needs one-hour buckets with WS-104 beside the estate. Grouping on the hour digits gives the buckets, and `SUM(host='WS-104')` counts rows where the comparison is true (SQLite evaluates it as 1):

```terminal
$ python minisiem.py search "SELECT substr(ts, 12, 2) AS hour_utc, SUM(host='WS-104') AS ws104, COUNT(*) AS all_hosts FROM events WHERE source='proxy' GROUP BY hour_utc ORDER BY hour_utc"
hour_utc | ws104 | all_hosts
03 | 3 | 16
04 | 3 | 45
05 | 1 | 24
06 | 14 | 37
07 | 11 | 36
08 | 3 | 32
09 | 5 | 26
10 | 2 | 25
11 | 5 | 32
12 | 2 | 11
```

WS-104 normally makes one to five requests an hour; in the 06 and 07 hours it made 14 of 37 and 11 of 36, roughly a third of all proxy traffic. The buckets do not say why; they say when to look. On real platforms use the time-bucketing function rather than a substring.

### The previous event: measuring intervals

Regularity is a property of the gaps between events. A **window function** reads neighbouring rows without collapsing them: `LAG(ts) OVER (PARTITION BY host, url ORDER BY ts)` gives each request the time of the same host's previous request to the same URL. The outer query summarises the gaps:

```terminal
$ python minisiem.py search "WITH r AS (SELECT host, url, ts, LAG(ts) OVER (PARTITION BY host, url ORDER BY ts) AS prev_ts FROM events WHERE source='proxy') SELECT host, url, COUNT(*) AS gaps, ROUND(AVG((julianday(ts) - julianday(prev_ts)) * 86400)) AS mean_gap_s, ROUND(MIN((julianday(ts) - julianday(prev_ts)) * 86400)) AS min_gap_s, ROUND(MAX((julianday(ts) - julianday(prev_ts)) * 86400)) AS max_gap_s FROM r WHERE prev_ts IS NOT NULL GROUP BY host, url HAVING gaps >= 8 ORDER BY max_gap_s - min_gap_s LIMIT 5"
host | url | gaps | mean_gap_s | min_gap_s | max_gap_s
WS-104 | https://cdn-telemetry-sync.example/api/v2/ping | 17 | 300.0 | 298.0 | 302.0
WS-103 | https://cdn.example.org/ | 9 | 3113.0 | 180.0 | 5820.0
WS-103 | https://intranet.banyan.example/ | 10 | 2982.0 | 300.0 | 6240.0
WS-107 | https://mail.banyan.example/ | 8 | 3172.0 | 60.0 | 11400.0
WS-108 | https://maps.example.net/ | 8 | 3698.0 | 420.0 | 18060.0
```

Eighteen requests give 17 gaps (the first row has no predecessor, hence `prev_ts IS NOT NULL`); multiplying a `julianday` difference by 86,400 gives seconds. The beacon's gaps lie between 298 and 302 seconds; the next most regular series ranges from 3 minutes to over 90. This matches the kit's `hunt.py` (`mean_gap=300s cv=0.004`) and, unlike rule R6, does not depend on constant byte sizes. The partition must be the series being measured: partitioning by host alone would interleave the beacon with ordinary browsing and hide it.

## Testing a query before you trust it

**Known positives.** The large-upload query must return the upload rule R4 already found. A missing known positive means a recall problem: a type, a boundary, a case or a NULL.

**Known negatives.** The `%cdn%` search returning `cdn.example.org`, used by all eight workstations, is a known negative showing up: a precision problem.

**Remove the last filter.** Drop the final `HAVING` or threshold. If rows just below the cut look like rows above it, the threshold is arbitrary.

Precision and recall give these checks numbers. If a query returns $R$ rows of which $T$ are genuine, and there are $G$ genuine matches in total, then

$$\text{precision} = \frac{T}{R}, \qquad \text{recall} = \frac{T}{G}$$

For the `%cdn%` search, $T = 18$, $R = 64$ and $G = 18$: precision about 0.28, recall 1.0. For the short-string time range, which returned 15 of the 17 WS-104 events in the intended window, precision is 1.0 but recall is $15/17 \approx 0.88$, and the missing two include the account creation. You rarely know $G$ in real work, which is why known-positive tests matter. Module 7 automates this with the kit's `test_rules.py`; for investigative queries, note which checks you ran.

## Equivalents in SPL and KQL

The table maps the operations used here to well-established forms in Splunk's SPL and Microsoft's KQL (Sentinel, Defender); check your platform's documentation for options and limits.

| Operation | minisiem SQL | SPL | KQL |
| --- | --- | --- | --- |
| Filter rows | `WHERE source='proxy'` | `search` terms or `where` | `where` |
| Count by entity | `GROUP BY host` with `COUNT(*)` | `stats count by host` | `summarize count() by host` |
| Distinct count | `COUNT(DISTINCT user)` | `stats dc(user) by src_ip` | `summarize dcount(user) by src_ip` |
| Filter after aggregation | `HAVING n >= 5` | a `where` after `stats` | a `where` after `summarize` |
| Time buckets | `substr(ts, 12, 2)` (teaching shortcut) | `bin _time span=1h` or `timechart` | `bin(TimeGenerated, 1h)` |
| Case-insensitive equality | `lower(host) = 'ws-104'` | depends on command (see note) | `=~` (while `==` is case-sensitive) |
| Join | `JOIN ... ON` | `join` (often replaced by `stats` over both sources) | `join kind=inner (...) on host` |
| Anti-join | `NOT EXISTS (...)` | a subsearch with `NOT` | `join kind=leftanti` |

Three cautions. In KQL, `dcount()` returns an estimate on large data sets, which matters when a threshold sits close to the count. In SPL, matching of field values in the `search` command is not case-sensitive, while comparisons in `where` are, so the same condition can behave differently in two places of one pipeline. In both languages, substring operators (KQL's `contains`, SPL wildcards) carry exactly the false-match risks shown above with `LIKE`.

## Common mistakes and misconceptions

- **"The query ran, so the answer is right."** Syntax errors are the cheap failures. The expensive ones run cleanly: the quoted event ID, the `%banyan%` exclusion, the short time bound, the `NOT IN` that returned zero.
- **Reporting `COUNT(*)` after a join.** Fan-out multiplies rows; 196 joined rows on WS-104 described 49 proxy requests. Count distinct values or aggregate before joining.
- **Putting outer-join conditions in `WHERE`.** In a `LEFT JOIN`, conditions on the right-hand table belong in `ON`; in `WHERE` they silently turn the query into an inner join.
- **Substring matching on structured fields.** URLs, paths, command lines and email addresses have parts. Compare the part that carries the meaning, and prefer fields the platform has already parsed.
- **Treating zero as proof of absence.** Zero is a result to explain, not a conclusion. Check it with a known positive before writing "not found".
- **Thresholds at the wrong grain.** A per-event threshold misses activity split across many events; a per-host threshold may hide which destination was involved. Apply the threshold at the grain the question is about.
- **Undocumented time ranges.** "In the last 24 hours" means nothing in a case read next week. Record absolute start and end, their inclusivity and the zone.

## Security implications, detection and defence

Queries are part of the evidence chain. A containment decision or a notification to CERT-In may rest on one query result, so it must be reproducible: saved with the case, with its specification, time range and run time.

False matches send responders to the wrong machines and teach the organisation to ignore the SOC. Missed matches close scoping early and leave a second foothold in place; gopal's VPN session from the spraying address is exactly what an over-narrow host-based query never reaches.

Queries also access personal data: proxy logs show what named employees browsed. In line with the DPDP Act 2023's purpose limitation, search for a defined investigative purpose, return only the fields needed, and use platforms that audit who searched for what. On a shared SIEM, unbounded queries can starve scheduled detections; time-bounding every search is the first control.

## Best practices

- Write the specification (population, condition, grain, window, output) in the case notes before the query.
- Check field types and fill rates per source before filtering on them; `typeof()` and a `GROUP BY` of the field are enough in minisiem.
- Compare parsed parts of structured fields; use exact matches for known values and anchored patterns where you must match a pattern.
- Use half-open time ranges in the stored format, and record absolute times with the zone.
- Bound every join with a key and a time window; count distinct values after joins.
- Use `NOT EXISTS` (or a platform's anti-join) for absence questions.
- Build long queries from named CTEs or pipeline stages that you can run one at a time.
- Test with a known positive, a known negative and the last filter removed; record which you used.
- Save the final query with the case, and give it a name that says what it answers.

## Practical exercise (authorised lab only)

Work only in your copy of the C08 kit. For each question write the specification, the query and one test.

1. **Spray breadth.** "Which external addresses failed against at least five different accounts on the VPN, and how many failures did each account receive?" Known positive: 203.0.113.66, eight accounts, one failure each.

## Key takeaways

- A query is a measuring instrument: write its specification (population, condition, grain, window, output) before writing it.
- Type mismatches, substring matches, short time bounds and NULLs in exclusions all run without error and return wrong answers; each has a precise alternative.
- Choose the grain the question is about, and apply thresholds and counts at that grain; CTEs keep different grains separate.
- Joins multiply rows unless bounded by a key and a time window; count distinct values afterwards, and keep outer-join conditions in `ON`.
- Window functions such as `LAG()` measure intervals and expose regular behaviour that volume-based queries cannot see.
- Test every important query against known positives and known negatives, think in precision and recall, and save the query with the case so its result can be reproduced.
