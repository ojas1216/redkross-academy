## Introduction and conceptual foundation

The first six lessons of this module described what telemetry sources record, the fields that make events searchable and the timestamps that put them in order. None of that matters until the events actually arrive where analysts search and rules run. The machinery that carries them there is the **collection pipeline**, the least glamorous and most frequently broken part of security operations.

A collection pipeline is the chain of components that takes an event from the system that produced it, moves it across the network, turns it into structured fields and stores it where it can be searched and retained. Vendors draw it differently, but the stages are always **source**, **collection**, **transport and buffering**, **parsing and normalisation**, **storage** and **analytics**. Each stage can lose, delay, duplicate or corrupt events, and almost none of those failures raise an alarm. A Windows host whose forwarding subscription has lapsed simply stops appearing. A firewall sending UDP syslog to a collector with a full disk does not retry; the packets vanish. A parser that cannot understand a new log format may drop events or store them as unparsed text that no rule ever matches.

This is why experienced SOC leads say that **"no alerts" is not the same as "nothing happened"**. A quiet queue can mean a quiet network, or it can mean that the evidence never reached the SIEM. The course's Module 2 case study makes the point: the US Government Accountability Office reported that during the 2017 Equifax breach a traffic-inspection device had an expired digital certificate, so encrypted traffic passed without inspection for about ten months; only after the certificate was renewed did administrators recognise signs of intrusion. The sensor was installed, the pipeline existed, and still the SOC was blind, because nobody was monitoring the health of the telemetry itself.

This lesson covers agent-based and agentless collection, the main forwarding technologies (Windows Event Forwarding, syslog, the Elastic Beats and Elastic Agent family and their equivalents), buffering and delivery guarantees, where parsing happens, and how to detect loss through source-health monitoring. Lesson 8 puts the ideas to work in the course lab kit.

> [!NOTE]
> You will meet the SIEM side of this chain (ingestion, parsing, normalisation and storage tiers) in much more detail in Module 3. This lesson stays on the question an analyst must be able to answer every shift: did the telemetry I am relying on actually arrive, complete and on time?

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Collection pipeline | The chain of components that moves events from their source into searchable storage: collection, transport, buffering, parsing, storage. |
| Agent | Software installed on the monitored system that reads local logs and sends them onward (for example Winlogbeat, Elastic Agent, Splunk Universal Forwarder, the Wazuh agent). |
| Agentless collection | Collection without installing software on the source: the source pushes (syslog) or a collector pulls (an API, Windows Event Forwarding, remote log reading). |
| Forwarder | A component whose job is to receive or read events and send them to the next hop; it may be an agent or a central relay. |
| Collector | A central system that receives events from many sources, for example a Windows Event Collector or a syslog server. |
| WEF | Windows Event Forwarding: the built-in Windows mechanism that forwards selected event log entries to a Windows Event Collector over WinRM. |
| Syslog | The standard protocol for sending log messages over a network, described in RFC 5424 (with the older BSD format in RFC 3164). |
| Buffer / queue | Temporary storage that holds events when the next stage is slow or unavailable, so they are delayed rather than lost. |
| Back-pressure | A signal from a slow downstream stage telling upstream stages to slow down or hold data. |
| Delivery guarantee | The promise a pipeline makes about each event: at most once (may be lost), at least once (may be duplicated) or exactly once. |
| Parsing at ingest | Extracting fields from the raw message when it is received, before storage (schema-on-write), as opposed to at search time (schema-on-read). |
| Source health | Whether each expected source is sending events at its normal rate, with the expected fields, and with acceptable delay. |
| Ingestion lag | The difference between when an event happened and when it became searchable in the SIEM. |

## The stages of a collection pipeline

Think of the pipeline as a series of hand-offs, each with its own owner and failure modes.

**Source.** The system that produces the event: a workstation's Security log, a server's journal, a firewall, proxy, VPN concentrator, identity provider or cloud platform. The source decides what is recorded at all. If audit policy does not enable process-creation auditing, or Sysmon is not installed, no pipeline can conjure those events. Local log size matters too: the Windows Security log has a configured maximum and by default overwrites its oldest events when full, so if forwarding stops for long enough, unsent events are lost. The local log is the pipeline's first buffer.

**Collection.** Reading events from the source and handing them on, by agent or agentless method (next section). Collection must define **which events** are selected, **how the collector knows where it got to** (so a restart neither skips nor repeats events) and **who may read** the source.

**Transport and buffering.** Carrying events to the next hop. Good transport is **encrypted** (TLS, or Kerberos-protected WinRM in a Windows domain), **authenticated** in both directions and **reliable** (it notices failed delivery). Queues on agents, relays or a message broker hold events when the next stage cannot accept them.

**Parsing and normalisation.** Turning raw messages into fields and mapping them to a common schema (Lesson 5), while fixing time problems such as a missing year or offset (Lesson 6).

**Storage and analytics.** Hot storage for investigation, colder tiers for retention, and the searches, rules and dashboards on top. For this lesson the key property is that storage can tell you, per source, **when the last event arrived** and **how many arrived per hour**: the raw material of health monitoring.

**Components.** On the left are four groups of sources. **Windows workstations** (Security log and Sysmon) represent endpoint telemetry. **Network devices** (firewall and proxy) represent devices that cannot host an agent. **Linux servers** run an agent. **Cloud and SaaS** represents identity and cloud platforms that are reached only through an API. In the middle are the collection components: the **Windows Event Collector**, which receives events through WEF subscriptions; the **Syslog relay**, which receives syslog over TLS; the **Agent on host**, which reads local files and journals; and the **API poller**, which pulls audit records on a schedule. All of them feed the **Buffer / message queue**, which in turn feeds **Parse + normalise**, then **SIEM storage**, then **Rules, searches, dashboards**. A separate **Source-health monitor** sits beside the chain.

**Relationships and arrows.** Solid arrows show the direction that events travel. Note that the arrow from **Cloud and SaaS** goes to the **API poller** labelled "pulled over HTTPS": the collector initiates that connection, while network devices push syslog to the relay. The dashed arrows into the **Source-health monitor** are not event data; they are measurements (last-seen time, events per hour, queue depth, parse-error count) taken from the buffer and from storage.

**Execution flow.** An event is written at the source, read or received by a collector, placed in the buffer, taken from the buffer by the parser, stored, and then evaluated by rules. Ingestion lag is the sum of the time spent in every one of those steps.

**Decision logic.** The monitor compares each measurement with what is expected: a source with no events for longer than its normal quiet interval, a queue that keeps growing, or a parse-error rate above zero raises a health alert to the SOC, exactly like a security alert.

**Technical interpretation.** Each collection method has different failure modes. A WEF subscription can lapse without the workstation noticing; syslog over UDP can lose packets silently; an API poller can fall behind if the provider throttles it; an agent can be stopped by a local administrator. The buffer converts short outages downstream into delay instead of loss, but only up to its capacity.

**Practical example.** At Banyan, the finance workstation WS-104 forwards its Security log through WEF, while the proxy sends syslog to the relay. If the relay's disk fills, the proxy's messages are dropped at the relay, and the health monitor sees proxy events per hour fall towards zero while Windows events continue normally.

**Security implications.** Every component in the middle column is a target and a single point of failure. An attacker who can stop an agent, alter a subscription or flood a relay can blind the SOC. Collectors and relays must be hardened, access-controlled and monitored like any other critical server.

**Key learning.** A pipeline is a chain of hand-offs; each one must be built for reliability and watched by a health check, because none of them reports its own failure.

## Agent-based and agentless collection

The most visible design choice in a pipeline is whether to install software on each source. Both approaches are used in every real SOC, usually side by side, because each suits different kinds of source.

### Agent-based collection

An agent is a program running on the monitored system. It reads local log files, the Windows event log or the Linux journal, keeps track of how far it has read, and sends events to a collector or directly to the SIEM. Examples include the Elastic Beats family (Winlogbeat for Windows event logs, Filebeat for files), Elastic Agent (a single agent managed centrally through Fleet that runs integrations for many log types), the Splunk Universal Forwarder, the Wazuh agent and the sensors of EDR products.

Agents have real advantages. They can read sources that are never exposed over the network (local files, the journal, application logs). They usually keep a record of their read position: Filebeat, for example, stores the offset it has reached in each file in a registry, so after a restart it continues from where it stopped instead of re-sending or skipping data. They can buffer locally when the network is down, compress and encrypt traffic, and add context such as the host name and agent identity to every event. Many can also filter at the source, discarding high-volume, low-value events before they consume bandwidth and licence.

The costs are equally real. Every agent is software to deploy, upgrade and keep compatible; it consumes resources on a system with another job; it runs with enough privilege to read security logs, which makes it a target; and it can fail: a broken upgrade on one image can silence hundreds of hosts at once.

### Agentless collection

Agentless collection gathers events without installing anything extra on the source. There are two directions.

- **Push from the source.** The source is configured to send its own events to a collector. Network devices, firewalls, proxies and many appliances support only this method, usually through syslog. Windows Event Forwarding in its source-initiated mode is also a push: the Windows host itself, configured through Group Policy, sends selected events to the collector.
- **Pull by the collector.** The collector connects to the source and reads events. Cloud and SaaS platforms are almost always collected this way, through an audit or management API that the collector polls on a schedule with a service credential. Collector-initiated WEF subscriptions and remote reading of event logs over the network also pull.

Agentless collection avoids the software estate, but it moves the burden elsewhere. Push methods depend on correct configuration on every device and often on unreliable transport. Pull methods need credentials with read access to sensitive logs, stored on the collector, and they are subject to the provider's rate limits, pagination rules and publication delays: cloud audit events can take minutes to become available through an API, which adds to ingestion lag.

| Question | Agent-based | Agentless |
| --- | --- | --- |
| What can it read? | Local files, event logs, journal, application logs | What the source exports (syslog, WEF, an API) |
| Where is state kept? | On the agent (read position, local buffer) | On the source (push) or the collector (pull cursor) |
| Main operational cost | Deploying and upgrading software everywhere | Configuring every device; managing API credentials |
| Typical silent failure | Agent stopped, crashed or broken by an upgrade | Subscription lapsed, syslog dropped, API cursor stuck |
| Typical sources | Servers, workstations, EDR | Network appliances, cloud and SaaS, Windows via WEF |

> [!TIP]
> The question is not "agents or no agents" but "which method for which source". A sensible default is: agents or WEF for Windows endpoints, agents for servers, syslog over TLS for appliances that support it, and API pulls for cloud and SaaS.

## Forwarding technologies you will meet

### Windows Event Forwarding (WEF)

WEF is built into Windows. A **Windows Event Collector** server runs the Windows Event Collector service, and **subscriptions** define which events it should receive, using XPath-style queries over the event logs (for example, selected Security log event IDs and the Sysmon operational log). In a **source-initiated** subscription, which is the usual choice in a domain, Group Policy tells each workstation which collector to contact, and the workstations push matching events to it. In a **collector-initiated** subscription the collector contacts a listed set of computers. Transport uses WinRM (the Windows implementation of WS-Management), by default on port 5985 for HTTP or 5986 for HTTPS; inside an Active Directory domain the HTTP channel is authenticated and encrypted with Kerberos. Forwarded events land in the collector's **Forwarded Events** log, from which an agent or connector ships them to the SIEM.

WEF's strength is that it needs no third-party software on the workstations. Its weaknesses are operational: subscriptions and Group Policy must be correct, the collector must be sized for the volume, and a workstation that cannot reach the collector simply keeps its events locally until its own log wraps.

### Syslog

Syslog is the oldest and most widespread log transport. A syslog message carries a priority (facility and severity), a timestamp, a host name and the message text. The older BSD format (RFC 3164) has a timestamp with no year and no time zone, which is the parsing problem Lesson 6 described; the newer protocol (RFC 5424) carries a full timestamp with offset. Traditionally syslog travels over **UDP port 514**. UDP has no acknowledgement and no retransmission: if the collector is down, busy or unreachable, messages are lost and neither side knows. Syslog can also be carried over TCP, and over TLS as defined in RFC 5425 (commonly on port 6514), which adds confidentiality, integrity and a connection that fails visibly. Central relays such as rsyslog and syslog-ng receive, buffer, filter and forward syslog from many devices.

### Beats, Elastic Agent and other shippers

The Elastic stack illustrates the agent model well, and the concepts carry over to other vendors. **Beats** are small single-purpose shippers: Winlogbeat reads Windows event logs, Filebeat reads files and many common log formats through modules, and others collect network or metrics data. **Elastic Agent** replaces a collection of Beats with one agent that runs integrations, is enrolled in and centrally managed by **Fleet**, and reports its own health status. Shippers send either directly to the storage cluster or through an intermediate processing tier (Logstash in the Elastic world) that can parse, enrich and queue. Other ecosystems have the same pieces under different names: the Splunk Universal Forwarder and Heavy Forwarder, the Wazuh agent and manager, Fluent Bit and Fluentd, and the cloud providers' own agents.

## Buffering and delivery guarantees

Every pipeline eventually meets a downstream stage that cannot keep up: a SIEM upgrade, a failed link, a burst of events. What happens next depends on buffering.

**Buffers turn loss into delay.** An agent with a local disk queue keeps events while the collector is unreachable and sends them when it returns. A relay with a disk-backed queue holds syslog it has received while the SIEM is down. Large deployments put a message broker such as Apache Kafka between collection and parsing, holding hours or days of events. An in-memory buffer loses its contents if the process restarts; a persistent (disk-backed) queue survives restarts.

**Back-pressure protects the buffer.** When a downstream stage is slow, a well-designed pipeline slows the stages upstream rather than letting a queue grow without limit. An agent that is told to wait reads the source more slowly and, because it records its position, loses nothing as long as the source keeps the events. Back-pressure fails when it reaches a stage that cannot wait: a UDP syslog sender cannot be told to slow down, and a Windows log that is overwriting its oldest events will not hold them for ever.

**Delivery guarantees describe what can go wrong.**

- **At most once.** Each event is sent once and never retried. If anything fails, it is lost. UDP syslog behaves this way.
- **At least once.** The sender retries until it receives an acknowledgement. Nothing is lost while the buffers hold, but if an acknowledgement is lost after the event was stored, the event is sent again and stored twice. Most agent-based shippers aim for this guarantee; Elastic documents at-least-once delivery for Filebeat, for example.
- **Exactly once.** Each event is stored once and only once. This is hard to achieve end to end and is usually approximated by at-least-once delivery plus de-duplication on a stable event identifier.

For a SOC the consequences are practical. At-least-once delivery occasionally produces duplicates, so counting rules ("ten failures in five minutes") must allow for them. At-most-once delivery occasionally loses events, so single-event detections (one log clear, one new admin) are only as good as the transport. And every buffer has a size: if an agent's queue holds four hours of a busy server's events, a six-hour outage loses two hours.

> [!WARNING]
> Buffers delay events, and delay matters too. A correlation rule that looks for "failure then success within ten minutes" can miss the pattern if one source's events arrive an hour late and the rule has already evaluated that time window. Ingestion lag must be measured, not assumed.

## Parsing at ingest and at search time

**Parsing at ingest (schema-on-write).** The pipeline parses each event when it arrives and stores structured fields. Searches are fast and rules can rely on consistent field names. The cost is that the parser must be correct before the data arrives: if a vendor changes its log format, events that the parser does not recognise may be rejected, dropped, or stored with an error tag and a single unparsed message field that no rule will ever match.

**Parsing at search time (schema-on-read).** The raw text is stored and fields are extracted when a search runs. Splunk is the best-known example of a platform that extracts many fields at search time. This is flexible, because a new extraction applies to old data immediately, but searches are slower and every analyst depends on the extraction definitions being right.

Most real deployments mix the two: they parse the fields that rules and dashboards depend on at ingest, keep the original raw event alongside the parsed fields, and extract rarer fields when needed. Keeping the raw event matters for two reasons. It lets you re-parse when a parser was wrong, and it is the evidence: in an investigation you need to show the original record, not only someone's interpretation of it. The course's teaching SIEM, `minisiem.py`, does exactly this, storing common fields as columns and the original JSON in a `raw` column.

A parse failure is therefore not cosmetic. It is a **silent detection failure**, because the rule that would have fired looks for a field that was never created. Module 3 treats parsing in depth; here, remember that the parse-error count is a health signal.

## Where telemetry is lost, and how to notice

Loss in a pipeline is rarely total and rarely loud. It is usually partial (one site, one host group, one event type), gradual (a queue that grows a little every day) or conditional (only during bursts, only after a vendor update). The SOC needs a deliberate way of noticing it, which is what **source-health monitoring** provides.

Source-health monitoring treats the pipeline itself as something to detect problems in. For every expected source it asks four questions:

1. **Is it present?** When did the last event arrive from this source, and from each host within it? A source or host that has been silent for longer than its normal quiet interval is a candidate problem.
2. **Is the volume normal?** How many events per hour, compared with the same hour on previous days? A sharp drop suggests loss; a sharp rise suggests duplication, a misconfiguration or an incident.
3. **Is the content complete?** Are the fields that rules depend on populated? Is the parse-error count zero? A source that still sends events but with an empty `user` field after an upgrade is as broken, for detection, as a silent one.
4. **Is it on time?** What is the ingestion lag, the gap between the event's own timestamp and the time it became searchable? Growing lag is often the first sign of a backlog that will become loss when a buffer fills.

The hard part is the word **expected**. A silent source is only a problem if it should be talking: a workstation is quiet at night; a domain controller never is. Good health monitoring therefore needs an **inventory of expected sources** (ideally from the asset inventory or CMDB, not from the SIEM itself, otherwise a host that has never sent anything is invisible) and a **baseline** of normal volume and quiet periods for each. Lesson 8 shows what happens when you apply a naive silence check to the course dataset without a baseline: a source that stopped sending events hours before the end of the day turns out to be a quirk of how that data was generated, not an outage, and the check correctly produces a question rather than a conclusion.

The rows are coloured to show where the risk is most often silent: red rows fail without any error the SOC normally sees.

**Relationships.** Each row reads left to right as a cause-and-effect chain: the failure in the second column produces the symptom in the third, which the check in the fourth detects. The rows are also ordered from source to storage, so the table follows the direction of event flow in the first figure.

**Execution flow.** In practice a health check runs on a schedule, for example every fifteen minutes. It queries the SIEM for last-seen time, hourly counts, field completeness and parse errors per source, compares them with the baseline and the inventory, and raises a ticket or alert when a threshold is crossed.

**Decision logic.** The symptom column shows why one check is not enough. A stopped agent produces silence for one host; a parser failure produces events that are present but useless; a full buffer produces rising lag before it produces loss. Each needs its own threshold, and "events are arriving" does not prove "events are usable".

**Technical interpretation.** The **Transport** row is the Equifax lesson: an expired certificate on a decryption device meant traffic was no longer inspected, yet nothing on the inspection side announced it. The **Parser** row explains why a vendor upgrade is a detection-engineering event: rules keyed on `user` or `src_ip` silently stop matching if those fields are no longer extracted. The **Storage** row is a compliance issue too: CERT-In's April 2022 directions require covered entities in India to keep logs of their ICT systems for a rolling 180 days within Indian jurisdiction, so a retention misconfiguration can be a regulatory breach as well as an investigative gap.

**Practical example.** At Banyan, an analyst runs the morning source-health check and sees that WS-104 has proxy events up to 07:00 UTC and then none for two hours, while every other host is normal. Using the table, she rules out the parser (other hosts parse fine) and storage (other hosts are stored), and focuses on the source and transport rows for that one host.

**Security implications.** Some of these failures can be caused deliberately. Stopping an agent, clearing a log or tampering with audit policy are recognised adversary behaviours, so a health alert on a single sensitive host is a security signal, not just an operations ticket.

**Key learning.** Health checks must cover presence, volume, completeness and timeliness, per source and per host, against an inventory and a baseline; any one alone misses whole classes of loss.

## Worked example: designing collection for Banyan Microfinance

The fictional Banyan Microfinance, whose telemetry you use in this course, has eight Windows workstations (WS-101 to WS-108), a web proxy, a VPN concentrator, a firewall and some cloud services. A SOC engineer would design its collection in five steps, which double as the best practices for any pipeline.

1. **Inventory from outside the SIEM.** List every source, its owner and the detections that depend on it (Sysmon for suspicious parent-child processes, the Security log for new administrators and log clearing, the proxy for beaconing and large uploads, the VPN for password spraying). Take the list from the asset register, so a workstation that has never sent an event still appears.
2. **Choose a method per source.** Source-initiated WEF for the workstations, with an agent on the collector shipping to the SIEM; syslog over TLS to a relay with a disk-backed queue for the proxy, VPN and firewall (if a device supports only UDP, put the relay on the same segment and record the risk); API pulls with a read-only credential for cloud services.
3. **Size the buffers.** Decide how long an outage each stage must survive and size queues accordingly; enlarge the workstations' Security log so that a collector outage of that length cannot cause overwriting.
4. **Parse and keep raw.** Parse rule-critical fields at ingest, convert time to UTC, record ingestion time, keep the raw event, and tag (do not drop) events that fail to parse.
5. **Monitor and test health.** Schedule searches for last-seen per source and per host, hourly volume against a baseline, field completeness, parse errors and lag, routed to the SOC queue with an owner. Then stop forwarding on a test workstation and confirm the alert fires: a health check that has never been seen to fire is an assumption, not a control.

## Common mistakes and misconceptions

- **"The SIEM shows events, so collection works."** Events from most sources prove nothing about the one that is missing. Check health per source and per host.
- **Building the expected-source list from the SIEM.** A host that has never sent anything never appears in it.
- **Treating UDP syslog as reliable.** It is at-most-once by design.
- **Assuming buffers are infinite.** Every queue has a capacity measured in hours; alert on queue depth before it is reached.
- **Dropping unparsed events.** Keep and tag them; otherwise a format change becomes invisible loss.
- **Ignoring duplicates and lag.** At-least-once delivery inflates counts after retries, and a rule window shorter than the lag misses correlations.
- **Filtering at the source without a risk decision.** Dropping an event type at the agent is permanent for that data; decide by detection value and record why.

## Security implications, detection and defence

The pipeline is part of the attack surface. An intruder with administrative rights on a host has every reason to reduce what the SOC can see, and MITRE ATT&CK records the behaviours: **T1562.001** (Impair Defenses: Disable or Modify Tools), covering stopping or tampering with security agents; **T1562.002** (Impair Defenses: Disable Windows Event Logging); and **T1070.001** (Indicator Removal: Clear Windows Event Logs). The course dataset contains a Windows event ID 1102, the Security log being cleared, which later modules investigate.

- **Alert on silence from sensitive hosts.** A domain controller or finance workstation that stops sending events during working hours deserves security priority, not just an operations ticket.
- **Forward tampering events fast.** Log-clear events (1102), audit-policy changes and agent service stops are themselves forwarded; near-real-time forwarding means the evidence of a cleared log usually reaches the SIEM even though the local copy is gone.
- **Protect collectors and credentials.** Collectors, relays and API pollers hold access to sensitive logs; harden them, restrict administration and rotate their credentials.
- **Protect integrity in storage.** Restrict deletion, audit analyst and administrator actions, and use tamper-evident storage for retention.
- **Respect privacy.** Telemetry contains personal data. India's Digital Personal Data Protection Act 2023 requires purpose limitation and reasonable security safeguards: collect what detection needs and set retention by policy.

## Key takeaways

- A collection pipeline is a chain of hand-offs (source, collection, transport and buffering, parsing, storage, analytics); each can lose, delay, duplicate or corrupt events, usually silently.
- Agents read local data and keep their own position and buffer; agentless collection relies on the source pushing (syslog, source-initiated WEF) or a collector pulling (APIs). Choose per source.
- UDP syslog is at-most-once; TLS syslog and acknowledged agent protocols fail visibly. Buffers turn loss into delay up to their capacity, and at-least-once delivery means occasional duplicates.
- Parse rule-critical fields at ingest, keep the raw event and count parse failures.
- Monitor presence, volume, completeness and lag per source and per host, against an inventory and a baseline. "No alerts" may mean "no visibility".
