## Introduction and conceptual foundation

Lesson 1 settled what severity claims: the harm a behaviour would cause if the alert is true. Prioritisation answers a different and more practical question: **given the alerts in the queue now and the analysts on shift now, what should be worked next?** It is a scheduling decision made under uncertainty and under a hard limit on attention. A SOC that rates every alert perfectly but works them in the wrong order can still let an intrusion run for hours while analysts close noise.

Module 1 introduced the default queue rule (highest priority first, oldest first among equals) and the lab kit's score, `priority = severity x confidence x asset criticality`. This lesson takes that score apart. It asks how each input is obtained, what the multiplication does to them, where the kit's model is blind, how alerts on one entity should be combined, how time and capacity change the order, and when an analyst should overrule the number.

The theme throughout is that a priority score is a *model*: a simplification built from assumptions. Like every model it is useful exactly as far as its assumptions hold, and an analyst who knows the assumptions knows when to stop trusting the order.

> [!NOTE]
> The worked examples use the course lab kit in `LAB_ASSETS/C08/` and the synthetic Banyan Microfinance dataset. Run the scripts only in your own working copy of the kit.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Priority | The position of an item in the order of work. Derived from a score, adjusted by time and context, and finally chosen by an analyst. |
| Priority score | A number computed from inputs such as severity, confidence and criticality, used to sort the queue. |
| Confidence | The probability that an alert from a rule is a true positive, ideally measured as the rule's precision over recent dispositions. |
| Precision | True positives divided by all alerts with a final disposition, for one rule over a period. |
| Asset criticality | How much a host, application or account matters to the business, from the CMDB or asset owner. |
| Entity | The thing alerts are about: a host, user account, source address or application. |
| Entity risk score | An aggregate of the scores of all recent alerts on one entity. |
| Tie-breaker | The rule that orders items with equal scores. |
| Starvation | Low-priority items waiting indefinitely because higher-priority items keep arriving. |
| Override | An analyst working an item out of score order, with a recorded reason. |

## Anatomy of the kit's score

`LAB_ASSETS/C08/triage.py` computes priority in one short function:

```python
def priority(rule, host):
    sev, conf = RULE_META[rule]
    crit = ASSETS.get(host, ("unknown asset", 2))[1]
    return round(sev * conf * crit, 1)
```

Three inputs, from three owners. `sev` and `conf` come from `RULE_META`, which the script's own comment says is "reviewed by detection engineering". `crit` comes from `ASSETS`, a stand-in for the CMDB, and falls back to 2 when the host is not in the table. The result is rounded to one decimal place. In theory the scale tops out at 4 x 1.0 x 3 = 12. With the kit's actual tables the range is narrower: from 10.8 (R5 or R2 on a criticality-3 host) down to 2.4 (R6 on a criticality-2 host, 2 x 0.6 x 2).

Running the kit (after `python minisiem.py load`) produces the queue you met in Module 1:

```terminal

**Decision logic.** Two rows deserve scrutiny. **Practical example.** An analyst arriving at 08:30 sees R5 at the top and takes it, which is correct. But a reviewer reading this table notices that six of the seven rows concern WS-104 and that R2 is the only alert involving an external actor with live access. The table invites the questions that the rest of this lesson answers: should the six be worked as one, and should R2 wait?

**Security implications.** Every input is an attack surface for mistakes. A wrong criticality in the CMDB, an outdated confidence or an inflated severity silently moves real alerts down. Decomposition makes such errors visible during quality review.

**Key learning.** Read a priority score as severity times confidence times criticality, and always ask what the score leaves out: entity, time, role and actor.

## What the multiplication does

Choosing to *multiply* the inputs is a design decision with consequences that are easy to miss.

**Each factor scales the others.** Halving confidence halves the score whatever the severity. That is usually what you want: a rule that is right half as often deserves half the urgency, all else equal.

**A zero erases everything.** If a host's criticality were entered as 0, or a new rule's confidence left at 0.0, every alert on that host or from that rule would score 0 and sink to the bottom, however severe. Multiplicative models need floors: a minimum confidence for new rules, and a minimum criticality for any asset.

**Ties are common.** Small integer scales multiplied together collide often. In the kit, 4 x 0.9 x 2 and 3 x 0.8 x 3 both give 7.2. The tie-breaker therefore matters more than it first appears.

Two alternative models are worth knowing.

- **Weighted sum.** `score = w1 x severity + w2 x confidence + w3 x criticality`. A single very high factor cannot be cancelled by a low one, which suits SOCs that want a High-severity alert never to fall far, but it lets several mediocre factors add up to an alarming score.
- **Lookup matrix.** IT service management practice (ITIL, for example) commonly derives priority from a grid of *impact* against *urgency*. A SOC can do the same with severity against criticality, using confidence only as a gate. Matrices are easy to explain and audit, but coarse.

None of these is correct in general. What matters is that the SOC knows which model it runs and tests it against real cases.

## Where the inputs come from

### Confidence should be measured

The kit's confidences (0.5 to 0.9) are values set by detection engineering. In a mature SOC they are derived from data: a rule's **precision**, the share of its alerts over, say, the last ninety days that analysts closed as true positives. That is why the disposition field from Module 1 matters so much: every careless "false positive" closure lowers a rule's measured confidence and so the future priority of everything it detects.

Three practical points follow. A new rule has no history, so it receives a documented default (often moderate) until enough alerts accumulate. A rule with very few alerts has an unreliable precision; ten alerts with one true positive is weak evidence. And confidence can depend on context as well as on the rule: an Office-spawns-PowerShell alert on a developer's workstation where macros are part of the job is less likely to be malicious than the same alert in Finance. Some SOCs keep confidence per rule *and* per business unit for this reason.

### Criticality must be maintained

Asset criticality comes from the CMDB and the asset owners, and it is only as good as their upkeep. Look at the default in `priority()`: an unknown host scores criticality 2. That is a policy decision, and an arguable one. A host the SOC has never heard of may be a forgotten test box, or it may be a newly deployed payment server, or a device an intruder has joined to the network. Calling it "average" hides that uncertainty. Many SOCs treat unknown assets as at least High criticality until classified, and raise a separate task to register them.

Using the kit's own function shows the effect:

```terminal
$ python -c "from triage import priority; print(priority('R2','WS-104'), priority('R1','UNKNOWN-9'), priority('R6','WS-107'))"
10.8 4.8 2.4
```

The three calls ask: what would R2 score on the finance workstation (10.8, equal to the current top alert); what would R1 score on a host missing from `ASSETS` (4.8, below both R3 alerts on WS-104); and what would R6 score on the sales laptop (2.4). The middle value is the warning: the same malicious-document execution falls by a third simply because the host is not in the inventory.

### Identity is missing from the formula

The kit's `USERS` table records that `divya` is a "payments approver", and `triage.py` prints it, but `priority()` never reads it. For alerts about accounts rather than machines, that is a real gap. R2 is a valid-credential login from an external address; its score uses criticality 2 because `PRIMARY_HOST` maps `gopal` to his sales laptop. Yet what the attacker now holds is an *account*, and what matters is what that account can reach. Had the sprayed account that succeeded been the payments approver, the score would rise to 10.8, but only because `PRIMARY_HOST` happens to map `divya` to the finance workstation (criticality 3); her approval rights would still play no part, and the same approver logging in from an unmapped or ordinary laptop would score 7.2 like any other user. A better model takes the higher of asset criticality and identity criticality for each alert, so that privileged and business-critical accounts lift their alerts wherever they appear.

## Ties and what the kit actually does

Module 1 stated the common tie rule: among equal scores, the oldest alert first, because it has waited longest and its SLA timer is nearest to breach. The kit does something different, and seeing why is a useful lesson in reading tools rather than trusting them.

`triage.py` builds tuples of `(score, rule name, host, ...)` and calls `sorted(queue, reverse=True)`. Python compares tuples element by element, so when two scores are equal it compares the rule-name strings, and in reverse order `"R2 vpn_spray_then_success"` comes before `"R1 office_spawns_script"`. The tie is broken alphabetically by rule name, not by time. R2 (06:46) is printed above R1 (06:14), the opposite of oldest-first.

In this teaching tool the effect is harmless, but the same pattern in a production SIEM view or SOAR playbook would quietly order work by a label rather than by risk or age. Whenever a queue is sorted, check what happens on a tie, and make the tie-breaker explicit: time waiting, then SLA deadline, then severity.

## Beyond single alerts: entity risk

The most important limitation of any per-alert score is that it scores each alert alone. Attacks are sequences, and their individual steps often look moderate. In the Banyan queue, WS-104 accounts for six of the seven lines; no single one is above 10.8, but together they are the intrusion.

**Entity risk scoring** addresses this by adding up the scores of recent alerts per entity (host, account or source address) and prioritising entities, not alerts. Summing the WS-104 lines from the queue gives 10.8 + 7.2 + 5.4 + 5.4 + 4.5 + 3.6 = 36.9, against 7.2 for the only alert about `gopal`. Two refinements are needed in practice. First, count each rule once per entity in a window, or a single noisy rule firing repeatedly dominates; counting the two R3 alerts once gives 31.5. Second, let the risk decay with time, so that old activity does not keep an entity at the top for weeks. Some SIEM products build this in as risk-based alerting, where rules write risk contributions and a separate threshold rule creates the alert the analyst sees; Module 3 introduced the idea as entity risk aggregation.

Entity scoring has one more benefit: it lets low-severity, low-confidence rules such as R6 stay enabled without each one paging an analyst. Their alerts contribute risk quietly and surface only when other evidence on the same entity accumulates.

## From scores to the next piece of work

Putting the pieces together, prioritisation in a working SOC is a short pipeline rather than a single number. The figure shows the stages between a scored alert and the case an analyst actually opens.

*Figure 5.4: From scored alerts to the next case an analyst works. Per-alert scores are grouped by entity, aggregated into entity risk, adjusted for time and context, and finally chosen by an analyst, whose dispositions feed back into rule confidence.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The flow shows how a SOC turns individually scored alerts into a decision about what to work next. It matters because the per-alert score is only the first of several inputs, and skipping the later stages is how queues end up ordered by noise.

**Components.** Six steps run from top to bottom. **Score each alert** (slate) carries "severity x confidence x criticality", the `triage.py` stage. **Deduplicate and group by entity** (blue) carries "host, account, source address". **Entity risk** (violet) carries "WS-104: 6 alerts, gopal: 1". **Adjust for time** (orange) carries "waiting time, SLA deadline". **Adjust for context** (orange) carries "campaign intel, account privilege, live access". The final step, **Analyst takes the next case** (dark), carries "override allowed, with a recorded reason". Downward arrows connect each step to the next. The note under the flow adds the feedback path: "analysts' dispositions update rule confidence, which changes next week's scores".

**Relationships and arrows.** Each downward arrow passes a progressively richer object: an alert with a score, then a group of alerts about one entity, then an entity with a risk value, then a candidate case with time and context applied, then a decision. The feedback described in the note is the slowest loop in the picture: analysts' closures change the confidence values the first step uses next week.

**Execution flow.** Scoring happens as alerts arrive. Grouping and entity risk are recomputed continuously. Time and context adjustments are applied when the queue is viewed. The analyst decides when they are free to take new work.

**Decision logic.** The time step raises items that have waited long or whose SLA warning is near, which prevents starvation of moderate alerts behind a stream of slightly higher scores. The context step raises items linked to an active campaign reported by threat intelligence, items involving privileged or business-critical accounts, and items where an attacker may have live access that a quick, pre-authorised action could cut off. The analyst may still take something else, but the reason goes in the case.

**Technical interpretation.** Only the first step is implemented in the course kit. Grouping and entity risk are what a case-management system or SIEM risk engine provides; time adjustment is usually a view that combines score with SLA timers; context adjustment draws on the threat intelligence platform and identity provider.

**Practical example.** In the Banyan queue, step one gives seven scores. Step two collapses six into the WS-104 entity and leaves `gopal` on his own. Step three ranks WS-104 at 36.9 against 7.2. Step five then lifts `gopal`'s alert: it is a successful login from an external address after a spray, the session may still be open, and disabling the account and ending the VPN session takes minutes. A two-person shift splits: one analyst opens the WS-104 case, the other takes R2.

**Security implications.** Each stage can fail silently. Without grouping, the six WS-104 alerts may be picked up by six analysts on different shifts. Without time adjustment, a moderate alert can sit for days. Without the feedback loop, rule confidences go stale and the first step's numbers stop meaning anything.

**Key learning.** Priority is decided per entity and per moment, not just per alert: score, group, aggregate, adjust for time and context, then let a named analyst decide.

## Time, capacity and starvation

A queue only works if, over a shift, the SOC can finish roughly as much work as arrives. When arrivals persistently exceed capacity, the queue grows, and the priority order silently becomes a decision about what will *never* be examined. Low-scored alerts are not deferred; they are abandoned. This is why prioritisation and tuning cannot be separated: if the tail of the queue is never reached, the honest options are to tune or retire the rules that fill it, to automate their handling, or to add capacity, not to pretend the alerts are being handled.

Inside a shift, two time effects matter. **Ageing** raises an item's effective priority the longer it waits, so that a steady stream of slightly higher scores cannot starve it. **Deadline proximity** raises items whose SLA warning point is close (the timers themselves were covered in Module 1). Both should be visible in the queue view, next to the score, so that an analyst can see why an item has risen.

> [!WARNING]
> Never let time pressure *lower* severity or confidence to make a queue look manageable. Time changes the order of work; it does not change the facts about an alert.

## When the analyst should overrule the number

The score is advice. Analysts are expected to depart from it when they know something the model does not, and to say so. Legitimate reasons include: the alert shares an entity, indicator or technique with a case already open; the actor appears to have live access and a fast containment step is available; threat intelligence or a colleague has flagged the indicator today; or the alert concerns a person or system the model cannot know is sensitive (a board member's account, a server in the middle of a payment run).

Illegitimate reasons look similar from outside, which is why the reason must be written down: picking easy alerts to improve personal closure counts, avoiding an unfamiliar alert type, or working only alerts from a favourite tool. The written override reason is what lets a shift lead tell the two apart.

## Worked example: the Banyan queue at 08:30

Imagine the night-to-day handover has just finished and two analysts, A and B, take the queue at 08:30 UTC. The kit's output is as shown earlier. Here is a defensible way to turn it into work.

1. **Read the scores, then group.** Six alerts name WS-104 and `divya`; one names `gopal`. Analyst A acknowledges R5 (10.8) and links the other five WS-104 alerts to a single case, as Module 1 practised.
2. **Check what the model cannot see for the odd one out.** R2 scored 7.2 using the sales laptop's criticality, but it concerns an account used from 203.0.113.66 after eight accounts failed from that address. A quick search in minisiem shows the failures:

```terminal
$ python minisiem.py search "SELECT ts, user, outcome FROM events WHERE source='vpn' AND src_ip='203.0.113.66' ORDER BY ts"
ts | user | outcome
2026-11-03T06:42:00Z | asha | failure
2026-11-03T06:42:07Z | ben | failure
2026-11-03T06:42:14Z | chen | failure
2026-11-03T06:42:21Z | divya | failure
2026-11-03T06:42:28Z | eshan | failure
2026-11-03T06:42:35Z | farah | failure
2026-11-03T06:42:42Z | gopal | failure
2026-11-03T06:42:49Z | hema | failure
2026-11-03T06:46:00Z | gopal | success
```

The `search` subcommand runs the quoted SQL against the minisiem database; `source='vpn'` restricts it to VPN events, `src_ip` fixes the external address, and `ORDER BY ts` puts them in time order. Eight accounts failed seven seconds apart, a classic spray rhythm, and four minutes later `gopal` succeeded. Note that `divya`, the user at the centre of the WS-104 case, was also one of the targets.

3. **Apply context.** A successful external login after a spray is a credential compromise with possible live access, and containment is quick. Analyst B takes R2 as an override of the score order and records: "Taken ahead of WS-104 secondary alerts: successful VPN login after spray from 203.0.113.66, possible live session, containment is quick; divya also targeted, cross-reference with the WS-104 case."
4. **Keep the cases connected.** The spray did not cause the WS-104 activity (R1 fired at 06:14, before the spray began at 06:42), so the two are different stories that touch the same person. Each case notes the other, so that whoever finds a link in, for example, `divya`'s later VPN activity, sees both.
5. **Revisit the order after each closure.** When B closes or escalates R2, the queue is re-read; nothing stays fixed for the shift.

The result differs from the printed order in two ways, both justified in writing: six alerts are worked as one case, and an alert with a mid-table score is worked immediately because the model could not see that it involved an external actor with valid credentials.

## Common mistakes and misconceptions

- **Treating the score as the decision.** It is an input; entity, time and context come after it.
- **Working alerts, not entities.** Six analysts each closing one WS-104 alert as "suspicious, no further evidence" is how chains are missed.
- **Ignoring identity.** Scoring account-based alerts by the criticality of the user's laptop understates credential compromise.
- **Letting unknown assets default to average.** An unregistered host is a question, not a medium-value asset.
- **Undefined tie-breakers.** Equal scores ordered by an accident of sorting.
- **Stale confidence.** Values set once and never recomputed from dispositions.
- **Pretending the tail is handled.** If low-priority alerts are never reached, say so and tune, automate or retire them.

## Security implications, detection and defence

Prioritisation is a target in its own right. An adversary who triggers a burst of noisy, high-volume alerts elsewhere can pull the SOC's attention away from a quieter intrusion; entity grouping and analysts who glance down the queue are the defences. Because criticality drives priority, the CMDB is security-relevant data: an attacker or careless change that lowers a server's criticality, or a new server never registered, lowers the priority of every alert about it. Changes to criticality and to rule confidence should be logged and reviewed like changes to detection rules. Finally, measure the queue itself: track how long alerts at each priority band wait, how many are never touched before closure by automation, and how often overrides turn out to be right.

## Best practices

- Document the scoring model, its inputs, their owners and its floor values.
- Derive confidence from recent dispositions, with a stated default for new rules.
- Use the higher of asset and identity criticality; treat unknown assets as high until classified.
- Make tie-breakers explicit: waiting time, then SLA deadline, then severity.
- Aggregate risk per entity with per-rule de-duplication and time decay.
- Show score, age and SLA state together in the queue view.
- Allow overrides, require a written reason, and review them.
- Watch capacity: if the tail is never reached, change the detections, not the definitions.

## Key takeaways

- Prioritisation decides what is worked next with limited attention; severity is only one input.
- The kit's score multiplies severity, confidence and asset criticality: each factor scales the others, zeros erase alerts and ties are frequent.
- Confidence should be measured from dispositions; criticality must be maintained and should include identity; unknown assets deserve caution.
- Check how a tool breaks ties: the kit's sort orders equal scores by rule name, not by age.
- Aggregate per entity: the WS-104 alerts rank far higher together (36.9) than any one alone.
- Time and context adjust the order; analysts may override, in writing.
