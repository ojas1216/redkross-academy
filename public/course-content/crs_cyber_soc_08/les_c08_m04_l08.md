## Lab objective and scope

This lab brings the whole module together. You will analyse one day of logs from the fictional Banyan Microfinance as an analyst would on receiving a raw export with no alerts attached: source by source first, establishing what normal looks like in each and picking out the exceptions, then across sources, joining the exceptions by entity and time into a single timeline, and finally writing a short **findings note** that states what happened, how confident you are, what the evidence is and what remains unknown.

Module 3's SIEM lab started from the six saved correlation rules and pivoted outwards from their alerts. This lab deliberately does the opposite: it runs `minisiem.py rules` only at the very end, as a cross-check. Rules only find what someone thought to write a rule for; the analyst who can read each log source on its own terms, as Lessons 1 to 6 taught, finds what the rules miss and can judge what the rules find. At the end you will compare your findings with the rule output and see whether the two agree.

By the end of the lab you will be able to:

1. Build a per-source baseline for Windows Security, endpoint process, VPN and proxy events using aggregation queries.
2. Separate genuine exceptions from routine noise in each source and explain why each exception matters.
3. Join exceptions across sources on host, user, address and time into one timeline.
4. Run scope checks that confirm or rule out other affected hosts and accounts.
5. Write a findings note that distinguishes observed facts from inferences and lists open questions.

> [!IMPORTANT]
> **Authorisation and scope.** This lab uses only the synthetic Banyan dataset (`banyan_events.jsonl`) shipped in the course lab kit, analysed with the kit's own `minisiem.py` on your own computer. Every person, host, domain and address in it is fictional; external addresses come from the RFC 5737 documentation ranges and domains end in `.example`. Do not apply these queries to real organisational logs unless you are authorised to do so as part of your job, and remember that real proxy and authentication logs are personal data under the DPDP Act 2023.

## Key terminology

| Term | Meaning in this lab |
| --- | --- |
| Baseline | The normal shape of a source: which event types occur, how often, for whom and when. |
| Exception | An event or pattern that departs from the baseline and needs explaining. |
| Noise | An exception with a benign, sufficient explanation (a mistyped password). |
| Entity | The host, user, address or domain an event is about; the join key across sources. |
| Merged timeline | All exceptions from all sources on one UTC time axis, with their entities. |
| Scope check | A query that tests whether other hosts, accounts or addresses are involved. |
| Finding | A statement supported by cited evidence, with a confidence level. |
| Open question | Something the data cannot answer that must be resolved by other means. |
| Findings note | The short written output of the analysis: findings, evidence, gaps, recommendations. |

## How the lab is organised

The method has four stages. **Orient**: confirm what data you hold and its time span. **Baseline each source**: for each log type, run a summary query that shows the routine pattern, then list what departs from it. **Merge**: bring every exception onto one timeline and look for shared entities and short gaps in time. **Scope and write**: test whether the activity reaches beyond the entities already found, then write the findings note.

The order matters. Baselining each source first prevents the most common error in multi-source analysis, which is anchoring on the first suspicious event and then reading every later event as confirmation. By the time you merge, each exception has already been judged on its own source's terms: a failed logon with status `0xC000006A` is judged against the other logons, not against the phishing story.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows how the lab turns four separate log sources into one findings note. It matters because it fixes the order of reasoning: each source is understood on its own before anything is joined, so that exceptions are judged against the right baseline and confirmation bias has less room.

**Components.** Four input boxes sit in a row at the top, one per source. **Windows Security** (blue) carries logons, failures and account-management events. **Endpoint process (Sysmon)** (blue) carries process starts with their parent processes. **VPN** (slate) carries remote-access successes and failures with the source address. **Web proxy** (slate) carries each request with host, user, URL and bytes sent. Each has an arrow to a matching orange box labelled **Baseline and exceptions**, with the source's main question in the sub-label. These four feed a violet box, **Merged timeline**, labelled "join on host, user, address and time". The timeline feeds a green box, **Scope checks** ("other hosts? other accounts?"), which leads to the dark outcome box **Findings note** ("facts, confidence, gaps, actions").

**Relationships and arrows.** Arrows point in the direction of analysis, from raw source to conclusion. There is no arrow between the four source boxes: at the baseline stage the sources are deliberately kept apart. The only place sources meet is the merged timeline, and they meet there through shared entities, not through narrative.

**Execution flow.** Steps 2 to 5 of the lab are the four baseline boxes, in any order. Step 6 is the scope-check box (run here before the timeline because its results decide which events belong on it), Step 7 the merged timeline, and Step 8 the findings note.

**Decision logic.** In each baseline box the analyst classifies every exception as noise, suspicious or unexplained. Only suspicious and unexplained exceptions move to the timeline. At the scope-check box, a positive result (another host contacted a bad domain) sends the analyst back to baseline that host; a negative result is recorded as a finding in its own right.

**Technical interpretation.** Each baseline box is an aggregation query at a grain suited to the source: event ID and outcome for Windows, parent and child process for Sysmon, user, address and outcome for VPN, domain and host breadth for the proxy. The merged timeline is a single query whose `WHERE` clause is the union of the exception conditions, grouped so that repeated events (the beacon) appear as one row with a first and last time.

**Practical example.** In this dataset the Windows baseline is eight interactive logons, one per workstation, and two failed logons; the exceptions are a new account, a group change and a cleared log. The VPN baseline is too small to be a baseline at all, which is itself a finding recorded under gaps.

**Security implications.** A note that mixes facts and inferences, or omits gaps, leads responders to over- or under-react. The structure in the dark box (facts, confidence, gaps, actions) is what makes the note usable by the incident handler who receives it.

**Key learning.** Understand each source alone, then join on entities and time, then test scope, then write: the order protects the analysis from its own first impression.

Note what the data does **not** say: these events record the account under which the action was performed, not that the person divya performed it.

### Step 3: Endpoint process events

Stack Sysmon process creations by parent and child, keeping only the executable names. The expression `replace(x, rtrim(x, replace(x, '\', '')), '')` strips everything up to the last backslash: the inner `replace` removes the backslashes, `rtrim` then trims every trailing character that is not a backslash, leaving the directory part, which the outer `replace` deletes from the full path.

```terminal
$ python minisiem.py search "SELECT replace(parent_image, rtrim(parent_image, replace(parent_image, '\', '')), '') AS parent, replace(image, rtrim(image, replace(image, '\', '')), '') AS child, COUNT(*) AS n, COUNT(DISTINCT host) AS hosts FROM events WHERE source='sysmon' GROUP BY parent, child ORDER BY hosts, n"
parent | child | n | hosts
WINWORD.EXE | powershell.exe | 1 | 1
explorer.exe | excel.exe | 8 | 8
explorer.exe | explorer.exe | 8 | 8
explorer.exe | msedge.exe | 8 | 8
explorer.exe | outlook.exe | 8 | 8
```

The baseline is four applications started by Explorer on every one of the eight workstations. One pair occurs once, on one host: Word starting PowerShell. Read that event in full:

```terminal
$ python minisiem.py search "SELECT ts, host, user, json_extract(raw, '$.command_line') AS command_line FROM events WHERE source='sysmon' AND image LIKE '%powershell%'"
ts | host | user | command_line
2026-11-03T06:14:00Z | WS-104 | divya | powershell.exe -NoP -W Hidden -EncodedCommand <redacted-for-course>
```

The options request no profile, a hidden window and a Base64-encoded command, a combination that legitimate Office documents have little reason to use. The course redacts the encoded content, so the lab cannot say what the command did; that is an open question for the endpoint team, who would recover it from the host's own PowerShell logging or the document itself.

Also note an absence: a Word process start appears nowhere in the data.

```terminal
$ python minisiem.py search "SELECT COUNT(*) FROM events WHERE lower(image) LIKE '%winword%'"
COUNT(*)
0
```

The process that started PowerShell was never itself logged as starting. In a real estate that would be a collection gap worth raising (a filtered event, an agent that started late); here it is a limitation of the synthetic data. Either way it belongs in the note's gaps, not silently ignored.

### Step 6: Scope checks

Before building the timeline, test whether the activity reaches other entities. First, every host that contacted any of the three single-host domains:


### Step 7: Build the merged timeline

Now bring the exceptions from Steps 2 to 5 onto one timeline. The query below defines the domain once in a CTE, derives the set of single-host domains in a second CTE, and selects every exception: the account and log events, the Office-spawned process, VPN successes and requests to rare domains. Grouping by source, host, user and activity collapses the 18 beacon requests into one row with a first and last time:

```terminal
$ python minisiem.py search "WITH e AS (SELECT *, substr(url, 9, instr(substr(url, 9), '/') - 1) AS domain FROM events), rare AS (SELECT domain FROM e WHERE source='proxy' GROUP BY domain HAVING COUNT(DISTINCT host) = 1) SELECT MIN(ts) AS first_ts, MAX(ts) AS last_ts, COUNT(*) AS n, source, COALESCE(host, '-') AS host, user, COALESCE(domain, 'event ' || event_id, 'vpn from ' || src_ip) AS activity FROM e WHERE event_id IN (4720, 4732, 1102) OR lower(parent_image) LIKE '%winword.exe' OR (source='vpn' AND outcome='success') OR domain IN (SELECT domain FROM rare) GROUP BY source, host, user, activity ORDER BY first_ts"
first_ts | last_ts | n | source | host | user | activity
2026-11-03T06:12:00Z | 2026-11-03T06:12:00Z | 1 | proxy | WS-104 | divya | banyan-payroll-update.example
2026-11-03T06:14:00Z | 2026-11-03T06:14:00Z | 1 | sysmon | WS-104 | divya | event 1
2026-11-03T06:17:00Z | 2026-11-03T07:42:02Z | 18 | proxy | WS-104 | divya | cdn-telemetry-sync.example
2026-11-03T06:46:00Z | 2026-11-03T06:46:00Z | 1 | vpn | - | gopal | vpn from 203.0.113.66
2026-11-03T07:02:00Z | 2026-11-03T07:02:00Z | 1 | windows | WS-104 | divya | event 4720
2026-11-03T07:03:00Z | 2026-11-03T07:03:00Z | 1 | windows | WS-104 | divya | event 4732
2026-11-03T08:12:00Z | 2026-11-03T08:12:00Z | 1 | proxy | WS-104 | divya | files-share-drop.example
2026-11-03T08:17:00Z | 2026-11-03T08:17:00Z | 1 | windows | WS-104 | divya | event 1102
2026-11-03T13:33:00Z | 2026-11-03T13:33:00Z | 1 | vpn | - | gopal | vpn from 198.51.100.104
```

`COALESCE` returns its first non-NULL argument, so the activity column shows the domain for proxy rows, the event ID for Windows and Sysmon rows (Sysmon event ID 1 is a process creation, the WINWORD to PowerShell event from Step 3), and the source address for VPN rows. The 13:33 VPN row is included deliberately as the comparison baseline; it is not an exception.

Read the timeline as a sequence on WS-104: a macro-enabled document is downloaded from a look-alike domain (06:12); two minutes later Word starts hidden, encoded PowerShell (06:14); three minutes after that a five-minute beacon to a domain no other host uses begins (06:17 to 07:42); a new account is created and made a local administrator (07:02 to 07:03); 48.2 MB is uploaded to a file-sharing look-alike (08:12); and five minutes later the Security log is cleared (08:17). Every step is on the same host and account, each within minutes of the previous. That is the classic shape of a phishing-led intrusion: delivery, execution, command and control, persistence, exfiltration, defence evasion.

The VPN row at 06:46 shares no entity with WS-104. It falls in the middle of the WS-104 activity, but nothing in the data links the two: different account, no host on the VPN event, and an address that appears in no other source. Keep it as a **separate thread** and do not let the timeline's proximity merge it into the main story.

### Step 8: Write the findings note

The findings note is the product of the lab. It is short, factual and structured so that the incident handler can act on it. Before writing prose, lay the findings out as a register: one line per finding, its source, its key evidence and a confidence level that reflects how directly the logs show it.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram is the findings register for the Banyan analysis: every finding the lab supports, with the log source it comes from, the evidence that supports it and the analyst's confidence. It matters because it separates what the logs show directly from what the analyst infers, which is the main quality test of any findings note.

**Components.** The table has four columns: **Finding**, **Source**, **Evidence** and **Confidence**. Seven rows follow the timeline. **Look-alike document download** (proxy; `invoice.docm` at 06:12, one host). **Office spawned hidden PowerShell** (Sysmon; WINWORD to powershell.exe, encoded, 06:14). **Regular beacon to rare domain** (proxy; 18 requests, 298 to 302 s gaps). **Privileged account created** (Windows; 4720 and 4732 `svc_update`, 07:02 to 07:03). **Bulk upload** (proxy; 48.2 MB to `files-share-drop.example`, 08:12). **Security log cleared** (Windows; 1102 at 08:17). **VPN spray then success** (VPN; 8 accounts failed, gopal success 06:46). Rows are coloured by tone: the five WS-104 compromise rows are red or orange, the log clearing is dark as the most serious act against evidence, and the VPN thread is violet as a separate, unresolved line.

**Relationships.** The first six rows share host WS-104 and account divya, and their order is the order of the intrusion. The seventh row shares no entity with them. The Confidence column is the key relationship: "High" where a single event directly records the fact, "Medium" where the finding is an inference from a pattern (a beacon is inferred from regularity, not observed as malware).

**Execution flow.** Reading top to bottom retells the incident in time order, which is also the order the findings note should use.

**Decision logic.** A finding earns "High" when the log event is the fact itself (a 4720 is an account creation). It earns "Medium" when the evidence is consistent with the interpretation but another explanation remains possible: the regular requests could in principle be an unknown legitimate agent, and the VPN success could be gopal himself on an unusual network. Nothing is rated "Low" here, because a low-confidence item belongs under open questions instead.

**Technical interpretation.** Each Evidence cell is the condensed result of a query from Steps 2 to 7, so every row can be reproduced from the case notes. The Source column lists exactly one source per finding; correlation across sources is expressed by the shared entities, not by mixing sources in a cell.

**Practical example.** The incident handler reading this register can act on rows 1 to 6 immediately (isolate WS-104, disable `svc_update`, block the three domains, preserve evidence) and route row 7 to the identity team for a credential reset and a conversation with gopal.

**Security implications.** Overstating confidence leads to wrong containment; understating it delays it. Rating each line separately also helps reviewers challenge a single inference without discarding the whole analysis.

**Key learning.** A finding is a fact plus its source, its evidence and an honest confidence; keep separate threads separate until the data links them.

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| `no such table: events` | `load` was not run in this folder; run `python minisiem.py load` in the same directory as `minisiem.db`. |
| A query prints only the header row | A condition excludes everything: check quoting, letter case and event IDs written as numbers, not text (Lesson 7). |
| `json_extract` output is `None` | The field does not exist in that source's raw event, or the JSON path is misspelt (`$.logon_type`, not `$.LogonType`). |
| The shell reports an unexpected quote or changes the SQL | Keep the whole SQL statement inside one pair of double quotes and use only single quotes inside it; do not add a `$` followed by letters inside the statement, because the shell may expand it as a variable. |
| Counts differ from the lesson | The dataset was regenerated or edited. Recopy `banyan_events.jsonl` from the kit, or run `python make_dataset.py` in your copy, then `load` again. |

## Key takeaways

- Analyse each log source on its own baseline first; exceptions only mean something against what is normal for that source.
- Classify every exception as noise, suspicious or unexplained, with the evidence for the choice.
- Merge exceptions on entities and time, and keep threads separate when the data does not link them.
- Scope checks with empty results are findings, and their limits (time span, missing sources) belong in the note.
- A findings note states facts with sources and confidence, lists gaps and open questions, and recommends actions without overstating what the logs show.
- Independent analysis and saved rules check each other: here the baseline found the initial phishing download that no rule covers.
