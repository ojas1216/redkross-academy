## Introduction and conceptual foundation

An alert is a claim. When a SIEM rule, an EDR engine or an analyst's saved search raises an alert, it is saying "something that matches a pattern of concern happened here, at this time, involving these entities". It is not saying that an attack took place. Whether the claim is true, how serious it is and what should be done about it are questions that people answer later, one step at a time. The **alert lifecycle** is the name for those steps: the path an alert follows from the moment it is generated to the moment it is closed with a recorded decision, and the feedback that closure sends back into the detection system.

The lifecycle matters because a SOC handles alerts in volume. A mid-sized organisation can produce hundreds or thousands of alerts a day across its endpoint, network, identity and cloud telemetry. Without a defined path, alerts are handled inconsistently: one analyst closes an alert after a glance, another spends an hour on the same pattern, a third leaves it in the queue because nobody is sure who owns it. The result is the failure that post-incident reviews describe again and again. The detection worked, the alert existed, but nobody acted on it in time. The US Senate Commerce Committee majority staff analysis of the 2013 Target breach, for example, reported that Target appears to have failed to respond to multiple automated warnings from its intrusion detection software. A lifecycle with clear stages, owners and exit criteria is the SOC's defence against that outcome.

Lessons 1 and 2 showed how a SOC is organised into tiers and roles. This lesson follows one unit of work, the alert, through that organisation: eight stages, the dispositions an alert can end with, and the record closure must leave. The worked example uses the six correlation rules in `LAB_ASSETS/C08/minisiem.py` and the work queue produced by `LAB_ASSETS/C08/triage.py`. Module 4 teaches triage technique and Module 7 incident response; here the goal is the shape of the whole journey.

> [!NOTE]
> Stage names, state names and disposition labels differ between SOCs and between products. Some platforms call an alert an "offence", a "detection" or a "notable event"; some merge triage and investigation into one state. Learn the purpose of each stage rather than one vendor's vocabulary, and adopt your employer's terms when you join a team.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Event | A single recorded occurrence in a log source, such as a process start, a logon or a proxy request. |
| Alert | A record created when a detection (rule, model or analyst search) matches one or more events and decides a human or automation should look. |
| Case | A container that groups one or more related alerts, the evidence collected and the decisions made about them. |
| Incident | A confirmed or strongly suspected security event that threatens confidentiality, integrity or availability and requires a coordinated response. |
| Queue | The ordered list of alerts waiting for an analyst, usually sorted by priority and age. |
| Triage | The first assessment of an alert: is it plausibly real, what does it involve, how urgent is it? |
| Disposition | The recorded conclusion about an alert: true positive, benign true positive, false positive or undetermined. |
| Escalation | Handing an alert or case to a higher tier or to incident response, with ownership transferred and acknowledged. |
| Suppression | A documented rule that stops a specific, known benign pattern from generating alerts, with an owner, reason and expiry. |
| Playbook | Documented steps for handling a particular alert type, including what to check and when to escalate. |

## Why alerts need a lifecycle at all

Like a service-desk ticket, an alert needs a creator, an owner, a status and a resolution. Security adds three reasons for discipline. **Asymmetry of cost**: closing a false positive slowly wastes minutes, but closing a true positive wrongly can let an intruder spread, so the lifecycle must make evidence-free closure hard and escalation easy. **Adversarial pressure**: attackers create noise, act at night or move slowly so that no single alert looks serious, which grouping related alerts into cases counters. **Learning**: every closed alert says something about the rule, the telemetry and the playbook, and the final stage exists to capture it.

## The eight stages

The stages follow the normal order of work, although an alert can loop back when new evidence appears. Each stage has a clear question and a clear output.

### 1. Generation

An alert is born when a detection matches. Detections take several forms:

- **Signature or rule matches**: a condition on one event, such as "Windows Security event 1102 (the audit log was cleared)".
- **Correlation rules**: conditions across several events, sources or time windows, such as "five or more distinct users failed VPN logon from one IP address, followed by a success from the same address".
- **Analytics and models**: anomaly scores, rare-behaviour detections and user and entity behaviour analytics.
- **Human generation**: an analyst's hunt finding, a user report to the help desk or a notification from a partner or CERT.

Whatever the source, a good alert at birth already says which detection fired, when, on which entities (host, user, IP address, process, URL), with a link to the raw events. An alert with only a title and a severity forces every analyst to rebuild that context by hand. Detection engineering (Module 6) owns this quality.

**Output:** an alert record with a rule name, timestamp, entities and evidence links.

### 2. Queueing and prioritisation

New alerts enter a queue. The order of the queue decides what analysts look at first, so it is a security control in its own right. Most SOCs start from the rule's **severity** (how bad the behaviour would be if real) and add context such as rule **confidence** (how often the rule has been right historically) and **asset criticality** (how much the affected system matters to the business). The lab's triage helper computes a simple product of the three, which you will see in the worked example. Age is also important: an alert that has waited for an hour should not be overtaken indefinitely by a stream of newer, slightly higher scores.

Queueing is also where **deduplication** collapses repeated hits of one rule on one entity into a single alert with a counter.

**Output:** a prioritised, deduplicated queue position.

### 3. Triage

Triage is the first human (or automated) look. It answers a narrow set of questions quickly: what did the rule detect, which entities are involved, is the alert plausibly real, and is it urgent? Triage enriches the alert with context (who is this user, what is this host, is this IP internal or external) and looks briefly at the raw events. Many alerts end here: a clear false positive caused by a data error, or a benign true positive matching a documented change. Others move on to investigation. Module 4 is devoted to triage technique, including a time-boxed workflow and validation methods.

**Output:** an early decision: close with a disposition, investigate further or escalate now.

### 4. Investigation

Investigation builds the story. The analyst constructs a timeline of events around the alert, identifies related alerts on the same entities, establishes scope (how many hosts, users and accounts are involved) and tests hypotheses against the evidence. Investigation is where alerts are grouped into **cases**, because the question shifts from "is this alert real?" to "what is happening, and how far has it gone?". Tier 2 analysts usually own this stage for anything beyond the simplest alert.

**Output:** a timeline, a scope statement and a set of supported or refuted hypotheses.

### 5. Disposition

The disposition is the formal conclusion. Common labels are:

- **True positive (TP)**: the detection was correct and the activity is malicious or violates policy.
- **Benign true positive (BTP)**: the detection worked as designed, but the activity is authorised, such as an administrator's approved script or a scheduled penetration test.
- **False positive (FP)**: the detection matched something it should not have, because of a logic error, a parsing error or missing context in the rule.
- **Undetermined (or inconclusive)**: the evidence is insufficient to decide. The record must say what is missing and what would resolve it.

The distinction between BTP and FP is not pedantry. A BTP means the rule is healthy and the organisation needs a documented exception or a process change; an FP means the rule itself needs fixing. Mixing them corrupts the false-positive rate that detection engineers use to tune rules.

**Output:** a disposition label and the reasoning that supports it.

### 6. Escalation and response

A true positive with real or potential impact is escalated: to Tier 2 or Tier 3, to the incident response function, or to on-call staff out of hours. Escalation is a transfer of ownership, not a message. It is done through the case system, with the evidence attached, and it is complete only when the receiving person or team acknowledges it. Response actions such as isolating a host or disabling an account are recommended or performed according to the SOC's authority and playbooks (Module 7).

**Output:** an acknowledged hand-off, a declared incident if warranted, and response actions under way.

### 7. Closure

Closure records the end of the SOC's work on the alert in a note that someone who was not there can review (covered in detail below).

**Output:** a closed alert or case with disposition, evidence references and actions.

### 8. Feedback

Feedback turns closed alerts into better rules, playbooks and telemetry. Without this stage the lifecycle is a line; with it, it becomes a loop.

**Output:** tuning tickets, playbook changes, telemetry gaps raised with owners.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram represents the full journey of one alert inside a SOC, from the moment a detection fires to the moment its lessons return to the detection layer. It matters because every SOC process you will meet later (triage in Module 4, escalation in Module 7, metrics in Lesson 7 of this module) attaches to one of these boxes.

**Components.** The top row of boxes is the linear part of the path: **Generated** (a rule, model or analyst creates the alert), **Queued and prioritised** (severity, confidence and asset criticality decide its place), **Triage** (is it plausibly real and urgent?) and **Investigate** (timeline, scope, related alerts). The violet diamond, **Disposition?**, is the decision point. Below it sit four outcome boxes: **True positive**, **Benign true positive**, **False positive** and **Undetermined**. Each leads to its own action box: **Escalate to incident response**, **Close with documented reason**, **Close and tune the rule** and **Monitor and record the gap**. The dark box, **Closure record**, is the single place every path ends, and the dashed **Feedback** arrow runs from it back to **Generated**.

**Relationships and arrows.** Solid arrows show the normal order of work and the transfer of the alert from one stage to the next. The arrows out of the decision diamond are labelled with the disposition, because the disposition alone decides the next action. The dashed arrow is different in kind: it carries information rather than the alert itself. Closure records produce tuning tickets, playbook changes and telemetry requests that change how future alerts are generated.

**Execution flow.** An alert moves left to right through generation, queueing and triage. Triage can take a shortcut to the decision point when the answer is obvious (a clear false positive), which is why the diagram shows triage feeding the decision directly as well as through investigation. Otherwise investigation runs first, then the disposition is recorded, the matching action is taken and the closure record is written.

**Decision logic.** A true positive is escalated, and the case closes only after response work is complete. A benign true positive closes with the authorisation documented, for example a change ticket number. A false positive closes and raises a tuning request because the rule matched something it should not have. An undetermined alert is not quietly closed: the analyst records what evidence was missing and either monitors the entities or raises a telemetry gap.

**Technical interpretation.** In a SIEM or case management platform, these stages are status values on a record, with timestamps written at each transition. Those timestamps are what later make metrics such as mean time to acknowledge possible, so the diagram is also a map of where measurement data comes from.

**Practical example.** In the course lab, rule R1 (`office_spawns_script`) fires for host WS-104 at 06:14 UTC. It is generated by minisiem, queued by `triage.py` with a priority of 7.2, triaged by checking the preceding proxy download, investigated alongside four other rules on the same host, given a true positive disposition, escalated, and closed in a case whose feedback notes that the beacon rule should alert sooner.

**Security implications.** The two most dangerous failures sit at the edges of the diagram: alerts that never leave **Queued** (nobody owns them) and closures that skip the evidence and feedback steps. Both are detectable, by monitoring the age of unacknowledged alerts and by sampling closure records for quality.

**Key learning.** Every alert must reach a recorded disposition and a closure record, and every closure must be able to send feedback to the detection layer. The disposition decides the action; the closure record makes the decision reviewable.

## Alert states, ownership and timestamps

Stages describe the work; **states** describe where a particular alert is right now. A case management system needs a small, unambiguous set of states, because states drive queues, dashboards and service-level timers. A typical set looks like this:

| State | Meaning | Who owns it | Typical exit |
| --- | --- | --- | --- |
| New | Created, not yet looked at | The queue (nobody yet) | An analyst acknowledges it |
| In progress | An analyst is triaging or investigating | Named analyst | Disposition, escalation or pending |
| Pending | Waiting for an external answer (user, IT owner, vendor) | Named analyst | Answer received, or time limit reached |
| Escalated | Handed to a higher tier or incident response | Receiving team, after acknowledgement | Response complete |
| Closed | Disposition and closure note recorded | Nobody (reopen if new evidence) | Reopened only with a reason |

Three rules make states trustworthy. First, **every state except New and Closed has a named owner**. An alert "in progress" with no owner is a New alert pretending to be handled. Second, **every transition is timestamped in UTC** by the system, not typed by the analyst. These timestamps feed the metrics in Lesson 7 (time to acknowledge, time to resolve) and the service levels in Lesson 6. Third, **Pending is time-limited**. An alert waiting for a user to confirm whether they ran a script cannot wait indefinitely; the playbook should say what happens if no answer arrives, which is usually escalation rather than closure.

## Worked example: the Banyan queue through the lifecycle

The course lab kit contains one day of synthetic telemetry from a fictional company, Banyan, in `LAB_ASSETS/C08/banyan_events.jsonl` (340 events from proxy, Sysmon, Windows Security and VPN logs). `LAB_ASSETS/C08/minisiem.py` loads those events into SQLite and runs six saved correlation rules. Running the rules is the **generation** stage.

```terminal
$ python minisiem.py load
loaded 340 events
$ python minisiem.py rules
R1 office_spawns_script: 1 hit(s)
    ('2026-11-03T06:14:00Z', 'WS-104', 'divya', 'C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe')
R2 vpn_spray_then_success: 1 hit(s)
    ('203.0.113.66', 8, 'gopal', '2026-11-03T06:46:00Z')
R3 new_local_admin: 2 hit(s)
    ('2026-11-03T07:02:00Z', 'WS-104', 'divya', 'svc_update')
    ('2026-11-03T07:03:00Z', 'WS-104', 'divya', 'svc_update')
R4 large_upload: 1 hit(s)
    ('2026-11-03T08:12:00Z', 'WS-104', 'divya', 'https://files-share-drop.example/upload', 48200000)
R5 log_cleared: 1 hit(s)
    ('2026-11-03T08:17:00Z', 'WS-104', 'divya')
R6 beacon_regular_small: 1 hit(s)
    ('WS-104', 'https://cdn-telemetry-sync.example/api/v2/ping', 18, 220, 220)
```

The `load` subcommand creates the `events` table with normalised columns plus the raw JSON of each event, and `rules` runs each saved SQL rule and prints up to three hits. Read each hit as an alert at birth. R1 says a Word process started PowerShell on WS-104. R2 says eight distinct users failed VPN logon from 203.0.113.66 before `gopal` succeeded from the same address. R3 fired twice, for Windows Security events 4720 (a user account was created) and 4732 (a member was added to a security-enabled local group), both concerning the account `svc_update`. R4 reports an upload of 48,200,000 bytes. R5 is event 1102, the Security audit log being cleared. R6 is a grouped rule: 18 proxy requests from WS-104 to one URL, all exactly 220 bytes.

Generation has given you rule names, times and entities, but not whether any of it is malicious or where to start.

The **queueing** stage is performed by `LAB_ASSETS/C08/triage.py`. It reruns the same rules, enriches each hit with asset and identity tables, applies documented suppressions and computes `priority = severity x confidence x asset criticality`, using per-rule severity and confidence values that detection engineering is assumed to have reviewed.

```terminal
$ python triage.py
10.8  R5 log_cleared             host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 7.2  R2 vpn_spray_then_success  host=WS-107 (sales laptop) user=gopal (standard) ip=external (documentation range in this lab)
 7.2  R1 office_spawns_script    host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 5.4  R3 new_local_admin         host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 4.5  R4 large_upload            host=WS-104 (finance workstation) user=divya (payments approver) ip=n/a
 3.6  R6 beacon_regular_small    host=WS-104 (finance workstation) user=None (?) ip=n/a
```

The first column is the priority score. R5 scores highest: severity 4, confidence 0.9, on a finance workstation of criticality 3, gives 10.8. R6 scores lowest because the rule's base severity is 2 and its confidence 0.6. The R2 hit names WS-107 although VPN events carry no host field; the helper maps the user to a primary device through a `PRIMARY_HOST` table, which a real SOC would replace with DHCP, VPN or EDR data, and the method used should be recorded in the alert. The R6 line shows `user=None` because that rule groups by host and URL and returns no user; enrichment has to tolerate missing fields.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The table shows the seven alerts from the Banyan lab at the point where queueing ends and investigation begins. It exists to make one lesson concrete: the queue tells an analyst where to start, but it does not tell the story, and the lifecycle only works when investigation regroups alerts by entity and time.

**Components.** Each row is one alert produced by `minisiem.py` and scored by `triage.py`. The **Queue** column gives the position in the work queue, highest priority first. **Rule** names the detection as printed by the tools. **Priority** is the score from `triage.py`. **Event time (UTC)** is when the underlying activity happened, taken from the rule output; for R6, which groups many requests, it is the first beacon request at 06:17. **Case after grouping** shows where investigation places the alert. Rows are coloured by that outcome: the six WS-104 alerts share one tone, the VPN alert another.

**Relationships.** Read down the Queue column and the Event time column together. The highest-priority alert (R5, 08:17) is the latest event of the day, and the lowest-priority alert (R6, from 06:17) is one of the earliest. The rows that share host WS-104 and user `divya` form one case, CASE-0001. R2 involves a different user, a different host and an external source address, so it is recorded as a linked case whose connection to CASE-0001 remains a hypothesis.

**Execution flow.** An analyst takes R5 first, because a cleared audit log on a finance workstation is serious in itself. The first investigative question is "what else happened on this host and account?", which pulls R1, both R3 hits, R4 and R6 into the same case. The analyst then rebuilds the sequence in event-time order: PowerShell started by Word at 06:14, beaconing from 06:17, a new local administrator at 07:02 and 07:03, a large upload at 08:12 and the log cleared at 08:17.

**Decision logic.** Grouping is driven by shared entities and plausible time windows. Alerts that share both host and user within the same morning are grouped. R2 shares neither, so it is not merged; it is linked, with the reason written down, so that a later finding can confirm or remove the link.

**Technical interpretation.** `triage.py` scores each alert independently and does no grouping or time ordering; that is the analyst's and the case system's job, and it is why the two columns disagree.

**Practical example.** An analyst who closed R6 as "probably telemetry software" because of its low score would discard the earliest evidence of command and control. Grouped with R1, the 220-byte requests become strong corroboration.

**Security implications.** Attackers benefit when alerts are worked one at a time in score order; grouping and event-order timelines defeat that.

**Key learning.** Work the queue by priority, but investigate in event-time order and close in cases, not in isolated alerts.

### Corroborating the main case

The investigation of CASE-0001 then gathers evidence for the remaining stages. A targeted search confirms what preceded the R1 alert:

```terminal
$ python minisiem.py search "SELECT ts, source, event_id, image, url, bytes_out FROM events WHERE host='WS-104' AND ts BETWEEN '2026-11-03T06:10:00Z' AND '2026-11-03T06:23:00Z' ORDER BY ts"
ts | source | event_id | image | url | bytes_out
2026-11-03T06:12:00Z | proxy | None | None | https://banyan-payroll-update.example/invoice.docm | 812
2026-11-03T06:14:00Z | sysmon | 1 | C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe | None | None
2026-11-03T06:17:00Z | proxy | None | None | https://cdn-telemetry-sync.example/api/v2/ping | 220
2026-11-03T06:22:01Z | proxy | None | None | https://cdn-telemetry-sync.example/api/v2/ping | 220
```

The `search` subcommand runs the analyst's SQL against the loaded table and prints a header row followed by the results, separated by `|`. A macro-enabled document is fetched from a look-alike domain two minutes before Word starts PowerShell (Sysmon event ID 1 is process creation), and the first fixed-size request to the beacon URL follows three minutes later. Three log sources agree. That corroboration supports a **true positive** disposition for the WS-104 alerts and an **escalation** to incident response. The VPN alert R2 is also a true positive for the behaviour it detects, a password spray followed by a success, but whether the same actor is behind both cases is recorded as undetermined until investigation shows otherwise.

## Closure: what a closed alert must answer

Closure is where the lifecycle produces its permanent record. A useful test is to imagine the closure note being read six months later by someone investigating a related incident. They were not on shift, they cannot ask you, and they need to decide quickly whether your conclusion still holds. Four questions structure the note:

1. **What happened?** A short factual statement in event-time order, with UTC timestamps and entity names.
2. **What evidence supports the conclusion?** The exact queries run, the events or artefacts examined, and references to exported evidence. Opinion and hypothesis are labelled as such.
3. **What was done?** The disposition, any escalation (to whom, when, acknowledged by whom), and any response actions.
4. **What should change?** Tuning requests, playbook updates, telemetry gaps or follow-up hunts, each with an owner.

For a false positive, the note is short but still complete. "FP, closing" is not a closure note. "FP: rule R4 matched the nightly backup upload from the backup server to the approved storage endpoint; confirmed with the backup schedule and change record; requested a narrow exclusion for that destination and host, with an expiry date, via a tuning ticket" is. The difference is that the second note lets a detection engineer act, and lets a reviewer confirm that the analyst did not simply dismiss a real upload.

A true-positive alert normally closes with its parent case, referencing the case's final report.

> [!IMPORTANT]
> Evidence referenced in a closure note must outlive SIEM retention. For cases that may lead to legal or regulatory action, export the events with a hash and custody record, as `LAB_ASSETS/C08/evidence_export.py` does (Lesson 4 and Module 7).

## Feedback: closing the loop

The feedback stage is where a SOC stops paying the same cost twice. Each disposition suggests a different kind of feedback.

- **False positives** point at the detection. The fix is better logic (for example, requiring a parent-child process relationship rather than a process name alone), narrow context exclusions or measured threshold changes. The lab's triage helper shows the shape of a well-formed suppression: `("R3", "user", "itadmin", "approved build account, CHG-1042", "2026-12-31")`. It names one rule, one field and one exact value, gives a reason that points to a change record, and expires.
- **Benign true positives** often point at process. If administrators routinely create local accounts outside the change process, the right fix may be the process, not the rule. Where the activity is legitimately frequent, a documented and time-limited exception is appropriate.
- **True positives** point at coverage and speed. How long did the first relevant alert wait? Was there an earlier signal that should have scored higher? In the Banyan example, the beacon from 06:17 was detectable more than an hour before the log was cleared at 08:17, which is a useful question to bring to detection engineering.
- **Undetermined** alerts point at telemetry. If the analyst could not decide because the process command line, DNS logs or VPN device identifiers were missing, that gap is the finding.

Feedback must be ticketed and owned; an idea mentioned only in a closure note is lost. Module 6 covers how detection engineers act on it.

## Common mistakes and misconceptions

- **"An alert is an incident."** An alert is a claim to be tested; triage, investigation and disposition decide whether it becomes one.
- **Closing without evidence.** A closure note that records a label but no reasoning cannot be reviewed, and analysts under pressure drift towards closing difficult alerts as false positives.
- **Working each alert in isolation.** As the Banyan queue shows, the lowest-scoring alert can be the earliest and most informative. Always check related alerts on the same entities before closing.
- **Confusing BTP with FP.** Recording an authorised administrator action as a false positive tells detection engineers that a healthy rule is broken, and they may weaken it.
- **Escalating by conversation.** A chat message, a phone call or a corridor remark is not an escalation until the case record shows the new owner and their acknowledgement.
- **Permanent or broad suppressions.** A wide wildcard removes coverage for exactly the pattern an attacker would hide behind.

## Security implications, detection and defence

The alert lifecycle is itself an attack surface: noise, timing, slow low-scoring steps and, as in the Banyan scenario, log clearing all target its weak points. Each has a lifecycle-level defence.

**Unacknowledged alerts** should themselves be monitored. A dashboard or a meta-alert that fires when a high-severity alert has stayed in New beyond its service level (Lesson 6) catches the failure described in the Target analysis, where warnings existed but no effective response followed.

**Grouping and correlation across alerts** counters slow, low-scoring intrusions. Case management systems that automatically attach new alerts to an open case on the same host or user make the pattern visible without relying on one analyst's memory.

**Closure quality reviews** counter drift: a reviewer samples closed alerts, especially false positives on high-severity rules, and checks the evidence. This also exposes an insider closing alerts to hide activity.

**Integrity of the lifecycle record** matters: state changes and notes must be attributable to named users. In India, CERT-In's directions of April 2022 require covered entities to report specified incidents within six hours of noticing them and to retain ICT logs for 180 days, and the Digital Personal Data Protection Act 2023 adds breach-notification duties; an accurate record of when an alert was raised, acknowledged and escalated supports these obligations.

> [!WARNING]
> Never close or suppress an alert because it is inconvenient, because someone asked informally or because the queue is long. The closure record is a professional statement made under your name.

## Best practices

- Use a small set of owned states with system-written UTC timestamps, and put a deadline on Pending.
- Require a disposition and a four-part closure note before any alert can be closed.
- Track benign true positives and false positives separately per rule.
- Group alerts into cases and check related alerts before closing any one of them.
- Escalate only through the case system; make every suppression narrow, ticketed and expiring; ticket every feedback item with an owner.

## Practical application (authorised lab only)

This exercise uses only the synthetic Banyan dataset and the course lab kit on your own computer. No live system is involved.

1. Copy the `LAB_ASSETS/C08/` folder to a working directory and open a terminal there. If `banyan_events.jsonl` is missing, run `python make_dataset.py`, which should report `events written: 340`.
2. Run `python minisiem.py load` and confirm `loaded 340 events`, then `python minisiem.py rules`. Treat each hit as a newly generated alert and write down its rule, time and entities.
3. Run `python triage.py` and record the queue. For each line, explain in one sentence why it has that priority, using the severity, confidence and asset criticality values in `triage.py`.
4. Re-sort the seven alerts by event time. Group them into cases and justify each grouping in terms of shared entities and time.
5. Run the targeted search from the worked example and record which log sources corroborate the R1 alert.
6. Assign each alert a disposition. For the one you are least sure of, write what evidence would change your mind.
7. Write a closure note for CASE-0001 using the four questions, and one feedback ticket addressed to detection engineering.

If `triage.py` fails with `no such table`, run `python minisiem.py load` in the same folder first. When you finish, you may delete `minisiem.db`; keep the rest of the folder for later modules.

## Key takeaways

- An alert is a claim to be tested. The lifecycle (generation, queueing, triage, investigation, disposition, escalation, closure, feedback) is how a SOC tests it consistently.
- Dispositions are true positive, benign true positive, false positive and undetermined; each leads to a different action and a different kind of feedback.
- States need named owners and system-written timestamps. Escalation is a transfer of ownership through the case system, complete only when acknowledged.
- Priority decides where to start, not what the story is. In the Banyan lab the highest-scoring alert was the last event and the lowest-scoring one among the first.
- A closed alert must answer what happened, what evidence supports the conclusion, what was done and what should change, so that it can be reviewed by someone who was not there.
- Feedback turns closed alerts into better rules, playbooks and telemetry.
