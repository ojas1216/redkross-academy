## Introduction and conceptual foundation

Module 5, Lesson 3 taught enrichment from the analyst's chair: take one alert, pull out its entities, add asset, identity, network, intelligence and history context, and weigh each indicator match by validity, confidence and fit. That is the right skill for one alert. It does not scale to a SOC. A mid-sized team sees thousands of events per hour that carry an external address, a domain or a file hash, and the same handful of values appears again and again. Enriching by hand repeats the same lookup hundreds of times, gives different results depending on who looked, and leaves no record of where context came from or when it was true.

An **enrichment workflow**, in the sense of this lesson, is the answer: intelligence-driven enrichment turned into a **repeatable pipeline**. The pipeline takes entities from events or alerts, cleans them into a canonical form, decides which of them may be looked up and where, consults its sources in a fixed order, remembers what it learned for a defined time, stays within the limits each source imposes, and writes back every result together with a record of where it came from. The analyst still judges the result.

Five design questions define such a pipeline and form the spine of this lesson: **lookup order** (which sources, in what sequence, and when to stop), **caching** (what is remembered and for how long), **rate limits** (what happens when a source says "slow down"), **privacy** (which values may leave the organisation at all) and **provenance** (what is recorded so that a result can be reproduced months later).

The lab kit gives a small but real data set to reason with. The Banyan events in `minisiem.db` (loaded from `banyan_events.jsonl` by `LAB_ASSETS/C08/minisiem.py`) and the five-indicator fictional feed inside `LAB_ASSETS/C08/ioc_match.py` are enough to show why each design decision matters and what goes wrong without it.

> [!NOTE]
> This lesson assumes the per-alert interpretation from Module 5, Lesson 3 (validity before confidence, "no match" is not "clean") and the ingest-time versus search-time distinction from Module 3, Lesson 3.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Entity | A value extracted from an event that can be looked up: an IP address, domain, URL, file hash, e-mail address or account name. |
| Canonical form | The single agreed spelling of an entity (for example a lower-case host name without a trailing dot) so that equal values compare equal. |
| Lookup cascade | The fixed order in which a pipeline consults its sources, from cheapest and most private to most expensive and most exposed. |
| Short-circuit | Stopping the cascade early because an earlier source gave a definitive answer (for example the value is internal or on an allowlist). |
| Cache | A store of previous lookup results keyed by entity and source, each kept for a time-to-live (TTL). |
| Negative caching | Remembering that a lookup returned nothing, usually for a shorter TTL than a positive result. |
| Rate limit / quota | The maximum number of requests a source accepts per period; exceeding it produces a refusal or a throttled response. |
| Backoff | Waiting progressively longer before retrying a failed or refused request instead of retrying immediately. |
| Privacy gate | The pipeline stage that decides, before any lookup, whether a value may be sent to a given source. |
| Provenance | The recorded origin of a result: source, query time, as-of date, source confidence, marking and whether it came from cache. |
| As-of date | The date against which validity is evaluated; fixing it makes a run reproducible. |

## Why a pipeline and not a habit

The difference between enrichment as a habit and enrichment as a pipeline is easiest to see with numbers from the course data. The Banyan data set has 340 events. Counting how many of them carry a URL or a source address, and how many distinct values those are, takes one query in minisiem:

```terminal
$ python minisiem.py search "SELECT COUNT(*) AS events, COUNT(url) AS with_url, COUNT(DISTINCT url) AS distinct_urls, COUNT(src_ip) AS with_ip, COUNT(DISTINCT src_ip) AS distinct_ips FROM events"
events | with_url | distinct_urls | with_ip | distinct_ips
340 | 284 | 9 | 304 | 11
```

`search` runs one read-only SQL statement against the `events` table and prints the column names and rows separated by `|`. `COUNT(url)` counts rows where the field is present; `COUNT(DISTINCT url)` counts different values.

The result is the first argument for a pipeline. A naive per-event approach would perform 284 URL lookups and 304 address lookups, 588 in all. There are only 9 different URLs and 11 different addresses. **Deduplication alone removes about 97 per cent of the work**, before any question of which values deserve a lookup at all.

Breaking the distinct values down shows the second argument:

Three of the nine URLs are Banyan's own services under `banyan.example`. Eight of the eleven addresses are in the internal range `10.40.0.0/24`. One "address" is the literal string `-`, a placeholder some source writes when it has no value; it is not an entity at all, and a pipeline that sends it to a reputation service wastes a request and pollutes its cache. That leaves six external host names and two external addresses: **eight lookups that can tell the SOC anything new about the outside world**, out of 588 naive ones. Every one of the internal values is not merely a wasted lookup; sent to an outside service it would be a disclosure of Banyan's internal naming and addressing.

The third argument is consistency: looked up once by a defined procedure, `cdn-telemetry-sync.example` carries the same context, sources and timestamp in the `R6` beacon alert and the `R1` alert on the same host.

## Pipeline architecture

A practical enrichment pipeline has six stages. The order matters, because each stage protects the ones after it.

**1. Extract.** Pull entities from the event or alert using the normalised fields (`src_ip`, `url`, `host`, `user` in minisiem; the equivalent common-schema fields in a production SIEM).

**2. Canonicalise and deduplicate.** Turn each value into its canonical form and drop repeats. Host names go to lower case without a trailing dot; URLs yield their host name for reputation lookups while the full URL stays as evidence; hashes become lower-case hexadecimal. Placeholders (`-`, empty, `0.0.0.0`) and malformed values are discarded and counted, since a rise in them signals a parsing problem. Indicators pasted in "defanged" form (`hxxps://example[.]com`) are refanged for matching only.

**3. Classify and gate.** Decide what kind of value each entity is and where it may go. Internal addresses, internal domains, account names and internal URLs are resolved only against internal sources (the CMDB, the identity provider, local history). External values pass a **privacy gate** that checks the destination source against the value's sensitivity and against the sharing marking of any intelligence already attached to it.

**4. Look up in cascade.** Consult sources in a fixed order and stop as soon as the answer is definitive.

**5. Record with provenance.** Write each result as a structured record of where and when it came from.

**6. Attach and feed back.** Attach the records to the alert (at ingest or search time, Module 3) and feed outcomes back: a rejected match becomes feedback to the source and, where appropriate, an allowlist entry with an owner and expiry.

**Components.** The orange box at the top, **Entities from alerts**, is the input; its sub-label gives the Banyan scale, 588 values from normalised fields. The blue box **Canonicalise + dedupe** reduces them to 20 distinct values and drops the `-` placeholder, leaving 19. The violet box **Classify + privacy gate** is the control point: it splits the stream. The slate box **Internal sources only** receives internal addresses, internal domains and accounts (CMDB, identity provider, history). The external values continue down the cascade of four boxes: green **1 Allowlists / warning lists**, blue **2 Cache**, blue **3 Internal TIP + ISAC data**, and slate **4 Approved external service**. Both the internal branch and the cascade feed the dark box **Record with provenance**, whose sub-label lists the fields every result must carry, and from there the green box **Attach to alert + feed back**.

**Relationships and arrows.** Every solid arrow points downstream: data flows from extraction to the record, never the other way. The arrows down the cascade mean "not answered yet, ask the next source". The arrows from each cascade box straight to the record represent a short-circuit: once a source gives a definitive answer, the lower boxes are not asked.

**Execution flow.** Extract, canonicalise, classify, then either resolve internally or walk the cascade, record, and attach. Classification always happens before any lookup, so no value reaches a source it should not.

**Decision logic.** The gate makes the first decision: internal or external, and for external values, which sources are permitted. In the cascade, each stage decides whether its answer is definitive. An allowlisted value (for example a widely used content-delivery host that the SOC has documented as benign) stops at stage 1. A fresh cached result stops at stage 2. Only values that no earlier stage could answer, and that the gate allows, reach stage 4.

**Technical interpretation.** The cascade is ordered by cost and exposure: local lists cost nothing and reveal nothing; the cache costs a local read; the internal threat-intelligence platform costs a query but stays inside the organisation and any trusted community; an external service costs quota and reveals the value to a third party.

**Practical example.** In Banyan's data, the eight internal addresses and three `banyan.example` URLs take the internal branch. Of the eight external values, `cdn-telemetry-sync.example` and `203.0.113.66` are answered at stage 3 by the ISAC-A data already in the feed, and later alerts on the same values are answered at stage 2 from cache.

**Security implications.** Skipping the gate leaks internal names; skipping the cache exhausts quotas during an incident; skipping provenance makes conclusions unreproducible.

**Key learning.** Gate first, then ask sources from cheapest and most private to most expensive and most exposed, and record where every answer came from.

## Lookup order: the cascade in detail

The order of sources is a written policy decision. A sound default:

| Stage | Source | Why here | Typical definitive answer |
| --- | --- | --- | --- |
| 0 | Internal reference data | Free, private, most relevant | "Internal host, owned by Finance, criticality high" |
| 1 | Allowlists and warning lists | Free; prevents false matches on known-benign values | "Public resolver / major CDN / our own SaaS tenant" |
| 2 | Cache | Avoids repeating a recent lookup | "Answered 40 minutes ago, still within TTL" |
| 3 | Internal TIP and community data | Curated, marked, already trusted | "ISAC-A, confidence 85, valid until 2026-12-31" |
| 4 | Approved external services | Broad coverage, costs quota, reveals the query | "Reputation and registration details" |

Three rules make the cascade behave.

**Stop on a definitive answer, but know what "definitive" means.** An internal address is definitively internal; no external source can add anything useful about `10.40.0.23`. An allowlist entry is definitive only for its purpose (a public resolver should not match as an indicator, yet may still matter in a hunt). A cache hit is definitive only while fresh. A stage-3 match is often not final, because the analyst may want registration age from stage 4; the policy says which fields stage 4 may add.

**Allowlists sit before intelligence, not after.** Feeds contain mistakes, and some contain values that are technically associated with malicious activity but shared by millions of benign users: large cloud ranges, public resolvers, content-delivery hosts, popular software update domains. Checking these lists first stops a bad feed entry from turning ordinary traffic into an alert storm. Every allowlist entry needs an owner, a reason and a review date, exactly like the suppressions of Module 5, Lesson 5; an allowlist without expiry becomes a hiding place.

**Internal intelligence outranks external reputation.** The fictional feed in `ioc_match.py` already shows why: the look-alike `banyan-payroll-update.example` came from Banyan's own team, registered on 29 October, and it is about Banyan specifically. When internal and external sources disagree, the pipeline records both and shows the disagreement.

## Caching

A cache stores the result of a lookup so that the next request for the same value from the same source can be answered locally. The cache key is therefore the pair *(canonical value, source)*, not the value alone: the ISAC data and an external reputation service can legitimately say different things about the same domain, and both answers must survive.

**Time-to-live by entity type.** How long an answer stays trustworthy depends on how fast the underlying fact changes. Lesson 1 of this module discussed the shelf life of indicator types; the cache TTL should follow it. A file hash's identity never changes (a given SHA-256 always names the same content), so a verdict on a hash can be cached for a long time, though the verdict itself may be revised as vendors learn more. A domain's reputation changes over days to weeks. An IP address's reputation can change within hours, especially for cloud and residential ranges where addresses are reassigned. Start with long TTLs for hashes, medium for domains and short for addresses, write the numbers down, and record the TTL in each cache entry.

**Negative caching.** "The source knows nothing about this value" is also an answer worth remembering, otherwise every new event re-asks the same question. But a negative answer ages faster than a positive one: a domain that no one has reported today may be reported tomorrow, once a campaign is noticed. Negative results therefore get a shorter TTL, and they are recorded as *no data from source X as of time T*, never as *clean*. This is the pipeline version of the Module 5 lesson that absence of a match is not evidence of absence.

**Invalidation.** A feed revoking or downgrading an indicator, or the TIP marking it a false positive, must flush every cached result derived from it regardless of TTL; a pipeline change should flush or version-label old results.

**Cache and validity are different clocks.** An indicator has its own `valid_until`, set by its producer; a cache entry has a TTL set by you. A result fetched yesterday and still inside its cache TTL can describe an indicator whose validity ended this morning. The pipeline must re-check validity against the as-of date every time it serves a cached result, not only when it first fetched it.

The kit shows the validity clock clearly. `ioc_match.py` evaluates `valid_until` against a fixed constant, `AS_OF = date(2026, 11, 3)`. Running a copy of the script with only that constant changed to `date(2026, 11, 15)` gives:

```terminal
$ python ioc_match_1115.py

MATCH    domain banyan-payroll-update.example    conf= 70 hits=  1 first=2026-11-03T06:12:00Z src=internal TLP:GREEN
EXPIRED  ipv4   203.0.113.66                     conf= 60 hits=  9 first=2026-11-03T06:42:00Z src=ISAC-A TLP:GREEN
         expired indicator still matches: review before acting
EXPIRED  ipv4   198.51.100.104                   conf= 40 hits=  1 first=2026-11-03T13:33:00Z src=open feed TLP:CLEAR
         expired indicator still matches: review before acting
no match sha256 9f2c...e1a0                      conf= 90 hits=  0 first=- src=vendor TLP:AMBER
```

The copy, `ioc_match_1115.py`, was made in a scratch folder next to a freshly loaded `minisiem.db`; the original script in the kit was not modified, and the script takes no arguments. The events are identical, so the hit counts are identical. The only difference from the original run is the status of `203.0.113.66`: its `valid_until` of 2026-11-10 is before the new as-of date, so the same nine VPN events now come back `EXPIRED` with the review warning. A cache that had stored "MATCH, confidence 60" on 3 November and served it unchanged on 15 November would be serving a wrong answer. The run also shows why the as-of date belongs in provenance: two honest runs over the same data disagree, and only the as-of date explains why.

## Rate limits, quotas and failures

Every external source, and many internal ones, limits how fast it may be queried. The pipeline must treat these limits as normal operation, because it is most likely to hit them during an incident, when analysts most need context.

**Budget before you call.** The deduplication and cache stages are the first rate-limit control: the Banyan example went from 588 candidate lookups to eight external values. Beyond that, a pipeline can keep a request budget per source and per period, and spend it in priority order: values from high-severity alerts first, background enrichment of low-priority events last or in off-peak batches.

**Respect refusals.** HTTP-based services commonly signal "too many requests" with status code 429 (defined in RFC 6585) and may include a `Retry-After` header (defined in the HTTP semantics specification, RFC 9110) saying how long to wait. The correct response is to stop sending to that source, wait at least as long as asked, and then retry with **backoff**: each consecutive failure lengthens the wait, usually with a little random jitter so that many workers do not retry in lock-step. Retrying immediately in a loop is how an integration gets its key suspended.

**Time out and say so.** A source that does not answer within a set time is treated as unavailable for this run. The result recorded is *source X unavailable at time T*, which an analyst reads very differently from *no data* and completely differently from *clean*. The alert proceeds with whatever the other stages produced; enrichment must never block an alert from reaching the queue.

**Degrade in a known way.** If the external service is down, alerts carry internal context only and are flagged for re-enrichment. If the internal TIP is down, the pipeline raises a health alert: six hours of silently lost intelligence matching is a coverage gap for the shift handover and any overlapping case record.

**Purpose.** This sequence diagram shows the time order of one lookup for an external value that is not yet cached, including a refusal from a rate-limited source. It matters because caching and rate-limit handling are where enrichment pipelines most often fail under load, and the failure is invisible until an incident.

**Components.** Four lanes run left to right. The orange **Pipeline worker** is the enrichment process handling one entity. The blue **Cache** stores earlier results keyed by value and source. The violet **Internal TIP** is the organisation's own threat-intelligence platform, holding feed and community data with markings. The slate **External service** is an approved third-party reputation source with a quota.

**Relationships and arrows.** Solid arrows are requests; dashed arrows are responses. The worker talks to every other lane, but the other lanes never talk to each other: the cache does not fetch on its own, and the external service never sees the internal platform.

**Execution flow.** First the worker asks the cache for the value and source and gets a dashed **miss**. It then asks the internal TIP, which answers with **no data**, recorded with its time. Only then does the worker query the external service for the canonical external domain. The service answers **429 Too Many Requests** with a `Retry-After` value. The worker waits and backs off, then sends the same request again and receives a dashed **verdict + source details**. Finally it writes the result to the cache with a TTL that depends on the entity type, and that final arrow carries the provenance fields as well.

**Decision logic.** Each arrow pair is a decision point. A cache hit within TTL would have ended the sequence after the first exchange. A TIP match would have provided the core intelligence and, depending on policy, made the external call optional. The 429 is not an error to log and ignore; it is an instruction that changes the worker's timing.

**Technical interpretation.** The negative TIP answer is also cacheable, with a shorter TTL. The retry obeys the server's requested delay rather than a fixed local timer, and the backoff grows if the refusal repeats. Both the TIP result and the external result are recorded separately, because the cache key includes the source.

**Practical example.** Of Banyan's external values, `files-share-drop.example` (the destination of one upload) is not in the fictional feed, so it would follow this exact path; a second alert on the same host later that day would stop at the first exchange.

**Security implications.** A worker that ignores 429 can lose its key mid-incident. A worker that treats a timeout as "clean" hides risk. A worker that sends internal values here leaks them; the gate in Figure 1 prevents that before this sequence starts.

**Key learning.** Ask the cache, then your own intelligence, then the outside world; obey the outside world's limits; and store every answer with its source and age.

## Privacy and sharing at pipeline scale

Module 5 set out the analyst's rules: minimum personal data, nothing internal to public services, passive rather than active lookups, and respect for sharing markings. A pipeline must enforce the same rules mechanically, because it makes thousands of decisions a day that no analyst will review individually. Four controls do this.

**A classification list that the gate trusts.** The gate needs an authoritative list of what is internal: address ranges (in Banyan, `10.0.0.0/8` as used by `triage.py`'s `ip_context` function), internal domain suffixes (`banyan.example`), the organisation's SaaS tenants and partner domains. Values matching the list never leave. The list is owned and versioned; a missing internal suffix becomes a disclosure on the first run.

**Per-source permissions.** Each source in the cascade has a written statement of what it may receive: entity types, sensitivity, and whether submissions are retained or shared by the provider. A contracted service with a data-processing agreement may receive external domains and addresses; a free public service that publishes submissions may receive nothing from an alert without analyst approval. File content is never uploaded automatically to a service that shares submissions.

**Markings travel with the value.** If a value entered the organisation through intelligence marked TLP:AMBER, sending that value to an external enrichment service passes it to a third party outside the recipient organisation, which the marking does not permit. Lesson 7 of this module covers TLP 2.0 in full; for the pipeline, the rule is that the gate checks the most restrictive marking already attached to a value before choosing destinations. In the kit's feed, `cdn-telemetry-sync.example` (TLP:AMBER from ISAC-A) may be matched internally but not submitted to a public service, whereas `198.51.100.104` (TLP:CLEAR, open feed) carries no such restriction.

**Personal data is minimised and logged.** Account names, e-mail addresses and anything else that identifies a person are enriched only from internal sources and only with the attributes the security decision needs. India's Digital Personal Data Protection Act, 2023 expects processing for a lawful purpose with reasonable safeguards; copying full HR records into every alert fails that test. The pipeline's query log is personal data too.

> [!CAUTION]
> The pipeline never resolves, browses or scans an indicator from the corporate network as a form of "enrichment". Active contact warns the adversary and, against third-party systems, can be unauthorised access under the IT Act 2000. Active analysis belongs in an isolated, authorised lab.

## Recording provenance

Provenance answers the question every reviewer eventually asks: *how did we know that, and when?* Without it, an enriched alert is a collection of assertions with no way to check them. With it, any value can be traced to its source and reproduced.

A minimal provenance record for one enrichment result carries the following fields. The format below is a design illustration for this lesson, not the output of a particular product; the values come from the kit's feed and its original run.

```json
{
  "entity": "cdn-telemetry-sync.example",
  "entity_type": "domain",
  "matched_in": "events.url (18 events, first 2026-11-03T06:17:00Z)",
  "source": "ISAC-A",
  "source_confidence": 85,
  "context": "C2 for loader seen in finance-sector phishing",
  "valid_until": "2026-12-31",
  "as_of": "2026-11-03",
  "marking": "TLP:AMBER",
  "retrieved": "live",
  "query_time_utc": "2026-11-03T07:05:00Z",
  "pipeline_version": "enrich-1.4",
  "gate_decision": "internal match only; external submission not permitted (TLP:AMBER)"
}
```

Each field has a job. `source` and `source_confidence` keep the producer's assessment separate from the SOC's own. `valid_until` and `as_of` together let a reviewer recompute the validity status, exactly as the two `ioc_match.py` runs showed. `marking` controls where the record may be copied. `retrieved` says whether the answer was live or served from cache, and if cached, the cache entry should carry its own original query time. `query_time_utc` is when the pipeline asked, not when the event happened; `pipeline_version` identifies results from a buggy release. `gate_decision` documents the privacy reasoning so that a reviewer can see the omission of an external lookup was deliberate.

Two further rules keep provenance useful. First, **never overwrite; append.** If the same value is enriched again tomorrow with a different answer, the case keeps both records; the change itself is information. Second, **keep the producer's words and the SOC's judgement apart.** "ISAC-A reports C2, confidence 85" is provenance; "we assess the beacon as malicious with high confidence" is an analytic conclusion written in the case notes (Module 5, Lesson 7), citing the provenance record as one piece of its evidence.

## Worked example: the Banyan pipeline run

Bringing the stages together for the Banyan data on 3 November 2026:

1. **Extract** 284 URL values and 304 address values from normalised fields.
2. **Canonicalise and deduplicate** to 9 URLs and 11 address strings; drop the placeholder `-` (10 events), leaving 10 addresses.
3. **Classify and gate.** Internal: 8 addresses in `10.40.0.0/24` and 3 URLs under `banyan.example`, resolved against the CMDB and history only. External: 6 host names extracted from URLs and 2 addresses.
4. **Cascade.** Stage 1 allowlists answer the routine destinations if the SOC has documented them (in the synthetic data, `news.example.com`, `cdn.example.org` and `maps.example.net` stand in for ordinary browsing). Stage 3, the TIP holding the kit's feed, answers four values: two domains and two addresses, exactly the four `MATCH` and `EXPIRED` lines of `ioc_match.py`. The remaining unexplained value, `files-share-drop.example`, goes to an approved external service under the rules of Figure 2.
5. **Record** each result with provenance; the `198.51.100.104` record carries `EXPIRED` and the review warning, and the vendor hash carries *no data in telemetry*, not *clean*.
6. **Attach** the records to the `R6`, `R1`, `R2` and `R4` alerts, and send feedback: if the analyst confirms that `198.51.100.104` was `gopal`'s ordinary VPN session, that is reported to the open feed's maintainers where a channel exists and recorded against the indicator in the TIP.

The run used eight external lookups and at most one external submission, leaked nothing internal, and produced records that will still explain themselves after the 10 November expiry of the spraying indicator changes the answer.

## Common mistakes and misconceptions

- **Enriching events instead of entities.** Looking up the same value once per event multiplies cost and quota use by the event count; enrich distinct canonical values and join the results back.
- **Serving cached matches without re-checking validity.** The cache clock and the indicator's validity clock are independent.
- **Treating timeouts and refusals as "clean".** They are *no answer*, and the record must say so.
- **Allowlists without owners.** An allowlist entry with no reason and no review date is an unaudited suppression.

## Security implications, detection and defence

The enrichment pipeline is itself an attack surface and a dependency. Its API keys belong in a secrets store, and its outbound connections should be restricted to approved sources and logged. An adversary who can influence a feed the pipeline trusts (a poisoned community feed, or an open feed that accepts submissions) can try to make benign infrastructure look malicious, to cause disruptive blocks, or to get their own infrastructure onto an allowlist; source reliability grading (Lesson 2) and allowlist governance are the defences.

Monitor the pipeline like any production service: per-source request, refusal and timeout counts, cache hit rate, values dropped at stage 2, and event-to-enriched-alert time. A falling TIP hit rate may mean a feed stopped updating.

## Key takeaways

- Enrichment at SOC scale is a pipeline: extract, canonicalise, gate, look up in cascade, record, attach and feed back; in the Banyan data 588 naive lookups become eight external values.
- The cascade runs from internal data, allowlists and cache to the internal TIP and only then external services, stopping on a definitive answer.
- Cache by value and source with type-specific TTLs, cache negatives briefly, and re-check validity against the as-of date on every use.
- Rate limits and timeouts are normal operation: back off, and record *unavailable*, never *clean*.
- The privacy gate and provenance records make enrichment safe to run and possible to reproduce.
