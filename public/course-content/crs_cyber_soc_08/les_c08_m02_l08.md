## Lab objective and scope

This lab turns the telemetry ideas of Module 2 into hands-on checks. You will regenerate the course dataset, ingest it into the course's teaching SIEM, inventory the sources it contains, measure their volume and silence, check the completeness of their fields, see how a parser turns raw syslog and JSON into a common schema, and then deliberately break the pipeline in three ways to see what an outage, a parse failure and duplicate delivery look like from inside the SIEM. The goal is the habit Lesson 7 argued for: **before you trust an empty alert queue, prove that the telemetry arrived, complete and on time.**

By the end of the lab you should be able to answer, for any source in the dataset: when did it first and last send events, how many per hour, from which hosts, with which fields populated, and what would a failure look like?

> [!IMPORTANT]
> **Authorisation and scope.** Everything in this lab runs on your own computer against a synthetic dataset about a fictional organisation, Banyan Microfinance. All names, hosts and addresses in it are fictional; IP addresses use private ranges and the RFC 5737 documentation ranges, and domains end in `.example`. No network connection is made and no real system is touched. The fault-injection step changes only copies of the dataset inside your own working folder.

## Key terminology

| Term | Meaning in this lab |
| --- | --- |
| Source inventory | The list of sources and hosts that are expected to send events, with first-seen and last-seen times. |
| Last seen | The timestamp of the most recent event from a source or host. |
| Silent minutes | Minutes between a source's last event and a reference time (here the last event in the whole dataset). |
| Hourly volume | Events per source per hour, the basic shape against which drops and spikes are judged. |
| Largest gap | The longest interval between consecutive events from one host, found with a window function. |
| Field completeness | The share of a source's events in which a rule-critical field is populated. |
| Fault injection | Deliberately damaging a copy of the data to see whether a check notices. |

## How the lab kit models a pipeline

The three kit scripts each stand in for one part of the pipeline described in Lesson 7. `make_dataset.py` plays the sources and the collection tier: it writes one fictional day of events from four sources (Windows Security, Sysmon-style endpoint, web proxy and VPN) into `banyan_events.jsonl`, one JSON event per line, already normalised into common field names. It uses a fixed random seed, so every learner gets byte-for-byte identical data. `minisiem.py` plays ingestion and storage: its `load` command reads the file line by line, copies twelve common fields into columns of an SQLite table called `events`, keeps the original JSON in a `raw` column, and builds an index on the timestamp; its `search` command runs any SQL you give it, standing in for a SIEM query language. `normalise_demo.py` plays the parser: it takes one raw firewall syslog line and one raw VPN JSON record, in two different formats and time conventions, and emits both in the same schema.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram maps the three kit scripts and their files onto the pipeline stages of Lesson 7, so that each command you run in this lab is clearly an action at a known stage, and each health check is clearly a measurement of a known component.

**Components.** On the left, **make_dataset.py** (labelled "sources + collection", fixed seed) produces **banyan_events.jsonl**, the 340-line JSON Lines file that stands for the events delivered by the collection tier. **minisiem.py load** is the ingestion step: it parses each line and writes the **events table in minisiem.db**, which holds twelve field columns plus the **raw** column. **minisiem.py search** is the query layer used for the health checks. On a separate branch, **normalise_demo.py** takes a **Raw syslog line** (firewall, local time, no year) and a **Raw VPN JSON** record (UTC) and turns both into **Normalised events** with ECS-style names. At the bottom, **Source-health checks** (inventory, volume, silence, completeness) read from the events table, and **make_faults.py**, the small helper you write in step 9, creates faulty copies of the dataset that feed the same load step.

**Relationships and arrows.** Solid arrows follow the data: the generator writes the file, the loader reads it and writes the table, and searches read the table. The dashed arrow from **make_faults.py** shows that the fault drills reuse exactly the same ingestion path with damaged input, which is the point: you are testing whether your checks notice problems, not testing a different pipeline.

**Execution flow.** You run the steps in order: generate and verify, load, run the health searches, run the parser demonstration, then inject faults and repeat the relevant checks.

**Decision logic.** At each health check you compare the result with what you expect: is every source present, is each hour's volume plausible, is any host silent, is any rule-critical field empty? An unexpected answer becomes a question to investigate, not an immediate conclusion.

**Technical interpretation.** The kit's events are already normalised by the generator, which is why `minisiem.py` can copy fields straight into columns. In production, the parser stage sits between the file and the table; `normalise_demo.py` shows what that stage does to two raw formats.

**Practical example.** When step 9 removes two hours of WS-104's proxy events, the load succeeds, the table looks healthy at a glance, and only the hourly-volume and largest-gap checks reveal the hole.

**Security implications.** The table is the only evidence the analyst sees. Whatever is lost, duplicated or unparsed before it reaches the table is invisible to every rule and every search that follows.

**Key learning.** Every health check in this lab measures one arrow on this diagram; knowing which arrow tells you where to look when a check fails.

## Step 1: regenerate and verify the dataset

A health check is only meaningful if you know exactly what data you started with. Regenerate the dataset and record its hash:

```terminal
$ python make_dataset.py
events written: 340
sources: ['proxy', 'sysmon', 'vpn', 'windows']
$ python -c "import hashlib; print(hashlib.sha256(open('banyan_events.jsonl','rb').read()).hexdigest())"
1dd2040ec8e28424b662143f826410fe0e7c2a9bb6898b6611e43f09f14b612b
```

`make_dataset.py` takes no options. It overwrites `banyan_events.jsonl` in the current folder and reports how many events it wrote and which sources they came from. The one-line Python command reads the file in binary mode and prints its SHA-256 digest. Because the generator uses a fixed seed and writes with sorted keys and Unix line endings, your digest should match the one above exactly; if it does, you and every other learner are analysing identical evidence. If it does not, check that you are running the kit's unmodified script and that no editor has rewritten the file's line endings.

Recording a hash of the input before analysis is a habit worth keeping: in a real investigation it is how you later show that the evidence you analysed is the evidence you collected.

## Step 2: ingest into the teaching SIEM

```terminal
$ python minisiem.py load
loaded 340 events
```

The `load` command creates (or recreates) `minisiem.db` in the current folder. It first drops any existing `events` table, creates a fresh one, inserts every line of `banyan_events.jsonl` and indexes the timestamp column. The count matches the generator's 340, which is the first and simplest health check: **events written equals events loaded**. In a production pipeline the equivalent comparison (events sent by the forwarder against events indexed by the SIEM, per source, per hour) is one of the most useful loss checks you can build.

Remember the order of operations in `load`, drop first and insert second. Step 9 shows why it matters.

## Step 3: build the source inventory

The first health search answers "what is here, and over what period?":

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS n, MIN(ts) AS first_seen, MAX(ts) AS last_seen FROM events GROUP BY source ORDER BY n DESC"
source | n | first_seen | last_seen
proxy | 284 | 2026-11-03T03:19:00Z | 2026-11-03T12:32:00Z
sysmon | 33 | 2026-11-03T03:13:00Z | 2026-11-03T06:14:00Z
windows | 13 | 2026-11-03T03:07:00Z | 2026-11-03T08:17:00Z
vpn | 10 | 2026-11-03T06:42:00Z | 2026-11-03T13:33:00Z
```

The `search` command takes one argument, an SQL statement in double quotes, and prints the column names and then each row separated by ` | `. `GROUP BY source` produces one row per source; `MIN(ts)` and `MAX(ts)` work on the ISO 8601 UTC timestamps because strings in this format sort in time order, which is one practical reason Lesson 6 insisted on a single, sortable time representation.

**Interpretation.** All four expected sources are present. Proxy events dominate (284 of 340), as Module 1 noted: web telemetry is high-volume. The day runs from 03:07 UTC (08:37 IST, the first workstation logon) to 13:33 UTC. Two rows deserve attention. Sysmon's last event is at 06:14 UTC, more than seven hours before the end of the data, and the VPN's first event is not until 06:42 UTC. Neither is yet a conclusion; both are questions for the next steps.

## Step 4: measure hourly volume per source

```terminal
$ python minisiem.py search "SELECT substr(ts,12,2) AS hour_utc, SUM(source='proxy') AS proxy, SUM(source='sysmon') AS sysmon, SUM(source='windows') AS windows, SUM(source='vpn') AS vpn FROM events GROUP BY hour_utc ORDER BY hour_utc"
hour_utc | proxy | sysmon | windows | vpn
03 | 16 | 4 | 8 | 0
04 | 45 | 18 | 2 | 0
05 | 24 | 10 | 0 | 0
06 | 37 | 1 | 0 | 9
07 | 36 | 0 | 2 | 0
08 | 32 | 0 | 1 | 0
09 | 26 | 0 | 0 | 0
10 | 25 | 0 | 0 | 0
11 | 32 | 0 | 0 | 0
12 | 11 | 0 | 0 | 0
13 | 0 | 0 | 0 | 1
```

`substr(ts,12,2)` takes the two hour digits from a timestamp such as `2026-11-03T06:14:00Z` (characters 12 and 13). In SQLite a comparison such as `source='proxy'` evaluates to 1 or 0, so `SUM(source='proxy')` counts the proxy events in each hour; this pivot gives one column per source, which is the shape of a typical SIEM source-volume dashboard.

**Interpretation.** Proxy volume follows the working day and tails off after 12:00 UTC (17:30 IST). Windows events cluster at 03:00 UTC, when the morning logons happen. Sysmon is busy for three hours and then flat at zero. The VPN is almost entirely in the 06:00 hour, with nine events, and one at 13:00. In a real SOC, a source that drops to zero in the middle of a working day would trigger a health alert. Before raising one here, you need the baseline, which is the subject of the next step.

## Step 5: run a silence check, and test it against a baseline

A silence check computes how long each source has been quiet. Here the reference time is the last event in the dataset, 13:33 UTC; in production it would be "now".

```terminal
$ python minisiem.py search "SELECT source, MAX(ts) AS last_seen, ROUND((julianday('2026-11-03T13:33:00Z') - julianday(MAX(ts)))*24*60) AS silent_min FROM events GROUP BY source ORDER BY silent_min DESC"
source | last_seen | silent_min
sysmon | 2026-11-03T06:14:00Z | 439.0
windows | 2026-11-03T08:17:00Z | 316.0
proxy | 2026-11-03T12:32:00Z | 61.0
vpn | 2026-11-03T13:33:00Z | 0.0
```

`julianday()` converts a timestamp to a fractional day number, so the difference of two of them multiplied by 24 and 60 is a number of minutes. `ROUND` removes the fractions.

**Interpretation.** Taken literally, this says Sysmon has been silent for 439 minutes (7 hours 19 minutes) and Windows Security for 316 minutes, and a naive threshold of, say, 60 minutes would raise alerts for both, and arguably for the proxy too. This is the moment to check the baseline. Open `make_dataset.py` and read how it creates Sysmon events: for each user it writes four routine process starts (`explorer.exe`, `outlook.exe`, `msedge.exe`, `excel.exe`) at random times within 120 minutes of the morning logon, plus one storyline event. The generator never models afternoon process activity at all. So the Sysmon silence is a property of how this teaching dataset was built, not an outage. A real Sysmon deployment on busy workstations would produce process events all day, and seven hours of silence would be a genuine alarm.

That is the lesson of this step: a silence check produces a **candidate**, and the candidate is resolved by comparing it with what the source normally does. In production the baseline is the same hour on previous days, not a reading of the generator's code, but the reasoning is identical. The Windows Security silence has the same explanation, with one twist you should note for later modules: the last Windows event is at 08:17 UTC, and Step 6 shows which host produced it.

> [!TIP]
> Set silence thresholds per source, and ideally per host group and time of day. A domain controller and a laptop do not share a normal quiet interval, and nor does a workstation at 11:00 and at 03:00.

```terminal
source | host | n | last_seen
sysmon | WS-101 | 4 | 2026-11-03T05:35:00Z
sysmon | WS-102 | 4 | 2026-11-03T04:39:00Z
sysmon | WS-103 | 4 | 2026-11-03T05:40:00Z
sysmon | WS-104 | 5 | 2026-11-03T06:14:00Z
sysmon | WS-105 | 4 | 2026-11-03T05:34:00Z
sysmon | WS-106 | 4 | 2026-11-03T04:47:00Z
sysmon | WS-107 | 4 | 2026-11-03T04:51:00Z
sysmon | WS-108 | 4 | 2026-11-03T04:51:00Z
windows | WS-101 | 1 | 2026-11-03T03:36:00Z
windows | WS-102 | 2 | 2026-11-03T04:05:00Z
windows | WS-103 | 1 | 2026-11-03T03:50:00Z
windows | WS-104 | 4 | 2026-11-03T08:17:00Z
windows | WS-105 | 1 | 2026-11-03T03:39:00Z
windows | WS-106 | 1 | 2026-11-03T03:07:00Z
windows | WS-107 | 1 | 2026-11-03T03:33:00Z
windows | WS-108 | 2 | 2026-11-03T04:05:00Z
```

**Interpretation.** All eight workstations (WS-101 to WS-108) report through both endpoint sources, so there is no missing host compared with the inventory. Every host has the four routine Sysmon events except WS-104, which has five, and WS-104 also has the most Windows Security events and the latest one. You saw in Lesson 7 that the dataset includes a Security log clear (event ID 1102); a last-seen time per host is exactly where such an event becomes visible as "the last thing this host said". The investigation of WS-104 belongs to later modules; for a health check, the point is that per-host last-seen is the view that reveals a single host going quiet.

For high-volume sources such as the proxy, the most sensitive check is the **largest gap** between consecutive events from each host:

```terminal
$ python minisiem.py search "SELECT host, MAX(gap_min) AS max_gap_min FROM (SELECT host, ROUND((julianday(ts) - julianday(LAG(ts) OVER (PARTITION BY host ORDER BY ts))) * 1440) AS gap_min FROM events WHERE source='proxy') GROUP BY host ORDER BY max_gap_min DESC LIMIT 3"
host | max_gap_min
WS-107 | 88.0
WS-104 | 75.0
WS-105 | 71.0
```

`LAG(ts) OVER (PARTITION BY host ORDER BY ts)` gives, for each proxy event, the timestamp of the previous event from the same host; the inner query turns the difference into minutes (1,440 minutes per day), and the outer query keeps the largest gap per host and lists the top three. On the clean dataset the longest proxy silence of any workstation is 88 minutes. Keep this result: it is your baseline for step 9.

## Step 7: check field completeness

Events that arrive but lack the fields rules depend on are a quieter kind of failure. Count the empty (NULL) values of key fields per source:

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS n, SUM(host IS NULL) AS no_host, SUM(user IS NULL) AS no_user, SUM(src_ip IS NULL) AS no_src_ip, SUM(outcome IS NULL) AS no_outcome, SUM(event_id IS NULL) AS no_event_id FROM events GROUP BY source ORDER BY n DESC"
source | n | no_host | no_user | no_src_ip | no_outcome | no_event_id
proxy | 284 | 0 | 0 | 0 | 284 | 284
sysmon | 33 | 0 | 0 | 33 | 33 | 0
windows | 13 | 0 | 0 | 3 | 0 | 0
vpn | 10 | 10 | 0 | 0 | 0 | 10
```

**Interpretation.** Most of the NULLs are by design, and knowing which is the point of a completeness baseline. Proxy events carry an HTTP `status` rather than an `outcome` and have no event ID; Sysmon process events have no source address; VPN events identify a user and an external address but not an internal host. These are the field-semantics differences of Lesson 5. The `user` column is fully populated in every source, which matters because most of the kit's detections pivot on it. A completeness check alerts when these numbers **change**, for example when `no_user` for the VPN jumps from 0 after a firmware upgrade.

The Windows row hides a subtlety:

```terminal
$ python minisiem.py search "SELECT source, src_ip, COUNT(*) AS n FROM events WHERE source='windows' GROUP BY src_ip"
source | src_ip | n
windows | None | 3
windows | - | 10
```

Ten Windows events have the literal string `-` as the source address and three have no value at all. The ten are interactive logons (event IDs 4624 and 4625 with logon type 2), for which Windows records `-` because there is no network source; the three are account-management and log-clear events that have no source-address field in the dataset. A completeness check that only counts NULLs would treat `-` as populated. Decide, per source, which placeholder values count as empty.

## Step 8: watch a parser normalise two raw formats

So far the data arrived pre-normalised. `normalise_demo.py` shows what the parsing stage of a pipeline does to raw input:

```terminal
$ python normalise_demo.py
{"@timestamp": "2026-11-03T06:46:21Z", "destination.ip": "10.40.0.5", "destination.port": 3389, "event.action": "drop", "event.module": "firewall", "host.name": "fw01", "network.transport": "tcp", "source.ip": "203.0.113.66"}
{"@timestamp": "2026-11-03T06:46:00Z", "event.action": "login", "event.module": "vpn", "event.outcome": "success", "source.ip": "203.0.113.66", "user.name": "gopal"}
```

The script takes no arguments. Its first input is a classic BSD-style firewall syslog line, `Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389`, which has no year and no time zone. The parser supplies the year (2026) and, because the firewall is configured in India Standard Time, applies UTC+05:30 and converts: 12:16:21 IST becomes 06:46:21Z. It then extracts the action, host, addresses, protocol and port with a regular expression and maps them to Elastic Common Schema-style names (`source.ip`, `destination.port`, `event.action`). The second input is a VPN record in JSON whose timestamp is already UTC; the parser renames `clientIP` to `source.ip`, `user` to `user.name` and lower-cases `SUCCESS` to `success`.

**Interpretation.** After parsing, the two records from different devices share field names and a time base, and they can be correlated: the same external address, `203.0.113.66`, was dropped by the firewall on port 3389 at 06:46:21Z and logged in successfully to the VPN as `gopal` 21 seconds earlier. Before parsing, the syslog line claimed a time of 12:16 and the VPN 06:46, and a naive comparison would have put them five and a half hours apart. This is why parsing at ingest is a pipeline-reliability concern: a wrong time-zone assumption in the parser silently breaks every cross-source correlation that follows. Module 3 builds on this script in detail.

## Step 9: inject faults and prove the checks notice

A health check that has never been seen to fire is an assumption. In this step you create three damaged copies of the dataset, each modelling a failure from Lesson 7, load each one into its own copy of the teaching SIEM, and see which checks catch it. Save the following helper as `make_faults.py` in your working folder. It is not part of the kit; it only reads your copy of `banyan_events.jsonl` and writes new files into three subfolders.

```python
"""Build three faulty copies of the lab dataset for source-health drills."""
import json
import shutil
from pathlib import Path

lines = Path("banyan_events.jsonl").read_text(encoding="utf-8").splitlines()

def write(folder, rows):
    Path(folder).mkdir(exist_ok=True)
    shutil.copy("minisiem.py", folder)
    Path(folder, "banyan_events.jsonl").write_text("\n".join(rows) + "\n", encoding="utf-8", newline="\n")
    print(folder, "->", len(rows), "lines")

def lost(line):
    e = json.loads(line)
    return (e["source"] == "proxy" and e.get("host") == "WS-104"
            and "2026-11-03T07:00" <= e["@timestamp"] < "2026-11-03T09:00")

write("outage", [l for l in lines if not lost(l)])        # two-hour proxy outage for WS-104
write("broken", lines[:100] + [lines[100][:-20]] + lines[100:])  # one truncated record
write("dup", lines + lines[200:205])                       # five events delivered twice
```

The `outage` copy drops every proxy event from WS-104 between 07:00 and 09:00 UTC, as if that host's traffic had stopped reaching the relay. The `broken` copy inserts one record whose last 20 characters are cut off, as a truncated network write would leave it. The `dup` copy appends five events a second time, as an at-least-once forwarder would after lost acknowledgements. Each folder gets its own copy of `minisiem.py`, because the script reads `banyan_events.jsonl` and writes `minisiem.db` in the folder it runs in.

```terminal
$ python make_faults.py
outage -> 326 lines
broken -> 341 lines
dup -> 345 lines
```

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The chart shows Drill A's result as a source-health dashboard would: WS-104's proxy events per UTC hour after the simulated outage, so that you can see why a per-host hourly view exposes a hole that the overall load count hides.

**Components.** There are ten bars, one per hour from **03 UTC** to **12 UTC**. The bars for 03, 04, 05, 06, 09, 10, 11 and 12 show the counts from the outage copy: 3, 3, 1, 14, 5, 2, 5 and 2. The two red bars for **07 UTC** and **08 UTC** have a value of zero and are labelled with the clean-day counts they should have shown, 11 and 3. The 06 UTC bar is highlighted because it is the busiest hour for this host on this day.

**Relationships.** Read the bars left to right as time. The chart compares each hour against two references at once: neighbouring hours on the same day, and the clean dataset, which plays the role of the baseline that a real SOC would take from previous days.

**Execution flow.** The health search runs, groups WS-104's proxy events by hour, and the dashboard draws one bar per hour of the expected working day. Unlike the raw query output, a dashboard built on an expected list of hours shows the missing hours as zero instead of omitting them.

**Decision logic.** A rule such as "a host that normally sends proxy traffic during working hours sends none for a full hour" fires on 07 UTC and again on 08 UTC. A softer rule, "an hour below a fraction of its baseline", would also flag 08 UTC on a day when traffic was merely reduced.

**Technical interpretation.** The 14 events at 06 UTC are worth a second look in their own right: on the clean day that hour includes the start of a regular, small-request pattern from WS-104 that later modules analyse. For health purposes, the point is that a high-volume hour followed by two empty ones is not a normal shape for an office workstation.

**Practical example.** At Banyan, the morning-shift analyst who sees this chart would check whether WS-104 was switched off (Windows logon and Sysmon events would also stop), whether its proxy configuration changed, or whether the relay dropped its traffic, and would open a pipeline ticket with the SIEM engineering team.

**Security implications.** A single sensitive host falling silent is exactly what an intruder who stopped an agent or redirected traffic would produce. The health alert therefore goes to the SOC queue, not only to operations.

**Key learning.** Draw per-host volume against an expected list of hours and a baseline; a missing hour is invisible in a raw count but obvious as a zero bar.

### Drill B: one malformed record


The traceback is abridged here; your file paths will differ. The truncated record ends inside a string value, so the JSON decoder rejects it, `load` stops, and the script exits with an error. ...
```terminal
json.decoder.JSONDecodeError: Invalid control character at: line 1 column 167 (char 166)
$ python minisiem.py search "SELECT COUNT(*) AS n FROM events"
n
0
```

One bad line out of 341 emptied the whole store. Recall from step 2 that `load` drops the table before inserting: the drop succeeded, the inserts never happened, and the SIEM now holds nothing. Every rule and every search would return zero results, and an analyst glancing at an empty queue might think it was a quiet day. This is a deliberately simple teaching script, but production pipelines fail in the same two ways: a strict parser that stops a whole batch on one bad record, or a lenient one that silently discards the record. The defences are those of Lesson 7: tag and keep unparsable records, count them, never destroy good data before new data is safely written, and alert when a source's volume falls to zero.

### Drill C: duplicate delivery

```terminal
$ cd ../dup
$ python minisiem.py load
loaded 345 events
$ python minisiem.py search "SELECT COUNT(*) AS rows, COUNT(DISTINCT raw) AS distinct_events, COUNT(*) - COUNT(DISTINCT raw) AS duplicates FROM events"
rows | distinct_events | duplicates
345 | 340 | 5
```

The load succeeds and reports 345 events, five more than the generator wrote. Comparing the row count with the number of distinct raw events reveals the duplicates, because the `raw` column holds each event exactly as delivered. To see which ones:

```terminal
$ python minisiem.py search "SELECT source, COUNT(*) AS copies, substr(raw,1,60) AS event_start FROM events GROUP BY raw HAVING COUNT(*) > 1"
source | copies | event_start
proxy | 2 | {"@timestamp": "2026-11-03T07:37:00Z", "bytes_out": 220, "ho
proxy | 2 | {"@timestamp": "2026-11-03T07:38:00Z", "bytes_out": 3108, "h
proxy | 2 | {"@timestamp": "2026-11-03T07:42:00Z", "bytes_out": 708, "ho
proxy | 2 | {"@timestamp": "2026-11-03T07:42:02Z", "bytes_out": 220, "ho
proxy | 2 | {"@timestamp": "2026-11-03T07:43:00Z", "bytes_out": 2936, "h
```

All five are proxy events from the 07:00 hour. Duplicates rarely matter for a single-event detection, but they inflate counts: any rule or metric that counts requests per host per hour would over-report that hour. Real events often lack a unique identifier, and two genuine events can share every field, so de-duplication on the whole raw record is a teaching shortcut; production pipelines de-duplicate on an event ID assigned at the source or by the forwarder.

## Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| `no such table: events` | You ran `search` before `load` in this folder. Run `python minisiem.py load` first. |
| `FileNotFoundError: banyan_events.jsonl` | You are not in the folder that holds the dataset, or you skipped step 1. |
| Hash in step 1 differs | The script or file was modified, or line endings were converted. Re-copy the kit and regenerate. |
| Counts differ from this lesson | You are searching a fault-drill database. Check which folder your terminal is in. |
| `no such function: LAG` or a syntax error near `OVER` | Your SQLite is older than 3.25. Use a current Python release. |
| Quoting errors in the shell | Keep the whole SQL statement in double quotes and string values in single quotes, as shown. |

## Key takeaways

- Start every analysis by proving what data you have: hash the input, and compare events written with events loaded.
- A source inventory with first-seen and last-seen times, hourly volume per source and per-host coverage are the core source-health views.
- A silence check produces candidates; the baseline decides. In this dataset the Sysmon silence is a property of the generator, not an outage, and you can prove it by reading the source.
- Field completeness has its own baseline: many NULLs are by design, and placeholders such as `-` must be counted as empty where they mean empty.
- Parsing fixes formats and time: `normalise_demo.py` turned an IST syslog time of 12:16:21 into 06:46:21Z so it could be correlated with a UTC VPN record.
- Fault drills prove the checks work. A two-hour outage loaded without error and was caught by the largest-gap check; one malformed record emptied the store; duplicate delivery inflated counts until distinct raw events were compared.
