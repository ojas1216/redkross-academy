## Introduction and conceptual foundation

The report button brings a message into the SOC. The next responsibility is to learn enough about any links or attachments to decide what needs protection. A mail client makes both objects easy to activate, which is a poor property for an evidence viewer. Start from the preserved artifact and an approved analysis workflow. The first pass is static. Read the parts already available to the organisation, compare them with trusted context, and decide whether specialist analysis is justified. The analyst should be able to explain the purpose of each check and what further evidence would change the outcome.

A link can have friendly display text and a different recorded destination. A document can have a familiar name and content that does not fit the work the recipient expected. Neither discrepancy proves a compromise. It does justify preserving evidence and examining the message in context. The important distinction is between finding a suspicious object and finding evidence that a person interacted with it. A delivery trace, an automated preview and a user-initiated browser request answer different questions. Keep their classifications separate while deciding whether the case needs endpoint or identity response.

## What to preserve before looking

Ask for the original as provided by the approved reporting route. Preserve the original message and record its case identifier, the receiving account, the acquisition method and the timestamp. An analyst can work from a separate derived view containing plain text and a list of filenames or link destinations. A screenshot is useful for visual context when it is all that is available. It may omit the destination, the attachment or the trace information, so state that limitation and request a proper export from the mail team where policy permits. Do not ask the employee to open the message again to get more evidence.

The original may include private data, tracking identifiers, or content that a viewer automatically fetches. Use the approved viewer with remote content disabled and the evidence store that the organisation has designated. Restrict case access to the people who need it. Avoid copying the message body into ticket comments or chat for convenience. The raw record should remain available to authorised investigators so that later examination does not depend on screenshots or recollection. If you create a redacted view for an update, name it as a derivative and refer back to the original evidence identifier.

Record both the supplied filename and where you obtained the bytes. If an approved ingestion service extracted the file from the original message, preserve the extraction record. A user might submit a document saved days earlier under a new name. A matching hash may later establish that two byte streams match. A filename match alone cannot establish that the submitted copy is the same as the delivered attachment. In the same way, a copied URL can omit a meaningful path or include a line break that came from the view. Keep the source, the exact value and any display transformation distinct.

## Interpret link evidence statically

Analysts commonly need to compare three separate fields. The first is the display text a reader saw. The second is the destination recorded in the original message. The third is any destination actually observed by an approved browsing, security or proxy service. At intake the third field often does not exist. Write ?not observed? and preserve that gap. A service can add a protective rewrite or redirect, and legitimate businesses can use several domains. A different recorded destination raises a question to check with an independent source, such as the administrator of the approved mail rewrite service or the known owner of the business workflow.

A URL includes the URI scheme, an authority that normally contains the host, and optional path and query. The host is the relevant starting point when asking who operates the destination. A familiar organisation name elsewhere in the text is not proof that the destination belongs to that organisation. When the supplied value is long or ambiguous, use an approved offline parser that separates those fields and displays the original beside the parsed parts. Retain the displayed form and the host as separate fields to make it possible to review whether the parser handled the value correctly. If the parser cannot interpret the value, write that state down and route the artifact for review. Do not choose a destination by visually scanning a confusing string.

Treat path and query content as potentially sensitive. They can include identifiers tied to a recipient or a document and may be more revealing than a domain name. An analyst may need the full record to investigate an incident, while a general team update may need only a defanged domain and an evidence pointer. Use the right copy in each destination. If an approved internal reputation system already knows the domain or hash, record the current result, source and date. Reputation data can be incomplete or stale. A previous observation is a lead whose relevance depends on the exact asset, time and purpose.

An application or mail gateway may have fetched a link automatically. Look for context around any observed request. Did it originate from an internal analysis service, an employee device, a proxy identity, or an unclassified source? Was the next related record a browser navigation tied to the recipient's session, an automated security action, or only a DNS lookup? A DNS lookup helps identify interest in a name, but it does not establish the final URL or user action. State each observation at the level supported by the source. Support for a click can increase when a user report and a device record align in time. A click alone does not settle whether a person entered data, approved a prompt or transferred funds.

## Interpret attachment evidence statically

Start with the claimed filename, the mail system's declared media type, the observed size and any file identification produced by your approved tools. Extensions and MIME labels describe claims or presentation. A file-type recogniser tries to identify structure from bytes, and its output can still be incomplete, especially for container formats. Treat the parser and the evidence source as separate. For example, a gateway may describe a container file while a trusted internal tool identifies the kind of document inside it. Those results can both be correct. Preserve the raw artifact and record what each tool actually saw.

Look for a mismatch between the expected work and the delivered object. An accounts payable employee might expect a routine invoice in an approved service and receive an unexpected attachment instead. Verify the business context through the organisation's known vendor or service channels. If the file needs technical review, send the preserved object through the policy-approved intake route for analysis. An analyst should never need to enable active content or open the object from a normal workstation to determine whether it is relevant to the case. When a safe path is unavailable, preserve it and escalate. Write down why the assessment remains provisional.

A SHA-256 digest lets the SOC refer to exact bytes. Compute or obtain it through the approved evidence pipeline and log the value with the tool or source and timestamp. The same payload may appear under several filenames, so exact matching can support grouping. On the other hand, a changed object, even one that appears similar to a human reader, usually yields a different digest. An unmatched digest means that this byte stream was not found in the lookups performed. It does not indicate a safe file. A known digest must also be interpreted with the quality and source of the record. A digest and a filename do not establish whether the document was actually opened.

Collect the container and any individual extracted object as different evidence items when extraction is part of the approved workflow. The evidence record should show which object came from which message and which digest describes it. If a file is encrypted or malformed, note exactly what the receiving system observed. Avoid claiming that the attachment was examined when only its outer container was visible. The analyst can ask the specialist which further work is permitted, what controls apply, and whether existing endpoint observations can answer the response question with less exposure to the original file.

### Visual Walkthrough & Architectural Breakdown

Read the first box as a change in working material. The report is a user interaction and a signal. The preserved message is an artifact. The SOC acquires the best available source through the approved route and keeps it intact. The second box produces two lightweight records: a link record containing display text and the destination in the source, and an attachment record containing the claimed filename and any reliable static observations. The evidence identifiers in those records make it possible to review a discrepancy without opening the same item independently on several workstations.

The comparison step asks whether the recorded values fit the stated business purpose and earlier findings. A familiar filename has little value when an invoice was never expected. An unfamiliar domain may be an approved mail service. Use an independently maintained directory or policy to test an explanation. Review activity observations separately. If the available logs document only an automated preview, the report should not say the employee clicked. The figure therefore shows static classification and activity context as inputs to the same decision. Neither input substitutes for the other.

The final decision box is about ownership. A pending classification can go to a specialist using an approved route while the incident lead deals with an urgent user interaction. For example, a user may confirm they entered an authentication secret while the original message is still being collected. The lead can direct an identity response without waiting for complete file identification. Conversely, an unexplained attachment can justify holding other copies for review even when no activity has been confirmed. The final case record preserves both decisions and their rationale. A next-shift reviewer should be able to tell which action was justified by the artifact, which was justified by the user or device evidence, and what event would prompt the case to be reassessed.

## Work a case from a static record

The following records are fictional training observations. The mail gateway delivered an invoice notice to a payments approver. A case note records display text ?View November invoice? and a destination host under `invoice-review.example`. The finance team's independently maintained vendor record names a different approved portal. A gateway preview record occurred immediately after receipt. The employee says they reported the email without clicking. The report includes a file named `November-statement.docm`, but the only classifier output is the stated MIME label. Accounts payable has not confirmed that the transaction is expected.

One reasonable intake conclusion is that the request and destination are unverified, and the only recorded request comes from an automated security service. No employee click is established by the training records. Ask the mail owner to preserve the original and search for comparable deliveries using identifiers associated with the case. Ask Finance to verify the invoice with the known vendor. Ask the approved artifact-analysis team to identify the preserved attachment, beginning with saved static evidence. The analyst can prioritise according to the possible payment impact and evidence of exposure even without deciding that malware executed. The next status update should include what the teams found and what remains open.

Change one fact for a second run. The recipient separately confirms opening the link and entering a work password. Activity evidence now justifies involving the identity team immediately, even if the mail classification is unchanged. Record what the reporter says they did and the approximate time. Never ask for the password. Use an independently verified channel to coordinate response and preserve the sign-in timeline. If another analyst later learns the portal was authorised, that discovery is important, but the unexpected credential entry still needs a careful review of context before the identity team reverses its action. The artifact verdict and the account decision each follow their own evidence.

Change a different fact for the third run. Endpoint telemetry shows the employee's system launching an unusual process after opening the document. Record the stated open time and the observed process time, identify the data source and note whether the record directly associates the process with the document. Escalate to the endpoint responder with the evidence and a request to verify the process chain and scope. The original can remain protected while that work proceeds. Do not combine the previous variation with this one. In operations two similar cases can have the same subject and different consequences, so keeping the evidence and its case ID together prevents overestimating impact.

## Reviewer checklist

Before handing the case off, check whether a peer can locate the original and understand which file was examined. Verify that any lookup has a date and data source. Check that suspicious destinations appear in a form suitable for the reader and that the unmodified version remains in the approved evidence store. Ask whether the case distinguishes a legitimate rewrite, automated traffic and a real client observation. Look for broad statements such as ?nobody clicked.? If the SOC can only search a specific set of sources and times, state those bounds and describe any missing data. The most important missing observation often dictates which specialist should own the next step.

For routine review, compare the case note against three questions. What do we know about the object? What do we know about user or system activity? Which person or team is authorised to reduce risk while preserving evidence? A complete answer can acknowledge uncertainty. In an incident, a precise next action sometimes matters more than a perfect classifier verdict. Clear notes help the organisation route the mail, identity and endpoint decisions to the people who can verify their outcomes.

## Practical application

Use the three fictional variants above. Prepare a table with columns for observation, source, limitation, decision and owner. Include at least one item that is suspicious but does not establish user interaction, one item that justifies immediate action, and one item that needs confirmation. For each item, identify one later observation that could change the decision. Then draft a status update that a service desk analyst could share without including any live destination or personal information. A peer should be able to infer the same case priorities without seeing the original attachment.

## Key takeaways

- Preserve the original and use a controlled view for static inspection.
- Keep observed destinations, automated requests and confirmed user actions separate.
- Use exact file identity, policy-approved lookups and independent business verification.
- Give each uncertain claim a next owner and a review condition.
