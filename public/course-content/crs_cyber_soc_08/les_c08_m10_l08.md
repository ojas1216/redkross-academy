## Lab overview

This lab brings together the whole module. You will plan and carry out a complete paper hunt over a supplied evidence pack, reach a defensible outcome for each case, and write a scoped hunt report. The lab is designed for 90 minutes and can be completed with no network access, no live systems and no software beyond a text editor.

The lab is read-only and defensive throughout. You will analyze saved, fictional records. You will not reproduce any activity, contact any domain or address, or handle any file. All domains use the reserved .example suffix, and all external addresses are from documentation ranges.

The evidence pack has two parts with different provenance, and keeping them apart is part of the assessment.

- **Part A: Banyan saved-record facts.** These facts come from the Banyan Microfinance lab kit. Verify them against the original JSON Lines file. Cite the filename and one-based line numbers so another analyst can find the same records.
- **Part B: synthetic lab fixture.** These records were authored for this lab to give you a benign comparison case. They are not Banyan data and not output from any system.

The lab has four cases. Expect one to end positive for escalation, one benign, and two that are wholly or partly no-data. The point of the lab is not to find something bad. It is to show that your outcome for each case follows from the records and states what they cannot show.

## Learning goals for the lab

By the end of the lab you should be able to:

- Form and prioritize hypotheses from the supplied records, writing refuting evidence first.
- Build a data-needs matrix that classifies each question as answerable, partial or unanswerable.
- Trace hunt queries by hand and cite the records that support each result.
- Compare observations against the available baseline and state its limits.
- Assign positive, benign or no-data outcomes with confidence and reasons.
- Write a report that separates observation, enrichment, inference and gaps.

## Lab rules

1. Work only from the evidence pack. Do not assume records that are not described.
2. Keep Part A and Part B separate. Never use Part B values as Banyan baselines.
3. Write each hypothesis and its refuting evidence before you read the case's records closely.
4. Label every claim in your report as OBSERVED, ENRICHMENT or INFERENCE, and give its source.
5. Do not invent record identifiers. Cite Part A as "saved-record summary" unless you have the saved rows.
6. Use calibrated language. Avoid "malicious," "compromised" or "exfiltrated" unless the records support them.

## Lab tasks and timing

**Task 1, 10 minutes: hypotheses.** Write one hypothesis for each case, using behavior, scope, predictions, refuting evidence and data feasibility.

- Case 1: WS-104 download, Office child process and later outbound activity.
- Case 2: WS-411 large upload in Part B.
- Case 3: VPN authentication pattern from 203.0.113.66.
- Case 4: a connection between the gopal VPN authentication and WS-104.

Rank the four by impact, plausibility and feasibility.

**Task 2, 10 minutes: data needs.** Build a data-needs matrix with one row per prediction. Mark each answerable, partial or unanswerable, and state the consequence.

**Task 3, 20 minutes: queries.** Write pseudocode for:

- A stacking query that counts distinct hosts per destination in the Banyan proxy data for 2026-11-03.
- A sequence query that joins a WS-104 proxy request to an endpoint event with an Office parent within 0 to 10 minutes after.
- A VPN query that counts distinct failed identities per source address in a short window and shows any following success.
- A Part B query that compares each host's backup volume with its baseline maximum.

Trace each query by hand over the records available to you. For Part A, where only the summary exists, state what the query would return given the summary and what you would need to confirm in the saved rows.

**Task 4, 10 minutes: baselines.** State the baseline available for each case. For Case 1, explain what a same-day peer comparison could and could not show. For Case 2, compare L06 with WS-411's baseline and peers.

**Task 5, 15 minutes: validation and outcomes.** For each case, list corroborating evidence, test the main benign explanation, check for false negatives, and assign positive, benign or no-data with confidence and a reason. Assign outcomes per part where a case has parts that differ.

**Task 6, 25 minutes: report.** Write the hunt report using the structure from Lesson 6, with handoff notes for incident response, detection engineering and data engineering.

## Working notes: how to approach each case

These notes guide reasoning without giving the full answer. Attempt the tasks before reading the model findings.

**Case 1.** The predictions are a rare download, an Office child process shortly after on the same host, and later outbound activity unusual among peers. The summary gives a two-minute gap between 06:12:00 and 06:14, but the endpoint time is reported to the minute, so the gap is approximate. The main benign explanations are that the downloaded file was a legitimate business document and the child process a routine helper, that cdn-telemetry-sync.example is a widely used service, and that files-share-drop.example is a sanctioned file share. Your stacking query decides the second and third; the summary does not tell you how many other hosts contacted these domains.

**Case 2.** L06 is the largest row by a wide margin, at almost twice WS-411's baseline maximum, which is exactly the kind of observation that would be flagged by a volume-only rule. Look at destination prevalence and at the enrichment before deciding.

**Case 3.** Treat the authentication pattern and the post-authentication question as separate parts. Ask what a shared egress address would look like and whether the data could show it.

**Case 4.** Ask which field would link the two threads, and whether it exists.

## Model findings

Compare your work with the following. Wording can differ; the outcomes, reasons and limitations should match.

**Case 1, WS-104 thread: positive for escalation, moderate confidence, conditional on prevalence.**
OBSERVED (saved-record): proxy request from WS-104 to banyan-payroll-update.example at 06:12:00Z; endpoint Office child process at 06:14; 18 requests to cdn-telemetry-sync.example from 06:17:00Z to 07:42:02Z; one request to files-share-drop.example at 08:12:00Z with 48,200,000 outbound bytes.
INFERENCE: the download-then-Office-child sequence on one host is consistent with document-driven execution. The later activity is consistent with outbound communication and a large transfer.
Conditions: confirm in the saved rows that the endpoint record's host is WS-104 and that the three destinations are rare among workstations on 2026-11-03. If any destination is common among peers, lower confidence for the related part.
Limitations: no mail data, so delivery cannot be determined; no payload evidence, so file content and transfer content are unknown; baseline is same-day only if no earlier dates exist in the saved records; interval regularity of the 18 requests requires reading each timestamp.
Action: escalate to incident response with these conditions and gaps stated.

**Case 2, WS-411 large backup upload: benign, high confidence.**
OBSERVED (synthetic): L06, WS-411 sent 51,300,000 bytes to backup-vault.example at 01:02:44Z, within three minutes of five peers sending to the same destination.
OBSERVED (synthetic baseline): the destination is contacted nightly by all six hosts; WS-411's previous maximum is 26,500,000.
ENRICHMENT: CHG-SYN-2291 records an expected one-time increase for WS-411 from 2026-10-20.
INFERENCE: the volume deviation on L06 is explained by the documented change; the destination is common and expected.
Action: close, with a note to detection engineering that change-driven volume increases need a suppression process that has an owner and an expiry date. Recheck WS-411's next nightly volume to confirm the increase was one-time.

**Case 3, VPN authentication from 203.0.113.66: authentication pattern positive for escalation at moderate confidence; post-authentication activity no-data.**
OBSERVED (saved-record): failed authentication for eight distinct identities from 203.0.113.66, and success for gopal at 06:46:00Z.
INFERENCE: consistent with guessing across accounts followed by a successful authentication.
Benign alternative: shared egress address. Not ruled out; testing it needs historical VPN data showing whether this address normally carries many identities.
No-data: whether the gopal session accessed any resource could not be determined; VPN records contain no later session activity.
Action: escalate the authentication pattern so identity owners can verify the gopal authentication; hand data engineering a request for VPN session logging.

**Case 4, link between the gopal authentication and WS-104: no-data, link unsupported.**
OBSERVED: no shared host, identity or session field connects the VPN records to the WS-104 proxy or endpoint records.
INFERENCE: temporal proximity on the same morning is not evidence of connection. Inventory ownership of WS-104, if any, would be enrichment and cannot establish that gopal used WS-104 on 2026-11-03.
Action: report the two threads as separate findings; carry forward the link question with the trigger "revisit if session, endpoint logon or identity provider records linking the VPN identity to a host become available."

## Report structure for Task 6

Use these headings in your report:

1. **Summary.** Four cases, outcomes and confidence in plain language, no more than six sentences.
2. **Scope.** Entities, UTC windows, sources and exclusions for Part A and Part B separately.
3. **Data coverage and gaps.** The data-needs matrix and what it means for each case.
4. **Method.** Queries in full with versions, baselines used and validation checks performed by hand.
5. **Findings.** One subsection per case, with labeled claims and citations.
6. **Limitations.** Every gap that limits a conclusion, and the effect on the conclusion.
7. **Handoffs.** Separate notes for incident response, detection engineering and data engineering.

## Common errors in this lab

- **Merging the threads.** Writing that the VPN user reached WS-104, or presenting the morning as one intrusion.
- **Mixing provenance.** Using Part B baseline values to judge Banyan volumes.
- **Reading names as evidence.** Treating "payroll" or "telemetry" in a domain as telling you content or legitimacy.
- **Treating 48,200,000 bytes as content.** The proxy shows volume; content is unknown.
- **Closing Case 2 on volume alone, or escalating it on volume alone.** The outcome depends on prevalence and enrichment, not size.
- **Single outcome for Case 3.** The authentication pattern and session question have different outcomes.
- **Invented citations.** Making up row identifiers for Part A.

## Assessment rubric

Your instructor or reviewer will assess the report against five criteria, each scored from 0 to 4.

- **Hypotheses:** testable, with refuting evidence written first, and correctly scoped.
- **Data and queries:** a complete data-needs matrix; queries that use the correct building blocks; hand traces that are accurate.
- **Outcomes:** each case and part assigned correctly, with confidence and reasons.
- **Provenance and language:** Part A and Part B kept separate; claims labeled; calibrated wording; no invented citations.
- **Handoffs:** specific, audience-appropriate actions and carry-forward triggers.

A report that reaches the right outcomes but merges provenance or overstates confidence should not score above 2 on the relevant criterion. A report that reaches a different outcome with sound, documented reasoning and correct provenance can score well; the reasoning matters as much as the label.

## Key takeaways

- A complete hunt runs from hypothesis through data needs, queries, baselines and validation to a documented outcome.
- Positive, benign and no-data outcomes are all legitimate, and a single case can have parts with different outcomes.
- Provenance matters: keep saved-record facts, synthetic fixtures and enrichment clearly labeled and separate.
- Defensible findings state what the records show, what they do not show, and what would change the conclusion.

The first figure is the Part A evidence timeline for 2026-11-03 UTC, laid out as a table so that time, source, entity and claim type sit side by side. Each row is one saved-record fact. The final column labels what kind of claim the row is, and the row colors follow the threads: blue for the WS-104 proxy and endpoint thread, violet for the VPN thread, and red for the link row.

Read the table in time order and two parallel threads appear. The WS-104 rows run from 06:12:00 to 08:12:00 and share one entity, WS-104, so the sequence among them has a real basis in a shared host. The VPN rows run up to 06:46:00 and share another entity, the address 203.0.113.66. The entity column is the key to the figure: the threads never share a value in it. That is why the final red row, for the link between gopal and WS-104, is labeled unsupported. It is not an observation; it is a question the records cannot answer.

The claim-type column reinforces the provenance rule. Every row except the last is a saved-record observation summary, not an executed result and not a cited record. The saved endpoint row is at 06:14:00Z, which places it 120 seconds after the proxy request.

As an example of using the timeline, a learner drafting the Case 1 finding can read the blue rows straight across to write labeled OBSERVED lines, while the absence of any shared entity between blue and violet rows becomes the evidence for the Case 4 no-data outcome. A reviewer can check the report against the table row by row.
