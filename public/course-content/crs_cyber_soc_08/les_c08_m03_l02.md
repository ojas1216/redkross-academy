## Introduction and conceptual foundation

The previous lesson followed an event through the SIEM's ingestion layer until it was stored and searchable. Stored is not the same as useful. A raw firewall line such as `DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389` is perfectly searchable as text, yet a detection rule cannot ask "which source addresses were dropped more than fifty times?" until something has recognised that `203.0.113.66` is a source address and `3389` is a destination port. That something is the **parser**.

**Parsing** is the extraction of structured fields from a raw event: deciding which parts of the record mean what, pulling them out, converting them to the right types and attaching them to the event as named fields. It sits between ingestion, which decides what an event is and where it goes, and normalisation (Lesson 3), which decides what the extracted fields should be called so that every source speaks the same vocabulary. The three are often performed by one component in one pass, but they answer different questions, and separating them makes failures easier to diagnose. If a search for `source.ip` misses events, you need to know whether the address was never extracted (a parsing problem) or was extracted under another name (a normalisation problem).

Module 2 Lesson 5 used the lab kit's `normalise_demo.py` to show *what* a parser produces: two raw records mapped to common field names. This lesson treats the parser as a piece of software that will run against millions of records it has never seen. It asks how parsers are selected, which extraction techniques suit which formats, what happens when a record does not match, and how to build and test parsers that fail loudly and safely. In the worked example you will feed the kit's firewall parser variant lines in a copy of the kit, watch three of five fail, and then build a more tolerant parser that tags its failures instead of crashing.

> [!IMPORTANT]
> A parse failure is a detection failure that produces no error in the SOC queue. A rule keyed on a field that was never extracted does not fire, and does not complain. Every parser therefore needs a failure counter that somebody watches.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Parser | Code or configuration that extracts named, typed fields from a raw event. Wazuh calls its parsers decoders; Elastic builds them from ingest-pipeline processors; Splunk from field extractions. |
| Field extraction | Taking one value out of the raw record and storing it under a field name. |
| Regular expression (regex) | A pattern language for matching text; capture groups mark the parts to extract. |
| Named capture group | A regex group labelled with the field it fills, such as `(?P<src_ip>\S+)` in Python syntax. |
| Grok | A pattern library used by Logstash and Elasticsearch that names reusable regexes (for example for IP addresses and timestamps) so parsers can be composed from them. |
| Dissect | Delimiter-based extraction that splits text on fixed separators without regular expressions; faster but only for records with a fixed layout. |
| Key-value (KV) parsing | Splitting `key=value` tokens into fields, independent of their order. |
| Structured format | A format that carries its own field structure, such as JSON or XML; parsing means decoding, not pattern matching. |
| CEF | Common Event Format: a pipe-delimited header of vendor, product, version, signature ID, name and severity, followed by a key-value extension. |
| Parse failure | A record the parser could not interpret; it should be tagged and kept, not dropped. |
| Parse warning | A record parsed only partly, for example with a required field missing. |
| Golden sample | A real raw record, with its expected parsed output, kept as a regression test for the parser. |

## Raw formats and how each is parsed

Raw telemetry arrives in a handful of families. Each suggests an extraction technique and each has a characteristic trap.

| Format family | What it looks like | Technique | Characteristic trap |
| --- | --- | --- | --- |
| Free-text syslog | Header (time, host, program) then a message written for humans | Regex or grok on the header, then on the message | Message wording changes between versions |
| Key-value | `SRC=203.0.113.66 DST=10.40.0.5 DPT=3389` | Split on spaces and `=` | Values containing spaces or `=`; keys that appear only sometimes |
| Delimited (CSV, TSV, pipes) | `2026-11-03 12:20:05,WS-104,divya,...` | Split on the delimiter, respecting quoting | Column added or removed; delimiter inside a quoted value |
| JSON | `{"user":"gopal","result":"SUCCESS"}` | Decode with a JSON library | Nested objects, arrays, types that change between records |
| XML | Windows events rendered as XML | Decode with an XML parser, then select elements | Namespaces; data held as unnamed elements |
| CEF / LEEF | Pipe-delimited header plus key-value extension | Split header, then KV-parse the extension | Escaped pipes and equals signs; vendor-specific custom keys |

Two observations follow from the table. First, **structured formats remove pattern matching but not interpretation**. A JSON record from a VPN gateway decodes in one call, but someone still has to know that `result` holds the outcome and that its values are upper-case. Second, **text formats are parsed by position or by label**. A positional parser ("the fourth word is the host") breaks when anything is inserted before the value it wants. A label-based parser ("the value after `SRC=`") survives reordering and insertion. The worked example demonstrates the difference with real output.

## Extraction techniques

### Regular expressions

Regular expressions are the general tool. A regex parser describes the whole shape of the record and marks the pieces to capture. Three properties of regexes matter in practice.

**Anchoring.** A pattern anchored at the start (`^`) and, where possible, at the end (`$`) of the record either matches the whole line or nothing. An unanchored pattern may match part of a line that only resembles the expected format, producing plausible but wrong fields.

**Greediness.** A greedy quantifier such as `.*` consumes as much text as it can and then gives back only what the rest of the pattern needs. In a pattern like `.*SRC=(\S+)`, the greedy `.*` means that if `SRC=` appeared twice, the parser would capture the *last* occurrence. That is a correctness question whenever any part of the line can be influenced by someone other than the device, which the security section returns to.

**Performance.** Patterns with nested or overlapping quantifiers can take exponential time on certain inputs, a problem known as catastrophic backtracking. On a SIEM processing thousands of events per second, one pathological pattern meeting one unusual record can stall a parsing worker. Prefer specific character classes (`\S+`, `\d{1,5}`, `[^\]]*`) to `.*` wherever the format allows.

### Grok and dissect

Writing raw regexes for every source is slow and error-prone, so SIEM platforms provide higher-level tools. **Grok** gives names to well-tested sub-patterns (an IPv4 address, a syslog timestamp, a number) so that a parser reads as a sequence of named pieces rather than a wall of punctuation; Logstash and Elasticsearch ingest pipelines both offer it. **Dissect** skips regex entirely and splits a record on literal delimiters in a declared order. It is faster and easier to read, but it only works when the layout never varies. A common design uses dissect for a fixed header and then a KV or regex step for the variable message.

### Key-value, delimited and structured decoding

**KV parsing** tokenises the message and splits each token on the first `=`. Because it looks up values by key, it does not care about order and tolerates new keys. Its weakness is values that contain the separator: a URL with query parameters, or a message field with spaces, must be quoted by the source and handled by the parser. **Delimited parsing** must use a real CSV reader that understands quoting, never a naive split on commas. **JSON and XML** should always be decoded with a proper library; string-matching inside JSON breaks on whitespace, key order and escaping.

### Type conversion and validation

Extraction produces strings. A parser then converts them: ports and byte counts to integers, addresses to an IP type the SIEM can range-match, timestamps to a UTC time value using the rules from Module 2 Lesson 6. Conversion is also the first **validation**: a port of `99999` or a timestamp in 1970 indicates a parsing or source fault. A parser should also check that the fields detection depends on are present and record a **warning** when they are not, rather than silently storing an event with an empty `user`.

## The parser as a decision pipeline

Inside the SIEM, parsing is not one step but a short sequence of decisions applied to every event. The ingestion layer has already labelled the event with a source type, and that label selects the parser. The parser checks whether the record has the expected overall shape, extracts and converts fields, validates the result, and stores it. The important design choice is what happens on each "no" branch: a well-built parser never discards the event, it labels the problem and keeps the original.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows the decisions a parser takes for every single event and, above all, where events go when parsing does not succeed. It is the design that turns invisible parse failures into a number on a health dashboard.

**Components.** The top node, **Raw event + source type** (slate), is what ingestion hands over. **Select parser** (violet) chooses the parser registered for that source type. **Header matches?** (violet, a decision) tests whether the record has the expected overall shape. **Extract + convert** (blue) pulls out fields and converts types and time. **Required fields present?** (violet, a decision) checks the fields that rules depend on. Three outcome nodes follow: **Parsed event + raw** (green), **Partial: _parse_warning** (orange) and **Unparsed: _parse_failure** (red), each of which keeps the original record. All outcomes lead to **Stored and counted** (dark), and a dashed arrow from the failure node to **Parser health dashboard** (orange) shows the monitoring path.

**Relationships and arrows.** Solid arrows follow the event. The labelled arrows leaving the two decision nodes are the branches: **yes** and **no** from *Header matches?*, **all** and **some missing** from *Required fields present?*. The dashed arrow from the failure outcome to the dashboard is a measurement flow, not an event flow: the failure is counted, and the event itself is still stored.

**Execution flow.** An event enters, a parser is selected, its header is tested, fields are extracted and converted, required fields are checked, and the event is stored with one of three outcomes. Every path ends in storage; none ends in deletion.

**Decision logic.** A header mismatch means the parser does not understand the record at all: the event is tagged `_parse_failure` and stored with only its original text. A missing required field means the record was understood but is incomplete: it is stored with the fields that were found and tagged `_parse_warning`. Only a record that passes both tests is a clean parsed event.

**Technical interpretation.** The tags are what make failure searchable. A query for events tagged `_parse_failure`, grouped by source type and hour, is the parser health metric. A sudden rise after a vendor upgrade identifies exactly which source broke and when.

**Practical example.** In the worked example below, the line `fw01: link eth0 down` fails the header test and is stored with `_parse_failure` and its original text, while an ICMP drop with no destination port passes both tests, because a port is not required for ICMP, and is stored without a port field.

**Security implications.** Dropping unparsable events would give an adversary a way to hide: any record malformed enough to fail parsing would vanish. Keeping and counting them preserves the evidence and exposes the attempt.

**Key learning.** Every branch of a parser must end in storage with a label. Parse outcomes are a health signal, and unparsed events are evidence.

### Step 1: what the demo parser assumes

The demo's firewall parser, `from_syslog`, is built around one regular expression:

```python
m = re.match(r"(\w{3})\s+(\d+) (\d\d:\d\d:\d\d) (\S+) kernel: (\w+) .*SRC=(\S+) DST=(\S+) PROTO=(\w+) DPT=(\d+)", line)
```

Module 2 explained what each group captures. Read it now as a list of **assumptions** about every future record: the word after `kernel: ` is the action and consists only of word characters; `SRC`, `DST`, `PROTO` and `DPT` all appear; and they appear in exactly that order. The pattern is also positional in a subtle way: `PROTO=(\w+) DPT=` requires the port to follow the protocol immediately. And the code that follows uses `m[1]`, `m[2]` and so on without checking whether `m` is `None`, which is what `re.match` returns when the pattern does not match.

### Step 2: a test harness

The harness below (`parse_harness.py`, written for this lesson, not part of the kit) imports the demo's parser and feeds it five firewall lines: the original record and four realistic variants a real Linux firewall or a firmware update could produce.

```python
"""Feed variant raw lines to normalise_demo.from_syslog and count failures."""
import json
from normalise_demo import from_syslog

SAMPLES = [
    ("original", "Nov  3 12:16:21 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389"),
    ("two-digit day", "Nov 13 09:02:11 fw01 kernel: DROP IN=eth0 SRC=198.51.100.7 DST=10.40.0.5 PROTO=TCP DPT=22"),
    ("ICMP, no port", "Nov  3 12:17:40 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=ICMP TYPE=8 CODE=0"),
    ("keys reordered", "Nov  3 12:18:02 fw01 kernel: DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 DPT=445 PROTO=TCP"),
    ("new prefix", "Nov  3 12:19:15 fw01 kernel: [FW-IN] DROP IN=eth0 SRC=203.0.113.66 DST=10.40.0.5 PROTO=TCP DPT=3389"),
]

failures = 0
for name, line in SAMPLES:
    try:
        e = from_syslog(line)
        print(f"OK    {name}: {e['event.action']} {e['source.ip']} -> {e['destination.ip']}:{e['destination.port']} at {e['@timestamp']}")
    except Exception as exc:
        failures += 1
        print(f"FAIL  {name}: {type(exc).__name__}: {exc}")
print(f"parsed {len(SAMPLES) - failures} of {len(SAMPLES)}; parse failures: {failures}")
```

The `try`/`except` around each call is the harness's whole purpose: it turns a crash into a counted failure, which is exactly what the demo parser lacks. Run it:

### Step 3: interpreting the failures

Only two of five lines parsed. Each failure teaches something different.

- **Two-digit day: OK.** `\s+` after the month absorbs both `Nov  3` and `Nov 13`, and `(\d+)` accepts either length. `09:02:11` IST became `03:32:11Z`, correct for a +05:30 offset.
- **ICMP, no port: FAIL.** ICMP has no ports, so the firewall writes `TYPE` and `CODE` instead of `DPT`. The pattern demands `DPT=` and therefore rejects every ICMP drop. A rule looking for ping sweeps against internal hosts would see nothing.
- **Keys reordered: FAIL.** The same information as a normal TCP drop, with `DPT` before `PROTO`. The positional pattern rejects it. Here the dropped event is an attempt on port 445 (SMB) from the same external address, exactly what an analyst would want to correlate.
- **New prefix: FAIL.** Linux firewall rules can be configured to add a log prefix such as `[FW-IN]`; an administrator adding one is a routine change. `(\w+)` cannot match `[FW-IN]`, so every event from the modified rule is lost to the parser.

The error message is the same in all three cases, `'NoneType' object is not subscriptable`, because the parser does not check for a failed match. In a real pipeline that would be an unhandled exception per event, and depending on the platform either a dropped event or a stalled worker. The message also says nothing about *which* assumption failed, which makes diagnosis slow.

### Step 4: a more tolerant parser

The second script (`parse_kv.py`, also written for this lesson) applies the design from the figure. It uses a regex only for the fixed header, parses the rest as key-value tokens, and returns a tagged event rather than raising an exception.

```python
IST = timezone(timedelta(hours=5, minutes=30))
HEADER = re.compile(r"^(\w{3})\s+(\d{1,2}) (\d\d:\d\d:\d\d) (\S+) kernel: (?:\[[^\]]*\] )?([A-Z]+) (.*)$")

def parse_fw(line, year=2026):
    m = HEADER.match(line)
    if not m:
        return {"event.original": line, "tags": ["_parse_failure"], "error.message": "header did not match"}
    kv = dict(tok.split("=", 1) for tok in m[6].split() if "=" in tok)
    e = {"@timestamp": to_utc(f"{year} {m[1]} {m[2]} {m[3]}", "%Y %b %d %H:%M:%S"),
         "event.module": "firewall", "event.action": m[5].lower(), "host.name": m[4],
         "source.ip": kv.get("SRC"), "destination.ip": kv.get("DST"),
         "network.transport": kv.get("PROTO", "").lower() or None, "event.original": line}
    if "DPT" in kv:
        e["destination.port"] = int(kv["DPT"])
    if not e["source.ip"]:
        e["tags"] = ["_parse_warning"]
    return e
```

The header pattern is anchored with `^` and `$`, limits the day to one or two digits, accepts an optional bracketed prefix with `(?:\[[^\]]*\] )?` (a non-capturing group whose `[^\]]*` cannot run past the closing bracket), and captures the rest of the line in group 6. `split("=", 1)` splits each token on its **first** equals sign only, and the `if "=" in tok` filter skips tokens without one. Fields are looked up by key with `kv.get`, so order no longer matters and an absent key yields `None` instead of a crash. The port is added only when present, and `source.ip`, the field this source's detections depend on, is checked. The helper `to_utc` (not shown) performs the same IST-to-UTC conversion as the demo, and the script keeps `event.original` on every event.

The same script includes a CSV parser for a DNS log line, the third format suggested in the course's practical: `2026-11-03 12:20:05,WS-104,divya,DNS,QUERY,cdn-telemetry-sync.example`, with the time in IST.

```python
def parse_dns_csv(line):
    row = next(csv.reader([line]))
    if len(row) != 6:
        return {"event.original": line, "tags": ["_parse_failure"], "error.message": f"expected 6 columns, got {len(row)}"}
    ts, host, user, _proto, action, qname = row
    return {"@timestamp": to_utc(ts, "%Y-%m-%d %H:%M:%S"), "host.name": host, "user.name": user,
            "event.action": action.lower(), "dns.question.name": qname, "event.original": line}
```

`csv.reader` handles quoting correctly, and the column count is checked before the values are unpacked. The script parses the four lines that defeated or tested the demo parser, a non-firewall kernel message (`fw01: link eth0 down`) and two DNS lines, one of them missing its final column. To keep the output short, it prints `event.original` only on events that failed.

All four firewall drops now parse. The ICMP drop has no `destination.port`, which is correct; inventing a port of 0 would be wrong. **Purpose.** The figure contrasts two parsers for the same firewall source. It makes visible why one design lost three of five events and the other lost none of the firewall drops.

**Components.** The left panel, **Brittle: one positional regex** (red), condenses the kit demo's approach: one pattern that names every key in a fixed order, the unchecked `m[1]` access, and the harness results for the three failing variants. The right panel, **Tolerant: header regex + key-value** (green), condenses `parse_kv.py`: an anchored header pattern with an optional prefix, key-value lookup, an explicit failure return and the observed results. Highlighted text marks the parts that decide the outcome: the fixed `PROTO=(\w+) DPT=(\d+)` order and the `TypeError` on the left; `kv.get` and the `_parse_failure` tag on the right.

**Relationships.** Read the panels line by line against each other. Where the brittle parser encodes field order in the pattern, the tolerant parser looks fields up by key. Where the brittle parser assumes a match, the tolerant parser tests for one and returns a tagged event. Where the brittle parser requires every key, the tolerant parser adds optional fields only when present and warns when a required one is missing.

**Execution flow.** For each line, the left parser either matches completely or throws an exception that, in a pipeline, would drop the event or stall the worker. The right parser first tests the header; if that fails it stores a tagged event, and if it passes it extracts whatever keys exist.

**Decision logic.** The tolerant design moves the parser's decisions from "does the whole line match my picture of it?" to two smaller questions: "is this the right kind of record?" (header) and "which of the fields I care about does it contain?" (keys).

**Technical interpretation.** Tolerance has limits. A key-value parser still assumes values contain no spaces, and the header pattern still assumes the `kernel:` program name. A tolerant parser is not one that accepts anything; it is one whose assumptions are fewer, explicit and checked.

**Practical example.** When Banyan's network team adds the `[FW-IN]` prefix to one firewall rule, the left parser loses every event from that rule without any visible error; the right parser carries on, and the change shows up only as an unchanged event count.

**Security implications.** Silent loss of ICMP and SMB drops would hide reconnaissance and lateral-movement attempts. Tagged failures, by contrast, make an unexpected format visible on the health dashboard within an hour.

**Key learning.** Parse by label rather than position, check every match, and return a tagged event instead of crashing.

## Testing and maintaining parsers

The harness in the worked example is the seed of proper parser testing. A parser is code, and it deserves the same discipline as detection rules.

1. **Collect golden samples.** For each source type, keep real raw records covering every event type, the longest and oddest records, and records from each firmware or software version in use, each paired with its expected parsed output.
2. **Run them on every change.** Any edit to a parser, and any platform upgrade, runs the full sample set; a difference from the expected output blocks the change.
3. **Add every failure as a new sample.** When a `_parse_failure` appears in production, the record joins the golden set once the parser is fixed, so the same format can never break silently again.
4. **Treat vendor upgrades as parser changes.** Before a firewall, VPN or EDR upgrade, obtain sample logs from the new version and run them through the parser in a test environment.
5. **Re-parse after fixes.** Because the raw event was kept, events stored during the faulty period can be re-parsed or re-ingested, and the gap reviewed for missed detections.

The course's fictional case study shows the cost of skipping these steps. A vendor changed its VPN log format; the SIEM parser stopped extracting user names; brute-force rules keyed on `user.name` stopped firing for a month. A parse-failure or field-completeness panel would have shown the change on the first day.

## Common mistakes and misconceptions

- **Writing the parser from one sample.** One line shows one variant. Collect samples of every event type and version first.
- **Positional patterns for labelled data.** If the source labels its fields, use the labels; position breaks on the first insertion.
- **Unanchored, greedy patterns.** `.*` matches more than you think and can capture the wrong occurrence of a key.
- **No failure path.** A parser that throws, or returns nothing, on an unexpected record turns format drift into silent loss.
- **Dropping unparsed events.** Keep them with the original text and a tag; they are evidence and the raw material for fixing the parser.
- **Splitting CSV or JSON by hand.** Quoting and escaping defeat naive splitting; use real decoders.
- **Inventing values.** A missing port is absent, not zero; an unknown user is null, not "unknown". Invented values create false matches.
- **Confusing parsing with normalisation.** Extracting a field and naming it consistently are separate checks; diagnose which one failed.

## Security implications, detection and defence

Parsers read data that adversaries can sometimes influence, such as user names, URLs, user-agent strings, email subjects and file names, and so a parser is an attack surface.

- **Log injection.** If an attacker can place text such as `SRC=198.51.100.9` or a newline inside a field the source logs, a careless parser may extract a forged value or split one event into two. This weakness class is catalogued as CWE-117 (Improper Output Neutralization for Logs). Defences: prefer structured formats from sources, parse with anchored patterns, extract attacker-influenced fields last and by explicit delimiters, and never let a value from inside a free-text field overwrite a field from the header.
- **Regular-expression denial of service.** A pattern prone to catastrophic backtracking can be driven to consume excessive CPU by a crafted value (CWE-1333, Inefficient Regular Expression Complexity). Defences: specific character classes, anchoring, platform timeouts on parsing, and testing parsers with very long inputs.
- **Deliberate parse evasion.** An intruder who knows a rule keys on a parsed field may try to make their events fail parsing. Because failures are kept and counted, a burst of `_parse_failure` events from one host is itself worth investigating.
- **Never execute log content.** Parsers must treat every byte as data. Evaluating extracted values as code or templates turns a log line into an attack.
- **Protect parser configuration.** Changing a parser can blind a rule as effectively as stopping an agent; parsers belong under the same change control and review as detections.

## Best practices

- Select the parser by explicit source type, and keep one parser per source type and version.
- Anchor patterns, parse labelled data by key, and use real JSON, XML and CSV decoders.
- Give every parser a failure path that tags and keeps the event with its original text.
- Validate types and required fields, warning on partial parses rather than inventing values.
- Monitor parse failures and field completeness per source type per hour.
- Maintain golden samples and run them on every parser change and vendor upgrade.

## Key takeaways

- Parsing extracts named, typed fields from raw events; ingestion decides which parser runs, and normalisation (Lesson 3) decides what the fields are called.
- Each format family suggests a technique: regex or grok for free text, key-value for labelled tokens, a CSV reader for delimited data, real decoders for JSON and XML.
- In the kit test, the demo's positional regex parsed only 2 of 5 realistic firewall lines; a header regex plus key-value lookup parsed all four drops and tagged the genuine failures.
- Every parser branch must end in storage: clean, `_parse_warning` or `_parse_failure`, always with the original record kept.
- Parse failures are silent detection failures; monitor them per source type, test parsers with golden samples, and treat vendor upgrades as parser changes.
- Parsers face hostile input: guard against log injection and catastrophic backtracking, and never execute log content.
