## Introduction and lab objective

This lab closes the detection-engineering module by taking one detection through the whole lifecycle on the course dataset: requirement, research, design, implementation, testing, review and integration with triage. You will write a new correlation rule for the Banyan Microfinance storyline, prove it with positive and negative tests, run it against the full dataset, and put it through the review checklist from the previous lesson. Every output shown here was produced by running the commands on a private copy of the course kit with CPython 3.14.4; where a step failed, the failure is shown, because finding and fixing the failure is part of the lesson.

The detection gap comes from the coverage analysis earlier in this module. The storyline begins with a finance user, divya, downloading a macro-enabled document from a look-alike domain, after which Word starts PowerShell on her workstation WS-104. The existing rule R1 (`office_spawns_script`) catches the second event on its own. Nothing catches the *chain*: a macro-enabled document arriving from the web and, within minutes on the same host, an Office application starting a shell. That chain is stronger evidence than either event alone. A macro document download is common in some business units and weak on its own; Word starting PowerShell can occasionally be a legitimate macro. Together, close in time on one host, they describe the initial-access and execution steps of a malicious-document attack with much higher confidence.

**Objective.** Build, test and integrate rule R7 `macro_doc_then_shell`: a proxy event for a `.docm` or `.xlsm` URL followed within 10 minutes, on the same host, by Word or Excel starting `powershell.exe` or `cmd.exe`.

**Outcomes.** By the end you will have a rule in minisiem, seven new unit tests, a passing test run of 14 tests, one alert on the dataset, a triage entry, a Sigma version that passes `sigma check`, and a short review record.

## Step 3: design the rule

Write the requirement down before writing code. A one-paragraph requirement keeps the rule honest during review:

> R7 must alert when a host fetches a URL ending in `.docm` or `.xlsm` and, between 0 and 600 seconds later, the same host records a process creation in which the parent image is Word or Excel and the image is PowerShell or cmd.exe. It must not alert on other document types, on a shell started by another parent, on a spawn on a different host, on a spawn before the download, or on a spawn more than 600 seconds later.

Each clause becomes a condition and each "must not" becomes a negative test. The design choices deserve explicit reasons, because a reviewer will ask about each:

- **Why correlate rather than tune R1?** R1 should keep firing on its own, because a malicious document can arrive by email or USB with no proxy event. R7 is an additional, higher-confidence signal for the web-delivered case, not a replacement.
- **Why 10 minutes?** In the storyline the spawn follows two minutes after the download. Users usually open a downloaded document within minutes; a longer window catches slower users but raises the chance of joining unrelated events. Ten minutes is a starting value to be revisited with production data during tuning, and the boundary will be tested exactly.
- **Why match on path endings?** `\winword.exe` with the backslash prevents a match on a different binary whose name merely ends in the same letters; lowering both sides makes the match case-insensitive like Windows itself.
- **Why include Excel and cmd.exe?** The `.xlsm` workbook is the Excel equivalent of `.docm`, and cmd.exe is the other common interpreter a macro starts. Each addition needs its own positive test.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The diagram shows how R7 turns two weak signals from two different log sources into one stronger alert. It is the design the code in the next step implements, and the picture a reviewer should hold in mind when reading the SQL.

**Components.** Across the top row are the two inputs. The blue node, **Proxy event**, is a web request whose URL ends in `.docm` or `.xlsm`. The slate node, **Sysmon event 1**, is a process creation in which Word or Excel is the parent and PowerShell or cmd.exe is the child. Below them, the violet node **Join on host** represents the correlation condition that both events come from the same workstation. Under it, the violet node **0 to 600 s after download** represents the time window, measured in whole seconds. In the bottom part, the dark node **R7 alert** is the result, beside the red **No alert** node, and the green node **Triage queue** beneath it shows where the alert goes, with its `RULE_META` entry.

**Relationships and arrows.** Both input nodes point into **Join on host**: neither alone produces an alert. The join points into the window check, and the window check points to **R7 alert** only when the spawn happened between 0 and 600 seconds after the download. A dashed arrow from the window check to the red **No alert** node shows the outcome for every pair that fails: a spawn on another host, a spawn before the download, or a spawn more than 600 seconds later. From **R7 alert** the arrow continues to **Triage queue**.

**Execution flow.** When the rule runs, the SIEM pairs every qualifying proxy event with every qualifying Sysmon event on the same host, then keeps only the pairs inside the window. Each surviving pair is one hit, carrying the host, user, URL, both timestamps and the child image, which is exactly what an analyst needs to start triage.

**Decision logic.** There are three decisions in sequence: is the event qualifying (URL ending, parent and child images), is the host the same, and is the gap inside the window. Each corresponds to one or more negative tests in Step 5.

**Technical interpretation.** In minisiem this is a self-join of the `events` table, aliased `d` for the download and `p` for the process. The time gap is computed from the two `ts` strings. In a production SIEM the same design is expressed as a correlation search or, in Sigma, as a temporal correlation over two base rules.

**Practical example.** In the Banyan data, WS-104 fetched `invoice.docm` at 06:12:00 and Word started PowerShell at 06:14:00, a gap of 120 seconds, so the pair passes every check and produces one alert.

**Security implications.** The join on host is only as good as the host field. If the proxy recorded only an IP address and DHCP reassigned it, the join would fail silently; a reviewer must confirm the field's meaning in both sources.

**Key learning.** Correlation raises confidence by requiring two independent observations to agree on host and time; each agreement condition must be tested.

## Step 4: implement R7 in your copy of minisiem.py

Add one entry to the `RULES` dictionary in your copy of `minisiem.py`, after R6. The first version, as originally written for this lab, measured the window in minutes with SQLite's `julianday()` function:

```python
    "R7 macro_doc_then_shell": r"""
        SELECT d.host, d.user, d.url, d.ts AS download_ts, p.ts AS spawn_ts, p.image
        FROM events d JOIN events p ON p.host = d.host
        WHERE d.source='proxy'
          AND (lower(d.url) LIKE '%.docm' OR lower(d.url) LIKE '%.xlsm')
          AND p.source='sysmon' AND p.event_id=1
          AND (lower(p.parent_image) LIKE '%\winword.exe'
               OR lower(p.parent_image) LIKE '%\excel.exe')
          AND (lower(p.image) LIKE '%\powershell.exe'
               OR lower(p.image) LIKE '%\cmd.exe')
          AND p.ts >= d.ts
          AND (julianday(p.ts) - julianday(d.ts)) * 1440 <= 10""",
```

Line by line: the `r"""` prefix makes this a Python *raw* string, so the backslashes in `'%\winword.exe'` reach SQLite unchanged. (The kit's other rules avoid backslashes; in a normal string `\w` is an invalid escape that recent Python versions warn about.) `FROM events d JOIN events p ON p.host = d.host` joins the table to itself, pairing every event with every other event on the same host; `d` plays the download, `p` the process. The `d.` conditions select proxy events whose lowered URL ends in `.docm` or `.xlsm` (in SQLite `LIKE`, `%` matches any run of characters and the backslash has no special meaning). The `p.` conditions select Sysmon event 1 with a Word or Excel parent and a PowerShell or cmd.exe child. `p.ts >= d.ts` orders the two events, and the last line converts the difference in Julian days to minutes (1,440 per day) and keeps gaps of at most 10. The `SELECT` list returns what the analyst needs.

## Step 5: write positive and negative tests

Append a test class to your copy of `test_rules.py`, above the `if __name__ == "__main__":` line. It reuses the file's `run()` helper and its `WORD` and `PS` path constants:

```python
class R7(unittest.TestCase):
    rule = "R7 macro_doc_then_shell"
    DOC = "https://files.example/invoice.docm"

    def chain(self, url=DOC, child=PS, parent=WORD, spawn_host="WS-1",
              spawn_ts="2026-11-03T06:14:00Z"):
        return [dict(source="proxy", host="WS-1", url=url, ts="2026-11-03T06:12:00Z"),
                dict(source="sysmon", event_id=1, host=spawn_host, parent_image=parent,
                     image=child, ts=spawn_ts)]

    def test_docm_then_word_spawns_powershell(self):
        self.assertEqual(len(run(self.rule, self.chain())), 1)

    def test_uppercase_url_and_cmd_child(self):
        ev = self.chain(url="https://files.example/INVOICE.DOCM",
                        child=r"C:\Windows\System32\cmd.exe")
        self.assertEqual(len(run(self.rule, ev)), 1)

    def test_spawn_on_other_host_not_matched(self):
        self.assertEqual(run(self.rule, self.chain(spawn_host="WS-2")), [])

    def test_spawn_at_exactly_ten_minutes_matched(self):
        self.assertEqual(len(run(self.rule, self.chain(spawn_ts="2026-11-03T06:22:00Z"))), 1)

    def test_spawn_after_window_not_matched(self):
        self.assertEqual(run(self.rule, self.chain(spawn_ts="2026-11-03T06:23:00Z")), [])

    def test_spawn_before_download_not_matched(self):
        self.assertEqual(run(self.rule, self.chain(spawn_ts="2026-11-03T06:11:00Z")), [])

    def test_plain_docx_not_matched(self):
        self.assertEqual(run(self.rule, self.chain(url="https://files.example/notes.docx")), [])
```

The `chain()` helper builds the smallest event pair that should match: a download at 06:12:00 on WS-1 and a Word-to-PowerShell spawn two minutes later. Each test changes exactly one thing, so a failure points at exactly one condition. Two tests are positives: the basic chain, and a variant with an upper-case URL and a cmd.exe child, covering the case-insensitivity and the second child branch. One test is a **boundary positive**: a spawn at exactly 600 seconds must still match, because the requirement says "between 0 and 600 seconds". Four tests are near-miss negatives, one per "must not" clause: another host, 660 seconds later, one minute *before* the download, and an ordinary `.docx`. (A further negative for a non-Office parent is already covered in spirit by R1's Explorer test; adding it here is a good exercise.)

Thirteen tests pass, including every negative, and the boundary test fails: a spawn exactly ten minutes after the download produced zero hits instead of one. The logic *looks* right, since `<= 10` includes 10, so check what SQLite actually computes for that gap:

```terminal
$ python -c "import sqlite3;c=sqlite3.connect(':memory:');print(c.execute(\"select (julianday('2026-11-03T06:22:00Z')-julianday('2026-11-03T06:12:00Z'))*1440\").fetchone())"
(10.000000074505806,)
```

`julianday()` returns a floating-point day number. Ten minutes is 1/144 of a day, which has no exact binary representation, so the difference multiplied by 1,440 comes out a hair above 10, and `<= 10` is false. This is a classic boundary bug: invisible in the dataset (where the gap is two minutes), invisible to every test except the one written exactly at the edge, and capable in production of silently dropping real chains that land on the boundary. It is the reason boundary tests exist.

The fix is to do the arithmetic in whole seconds. SQLite's `strftime('%s', ts)` returns the Unix time of a timestamp as text; casting to `INTEGER` gives an exact count of seconds. The ordering and window conditions collapse into one exact range check, shown against the original in the next figure.

![Figure 7.16: R7 time window: floating-point bug versus integer fix](/assets/courses/cyber-08/v2/C08-M07-L08-F2.svg)

*Figure 7.16: R7 time window: floating-point bug versus integer fix. The first version of R7's window dropped a spawn at exactly ten minutes; computing the gap in integer seconds fixed it.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure compares the first and the fixed version of R7's time-window condition. It exists because the defect is a single line that reads correctly, and only a side-by-side view with the computed value makes the problem obvious.

**Components.** There are two code panels. The red panel on the left, **Buggy: float minutes**, holds the original two lines, `AND p.ts >= d.ts` and the `julianday(...) * 1440 <= 10` comparison, followed by the value SQLite computed for a ten-minute gap, `10.000000074505806`, and the consequence: the comparison is false, so the boundary chain is dropped. The green panel on the right, **Fixed: integer seconds**, holds the replacement, the two `CAST(strftime('%s', ...) AS INTEGER)` terms subtracted and tested with `BETWEEN 0 AND 600`, followed by the computed value for the same gap, `600`, and the consequence: the boundary chain is kept. The highlighted fragments are the float result in the red panel and the `BETWEEN 0 AND 600` range in the green one.

**Relationships.** The panels read left to right as before and after. The two conditions on the left (ordering by string comparison, window by floating point) become one integer condition on the right: the lower bound 0 enforces "not before the download" and 600 enforces "not more than ten minutes after".

**Execution flow.** For each joined pair, SQLite evaluates the condition. On the left it compares two strings, then computes a floating-point product and compares it with 10. On the right it converts both timestamps to integer Unix seconds, subtracts, and checks the inclusive range.

**Decision logic.** Inclusive `BETWEEN` matches the requirement's wording exactly. A gap of 600 passes, 660 fails, and a negative gap (spawn before download) fails, which is what the boundary, after-window and before-download tests check.

**Technical interpretation.** Floating-point arithmetic is exact only for values representable in binary, and most decimal fractions of a day are not. Integer seconds are exact. A second benefit is that the fix no longer depends on comparing timestamp *strings*, which works only while every source writes the identical ISO format.

**Practical example.** After the change, the same `python -m unittest test_rules -v` run reports 14 tests OK and the Banyan chain (gap 120 seconds) still matches.

**Security implications.** Boundary bugs in thresholds and windows routinely create blind spots, for example a "five or more" rule written as "more than five". An adversary who learns a window can also pace activity to sit just outside it, so window length is a tuning decision to revisit, and both sides of every boundary must be tested.

**Key learning.** Compute time windows with exact integer arithmetic, and keep the boundary test that exposed the bug so it can never return.

## Step 10 (optional): a portable Sigma version

The minisiem SQL is the implementation the tests prove. For portability, the same design can be written in Sigma as two base rules and a correlation rule in one multi-document YAML file, `rk_macro_doc_then_shell.yml` in your folder. The correlation part reads:

```yaml
title: Macro Document Download Followed by Office Shell on Same Host
id: 20a1fab6-6fea-41b4-ae22-f1893d0464b5
status: experimental
correlation:
  type: temporal_ordered
  rules:
    - rk_macro_doc_download
    - rk_office_shell_child
```

## Troubleshooting

- **`SyntaxWarning: "\w" is an invalid escape sequence`** on import: the R7 string lost its `r` prefix. Restore `r"""`.
- **R7 shows 0 hits:** you skipped `python minisiem.py load`, or a backslash is missing from the `LIKE` patterns. Debug clause by clause with `search`.
- **`KeyError: 'R7'` from `triage.py`:** add the `RULE_META` entry (Step 9).
- **Tests still pass after a mutation:** no negative test isolates the clause you weakened; add one.

## Key takeaways

- Correlating a macro-document download with an Office-spawned shell on the same host within 600 seconds raised confidence over R1 alone and produced one hit on the Banyan dataset.
- Write the requirement first: each "must" becomes a positive test, each "must not" a near-miss negative, and each boundary a test of its own.
- The boundary test exposed a real floating-point bug (`10.000000074505806` is not `<= 10`); integer seconds fixed it.
- Prove the tests can fail by mutating the rule, and integrate with triage, where a missing `RULE_META` entry crashed the whole queue.
