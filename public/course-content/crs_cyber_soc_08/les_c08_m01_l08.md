## Introduction and conceptual foundation

Ask a new analyst what tools a SOC uses and you will usually get a list of product names. The list is not wrong, but it misses the point. A SOC's capability does not come from any single tool; it comes from the **connections between them**. A SIEM with no endpoint logs cannot see a malicious process. An EDR alert that never reaches the case system is never worked. A SOAR playbook that enriches alerts with threat intelligence is useless if the intelligence platform has not been updated for months. Every gap in the chain is a place where an attack can pass unnoticed, and most real SOC failures are failures of integration rather than of detection technology.

A **SOC tooling map** is the answer to that problem. It is a documented picture of every tool the SOC depends on, what data each one receives and produces, which tool it passes that data to, who owns it, and what breaks if it stops working. Analysts use the map to understand where an alert came from and where to look next. SOC leads use it to find blind spots, duplicated spend and single points of failure. Auditors and incident reviewers use it to establish what the SOC could and could not have seen at a given moment.

This lesson closes Module 1 by tying together everything that came before it. The tiers and roles from Lessons 1 and 2 are the people who use the tools. The alert lifecycle from Lesson 3 is the path an alert takes across them. The analyst workflow and shift handover from Lessons 4 and 5 depend on the case management system as the single source of truth. The SLAs and metrics from Lessons 6 and 7 are calculated from the timestamps the tools record. The lesson describes each major tool category, draws the map that connects them, follows one alert across it, and then maps the categories onto the course lab kit you will use for the rest of the course.

> [!NOTE]
> Product names in this lesson are examples of well-known tools in each category, not recommendations. Categories are stable; products, licences and feature sets change every year. Learn what each category does and how it connects, and any specific product becomes easy to learn.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Telemetry | Machine-generated records of activity (logs, events, flows) that the SOC collects as evidence. |
| Collection pipeline | Agents, forwarders and connectors that move telemetry from sources to storage, parsing and normalising it on the way. |
| SIEM | Security information and event management: central storage, search and correlation of security telemetry, producing alerts. |
| EDR | Endpoint detection and response: an agent on each host that records detailed activity, detects threats and can take response actions such as isolating the host. |
| NDR / IDS | Network detection and response / intrusion detection system: sensors that inspect network traffic and raise detections. |
| SOAR | Security orchestration, automation and response: a platform that runs playbooks to enrich, route and act on alerts across other tools. |
| Case management | The system that holds every alert and incident as a case with owner, status, timestamps, evidence and notes. |
| TIP | Threat intelligence platform: stores indicators and context from feeds and partners, and answers lookups. |
| Sandbox | An isolated environment that runs a suspicious file or URL and reports its behaviour. |
| CMDB / asset inventory | The record of the organisation's assets, owners and criticality, used to prioritise alerts. |
| Identity provider (IdP) | The directory and authentication service (for example Active Directory or Microsoft Entra ID) that is both a telemetry source and a response point. |
| Platform health | Whether the SOC's tools are working: sources reporting, ingestion lag, parser errors, failed integrations. |

## The tool categories and what each contributes

### Telemetry sources and collection

Everything a SOC knows begins as telemetry. The main source families are **endpoint** (Windows Security events, Sysmon process and network events, Linux authentication and audit logs), **network** (firewall logs, DNS logs, proxy logs, flow records), **identity** (directory sign-ins, VPN authentication, multi-factor prompts), **cloud and SaaS** (control-plane audit logs, mailbox and file-sharing activity) and **applications** (web server and business application logs). Module 2 covers each family in detail.

Telemetry has to be moved, and the **collection pipeline** does it: endpoint agents (such as the Wazuh agent or Elastic Agent), syslog forwarders, Windows Event Forwarding and cloud API connectors. On the way, events are parsed into fields and normalised into a common schema, so that a source IP address is called the same thing whether it came from a firewall or a VPN. The pipeline is invisible when it works and catastrophic when it fails silently: a parser change that renames a field can break every detection that uses it without a single error message reaching the analysts.

### SIEM

The **SIEM** is the SOC's central nervous system. It stores normalised events for a defined retention period, lets analysts search them, and runs **correlation rules** that turn patterns of events into alerts. Well-known examples include Splunk, Microsoft Sentinel, Elastic Security and the open-source Wazuh platform. Its value is breadth: it is the only place where an endpoint event, a VPN login and a proxy upload from the same user can be seen on one timeline. Its weakness is that it can only correlate what it receives, and storing everything at full fidelity is expensive, so retention and source selection are always trade-offs. Module 3 covers ingestion, parsing, normalisation, correlation, dashboards, search and retention.

### EDR and NDR

**EDR** agents record detailed endpoint activity (process creation with command lines, file and registry changes, network connections) and run their own detection logic, often based on behaviour rather than signatures. Crucially, EDR is also a **response tool**: an authorised analyst can isolate a host from the network, terminate a process or collect files for investigation. Examples include Microsoft Defender for Endpoint and CrowdStrike Falcon.

**NDR and IDS** sensors watch traffic on the network. Open-source examples are Zeek, which produces rich protocol logs, and Suricata and Snort, which match traffic against signatures. They see what endpoints may not report: unmanaged devices, lateral movement between servers, and command-and-control traffic. Both EDR and NDR typically send their detections, and often their raw telemetry, into the SIEM so that everything can be correlated in one place.

### Case management

The **case management** system holds the record of the SOC's work. Every alert that a human must consider becomes a case with an owner, a status, a severity, timestamps for creation, acknowledgement and closure, the evidence collected, the analyst's notes and the final disposition. TheHive is a widely used open-source example; many organisations use a general ticketing platform instead. This is the system the shift handover in Lesson 5 depends on, and the source of every timestamp that the metrics in Lesson 7 are calculated from. If an escalation is not in the case system, as far as the SOC is concerned it did not happen.

### SOAR

**SOAR** connects the other tools with automated playbooks. When a case is created, a playbook can look up the source IP address in the threat intelligence platform, pull the host's owner and criticality from the CMDB, query the identity provider for the user's role, submit an attachment to a sandbox and write all the results back to the case before an analyst opens it. It can also carry out response actions through other tools' interfaces, such as asking the EDR to isolate a host or the identity provider to disable an account. Shuffle is an open-source SOAR; TheHive's companion engine Cortex runs analysers (enrichment lookups) and responders (actions). Module 11 builds playbooks with **approval gates**, so that any action that could disrupt the business requires a human decision.

### Context sources

Several tools exist mainly to answer questions during triage. The **threat intelligence platform**, such as MISP or OpenCTI, answers "is this indicator known, by whom, with what confidence, and is it still valid?" (Module 6). The **CMDB or asset inventory** answers "what is this host, who owns it and how critical is it?". The **identity provider** answers "who is this user and what can they do?". A **sandbox** answers "what does this file or URL do when it runs?" (Module 9). Vulnerability scanners answer "is this host exposed to the weakness this alert relates to?". Without context, every alert looks equally urgent; with it, Tier 1 can prioritise in seconds.

### Communication and coordination

Finally, a SOC needs channels to reach people: on-call paging for urgent escalations, a dedicated incident chat or bridge for major incidents, and an out-of-band channel for when the normal one may itself be compromised. These are tools too, and they belong on the map, because an escalation path that depends on one chat platform fails on the day that platform is unavailable.

## The SOC tooling map

The categories above are not a list but a system. The figure below shows the typical data and control flows between them. Read it as the path that evidence takes from the moment something happens on a host or network to the moment the SOC acts and learns from it.

*Figure 1.15: The SOC tooling map: how evidence flows between tools. A reference map of SOC tool categories, the data each passes to the next, and where the analyst decides.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure is a reference architecture for a SOC's tooling: which tools exist, what each one sends to the next, and where humans make decisions. It matters because every arrow is a dependency, and a broken arrow is a blind spot.

**Components.** **Telemetry sources** (slate, "endpoint, network, identity, cloud") are the systems being monitored; they are infrastructure the SOC does not own. The **Collection pipeline** ("agents, forwarders; parse + normalise") moves their events. **EDR / NDR sensors** ("own detections + response hooks") are both sources and detectors. The **SIEM** (orange, the focus) carries "store, search, correlate". **Case management** is the dark box, the trust anchor of the SOC: "one record per alert, with timestamps". **SOAR** (violet, the control plane) carries "playbooks + approval gates". **Context sources** ("TIP, CMDB, identity, sandbox") answer enrichment questions. The **Analyst** (orange) is the human decision point, "triage, investigate, decide". **Response actions** (green, the defender's outcome) read "isolate host, disable account, block". **Metrics and feedback** ("MTTA, MTTR, rule tuning") closes the loop.

**Relationships and arrows.** Solid arrows carry data or control forward. Telemetry sources feed the collection pipeline ("raw logs"), which feeds the SIEM ("normalised events"). EDR / NDR sensors feed the SIEM with "detections + telemetry". The SIEM sends "alerts" to case management. Case management triggers SOAR ("new case"); SOAR queries context sources ("lookups"), receives "context" back (a dashed reply arrow) and writes "enrichment" back to the case. The analyst "works the case" and gives an "approval" to SOAR, which then executes response actions. Response actions are carried out through the tools that can act: here the arrow labelled "via EDR / IdP / firewall" points back to the sensors. A dashed arrow from case management to metrics and feedback shows that closed cases feed measurement and tuning, which in turn improves the SIEM rules.

**Execution flow.** An event happens on a source, is collected and normalised, correlated in the SIEM, becomes an alert and then a case, is enriched automatically, is worked by an analyst, triggers an approved response if needed, and is closed. Its timestamps and disposition then feed the metrics.

**Decision logic.** The key decision sits with the analyst: is this real, and is the proposed action proportionate? SOAR can recommend and prepare, but disruptive actions pass through an approval gate. Low-risk, reversible actions, such as adding a tag or fetching context, can be fully automated.

**Technical interpretation.** Each arrow is a real integration: an agent configuration, a forwarder, an API key, a webhook. Each has credentials, a failure mode and a latency. The SIEM-to-case arrow, for example, is typically an API call; if it fails, alerts may be generated and never reach a human.

**Practical example.** At the fictional Banyan Microfinance, a Sysmon process-creation event on a finance workstation travels through the pipeline into the SIEM, where a rule for an Office application spawning a script interpreter fires. A case opens; SOAR adds the host's criticality and the user's role; the analyst confirms the activity is suspicious and approves host isolation through the EDR.

**Security implications.** The tools on this map hold extraordinary privilege: EDR can run actions on every endpoint and SOAR stores API keys for everything. They must be protected as critical assets, and their own health must be monitored.

**Key learning.** A SOC's capability lives in the arrows between its tools; draw the map, own every arrow, and check that each one is working.

## Following one alert across the map

The best way to understand the map is to follow a single alert across it, and the course lab kit makes that possible. The kit's dataset, `banyan_events.jsonl`, generated deterministically by `LAB_ASSETS/C08/make_dataset.py`, contains one fictional day of normalised events from four sources at Banyan Microfinance. The kit's teaching SIEM, `LAB_ASSETS/C08/minisiem.py`, loads them into SQLite (ingestion), keeps common fields as columns (normalisation) and runs saved searches and correlation rules. Its real output for the load and a source-count search is:

```terminal
$ python minisiem.py load
loaded 340 events
$ python minisiem.py search "SELECT source, COUNT(*) AS n FROM events GROUP BY source ORDER BY n DESC"
source | n
proxy | 284
sysmon | 33
windows | 13
vpn | 10
```

- `load` reads `banyan_events.jsonl` line by line, copies the common fields into columns of a table named `events` and keeps the original event as JSON in a `raw` column, which is how a real SIEM preserves the original record alongside the parsed fields.
- `search` runs any SQL query you supply against that table and prints the result with ` | ` separators; it plays the role of a SIEM's search language.
- A third command, `rules`, runs the kit's six saved correlation rules. You will use it from Module 3 onwards; this module does not reveal what it finds.

The source counts are already a tooling lesson. Proxy events outnumber everything else combined, which is typical: network and web telemetry is high-volume and cheap per event, while endpoint and identity events are fewer but richer. A SOC that sized its SIEM licence on endpoint logs alone would be surprised by its proxy volume, and one that dropped proxy logs to save money would lose its best view of data leaving the organisation.

Now place one of the kit's correlation rules on the map. Rule `R1 office_spawns_script` in `minisiem.py` looks for Sysmon process-creation events (event ID 1) whose parent image is `winword.exe` and whose image is `powershell.exe` or `cmd.exe`. The same logic is written as a Sigma rule in `LAB_ASSETS/C08/rk_office_spawns_shell.yml`, tagged with MITRE ATT&CK T1204.002 (User Execution: Malicious File) and T1059.001 (PowerShell). Following an R1 alert through the map:

1. **Telemetry source:** a Sysmon agent on a workstation records process creation with the parent and child image paths.
2. **Collection pipeline:** the event is forwarded and normalised into fields such as `host`, `user`, `image` and `parent_image`; in the kit, `make_dataset.py` has already done this, and `normalise_demo.py` shows how two raw formats are parsed into one schema.
3. **SIEM:** the correlation rule matches and produces an alert.
4. **Case management:** the alert becomes a case with a creation timestamp. This is where the MTTA clock from Lesson 7 starts.
5. **SOAR and context sources:** enrichment adds what a human needs to prioritise. In the kit, `triage.py` plays this role, adding asset criticality and the user's department and role from small built-in tables standing in for a CMDB and identity provider, then computing a priority score.
6. **Analyst:** Tier 1 validates, Tier 2 investigates the timeline in the SIEM, and the case is escalated if it is a true positive.
7. **Response actions:** if authorised, the host is isolated through the EDR and the user's sessions are revoked through the identity provider.
8. **Closure and feedback:** the case is closed with a disposition and evidence. `soc_metrics.py` style calculations measure how long it took, and any false positives feed rule tuning, which `test_rules.py` checks with known-bad and near-miss events.

Every one of these steps crosses an arrow on the map, and every arrow could fail. That is why the SOC lead's first question after a missed detection is not "why did the analyst miss it?" but "which arrow broke?".

## Step-by-step: building a tooling map for a SOC

A tooling map is a living document, not a one-off diagram. The following procedure produces one that is useful to analysts and defensible to auditors.

1. **Inventory every tool.** List every system the SOC uses or depends on, including the unglamorous ones: log forwarders, the paging service, the shared mailbox for user reports.
2. **Record each tool's function and data.** For each tool, note what it receives (inputs), what it produces (outputs) and in what format.
3. **Draw the arrows.** For every input and output, record the tool at the other end and the mechanism (agent, syslog, API, webhook, manual export). An output that goes nowhere is wasted; an input that comes from nowhere is a gap.
4. **Assign an owner to every tool and every arrow.** Integrations fall between teams. The SIEM team may own the SIEM and the endpoint team the EDR, but someone must own the connector between them.
5. **Define a health check for each arrow.** For a log source, "last event received less than N minutes ago"; for an API integration, "last successful call". Feed these checks into the SIEM or monitoring so that a silent failure becomes an alert.
6. **Record the failure impact.** For each tool and arrow, write what the SOC loses if it fails: "no endpoint process visibility for 2,000 workstations" is a sentence that gets budget approved.
7. **Mark coverage against assets.** Overlay the map with the critical assets from the CMDB. Which crown-jewel systems send logs, which have EDR, which are invisible?
8. **Review on change.** Update the map whenever a tool is added, replaced or reconfigured, and review it in full at least once a year and after every major incident.

A minimal inventory table for one row might look like this:

| Field | Example entry |
| --- | --- |
| Tool | Endpoint agent (Sysmon + forwarder) |
| Function | Records process, network and file events on Windows hosts |
| Inputs | Local operating system activity |
| Outputs | Normalised events to the SIEM over an encrypted channel |
| Owner | Endpoint engineering; connector owned by SOC platform team |
| Health check | Every host has sent an event in the last 60 minutes |
| Failure impact | No process-creation visibility; Office-spawns-script detections go blind |

## Common mistakes and misconceptions

**"Buying a better SIEM will fix detection."** Tools amplify process; they do not replace it. A SOC with unclear escalation paths, no asset inventory and untested rules will produce the same failures on a more expensive platform. Fix the map and the process, then choose tools to fill the gaps.

**Tool sprawl.** Organisations often accumulate overlapping tools, each with its own console, so analysts "swivel-chair" between six screens and copy data by hand. Every manual copy is a delay and a chance for error. Integrate into the case system or retire the duplicate.

**Treating the SIEM as a black box.** If nobody on the team can explain how an alert was produced, nobody can tell whether a quiet day is genuinely quiet. This is why the course teaches each function on a transparent script first.

**Ignoring platform health.** Silent failure is the default failure mode of telemetry. A source that stops sending events produces no alerts, and no alerts looks exactly like a safe day. Health checks must be explicit.

**Automating without approval gates.** A SOAR playbook that automatically disables accounts or isolates hosts on a single detection can cause an outage on a false positive, and an attacker who understands the playbook may even trigger it deliberately. Disruptive actions need a human approval step (Module 11).

**Over-privileged integrations.** Connectors are often created with administrator credentials "to make it work" and never reduced. Each integration should use its own service account or API key with the minimum permissions it needs.

**Forgetting people tools.** Paging, chat and out-of-band communication are part of the tooling map. If the escalation path depends on a single channel, it has a single point of failure.

## Security implications, detection and defence

SOC tools are among the most privileged systems in any organisation, and attackers know it. An EDR console can run actions on every endpoint; a SOAR platform holds API keys for the firewall, the identity provider and the EDR; the SIEM holds a searchable copy of the organisation's activity, including personal data. Compromising any of them gives an attacker either reach across the estate or the ability to blind the defenders.

Defending the SOC's own tools means:

- **Strong access control:** single sign-on with multi-factor authentication, separate administrative accounts, role-based access so that Tier 1 cannot change detection rules, and privileged access reviewed regularly.
- **Protected credentials:** integration keys stored in a secrets manager, scoped to minimum permissions, rotated, and never pasted into playbooks or tickets.
- **Monitoring the monitors:** the SOC's tools must log their own administrative activity to a place their administrators cannot quietly alter. Rule deletions, agent uninstallations, policy changes and new API keys are high-value detections.
- **Detecting attempts to blind the SOC:** attackers commonly try to stop logging. Windows Security event ID 1102 (the audit log was cleared) is a classic signal, and the course kit includes a teaching rule for it (`rk_security_log_cleared.yml`). Equally important is detecting the absence of expected events from a source that should be reporting.
- **Retention and integrity:** logs must be retained long enough for investigation and for legal obligations. In India, CERT-In's directions of April 2022 require service providers and other covered entities to maintain logs of their ICT systems for a rolling period of 180 days within Indian jurisdiction. Write-once or tamper-evident storage protects logs from an attacker who gains administrative access.
- **Data protection:** telemetry and case data contain personal data, so collection, access and retention should be minimised and justified in line with the DPDP Act 2023.

> [!CAUTION]
> Response actions are powerful. Isolating a host or disabling an account on production systems must only ever be done under the organisation's authorised playbooks and approval rules. In this course, every response action is discussed or simulated against synthetic data in your own lab.

## Best practices

- Maintain a **written tooling map** with an owner, health check and failure impact for every tool and integration.
- Make **case management the single source of truth**: every alert, escalation and decision is recorded there, not in chat.
- **Normalise early** into one schema so that rules, enrichment and hunts work across sources.
- **Automate enrichment freely, gate disruptive actions** behind human approval.
- Give every integration **least-privilege credentials** and log its use.
- **Alert on silence**: monitor every expected log source and integration for missing data.
- Protect SOC tools as **critical assets** with MFA, separate admin accounts and tamper-evident logging.
- **Review the map** after every major incident: the post-incident question "which arrow broke?" should update the map.

## Key takeaways

- A SOC's capability comes from the connections between its tools; a tooling map documents every tool, every data flow, its owner, its health check and its failure impact.
- The core categories are telemetry and collection, SIEM, EDR and NDR, case management, SOAR, context sources (TIP, CMDB, identity, sandbox) and communication channels.
- Case management is the single source of truth for every alert and the source of the timestamps behind SLAs and metrics.
- Automate enrichment, but put disruptive response actions behind human approval gates.
- Silent failure is the default failure of telemetry: monitor for missing data, not only for alerts.
- SOC tools are highly privileged and are targets themselves; protect them, log their administration and detect attempts to blind the SOC.
- The course lab kit maps each category to a transparent script: `minisiem.py` for the SIEM, `triage.py` for enrichment, `ioc_match.py` for intelligence, `test_rules.py` for detection testing, `evidence_export.py` for evidence, `hunt.py` for hunting and `soc_metrics.py` for metrics.
