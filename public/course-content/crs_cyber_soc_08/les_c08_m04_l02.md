## Introduction and conceptual foundation

Linux servers rarely have a desktop user. They are reached over SSH by administrators, by deployment pipelines and, on any server with a public address, by a constant stream of automated login attempts from the internet. Almost everything that matters about *who got in and what they were allowed to do* is written as plain text lines by a few programs: the SSH daemon `sshd`, the Pluggable Authentication Modules (PAM) framework, `sudo`, `su`, the login manager `systemd-logind` and the account tools `useradd`, `usermod` and `passwd`. Module 2 showed where those lines are stored (`/var/log/auth.log` on Debian and Ubuntu, `/var/log/secure` on Red Hat-family systems, and the systemd journal on both). This lesson is about reading them.

Linux authentication logs reward a different reading style from Windows events. There is no event ID and no structured Subject and Target section. Each line is a sentence written by one program, and the meaning is in the wording: "Failed password for invalid user admin" and "Failed password for admin" differ by two words and by an entire threat category. There is also no Logon ID. What ties a session's lines together is the **process ID** of the `sshd` process that handled the connection, and, once the session exists, the session number assigned by `systemd-logind`.

Three analytical problems dominate Linux authentication work.

1. **Separating background noise from targeted activity.** Every internet-facing SSH server receives automated guessing against names such as `root`, `admin` and `test` all day. It is almost never worth an alert by itself, and it can bury the few lines that are.
2. **Judging successes, not failures.** The interesting line is usually an `Accepted` line: from an unusual source, by an unusual method (a password where keys are the norm), or after a run of failures from the same address.
3. **Following what the session did with its privileges.** After login, `sudo` lines record which commands were run as root, and account-tool lines record new users and group memberships. Persistence on Linux often appears here first.

The kit's Banyan dataset contains no Linux hosts, so this lesson uses a short **illustrative** `auth.log` excerpt from a fictional server `web-01`, written for teaching with documentation IP addresses. The commands run against it are real, and the outputs shown are what those commands produce on that file. You can recreate the file from the listing and reproduce every result.

> [!IMPORTANT]
> The sample log is illustrative, not captured from a real system. Exact message wording varies between OpenSSH, PAM and sudo versions and distributions; always confirm the format on the systems you monitor before writing parsers or rules that depend on it.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| PAM | Pluggable Authentication Modules: the Linux framework that programs such as sshd, sudo, su and cron call to authenticate users and open sessions. `pam_unix` is the module that checks local passwords. |
| sshd | The OpenSSH server daemon. A parent process listens; each connection is handled by a child process with its own PID (named `sshd-session` on recent OpenSSH releases). |
| Pre-authentication (`[preauth]`) | The phase of an SSH connection before the user is authenticated. Lines tagged `[preauth]` describe connections that ended before login. |
| Invalid user | sshd's term for a user name that does not exist on the system. |
| Accepted | sshd's word for a successful authentication, followed by the method (`password`, `publickey`, `keyboard-interactive/pam`). |
| sudo | Runs a command as another user (usually root) if the sudoers policy allows; logs each command with the invoking user, terminal, working directory, target user and command line. |
| su | Switches user identity, typically to root, using the target account's password; logged through PAM. |
| systemd-logind | The login manager on systemd hosts; logs a numbered session for each login. |
| Journal | The systemd journal, a structured binary log that holds the same messages with extra fields (`_COMM`, `_PID`, `_SYSTEMD_UNIT`, `SYSLOG_IDENTIFIER`). |
| wtmp / btmp | Binary records of successful and failed logins, read with `last` and `lastb`. |

## Anatomy of an authentication line

A line in `auth.log` or `secure` written through the traditional syslog path has a fixed header followed by free text:

```text
Nov  3 06:53:05 web-01 sshd[2120]: Accepted password for deploy from 198.51.100.23 port 40188 ssh2
```

| Part | Example | What it tells you |
| --- | --- | --- |
| Timestamp | `Nov  3 06:53:05` | Local time of the host in the classic syslog format: no year and no time zone. Some configurations write ISO 8601 with an offset instead. |
| Host name | `web-01` | The system that wrote the line; essential once logs from many servers are merged. |
| Program and PID | `sshd[2120]` | Which program wrote the line and which process. The PID is the thread that ties one SSH connection's lines together. |
| Message | `Accepted password for deploy from 198.51.100.23 port 40188 ssh2` | The event, in the program's own wording: outcome, method, account, source address, source port, protocol. |

Two consequences follow for analysis. First, the timestamp must be interpreted: without a year or zone you need to know the host's time zone setting (`web-01` in this lesson runs in UTC) and the rotation date of the file to place a line in time correctly, which is why central collection that stamps a full time on receipt is so valuable. Second, the message is prose, so every search is a text pattern. A pattern that is too loose (`grep 'Failed'`) catches unrelated programs; one that is too tight misses a version that phrases things slightly differently.

On hosts where rsyslog is not installed (Debian 12, for example, no longer installs it by default) there is no `auth.log` at all and the journal is the only local record. The same messages are there, with structured fields that make filtering more reliable; the journal commands appear later in the lesson.

## Following an SSH session through the log

An SSH login is a conversation between the client and several programs on the server, and each program writes its own lines. Knowing which program speaks at each step tells you which lines to expect, which ones are missing, and how to join them.

When a client connects, sshd forks a child process for the connection; that child's PID appears on every sshd line about the connection until it ends. If the requested user does not exist, sshd writes `Invalid user NAME from ADDRESS port PORT` straight away. For each password attempt, sshd hands the check to PAM; on failure `pam_unix(sshd:auth)` may log an `authentication failure` line with the remote host in `rhost=`, and sshd logs `Failed password for NAME` (or `for invalid user NAME`) `from ADDRESS port PORT ssh2`. After too many failures on one connection (the `MaxAuthTries` setting, six by default) sshd drops it; otherwise the client gives up and sshd writes `Connection closed by authenticating user NAME ...` or `... by invalid user NAME ... [preauth]`.

On success sshd writes `Accepted METHOD for NAME from ADDRESS port PORT ssh2`, and for public keys appends the key type and fingerprint, which identifies *which* key was used. It then asks PAM to open a session (`pam_unix(sshd:session): session opened for user NAME(uid=N) by (uid=0)`), and `systemd-logind` registers a numbered session (`New session 57 of user deploy.`). At the end, sshd logs the disconnect and `session closed`, and logind logs `Removed session 57.` The session number is useful because logind uses it for everything the session does until it ends, and the journal tags later activity with it.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The sequence diagram shows one SSH password login from connection to disconnect and labels each step with the log line it produces. It explains why one login appears as several lines from different programs, and which identifier joins them: the sshd PID during the connection, the logind session number afterwards.

**Components.** There are four lanes from left to right. **SSH client** (slate, sub-labelled with the documentation address 198.51.100.23) is the remote party. **sshd[2120]** (blue) is the per-connection server process, its PID shown in the label because that PID appears on every line it writes. **PAM (pam_unix)** (violet) is the authentication and session framework, the policy point that checks the password and opens the session. **systemd-logind** (dark) is the login manager that records the session as a numbered, tracked object.

**Relationships and arrows.** Solid arrows are requests; dashed arrows are replies. The client sends "connect + user deploy" and then "password" to sshd. sshd sends "check password" to PAM, which replies "success". Labels that begin "logged:" mark the reply that writes a line to the log. sshd's reply to the client is "logged: Accepted password for deploy". sshd asks PAM to "open session" and PAM's reply is "logged: session opened for user deploy(uid=1001)"; sshd then sends "register session" to logind, whose reply is "logged: New session 57 of user deploy". The last three arrows show the end: the client sends "disconnect", sshd tells logind "session ended", and logind's reply is "logged: Removed session 57".

**Execution flow.** Read top to bottom: connection and user name, password check, acceptance, session opened, session registered, work happens (not drawn), disconnect, session removed. In the sample log the acceptance and session opening share the timestamp 06:53:05 and the disconnect lines share 07:04:51.

**Decision logic.** The branch not drawn is the failure path: if PAM had answered "failure", sshd would log `Failed password for deploy`, and either accept another attempt on the same connection or close it with a `[preauth]` line. If the user did not exist, sshd would log `Invalid user` before any password check, and PAM would never open a session.

**Technical interpretation.** The PID ties the pre-session and in-session sshd lines of one connection together, so `grep 'sshd\[2120\]'` reconstructs the connection. Once logind has a session number, the journal can attribute later activity to that login session as well.

**Practical example.** In the worked analysis, filtering on `sshd[2120]` returns exactly five lines: the acceptance, the session opening, the disconnect message, the disconnect itself and the session closing, giving the session's start, end and source without reading anything else.

**Security implications.** Because the lines come from different programs, a parser that only extracts sshd lines misses the logind session numbers, and one that only watches PAM misses the source address. Collect all of them, and alert on the `Accepted` line, not on the failures.

**Key learning.** An SSH login is several lines from sshd, PAM and logind; join them with the sshd PID and the logind session number, and read the `Accepted` line first.

## Reading the message families

### sshd: method, account, source

Every `Accepted` line answers three questions. **Method**: `publickey` means a private key was presented; `password` and `keyboard-interactive/pam` mean a secret was typed or supplied. On a server where administrators and automation use keys, a password acceptance is a deviation in itself. **Account**: is it a person, a service account used by automation, or `root`? Direct root logins should be disabled on most servers, so an accepted root login says something about both the activity and the configuration. **Source**: is the address one this account normally uses (the administrator's VPN range, the CI server), or new?

Failures are read by shape, exactly as with Windows 4625 events. `Invalid user` lines mean names that do not exist: internet scanners walk lists of common names (`admin`, `oracle`, `ubuntu`, `test`) and the result is noise unless a success follows. `Failed password for` a *real* account, especially one that only your organisation would know, from one source several times in a row, is targeted guessing (ATT&CK T1110.001). Failures against many real accounts from one source are a spray (T1110.003).

One logging behaviour can distort counts. rsyslog can compress identical consecutive lines into `message repeated N times: [ ... ]`, so a naive `grep -c 'Failed password'` undercounts a burst. Count in the SIEM from parsed events, or account for the repeat lines.

### sudo: who became root, and to do what

sudo writes one line per command:

```text
Nov  3 06:58:40 web-01 sudo:   deploy : TTY=pts/1 ; PWD=/home/deploy ; USER=root ; COMMAND=/usr/sbin/useradd -m -s /bin/bash backupsvc
```

The invoking account comes first (`deploy`), then the terminal (`pts/1`, an SSH pseudo-terminal), the working directory, the target user (`USER=root`) and the exact command line. This is one of the richest lines on a Linux system: it records not only that privilege was used but what for. Failures have their own wording: `N incorrect password attempts` when the user could not supply their own password, and `user NOT in sudoers` when policy does not allow the account to use sudo at all. The second is always worth a look, because legitimate administrators know whether they have sudo rights; an intruder on a low-privilege account often tries anyway (ATT&CK T1548.003, Sudo and Sudo Caching). Commands that start a shell (`COMMAND=/bin/bash`, `sudo -i`, `sudo su -`) are legitimate in many shops but end command-level logging: after them, sudo no longer records each command.

### Account tools, su and the noise

`useradd`, `usermod`, `groupadd`, `userdel` and `passwd` log through syslog when they change accounts: `new user: name=..., UID=..., shell=...`, `add 'NAME' to group 'sudo'` (or `wheel` on Red Hat-family systems), `password changed for NAME`. On a server managed by configuration management these lines appear rarely and in batches during deployments; an account created interactively from an SSH terminal (`from=/dev/pts/1`) outside a change is a deviation (ATT&CK T1136.001). `su` logs `session opened for user root(uid=0) by NAME(uid=N)`, which records who switched identity.

Much of a busy `auth.log` is routine: `CRON` opening and closing sessions for scheduled jobs, `systemd-logind` sessions, service accounts used by monitoring. Learn the routine lines on your servers so that you can filter them out of an investigation, but never delete them from collection.

## Normal and suspicious patterns

| Activity | Normal on a typical server | Deserves a look |
| --- | --- | --- |
| Invalid-user failures | Continuous low-rate noise from internet addresses | Only if a success follows from the same source, or if the names are internal and specific |
| Failures on a real account | Occasional, followed by success from the user's usual source | Repeated from one new source; many real accounts from one source |
| Accepted publickey | From known admin and automation sources, known key fingerprints | A new key fingerprint for an account; a new source |
| Accepted password | Rare or never on key-only servers | Any password acceptance on a key-only server; acceptance after failures |
| Root login | Disabled, so never seen | Any accepted root login |
| sudo commands | Administrators running service and package commands | Account creation, sudoers or SSH key changes, downloads piped to a shell, `user NOT in sudoers` |
| Account changes | Batches from configuration management | Interactive `useradd`/`usermod` adding to `sudo` or `wheel` |

## Triage of SSH failures

Faced with an alert about SSH failures from a source address, the analyst needs a quick, repeatable way to decide whether it is noise or the start of a case. The figure below shows the decision logic.

![Figure 4.4: Triage of SSH failures from one source](/assets/courses/cyber-08/v2/C08-M04-L02-F2.svg)

*Figure 4.4: Triage of SSH failures from one source. Two questions, asked in order, separate background noise from targeted guessing and from probable compromise.*

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The decision graph turns the patterns table into a triage path for SSH failures from one source. Its purpose is to stop two opposite mistakes: escalating every scanner on the internet, and ignoring the one source whose failures ended in a login.

**Components.** The start node, **SSH failures from one source** (slate), is the alert or hunt result. Two decision nodes (violet) ask the questions in order: **Any Accepted from this source?** and **Real accounts targeted?**. Three outcome nodes give dispositions: **Background noise** (green, record and suppress), **Targeted guessing** (orange, block the source and check the accounts) and **Probable compromise** (red). A final node, **Review the session** (dark), lists what to examine next: the sshd PID, sudo commands and account changes.

**Relationships and arrows.** From the start node an arrow goes to the first decision. Its "yes" edge leads straight to **Probable compromise**, because a success after failures is the incident regardless of the names tried. Its "no" edge leads to the second decision. From there, "no, invalid users only" leads to **Background noise**, and "yes" leads to **Targeted guessing**. **Probable compromise** leads to **Review the session**.

**Execution flow.** The question about success comes first because it is the cheapest test with the biggest consequence: one search for `Accepted` lines from the source address. Only when there is no success does the analyst spend time on the names and rates of the failures.

**Decision logic.** The second decision separates `Invalid user` lines (names that do not exist) from failures against real accounts. Real names imply knowledge of the organisation (a username format, a leaked list, a service account name) and turn noise into targeting, even without success.

**Technical interpretation.** Both questions are text searches keyed on the source address: `grep 'Accepted .* from ADDRESS '` for the first, and a count of `Failed password for invalid user` against `Failed password for` (without `invalid user`) for the second. In a SIEM they are filters on parsed fields: outcome, user validity and source.

**Practical example.** In the sample log, 203.0.113.50 tried `admin`, `oracle` and `ubuntu` (invalid) and `root` (real but disabled for login) with no success: noise, with root's presence noted. 198.51.100.23 failed three times as `deploy`, a real account name, and was then accepted: the "yes" edge, probable compromise, and the session review that follows is the worked analysis below.

**Security implications.** The graph assumes the source address is reliable. Attackers with many addresses can spread attempts so that no one source looks interesting, so the same questions should also be asked per *account*: did this account succeed from a source it has never used?

**Key learning.** Ask "did anything from this source succeed?" before anything else. A success after failures is a case; failures alone are noise or intent.

Thirty-eight lines are easy to read by eye, but a real server writes thousands a day, so the analysis is done with commands that scale. Work on a copy of the file in your own lab directory.

### Step 1: who failed, and from where

```terminal
$ grep 'Failed password' auth.log | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
      4 from 203.0.113.50
      3 from 198.51.100.23
$ awk '/Failed password/ { if ($9 == "invalid") print "invalid", $11, $13; else print "valid", $9, $11 }' auth.log | sort | uniq -c | sort -rn
      3 valid deploy 198.51.100.23
      1 valid root 203.0.113.50
      1 invalid ubuntu 203.0.113.50
      1 invalid oracle 203.0.113.50
      1 invalid admin 203.0.113.50
```

In the first pipeline, `grep -oE 'from [0-9.]+'` prints only the matching part of each line (`-o`) using an extended regular expression (`-E`), here the word "from" and the IPv4 address after it; `sort | uniq -c` counts identical lines; `sort -rn` orders by that count, numerically (`-n`) and in reverse (`-r`). The second command uses `awk`, which splits each line into whitespace-separated fields: in a failure line field 9 is either the user name or the word `invalid`, so the `if` picks the user name and source address from the right positions in each case and labels the account as valid or invalid.

Two different sources, two different shapes. 203.0.113.50 tried four names once each, three of which do not exist, a few seconds apart: a scanner's list. 198.51.100.23 tried one real, organisation-specific account three times on a single connection (PID 2101): targeting.

### Step 2: who succeeded, how and from where

```terminal
$ awk '/Accepted /{print $3, $7, $9, $11}' auth.log
06:41:12 publickey alice 192.0.2.10
06:53:05 password deploy 198.51.100.23
$ awk '/sshd\[/ && /(Failed|Accepted) /{ip=($9=="invalid")?$13:$11; if(/Accepted/) {print ip, "success after", f[ip]+0, "failures"} else f[ip]++}' auth.log
192.0.2.10 success after 0 failures
198.51.100.23 success after 3 failures
```

The first command prints time, method, account and source for each `Accepted` line. The second keeps a per-source failure counter (`f[ip]++`) as it reads failures in order and, at each success, prints how many failures from the same address preceded it: the "success after failures" test as a one-liner.

alice's login matches her baseline in every respect: key, usual source, no failures. deploy's login breaks it in three ways at once: a **password** instead of a key, a **source** that is not the CI server, and **three failures** first. Any one would justify a look; together they make this the first edge of the triage graph, probable compromise. The scanner from 203.0.113.50 never succeeded, so it is recorded as noise.

### Step 3: follow the session

```terminal
$ grep -F 'sshd[2120]' auth.log
Nov  3 06:53:05 web-01 sshd[2120]: Accepted password for deploy from 198.51.100.23 port 40188 ssh2
Nov  3 06:53:05 web-01 sshd[2120]: pam_unix(sshd:session): session opened for user deploy(uid=1001) by (uid=0)
Nov  3 07:04:51 web-01 sshd[2120]: Received disconnect from 198.51.100.23 port 40188:11: disconnected by user
Nov  3 07:04:51 web-01 sshd[2120]: Disconnected from user deploy 198.51.100.23 port 40188
Nov  3 07:04:51 web-01 sshd[2120]: pam_unix(sshd:session): session closed for user deploy
```

`grep -F` treats the pattern as a fixed string, so the square brackets need no escaping. The PID gives the session's boundaries: 06:53:05 to 07:04:51, under twelve minutes, ended by the client. Now ask what happened inside that window with root privileges:

```terminal
$ grep -E 'sudo: +[a-z_]+ : ' auth.log | awk -F' ; ' '{split($1,a," "); print a[3], a[6], $3, $4}'
06:58:40 deploy USER=root COMMAND=/usr/sbin/useradd -m -s /bin/bash backupsvc
06:59:12 deploy USER=root COMMAND=/usr/sbin/usermod -aG sudo backupsvc
$ grep -E 'useradd\[|usermod\[|userdel\[|groupadd\[' auth.log
Nov  3 06:58:40 web-01 useradd[2291]: new group: name=backupsvc, GID=1003
Nov  3 06:58:40 web-01 useradd[2291]: new user: name=backupsvc, UID=1003, GID=1003, home=/home/backupsvc, shell=/bin/bash, from=/dev/pts/1
Nov  3 06:59:12 web-01 usermod[2301]: add 'backupsvc' to group 'sudo'
Nov  3 06:59:12 web-01 usermod[2301]: add 'backupsvc' to shadow group 'sudo'
```

The first pipeline selects sudo command lines (the invoking user followed by a colon), splits them on the `" ; "` separator with `awk -F`, and prints the time and user from the header together with the target user and command. The second lists every account-tool line.

Five minutes after logging in, the `deploy` session used sudo to create a local account, `backupsvc`, with a login shell and home directory, and thirty-two seconds later added it to the `sudo` group. The `from=/dev/pts/1` in the useradd line matches the `TTY=pts/1` in the sudo line: the same interactive terminal. The deployment pipeline does not create users, and does not log in with a password from an unknown address. The name, like `svc_update` on Banyan's WS-104 in Lesson 1, imitates a service account. The pattern is the Linux counterpart of 4720 followed by 4732: create an account, give it administrative rights, keep a way back in (ATT&CK T1136.001 and T1098).

### Step 4: absence and context

What should be present if this reading is right? A new account intended for persistence will need a way to log in. The log shows no `passwd` line setting a password for `backupsvc`, and no further sudo commands. Two cautions apply before concluding "no password, so no access". An attacker can add an SSH public key to `/home/backupsvc/.ssh/authorized_keys` by writing a file, which writes nothing to `auth.log`; only file integrity monitoring or an auditd watch on those paths would record it (Module 2 covered auditd as a source). And a root shell started any other way would also escape sudo's command log. The absence statement for the case is therefore: "no password set for backupsvc is recorded in auth.log; key-based access cannot be excluded from this source."

Disposition: malicious. The deploy password must be considered compromised; the account and the new `backupsvc` account should be locked by the incident response team under the incident process, and the host's `authorized_keys` files, crontabs and recently changed files reviewed. The root cause findings are configuration: password authentication enabled on a key-only server, and unrestricted sudo for an automation account.

## The same questions in the journal

On systemd hosts the journal holds the same messages with structured fields, which allows filtering by program instead of by text pattern:

```bash
journalctl -u ssh --since "2026-11-03 06:30" --until "2026-11-03 07:30"
journalctl -t sudo --since today
journalctl _COMM=useradd -o json
```

`-u` filters by systemd unit: the SSH service unit is `ssh.service` on Debian and Ubuntu and `sshd.service` on Red Hat-family systems, so use the name your distribution uses. `--since` and `--until` bound the time window and accept absolute times or words such as `today` and `yesterday`. `-t` filters by syslog identifier, the program name in the classic header, here `sudo`. A `FIELD=value` argument matches any journal field; `_COMM` is the executable name recorded by the journal itself rather than claimed by the program. `-o json` prints each entry as one JSON object with all its fields, including the full timestamp, PID and host name, which is the form a collector forwards to the SIEM. Journal timestamps are stored with full date and time, so the year-and-zone ambiguity of the classic file disappears.

## Common mistakes and misconceptions

- **Alerting on every failure.** Internet-facing SSH produces constant failures. Alert on successes after failures, on targeted real accounts and on deviations in method and source.
- **Counting `Failed password` lines without reading them.** "for invalid user" changes the meaning entirely, and `message repeated` lines hide counts.
- **Ignoring the method.** `Accepted password` and `Accepted publickey` are different events for an account that should only use keys.
- **Treating the sudo log as complete.** A shell started through sudo, or a root shell obtained another way, runs commands that sudo never sees.
- **Assuming no `passwd` line means no access.** SSH keys are files; their creation is invisible in `auth.log`.
- **Reading timestamps without the host's zone.** Classic syslog lines carry neither year nor zone.

## Security implications, detection and defence

The detections that come out of this lesson are few and strong: an `Accepted` from a source that previously produced failures; any password acceptance for an account that normally uses keys; any accepted login as root; `user NOT in sudoers`; sudo commands that create users, change sudoers or touch SSH keys; and interactive `useradd` or `usermod` adding to `sudo` or `wheel`. Each depends on collecting `auth.log` or the journal centrally, quickly and with parsing that extracts user, source, method and command, because an intruder with root can edit or delete local text files.

Prevention closes most of the web-01 chain. Set `PasswordAuthentication no` and `PermitRootLogin no` in `sshd_config` on servers that use keys; restrict SSH to management networks or a bastion; give automation accounts sudo rules limited to the exact commands they need; and monitor `authorized_keys` files and sudoers with file integrity monitoring or auditd. Rate-limiting tools that block a source after repeated failures reduce noise but do nothing against a correct password, which is why the success is always the line that matters.

## Best practices

- Know each server's baseline: which accounts log in, from where and by which method, and which key fingerprints are expected.
- Triage failures by asking "did anything from this source succeed?" first.
- Reconstruct sessions with the sshd PID, then read sudo and account-tool lines inside the session window.
- Prefer the journal's structured fields, or SIEM-parsed fields, over raw text patterns for detections.
- Write absence statements that say which source was checked and what it cannot see.

## Key takeaways

- Linux authentication is recorded as text sentences from sshd, PAM, sudo, logind and the account tools; the wording is the meaning.
- The sshd PID joins a connection's lines; the logind session number tracks the session.
- Separate internet noise (invalid users, no success) from targeted guessing (real accounts) and above all from a success after failures.
- Read every `Accepted` line for method, account and source against the account's baseline.
- sudo and account-tool lines show what a session did with privilege; account creation plus group membership is the Linux persistence pattern.
- `auth.log` cannot see SSH keys written as files; state that limit when reporting absence.
