## Introduction and conceptual foundation

A web server is one of the few systems in an organisation that is deliberately exposed to everyone on the internet. Anyone, anywhere, can send it a request at any time, and most of the requests it receives are not from customers. Search-engine crawlers index it, uptime monitors poll it, automated scanners probe it for forgotten files and known weaknesses, and occasionally a person tries to make the application do something it was never meant to do. The web server writes down every one of those requests. Its logs are therefore the defender's most direct record of what the outside world tried to do to a public application, and of how the application answered.

This lesson teaches you to **read** that record as an analyst. Lesson 1 of this module worked through Windows events and Lesson 2 through Linux authentication logs; both describe what happened *on* a host. Web server logs describe what happened *at* a host's front door: each line is one HTTP request and one response. The new element is the content of the requests: you must recognise attempts to read files or alter database queries in encoded form, judge from the server's answer whether they achieved anything, and tell them apart from harmless requests that look similar.

Throughout the lesson we use the customer portal of Banyan Microfinance, the course's fictional company, at `portal.banyan.example`. The C08 lab kit contains no web server data (its dataset holds Windows, Sysmon, VPN and proxy events), so every access-log line here comes from a small **illustrative** sample written for this lesson with documentation addresses. The analysis commands were run against that sample, and their output is shown exactly as produced.

> [!NOTE]
> A web server log is not the same as the proxy log you met in Module 2. A proxy log records requests that *your users* make to other people's websites, on the way out. A web server log records requests that *other people* make to *your* website, on the way in. Lesson 6 of this module returns to proxy logs.

## Key terminology

| Term | Precise meaning |
| --- | --- |
| Access log | The web server's record of every request it handled: one line per request, written when the response is complete. |
| Error log | The web server's diagnostic log: start-up and configuration problems, denied requests, failures of modules or upstream applications. Not one line per request. |
| Common Log Format (CLF) | The original NCSA access-log layout: client, identity, user, time, request line, status and response size. |
| Combined Log Format | CLF plus two quoted fields at the end: the `Referer` and `User-Agent` request headers. The default in most Apache and nginx installations. |
| Request line | The first line of the HTTP request: method, path with query string, and protocol version, for example `GET /login HTTP/1.1`. |
| Status code | The three-digit HTTP response code (RFC 9110), grouped into classes 1xx to 5xx. |
| User agent | A free-text header in which the client describes itself. It is chosen by the client and proves nothing. |
| Referer | A header (spelled with one "r" in the standard) naming the page that linked to the requested resource. Also chosen by the client. |
| Percent-encoding | Representing a character as `%` and two hex digits, for example `%27` for an apostrophe and `%2F` for a slash, so that it can travel inside a URL. |
| Reverse proxy / load balancer | A system in front of the web server that receives the client's connection and forwards the request, so the web server sees the proxy's address unless it is configured to trust a forwarded header. |
| X-Forwarded-For | A request header in which proxies record the original client address. Any client can also set it, so it is trustworthy only when written by your own proxy. |

## Why web server logs matter to a SOC

Three properties make these logs valuable.

**They are the record of the attack surface.** Firewalls in front of a public web server must allow ports 80 and 443 to everyone, so firewall logs show only that connections happened. The access log shows what each connection asked for.

**They record the server's answer.** Every line contains the status code and the number of bytes returned. A request for `/.git/config` that received a `404` and 196 bytes is a failed probe. The same request receiving a `200` and 2,400 bytes means the repository configuration was handed over, which is a finding in its own right.

**They are high-volume and noisy.** A modest portal can write millions of lines a day, and a large share of them come from automation. Separating crawlers, monitors and background scanning from targeted activity is much of the skill.

There is also a regulatory reason to keep them well. The CERT-In directions issued in April 2022 under section 70B of the IT Act 2000 require organisations to maintain logs of their ICT systems for a rolling 180 days within Indian jurisdiction. Because the logs hold client addresses and sometimes personal data in query strings, the DPDP Act 2023 also applies to them.

## Anatomy of an access log line

Both Apache HTTP Server and nginx ship with the Combined Log Format as their usual default. In Apache it is defined with format directives:

```text
LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-agent}i\"" combined
```

In nginx the built-in `combined` format is defined with variables:

```text
log_format combined '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent"';
```

The two definitions produce the same layout. Here is one line from the illustrative portal sample:

```text
198.51.100.23 - - [03/Nov/2026:10:04:33 +0530] "GET /account/statement?month=10%27%20UNION%20SELECT%20NULL-- HTTP/1.1" 500 531 "-" "Mozilla/5.0 (X11; Linux x86_64)"
```

Reading it field by field:

- `198.51.100.23` is the **client address** (`%h` in Apache, `$remote_addr` in nginx): the address of whatever opened the TCP connection to the server. Behind a load balancer this is the load balancer, not the visitor.
- The first `-` is the **identity** field from the old RFC 1413 ident protocol. It is almost always `-`; nginx writes a literal hyphen.
- The second `-` is the **authenticated user** (`%u`, `$remote_user`). It is filled only for HTTP authentication handled by the web server itself (for example Basic authentication). Users who log in through the application's own login form do **not** appear here, which surprises many analysts.
- `[03/Nov/2026:10:04:33 +0530]` is the **time**, in the server's local time with its UTC offset. This server runs on Indian Standard Time; the line happened at 04:34:33 UTC. Module 2, Lesson 6 explained why you normalise to UTC before correlating.
- `"GET /account/statement?month=10%27%20UNION%20SELECT%20NULL-- HTTP/1.1"` is the **request line**: method, path including the query string, and protocol. It is logged as received, still percent-encoded.
- `500` is the **final status code** (`%>s`; the `>` asks Apache for the status after any internal redirects).
- `531` is the **response body size in bytes** (`%b`; a `-` means zero bytes). It excludes headers.
- `"-"` is the **Referer**: no referring page was sent.
- `"Mozilla/5.0 (X11; Linux x86_64)"` is the **User-Agent**: a short, generic browser-like string.

Decoded, the query string reads `month=10' UNION SELECT NULL--`. The apostrophe closes a string in a SQL statement, `UNION SELECT` asks the database to append the results of a second query, and `--` starts a comment that hides the rest of the original statement. The application answered with a server error. We will come back to what that answer means.

Microsoft IIS uses a different layout, the **W3C Extended Log File Format**: space-separated fields whose order is declared in a `#Fields:` header line at the top of each file, with times in UTC by default. The content is similar, but read each file's header rather than assume an order.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure lays the example access-log line out as a row of segments, one per field, so that you can see the Combined Log Format as a structure rather than a string. Analysts who know which position holds which field can read thousands of lines quickly and write parsing and search logic that does not break.

**Components.** From left to right the segments are: **Client address** ("198.51.100.23", top label `%h`), **Identity** ("-", `%l`), **User** ("-", `%u`), **Time** ("[03/Nov/2026:10:04:33 +0530]", `%t`), **Request line** ("GET /account/statement?month=10%27...", `"%r"`), **Status** ("500", `%>s`), **Bytes** ("531", `%b`), **Referer** ("-") and **User-Agent** ("Mozilla/5.0 (X11; Linux x86_64)"), both topped "Combined". The first seven, in blue, slate, orange and red tones, form the original Common Log Format; the last two, in violet, are the fields the Combined format adds. The request line is drawn widest because it is the longest and most interesting field, and the status is drawn in red because in this line it is the evidence that matters.

**Relationships.** The segments are positional: there are no field names in the log itself, only order. The request line and the two headers are wrapped in double quotes because they can contain spaces; everything else is space-separated. That is why the illustrative commands later in this lesson can use `awk '{print $9}'` for the status but must split on the quote character to extract the user agent.

**Execution flow.** The server fills these fields at different moments. Client address, time of arrival and request line are known as soon as the request is read; status and bytes only once the response has been sent. The line is written at the end, which is why a request that never completes (a client that disconnects mid-download) may be logged with a smaller byte count, and why the timestamp is the time the request was received.

**Technical interpretation.** Each field is under the control of a different party. The client address comes from the TCP connection and is hard to forge for a completed request. Status and bytes come from the server. The request line, Referer and User-Agent come entirely from the client, who can write anything. A good analyst weighs fields by who controls them.

**Practical example.** In the portal sample, the analyst reads this segment row for the 10:04:33 line and notes: an external client, no HTTP authentication, a query string carrying SQL syntax, a 500 status and a small, error-sized response, with a generic user agent and no referer. Each segment adds a fact; together they say "an injection probe reached code that failed".

**Security implications.** If an administrator changes the log format, every parser and saved search built on positions silently breaks; monitor for that. Because the request line is logged as received, attackers can use encoding to hide keywords from naive searches, so detection must decode before matching.

**Key learning.** Read a Combined Log Format line as nine positional fields, and trust each field only as far as you trust the party that wrote it.

## Status codes from the analyst's side

HTTP status codes are defined in RFC 9110. For a defender each class answers a different question about a suspicious request: was it served, redirected, refused, or did it break something?

| Code | Meaning | What it tells the analyst |
| --- | --- | --- |
| 200 OK | The resource was returned. | The request was served. For a probe of a sensitive path, this is the line that matters; check the bytes. |
| 206 Partial Content | Part of a resource was returned (range request). | Normal for media and resumable downloads; many 206s for one large file can indicate a download manager or bulk retrieval. |
| 301 / 302 | Redirect elsewhere. | Common after a login (`POST /login` then `302` to the account page) and for HTTP-to-HTTPS redirects. A 302 after a login attempt does not by itself prove success; read where the application redirects failures. |
| 304 Not Modified | The client's cached copy is still current. | Normal browser behaviour; zero body bytes. |
| 400 Bad Request | The server could not parse the request. | Malformed or deliberately mangled requests; often produced by scanners and by the server's own path normalisation rejecting traversal. |
| 401 / 403 | Authentication required / access forbidden. | Access controls working. Many 401s for one path from one source suggests password guessing against HTTP authentication. |
| 404 Not Found | No such resource. | Broken links, old bookmarks and, in bursts, content discovery: a client guessing paths. |
| 405 / 429 | Method not allowed / too many requests. | 429 shows rate limiting has triggered: a control firing, worth counting per source. |
| 500 Internal Server Error | The application failed while handling the request. | The input reached application code and caused an error. After an injection-shaped request, this is a strong prompt to read the error and application logs. |
| 502 / 503 / 504 | Upstream failure, unavailable, timeout. | Back-end or capacity problems; bursts can mark denial-of-service or a crashed application server. |

Two habits follow. First, always read **status and bytes together**. Error pages and "not found" pages tend to have a fixed size, so a run of `404 196` lines is one page repeated, and a line that breaks the pattern (a `200` with a much larger size for a path that usually fails) is the one to investigate. Second, remember that the status describes what the **web server** returned, not what the application did internally. An application that catches every error and returns a friendly page with `200` hides failures from the access log entirely; that is a logging weakness you should raise with the application owner.

## The error log

The error log is the server's diagnostic channel. It records start-up messages, configuration problems, requests the server itself refused, and failures talking to the application behind it. It is not one line per request, so it is far smaller, and that is its value: when the access log shows something unusual, the error log at the same second often explains it.

An nginx error log line for the probe of `/server-status` in our sample would look like this (illustrative):

```text
2026/11/03 10:04:14 [error] 2211#2211: *57 access forbidden by rule, client: 198.51.100.23, server: portal.banyan.example, request: "GET /server-status HTTP/1.1", host: "portal.banyan.example"
```

The fields are the local timestamp (no offset is written, so you must know the server's time zone), the severity in brackets, the worker process and thread identifiers, a connection number (`*57`), the message, and then key-value context: client, virtual server, request line and the `Host` header. "Access forbidden by rule" means an `allow`/`deny` rule in the configuration refused the request: the `403` in the access log was a deliberate control, not an accident.

For a `500` the web server's error log often says only that the upstream application returned an error. The detail lives in the **application log** (the framework's own log, or the database's error log). When the application is the target of an injection attempt, a database syntax error logged at the same moment as the access-log line is strong evidence that the input reached the query unsanitised, even though nothing was returned to the client. Make sure application and database logs are forwarded to the SIEM alongside the web server's, or this correlation is impossible.

## Who is really asking: addresses, proxies and user agents

### Client addresses behind proxies

Most production portals sit behind a load balancer, a content delivery network or a reverse proxy. The web server then sees every request coming from the proxy's address, and the access log's first field becomes useless for attribution unless the server is configured to take the real client address from a header such as `X-Forwarded-For`. Two errors are common. Some teams never configure it, so all traffic appears to come from two internal addresses. Others trust the header from anyone, so an attacker who adds `X-Forwarded-For: 192.0.2.1` to their requests appears in the log as that address. The correct design is to trust the header **only** when the connection comes from your own proxies, and to log both the connecting address and the forwarded address.

On an unfamiliar web log, first ask the platform team what the first field contains.

### User agents

The User-Agent header is whatever the client chooses to send. Browsers send long strings beginning `Mozilla/5.0`; command-line tools and libraries send their own names by default; well-behaved crawlers identify themselves and give a URL. Because it is self-declared, a user agent is **evidence about intent, never about identity**:

- A scanning tool's name in the user agent hints at automation, but anyone can copy or change it.
- A browser-like string proves nothing about a browser. In our sample the scanner sends the short string `Mozilla/5.0 (X11; Linux x86_64)`, which looks like a browser and is not one: it lacks the engine and version tokens real browsers send, and it requested no images, stylesheets or scripts.
- An empty user agent (`"-"`) is unusual for people and common for scripts, health checks and some API clients.
- A crawler claiming to be a major search engine can be verified by reverse DNS lookup of its address followed by a forward lookup of the name, as the search engines themselves recommend; a claim that fails the check is an impersonator.

Behaviour is more reliable than the header. Real browsers fetch a page and then its assets (stylesheets, scripts, images) within a second or two, send a Referer for those assets, and keep cookies. Automation tends to request pages without assets, at machine-regular intervals, with no Referer.

## Recognising scanning and injection attempts

Recognising an attack in a log needs a set of **shapes** and the habit of checking each against the server's answer.

### Content discovery

A content-discovery scan requests many paths the site does not have, looking for something left behind: environment and configuration files (`/.env`), source-control metadata (`/.git/config`), backups (`/backup.zip`), administration interfaces (`/admin/`, `/phpmyadmin/`), the login pages of popular content management systems the site may not even run (`/wp-login.php`), and server diagnostics (`/server-status`). In the log the shape is unmistakable: one source, a burst of `404`s within seconds, each for a different well-known path, usually with a fixed error-page size. It happens daily on any public server. The questions that turn background noise into a case are: did any of those paths answer `200`? Did the same source go on to do something else?

### Path traversal

Traversal attempts try to escape the web root by inserting `../` sequences into a path or parameter, aiming at files such as `/etc/passwd` on Linux or system files on Windows. Because servers normalise plain `../`, attempts are usually encoded: `..%2F`, `%2e%2e%2f`, or double-encoded `%252e%252e%252f`. In the sample, `GET /download?file=..%2F..%2F..%2Fetc%2Fpasswd` received a `400`. A `400` or `404` means the attempt was rejected or found nothing; a `200` with a response size similar to a system file is a likely compromise and an immediate escalation.

### Injection into parameters

Injection attempts place syntax from another language into a parameter so that the application passes it on to a database, a shell or a browser. In logs you see characteristic fragments, nearly always percent-encoded:

- **SQL injection**: an apostrophe (`%27`), keywords such as `UNION SELECT`, always-true comparisons such as `OR '1'='1'`, comment markers (`--`, `%23`), or time-delay functions.
- **Cross-site scripting**: script tags and event-handler attributes, usually encoded as `%3Cscript%3E` and similar.
- **Command injection**: shell metacharacters such as `;`, `|` and `$(` in parameters that should hold a number or a name.

The access log can only show injection in the **URL**. Data sent in the body of a `POST` request, which is where login forms and most API calls put their parameters, is not logged by default (and should not be logged wholesale, because it contains passwords and personal data). For that you rely on a web application firewall's logs, application-level logging of rejected input, or the database's error log.

The same suspicious request can be noise or an incident depending on what came back. The figure below turns this into the triage logic an analyst applies to any suspicious line.

### Visual Walkthrough & Architectural Breakdown

**Purpose.** The figure is a decision graph for one suspicious access-log line. It exists because analysts tend to react to the request (it looks alarming) when the deciding evidence is the response. It encodes the order of questions that separates background probing from a real compromise.

**Components.** The orange starting box is **Suspicious request in access log** ("scan path, traversal or injection marker"). Two violet decision boxes follow: **Known authorised source?** ("own scanner, monitor, crawler (verified)") and **What did the server return?**. Three outcome classes hang from the second: blue **4xx: 400, 403, 404** ("rejected or not found"), orange **5xx: 500, 502** ("input reached code that failed") and red **2xx / 3xx** ("the request was served"). The end states are green **Benign: document and tune**, slate **Record; watch source and volume**, orange **Read error and app logs** ("same second, same client") and dark **Escalate as possible compromise** ("bytes, follow-on requests, host").

**Relationships and arrows.** Every arrow points forward through the analyst's reasoning. From the authorisation check, the arrow labelled "yes" leads to the benign outcome and "no" leads to the status question. Each status class has its own arrow to an action. The orange error-log box has an arrow labelled "evidence it reached the query" into the dark escalation box, and the red served class goes straight there.

**Execution flow.** First rule out sources you know about, then read the status, then act. Authorisation comes first because a scheduled scan by your own vulnerability team produces exactly the same lines as an attacker's.

**Decision logic.** A 4xx means the control or the absence of the resource stopped the request; it is worth recording and counting, but it is not an incident alone. A 5xx means the input reached application code; it is a reason to look deeper but not yet proof. A 2xx or 3xx means the server answered successfully, and for a sensitive path or an injection-shaped parameter that is presumed serious until shown otherwise.

**Technical interpretation.** The status classes stand for layers of the stack: 4xx usually comes from the web server or framework before the business logic runs, 5xx from inside the application, and 2xx from a completed response. The decision graph is really asking "how deep into the system did this input get?".

**Practical example.** In the sample, 198.51.100.23's six 404s and one 403 go to the slate box. The traversal attempt's 400 joins them. The two SQL-shaped requests with 500 go to the orange box: the analyst opens the application and database error logs for 10:04:33 and 10:04:35. The same source's later `GET /api/v1/branches` with `200` is a public endpoint, but its timing (directly after the probes) means it is included in the case.

**Security implications.** A SIEM rule that alerts on every injection pattern will fire all day on a public site; one that alerts on injection patterns *with* 2xx or 5xx responses is far more useful. Unknown sources should never be assumed authorised: verify the scanner's address against the vulnerability team's schedule.

**Key learning.** Judge a suspicious web request by the server's answer, read in the order: authorised source, status class, then the deeper logs.

## Worked example: ten minutes of the portal's access log

The illustrative sample holds 23 lines written by the portal between 10:02 and 10:05 IST on 3 November 2026. Standard command-line tools show the method; Lesson 7 does the same in SIEM queries. The first three lines are an ordinary customer visit:

```text
203.0.113.14 - - [03/Nov/2026:10:02:11 +0530] "GET / HTTP/1.1" 200 5120 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:132.0) Gecko/20100101 Firefox/132.0"
203.0.113.14 - - [03/Nov/2026:10:02:12 +0530] "GET /static/app.css HTTP/1.1" 200 18432 "https://portal.banyan.example/" "Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:132.0) Gecko/20100101 Firefox/132.0"
203.0.113.14 - - [03/Nov/2026:10:02:30 +0530] "POST /login HTTP/1.1" 302 - "https://portal.banyan.example/" "Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:132.0) Gecko/20100101 Firefox/132.0"
```

This is what normal looks like: a page, then its stylesheet one second later with the page as Referer, then a login form submitted as `POST` and answered with a redirect. A full browser user agent is consistent throughout.

### Step 1: the shape of the responses

```terminal
$ awk '{print $9}' access.log | sort | uniq -c | sort -rn
     10 200
      7 404
      2 500
      1 403
      1 400
      1 304
      1 302
```

`awk '{print $9}'` prints the ninth space-separated field, which in the Combined format is the status (the request line counts as three fields: method, path, protocol). `sort | uniq -c` counts identical values and `sort -rn` orders them by count, highest first. Seven 404s and two 500s in three minutes is worth a closer look; on a busy site, compare with previous days.

### Step 2: who is receiving the errors

```terminal
$ awk '$9 ~ /^4/ {print $1}' access.log | sort | uniq -c | sort -rn
      8 198.51.100.23
      1 192.0.2.10
```

The condition `$9 ~ /^4/` keeps only lines whose status begins with 4, and `{print $1}` prints the client address. One source holds eight of the nine client errors. The single 404 for `192.0.2.10` is the crawler following an old link (`/branches/old-office`), a typical benign 404.

### Step 3: who the clients say they are

```terminal
$ awk -F'"' '{print $6}' access.log | sort | uniq -c | sort -rn
     11 Mozilla/5.0 (X11; Linux x86_64)
      4 Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:132.0) Gecko/20100101 Firefox/132.0
      3 Mozilla/5.0 (compatible; ExampleBot/2.1; +https://bot.example/)
      3 HealthCheck/1.0
      2 Mozilla/5.0 (Linux; Android 14) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/130.0 Mobile Safari/537.36
```

`-F'"'` makes the double quote the field separator, so field 6 is the text inside the third pair of quotes: the user agent. The busiest client is the short, generic string, all eleven of its lines from 198.51.100.23. `HealthCheck/1.0` belongs to Banyan's uptime monitor at 192.0.2.200, which requests `/health` once a minute and receives a two-byte answer; it is the most regular source in the log, and it is benign.

### Step 4: injection and traversal markers

```terminal
$ grep -Ei '%27|union|%2e%2e|\.\.%2f|\.\./' access.log | awk '{print $1, $7, $9}'
203.0.113.52 /search?q=O%27Brien 200
198.51.100.23 /download?file=..%2F..%2F..%2Fetc%2Fpasswd 400
198.51.100.23 /account/statement?month=10%27%20UNION%20SELECT%20NULL-- 500
198.51.100.23 /account/statement?month=10%27%20OR%20%271%27%3D%271 500
203.0.113.52 /static/app.js 304
```

`grep -Ei` searches case-insensitively with extended regular expressions for an encoded apostrophe, the word `union`, or encoded and plain traversal sequences; `awk` then prints the client, path and status. Five lines match, and two of them are false positives worth studying:

- `/search?q=O%27Brien` is a customer searching for the surname O'Brien. Apostrophes are part of real names and addresses; a rule that alerts on `%27` alone will alert on customers.
- `/static/app.js` matched because `grep` searched the **whole line**, and this line's Referer was the O'Brien search page. Matching must be done on the right field, decoded.

The three remaining lines are the probes from 198.51.100.23: traversal rejected with `400`, and two SQL injection attempts (`10' UNION SELECT NULL--` and `10' OR '1'='1`) on the statement parameter, both answered with `500` and a 531-byte error page.

### Step 5: the source's whole story

In order, 198.51.100.23's eleven lines read: seven discovery paths in three seconds (all `404` except `/server-status`, refused by rule), one traversal attempt (`400`), two injection attempts (`500`), then the public API (`200`, 1,874 bytes), all without a Referer or any assets.

The analyst's conclusion: an automated probe of the portal by an unknown external source, with no evidence of success in the access log, and **one open question**: the two 500s. The next action is to pull the application and database error logs for 10:04:33 to 10:04:35. If they show a syntax error, the statement page builds its query from the parameter unsafely; that is a vulnerability to fix even though this attempt returned nothing, and it should go to the application team as a priority. The source address is then searched across the other logs in the SIEM.

> [!IMPORTANT]
> The analyst in this example investigates by **reading logs** of requests other people sent. Reproducing the requests against the portal to "check" the vulnerability is testing, which requires written authorisation and belongs to the application security team under its rules of engagement, never to an analyst acting on their own initiative.

## Benign look-alikes

Most alarming-looking lines in a web log are harmless.

| Looks like | Usually is | How to tell |
| --- | --- | --- |
| Burst of 404s from one source | A crawler or a user following stale links; a broken page referencing a missing asset | Paths are real site paths, often with a Referer from your own site; the same 404 from many different clients points to a broken link |
| Regular requests every N seconds | Uptime monitoring, load-balancer health checks | A single fixed path (`/health`), tiny responses, a known source address agreed with operations |
| `%27` or `--` in a query | Names, addresses, product codes, pasted text | Appears in search or form fields, from clients with full browsing behaviour; no SQL keywords around it |
| Many requests with an unfamiliar bot user agent | A legitimate crawler, partner integration or SEO tool | Fetches `robots.txt` first; verifiable by reverse and forward DNS; respects disallowed paths |
| Discovery paths from one address | Your own vulnerability scanner or an authorised penetration test | The address and window match a scan schedule or a signed authorisation; confirm, do not assume |
| Spike of 5xx | A deployment or back-end outage | 5xx across all clients and paths at once, not one source; matches a change record |

## Common mistakes and misconceptions

- **"The user field shows who logged in."** It shows only users authenticated by the web server itself. Application logins appear nowhere in the access log; you need the application's own authentication log.
- **Treating the first field as the visitor.** Behind a proxy it is the proxy, and a trusted `X-Forwarded-For` may be the attacker's invention if trust is misconfigured.
- **Alerting on the request alone.** A rule for "SQL keywords in URL" produces thousands of alerts a day on a public site. Combine pattern, status and source behaviour.
- **Searching encoded text with plain keywords.** `UNION SELECT` written as `UNION%20SELECT`, `UNION/**/SELECT` or with mixed case will defeat a naive search. Decode, normalise case, then match.
- **Forgetting the body.** No injection in the access log does not mean no injection: POST parameters are not there.

## Security implications, detection and defence

From the defender's side, web server logs support three kinds of detection:

1. **Behavioural rules**: one source producing many distinct 404 paths in a short window (content discovery); many 401s on one path (password guessing against HTTP authentication); a sudden rise in 5xx from one source (input reaching failing code); a sensitive path such as `/.git/` or `/.env` answering `200` from any source (a misconfiguration being exploited, or about to be).
2. **Pattern rules on decoded fields**: traversal sequences and injection keywords in the decoded path and query, scoped to parameters that should never contain them, and raised in severity when the status is 2xx or 5xx.
3. **Correlation**: a source that probed the portal and then appears in VPN or firewall logs, or a probe followed by new processes started by the web server account on the host.

Defensive controls that make the logs more useful and the attacks less effective:

- Put a **web application firewall** in front of public applications and forward its logs; it sees request bodies the access log does not.
- Configure **real client IP** handling correctly, with trust limited to your own proxies, and log both addresses.
- Remove what discovery scans look for: no `.git` directories, environment files, backups or diagnostic pages in the web root; restrict `server-status` and administration paths to internal addresses.
- Fix injection at the source with parameterised queries and input validation; the log tells you where to look, it does not fix anything.
- Apply **rate limiting**, and log its decisions (429s).
- Forward access, error, application and database logs centrally and retain them for at least 180 days.

## Key takeaways

- Access logs record one line per request in a positional format; the Combined Log Format adds Referer and User-Agent to the Common Log Format.
- The request line, Referer and User-Agent are written by the client; status and bytes are written by the server. Weigh evidence by who controls the field.
- Read suspicious requests through the server's answer: 4xx rejected, 5xx reached code and needs the error and application logs, 2xx served and needs escalation.
- Scanning looks like bursts of 404s for well-known paths; traversal and injection look like encoded syntax in parameters. Decode before matching.
- Apostrophes in names, crawler 404s, health checks and authorised scans are the everyday look-alikes; rule them out with evidence, not assumption.
