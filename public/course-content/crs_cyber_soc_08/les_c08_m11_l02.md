## Introduction

A security alert is a signal to investigate. A case is the durable record of an investigation, including its evidence, decisions and assigned work. The distinction matters when a SOC receives several signals about the same risk. Keeping one case for the investigation lets several analysts contribute without losing the evidence behind each alert. TheHive provides this case-centred workspace. Cortex can run analyses against observables or execute approved actions through configured responders. A useful integration makes each result reviewable and uses the case to maintain decision authority.

This lesson describes the roles of the components and uses a paper workflow. No tenant, credentials or active connector is needed. Product screens and available integrations vary by release and configuration. Use the vendor's documentation for the version your team operates. Preserve the design goals across those differences: each source object is identifiable, each action has an authorised owner, and each reported result is backed by observable evidence.

## Model the investigation in TheHive

An **alert** originates in a source such as a SIEM, endpoint tool or reporting workflow. Store the external source, its stable reference, observed time and a short reason it was forwarded. A duplicate delivery can be associated with the original rather than opened as a second unrelated investigation. A new alert about the same asset may still be different evidence. Require a correlation reason before grouping. Record the source alert reference when analysts escalate it or add it to a case, rather than replacing alert history with a case identifier.

A **case** has an owner, scope, status and a set of tasks or decisions. It describes the incident being investigated or the question being resolved. Attach or reference the evidence that supports its conclusions. For example, a suspicious network request from a device and a separate high-priority authentication event can be managed under one incident lead while retaining their individual evidence and assignments. A case label should not overstate linkage. Treat ?under the same lead? as a coordination decision and ?same actor? as a finding that requires evidence.

An **observable** is a typed value relevant to an investigation, such as an address, hostname or file digest. A value may be entirely legitimate. The case should preserve who observed it, when and in which source, and any classification reached later. Do not treat every observable as an indicator of compromise. Several sources may report the same hostname with different scope, time or confidence. A meaningful record carries that context, and an analyst decides what it is useful for. Where the exact value is sensitive, restrict it or refer to the approved evidence store instead of copying it into broad notifications.

A **task** is assigned work with a completion criterion. An endpoint investigation task might request confirmation of a device's state and the exact source used. Its closure should include an observation or report pointer. A task log can show notes over time and name the reviewer. A case may have a closed request for mail scope and a pending identity verification at the same time. Treat each task state as its own fact before deciding the overall case status.

## Understand what Cortex adds

Cortex **analyzers** derive information about observables through configured services. A case analyst might select an internal service that recognises the digest of a known training file. An analysis report records data from that operation, such as which source returned a match and when. Review the configuration and data-handling terms before sending an observable anywhere. ?Read-only? describes the action's effect on a source system; it does not mean the tool sends no data. A lookup can disclose an indicator or context to the provider. Start with an approved internal source when it can answer the question.

Cortex **responders** are configured actions invoked against supported case objects. Their capabilities depend on the responder and integration. An action can be as limited as creating or updating a review task, or it can request protection from another service. The important distinction is that a response may have side effects. A green result from an integration is evidence about that execution. Confirm what the target service actually did. The team should be able to tell request acceptance, effective protection and independent verification apart.

Give the connection and actor only the permission needed for the step. A team that routinely enriches observable values does not need write access to all cases or asset controls. Use separate roles where the platform supports them. Protect credentials using the organisation's managed mechanism, and do not copy them into a case note or exercise file. Use sample identifiers in training. When a high-impact change is proposed, record the approval for the exact action and scope. Context such as ?incident lead approved this case? is not a universal permission to operate every responder.

### Visual Walkthrough & Architectural Breakdown

The first box is an external alert. It supplies evidence references and a reason for review. It may be linked with an existing case if the analyst can substantiate the relationship. Otherwise the case system holds a new draft or keeps the alert in triage. In either path the link to the original origin remains reviewable. The second box shows the case structure: case ID, assigned tasks and observed values. The case owner decides the investigation scope and which questions to ask. The next box is a typed observable selected from that case. It contains the essential value plus a reference to the original record, rather than an entire raw message.

The analyzer box represents a configured task that can return contextual data. Its report flows back to the case and should preserve a result and its provenance. A classification source might return ?not seen? or might be unavailable. Those outcomes support different decisions. The analyst can compare them with independent case evidence and choose whether to seek another source. Approval occurs after that interpretation where a protective change is proposed. The responder box represents an optional action against a specifically named case object or service under the approved configuration. Its outcome also flows back to the case.

For a training example, an internal analyzer connects a file digest with a previously reviewed document. The report states that the byte sequence matches the reviewed item, and the case analyst checks when and where that earlier analysis occurred. The finding does not establish that the document was executed here. The endpoint owner may be asked to verify a process relationship through a task. If a protective change becomes appropriate, the lead approves its scope and the responder records the result. A later analyst should be able to find the original alert, relevant observable, exact analyzer report, approval and verified outcome without having to reconstruct conclusions from unrelated notifications.

## Read an analysis report critically

A report describes a run. Look for the submitted observable, its type and normalised value, the configured analyzer, the observation time and the result source. A digest report may describe exact bytes while a domain report may refer to a general name with varied paths and tenants. A source might report confidence, age or limits of collection. Avoid carrying a label into the case without explaining which part of the evidence applies. The output of a low-confidence search can justify additional analysis, but it does not replace what the SOC knows about the affected account or endpoint.

Define outcomes for success, no-match, partial, unavailable and failure. A service might complete a search and return no record. That outcome is different from timing out before it searched a source. Some analyzers depend on several services and can return a valid result from one while another is unavailable. Preserve coverage in the report summary. For example, an analyst can say ?internal historical index returned no exact digest, and the permitted second source was unavailable.? That sentence lets the lead decide whether further investigation is needed and avoids false reassurance.

Keep historical results and current interpretation distinct. A domain may have been associated with suspicious activity six months earlier but now refer to a different service. The specific match and its timestamp remain evidence. The conclusion about the present case may be low confidence. The case note can say what new context would increase confidence and assign a next check. This helps the next analyst detect both stale intelligence and a repeated incident without erasing the history.

## Control a responder request

A reviewable responder request states the action, exact object, allowed scope, approval, intended effect and evidence needed to confirm it. If a responder operates on a case, verify whether that config changes the case, a particular observable or an external service. Selecting the right case does not by itself select the right target. The responder should be able to identify the intended object before taking action. When scope changes after approval, require new authority for the new request and preserve the earlier decision.

Trace results into the target system when possible. A responder may confirm that it submitted a task successfully. The case then contains a task reference, which can be compared with its status in the owning service. That is stronger than relying on a line in a log saying the responder completed. If a change is missing, verify the actual target and look for a failed or pending result. Do not retry a state change merely because the client did not receive the success response. First reconcile whether it already took effect.

A denial, cancellation or expiry is an expected result if the action is not authorised. Record the reason and the eligible next owner. If the underlying incident remains urgent, route it through the approved emergency process. Define who can use that route and what they need to document. A default path that treats ?no response received? as permission shifts authority from the responsible lead to a timeout, and is unsuitable for actions requiring approval.

## Worked paper case

Consider a fictional case H-17. The SIEM reports an uncommon attachment reference on a payments workstation. The alert includes the source ID, an observed time and a digest provided by an approved static pipeline. The analyst opens a case and adds the digest as a typed observable. The next task is to compare it with prior internal reports. A simulated analyzer returns a historical match whose prior case assessment was benign. The current workstation still shows an unusual process relationship. The analyst documents the digest match as evidence about the artifact and the endpoint observation separately. The next responder request should be an internal investigation task, rather than a decision that the entire event is harmless.

Now add a simulated duplicate alert. It has the same stable source ID and receipt intent, so it should link to H-17 without triggering the same task again. Add a third valid alert with a different source ID but the same digest. It may be new evidence even though the digest can use a cached report. Keep its source context and ask whether it belongs to H-17. The exercise shows that alert deduplication and analysis caching use different keys and have different purposes. A valid cache hit does not remove the need to account for the new alert.

Finally, suppose the incident lead approves the creation of a restricted case task and the responder records success. In the receiving case, verify the task ID, assigned owner and intended case. If the task exists twice, correct the repeat behaviour before using the same workflow again. If the task is missing, record the result as unresolved and investigate the scope and target rather than telling the incident lead that work was assigned. The workflow result is one piece of evidence about a change, while the case and target state show whether the intended change was achieved.

## Team design review

During a review, list which roles can view observables, run analyzers, approve responders and examine result records. Ask which data goes to each service and which cases can use the connection. Check one example where an outside partner supplies restricted information. The analyst should be able to describe a permitted path that records the value appropriately and either uses approved in-house services or requests a decision. Permissions should survive staff movement and changes to a case's audience. Examine valid configuration, not the owner's assertion that a workflow is rarely used.

Test two linked cases with one common observable. One case may have a different disclosure obligation or confidentiality restriction. Do not assume a connector may move details between the cases just because the value matches. Record the specific authority or reuse an independently authorised report. If the workflow cannot identify that difference, prefer a smaller set of read-only actions while the design is corrected. This review is also an accessibility and clarity check. A reviewer should be able to read the result status without relying on icon colour, and the meaning of the result should survive a shift handoff.

## Evaluate a handoff before expanding the connection

Before connecting a new analyzer, ask which data it receives and what its result can establish. A generic similarity lookup might cluster values and offer hints about context. A precise internal match can support stronger linkage to a known record. Neither should automatically change case scope. Include both a positive match and a known false association in acceptance tests. Confirm that an analyst can inspect the submitted input, identify the source of the result, and retain disagreement alongside other evidence.

Consider two cases handled by different teams. A historical analysis exists in one case and a newly reported digest matches it in a second. Use the result only if its permitted audience and relevance support reuse. An analyst can request a restricted reference or perform an approved minimal lookup without copying the first case's employee information. Test whether someone permitted to see the new case can infer private details through the result or linked task. A workflow that respects case permissions should not widen them through a convenient integration.

Give each responder a clear operating record. When a task-creation step succeeds, record the responder's identity, action time, operating case and the new task reference. When a higher-impact operation is simulated, record the proposed effect and its evidence rather than testing against a real control. A missing audit field can be a release blocker if it prevents verification of the exact target. The review should distinguish a product's capability from the organisation's authority to use it in a particular case.

## Key takeaways

- Link alerts and observed values to a case with owners and evidence.
- Read analyzer results in their source and time context.
- Bound each responder action and verify the effect where it occurs.
- Keep case, workflow and service records traceable across shifts.
